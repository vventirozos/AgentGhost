How it works

What it can do

Ghost has around thirty-five tools. You never pick one — you describe what you want and it chooses. This page is about what's actually possible.

Things you can ask for

Run code and work with files

Ghost can write a script, run it, read the output, and fix it when it breaks. It can read your files, search across them, and write new ones. All of it happens inside a Docker container that shares one directory with your machine.

You can also ask it to keep state between steps — variables, dataframes, a loaded model — so a long analysis works like a notebook rather than restarting each time.

The sandbox is a real boundary. Ghost cannot see or touch files outside the shared directory, and it cannot stop, start or reach a process you're running on your own machine. If you ask it to restart your server, it will tell you to do it yourself. That's not a limitation to work around — it's the point.

Look things up on the web

Plain search for simple facts, and a deeper mode that pulls several sources and writes up what they say. All of it goes over Tor.

One practical thing worth knowing: use plain keywords. The search backends Ghost reaches over Tor don't support site:, quoted phrases, or AND/OR. Including them returns nothing at all. To bias toward a source, name it as a keyword — "python asyncio docs", not "site:python.org".

Search Tor hidden services

Ordinary web search can't reach .onion sites — the scraper backends Ghost queries simply don't index them. So there's a separate path that queries the dedicated onion search engines (Ahmia, Torch, Haystak and others) and parses their result pages. One tool returns a ranked list of services; another fetches and synthesises the pages behind them.

Two design details, because they're what makes this work at all:

  • Every retry takes a different route. Whether an onion engine answers you depends on which Tor exit you happen to be using — the same query can fail and then succeed with no change but the circuit. So each attempt folds its number into the proxy credentials, which forces Tor to build a fresh circuit rather than reusing the one that just failed.
  • Engines that share an index count once. Some endpoints are different front doors onto the same underlying search index — a clearnet mirror and an onion address, for instance. Each engine is tagged with which index it serves, so when a result appears in several places, corroboration only counts independent sources instead of the same index reached two ways.

The engine list is configuration, not code (GHOST_ONION_ENGINES), and deliberately wide — onion endpoints rotate and die far more often than clearnet ones, so breadth beats betting on any single engine.

Expect empty results, and don't trust what you get. Zero results is a normal outcome here, not an error — it usually means the engines were unreachable from your current exit, and retrying the same query verbatim won't help. Ghost is told to drop to fewer keywords or fall back to normal search instead. And everything returned is an unverified hidden service: the agent is instructed to treat it as uncorroborated and say so, rather than reporting it as fact.

Drive a real browser

For pages that need clicking, typing and logging in rather than just reading. The browser runs inside the sandbox, so it can reach the internet through Tor and any service the sandbox itself is hosting — but not the rest of your network.

Read documents, PDFs and recordings

Hand it a file and it goes into memory as searchable passages. Audio and video are transcribed locally first, and each passage keeps its timestamp — so you can ask "what did they say about pricing?" and get an answer that points at the moment in the recording.

You don't need to ask it to write transcription code. It has this built in, and asking for a script instead gets a worse result.

Look at images

Screenshots, diagrams, photos, PDF pages. Useful for "why does this look wrong?" — including checking its own work when it has generated an image or built a web page.

Keep track of ongoing work

Projects are a durable to-do structure: tasks, dependencies, and status that survive restarts. This is how Ghost handles work that spans weeks rather than one conversation, and how it answers "where are we on X?" honestly instead of guessing.

Do things on a schedule, or when something happens

Two different shapes here, and the distinction is useful:

Scheduled

Fires on a clock. "Every morning at nine, summarise what changed." Standard cron syntax or a plain interval.

Cron times are UTC. Convert first if you want a local time.

Reactive

Fires on a condition. "When errors show up in the deploy log, investigate." Ghost polls a shell command and acts the moment it first succeeds.

Edge-triggered — it won't spam you while the condition stays true.

Query a Postgres database

Ghost has a dedicated database tool rather than making it write connection code by hand. Point it at a database and ask questions in English.

Tell you about itself

Ghost can report what it's been doing, what it has learned, what it's unsure about, and what it thinks is broken in its own tooling. This isn't the model improvising — these read from real stored records. Worth asking after a long stretch of unattended running.

How it decides which tool to use

Each tool carries a description telling the model when to use it and — often more importantly — when not to. Much of the tuning in this project is negative instruction: don't write a script to read a PDF, don't use the deep-research tool for a one-line fact, don't use the general search when the question is about one specific document.

That means a lot of "Ghost picked the wrong tool" problems are description problems, and they're fixed by editing text rather than code. The descriptions live in src/ghost_agent/tools/registry.py.

If it reaches for the wrong tool repeatedly, tell it directly in the moment ("use the document search, not general recall"). It records corrections like this as lessons, so the same mistake is less likely next time. How lessons work →

The full toolbox

Grouped by what they're for. You won't call these by name — this is here so you know what's available.

Doing work

ToolWhat it does
executeRuns Python, Node or shell inside the sandbox. Can keep state between calls like a notebook cell.
file_systemRead, write, search and list files in the shared directory.
browserDrives a real browser — navigate, click, type, screenshot.
postgres_adminQueries and administers a PostgreSQL database.
manage_servicesRuns a long-lived service inside the sandbox (a dev server, say) and keeps track of its port.
report_pdfTurns a result into a formatted PDF.
image_generationGenerates an image. Only available if you've configured an image-generation node.

Finding things out

ToolWhat it does
web_searchWeb search over Tor. The default for simple factual questions.
deep_researchSearches several sources and synthesises a report. Slower — for genuinely complex topics.
fact_checkVerifies a specific claim against external sources.
darkweb_search / darkweb_researchSearches Tor hidden services. Results are unverified by definition — Ghost is told to treat them as such.
vision_analysisLooks at an image or PDF page.
system_utilityWeather, your location, and a full health check of Ghost's own subsystems.

Memory

ToolWhat it does
recallSearches everything Ghost knows.
knowledge_baseIngests documents and recordings, asks a question against one document, records a fact, or forgets a topic.
update_profileSaves or deletes a durable fact about you.
scratchpadParks a note for the current conversation only. Expires after a day.
learn_skill / list_lessonsRecords a mistake-and-fix, and reads the lesson list back.

Tracking work

ToolWhat it does
manage_projectsDurable projects with tasks, dependencies and status.
manage_tasksScheduled tasks (a clock) and reactive watchers (a condition).
workspace / workspace_trackWatches files for changes and records what happened in your world while Ghost was away.
notify_operatorPushes you a notification when something needs you.

Its own state

ToolWhat it does
introspectReads back its diary, recent activity, what it learned, and how its experiments are going. The honest answer to "what did you do while I was away?"
self_stateRecords open questions and unfinished threads to carry into the next session.
postmortemThe queue of defects it has diagnosed in its own tooling.
flag_uncertaintyRegisters something it doesn't know. A high-impact unknown triggers a clarifying question instead of a guess.
replan / abort_attemptRethinks the approach, or declares a task impossible as specified rather than spiralling.

Extending and delegating

ToolWhat it does
create_skill / manage_skillsWrites a new reusable tool for itself, test-first, and manages the ones it has.
manage_composed_skillsChains existing skills into a bigger one.
delegate / delegate_to_swarm / jobsFarms work out to other LLM machines, if you've configured any. jobs also tracks a long execute command that outran its 10-minute budget: rather than being killed, a command still doing work is moved to the background and reported there.
