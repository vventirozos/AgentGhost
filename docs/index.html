Ghost Agent

A self-hosted AI agent. It runs on your own hardware, remembers what you tell it, does the work in a sandbox, and checks its own answer before it replies.

Python 3.10+ Runs locally Docker sandbox Tor-only egress No accounts, no API keys

Most AI assistants are a website you send text to. Ghost is a program you run. Nothing leaves your machine unless you asked for something that needs the internet — and when it does, it goes out through Tor.

What actually happens when you send a message

This is the whole product in five steps. Everything else in these docs is a detail of one of them.

  1. You send a message

    From the web page, Slack, your voice, or a plain HTTP request. It all arrives at the same place.

  2. Ghost looks up what it already knows

    It searches everything it has stored about you and about past conversations, and puts the most relevant pieces in front of the model — before the model starts thinking.

  3. The model decides what to do

    Answer directly, or reach for a tool: run some code, read a file, search the web, look at an image. Tools that touch your machine run inside a Docker container, not on your actual system.

  4. It repeats until the job is done

    Tool result goes back to the model, which decides the next step. Most questions take one pass. Real tasks take several.

  5. A second model checks the answer

    Before you see it — or just after, if the reply is streaming — a separate check asks "does this actually answer what was asked, and is it supported by what the tools returned?" If not, Ghost gets a bounded chance to fix it.

The turn loop. Steps 3 and 4 repeat; step 5 runs once.

One message, end to end walks through the same five steps with the parts named, for when you need to debug one of them.

Is this for you?

A good fit if

  • You want an assistant that keeps working when your internet or a vendor's API doesn't.
  • You care that your conversations stay on your own disk.
  • You're comfortable running a couple of background services and reading a log.
  • You want it to remember your projects across weeks, not just the current chat.

A poor fit if

  • You don't have a machine that can run a large language model locally, or a spare box to run one on.
  • You want zero setup. This needs Docker, Tor, and an LLM server running before it will start.
  • You need frontier-model reasoning quality. Ghost is built around a local model and trades some raw capability for privacy and control.

What you need before you start

An LLM server
Anything that speaks the OpenAI chat API — llama.cpp, vLLM, or Ollama. Ghost is tuned around Qwen 3.6 35B-A3, and the prompts assume a model of roughly that capability. See the note on model choice below.
Docker
The daemon must be running. Every piece of code Ghost executes goes into a container, so without Docker the tools that matter won't work.
Tor
A local Tor daemon on port 9050. Ghost refuses to start without it — see Safety and privacy for why that's deliberate.
Python 3.10+
Plus the packages in requirements.txt. A virtual environment is strongly recommended.
A note on model choice. Ghost is developed and tested against uncensored models — for the main model and for the verifier that checks its answers. It works with a standard aligned model, but expect refusals on operations that are routine for an agent running on your own machine and unusual for a chat assistant: clearing out its own sandbox, deleting files you asked it to delete, searching Tor hidden services, or handling security material.

A refusal doesn't look like an error. The tool never runs, the model explains why it won't, and the turn completes normally — so it reads as "the feature is broken" when the model simply declined. If something won't work, check the log for the model refusing rather than the tool failing. The verifier matters here too: an aligned judge can reject a perfectly good answer on subject matter alone, which shows up as unexplained retries.

How it compares

Self-hosted agents are a crowded category, and most of what Ghost does has an equivalent somewhere. The table below is about where the line is drawn — what's built in versus bolted on, enforced versus configured, measured versus assumed.

No product names, on purpose. These projects move quickly and a name-by-name matrix goes stale within months — and it would ask you to trust a claim about someone else's code that we haven't audited. The middle column describes the common design across self-hosted agents and the tools built for them, not any one project. Where something is genuinely widespread, it says so.
CapabilityThe usual approachIn Ghost
Runs on your own hardware The whole point of the category. Widely available. Same. No advantage claimed.
Sandboxed execution Common, especially in coding agents — usually a container per session. Same idea. One shared directory, its own process and network namespaces, memory and process caps.
Memory across sessions A mature field now, with several dedicated frameworks. Usually one store — vectors, sometimes plus a graph — retrieved by top-k similarity. Six stores, queried together and merged by rank rather than score, because similarity numbers from different stores aren't comparable. Source weights are learned per query intent.
Anonymous egress Direct connections. Tor is available as an optional add-on for specific tools, so the agent's other traffic still goes out normally. Tor is the transport for the whole process. A boot probe plus a process-wide socket guard blocks any direct connection to a public address. Unreachable Tor means Ghost doesn't start.
Hidden-service (.onion) search Available — several capable bolt-on skills exist, some with identity rotation. Built in, on the same enforced transport. Each retry takes a fresh circuit, and engines sharing one search index are tagged so corroboration counts independent sources.
Checking its own answers A known pattern — a critic or reviewer agent, usually wired per workflow by the developer. Runs on every substantive turn, unprompted. Asks whether the answer addresses the question before asking whether it's correct, escalates a cheap judge's refusal to the main model, and gets a bounded repair attempt. A refuted turn also un-learns whatever it taught.
Learning from its own runs Uncommon. Memory frameworks store what happened; they don't generally change behaviour because of it. Idle-time passes turn repeated successful tool sequences into named skills (several distinct supporting runs required) and failed turns into lessons. Skills are re-tested later rather than trusted indefinitely.
Tuning its own prompts Real and in production use — reflective optimizers like GEPA are an established technique, typically run offline against a strong teacher model. Same optimizer family, but pointed at your own local model with no teacher and trained on Ghost's own successful turns. Capped at 16 rounds because longer runs drift toward gaming the metric, and a tuned prompt ships only if it beats the hand-written one.
Models it trains itself Rare in self-hosted agents. Two, both plain logistic regression on its own recorded turns: one scores whether a partial plan is going anywhere, one predicts request difficulty. Small on purpose — readable as a list of weights.
Acting without being asked Agents generally act when invoked. Scheduling is usually external. A background loop runs consolidation, failure review, skill extraction and self-play during idle time, and never interrupts a turn. Scheduled and condition-triggered tasks are first-class.
Measuring whether a change helped Rare outside published benchmarks. Live randomised arms on real traffic with anytime-valid intervals, plus off-switches for most subsystems so they can be ablated rather than assumed.
Third-party accounts Usually at least one key — a search API is the common case. None. Search runs against scrapers over Tor, which costs result quality and is a deliberate trade.

What that costs

The same table read the other way. A local model caps reasoning quality below what a frontier API gives you. Search over Tor against scrapers is slower and less accurate than a keyed search API. The self-check spends an extra model call on every substantive turn. The idle-time learning only happens if the machine stays on. And more moving parts means more that can quietly stop working — several subsystems here have been silently inert for weeks at a time before instrumentation caught them, which is why so much of the tooling is about detecting that specific failure.

The unusual parts, in detail

The mechanism behind each of the rows above.

It remembers across sessions, in six different shapes

Closing the chat wipes nothing. Facts, relationships between things, a profile of you, lessons from its own mistakes, a running journal, and full past episodes are stored separately — because "what do I know about Postgres?", "who is Anna to me?" and "what went wrong last time?" want different shapes of answer. They're searched together and merged by rank rather than score. How memory works →

It refuses its own answers

A second model reads the final answer against the evidence the tools actually returned, and asks whether it answers the question before asking whether it's correct — because answering a different question is the more common failure. A high-confidence refusal sends Ghost back to fix it rather than shipping. How the self-check works →

It rewrites its own prompts, and mostly declines to

Three internal prompts — task decomposition, tool choice, and self-critique — are tuned by an optimizer trained on the agent's own successful turns, using the same local model with no teacher and no external service. It's capped at 16 rounds because longer optimization drifts toward gaming the metric, and a tuned prompt only ships if it beats the hand-written one. How prompt tuning works →

It turns repeated work into named skills

When several separate successful turns solve something with the same sequence of tools, that becomes a reusable skill — keeping the shortest validated path as the exemplar. Skills are re-tested later rather than trusted forever, since tools get renamed and models drift. How skills are extracted →

It can search Tor hidden services

Normal search engines don't index .onion sites, so there's a separate path through the dedicated onion engines. Each retry is forced onto a fresh Tor circuit, because whether an engine answers depends on which exit you drew — and engines that share a search index are counted once, so corroboration means independent sources. How onion search works →

It fails closed on the network

Outbound traffic goes through Tor, and this is enforced rather than intended: a boot-time probe plus a process-wide block on direct connections to public addresses. If Tor is unreachable, Ghost won't start. A silently-cleartext agent is worse than a stopped one. How that's enforced →

It works while you're away

Given a quiet stretch, Ghost consolidates memory, reviews turns that failed, extracts skills, retrains two small local models (⚠ §4BN: only the router leg retrains on a default box — the PRM leg is consumer-gated and skips), and practises against problems it invents for itself. None of it interrupts you, and none of it runs while you're active. Ask it what it did — the answer reads from a real ledger, not the model's recollection. The full idle schedule →
