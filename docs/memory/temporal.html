memory / temporal.py — anchoring

Store the invariant, derive the quantity. Facts that decay are rewritten at write time into facts that don't.

The defect it fixes (live, 2026-09-04)

On 2026-07-07 the user stated that his son Leonidas was 4 months old. Two months later the agent still answered "Leonidas is 4 months old". Nothing was corrupted — the store had faithfully kept what it was told. The problem is that a stated age is a measurement, not a fact: it is true only on the day it is said.

Why nothing downstream caught it:

  • The profile block carries no timestamp at all. ProfileMemory.get_context_string() renders bare - key: value lines into ### USER PROFILE ### on every turn. An unstamped line reads as present tense, for ever, with maximum authority.
  • The vector store's stamp was not enough. Rows are stamped and the prompt does carry CURRENT TIME, so the arithmetic was possible — but it required the model to notice an ISO stamp, subtract, and then overrule an unstamped profile line asserting otherwise. It never did.

The invariant behind an age is a birth date, which is constant. So the store keeps the birth date, and the current age is computed on the way into the prompt. The model is never asked to do the subtraction it demonstrably skips.

The two halves

What is on disk is therefore always a constant; what the model reads is always current. A derived value is never persisted — if it were, tomorrow's read would compound onto a frozen number and the bug would return through the store.

Why the anchor is placed in ProfileMemory.update()

Every writer funnels through it — the update_profile tool (both its bus and legacy paths), the memory bus's _profile leg, and smart-memory consolidation — so nothing can bypass the rewrite. tool_update_profile anchors additionally, up front, because it also mints a vector fact ("User <key> is <value>") and a graph triplet from the same value: anchoring only inside the profile store would leave those two siblings holding the decaying snapshot, which is the three-stores-disagree shape §4M MAJOR-4 already had to fix once. anchor() is idempotent, so the second application is a no-op.

Design decisions

Midpoint anchoring

"9 years old" means the true age is in [9, 10), so the best estimate of the birth date is said_at − 9.5y, not said_at − 9y. Naive subtraction biases every later derivation one unit high — the exact error class the module exists to remove. The residual uncertainty is why every derived age renders with a ~.

Precision survives the round trip

An anchor is written at the granularity its statement supports: an age in years anchors to the month (born ~2017-01, ±6 months), an age in months or finer to the day (born ~2026-02-20). derive() reads that granularity back and renders a coarse anchor in years only. Without it, "my son is 1 year old" came back as "~18 months old" — more precise than anything known, and not what the user said. This was caught by a round-trip pin, after an earlier pin written against the arithmetic helpers passed while the pair that actually runs disagreed.

One anchor shape, two spellings read

People type born March 12, 2026, not ISO. anchor() canonicalises the month-name form (March 12, 2026, 12 March 2026, Mar 12, 2026, in March 2026) to ISO so there is one shape to read, and derive() reads the named form too, for rows written before that existed. Found live: the operator stated both children's exact birth dates in a chat turn, the pre-change code stored them verbatim, and they carried no derived age at all — an exact date the model still has to subtract from by hand is the original defect one step further along.

Coarseness is the estimate marker, not the granularity

born ~2017-01 came from "9 years old" and is good to ±6 months, so rendering it in months would be false precision — it renders in years. born 2026-03 came from someone saying "born in March 2026" and is good to ±15 days. Keying coarseness on month-granularity alone rendered that five-month-old infant as "~0 years old"; it keys on the ~.

Unit follows magnitude

An infant anchored in months ages into years by itself: ~3 weeks old → ~6 months old → ~2 years old. A stored snapshot can never do this — "4 months old" stays "4 months old" through the child's third birthday.

KV-cache stability

The gloss is a rounded age, never a date or a day count, so the rendered profile block changes only when the derived age changes — about monthly for an infant, yearly for a child. {{PROFILE}} sits inside the byte-stable system prefix core/agent.py deliberately keeps identical across turns for upstream prefix-cache hits; rendering "today" here would have invalidated that prefix every single day.

Conservative matching

A rewrite requires an explicit age cue — "old", "age", "aged", "yo", "mo". A bare "4 months" is left alone: it is far more often a duration ("4 months of runway") than an age, and a wrong rewrite is worse than a miss. Implausible counts (aged 900 years) are left alone too.

Protected spans — quoted records and derived glosses

Two kinds of span are never rewritten, for the same reason: neither is a claim the store owns.

  • A quoted string is a record — a search query the agent ran, a command, a code literal. Live proof: a stored skill lesson held web_search(query="Thodoris basketball Panellinios age 9"), and an unguarded pass rewrote the query text itself.
  • A derived gloss is render output. If one flows back into a writer, anchoring it would freeze a rendered value into the store — reintroducing the snapshot the module exists to eliminate.

Predicative vs attributive position

A predicative or parenthetical age is replaced: Thodoris (9 years old) → Thodoris (born ~2017-01). A fully-hyphenated attributive compound fills an adjective/noun slot, and replacing it produces garbage — "equipment for a born ~2017-02-20 named Thodoris" was the live result on a real stored fact. That one form is annotated instead: a 9-year-old (born ~2017-01) named Thodoris, which derive() renders as a 9-year-old (born ~2017-01 → ~9 years old) named Thodoris. The trade is deliberate: the stale token survives in the only position where removing it costs grammaticality, and the authoritative value sits immediately after it. The syntactic rule is mechanical — hyphenated compound ⇒ attributive ⇒ annotate; spaced ⇒ predicative ⇒ replace.

Restatement refines, it does not accumulate

Anchoring makes two statements of the same fact differ in bytes ("4 months old" in July and "6 months old" in September anchor to different dates), so the profile's exact-string dedup would have kept both and injected two contradictory birth dates into every prompt. ProfileMemory._same_fact() compares signature() — an anchor-blind form — so the newer statement refines the anchor in place. The exemption is scoped to values that actually carry an anchor; everything else keeps byte-exact dedup semantics, so this cannot silently collapse distinct interests.

Relative dates

"3 years ago" is the same defect class — it silently re-anchors to whenever it is next read — so it is absolutised to in ~2023-07-07 at write time. No gloss is derived for it: the value is already a constant and the prompt carries CURRENT TIME. Fuzzier forms ("last March", "next week") are deliberately not handled: ambiguous, low value, and a high false-rewrite risk.

Recall stamps

VectorMemory._render_item now prints elapsed time next to the ISO stamp — [2026-07-07T21:29:05Z · 59d ago]. An absolute stamp makes the model find CURRENT TIME elsewhere in the prompt and subtract; the elapsed value is what it actually needs. A malformed stamp degrades to the old rendering rather than raising — this runs for every retrieved row.

Known limitations

  • "born" reads oddly for a non-person ("the release born ~2026-02-20"). Accepted: profile facts carrying ages are overwhelmingly about people and pets, and the marker's legibility to both a regex and an LLM is worth more than the rare awkward phrasing.
  • An age used as a category is still annotated. "a ball best for a 9-year-old" is a product attribute that does not decay, but the attributive branch will annotate it. Noisy, not corrupting — the original token survives. The repair script does distinguish the two cases (see below); the write path does not, because the distinction is semantic and a regex that pretended to have semantics would be worse.
  • Perishable-but-underivable facts — a job, a location, "currently learning X" — have no invariant to derive, so anchoring cannot help them. They are covered by the companion mechanism: per-value as_of provenance and a staleness marker, in memory / profile.py.

Repairing an existing corpus

scripts/repair_temporal_anchors.py. The module stops new snapshots but is dead code against what is already stored, so the live corpus needed a one-time pass. Dry run by default; --apply writes; every target is backed up first.

Three things the script refuses to do. It will not guess a said_at — a rewrite anchored to the wrong date is worse than the snapshot because it looks authoritative, so an undated row is reported as unrepaired rather than silently skipped. It will not open Chroma directly — a second PersistentClient against the live dir risks HNSW corruption, so vector rewrites go through the owning process via correct_fragment. And it will not sweep blindly: in the graph, an age is only a decaying claim when the predicate says it is about the subject. thodoris IS_AGE "9 years old" was repaired to thodoris BORN "~2017-02" (rewriting the object alone would have left IS_AGE pointing at a birth date — a worse record than the one it replaced); wilson evolution youth IS_BEST_FOR "9-year-old" was skipped, because a ball stays suitable for nine-year-olds.

Vector document, episode and skill rows are excluded outright: a document's ages belong to the document's own timeline, and a skill lesson is a record of what was done.

Two behaviours the script has that anchor() deliberately does not. The predicate can supply the cue. thodoris IS_AGE "9 years" survived the first pass — the object alone reads as a duration, which anchor() correctly refuses to rewrite. Under an age-ish predicate the cue is already established, so _with_predicate_cue() supplies it (and a bare number means years). This stays in the script: loosening anchor() would reintroduce "4 months of runway". A repaired form that already exists means the row is a duplicate. triplets is UNIQUE(subject, predicate, object), so such a row cannot be updated into place and must not be — it gets the store's own supersession mark (valid_until, which every graph read path filters on) instead. Both were found by running the repair on the live graph, not by reading it; the collision raised IntegrityError and rolled the batch back without changing anything.

Tests

tests/test_temporal_anchoring.py — 25 pins, each written to fail when its mechanism is removed, with the mutants it answers to named in its docstring. The time-dependent pins assert the rendered value changes as the clock moves rather than matching a fixed string (a string pin would pass with the whole feature deleted), and the arithmetic pins recompute the expected date instead of hardcoding it. Two defects were found by pins during development (the year/month precision loss, and the missing "weeks" case in the gloss-stripping regex); two more by sweeping the live corpus before shipping, and two by running the repair. The mutation battery scores 32/32 killed — its first run scored 19/22, and all three survivors were weak pins, not weak code: an unreachable guard removed as dead code, and two pins asserting on tokens rather than executing the consumer.

API

FunctionEffect
anchor(text, said_at=None) -> strRewrite ages / relative dates into absolute anchors. Idempotent. Non-string input, protected spans and implausible ages pass through untouched — it runs on every profile write and must never be able to destroy a value.
derive(text, now=None) -> strAppend the value true at now to every anchor. Strips any previous gloss first, so it is idempotent and self-correcting. A future-dated anchor renders no age.
signature(text) -> strAnchor-blind form, for equality checks that must treat two statements of the same fact as identical.
has_anchor(text) -> boolWhether the text carries at least one absolute anchor.
