memory / youtube_ingest.py — a YouTube link, over Tor, into the knowledge base

The route knowledge_base(action='transcribe', filename='<youtube url>') takes (§4KE, 2026-09-24). Everything egresses through Tor; no cookies, accounts or keyed APIs are involved.

Why it exists

Until September 2026 YouTube was handled by a composed skill whose first step ran a shell script inside the sandbox: pip install yt-dlp, install deno, download the audio with exit-node rotation, then a second step transcribed yt_audio.m4a. It never completed. The sandbox promotes any command still running at 90 s to a background job, the sequential runner books that as a failed step, and the transcribe step never ran — the live registry showed 3 uses, 0 successes. It also wrote every video to one constant filename, so the knowledge base's name-keyed dedup would have answered every later video from the first; it ran unpinned installs as root at run time; and its quoted-heredoc defence for the URL could be ended by a line break in the URL. The review that found all this is in PROJECT_JOURNAL.md §4KE.

What was measured before designing it

Route over Tor (2026-09-24)Result
yt-dlp, default and 8 other player clients, no PO token0 / 9 circuits — "Sign in to confirm you're not a bot"
Invidious instances, Piped, timedtext endpoints, third-party transcript sitesdead, or the same wall on their side
yt-dlp + a locally minted PO token (BotGuard solved by the helper)5 / 12 circuits; failures in 2–9 s; captions and audio both flow

The wall is per-circuit once a proof-of-origin token is present, so the winning shape is the one tools/search.py already uses: a handful of attempts, each on a fresh circuit (a distinct SOCKS username makes Tor build a new one), fail fast, stop early on a fault no exit can pass.

How a link flows

  1. Recognise. youtube_video_id() accepts watch, youtu.be, shorts, live, embed and music URLs and rejects channels, playlists and look-alike hosts (those fall to the ordinary web fetch).
  2. Dedup by video. A document named yt-<id>.… already in the library means Skipped, whichever tier ingested it, before any network.
  3. Resolve. yt-dlp runs as a module of the agent's own interpreter (python -m yt_dlp, so the venv's pinned yt-dlp and the PO-token plugin are what run), with --proxy socks5h://<tag>:isolate@127.0.0.1:9050 (remote DNS — socks5:// would resolve the host locally) and --extractor-args youtubepot-bgutilhttp:base_url=…. Up to eight circuits; a bot wall, a 429/403, a "format not available" (SABR-only session) or a transport error earns another circuit; a private/removed video or an unknown error stops at once with yt-dlp's own last ERROR line as the reason.
  4. Captions tier. choose_caption_track() prefers a manual track, then the ORIGINAL-language automatic track (<lang>-orig) — the other automatic keys are machine translations and would hand back English for a Greek talk. One language per request (a second one on the same circuit drew a 429). Fetched on the circuit that just resolved the video, parsed from json3 (word segments joined per event) or VTT (tags stripped, rolling duplicates collapsed), grouped into ~90-second passages, indexed under yt-<id>.captions.<lang>.
  5. Audio tier. No usable captions: download the audio track into the sandbox as yt-<id>.m4a on its own circuit and hand it to memory/audio_ingest.py (the private audio node). Recordings past GHOST_AUDIO_MAX_S are refused with the reason.
  6. Persist structure. An outline record (one entry per passage), the ordered transcript beside the store (set_document_text, read back by action='transcript', dropped with the document) and a summary row that carries the title, URL, language, gaps and the opening words — not just counts.
  7. Reply. SUCCESS: … with the first 3,000 characters of the transcript and the offset to continue from, so "summarise it" needs no second call.

The PO-token helper

com.local.ghost-pot is a system LaunchDaemon running the bgutil-ytdlp-pot-provider server from ~/Data/AI/PotProvider on 127.0.0.1:4416 (plist and notes under interface/externals/pot_provider/). yt-dlp forwards its per-attempt proxy to the helper, so the BotGuard challenge fetch rides the same Tor circuit as the video request — verified in the plugin source and the helper's log. If the daemon is down the route tries to spawn the server itself; if that fails too, the error names the helper as the cause instead of "every exit blocked". Overrides: GHOST_YT_POT_URL, GHOST_YT_POT_DIR, GHOST_YT_ATTEMPTS, GHOST_YT_INFO_TIMEOUT_S, GHOST_YT_AUDIO_TIMEOUT_S, GHOST_YT_PASSAGE_S, GHOST_YT_POT_LOG (log of an on-demand spawn).

The canary (§4KH, 2026-09-24)

YouTube rotates its BotGuard challenge from time to time; when it does, the helper's tokens stop being honoured and every circuit is refused until yt-dlp and the helper are updated together. Rather than learn that at the next pasted link, the agent probes the route itself: memory/youtube_canary.py, driven from the idle scheduler's tick, once per GHOST_YT_CANARY_HOURS (default 24; 0 disables), first GHOST_YT_CANARY_BOOT_DELAY_S (600) after boot, in a worker thread, never while a turn is in flight. One probe = helper /ping, Tor liveness, then a resolve-only fetch of a fixed public video on up to GHOST_YT_CANARY_ATTEMPTS (4) fresh circuits — no captions, no audio, no store writes.

States: ok; walled (every circuit refused — rotation suspected) and unstable (every circuit failed with mixed faults: 403s, timeouts, a SABR-only session) are the two verdicts an exhausted rotation produces, and since four circuits failing by chance is about 13% per run whatever the cause, both are held and re-checked after GHOST_YT_CANARY_RECHECK_S (15 min), announced only when a second consecutive run confirms them; error (the rotation stopped early on a terminal fault), helper_down and tor_down are announced at once. It speaks only on a transition: entering a failure state writes one notify-severity activity record (Slack DM to the owner, webhook/ntfy), returning to ok writes one recovery notice, a steady state writes nothing, and a message the ledger did not accept is retried on the next run rather than forgotten. The current verdict is always on /api/health as youtube_route (settled state, the last run's own last_state/last_reason, a pending held verdict, ISO timestamps) and in $GHOST_HOME/system/youtube_canary.json; POST /api/youtube-canary/run starts a probe now (the operator's button after an update). The remedy it names, bin/update-youtube-stack.sh, is deliberately a manual, one-command step: it checks for passwordless sudo first, upgrades yt-dlp and the plugin in the agent's venv, builds the helper at the release matching the plugin, restarts the daemon, and proves the result with a live resolve — fetching from PyPI, GitHub and npm over the clear from the host, which is operator egress, not the agent's.

The macro that remains

youtube_transcribe(url=…) still appears in the tool list, as a one-step alias of the knowledge-base call. Its definition is code (tools/yt_download.CODE_OWNED_MACROS); the composed-skill registry overwrites a stored copy whose steps differ at load, keeping its usage counters, so a change ships with the code — no more stopping the agent for a sync script. See composed_skills.

§4PI review — the route, the transcription and the operations read as one path 2026-10-15

Three fresh-eye readers (the route; transcription + summary; ops + security), three live probes before the fixes (a fresh captioned video, a dedup re-request, a local m4a — all right), then a fourth reader on the diff. The corpus is thin (four real YouTube turns since July), so the readers were the instrument. What they found, and what changed:

The route (memory/youtube_ingest.py)

  • Captions were fetched once. The chosen track was tried only on the circuit that resolved the video; any 429 there demoted a captioned video to the audio tier (eight 900 s circuits plus the node) and the final error said "has no captions". fetch_captions_rotating tries the resolving circuit, then GHOST_YT_CAPTION_ATTEMPTS (3) fresh ones; the audio-tier error now names the captions that could not be fetched.
  • Live streams. is_live/live_status were never read; a live broadcast (duration None → 0, under the cap) ran -f ba on the live HLS to the timeout on every circuit — two hours, reported as "timed out". Refused up front with the cause.
  • A wall clock on the fetch. GHOST_YT_FETCH_BUDGET_S (1,200 s) bounds resolve + captions + audio download: _rotate(deadline=) stops rotating when it is spent and _bounded() shortens each attempt's timeout to what remains. The NODE budget (2 h) for a long recording is unchanged and by design.
  • Dedup of a partial run. "Already in the knowledge base" hid a transcript that had stopped early; the sidecar now records stopped and the Skipped reply says PARTIAL with the gaps and the forget-then-redo route.
  • Hygiene. yt-dlp, its plugin and deno run with an allowlisted environment (they inherited GHOST_API_KEY); ensure_pot_server spawns a helper only with GHOST_YT_POT_SPAWN=1 (a second helper beside launchd's took the port and crash-looped the daemon, seen 2026-09-24); a configured proxy URL carrying credentials no longer voids circuit isolation; deno-missing / helper faults are named from the whole stderr instead of being retried eight times as "format not available"; a malformed caption file is a caption failure, not a route crash; the title is one clean line and the preview is neutralised like the paged route; url=/link= are accepted argument names; the in-flight claim is keyed on the video id.

Transcription and the summary (memory/audio_ingest.py, tools/memory.py, the prompt)

  • "Musicians" was silence. _split_no_speech prefix-matched bare words: "Musicians from across Europe…" was stored as "ians from across Europe…", "Music is what we do here." was booked as silence and counted as transcribed. A bare word is a sentinel only as the whole reply; only a bracketed sentinel may lead real text.
  • Coverage. A window cut at the token budget counted as fully transcribed ("12:00 of 12:00 … NOT transcribed: 0:00–12:00"); it is now a gap, and the union still advances so the tail is not re-sent. The abort says "not answering" only for transient faults (an HTTP 400 or an exhausted token budget is "unusable output"). A window that cannot finish inside the budget is not started (floor min(WINDOW_TIMEOUT_S, budget/4)), and the budget gap starts where coverage ends. The duration prefers the audio stream (a container whose format outlives its audio made silent windows "transcribed").
  • The summary route. The KNOWLEDGE prompt rule sent every question about one document to query, so a two-hour talk was summarised from eight chunk hits or the 3,000-char ingest preview — and query itself returned the document-summary row (audio content under a system-looking label) as a passage. The rule now says: read the transcript in order to [end of transcript], never summarise from hits, the preview or world knowledge, say what was read; search_document filters type="document". Pages break at line ends so every page opens on a timestamp.

Operations (memory/youtube_canary.py, bin/update-youtube-stack.sh)

  • The canary never confirmed an alternating wall. walled and unstable differ only by whether all four failures were bot walls or three walls and a timeout — a mix that flips run to run under Tor; confirmation required the identical state, so ok → walled → unstable → walled … stayed ok for days and never paged. The two held verdicts now confirm each other. Also: the state file keeps a .bak and loads from it when corrupt (a fresh start forgot announced); a failed thread start releases the guard; recheck_in_s is the time remaining.
  • The update script upgraded pip first, rsync --deleted over the running daemon's build, restarted before verifying and had no rollback (a 0/6 verify is ≈5 % luck on a healthy stack). Now: build in a mktemp dir → stage beside the live helper → pip (previous pins saved) → atomic swap keeping <POT_DIR>.prev → restart → wait for /ping → verify; --rollback and --plan.
  • The model could run yt-dlp itself. pip install yt-dlp && yt-dlp <url> in the sandbox installs over Tor and is bot-walled on every exit (the 600 s promoted-job loop of 2026-08-11); execute now refuses yt-dlp / youtube-dl / pytube commands (heredoc and quoted text stripped) and names the knowledge_base route.

The reader's round on the fixes (r2)

A fresh reader of the diff found four MAJORs inside the first cut, all fixed and pinned: transcript paging could loop forever on a line longer than the page (a 12-minute audio window is one line) — the mid-line pull-back now applies only when the line fits a page; the canary, once a wall was confirmed, paged the owner again on every walled↔unstable flip — a flip between the two held verdicts is no longer a transition; the helper-warning regex outranked the terminal check, so a private video under a routine "GVS PO Token" warning burned eight circuits labelled a helper error — terminal faults are read first; and --rollback read the pins file from the wrong directory — the pins are saved beside the previous helper, and with no previous build the rollback refuses rather than un-pair the stack. Minors: caption attempts now refresh the fetch budget, count bot walls and do not rotate a track fault; the sandbox block reads python -c 'import yt_dlp' and pip install "yt-dlp"; "Silence." with a trailing stop is silence; the shared socks_url_with_identity keeps IPv6 brackets. The job-promotion tests had used yt-dlp … as their long-running fixture; that shape is now refused by design, so the fixture is a neutral script.

Left to the operator (plist / daemon config): the helper's log (0644, never rotated) records every PO token and the owner's video ids; the helper runs as the operator's own account. Pins: tests/test_4pi_youtube_review.py; battery scripts/mutate_4pi.py.

§4RR — two faults found by an end-to-end run 2026-10-26

An end-to-end transcription of a 15-minute talk (captions tier and forced audio tier, stub store) found two faults that no unit test could see:

  • A bot wall became "repair the stack". yt-dlp 2026.10 prints "n challenge solving failed … Ensure you have a supported JavaScript runtime …" on every fetch (deno is installed; the EJS solver script is not). The stack-fault regex matched any "javascript runtime", so the first bot-walled circuit was classed terminal and the fetch stopped after one circuit instead of rotating. It now matches only yt-dlp's real missing-runtime line, "No supported JavaScript runtime could be found".
  • Every 12-minute audio window failed. A 720 s window is 18,068 prompt tokens (25 audio tokens/s); it was sized for a 32,768-token slot, and nova has run 4 × 16,384 since 2026-10-25, so each window returned HTTP 400 and was stored as a gap under a "SUCCESS" reply. The window is now fitted to the node's real slot per recording (node_slot_ctx reads /props; fit_window_seconds budgets 25 audio + 5 transcript tokens per second + 512 for the prompt), and the default cap is 480 s, which fits a 16k slot even when /props cannot be read. Measured on nova's Gemma: 720 s → HTTP 400, 600 s → transcript cut at the slot, 480 s → complete in 72 s.

The warning itself was real: the EJS challenge-solver scripts were missing. yt-dlp-ejs==0.8.0 (the version yt-dlp 2026.10.21 pins) is now in the agent venv, and bin/update-youtube-stack.sh installs whatever version the upgraded yt-dlp pins and saves it with the rollback pins.

Pins: tests/test_4rr_youtube_fixes.py (verbatim yt-dlp stderr from the live run).
