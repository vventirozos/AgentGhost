memory / fact_ledger.py — FactLedger

When each fact about the owner was stated, replaced or removed, and in which of the owner's own words.

Why it exists (§4QM, 2026-10-21)

A profile value knows when it was learned (as_of, §4EM) and nothing else: a replaced singleton keeps one previous, a removed list value goes to a 30-day archive, an owner graph edge expires with a log line. Nothing recorded which request stated a fact or what the owner typed, so "since when do you know where I live?", "what car did I have before?" and "why do you think my wife is called X?" had no answer, and a wrong owner fact (§4KY) could not be traced to the line that put it there. The 2026 evidence: provenance-typed facts with validity overtake curated summaries after nine weeks; Devin, Codex, Copilot, Perplexity and ChatGPT all ship per-memory sources.

What a row is

One append-only SQLite table, memory_dir/fact_ledger.db: at, store (profile | graph), category, key, value, event, prev_value, req_id, said (the owner's sentence, ≤ 200 chars), via (profile | graph | extractor | bus | backfill), how (delete, remove_item, prune:<word>, drop_previous, forget <entity>, delete_edge, superseded by …).

EventWritten when
stateda new value lands (a singleton's first value, a new list item, a new owner edge)
restatedthe same value is written again (the owner confirmed it; the profile refreshes its stamp)
replaceda singleton field changes value — the row carries the old value
removeddelete, remove_item, prune_value, drop_previous, a forget, a mirror edge deleted
expireda functional owner edge superseded by a newer value (graph)
backfilledseeded by scripts/fact_ledger_backfill_4qm.py from the stores that existed before the ledger

Who writes

ProfileMemory (update, delete, remove_item, prune_value, drop_previous, drop_previous_mentioning) and GraphMemory (add_triplets for edges with a user end, the functional-predicate expiry, delete_edge, forget_entity) call _ledger_record after their own write committed (graph rows are queued until commit(), profile rows until save(); a failed write leaves no row). The ledger never decides what is live: reading it changes nothing, and a ledger that cannot be written is logged while the store write stands. Not recorded: the owner's chatter edges (user ASKED_ABOUT weather, GREETED — _is_owner_fact) and the profile's own mirror edges (user HAS_<KEY> from sync_owner_field: the profile row is the record, one fact = one line). A value the per-key cap (8) pushes out is recorded removed … capped at 8.

The owner's words. A row never carries the whole message (review r1: a token pasted beside "my car is a Ducati" would have gone into the ledger and back into a prompt). current_source(via, value, field) keeps only the owner's clause that states the value — attribution.owner_clause_for: the clause with the field's predicate cue first ("We moved to Athens in May" beats "I was in Athens for a wedding" for a home), then the widest word coverage; raw words, case and accents kept — and record() redacts every said with the trajectory recorder's rules (distill/redact: keys, e-mails, passwords, paths). The background extractor passes the clause it matched in the owner's turn (_owner_sentence_for) and the turn's request id (the smart-memory journal item carries it), never the drain's SYSTEM request. A question is never a statement: owner_statements skips sentences that open like one without a "?" ("do you remember my wife fotini", "tell me about my car bmw", "θυμάσαι τη γυναίκα μου"). A probe's, a member's or a background job's write is refused before the ledger, as before (_owner_write_block). The seeded placeholder name User is not a previous value.

Who reads

Off in production: the ledger is written on every owner-fact change but shown to nobody, because GHOST_FACT_HISTORY (see Switches) is unset in the launcher; the paired replay failed twice (§4QM). With the switch on, on a first-person question about the owner, the memory bus's _fetch_history adds up to eight lines under ### WHAT YOU TOLD ME, AND WHEN ("root.location = Athens, Greece — since 2026-07-08 (you said: "…")" for a row the live agent wrote at the owner's turn, "graph.has_medication = entresto — on record since 2026-10-03" for a seeded row whose date is only the store's stamp, "graph.has_condition = heart failure — on record since 2026-10-03 (confirmed by you on 2026-10-03)" for a seeded row the owner confirmed in person (§4QN: a how that starts "confirmed by you" is shown beside the owner's words — once; an internal removal reason such as prune:bmw still shows only when the row has no words), "assets.vehicles: "BMW 118i" removed 2026-10-20 (you said: "we sold the BMW")"), and recall appends the same section on a question about the owner (history words — "since when", "what did I tell you", "why do you think" — widen it to sixteen lines but never open it: "history of python" earns nothing). Both are behind GHOST_FACT_HISTORY (default 0) and the probe arm fact_history. The paired replay (§4QM, 2026-10-22: 16 self-questions × 3 samples × 2 arms, blind-graded twice) FAILED the fixed rule — RIGHT −6.7 points, WRONG unchanged on the ten block-present questions — because today every row is a seeded one whose date is a store stamp (a profile's last write, a graph edge's creation), and introspect's trajectory search dates the owner's real turn better; the block won only where the seeded date was the statement date. The switch stays off until live rows (written at the owner's turn) accumulate and a replay proves them. The hydrated lines apply the profile's whole on-demand rule (is_on_demand: the policy set, *_description keys, address-like keys, street-looking values), pass through the profile's egress scrubber, and are withheld entirely when those rules cannot be read. Lines are one per (field, value, event), newest first, grouped in SQL so a value restated forty times cannot hide the older replaced/expired row a question is about; days are local.

Backfill

scripts/fact_ledger_backfill_4qm.py seeds one row per current profile value (dated by its stamp, or undated when it has none — never "today"); a replaced singleton becomes a replaced row carrying its prev_value and the previous value a backfilled row on its own stamp; one backfilled row per live owner edge that neither mirrors a profile field nor carries a value any profile field already holds (dated by valid_from — a store date, so it renders "on record since", never "since") and one expired row per expired owner edge. Each is attributed to the owner's own statement clause in the trajectory corpus (full word coverage, questions excluded, the raw clause kept) at or before the fact's date. A fact nothing in the corpus states is seeded without words and listed as UNATTRIBUTED for the owner; nothing live is changed either way. Report mode by default; --apply takes the memory directory's writer lock first (§4MN: stores are single-writer — run it in the restart window, the agent exits 75 and launchd retries until the lock is free) and is idempotent (rows compared the way the ledger stores them).

§4QN (2026-10-22) — the seeded rows nothing attributed. Thirteen live rows were seeded without words: the backfill matches a first-person statement CLAUSE with full word coverage, and the owner's real statements fell outside that — a clause split at a comma ("…, Athens, Greece"), a fact stated about someone else without "my" ("fotini was born at 10 Jan 1982"), a value that is the extractor's paraphrase, or a fact the owner confirmed in person (§4KY/§4LC, 2026-10-03: heart failure, blood clot, Entresto, the role). scripts/fact_ledger_attribute_4qn.py repairs them from an EVIDENCE file kept outside the repo (it quotes the owner): per row the owner's clause, the turn's local time or request-id prefix and an optional how. Nothing is trusted from the file alone — a clause is written only when an owner turn in the trajectory corpus at that minute (±2 min) or under that request id contains it; otherwise the row stays UNATTRIBUTED and is listed. An entry with no clause must carry a how that starts "confirmed by you", which the render shows. Only rows marked unattributed are touched, so a second run is a no-op. --delete-twins removes the seeded graph rows that carry the same value as a seeded profile row in the ledger (the twin rule the backfill gained in §4QM, applied to what it had seeded before it) — but only when the graph row adds no evidence of its own (its said empty or equal to the profile row's, no confirmation); a row with its own clause, a how that starts "confirmed by you" (review r2: a confirmation is evidence, and a later twins-only run has no evidence file to name it), or one named in the evidence file, is KEPT and listed (review r1: value-only matching would delete born_in = Athens beside location = Athens, and the only row carrying the owner's clause). Report mode by default; --apply takes the writer lock and first copies the db to system/backups/<stamp>-4qn/memory/. Applied on the live ledger on 2026-10-22: 13 rows attributed, 7 twins deleted (owns ×3, married_to, has_spouse, has_memory_usage ×2), 1 kept (has_hobby = brazilian jiu jitsu, its own clause), 0 missing.
