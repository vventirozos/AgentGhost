memory / profile.py — ProfileMemory

Canonical user profile with multi-value merge semantics.

Storage

JSON at path/user_profile.json; atomic temp + os.replace; threading.RLock guards reads / writes.

Schema

{
  "root":          { "name": Value },
  "relationships": { "wife|husband|son|daughter": Value },
  "interests":     { "science|general|...": Value },
  "assets":        { "car|...": Value }
}

Value := str                      # LEGACY — as_of unknown
       | {"v": str, "as_of": ISO} # stamped
       | list[Value]              # multi-valued (merge keys)

Both shapes coexist for ever: a legacy bare value is never back-filled with a fabricated date. See provenance below.

Canonicalisation

Common synonyms remap at write time: wife → relationships.wife, vehicle → assets.car, etc. The caller receives the rewritten key in the return message so the agent can keep its mental model synced.

Merge semantics

Scalar → scalar: replace if different, else promote both to a list. Lists are deduped and order-preserved. Singular keys are exempt (they replace) and merged lists are now bounded — see below.

Singleton keys — corrections replace, not accumulate (2026-07-22)

Singular relationship / possession / identity keys — wife, husband, spouse, son, daughter, car, home, employer, name, … (module-level _SINGLETON_KEYS) — are now SINGLETONS: a second write REPLACES rather than merges. The merge branch exists for facts that genuinely coexist (python AND rust are both interests), but applied to a singular noun it turned every correction into an accumulation: update("relationships","wife","Anna") then (…,"wife","Maria") produced - wife: Anna, Maria, injected into the system prompt every turn for ever with nothing anywhere able to reconcile it. These are exactly the keys the canonicalisation table CREATES, so a correction was guaranteed to hit the merge branch. Rule of thumb: a genuinely multi-valued fact belongs under a PLURAL key (pets, children, languages, topics), which keeps merge semantics untouched.

Bounded merge — no unbounded prompt growth (2026-07-22)

Merging keys were previously uncapped, and every merged key is rendered inline by get_context_string() into every system prompt, so an unbounded key is a slow context-pressure leak. A merging key is now capped at _MAX_VALUES_PER_KEY = 8, dropping the OLDEST first (the newest statement is the most likely to be current) with the trim logged at WARNING. notes.info — the DEFAULT sink a malformed profile_update lands in (the callers default category="notes", key="info", so any dict the model emits without those keys dumps the whole extracted fact here) — gets a much tighter ring: _SINK_MAX_VALUES = 3 values of _SINK_MAX_VALUE_CHARS = 200 chars each. It had no cap, no TTL and no dedup beyond exact-string match, growing straight into the prompt. Tests: tests/test_memory_store_durability.py.

Log levels (2026-07-25): the sink ring rotating at its designed 3-cap is routine by-design behaviour, not a leak signal — it now logs at debug only. A real multi-valued key overflowing the 8-cap keeps the operator-stream WARNING: that is the context-pressure-leak signal the message exists for. (The repeated notes.info WARNING was operator-flagged as noise the same day the smart-memory caller stopped feeding the sink — see below.)

Forgetting values (not just keys)

The profile is injected into the system prompt every turn via get_context_string(), so it is the authoritative source the model answers from — vector and graph stores are secondary. This made one deletion bug user-visible: pets / interests / assets are stored as values (e.g. assets.pets = ["Hanzo the dog", "Mortimer the iguana"]), but unified_forget's profile sweep only matched keys. forget('mortimer') therefore never reached the row — it kept being injected, so the model kept "remembering" the deleted pet even after reporting success. The merge semantics above compounded it: a "Mortimer is gone" interaction appended a soft-delete tombstone string ("Mortimer the iguana (removed)") rather than deleting anything.

prune_value(category, key, target) closes this: it removes every list item (or a matching scalar) whose text mentions the target, collapsing a surviving singleton list back to a scalar and dropping the key — and the category — when nothing remains. Matching is token/word-boundary aware so forget('age') does not strip a value of 'language', while forget('mortimer') still matches 'Mortimer the iguana (removed)'. unified_forget now runs this value sweep after its key sweep (see memory tools).

Robustness — profile_update shape

The smart-memory consolidation prompt asks the LLM to return profile_update as an object ({category, key, value}). The model occasionally ignores this and emits a bare string instead. The agent now coerces any non-dict profile_update to None at parse time: such a fact is still stored as a normal auto vector memory but skips the identity / profile_memory.update path entirely. This prevents the previous crash — 'str' object has no attribute 'get' — which fired (and was swallowed) when a high-score string slipped into the identity branch.

Project-state screening + sink-write guard (2026-07-25)

Operator log review caught the profile being polluted by project chatter: the smart-memory scorer inflated tracked-project status sentences to 0.90, storing them as timeless user truths AND churning them through the 3-slot notes.info ring (100% of the user's notes became project state). Three layers now stop this, all in core/agent.py's run_smart_memory_task:

  • Prompt rescoring. The scoring matrix scores TRACKED-PROJECT STATE at 0.2 → DISCARD ("the project store already records these"); a durable user preference learned during project work stays 0.9.
  • Deterministic backstop _is_tracked_project_state (small models inflate past the prompt). A fact is project-state when it carries a verified 12-hex project id, the bound project's title, or — added the same day after a buffered-journal drain refilled the freshly-scrubbed ring with paraphrased state naming neither — agent-workflow verification vocabulary (_WORK_STATE_CUE_RE: "verifier", "refuted", "failed verification", "previous attempts", "project IDs"). Preference-phrased sentences are exempted before any of these checks. Both the fact and the effective profile value (profile_update.value falls back to the fact) are screened.
  • Sink-write guard. A profile_update naming NEITHER category nor key — the shape that lands in the notes.info junk drawer with the whole fact as its value — is dropped entirely (debug log): the fact is already stored in vector memory on the same path, so the sink write was pure duplication that churned the ring on every consolidation. A well-formed profile_update naming its slot flows unchanged; such facts degrade to auto (not identity), the same convention as the non-dict shape above.

Tests: tests/test_project_state_memory_hygiene.py (backstop + workflow cue), tests/test_agent_smart_updates.py (sink guard), tests/test_memory_store_durability.py (log levels).

API

MethodEffect
load() / save(data)Whole-file read / write. load() UNWRAPS to the legacy shape; save() preserves the stamps of unchanged values.
load_raw() -> dictThe on-disk shape, stamps included. Used by update / delete / prune_value / get_context_string — going through load() there would strip provenance on the next save.
as_of(category, key) -> str | NoneWhen this store learned the value (newest stamp for a multi-valued key). None when unknown — never a guess.
stamp(category, key, as_of) -> intAttach provenance to UNSTAMPED items only. Cannot change a value; refuses a falsy date. Returns how many it stamped.
update(category, key, value, as_of=None) -> strMerge-semantic update; returns sync message describing canonical mapping.
delete(category, key) -> strRemove a whole key; status string.
prune_value(category, key, target) -> strRemove list items / a scalar that mention target (token-boundary match); drops the key/category when emptied. Lets forget reach entities stored as values.
get_context_string() -> strFormat for LLM injection.

Per-value provenance — as_of (2026-09-04)

Anchoring (below) fixes decaying facts that have a derivable invariant: an age has a birth date behind it, so the current value can be recomputed. Plenty of facts decay with no invariant — an employer, a location, "currently learning X". For those the only truthful thing the store can say is when it learned them, and a bare string could not say even that.

That gap was not hypothetical. The corpus-repair script could not ask this store when relationships.sons was recorded; it had to infer the date from the contradiction log, a different store — which is why it carries a --said-at flag and a refuse-to-guess rule.

Stamps are per VALUE, not per key

A merging key accumulates its items at different times, so one stamp for the key would be a lie about every item but the last. A scalar becomes {"v": …, "as_of": …}; a list becomes a list of those. Promotion from scalar to list carries the existing item over untouched, so its own date survives.

The reader contract is what makes this cheap

load() returns the legacy shape — every value unwrapped to a plain string or list — so all twelve production readers (enumerated from the AST, not from a hand-written list) are untouched by the migration. Only code that wants provenance calls load_raw() or as_of(). save() re-attaches the stamp of any value handed back unchanged, which closes the save(load()) footgun structurally: once unwrapped the two shapes are indistinguishable, so no convention could.

Quiet by default

A marker only appears where it changes how the fact should be read. A durable key (_DURABLE_KEYS: name, birthday, pronouns, wife, sons, …) is never marked — a name is not more doubtful for being a year old. A perishable value younger than _STALE_AFTER_DAYS = 90 renders exactly as before. Past that it reads (as of 2026-04-01), and past _VERY_STALE_AFTER_DAYS = 365, (as of 2024-02-01, may be stale). An unstamped legacy value is never marked either: absent provenance is not evidence of age. The marker is a fixed date string, so it does not churn the byte-stable {{PROFILE}} prefix.

A restatement refreshes the stamp, on both the scalar and the list path — the user saying a fact again is evidence it is still true, and "last confirmed" is what the marker reports.

Recovering provenance for the existing corpus

scripts/repair_temporal_anchors.py --targets profile-stamps. Dates are recovered, never invented, and only from stores that record a fact WRITE: the minted vector fact (User <key> is <value>) and the contradiction log, which preserves superseded ones verbatim. A document that happens to contain the words records nothing about the profile — the first version matched any corpus mention and dated name = Vasilis from a chess prompt and debugging_tool_macos = dtrace from a PostgreSQL manual. Values shorter than 12 characters are not attributable by text match at all. Anything undatable is reported UNRECOVERED rather than stamped with today, which would date every legacy fact to the day of the upgrade and make the marker lie for a year.

ProfileMemory.stamp() is the write path, deliberately surgical: routing the backfill through update() would re-anchor, canonicalise and cap the values — a migration able to rewrite what it was only supposed to date. It cannot change a value, never overwrites an existing stamp, and refuses a falsy date.

⚠ Deploy order: code, then data. New code reads legacy bare values fine (unwrapping is identity on a string), but an agent still running the older ProfileMemory renders a stamped value as a raw dict — {'v': 'Athens, Greece', 'as_of': …} — straight into every system prompt, and hands the same dict to tool_check_location. The script prints this before applying.

Temporal anchoring — a stated age is not a fact (2026-09-04)

This store renders bare, unstamped - key: value lines into ### USER PROFILE ### on every turn, so anything time-dependent written into it reads as present tense for ever. Live: relationships.sons = "Thodoris (9 years old) and Leonidas (4 months old)", stated 2026-07-07, was still being recalled verbatim two months later.

Two changes, both in this file:

  • update() anchors at the store BOUNDARY — "Leonidas (4 months old)" is stored as "Leonidas (born ~2026-02-20)". Placed here rather than per-caller because every writer funnels through update(): the update_profile tool (both paths), the bus's _profile leg, and smart-memory consolidation. Nothing can bypass it.
  • get_context_string() DERIVES the current value at render time: - sons: Thodoris (born ~2017-01 → ~9 years old) and Leonidas (born ~2026-02-20 → ~6 months old). The disk keeps constants; the prompt gets what is true today, and the model is never asked to subtract a timestamp it will not notice. The gloss is a rounded age, not a date, so the block still changes only when the age changes — {{PROFILE}} is inside the byte-stable system prefix and must not churn daily.

_same_fact() is the dedup change this forced. Anchoring makes two statements of the same fact differ in bytes ("4 months old" in July, "6 months old" in September), so the exact-string merge dedup would have kept BOTH and injected two contradictory birth dates into every prompt. Values carrying an anchor now compare on temporal.signature() — anchor-blind — so the newer statement refines in place. The exemption is deliberately scoped to anchored values: everything else keeps byte-exact semantics, so this cannot silently collapse distinct interests (python and Python still both persist). See memory / temporal.py for the full design, the known limitations, and the corpus-repair script. Tests: tests/test_temporal_anchoring.py.

Audit fixes (2026-07-26)

Fail-closed on transient read errors. ProfileMemory was the only small store without the _degraded discipline its siblings have: an EIO/EACCES read was treated as corruption — the INTACT profile was shunted to a .corrupt-* sidecar, identity reverted to {"name": "User"}, and the next save() overwrote the real file. Now: OSError (≠ FileNotFoundError) serves the default in-memory, leaves the on-disk file untouched, and BLOCKS writes until a read succeeds; parse corruption keeps the sidecar path. save() also fsyncs before the rename (torn-write window). The bus's profile leg and the smart-memory consolidation both now REQUIRE category+key on a profile_update — the old "info"/"notes" defaults minted permanent junk keys like cli_tools.info outside the notes ring (no rotation, no value cap, injected into every prompt). Tests: ::TestProfileFailClosed.
