memory / skills.py — SkillMemory

Lessons learned from past mistakes. Vector-backed retrieval with BM25 re-rank; utility-driven retention; verified-first pinning.

Storage

  • JSON at memory_dir/skills_playbook.json.
  • Vector embeddings stored alongside in VectorMemory with metadata.type = "skill".
  • threading.RLock for JSON reads/writes; lazy-init fallback for tests.

Atomic save (cross-process)

_save_playbook_unlocked writes to a temp file and then os.replaces it over the live playbook (atomic on POSIX). Two problems the in-process RLock alone could not solve — Slack, web and CLI each run their own process — are now closed:

  • Torn temp file. The temp path was FIXED (skills_playbook.tmp), so two processes writing at once interleaved into one corrupt temp that os.replace then promoted. The temp name now carries the writer's PID (skills_playbook.<pid>.tmp), so each process promotes only its own fully-written file. Any leftover temp on the error path is unlinked in a finally.
  • Concurrent promotion. The write + replace is wrapped in an fcntl advisory lock (_crossproc_lock) on a sibling skills_playbook.lock file — mirroring FrontierTracker — so at most one writer (across processes, or two SkillMemory instances in one process) is inside the critical section at a time. On platforms without fcntl the lock degrades to a graceful no-op (the PID-unique temp still prevents cross-process tearing). Covered by tests/test_memory_crossproc_locking.py.

source_refs (2026-07-14): evidence handles the lesson was generalized FROM — e.g. ["ep:12", "ep:15"] for the episode rows behind a dream episode-strategy. Unioned (deduped, capped 20) when a duplicate lesson is merged/reinforced; mirrored onto the vector twin as a comma-joined source_refs metadata string so tool_recall hits can print an EVIDENCE REFS: line. Distinct from source (free-form origin tag) and source_trajectory_id (retraction key). Tests: tests/test_memory_provenance.py.

dimension (2026-07-19): the harness layer the recorded failure was attributed to — see failure_dimension. Auto-classified at the write chokepoint for real-mistake lessons (heuristic regex over trigger + anti_pattern; kill switch GHOST_FAILURE_DIM=0); empty for mistake-less rules, legacy rows, and unclassifiable records (the dream distillation pass adjudicates those offline via the worker). An explicit dimension= kwarg wins. Back-filled onto an existing row on dedup merge; mirrored onto the vector twin metadata. source="distilled" marks the cross-case pattern lessons the dream-side failure_distill pass writes — their distilled(<dim>/<cluster>): trigger prefix is a dedup contract: re-distillation reuses the trigger verbatim so frequency accumulates on one row. Tests: tests/test_lesson_dimension.py.

Lesson-quality gate at the write chokepoint (2026-07-16)

The dream heuristics loop had an actionability gate since 2026-07-13, but it lived inside dream — so self-play and other producers bypassed it, and observations still leaked in. Measured on the live playbook: 23 of 50 lessons were mistake-less pseudo-entries and they drew 28% of all retrievals — the single most-retrieved item being a dream chess-persona note ("When playing live chess against Vasilis, provide continuous coaching commentary", 84 retrievals), alongside self-play observations ("On a regex_parse task that has a familiar shape…") and user preferences ("The user prefers ripgrep") that match no real query.

The gate now runs at learn_lesson — the single write chokepoint, so it covers every producer (dream, self-play, reflection, episode consolidation). The logic (memory/lesson_quality.py, a leaf module shared with core.dream to avoid an import cycle): a lesson that records a real mistake is a genuine correction and always passes; a mistake-less entry is a rule/observation, so its solution must read as an actionable heuristic (_is_actionable_heuristic — imperative starter, or conditional + modal). verified gets no bypass — it would only ever exempt a verified observation (a verified fix has a mistake; a verified actionable rule passes anyway). The 11 non-actionable lessons on the live playbook were pruned retroactively (50 → 39; backup at skills_playbook.json.pre-quality-prune-20260716), and their orphaned vector twins were then deleted in-process via VectorMemory.delete_skill_twins (POST /api/memory/delete_skill_twin — a second PersistentClient against the live Chroma dir risks HNSW corruption, so the delete must run inside the owning process; 11 twins removed, 7315 → 7304 docs, verified idempotent). This is the content-quality complement to the 2026-07-15 retrieval-routing fix: routing now surfaces lessons (mediation ~1% → ~85% in B4), and this stops ~a quarter of what surfaces from being noise. Tests: tests/test_lesson_quality_gate.py, tests/test_delete_skill_twins.py.

Trivial tool-routing floor (2026-07-29): a mistake-less rule whose entire content is a bare topic→tool mapping — "When asked about the weather, use the system_utility tool.", minted by REM from a single one-shot success — is rejected by _TRIVIAL_TOOL_ROUTING_RE inside _is_actionable_heuristic. The tool registry / router already encodes that mapping (the agent routed the minting turn correctly WITHOUT the lesson, which is exactly how the lesson got minted); such entries dilute retrieval without adding behaviour. Rules that add anything past the tool name ("…use system_utility with location defaulting to Athens") still pass, and real-mistake lessons are untouched. Tests: tests/test_log_audit_fixes_2026_07_29.py::TestTrivialToolRoutingFloor.

Conversational-trigger gate (2026-07-18)

The 2026-07-16 gate waved through any lesson carrying a real mistake. The 2026-07-17 overnight REM cycle showed the gap: genuine mistakes attached to TRIGGERS lifted verbatim from user chat — "proceed with the next task", "it still does the same. the game never starts, notify me in slack when…". A trigger is the lesson's retrieval key; raw conversation fragments are keys no future query will match, so such entries are permanent playbook noise however real the mistake was.

_is_conversational_trigger (in memory/lesson_quality.py) now also gates mistake-bearing lessons. Default-ACCEPT — only unambiguous chat tells reject: pronoun-initial fragments with no antecedent ("it still does…", "that didn't work…"), short bare turn-level commands ("proceed", "try again", ≤ 60 chars), and direct-address phrases ("notify me in slack", "let me know"). Deliberately NOT rejected: user-question triggers ("How do I parse JSON?", "Please parse JSON!") — the paraphrase-normalised dedup counts on them recurring — and "you"-phrasing, which is legitimate rule language addressed to the agent. Tests: tests/test_lesson_quality_gate.py::TestConversationalTrigger.

Retention & eviction

PLAYBOOK_MAX = 300 under ACE (GHOST_PLAYBOOK_MAX; the historical default was 50). Trim policy:

  1. Newest lesson is always kept (head pin).
  2. Verified lessons pinned next.
  3. Remaining slots filled by unverified, ranked by utility.

Utility formula

utility = confidence·0.5 + hit_rate·0.8 + (0.3 if verified) + log(freq)·0.1 + stale_penalty
        × outcome_mult   # 2026-07-24, once ≥ _OUTCOME_MIN_OBS decisive outcomes accrue

outcome_mult (2026-07-24): hit_rate above is relevance-gated success credit only — a lesson can lose rank by not being credited but never by being present when a turn failed. The outcome arms close that gap: out_rate = (succeeded_retrievals + 1) / (succeeded + failed + 2) (Beta(1,1)-smoothed present-on-success fraction), and outcome_mult = 0.4 + 0.75·out_rate — ×0.40 for a lesson present only on failures (sinks it below the prune cutoff), ×1.15 for one present only on passes. Cold-start-safe: neutral until _OUTCOME_MIN_OBS = 4 decisive outcomes accrue, so a fresh lesson is never punished for one unlucky co-occurring failure. Kill switch GHOST_LESSON_OUTCOME_UTILITY=0 makes the arms record-only (bookkeeping without the ranking effect). See Outcome-gated learning loop below.

Retrieval (three-tier, picked by query + memory_system presence)

get_playbook_context(query, memory_system, distance_threshold=0.45, limit, record_retrievals) dispatches to one of three paths:

  1. Vector path — memory_system AND query both present. Runs a Chroma query over type="skill" docs, tightens by DEFAULT_RETRIEVAL_DISTANCE = 0.45, then re-ranks with a BM25-lite keyword-overlap bonus. Best path; used whenever the bus wires a vector tier. Domain rescue (2026-07-09): the 0.45 floor demands near-verbatim similarity (~cosine 0.78 on the L2-normalised MiniLM embeddings), which a GENERALIZED lesson can never reach against a concrete task prompt — measured live on the B4 run: the arm's real self-play lesson sat at distance 1.056 from a matching probe, so the skill tier filtered it on all 96 probe turns and the learning loop was write-only (mediation ≈ 0). A candidate past the strict floor is now admitted up to _DOMAIN_RELAXED_DISTANCE = 1.25 when its domains metadata contains the query's cluster per _explicit_query_cluster() — which requires an explicit CLUSTER_KEYWORDS hit (NOT classify_cluster, whose python_general fallback would let every small-talk turn "match"). Untagged lessons (e.g. reflection writes) derive a domain from their trigger text. Semantic near-match OR domain match — never a blind dump. Tests: tests/test_lesson_retrieval_domain_gate.py (incl. the forensic B4 reproduction).
  2. BM25 fallback — query is present but memory_system is None (vector store offline, init failed, or a bus is wired without a vector tier). Scores each lesson's trigger by IDF-weighted coverage of the query and admits it only above _BM25_MIN_SCORE. Returns "" if nothing clears the floor — never falls through to recency.
    ⚠ Fixed 2026-08-11 (§4AP) — it used to match almost anything. The score was the raw fraction of query tokens present in the trigger, with no IDF and no stopword filter, and the gate was score > 0. One shared the scores 1/9, so on the live 50-lesson playbook "what year did the treaty of westphalia end the thirty years war", "describe the mating rituals of the emperor penguin in antarctica" and "how do i bake a sourdough loaf" each retrieved 5 tool-use lessons; only literal gibberish scored 0. This branch is reachable in production — main.py assigns context.memory_system inside a try/except that logs and continues, so a VectorMemory init failure routes every turn through it.

    The fix is a stopword filter plus standard BM25 IDF built from the playbook's own triggers, ln((N−df+0.5)/(df+0.5)+1), scoring coverage of the query's information mass. IDF is what makes it self-calibrating — no hand-written list can track which words are boilerplate in this playbook, but the corpus always knows. Both guards are needed: a stopword appearing in exactly one trigger would otherwise earn a high IDF and become the strongest match. The same IDF corpus feeds the vector path's re-ranker, so a term is worth the same on both paths.

    The floor is calibrated, not chosen. On the live playbook: unrelated queries score 0.00–0.20, genuine paraphrases 0.26–0.54, near-verbatim task queries 0.66–1.00. _BM25_MIN_SCORE = 0.30 (override with GHOST_BM25_MIN_SCORE) clears every unrelated query by 50%. The two paraphrases it drops were both matching a wrong lexically-similar trigger — "shut down the chess server" pulling a chess post-mortem lesson — so dropping them is correct. Precision over recall is deliberate here: this branch only runs when the vector store is already down, so a missing lesson costs what the outage already costs, while an irrelevant one actively pollutes the prompt. Pinned by tests/test_bm25_fallback_relevance.py, where every rejection case is paired with a must-still-retrieve case.
  3. Recency fallback — no query supplied (system-prompt-injection usage). Returns the N most recent lessons regardless of content, under the ## RECENT LESSONS header.

Before the fix, the recency fallback fired whenever the vector path was unavailable — including on a real query. A question like "what's the capital of France?" would surface an unrelated Python-syntax lesson just because it happened to be the most recent entry, polluting context with junk. The new three-tier dispatch preserves the recency path ONLY for the no-query case (the SYSTEM_PROMPT cold-inject). Covered by tests/test_skills_bm25_fallback.py.

When a lesson is surfaced, record_retrieval increments the counter and emits a debug log keyed by source + source_challenge_hash — so the "is this self-play lesson ever actually used?" question has data to answer.

Dedup

Vector similarity check (distance < 0.20; < 0.21 for mistake-less rules — recalibrated 2026-08-08 (§4M): the live corridor between "reworded twin" and "distinct rule" shrank to [0.192, 0.213] (rewordings reach 0.1921, distinct rules come as close as 0.2134), leaving the original 2026-07-20 pair 0.15/0.25 outside it from both ends — reworded twins re-saved AND a distinct-rule pair sat inside the admit zone. The metric is chroma-default squared-L2 on normalized embeddings (= 2× cosine distance). Override with GHOST_RULE_DEDUP_DIST, tests tests/test_skill_dedup.py::TestMistakeLessWideThreshold + the §4M corridor pin) or a normalized trigger match merges frequency + solution instead of inserting a duplicate. The JSON fallback no longer requires an exact lowercased string: _normalize_trigger() lowercases, strips punctuation, drops stopwords and sorts the remaining significant tokens, so paraphrased triggers ("How do I parse JSON?" ≡ "parse JSON") collapse onto the same key and frequency actually accumulates toward graduation.

Vector-hit twin lookup + orphan self-heal (2026-07-29): the vector-dedup bump used to search the playbook under the incoming trigger only — but a reworded near-duplicate's JSON twin is stored under its own trigger, so every reworded re-learn logged "no JSON twin to bump" and silently dropped, starving the frequency counter. The bump now retries under the stored duplicate's own trigger (recovered from the vector hit's trigger metadata, falling back to the document's SITUATION: line via _dup_trigger_from_vector_text). When NEITHER trigger matches a playbook row, the vector entry is a TRUE orphan (residue of a partial scrub) — previously it vetoed that lesson on every future attempt; now the orphan is deleted and the lesson written fresh (learn_lesson returns "written"), leaving both stores consistent. A bulk sweep, reconcile_vector_orphans(memory_system, limit=2000), runs as a rider on the skills-auto idle cooldown (wired in agent.py): it scans type="skill" vector entries and deletes those with no playbook twin — the twin test is token-subset so a metadata trigger truncated at 200 chars still matches its full twin, and entries with no recoverable trigger are never deleted blind. Tests: tests/test_log_audit_fixes_2026_07_29.py, tests/test_skill_dedup.py.

§4M twin-destruction fix + heal (2026-08-08): the twin's metadata stores the row's trigger, but both cleaners above keyed the playbook task-first — self-play/dream rows have task ≠ trigger by design, so their healthy twins tested as orphans and were deleted (~1 per idle cycle live; 36/50 lessons went dark to bus retrieval, which has no BM25 fallback when the vector branch answers). Three facets fixed: the reconcile now indexes both fields per lesson; an untruncated metadata trigger must cover ≥ half of the matched field's token set (a bare subset let a TRUE orphan hide forever behind any unrelated lesson containing its few tokens); and the reworded-twin re-locate gained the or trigger == clause the primary lookups already had. The inverse pass, heal_missing_twins(memory_system, limit=2000), runs on the same idle cooldown: it re-embeds playbook lessons whose vector twin is missing (matched by normalized trigger-or-task at the write's own [:200] truncation), preserving the lesson's original timestamp so healed twins don't jump the eviction queue. Idempotent — the stores converge from both directions. Pins: tests/test_learning_stack_audit.py (§4M block).

Listing lessons (user-facing surface)

list_lessons(scope, source, limit) returns lessons filtered by time window and source, most-recent first. Boundaries use local wall-clock:

  • scope="today" — since local midnight.
  • scope="week" / "7d" — last 7 days.
  • scope="all" — entire playbook.
  • source="self_play" (etc.) — filter by provenance.

Surfaced to the LLM via the list_lessons tool (see tools / memory). Phrases like "what did you learn today?" / "what have you learned so far?" are routed to this tool via SYSTEM_PROMPT.

Lesson quarantine + hydration side-channel (2026-07-17)

quarantine_lesson(trigger, reason) marks matching playbook entries quarantined — excluded from BOTH retrieval surfaces (get_playbook_context and get_playbook_items share the _filter_quarantined chokepoint, covering the vector branch too) but kept on disk with reason + timestamp for operator review/reinstatement. Written for counterfactual replay's regression verdicts — a false regression must never silently delete a good lesson. Additionally, get_playbook_context stashes last_playbook_triggers (the lessons that actually entered the prompt this turn; turns are globally serialized) and _record_turn_trajectory stamps them into the trajectory's extra.hydrated_lessons — the attribution set a future regression points at.

Outcome-gated learning loop (2026-07-24)

The gap it closes. The retrieval-feedback loop was credit-only: record_helpful_retrieval and credit_recent_retrievals increment helpful_retrievals when a turn succeeds and the lesson is relevant, but nothing ever debited a lesson for being surfaced on a turn that FAILED. So hit_rate = helpful/(retrievals) conflated two very different populations — "present on a success it wasn't credited for" and "present on a failure" — and a genuinely harmful lesson could ride along on failing turns invisibly, its retrievals climbing while nothing marked it as a liability. This is the experience-following failure mode (a retrieved memory is reproduced whether or not it is appropriate; good and bad lessons transfer with equal fidelity). The prior scrub path (retract_lessons_from_trajectory) only removes lessons authored in a failed turn — never lessons retrieved into one.

The mechanism. Two new arms — succeeded_retrievals / failed_retrievals — record, per lesson, the verified outcome of the turns it was surfaced into (fed by record_surfaced_outcomes). compute_lesson_utility folds the ratio in via outcome_mult (above), so a lesson persistently present when turns fail loses utility and becomes a prune_low_utility candidate — the loop closes through the existing, bounded prune machinery (≤ 25%/pass, verified pinned, needs ≥ 5 retrievals). No new destructive path.

Grounding — it uses the real outcome, not an LLM judge. The separate judge_hydration_usefulness path (in MemoryBus) credits via a worker LLM's opinion of whether a snippet looked used in the reply; that is a surface signal and LLM-judge-based curation silently fails to retire bad items. The outcome arms instead key off resolve_turn_outcome (passed/failed) — a structural execution failure or a real verifier verdict. Only decisive outcomes are recorded; a turn that never earns a verdict contributes nothing, so the arms never fill from mere absence-of-failure.

Wiring (both finalize paths + the async-critic late path). Agent._record_lesson_outcomes runs at finalize on both outcome classes (outside the success-only credit gate). When the outcome is decisive at finalize (a structural execution failure, or an inline verifier verdict) it records immediately. When it is undecided — a clean turn whose async-critic verdict has not yet landed (the production case) — it stashes the surfaced triggers by trajectory_id in a bounded map; _backfill_trajectory_outcome drains that stash via _flush_stashed_lesson_outcome when the late verdict arrives. This gives the late-verdict path a second consumer and captures the verifier's REFUTED signal (the strongest "this answer was wrong") that a finalize-only hook would miss.

Observability. Per-turn recording emits one logger.info line to the grep-friendly FileHandler log ($GHOST_HOME/system/ghost-agent.log, the same sink as Hydration tiers and other per-turn diagnostics — NOT the pretty console stream at Logs/ghost-agent.log, which is WARNING+ only): lesson-outcome: N surfaced lesson(s) -> present-on-{FAILURE|success}, plus … stashed N surfaced trigger(s) for traj … (await late verdict) on the async-defer path. Routine per-turn ticks stay off the operator's pretty stream by design. The one actionable event — the loop retiring a lesson that kept riding along on failures — DOES go to the pretty stream, named: SKILL PRUNE … K outcome-gated (present-on-failure): '<trigger>' (succ=…,fail=…), so a prune driven by the failure arm is legible (not buried as generic "low-utility"). Audit grep: grep lesson-outcome $GHOST_HOME/system/ghost-agent.log.

Defaults & safety. Recording is always on (pure bookkeeping, zero behaviour change). The ranking/prune effect is cold-start-neutral until _OUTCOME_MIN_OBS = 4 decisive outcomes accrue and is governed by GHOST_LESSON_OUTCOME_UTILITY (default on; set 0 for record-only, so the operator can watch the arms fill before letting them prune). Verified lessons remain pinned regardless — verification outranks co-occurrence statistics. The read-only skill proxies (ReadOnlySkillMemory, dream's sim proxy) block record_surfaced_outcomes so idle simulations never mutate the production playbook. Tests: tests/test_lesson_outcome_utility.py.

§4AO — why the prune stays off: three measured defects (2026-08-11)

scripts/label_noise_audit.py (read-only, no LLM) asked whether the per-turn outcome label is wrong often enough to explain the prune's behaviour. It is a contributor, but not the only one, and fixing the judge alone would not make this ranking safe.

  1. Label noise decides about half the victim set. Measured against the oracle bench: false-REFUTE 0.121, false-CONFIRM 0.242. Simulating both worlds from the same true rates — ticks recorded perfectly vs passed through those rates, sampling noise held fixed — the kill list differs in 96.2% of 2000 replicates, and 51.9% of the victim set is decided by the label alone.
  2. The ranking is not identifiable at this evidence level. χ²=38.23, dof=29, p=0.117 across the 30 lessons carrying any decisive outcome: the spread is consistent with every lesson sharing one true success rate, and 61% of the observed variance in per-lesson rates is what binomial noise alone predicts. Separating a lesson 6pp below the pool at 80% power needs ~418 decisive outcomes per lesson; the median today is 3, and the whole playbook holds 324.
  3. The multiplier is mis-centred, so having evidence is a penalty. 0.4 + 0.75·out_rate crosses 1.0 at out_rate 0.80, but the live playbook pools at 0.7407. A lesson at the population mean is multiplied by 0.9556 (a 4.4% demotion) while a lesson with fewer than _OUTCOME_MIN_OBS decisive outcomes is multiplied by 1.0 and pays nothing. Measured rank movement from the multiplier alone, all downward: ↓15, ↓15, ↓13, ↓10, ↓9, ↓6. That is why the kill list is headed by the four most-measured lessons in the playbook (297, 217, 27, 17 retrievals, 64–75% success) — they are condemned for having been measured.
⚠ Bias is not the same as variance, and only one of them matters here. The first version of this audit de-attenuated each lesson's observed rate to its noise-corrected truth and found the same victims — and concluded label noise was exonerated. That was an artifact: (observed − FCR)/(1 − FRR − FCR) is monotone, so removing the label's systematic bias cannot reorder a rank-based prune. A bottom-quartile cutoff is structurally immune to bias; what corrupts it is variance. An audit built the first way can only ever exonerate.
⚠ A rank cutoff is decided only by the lessons adjacent to the boundary. Population-level separation is irrelevant — the boundary has to fall in a gap. Identical lessons tie exactly and the cutoff slices arbitrarily through the tie; lessons spaced closer than the standard error of their own counts are ordered by noise. Both are pinned in tests/test_label_noise_audit.py, whose load-bearing pair is two-sided: the counterfactual must convict where noise decides the victims and exonerate where the evidence is ample.

What would have to change. Re-centring the multiplier on the playbook's own pooled rate, and replacing the relative-quartile cutoff with an absolute one, are both necessary and neither is sufficient — at a median of 3 decisive outcomes per lesson no cutoff ranks lessons rather than noise. Note that compute_lesson_utility also drives the live cap-trim (_trim_playbook_by_utility, which fires on every write once the playbook is full), so re-centring it is an operator-visible retention decision, not a silent fix.

§4EG — ACE grow-and-refine: the cap no longer sheds proven lessons (2026-09-03)

The playbook cap is free on prompt budget — injection is a top-k retrieval under the bus governor, so store size never reaches the prompt. A low cap therefore only shed knowledge: measured 2026-09-03 the store sat at 50/50 and cap-trim had dropped 664 lessons, 50 of them with positive net outcome credit (one at 28 retrievals, 7 succ / 4 fail). Retrofitting ACE's grow-and-refine discipline: GHOST_ACE_PLAYBOOK=1 (default) raises the cap (GHOST_PLAYBOOK_MAX, default 300) and pins a lesson that is verified OR has positive net outcome credit (succeeded_retrievals > failed_retrievals). _trim_playbook_by_utility then keeps the store oversized rather than ever evict a protected lesson (fail-open, like the archive path); the cap can only target unproven or proven-harmful lessons, which also sink in retrieval ranking and are never injected. prune_low_utility skips protected lessons too. Kill switch GHOST_ACE_PLAYBOOK=0 restores the exact legacy cap=50 + drop-lowest-utility rule. Archive replay: of the 50 usefully-dropped lessons, grow-and-refine retains 50/50 vs 2/50 under the legacy cap. Pinned in tests/test_4eg_ace_playbook.py including the kill-switch differential.

Probe lessons and the reflection kind filter (§4FB, 2026-09-06)

Reflection now mints only from trajectories whose task_kind is in admitted_task_kinds("reflection") (today: user_request), so bench, self-play, reflection and probe rows never become lessons. Lesson provenance (§4FD, 2026-09-07)

Every lesson record now carries origin: "user" (written during a real user request), "auto" (idle machinery — reflection, dream, post-mortem, distillation — or an internal sched-/job-/sub- turn), "probe" (a diagnostic; must never teach, stamped so a leak is visible), "bench", or "" for legacy rows. A frequency bump needs new evidence 2026-09-30 §4KS

frequency is read as "how many independent times this lesson was learned": it lifts the utility score and, at three, makes a lesson eligible for graduation. Both dedup branches (exact trigger and vector match) bumped it on every re-learn, whatever the re-learn was derived from. In one day's log a distilled lesson stood at 84 "from 5 cases" (re-synthesised each time its cluster changed), a dream heuristic went 13 → 16 by re-reading a 60-fragment window of which 57 were unchanged, and a replay of the same self-play challenge bumped its lesson again.

A re-learn now names what it was derived from — the trajectory id, the challenge hash, source_refs, and the new evidence_refs — which is digested and remembered on the lesson (evidence_keys, newest 240). A dedup hit counts only if it brings a key the lesson has not seen (evidence_is_new). For a window a caller re-reads, the caller asks for a share: the dream passes its fragment window with evidence_min_new_fraction=0.5, so a re-derived heuristic counts again only once half the window is fragments it has not been derived over; a re-detected [Pattern] names the pattern and its support, so it counts again only when the support changed. A re-learn that names no evidence bumps as before — unknown provenance is not stale provenance. Rows written before this carry no keys; their own provenance fields count as seen.

What this costs. Replayed over four days of dream cycles, 29 bumps become 2. A period with only self-play traffic adds few fresh fragments, so dream heuristics stop climbing during it — that is the intent, but it also means a rule that is genuinely re-confirmed by the same material gains nothing.

Pins: tests/test_4ks_log_review_fixes.py (block H, both dedup branches), with an AST enumeration that every frequency assignment in learn_lesson sits under the evidence test.

A lesson for one request stays with that request 2026-10-02 §4KW

Two kinds of lesson (memory/lesson_scope.py):

  • scope="request" — one request's corrected plan, with its source_request. It enters a prompt only when the new request IS that request (same_request; superseded — the current rule is in the fourth review): character similarity ≥ 0.85, or the shorter request's content words all in the longer one and at least half its size.   • a general lesson — its trigger names a SITUATION CLASS. Retrieved by relevance, as before.

How triggers are made now. The reflection prompt asks, besides the plan, for a GENERAL LESSON block (SITUATION / MISTAKE / RULE in general terms, or NONE). The plan is written request-scoped; the rule is written as a general lesson only when the plan judge CONFIRMED the plan and is_general_trigger / is_general_text pass (no URL, path, @-mention, quote or number from the request; at most half its content words the request's). A vector twin from the other scope is written fresh, never merged.
