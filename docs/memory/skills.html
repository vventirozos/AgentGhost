skills — the lesson store (removed)

2026-11-06 §4TD The lesson store is gone: memory/skills.py (SkillMemory, the playbook skills_playbook.json), memory/lesson_scope.py, memory/lesson_quality.py, and the two model tools learn_skill and list_lessons. The page keeps its file name so old links still work.

"Skills" in this file name meant lessons: a mistake and its fix, written down and put back into later prompts. It never meant the custom tools the agent writes for itself. Those are acquired skills (create_skill, manage_skills), and they are unchanged.

What it was

A JSON playbook of lessons under the memory directory, each one a trigger ("when …"), the mistake and the fix. Every lesson also had a copy in the vector store (its "twin", a row of type skill) so it could be found by meaning. Lessons were written by reflection, by the idle "dream" pass, by post-mortems and by the model's own learn_skill call; they were scored by how often they were shown and whether the turn that saw them went well; and the best matches were put into the prompt as a "SKILL PLAYBOOK" block. The store had its own dedup, quarantine, pruning, retraction after a refuted turn, and a scope rule (a plan for one request was shown only when that request came back).

Why it was removed

Measured on 27 days of live data (journal §4SZ):

  • The automatic lessons had been out of every prompt since 2026-10-13 (§4ON): a blind comparison on real owner requests found they added nothing, and replies were about 45 % slower with them.
  • 26 lessons were still in the store. list_lessons still listed them and the learning report still described them as live.
  • learn_skill had 0 calls in 30 days.
  • The idle producers were removed in §4NM (2026-10-11) and the replay loop in §4SZ (2026-11-05), so nothing wrote a lesson any more except the model's own call.
  • The two tool definitions and the prompt rule that routed to them were part of the cached head of every request.

What replaced it

  • Owner rules. What changes the agent's behaviour is a rule the owner states: learn this rule: …. The rules are shown on every owner turn. See Owner rules.
  • Custom tools for things the agent should be able to do again: create_skill / manage_skills. See acquired_skills.
  • The experience store (human-graded past turns) is unchanged. See experience.

What went with it

  • the tool definitions, handlers and dispatch entries of learn_skill and list_lessons; the system prompt's LESSONS SURFACE rule; the pointers to list_lessons in the manage_skills and introspect descriptions;
  • in the turn loop: the "SKILL PLAYBOOK" prompt block and its per-request cache, the retrieval credit and the outcome credit after a turn (with their two rings on the context), the retraction of a turn's lessons after a refute, a correction or a thumbs-down, the refusal of learn_skill on a probe's or a member's turn, and every list that named the two tools;
  • the lesson tier of the memory bus (skill): its fetch, its credit after fusion, its fan-out leg on a write. See bus;
  • the lesson credit that ran when a thumb was recorded (/api/feedback). The label, the hint after a thumbs-down and the mood hook are unchanged. See feedback;
  • the operator routes POST /api/lessons/quarantine and POST /api/memory/delete_skill_twin;
  • the two lesson passes of the idle store-hygiene job (drop orphaned twins, re-embed missing ones) and the same pair at boot. The job still removes expired temporary video transcripts;
  • the lessons block of the learning report, the lessons.playbook row of the loop-yield report, and the lesson count on the health check (the line is now "Rules"). See introspect and system;
  • the lesson rows of the privacy forget preview and the lesson step of reset_all;
  • the "recent mistakes" the diary rewrite read from the store;
  • the read-only wrappers of the store (ReadOnlySkillMemory in isolation and in readonly).

The simulated-context marker

The read-only wrapper did a second job: its is_read_only attribute was how about ten guards recognised a simulated context (an isolated replay, a coding leaf). With the store gone, the marker is one explicit flag on the context, simulated. It is stamped by mark_simulated at the two places the wrapper was installed and read through is_simulated_context. A copy that will not take the stamp is refused. The table of guards is on the isolation page.

What still holds

  • Old data is purged at deploy. scripts/lesson_purge_4td.py, run with the agent stopped, exports the vector rows of type skill to a backup dir, reads the export back, deletes exactly those rows and moves skills_playbook.json, its lock file and skills_pruned_archive.jsonl to the same dir. Without the purge forget would answer "Nothing stored matches" while those rows and files still quoted the name. Nothing reads, rewrites or creates these files any more. A row deleted this way stays in the bytes of chroma.sqlite3 (its write-ahead queue and free pages) until the file is compacted.
  • The lesson copies in the vector store are never served. They are the rows whose metadata type is skill. Only the purge above deletes them, and no search returns one, purge or not: every read path asks the store to leave that type out and drops any such row that comes back (RETIRED_ROW_TYPES in vector). The privacy forget neither lists nor deletes them; reset_all erases the whole collection, these rows included.
  • A model that still calls learn_skill or list_lessons (from old conversation history) gets the ordinary unknown-tool reply with the list of tools. Neither name is ever mapped onto a similar tool, whatever custom tool exists.
  • Small helpers other code used moved: the turn's request text and the word-folding used by forget are in memory/request_text.py; "which population is writing" and "may this stored turn be learned from" are in memory/population.py.
  • The probe arm no_lessons still exists: a labelled probe sent with it is shown no owner rule.
