memory / contradiction_log.py — ContradictionLog

Append-only audit log of belief revisions. Drives "I previously thought X, but updated because…" explanations.

Storage

  • JSON at memory_dir/contradiction_log.json.
  • FIFO cap MAX_ENTRIES = 200.
  • Atomic temp + os.replace; threading.RLock.

Load hardening (2026-07-22)

_load() distinguishes three outcomes rather than the old except Exception: return [] that made an unreadable file behave exactly like an absent one — so the next record() atomically overwrote 200 entries of belief-revision history with a single entry, silently:

  • absent → [] (normal cold start);
  • corrupt (bad JSON / wrong type / undecodable bytes) → move the raw bytes to a timestamped contradiction_log.corrupt-*.json sidecar, WARNING, start clean;
  • present-but-unreadable (OSError — EIO / EACCES) → return [] for reads but set _degraded (logged at ERROR); while set, _save() REFUSES to write. The flag clears automatically as soon as a read succeeds.

__init__ now probes via _load() at construction — not lazily on the first record() — specifically because clear() writes without reading: a lazy check left one path that could overwrite a corrupt / unreadable file without preserving it. Tests: tests/test_memory_store_durability.py.

Entry shape

{
  "timestamp":   "ISO",
  "new_fact":    str,
  "superseded":  [{ "id": str, "text": str }],
  "deleted_ids": [str],
  "reason":      str
}

API

MethodPurpose
__init__(memory_dir)Open log file; probe via _load() so an unreadable / corrupt log is detected (and quarantined) at boot.
record(new_fact, old_facts, deleted_ids, reason="") -> boolAppend a revision. Returns whether it actually landed — False when the store is degraded and the write was skipped. It previously returned None either way while still logging "Belief revised", so a caller that had already performed an irreversible delete could not tell that the erasure went unrecorded.
get_recent(limit=10)Most recent entries.
explain_belief_change(query)Find revisions relevant to a message and render the top 5, best match first. See the matching section below.
clear()Wipe (refused while _degraded, so it can't overwrite an unreadable file).

Audit fixes (2026-07-26)

explain_belief_change actually fires now. Matching required the WHOLE query to be a substring of a stored fact, while the production caller passes the entire user message — "what car do i drive now?" in "user drives a bmw" is never true, so the 2026-07-20 wiring stayed inert for any multi-word message. Matching became significant-token overlap (stopword-screened, prefix-tolerant for inflections like drive/drives), with exact containment still honored. Saves also fsync before rename. Tests: ::TestBeliefChangeMatching.

Matching, and how it was over-corrected (2026-08-08)

The un-inerting fix above swung the failure to the opposite extreme, and it took replaying the matcher against real data to see it. Measured on the live 96-entry ledger, it fired on 67 of 67 memory-hydrating turns — every one — injecting roughly 215 tokens of near-arbitrary history into the prompt under an authoritative ## BELIEF REVISION HISTORY: heading. Four things combined to cause it:

  • One shared token was enough, taken over the full cross-product of query and entry tokens.
  • Prefix tolerance was unbounded, so code matched codename and dark matched darkweb.
  • Stopwords were screened on the query side only. Words like user (present in 50 of the 50 entries then searched) and project (48 of 50) therefore matched nearly any message.
  • The five results were the five most recent, not the five best — and the search window was capped at the newest 50 entries, of which 46 were one burst of self-play churn. Every genuinely useful revision sat beyond that window and was unreachable.

Matching now requires at least two shared content tokens covering at least a third of the query, screens stopwords on both sides, bounds prefix tolerance to near-equal-length pairs, ranks by relevance before truncating, searches the whole (capped) ledger, and renders the stored reason — which every entry carries and none previously displayed.

Why a ratio and not just a count. A flat two-token floor looks sufficient and isn't: long messages clear any fixed count incidentally. Replayed over 240 real user turns, a floor of two still fired on 61% of them, and on messages with 16+ content tokens it fired 98% of the time. Requiring proportional coverage brought that to 36% with the length bias gone. Both numbers came from real traffic — an earlier estimate drawn from a hand-picked sample of ten queries suggested 20% and was simply wrong.

Recall is deliberately limited in exchange. A token matcher cannot connect "what car do I drive?" to "the user owns a BMW" — they share no words — and single-content-token questions no longer match at all. That is the right direction to fail: a missed explanation costs nothing, while a spurious one enters the prompt as authoritative history. Tests: tests/test_belief_revision_4r.py.
