Install and run it

Four things have to be running before Ghost will start. Get those right and the rest is one command.

The order matters

Ghost is not a standalone program — it's a coordinator. It expects three other services to already exist, and it checks for them at boot. Start them in this order.

  1. An LLM server

    Anything that speaks the OpenAI chat API: llama.cpp's llama-server, vLLM, or Ollama. Ghost's prompts are tuned for Qwen 3.6 35B-A3; a much smaller model will follow the tool-calling format badly and you'll see a lot of failed turns.

    Ghost connects to this via --upstream-url. Default: http://127.0.0.1:8080

  2. Docker

    The daemon needs to be running before Ghost starts. Every piece of code the agent executes goes into a container — no Docker means the execute, browser and file tools can't work.

    Ghost talks to the Docker socket directly. You don't need to build anything; it pulls python:3.11-slim-bookworm on first use.

  3. Tor

    A local Tor daemon listening on 9050. Ghost probes it at boot and refuses to start if it's unreachable. That's on purpose — see Safety and privacy.

    On macOS: brew install tor && brew services start tor

  4. Ghost itself

    Once the three above are up, start the agent.

Install

git clone <your-repo> Agent
cd Agent

python -m venv venv
source venv/bin/activate
pip install -r requirements.txt

The first install pulls in ChromaDB, sentence-transformers and PyTorch, so it's a large download and takes a while. That's a one-time cost.

Environment variables

Four of these matter. Set them in your shell profile or a startup script — Ghost reads them at boot, not from a config file.

export GHOST_HOME="$HOME/ghost"          # where everything is stored
export GHOST_API_KEY="<a long random string>"
export GHOST_MODEL="qwen-3.6-35b-a3"     # must match your LLM server's model name
export TOR_PROXY="socks5://127.0.0.1:9050"
VariableDefault if unsetWhat it does
GHOST_HOME ~/ghost_llamacpp The root of everything Ghost owns: memory, logs, the sandbox, learned skills, trajectories. Back up this one directory and you've backed up the agent.
GHOST_API_KEY none The key clients send as an X-Ghost-Key header. Required if you bind to anything other than localhost.
GHOST_MODEL qwen-3.6-35b-a3 The model name Ghost asks the upstream server for. If this doesn't match what your LLM server serves, every request fails.
TOR_PROXY socks5://127.0.0.1:9050 Where the Tor SOCKS proxy lives. The default is correct for a standard local Tor install.
Not a real setting: GHOST_SANDBOX_DIR appears in some older instructions but nothing reads it at startup. The sandbox directory is always $GHOST_HOME/sandbox. Setting it has no effect.

What lives under GHOST_HOME

sandbox/
The working directory shared with the Docker container. Files the agent creates for you land here.
system/memory/
All six memory stores — the vector database, the graph, your profile, learned lessons, the journal, past episodes.
system/ghost-agent.log
The durable log. The live console shows a cleaner version of the same thing.
trajectories/
A record of each turn, used by the background learning passes. Safe to delete; you just lose training material.

Start it

python -m src.ghost_agent.main \
    --upstream-url "http://127.0.0.1:8080" \
    --host 127.0.0.1 --port 8000 \
    --verbose

Boot is noisy on purpose — it prints each subsystem as it loads, so a hang tells you exactly which one is stuck. Expect it to take 30–60 seconds the first time while the embedding model loads.

Binding beyond localhost. --host 0.0.0.0 makes Ghost reachable from your network. It will refuse to start in that mode unless you've either set a real GHOST_API_KEY or passed --api-key '' to knowingly turn auth off. An unset key on a public bind is indistinguishable from a mistake, so Ghost treats it as one.

Check that it actually works

"It started" and "it works" are different things. Ghost can boot in a degraded state where HTTP answers fine but memory never loaded. The health endpoint is how you tell.

curl -s -H "X-Ghost-Key: $GHOST_API_KEY" \
     http://127.0.0.1:8000/api/health | python -m json.tool

Three fields are worth reading every time:

memory_system_loaded
Must be true. If it's false, Ghost booted without memory — it will still answer you, but it remembers nothing and every background learning pass is silently disabled.
biological_watchdog_alive
Must be true. This is the background loop that consolidates memory and learns while idle. If it's false, that daemon died and Ghost has stopped improving.
nodes
Which extra LLM machines are wired up, by role. An empty list for a role means that work runs on your main model instead. Not a problem — just worth knowing.

Then send it something:

curl -s -X POST http://127.0.0.1:8000/api/chat \
  -H "X-Ghost-Key: $GHOST_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"'"$GHOST_MODEL"'","messages":[{"role":"user","content":"What is 2+2? Answer in one word."}],"stream":false}'

If that returns an answer, the whole chain works: your client reached Ghost, Ghost reached the LLM server, and the reply came back.

Add a face

The HTTP API is the foundation, but nobody wants to talk to curl all day. The web UI is a separate process that talks to the agent you just started:

python interface/server.py

Slack, voice and the desktop client are also separate processes. The Interfaces page covers all of them, including which ports they use and what each one is good for.

Keeping it running

Ghost is meant to run continuously — the memory consolidation and self-improvement passes only fire when it's been idle for a while, so an agent you start and stop never gets to do them. On macOS that means a launchd job; on Linux, a systemd unit.

If you use launchd with KeepAlive: a plain kill restarts the process (that's how you deploy a change), and only launchctl bootout actually stops it. Make sure GHOST_HOME is exported inside the job definition — a launchd process doesn't inherit your shell profile, and without it Ghost quietly starts on a brand-new empty memory at the default path.

If it won't start

Most first-run failures are one of four things, and each has a distinct symptom. When something breaks walks through them.
