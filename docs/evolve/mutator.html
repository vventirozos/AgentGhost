⚠ The brief must contain the file

The template named the target and gave the evidence, and showed none of the source. So the model was asked for a unified diff — exact context lines, exact line numbers — against a file it had never seen, and did the only thing it could: it invented class ExecuteTool(BaseTool) for a module that has no classes at all. patch --dry-run refused all four hunks and materialize failed closed, so nothing downstream was corrupted — but E1 could not produce an applicable diff except by luck.

The brief now embeds the numbered source. A file over the 120 KB budget is refused with a stated reason rather than briefed blind: asking for exact-context hunks against a file the model cannot see is a request that cannot succeed, and spending a model call on it is the same error in a cheaper form.

Two further defects surfaced with it. The existing 8 KB prose cap applied to the whole brief, so embedding the source truncated the hard constraints off the end — the brief kept the evidence and dropped the rules the diff is judged by; prose and source are capped separately now. And the target path resolved against the process CWD, which is correct from the repo root and silently wrong under launchd, where the daemon's CWD is not the repo: it would have passed every test and lost its source in production.

The edit is the model's, the coordinates are the machine's

With the file in the brief, the model's edits came back right and its bookkeeping wrong — a correct three-line addition headed @@ -466,6 +466,7 @@ when its body held 9 new lines (patch: malformed), then a correct one-line addition declaring line 468 when the context sat at 467 (applied_where_it_said refused, because the artefact an operator reviews must be the artefact that ran).

repair_hunk_counts recomputes the counts from the hunk's own body. repair_hunk_starts re-anchors the start line to the context's location in the real file — but only on an unambiguous match: zero matches or two both leave the header exactly as written so patch still refuses it, because guessing between two candidate locations is how a repair becomes a relocation nobody authorised. Both report what they changed (hunks_reanchored) rather than normalising silently, since a rising repair count is evidence the brief needs work.

⚠ Three ways the repair itself was the bug

Every one of these was found by measurement, and each produced a plausible failure that blamed something else.

  • The new-side start is not the old-side start. Hunk 2+ of a file is offset by the net lines earlier hunks added. Setting the two equal rewrote an already-correct @@ -6,2 +7,3 @@ to +6,3; patch applied it anyway, applied_where_it_said then rejected the candidate, and the message blamed patch. Every multi-hunk proposal was a self-inflicted permanent failure reported as someone else's fault. All five re-anchor fixtures were single-hunk, where old-start equals new-start by construction, so nothing could see it. A running per-file offset fixes it, and the diff-repair pair is now fuzzed over real repo sources with real patch: 31/31 correct diffs left byte-identical, 30/31 bogus ones re-anchored and applied, 1 correctly refused as ambiguous.
  • --- is ambiguous. A deleted source line reading -- x becomes --- x in the diff — the same prefix as the --- a/path header. Breaking the body scan on the prefix truncated the hunk, which mis-counts the header and poisons the running offset for every later hunk. Measured: the header collapsed to @@ -1,1 +1,1 @@ and patch exited 1. A real header is only ever the first half of a --- /+++ pair, and both repairs now share one end-of-body rule. The same ambiguity ran the other way in applied_where_it_said: an added line spelled +++ /dev/null was read as a header, after which every remaining hunk was skipped and the check returned "no objection" for a diff it had stopped reading.
  • The repair broke diffs that already applied — 8.7% of them. The fix for the ambiguous --- also treated "blank line followed by a new hunk header" as a section separator. Within one file section that blank is the hunk's last context line: it was dropped from the body (shrinking both counts) and still emitted, so patch saw a stray blank plus @@ and started a headerless section. Measured over real repo files, with the one model behaviour this module's comments call constant (a blank context line arriving as "" rather than " "): 26 of 299 diffs that applied cleanly before the repair failed after it. The cost is permanent — run_mutation archives the failure by normalised hash, so the novelty filter blocks the model from ever re-proposing the same correct edit. Only a differential test catches this class: a diff patch accepts before the repair must still be accepted after it, with the same resulting bytes. Every unit test in the group compared the output against a hand-written expectation and none could see it.
  • applied_where_it_said could not object to a deletion. A pure-deletion hunk has an empty post-image, so the comparison was [] == [] — true wherever the hunk landed. Measured: a two-line deletion declared at line 1 was applied 400 lines away, patch exited 0, both containment checks stayed silent, and the candidate was archived and offered to an operator. Whole-file deletion was blind the same way: +++ /dev/null set the current file to None and every hunk was skipped, while Apple patch leaves a 0-byte file rather than removing it.
  • The re-anchor read whatever the model named. repair_hunk_starts runs before validate_diff, so the +++ line had not been checked against the fence when it was opened. +++ b/../outside_secret.txt read a file outside the repo and re-anchored against it; an absolute path discarded the root entirely; +++ /dev/zero reached 3.9 GB RSS in two seconds and never returned, and a FIFO blocked indefinitely — synchronously, on the event loop, unlike materialize, which is wrapped in asyncio.to_thread for exactly this hazard. Now repo-relative, regular-file, size-bounded.
  • The ledger counted normalisations as relocations. @@ -1 +1,2 @@ is the valid short spelling of @@ -1,1 +1,2 @@. Comparing header strings counted that rewrite as a move, so hunks_reanchored reported the model missing anchors it had hit exactly — in the one field whose whole job is to say honestly how sloppy the model was. The comparison is now on the parsed start numbers.

evolve / mutator.py — one proposal, from evidence or not at all

Picks a parent from the archive, picks a target the recorded evidence actually indicts, asks the main model for a small unified diff, and materialises a candidate snapshot. It proposes; it never applies.

Why the evidence floor is a mechanism and not a slogan

A mutator with no evidence floor asks a model to improve a file it has no complaint about — and the model, being a model, produces a plausible diff anyway. Those diffs are then spent against an evaluation cascade whose expensive stage has single-digit throughput a night, so a stream of ungrounded candidates is a stream of coin flips dressed as evolution. A target with fewer than MIN_EVIDENCE_ITEMS recorded failures is not eligible, and a run with no eligible target produces nothing and says which nothing.

The three sources, and the rule they carry

SourceWhat it contributesState on this box
foresightper-tool transition failures with their error heads, already redacted at write timepresent — 751 rows, 73 failures
postmortemdefects.jsonl at ONE canonical path, capped and deduped by signatureabsent — the engine is behind --postmortem and has never run
dream_creditreplay verdicts touching that toolabsent — admissibility-gated

Exactly one has data, and that is why Evidence carries present and reason rather than just a list. A brief built from one source is not the same artefact as a brief built from three, and a mutator that silently degrades to whichever source happens to be populated is inventing the difference. Every brief names the sources that were empty and why, under an explicit instruction not to read their silence as agreement, and every ledger row records which ones contributed.

dream_credit is off twice over: the operator flag defaults off, and the admissibility row for dream_credit is still real_only because §4CM D4 has not returned PASS. The row is the authority — setting the flag alone does not open the source. A flag that overrides a reviewable file is how an unvalidated label source opens, which this project has now paid for twice (§4AO, §4BE).

A guard that fires is not a defect

This is the sharpest correctness point in the module. The live evidence for execute contains:

SYSTEM BLOCK: shell command rejected by pre-execution validator:
deny-listed pattern: \b(?:curl|wget|fetch)\b[^|]+\|\s*(?:sudo\s+)?(?:sh|bash|zsh…

That is the security guard working. Handing it to a model under the instruction “propose the smallest change that would prevent this failure” is a request to weaken the deny-list — and tools/execute.py is inside the mutable fence while tools/validators.py is not, so the fence would not stop the resulting diff. Guard refusals are therefore excluded from the evidence and counted, so the brief can say “N further failures were excluded because they were the scaffold's own guards refusing” rather than quietly shrinking.

The effect on the live ranking is not cosmetic:

TargetBefore the filterAfterExcluded
file_system15 — rank 18 — rank 37 replace-guard refusals
execute15 — rank 213 — rank 12 pre-execution blocks

Without it, the first live brief would have asked a model to change the file-replace corruption guard — a guard installed after 50 of 99 replace calls arrived with byte-identical arguments.

Two details of the filter matter. It matches by containment, not startswith like foresight.is_synthetic_result, because the ledger stores the tool's whole result envelope (--- execution result --- exit code: 1 stdout/stderr: system block: …) and lowercases it — a prefix test finds none of them and the filter would be inert while appearing to work. And the marker list is borrowed from foresight._SYNTHETIC_RESULT_PREFIXES, not copied, plus a two-entry supplement for in-tool refusals that list does not cover (it enumerates results for calls that never executed; these come from a tool that ran and refused its arguments). A test fails if a supplement entry becomes redundant or stops being emitted, so it cannot quietly become a drifting second copy.

⚠ This filter is ranking hygiene, not the security boundary — and the first version pretended otherwise. A fresh-eye review found it wired to exactly ONE of the three sources while the module docstring claimed the property for the module, and its two enumerated messages missed seven emitters: the SSRF guard, the destructive-operation guard, the read-budget refusals, the replace-size refusal, Block REJECTED and the vision size guard — all in tools/file_system.py, which is inside the fence. Filtering evidence is an open-ended blacklist over text nobody controls.

Three attempts at a lexical gate, and why there isn't one

The loop needed to stop a candidate from weakening a safety check. Three review rounds killed three versions of a mechanical gate, and the honest conclusion is that there should not be one.

VersionWhat it didWhat measurement showed
v1reject a diff that removes a “refusal-shaped” line4 of 4 invented test fixtures matched; 5 of 7 real guard lines missed. Twelve of twenty alternatives matched nothing in the repo. Written from an imagined vocabulary and tested against the same imagination — and both mutation batches called it pinned, because a never-matching regex fails all six of its params.
v2count refusal-emitting lines before/after the patch, reject any decreaseMarginal coverage over v1 contained zero guards; 8 of 15 markers appeared nowhere a candidate can edit; and the count went up (+1) when a real refusal was deleted alongside two added comments. Its false positives were terminal — outside the retry loop, blacklisting the diff permanently.
v3widen the vocabulary until it reaches the real lines33% of its 382 matches across the mutable fence are pure comments. Six verbatim ordinary lines from the tree are rejected by it — a task-status set, a cache key, a health string, a prompt legend, a comment beside a timeout, and _invalidate_form_token(…) matched on “VALIDATE”. A 30-line hunk trips it 31–73% of the time depending on the file.

A lexical test cannot decide a semantic property. Each round bought recall with precision, and none of them could see the attacks that matter: an early return above a guard, an or True in a condition, a changed constant, a guard moved into dead code.

So guard_flags flags and does not judge. Removed lines that look like safety machinery ride on the proposal, on the archive node and on the ledger row, and learning_health prints “N proposal(s) removed a refusal-shaped line — read those diffs first”. The operator who applies the patch decides. Its measured reach, with the test selectors fully decoupled from the pattern, is 11% of the enforcement-adjacent lines in the fence — and every earlier, larger number for this was inflated by selectors that were themselves alternatives of the regex being measured. 11% is a usable hint for a human reading a diff and would have been indefensible as a gate; that gap is the whole argument.

What actually bounds this loop: the write fence (an allow-list, with the evaluator outside it), the target-file constraint, the diff-shape caps, the throwaway snapshot, and the fact that promotion is operator-applied. Nothing here is load-bearing on its own.

The fence asks the filesystem, because a string transform is only a guess

Found twice, one round apart. This volume is case-insensitive APFS, so Registry.py is registry.py — and an exact deny-list compared case-sensitively admitted it. Verified end to end: a diff headed a/src/ghost_agent/tools/Registry.py cleared is_mutable, cleared check_diff_scope, cleared archive.admit, and patch wrote the real tool registry — the first entry on the immutable list.

Applying .lower() was not enough: the volume's equivalence is unicode fold, and regiſtry.py (U+017F) opens the same file while .lower() leaves it alone. So the strings are compared with .casefold() — identical to .lower() for ASCII, so the allow-list is unchanged — and resolves_to_immutable() asks os.path.samefile, which compares device and inode. A case-fold can only ever approximate the filesystem's equivalence relation; samefile is it. (Path.resolve() is not enough either: on macOS it preserves the spelling it was given, so the two names resolve unequal while opening the same bytes.)

Which file implements which tool

Which file implements which tool

Resolved by walking the dispatch entry's closure — executed fact — and never guessed from the name. inspect.getsourcefile reports registry.py for all 41 tools, because every dispatch entry is a closure defined inside get_available_tools; and registry.py is immutable. A name-based or getsourcefile-based mapping would make every tool unmutable, and the mutator would propose nothing, forever, silently. It fails closed: anything unresolvable, or resolving only to immutable files, is simply not a target.

Ranking by count, not by rate — and the floor is per source

One failure in one call is a 100% failure rate and no evidence at all. Targets are ordered by absolute failure count; the rate is carried into the brief but does not order, and it is computed within the dominant source, because a summed rate is arithmetic over two different denominators.

Eligibility is measured against the most any single source saw, never the sum. The sources overlap with no key to join on — the postmortem engine files defects derived from the same failed runs the foresight ledger records — so two real failures seen twice used to clear a floor of three.

The evidence sources are read from bounded, canonical paths. An earlier version globbed for defects.jsonl anywhere under $GHOST_HOME, which contains sandbox/ — the model's own writable workspace. Anything the agent chose to name that became evidence: its tool field picked the target, its (uncapped, undeduped) count beat the real ranking outright, and its summary was copied verbatim into a brief asking a model to rewrite that tool. A prompt-injection channel from the sandbox into the self-modification loop, which the fence does not close — the fence bounds which file gets rewritten, not why.

The diff, and what happens to it

Rejections are mechanical and happen before anything reads intent: not a unified diff, no parseable paths, over the shape caps, touching anything outside the fence, or a normalised hash the archive has already seen. A rejected diff gets one retry carrying the rejection reason, because “at most two files” is a rule a model can comply with once told; more than that is paying for the same mistake.

Materialisation snapshots src/ into system/evolve/work/<id>/ and applies the diff to the copy. Three details are load-bearing:

  • patch is dry-run first. Without it, a diff whose second hunk fails leaves the first applied — a candidate that compiles, evaluates, and corresponds to no diff anyone proposed.
  • -F0, and then a check that -F0 is not enough. -F0 disables fuzz; it does not disable offset. Measured on this box: Apple patch 2.0-12u11 applies a hunk 25 lines from its declared position and says nothing at all, exit 0 — so grepping its output for “offset” would have been a check that never fires. applied_where_it_said reconstructs each hunk's post-image and compares it against the file at the line the hunk declared. A self-modification fence cannot accept “applied approximately”: the artefact the operator reviews has to be the artefact that ran.
  • Containment is verified after the fact. The fence tests path strings; an escape can live in the filesystem instead, and MAX_FILES = 2 is exactly enough for the classic traversal — create a symlink inside an allowed prefix, then write through it. This box's patch ignores new file mode 120000, so the vector is inert here; shutil.which takes whatever PATH offers and GNU patch ≥ 2.7 honours git extended headers.
  • Every failure path discards the snapshot, and the failing diff is archived as rejected. Before that, a diff that would not apply left 12 MB behind forever and was invisible to the novelty filter — so the model re-proposed it the next night, into a fresh directory, every night.
  • The trailing newline is restored. Every model reply passes through a fence-stripper whose .strip() removes it, and patch then fails the hunk — so every proposal would have died at materialisation with a message that reads like a bad diff rather than a lost byte. Found by a test, not in production.

A missing patch binary is refused before the snapshot rather than after, and never worked around: hand-applying a diff here would be a second implementation of patch inside a security fence.

The ledger

One row per run, including the runs that produced nothing. Without it, “the mutator proposed nothing last night” and “the mutator never ran” are the same observation — the activation-counter lesson, applied to the loop that is supposed to be improving things. The outcomes are distinct on purpose: no_evidence, no_model_output, rejected, duplicate, materialize_failed and proposed are five different problems with one symptom.

Where it runs

Biological phase 3d, 15-minute idle floor (it spawns no containers and does not compete with a solve), 6-hour cooldown — at most four candidates a day, deliberately slower than the cascade that will consume them, because a proposal nobody has evaluated is a queue and not progress. Bounded by asyncio.wait_for, and the clock advances on every path including the failures, or a broken dependency re-imports and re-logs on every 60-second tick for as long as the box stays idle. Registered EXPECT_GATED in PHASE_EXPECTATION: GHOST_EVOLVE defaults off, so a zero must report the gate rather than manufacture an alarm.

What does not exist yet

The evaluation cascade (E2), the scheduled negative controls (E3), and the proof run (E4). Promotion is operator-applied by design — this module only ever writes a candidate and a ledger row.
