Negative controls (E3)

Every stage of the evaluation cascade is a guard, and a guard that has never visibly fired is not known to be alive. E3 builds three known-bad candidates and checks the cascade refuses each one, at the stage it should die at.

SCHEDULED as of §4CS, 2026-08-24. §4CO recorded this as still owed: one control run was performed by hand on 2026-08-23 and passed — into a throwaway home, so nothing durable recorded that it had ever happened. This project's own rule is that a guard which never demonstrably fires is presumed dead, and E2's entire value is refusing things.

The schedule. Idle phase 2.7f in core/agent.py runs the controls weekly (INTERVAL_S — ONE definition, shared with the liveness probe's staleness bound so the two cannot drift). Shallow by design (each control stops at the stage it is supposed to die at), but still minutes of work because the guard control runs stage 1 for real over ~45 pin files. The cooldown anchor is durable, read from negative_controls.json's own timestamp: an in-memory anchor makes the cadence "once per deploy", so on a box that restarts often a weekly job runs every boot. GHOST_NEGCTRL=0 disables it. It runs the CONTROLS, not the Evolve loop — three deliberately-bad candidates are built in a temporary tree, refused, and discarded; nothing is promoted and nothing is written to the repo.

The firing is visible. An evolve.negative_controls probe in core/liveness.py reads the result file under introspect action='learning'. Never run reads no_source — an instrumentation gap, and it must not render as a tick. The phase is registered in PHASE_EXPECTATION as on_output (changed 2026-08-30, §4DY). It was periodic, which is judged against a 24 h alarm window — and this loop runs on a seven-day interval (INTERVAL_S = 7*24*3600), so a healthy weekly loop was branded ✗ DEAD six days in seven, next to a genuinely stale one. Its liveness signal is the probe above, which reads the result file's own timestamp; the ledger count never was one.

A control that fails to fire is LOUD, and that is NOT a zero. A run where two of three controls held has a POSITIVE count and is the single most important line on the view, so alarm_if_zero cannot express it — ProbeResult grew an explicit alarm. It fires on: a control that did not reject; a control missing from its own results; an unverified control; a PARTIAL run (a control that was never selected contributes to a green suite by being ABSENT); and a schedule that has STOPPED (older than two intervals). One missed window does not alarm — a monitor that cries on a benign zero is one the operator learns to scroll past. The denominator is DEN_NONE: it runs off the idle clock, so no amount of quiet excuses its silence.

First live run, 2026-08-24 — all three fired and held against the real tree: edits_a_test refused at stage0_static (diff scope), deletes_a_guard at stage1_pins (1 failed / 289 passed in the pin set), no_op_claiming_improvement at stage3_paired (not better, p=1.000). Tests: tests/test_4cs_negative_controls_schedule.py (15 tests, all mutation-pinned).

The three controls

  • edits a test → must die at stage 0, on diff-scope, before anything is compiled. A candidate that may edit the tests judging it is not a candidate.
  • deletes a guard → must pass stage 0 (it is in scope and it compiles) and die at stage 1, because a pin asserts the guard fires. This is the strongest of the three: it generates a diff against the live tree, materialises a snapshot, and runs the canonical pins in a subprocess. Measured: pins failed: 2 failed, 116 passed.
  • a no-op claiming improvement → must die at stage 3, where identical arms are "not better".

The diffs are generated, not stored. A stored diff rots the moment the file it patches moves, and a control that no longer applies reports a cascade failure that is really a stale fixture. A control whose target has moved is reported as a named failure — never as a traceback, which says nothing about which controls held, and never as a pass.

⚠ Three ways a control lies about itself

Each of these was live in this file, and each made the suite greener than the truth.

1. The control that ignored its own diff

The shallow no-op check called paired_verdict([(True, True)] * 20) — a hard-coded input. Pointing the target at a file that does not exist, or making the "no-op" delete half of database.py, left the control green: it was a test of the decision function wearing the name of a control over a no-op candidate. The premise is now established first — the diff is materialised and the candidate's syntax tree compared to the canonical one — and only then is the decision function asked to rule.

2. The report that contradicted its own verdict

The guard control's detail line read reason or "pins failed as required". reason is empty on success, so a run in which the pins let the deleted guard through printed "pins failed as required". The one outcome the control exists to catch was the one it described as a pass.

3. The phrase that could not tell "failed" from "never ran"

The control scored itself on "pins failed" in reason. Stage 1 phrased every decline that way, including "no tests ran". A run in which the pins never executed therefore scored the control green. Stage 1 now reports the failure kind as a field — failed / not_run / unreadable — and only failed counts. A substring is not an identity.

⚠ "Not run" is a third state

all_ok is not all(r.ok). Deep mode cannot drive stage 3 yet, and a control that reports ok=True because nothing executed made the thorough mode greener than the shallow one — this module's own rule inverted by its own reporting field. A result carries verified alongside ok, all_ok requires both, and the persisted record names what was left unverified so a health view can render the gap rather than a tick.

What reads the result

Nothing yet. last_run() was documented as "what the learning-health view reads" while no learning-health code opened it — a reader checking whether the controls are surfaced would have stopped at that line and concluded they were. The suite is run on demand by the operator; nothing calls it automatically.

Cost and hygiene

Shallow mode stops each control at the stage it is supposed to die at, which is both faster and exactly what is being asserted — only the no-op needs stages 2–3, and those cost hours. Every snapshot is reclaimed: sweep_work_dirs keeps a bounded number, so a control leaking ~10 MB per run would evict real candidates — the suite that checks the loop quietly destroying the loop's own work.
