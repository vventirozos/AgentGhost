The evaluation cascade (E2)

A candidate is a materialised snapshot — the repo with one mutator diff applied. This module decides whether that snapshot goes any further, and every stage runs in the parent process: the candidate is only ever the subject, never the harness.

Two rules shape all of it

1. The harness is read from the canonical tree, never the candidate's copy. fence.harness_digest is taken before and after every stage. If it moves, the generation aborts — the stage does not merely fail, because a moved harness means no result from the run can be trusted, including passes already collected. Additions count: "it only added things" is the exact shape of a candidate writing its own passing test.

2. Nothing counts as a pass by default. A touched file that maps to no test, a pytest run that collected nothing, an empty diff — each produces zero failures, and zero failures is the shape of a green result that verified nothing. Each is an explicit refusal.

Stage 0 — static (seconds)

Diff-scope first, because a diff touching a file it may not touch is not a thing to compile and reason about, it is a thing to refuse. Then: every touched path exists in the snapshot (materialize can report success on a partial apply), every touched .py compiles, and no production module was rewritten to the test import form.

That last check is not style. Production runs as python -m src.ghost_agent.main and imports src.ghost_agent.*; a production module rewritten to ghost_agent.* loads a second copy of the package with its own state, a defect this repo has already paid for.

Stage 1 — pin smoke (minutes)

The canonical tests that cover the touched files, run against the candidate's code: the subject is swapped, the judge is not. Test selection is mechanical from the repo's own naming (tools/browser.py → tests/test_browser*.py), and a touched file that maps to nothing fails the stage rather than passing it by running zero tests.

⚠ The premise deserves its own test, and has one. This repo's suite uses both import forms: ghost_agent.* resolves through PYTHONPATH, src.ghost_agent.* through the working directory. Getting PYTHONPATH right and cwd wrong would satisfy the first and silently miss the second — every pin passing against the incumbent while the cascade certifies code it never executed. The pin builds a two-root mini-repo, asserts both import forms see the candidate, and includes the negative control: pointing the stage at the incumbent must fail, or the positive proves nothing.

pytest's exit code alone is not read. It exits 5 on "collected 0 items" — a non-zero that looks like a failure and a zero-failure count that looks like a pass — so the summary line is parsed too.

The abort is a veto, not a decoration

The result is recorded before the final harness check, so the check can overturn it. Written the other way round, passed was still at its default every time the check could fire: the abort could never actually reverse a result, and deleting the line that forced it changed nothing. Mutation testing caught that; the ordering is now what makes a run whose pins passed and whose harness then moved come back False.

Stage 3 — paired confirm (overnight)

Candidate against incumbent on a held-out slice, the same items to both arms, scored with an exact two-sided McNemar over the discordant pairs.

The holdout is a pure function of the item id (sha256, 25% of every bank), not a saved list. A holdout that lives in a file can be regenerated, corrupted, or quietly re-rolled after a candidate scores badly on it — and the re-roll looks exactly like a fresh split. The disjointness is enforced in one place, inside the sampler, rather than by every caller remembering to filter: the mutator's brief may reference stage-2 results, so an item appearing in both pools is one the candidate was tuned against and is then judged on. Measured on the real corpus: 3,610 items → 888 held out (24.6%), 2,722 public, zero overlap between the two samples.

Both arms run in the same call, and through the same function. A cached incumbent would be a comparison across time — the model, the box and the sandbox all drift, and pairing exists precisely to remove that. Paying twice is the point. Two near-identical call sites would drift too, and that drift is indistinguishable from the effect being measured.

Promotion needs a significant win, not an absence of harm. "We could not tell the difference" is the answer for almost every candidate; treating it as success promotes noise. A tie gives p = 1.0 and fails. So does a narrow lead. And the direction guard is load-bearing on its own: an 8–0 loss to the incumbent scores p = 0.008, comfortably significant, because significance alone cannot tell a win from a loss.

An item that infra-aborted in one arm is dropped, not guessed. Scoring it as a failure charges a harness fault to the candidate; scoring it as a pass does the reverse. Either way the pairing is broken, so the count of dropped pairs is reported rather than absorbed.

passed is not promotable

Stages 2 and 3 cost an hour and a night, and run only when their items are supplied — most candidates die for free in stage 0. So passed means only "nothing run so far said no". A candidate that cleared a four-second static check and a pin smoke would otherwise look identical to one that beat the incumbent on held-out data. promotable requires stage 3 to have actually run and passed, and any abort voids it however many stages went green.

Stage 4 — the operator packet

A JSON packet under system/evolve/proposals/ carrying the diff, the brief, every stage result, the McNemar p, and the paired CI on p_incumbent − p_candidate (negative means the candidate is ahead). A p-value tells an operator whether to believe the difference; the interval tells them how big it is, and both are needed to decide.

Only for a promotable candidate. A packet in that directory is an endorsement — it says the cascade believes this diff beat the incumbent on data it had never seen. Writing one for a candidate that merely compiled would put an unproven change in front of an operator carrying that implication, which is worse than writing nothing. The refusal names the missing gate, because "not promotable" alone sends someone to read the source.

And exactly once. Fire-once has bitten this project before. A second cascade over the same node rewrites the packet and stays silent: an operator already told, who has not yet acted, does not need telling again, and a ledger that repeats itself trains people to ignore it. Delivery is best-effort — a failed notification never loses the packet, because the file on disk is the durable record and Slack being down is the wrong reason to drop a result.

The packet is written last, after the final harness check. Written earlier it would be an endorsement on disk that a subsequent abort could not retract: the notification has already left, and "we told you, then found the harness had moved" is not a correction anyone can act on.

A graded signal beside the binary one

The binary gate counts only pass/fail, so a candidate that solves in one attempt where the incumbent needed three scores identically to one that changed nothing. Stage 3 also reports an exact two-sided sign test on attempt counts — the same primitive as the binary gate applied to the direction of the difference, so it needs no new statistics to validate. Ties are excluded (that is what a sign test does) and reported, because a verdict resting on two untied pairs out of twenty-four is a verdict about almost nothing.

It is reported, never a gate. Promotion still turns on the binary rule alone; a test asserts it. Adding a second route to an operator changes what reaches them, and that is a decision to take deliberately rather than acquire as a side effect of measuring something new.

Measured on the first real run: 24 pairs, 21 ties, candidate fewer 2, incumbent fewer 1, p = 1.0, means 1.583 → 1.542. The extra resolution is real but thinner than it looks — gsm8k_text averages 2.75 attempts, but a stratified draw is mostly gsm8k, where attempts are nearly always 1.

⚠ What the gate scores, and what the evidence said

The first real candidate exposed a mismatch that no amount of tuning fixes. E1's brief indicted execute on 13 real failures out of 56 calls — missing deno/unzip, a 600 s timeout, yt-dlp errors — and the model wrote a fix for exactly that. Stage 3 then judged it on "Janet's ducks lay 16 eggs per day…": arithmetic word problems and small Python functions.

A correct fix for a shell-dependency failure is invisible on that benchmark; only a regression could show. This is the same wrong-regime error as the replay census measuring an empty fork, one level up — the evaluation cannot exercise the failure the evidence names. Until bench items are minted from the agent's own failure corpus, the cascade can reject a bad candidate but cannot demonstrate a good one.

What the bar costs, measured from the gate itself: 6 candidate-only wins with zero losses to clear α = 0.05 — the same at n = 24 and n = 120, since McNemar counts only discordant pairs. One loss raises it to 8, two to 10, against an incumbent that fails 4 items in 24.

The invariant that outlives the stages

All four stages now exist, so "stage N is absent" has nothing left to guard — but the property it stood in for does. Promotion is operator-applied. The evaluator's job ends at a packet on disk: it may not copy a candidate over the canonical tree, shell out to patch, or call the mutator's materialize. A test asserts every one of those absences, because autonomy is earned in a later version, not acquired by a helper someone adds because it was convenient.
