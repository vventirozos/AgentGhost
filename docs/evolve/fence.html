evolve / — the fence and the archive

Archive-based self-evolution of the scaffold, behind evaluators the candidate cannot touch. This page covers what exists: the write fence and the lineage archive. The mutator and the expensive evaluation stages do not exist yet.

The failure mode this is shaped by

It is not "the mutator writes bad code" — that is what an evaluator is for. It is the agent modifying the thing that measures it. DGM's agent learned to fabricate test logs. The AI Scientist raised its own timeout rather than finishing inside it. Neither was caught by a better mutation; both were caught, eventually, by somebody noticing the evaluator had moved.

So the fence is two separate mechanisms, and neither is sufficient alone.

A path allow-list

is_mutable(path) admits tool implementations and prompt constants. It refuses tests/, eval/, scripts/, evolve/ itself, core/agent.py, the isolation and replay modules, memory/, selfhood/, sandbox/, main.py, conftest.py and pytest.ini. Two paths inside a mutable tree are also refused: tools/registry.py, which is the tool surface itself, and tools/validators.py.

An allow-list rather than a deny-list, because the repo grows: a module added next month must be un-mutable until somebody decides otherwise. And it fails closed on anything it cannot classify — an absolute path, a path that escapes the repo, an empty string. "I could not tell" must never read as "allowed" for a write fence. Normalisation happens before the prefix test, which is the difference between a fence and a substring check: a/../tests/conftest.py is refused.

A harness checksum

The allow-list can only reject what it can see in a diff. A candidate that reaches the filesystem some other way — a fixture that writes, an import with a side effect — moves the checksum. harness_digest() hashes every file under the harness trees; compare_harness() reports what changed between two readings.

A dict rather than a single hash, so the alarm can name which file moved — a single digest says only that something did, which is the least actionable form of a true alarm. And additions count: a test file a candidate adds is a test file that runs, and "it only added things" is exactly the shape of a candidate writing its own passing test.

Selection is not hill-climbing

HGM's result is that a node's own score poorly predicts its descendants'. Greedy selection on own-score therefore walks into whichever local optimum scores best early, and discards the branch that would have gone furthest before it has children. So parents are sampled in proportion to what their clade has achieved:

weight = best-DESCENDANT-score × 1/(1 + children)
TermWhy
best descendant, never own scoreThe HGM finding, and the entire reason this is not hill-climbing.
UNKNOWN_PRIOR = 0.35 for a node with no scored descendantsDeliberately above what a node whose descendants all scored zero would get. An archive that ranks the unknown below the known-bad stops exploring.
1/(1+children)A node tried five times and still leading is worth trying again — but not five times as often as one nobody has touched.
the root is always selectableA lineage that has painted itself into a corner must be able to start over from the unmodified tree.

The clade walk is cycle-safe. A hand-edited archive can name a parent that is also a descendant, and a naive walk recurses forever inside a nightly job nobody is watching.

Novelty is an identity question, not a text question

EvoTrace measured around 30% of evolved lines to be resurrections of code that already existed in the lineage. Re-evaluating a diff the archive has already seen costs a full cascade and can only reproduce a verdict already on disk.

normalized_diff_hash keeps only added and removed lines, stripped and sorted. The same edit expressed against a shifted file, with different blob hashes or with its hunks reordered, hashes the same and is refused. A raw-text hash would let it re-enter under a new identity.

diff_touched_paths reads both the --- and +++ headers, because a rename or a delete names its victim only on the --- side — a fence that reads one side can be walked around by a diff that only deletes.

Shape caps (at most two files, at most 120 changed lines) run before the fence. Not a quality judgement: a bounded diff is one an operator can actually read before approving, and a whole-file rewrite is a replacement rather than a mutation.

Rejects are kept — the design, and what of it runs today

An archive that keeps only survivors cannot tell "the mutator improved" from "the evaluator got looser". The design is that every candidate stays, with the stage it died at recorded, and archive_stats reports the histogram — because "the mutator produced nothing usable" and "the mutator produced nothing" are different states.

⚠ What actually runs, as of 2026-08-22: the mutator archives a node for a proposal and for a diff that failed to materialise, so those two are kept. admit, record_stage and archive_stats have no production callers — they belong to the evaluation cascade (E2), which does not exist, so no node leaves candidate status and nothing renders the histogram. Stated here because the paragraph above described all of it in the present tense for a while, which is how a reader ends up trusting a mechanism that never runs.

A node whose score is None has never been measured, which is not zero and must not be averaged as if it were.

What does not exist yet

The harness checksum (harness_digest / compare_harness) is built and uncalled: it is meant to be taken before and after every evaluation stage, and there are no evaluation stages yet. The section above describes it in the present tense because that is its design, not its current behaviour.

The mutator now exists (§4CN E1). Still missing: the expensive evaluation stages (bench smoke, the paired held-out confirm), the scheduled negative controls, and the post-promotion tripwire. Promotion is operator-applied by design in v1 — the loop produces evidence-carrying proposals, never self-applied changes — so nothing here can act on its own regardless.
