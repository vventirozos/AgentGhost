How it works

Labs: real machines on demand

When a task needs a real database server, a three-node cluster or a running web app, Ghost doesn't fake it in its sandbox. It asks a separate machine, the labs host, for disposable machines, works on them, and throws them away. This page explains how that works and shows what happens for a few typical requests.

What it is

The agent's own sandbox (execute, file_system) is one container: no root, no extra ports and no network faults. That suits writing and running code. It doesn't suit "start PostgreSQL 18 with a replica, cut the primary off the network and watch the failover".

ghost-labs is a small service on another machine on the tailnet (the host is called disorder). It has no AI in it: the agent asks for something, and the service either does exactly that or answers with an error and a hint. Each lab is a set of Docker containers (its members) on a private network of their own, made from a template.

Two places to work

There's no routing switch. The rule is simple: build in the workspace, run the system under test in a lab. Code, SQL files, configs and reports live in the workspace, because labs disappear. Labs are where those things run on real servers. Files move between the two with lab put and lab get, and a whole folder ships with lab deploy. The recipe of a lab (lab spec) can be saved in the workspace too, so the same setup can be rebuilt later.

The templates

"Tor" means the lab reaches the internet only through the host's Tor gateway, as the agent itself does. "None" means it has no route out at all. A lab never reaches the agent's Mac, the tailnet or the home network (the host firewall drops it). Its published ports are served on the tailnet over HTTPS; a kept app created with lan: true is also reachable on the host's LAN address.

A lab's life

  1. create: the tool asks for the template and waits until the readiness check passes (at most 5 minutes, and never past the turn's own deadline). The lab goes into the inventory as soon as the host answers. If no answer comes, the tool says to run lab list before creating another.
  2. use: exec commands, put/get files, member faults (stop, kill, pause, isolate, rejoin), logs, http to a member's port, or run a long job or server on a member.
  3. end: the agent destroys it when done. If it forgets, the host's reaper removes it once it has been idle too long (4 h for an ad-hoc lab, 12 h in a project, 2 h for an autopilot build's lab, 30 min for a test probe) or once it reaches its maximum age.

A lab made inside a project can instead be kept: it stays up, runs one app under a stable URL, gets daily backups and a supervisor that restarts the app, and the owner is told when it goes down. See the kept app example.

Space is limited: a RAM budget, at most 4 disposable labs at once, and a separate allowance for kept labs. When the pool is full, the owner's create evicts the oldest autopilot lab; it never evicts the owner's own labs. Separately, autopilot can't destroy a lab you used in the last 30 minutes (owner_active).

Who may do what

CallerDisposable labsKept labs and apps

Labs and runs are filed per conversation or per project (conversation:<key> / project:<id>). lab list shows your own by default (all_owners=true shows every lab). Autopilot and probes are confined to their own labs; you can act on any lab id, and destroying another owner's lab says whose it was. Runs are read and stopped only from the conversation or project that started them.

Worked examples

Each example shows what you might type, then the tool calls the agent makes. Ids such as lab_1b9cdae5 are illustrative. You never have to name a tool yourself; it's shown here so you can follow the logs.

1. Run some SQL on a real PostgreSQL

Check what SELECT 41+1; returns on PostgreSQL 18.
lab(action="create", template="pg-single", label="quick sql")
  → [lab_1b9cdae5] ready — pg1 10.89.3.10 (ghost-lab/pg:18)
lab(action="exec", lab_id="lab_1b9cdae5", member="pg1",
    cmd="psql -U postgres -v ON_ERROR_STOP=1", stdin="SELECT 41+1;")
  → exit 0 ·  ?column? ... 42
lab(action="destroy", lab_id="lab_1b9cdae5")
  → destroyed

The local Postgres the agent used to have is gone (§4SX Phase E). A remembered call to postgres_admin or psql is redirected to the lab tool. Nothing runs from that call; the tool answers with this route. If the model runs psql (or mysql, psycopg, asyncpg) in the sandbox anyway, the client finds no server and the result carries a NO DATABASE SERVER HERE note that names this same route (details).

2. Load a SQL file from the workspace

Write a schema file, load it into a fresh database, and save the result.
file_system(operation="write", path="schema.sql", content="CREATE TABLE t(x int); ...")
lab(action="create", template="pg-single")
lab(action="put", lab_id="lab_…", member="pg1", sandbox_path="schema.sql", path="/tmp/schema.sql")
  → [lab_…/pg1] put /workspace/schema.sql → /tmp/schema.sql (412 bytes)
lab(action="exec", lab_id="lab_…", member="pg1", cmd="psql -U postgres -f /tmp/schema.sql")
lab(action="exec", lab_id="lab_…", member="pg1", cmd="pg_dump -U postgres -f /tmp/dump.sql postgres")
lab(action="get", lab_id="lab_…", member="pg1", path="/tmp/dump.sql", sandbox_path="out/dump.sql")
  → [lab_…/pg1] got /tmp/dump.sql → /workspace/out/dump.sql (8,120 bytes, now in the workspace)
lab(action="destroy", lab_id="lab_…")

A sandbox_path means exactly what it means to file_system. schema.sql, /schema.sql and /workspace/schema.sql are the same file, and inside a project they are the project's file. The result always shows where the file really landed (/workspace/…). Links are never followed, and nothing outside the workspace is read or written. A get says when it REPLACED an existing file.

3. A failover experiment

Start a 3-node Patroni cluster, cut the leader off the network, and tell me who takes over and how long it took.
lab(action="create", template="patroni-3", label="failover")
lab(action="exec", lab_id="lab_…", member="pg1", cmd="patronictl -c /etc/patroni.yml list")        → leader: pg1
lab(action="member", lab_id="lab_…", member="pg1", op="isolate")               → pg1 isolated
lab(action="exec", lab_id="lab_…", member="pg2", cmd="patronictl -c /etc/patroni.yml list")        → leader: pg2 (after ~30 s)
lab(action="member", lab_id="lab_…", member="pg1", op="rejoin")
lab(action="spec", lab_id="lab_…")   → the recipe (the agent saves it with file_system, for a rerun)
lab(action="destroy", lab_id="lab_…")

The faults are stop start restart kill pause unpause isolate rejoin. isolate takes a member off the lab network without stopping it, which is the split-brain case a plain stop can't show.

4. A long job or a server on a lab member

Run a 10-minute pgbench on the lab and tell me the TPS.
run(action="start", name="bench", where="lab_…/pg1", lifetime="job",
    command="pgbench -i -s 10 -U postgres && pgbench -T 600 -U postgres")
  → started; `run status` / `run collect name=bench`
… later …
run(action="collect", name="bench")
  → tps = 1843.2 …  (FAILED if it exited non-zero; UNRESOLVED while still running)

The same run tool starts jobs and servers in the workspace (where=workspace). run status lists this conversation's or project's runs, wherever they are. A job is graded by how it really ended, never by what it printed.

5. Check a web page served by a lab

lab(action="create", template="web")
lab(action="put", lab_id="lab_…", member="web1", sandbox_path="site/index.html", path="/srv/www/index.html")
lab(action="http", lab_id="lab_…", member="web1", port=80, path="/")
  → 200 · text/html · <!doctype html> …

http is the only way to reach a lab's port; the agent's browser cannot. A published port also gets a tailnet HTTPS URL, shown by lab status, that you can open yourself.

6. Keep an app running (production)

In my chess project: put the app online and keep it running.
lab(action="create", template="python-app", label="chess v1")       # inside the project
lab(action="keep", lab_id="lab_v1",
    params={"app": {"name": "chess", "member": "app", "port": 8080, "cmd": "gunicorn -b 0.0.0.0:8080 app:app"}})
  → lab_v1 is now KEPT (production, no expiry): app chess … — https://<labs host>:20001/ … Next: `lab deploy` the app's folder
lab(action="deploy", lab_id="lab_v1", params={"folder": "/workspace/app"})

The app then has daily backups and a supervisor that restarts it. A new version is a second lab of the same app, kept the same way: that keep answers "STAGED next version — lab deploy it, then lab switch it in". Then:

lab(action="rehearse", lab_id="lab_v2")                      # recreates + redeploys v2, then probes a throw-away twin (empty data, fake secrets)
lab(action="switch",   lab_id="lab_v2", params={"from_lab": "lab_v1"})   # the stable URL moves; a failed probe reverses it
lab(action="rollback", lab_id="lab_v2")                      # back to v1 if v2 misbehaves
lab(action="backup",   lab_id="lab_v2");  lab(action="backups", lab_id="lab_v2");  lab(action="restore", …)
lab(action="app",      lab_id="lab_v2", op="restart")        # start | stop | restart

Only you can do these. Autopilot and members never change a kept machine. App secrets are never tool arguments; you set them on the agent with PUT /api/operator/labs/<lab_id>/secrets, and the host masks them in every output as <secret:NAME>. A kept app that goes down twice in a row sends you one notice. Every kept app is listed on the Apps page.

7. Autopilot uses a lab while you're away

An unattended project build may create disposable labs in its own project (to test a migration, say). They are tagged with the build step. When the step ends, or the agent restarts, its leftover runs are stopped and its labs destroyed. If the host is full, its labs are the first to be evicted for yours. It may read a kept app's status, but it can't touch it.

Setting it up

  1. On the labs host: copy interface/ghost-labs/ to /opt/ghost-labs and run sudo /opt/ghost-labs/install.sh. It builds the images, installs the firewall and services, and prints the address.
  2. On the agent's machine: copy the host's /etc/ghost-labs/api_key into ~/Data/AI/.ghost_labs_key (mode 0600), and set GHOST_LABS_HOST=http://<tailnet IP>:8700.
  3. Restart the agent. Its boot log shows labs — labs host … ok=True, and the lab tool appears. With no host or no key, the tool is simply not offered.

On the host, ghost-labs status | list | templates | gc | destroy <lab_id> manage it by hand. destroy --all is refused on purpose.
