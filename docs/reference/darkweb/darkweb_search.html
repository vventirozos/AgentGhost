tools / darkweb_search.py

Discovery of Tor hidden services (.onion) via dedicated onion search engines, with per-attempt circuit rotation, cross-engine corroboration ranking, and an optional deep-read research mode.

Why a separate tool

The clearnet search tool (search.py) queries scraper backends — DuckDuckGo, Yandex, Brave, Yahoo — that do not index Tor hidden services. Discovering .onion content requires querying dedicated onion search engines (Ahmia, Torch, Torgle, …) and parsing their result pages. The transport is the same Tor SOCKS proxy the rest of the agent already uses; what is new is the engine set and the result parsing.

Tools

ToolPurpose
darkweb_searchFan a query across the onion-engine set over Tor, parse the .onion result links/titles/snippets, de-dup by onion host, rank by cross-engine corroboration, and return a ranked list. List-only — pair with browser / darkweb_research to actually read a result.
darkweb_researchThe dark-web analogue of deep_research: runs darkweb_search, then fetches the top onion pages over Tor and distils each via the worker LLM into a synthesised report. Optional urls (up to 8 onion pages, e.g. what darkweb_search listed) are read first; without a query only those are read (§4UN-darkres).

Onion-engine registry (_ONION_ENGINES)

Onion search-engine endpoints rotate and die far more often than clearnet ones, so the set is config-driven and intentionally wide — breadth plus circuit rotation wins, the same philosophy as search.py's _TOR_BACKENDS. The built-in default is:

  • ahmia — the clearnet mirror ahmia.fi (still fetched over Tor); indexes onion services and filters known-abuse material at the index level.
  • ahmia-onion — Ahmia's own .onion endpoint. Listed alongside the clearnet mirror on purpose: the two have independent reachability, so one is often up when the other is blocked. They serve the same search index, though, so both carry index: "ahmia" — reaching Ahmia over two transports must not be mistaken for independent corroboration (see ranking below).
  • torch — a broad unfiltered onion index, for reach. Re-pointed 2026-07-29 (see below); the fastest engine in the set at 1.6–6.6 s.
  • torgle — added 2026-07-29 as a third independent index. Slower (9–25 s) and smaller, but its value is not its size: with only Ahmia and Torch alive, one engine having a bad day left corroboration ranking with nothing to corroborate against.

On dead endpoints: haystak was in the initial default set but was dropped after live functional testing — its v3 endpoint failed on every attempt across many rotated Tor circuits (SOCKS5 connect / timeout), i.e. the hidden service is down rather than exit-node blocked, and its retry could burn a full _ONION_TIMEOUT and inflate the tail latency of the whole (concurrent) call. It — or any replacement onion engine — can be re-added via GHOST_ONION_ENGINES once a live endpoint is known. This is the expected maintenance mode for onion engines, which rotate and die far more often than clearnet ones.

Engine survey (2026-07-29): Torch was not dead, it had moved

Torch had been timing out on every search, costing the tool a full _ONION_ENGINE_DEADLINE (38 s) on every call while contributing nothing. Probing the configured torchdeed… address across fresh circuits gave 0/10, every one a 30 s timeout — the same signature that got haystak dropped. But the service was not gone: it is alive at xmh57jrknzkhv6y3ls3ubitzfqnkrwxhopf5aygthi7d6rplyvk3noyd.onion under its Xapian Omega CGI path, /cgi-bin/omega/omega?P={q}. The old /search?query= path returns 404 there — so at the right address with the wrong path it would still have looked dead. Adding &HITSPERPAGE=100 lifts one page from 7 unique onions to 28 (the parser de-dupes by host, so 100 hits collapse to 28 hosts). Measured 4/4 reachable at 1.6–6.6 s.

Candidates were measured with this module's own _fetch_raw_html + _parse_onion_results + _diagnose_empty_body, over live Tor on rotated circuits — not by reading engine lists. A directory page saying an engine is up is not evidence that our fetch and our parser can get results out of it.

Net effect: three independent indexes instead of one, and a typical search dropped from 38 s (dominated by torch's timeout) to 17–28 s. The rejected addresses are recorded in a comment beside the registry so the next person re-measures rather than re-discovers them; all of them are re-addable via GHOST_ONION_ENGINES if they come back.

The whole set is overridable at runtime via the GHOST_ONION_ENGINES env var (a JSON list of {"name","url"[,"index"][,"form_token_from"]} objects, where url contains a single {q} placeholder). The optional index marks endpoints that share one underlying search index so they count once in corroboration ranking; omitted, it defaults to the entry's own name (treated as an independent index). The optional form_token_from names a page whose search form carries a hidden field the engine requires on the query string — see the form-token section. A malformed override falls back to the built-in default rather than silently disabling dark-web search, and an individual entry whose URL carries a stray placeholder other than {q} (which would raise a KeyError in .format on every query and be silently skipped) is rejected at load with a warning instead.

Circuit rotation + timeouts (reused from search.py)

Onion search engine reachability is exit-node dependent in exactly the same way clearnet search is, so the same per-attempt circuit rotation applies: _proxy_for_attempt (imported from search.py) folds the attempt index into the SOCKS username:password, and Tor's IsolateSOCKSAuth hands each attempt a different exit node. Each engine is tried up to 2 times, each on a fresh circuit, and all engines are queried concurrently.

Timeouts are deliberately higher than clearnet search. Onion round-trips are materially slower: _ONION_TIMEOUT = 30 s per engine request (a curl low-speed limit; the wall clock is the caller's _ONION_ENGINE_DEADLINE / page deadline, and since §4PD the form-token fetch has its own) (vs. search.py's _DDGS_TOR_TIMEOUT = 18 s), and _ONION_PAGE_TIMEOUT = 35 s for each onion page fetch in the research phase — of which a page has _ONION_FIRST_BYTE_S = 15 s to send its first answer (§4UN-darkres). These clear a healthy onion service while still letting dead endpoints fail fast on connect error. Like the clearnet timeout, they are empirically tunable.

Per-engine deadline (dead-engine hardening). Unlike search.py — which hands its whole backend set to ddgs in a single call bounded by one shared timeout — this tool fans the engines out itself with asyncio.gather, so the search can only finish once the slowest engine returns. A dead or hung engine that burns its per-attempt timeout twice (~2×_ONION_TIMEOUT) would therefore dominate the gather and inflate every call's latency. To bound this structurally (not just by curating the engine list), each engine runs under an overall _ONION_ENGINE_DEADLINE = _ONION_TIMEOUT + 8 s via asyncio.wait_for: it allows one full attempt (a slow-but-alive engine legitimately needs up to _ONION_TIMEOUT) plus a short window for a fast second circuit, then skips the engine so the gather proceeds. Since 2026-09-14 the fetch is an awaitable on the same loop, so cancelling the await aborts the transfer itself (it used to leave a worker thread running until curl's own timeout). This makes engine curation a tuning aid rather than the only thing standing between a newly-dead engine and a slow tool. Covered by tests/test_darkweb_search.py::test_slow_engine_bounded_by_deadline.

socks5h — mandatory for .onion

_normalize_tor_proxy forces the proxy to socks5h:// form (note the h), which routes DNS resolution through the proxy. This is mandatory: .onion has no clearnet DNS, so a plain socks5:// proxy (local resolution) would fail to resolve every hidden service. The SSRF guard shared by the fetch helpers treats a DNS-resolution failure as allow, so .onion hosts pass it cleanly.

Result parsing & ranking

Each engine renders results differently, so _parse_onion_results is deliberately tolerant: it walks anchors to harvest (onion-url, title) pairs with a nearby snippet, unwraps Ahmia-style redirect_url= wrappers, then does a regex sweep of the whole document to catch onion URLs that appeared as plain text. Addresses are v3 only (56 base32 characters) and must pass the v3 checksum (§4UN-dark). Results are de-duped by URL, at most three per host (§4UN-dark; it was one per host).

Self-link filtering. A tolerant whole-page harvest also picks up the nav/footer/sidebar links every engine page carries — including the engine's own onion address and those of sibling engines. Those are excluded (_engine_onion_hosts) so an engine's home link can't masquerade as a result and, worse, ride the corroboration ranking to the top.

Corroboration by independent index, not by endpoint. After the topic check (§4UN-dark: on-topic rows first), onions surfaced by more than one independent index sort first — cross-engine corroboration is the only cheap relevance signal available for unindexed hidden services. Crucially the count is over distinct index tags, not engine names: Ahmia's clearnet and onion endpoints share index: "ahmia", so a hit reached over both Ahmia transports counts as one source, not two. Counting endpoints instead would have let any Ahmia-only result outrank a genuinely Ahmia-plus-Torch-corroborated one — turning "corroboration" into "is it in Ahmia."

Raw-HTML fetch vs. text fetch

The search phase needs the raw result HTML to parse out links, so it uses a dedicated _fetch_raw_html (curl_cffi with TLS impersonation, falling back to httpx). The research phase wants page text, so it wraps the same fetch in _fetch_onion_text, which strips tags after the fact. It deliberately does not reuse the shared helper_fetch_url_content, for two reasons: (1) that helper ignores the passed proxy and reads TOR_PROXY from the environment, silently discarding both a caller-supplied proxy and the per-query anonymity identity tag; and (2) on any fetch error or 503 it calls request_new_tor_identity, which does a global NEWNYM or — if the control port is closed — a tor service restart. Since onion fetches fail often and research fans them out concurrently, that would re-circuit or restart Tor mid-run and sabotage the sibling fetches. _fetch_onion_text keeps the shared SSRF guard but honours the passed proxy and never re-circuits.

Untrusted-body cap. Onion engines are adversarial by this tool's own posture, so _fetch_raw_html caps every response at _MAX_ONION_BODY_BYTES (5 MB): it refuses binary content-types and bodies whose declared Content-Length exceeds the ceiling, and truncates the decoded text as a backstop against a server that lied about its size or streamed chunked (mirroring the cap helper_fetch_url_content enforces on clearnet). Streaming enforcement (2026-07-07): the fetch now STREAMS the body (curl_cffi aiter_content / httpx aiter_bytes) and stops reading at the cap, so a chunked body with no (or a lying) Content-Length can no longer be materialised whole via r.text before the truncation backstop runs — the read itself is bounded, closing the OOM window a hostile engine could open by streaming a multi-GB body straight into memory.

Bounded on the loop, not on threads (2026-09-14). The fetch runs on the event loop through curl_cffi's AsyncSession, with _onion_gate() — an asyncio.Semaphore rebuilt whenever the running loop changes — holding the same 16-way bound the old _ONION_EXECUTOR thread pool provided, so excess fetches queue instead of piling concurrent circuits onto Tor. It used to be a synchronous Session on that pool, and that aborted the whole process. A second benefit of the move: when the per-engine deadline fires, asyncio.wait_for now really does abort the transfer, instead of cancelling the await and leaving a worker thread running on until curl's own timeout.

Anonymous mode

Under --anonymous, the same stylometric egress scrubbing as clearnet search applies: darkweb_search uses the deterministic scrub_query plus a per-query SOCKS identity tag; darkweb_research uses the stronger LLM-based neutralize_query. Tor anonymises the network; this anonymises the content fingerprint of the query before it leaves the box. Because the research deep-read now fetches onion pages through the caller's proxy (via _fetch_onion_text) rather than the environment default, the per-query identity tag actually reaches the page fetches too, instead of being discarded at the transport boundary.

Deep-read sizing & caching

The per-source extract in darkweb_research is sized to the worker model's context window (max_context) rather than a fixed 40k chars: it reserves room for the prompt scaffold plus max_tokens and shrinks the source slice accordingly (≈4 chars/token, with a 4k-char floor and the 40k ceiling), so a small-context worker can't overflow on the distill call. The synthesised report is cached under an onion-research:: key (distinct from the list search's onion::), so a repeated identical research request is served from cache instead of re-fetching every onion over Tor.

Safety posture

Hidden services are unverified and frequently malicious. The tools never auto-execute or auto-download anything — darkweb_search returns links only, and darkweb_research returns extracted text with an explicit instruction to treat all claims as unverified and corroborate before relying on them. Every reached onion host is logged to the operator's live stream via pretty_log with a distinct 🧅 icon.

Tests

Parsing (anchors, redirect unwrapping, plain-text sweep, de-dup), independent-index corroboration ranking (the two Ahmia endpoints are not double-counted), engine self-link filtering, the per-engine deadline, the untrusted-body size cap (_cap_body: binary refusal, declared-oversize refusal, truncation), the actionable zero-results error, anonymous-mode scrubbing, the GHOST_ONION_ENGINES override + malformed fallback + stray-placeholder rejection, socks5h normalisation, result caching, the research deep-read path honouring the passed proxy, research caching, and max_context-bounded extraction are covered by tests/test_darkweb_search.py.

Onion DNS-leak fix (2026-07-14)

_fetch_onion_text (the research-phase page fetch) validated the onion URL with the SSRF guard's default resolve=True — a host-side getaddrinfo on the .onion hostname. For a hidden service this is the sharpest form of the leak: it tells the host resolver which hidden service is being visited (and fails anyway, since .onion addressing lives at the Tor SOCKS layer, not the host resolver). Now passes resolve=False — this path is always over Tor. The literal-internal-IP string check still runs. Covered by tests/test_fetch_dns_leak.py.

Dead-engine detection + charset (bug-hunt 2026-07-26b, HIGH)

Both Ahmia endpoints stopped returning parseable results, silently degrading darkweb_search to torch-only (flaky) while the tool blamed the query ("transient downtime / too-specific"). Root mechanism was a SILENT empty-parse: a 200 that parses to zero results was indistinguishable from an unreachable engine — no log. Now a 200-with-zero-results logs a distinct diagnostic. Separately, _fetch_raw_html honoured the declared charset instead of force-utf-8 decoding (Cyrillic/CJK onion content — a large fraction of the darknet — came back as mojibake).

The diagnosis in this section was wrong, and the correction is instructive — see the form-token entry below. Ahmia was never serving a JS-only template. The "live-confirmed 4727-byte page with zero result links" was Ahmia's homepage, reached by a 302 the fetcher silently followed; the JS-only label came from a display:none notice on that homepage matching a bare "javascript" substring test. The engine was healthy the whole time.

Ahmia form token + honest empty-body diagnosis (2026-07-28)

Ahmia gates its search endpoint behind a hidden form field: /search/?q=… 302-redirects to / unless the query string also carries the <input type="hidden"> pair from its search form. Measured live over both the clearnet mirror and the onion endpoint — the redirect is not Tor-, exit-node-, user-agent-, cookie-, or referer-dependent; it is purely the missing parameter. With the token appended, the same endpoint returns a full results page (~1.1 MB, ~2900 onion links).

An engine entry may now declare form_token_from (a URL whose search form carries the field); both Ahmia entries do. _form_token scrapes the pair via _parse_form_token — preferring a form whose action/id/class looks like a search endpoint, so an unrelated CSRF field on a newsletter box can't be mistaken for it — and caches it for _FORM_TOKEN_TTL (30 min). The token is stateless (no cookie or session is involved), which is what makes caching it across circuits sound. Only a successful read is cached. A None from a page we actually fetched means "this engine needs no token" and is worth remembering; a None because Tor timed out or the page returned 503 means nothing, and caching it would turn one transient blip into 30 minutes of the engine querying without the token it requires — 30 minutes of zero results, the exact failure the token exists to end. Same discipline the rest of the project applies to measurement: never record a failed measurement as a neutral value. It is scraped rather than hard-coded because the entire point of such a token is that the operator can rotate it; if a query is still redirected away, the cached pair is dropped so the next (already circuit-rotated) attempt re-scrapes. The fetch fails open — on any error the engine is queried exactly as before — and runs under a tighter _FORM_TOKEN_TIMEOUT = 12 s than the search itself, since it spends the same per-engine deadline the query needs.

Why the old diagnosis was confidently wrong. _fetch_raw_html follows redirects, so the status code alone cannot tell you whether the body came from the URL you asked for: a dead endpoint that 302s to a live homepage is indistinguishable from a live endpoint serving an unparseable page. The empty-body branch then tested for the bare substring "javascript" — present in almost every modern page — and Ahmia's homepage happens to carry a display:none notice reading "we have not deployd non-JavaScript version of Ahmia yet", intended for non-Tor-Browser visitors. Two independent weaknesses lined up to produce a specific, plausible, actionable, and entirely incorrect instruction to the operator: swap engines, when the real fix was one query parameter. That message stood in these docs for two days.

The fix is structural rather than a better guess. _fetch_raw_html accepts a meta dict and reports the final_url a body was actually served from, and _diagnose_empty_body ranks the possible explanations by how much the evidence actually supports, because each message ends in a different operator action:

  1. redirected — we were served a different location than we asked for. Whatever that page says is evidence about a page we never requested, so this has to win over anything read out of the body.
  2. no-hits — the engine explicitly says the query matched nothing (_NO_HITS_RE). This is the ordinary case and it is not breakage.
  3. js-only — requires both a needs-JavaScript sentence (_JS_ONLY_RE) and a body under _JS_SHELL_MAX_BYTES (32 KB), since a page that genuinely cannot render without JS is a shell.
  4. parser — none of the above; the result format may have drifted.

The first version of this fix did not go far enough, and the review that caught it is worth recording. Two independent reviewers found that the js-only branch still produced the original lie by a different route: Ahmia's no-JS banner is in its site-wide template, not just the homepage, so a perfectly healthy zero-hit search — token accepted, no redirect, engine fine — still matched the wording and still told the operator to replace the engine. Verified against a live zero-hit page. Three things were wrong: there was no branch at all for the most common cause (the query simply had no matches); the wording test was polarity-blind, so "works without JavaScript" and "No JavaScript required" — precisely the boasts privacy-focused onion engines put in their footers — matched as evidence of breakage; and the sentence alone was allowed to carry a conclusion it cannot support without the structural size check. The lesson generalises past this file: tightening a heuristic is not the same as bounding what it is allowed to conclude.

_redirected_away is likewise deliberately conservative, normalising host case, www., default ports and path case before comparing — a false positive there is not merely a bad message, it evicts a good token and buys a wasted retry on every query. Token eviction is further gated on having actually sent a token and on being the first attempt, so a captcha or exit-ban page cannot throw away a working one. Redirect messages name host + path (the host is the load-bearing part — a foreign host and this site's homepage call for different responses) but never the query string, which carries the search terms; onion hostnames are scrubbed downstream by the log redactor.

Deadline accounting. A token engine spends an extra fetch inside the per-engine deadline, so _ONION_ENGINE_DEADLINE is extended by the token budget for those engines. Shrinking the search timeout instead would guillotine slow-but-alive engines — the failure mode search.py's mojeek timeout already taught this project once.

The generalisable lesson for the next engine that breaks: check the redirect chain before believing an engine-health diagnosis, never anchor a health check on a substring ordinary pages contain, and make sure a diagnostic has a branch for "nothing is wrong". Covered by tests/test_darkweb_form_token.py, including the ordering regression, the live-verified zero-hit page, the polarity boasts, cosmetic redirects, fragment and duplicate-parameter URL assembly, and the deadline headroom.

The fetch that killed the agent (2026-09-14, §4GM)

The agent died twice in twelve hours — SIGABRT at 2026-09-13 22:19:51 and again at 2026-09-14 09:07:40, the second time in the middle of a live investigation, one second after an onion engine's post-deadline fetch was still running. Both macOS crash reports carry the same stack, on a worker thread: 

abort ← malloc_report ← ...POINTER_BEING_FREED_WAS_NOT_ALLOCATED
      ← Curl_freeset ← curl_easy_reset        (libcurl-impersonate)
      ← _cffi_f_curl_easy_reset               (curl_cffi)
      ← ...Python frames... ← thread_run

_fetch_raw_html was the only synchronous curl_cffi.requests.Session left in the tree, and it ran on a thread pool. With stream=True that path duplicates the easy handle (curl_easy_duphandle), resets the parent immediately, performs the transfer on a thread pool of curl_cffi's own, and resets the duplicate from a done-callback on yet another thread. libcurl-impersonate does not deep-copy that option set, so the two resets free the same pointer and libmalloc aborts the process. It was reproduced locally in about forty seconds by replaying that exact call shape — impersonation, SOCKS proxies, stream=True, body abandoned at the byte cap — on eight threads: the same curl_easy_reset double free, plus a second crash reading “memory corruption of free block” inside curl_slist_append.

Nothing above libcurl can survive that: the process is gone with no traceback, the in-flight request is lost, and launchd restarts the agent a few milliseconds later — which is exactly what the operator saw as a restart mid-thought.

The fix is to stop using that shape. The fetch now runs on AsyncSession, the path every other fetch in this codebase already used: it takes a handle from a pool and resets it on the loop thread, and there is no duphandle in the async code at all. The 16-way bound the thread pool provided is kept as _onion_gate(). Cancellation improves as a side effect — the per-engine deadline now aborts the transfer instead of orphaning a thread. Pinned by tests/test_4gm_onion_fetch_async.py, whose last test drives 144 abandoned/failing fetches in a child process and fails on a non-zero exit, so the abort is a red test rather than a dead suite.

The generalisable lesson: a C library's threading contract is part of your API surface. This call site had been correct Python for months — the cap, the charset, the SSRF guard, the redirect bookkeeping and the bounded pool were all carefully built on top of a primitive that could not be used from more than one thread. Nothing in the Python layer can detect that; only the crash report names it.

Breadth in one round: extra_queries 2026-09-14 §4GN

A dark-web brief that enumerates ten phrasings and five target forums used to cost ten sequential tool calls — so in practice it got two. Measured twice on the same investigation: the original run (cf45e352) ran two queries, the re-run (da4c17ba) ran two again, against a brief naming BreachForums, Exploit, RaidForums mirrors, paste sites and leak indexes. Nothing was wrong with the model's judgement; each extra phrasing carried a whole round-trip's latency, and it was spending that budget on the clearnet instead.

darkweb_search now takes up to three additional phrasings in extra_queries and runs them in the SAME round. Four phrasings × four engines is sixteen onion fetches — exactly the bound _onion_gate already enforces — inside one per-engine deadline instead of four. Results merge on the onion host and keep the signal the single-query merge already prizes (a service surfaced by MORE INDEPENDENT INDEXES ranks higher), extended with the phrasing that surfaced it: each row is tagged (via ahmia, torch; matched: revolut government email; revolut breach sender domain), so a broad hit is distinguishable from a lucky one. In anonymous mode each phrasing keeps its OWN identity-tagged SOCKS circuit — running the set over one circuit would relink precisely what the per-query tag exists to separate.

Two details that are load-bearing rather than cosmetic. Deduplication happens before the cap: the cap bounds fetch cost, and a repeated or whitespace-variant phrasing costs nothing to drop, so letting it consume a slot would silently narrow a brief that listed five wordings of which two normalise the same. And a single-query call is byte-identical to what it always was — no phrasing header, no matched: tag — because the result text is what the 5-minute cache stores and what every caller downstream parses.

"No documents match your query" is a zero-hit answer 2026-09-15 §4HB

torch runs Xapian Omega, whose zero-hit page reads No documents match your query. _NO_HITS_RE knew "no results", "no matches", "nothing found" — not that — so every torch miss fell through to the last branch and was reported at WARNING as "the engine's result format may have drifted". Fetched over Tor on 2026-09-15: every "empty" torch response in the log (1.7–1.9 KB) is that page. The phrasing is now in the pattern; tests/fixtures/torch_zero_hits_2026-09-15.html is the real body (form token scrubbed) and tests/test_darkweb_no_hits_phrasings.py pins it, together with the requirement that a genuinely unparseable page still reaches the parser branch — that is the drift signal.

Titles are not pages; read the on-topic ones 2026-10-04 §4LG

  • darkweb_search's header says its results are titles and snippets only — no page was opened (a reply had described "active MH370 threads" from directory titles).
  • darkweb_research fetches 3× the candidates and opens on-topic results with a path first (rank_for_reading, the web search's own topic check): ranked by engine agreement alone, 32 of 36 pages read yielded nothing, 25 of them homepages.

Torch is a fallback 2026-10-04 §4LH

Over 3 weeks torch was useful in 22% of searches (78 "no matches", 34 timeouts at the 38 s deadline). It now carries "tier": "fallback", and an engine in GHOST_ONION_ENGINES may carry the same. _darkweb_search_raw asks the first-tier engines, and only when they found fewer than _FALLBACK_MIN_HOSTS (5) distinct onions does it ask the fallback tier, with its own short deadline _FALLBACK_DEADLINE_S (12 s; torch answers in 2–6 s when it answers). The skip and denominator arithmetic counts the engines actually asked. A search with zero results always reaches the fallback, so "asked N of M" stays whole. GHOST_ONION_FALLBACK_TIER=0 puts every engine back in one wave.

§4LI: a fallback engine cut by the 12 s deadline is recorded as a failure by the circuit breaker (the cut cancelled _query_engine before its own timeout could record anything, so a dead torch was paid for on every thin search), using utils.aio.wait_for.

Research yield on onion sites 2026-10-11 §4NK

darkweb_research now shares the clearnet research helpers (§4NJ; search.run_research_slots, slot_coverage, research_no_facts). Of 58 stored onion sources, 45 came back "nothing relevant" and 11 had facts. Bare homepages yielded 0 facts in 25 reads; pages with a path yielded facts in 11 of 29.

  • What is opened: is_onion_reading_candidate(url, on_topic) skips off-topic bare homepages, script/style/image/font files and a site's own search-results pages while another candidate exists. An on-topic homepage is still read (§4LG: topic beats path), and so are .txt/.json/.xml files: on onion sites a paste or canary is the content. If nothing qualifies, the ranked list is read as before.
  • A DDoS-guard interstitial is a failed fetch (search.is_bot_check_page).
  • A failed onion hands its slot to the next result (up to 7 reserves, 2 per slot, inside the phase deadline). Coverage is counted in slots, and replaced services get their own line. A reserve that the deadline stopped marks the run as truncated, so it is not cached.
  • No relevant facts: the [⚠ NO RELEVANT FACTS: …] banner and reason code darkweb_research_no_relevant_facts, also on a cache hit. The evidence gate reads it as empty.
  • The extractor recheck works as in deep_research: see search §4NK.

darkweb_search (the listing) fetches only engine result pages, so none of these source fixes apply to it. There is no recorded case of an engine bot-check page being misread as format drift. Tests: tests/test_4nk_darkweb_research.py.

§4PU (2026-10-17): a past year next to "today" is dropped

The model's training ends in 2025, so it sometimes adds "2025" to a question about today. This happens even though every turn shows it CURRENT TIME (live request 3c527b55 searched "VUAA Vanguard S&P 500 ETF price today 2025" on 2026-10-17). Before searching, search.drop_stale_year removes a year only when all of these hold:

  • The year comes right after a point-in-time word: today, tonight, now, currently, this week/month, or the Greek σήμερα, τώρα, φέτος. "Price today 2025" says two different dates at once. A year before the word is left alone, because it is usually a product, model or edition ("Hyundai Tucson 2025 now recall", "ISO 27001 2022 currently"). Only the copy right after the word is removed, so "Camry 2025 price today 2025" keeps the model year. "Current" and "latest" are not enough, because they describe a noun that can carry a real year: "SQL Server 2025 latest update", "current F1 season 2025", "Office 2024 current price".
  • The year is a bare token before this one. 2024-10, v2025, $2025 and 2025's are left as they are, and so is a date like "October 2025".
  • None of your recent messages (the last four, this one included) contains that year, even as "…of 2025." or "FY2025". "What version of postgres was released in 2023?" keeps 2023.
  • Nothing makes the year the subject of the search. The word right before it isn't a period or comparison word (for example since, in, of, for, from, until, vs, FY, tax, Q1–Q4, a month name, or Greek από, μέχρι), and the query has no comparison or period word anywhere (for example vs, versus, compared, annual, report, fiscal, tax, earnings, YTD, 10-K, results, season, edition, since). The full lists are _YEAR_ANCHOR_BEFORE and _YEAR_ANCHOR_ANY_RE in tools/search.py.
  • The query does not also name this year.

The rule is narrow on purpose. Two review rounds showed that a wider list of "now" words dropped years that mattered (product names, comparisons, seasons), while each patch for those missed real stale years. A year it misses is searched as before, but a year it drops by mistake gives a wrong search. A replay over the 3,828 logged search calls since August changes exactly one query: 3c527b55.

The log prints Search Year — web_search: dropped past year 2025 from a query about now ‹…› → ‹…›. The result ends with "(Searched without '2025': the query asks about now, and today is 2026-10-17. If you meant that year itself, say so in the query — 'since 2025' or 'in 2025' keeps it.)". The check covers web_search and deep_research (and fact_check, which uses it). It also covers darkweb_search (every query, including extra_queries) and darkweb_research. Both research tools run it again after the anonymising rewrite.

Fresh-eye review: the dark-web tools 2026-10-14 §4PD

  • CRIT fixed — the parser froze the event loop. _parse_onion_results called block.get_text() once per anchor (quadratic: 8,000 anchors in a 1.1 MB page = 40 s with every owner turn, Slack and the heartbeat stalled) and ran synchronously. It now computes one text per block, reads at most _PARSE_MAX_ANCHORS (1,500) anchors, and runs under asyncio.to_thread.
  • A redirect to another host is not the onion. _fetch_onion_text records the final URL and refuses (naming the host) a body served from a different host — an onion bouncing to the clearnet was read and attributed to the onion. An engine answering from another host is logged on every response.
  • Result rows cannot forge rows or banners. Titles and snippets are one line with no [/] and no ### run, so an engine's HTML cannot add a ### 2. … [Onion: …] (via …) row or a [⚠ SYSTEM …] line.
  • An honest "no documents match" page does not trip the breaker (three exotic queries on a small index used to put the engine in cooldown and the next search was told the engine had failed). The breaker still advances on empty bodies, redirects and errors.
  • A fetch failure is the fetcher's type (FetchError), not the page's first word; v2 (16-char) onions are no longer harvested (dead since 2021); a model-passed max_results/max_sources is coerced to an int in range instead of raising inside gather() and reading as "zero results".
  • Anonymity note: the per-query SOCKS identity tag reaches page fetches only under --anonymous; in the default mode page fetches ride the shared default circuit (the search phase re-tags per engine and attempt either way). NO_PROXY/no_proxy in the environment would bypass an explicit proxy under libcurl — not set by the launcher or the LaunchDaemon; keep it so.

Internet-tools review: the dark-web tools 2026-11-13 §4UN-dark

  • No invented onion addresses. onion_v3_valid checks the checksum built into every v3 address (the 56 characters are base32 of pubkey + 2-byte checksum + version 3; checksum = SHA3-256(".onion checksum" + pubkey + 0x03)[:2]). The parser, the wrapper unwrap and the plain-text sweep keep only valid addresses. In darkweb_research a worker's summary (the first pass and the recheck) keeps an address only when it is verbatim in the page it summarised (keep_page_onions); any other one becomes the link guard's own "[onion address removed …]" mark. Before, a summary that copied an address and changed a letter put a fake address into tool output, and every later guard accepted it as seen. The reply guard (core/link_grounding._onion_kind) now calls a 56-character address with a failing checksum invalid, and onion_claim_issues says "its built-in checksum fails" — unless that exact address is in the user's own words (user_text): then the reply quotes it. One that only tool output held gets a non-blocking note (notes, logged), not an issue; one seen nowhere is an issue (r2). onion_v3_valid lives in core/link_grounding.py (core does not import tools); darkweb_search re-exports it. A subdomain address (www.<v3>.onion) is validated on its v3 label.
  • "No match" is an answer. An engine whose page says no documents matched is not asked again on a second circuit, and is never charged a breaker failure for it, even when the overall deadline then runs out. A page that says "no match" and holds at most _NO_HITS_MAX_LINKS (5) onion links is that answer: the links are page furniture (an ad, a sidebar). The phrase is read on the page's visible text nodes that are not inside any result's own element (the parser's rest; r3: built from the nodes, because cutting an ad's text "No" or "results" out as a substring split the banner): a 3-result page whose snippet read "Unable to find your order?" was booked as no match and its real results dropped. A result's own text is its nearest block that holds that link and no other, or just the link's text — never a wrapper: r1 deleted the widest such block, which also held the banner when the ad and "No documents match" shared a wrapper (wrap div, Ahmia li.result), and the ad was booked as a result. Limit: a link sitting directly in the same block as the banner, with no block of its own, reads as a result. "No results" text inside a script, style, template or comment does not count (_visible_text).
  • Per-URL results, honest snippets. A forum's /thread/123 is its own result beside the site's homepage (at most _MAX_PATHS_PER_HOST = 3 per site — www.<v3>.onion and <v3>.onion are one site, a :port makes another URL; on-topic rows first, then a page with a path before the bare homepage). A snippet is the text of the largest block that holds this one result and no other; only links that will be results count as "another result" (the engine's own cached/report links blanked every snippet). Results that shared one container got the whole list's text, so an unrelated row carried another row's words and ranked as on-topic. Engines with a known result container read only inside it (result_selector: Ahmia li.result; configurable in GHOST_ONION_ENGINES).
  • Page furniture and ads. Nothing is remembered between searches. A first version learned the links on an engine's no-hits page as "furniture" and dropped them from every later query for a day; the review (r1) found it hid real hits (one false no-hits page put three real URLs on the list; Ahmia's sidebar link was later lost as a real li.result; the whole set was re-stamped on every no-hits page, so it never expired). Instead an ad is handled where it shows: on a no-hits page it is not a result (above), and on a results page it ranks with the off-topic rows. Rows are ranked on-topic first, and among off-topic rows a bare homepage below a page with a path (r2: an ad two engines both showed outranked an off-topic real page), before index agreement, so an ad or a "popular sites" link two engines both show cannot lead. Host agreement (the same site under several engines or phrasings) is a weaker, second signal.
  • What each engine's query came to. Every engine query ends as one of: results, answered with no match, answered with nothing parseable, redirected away, needs JavaScript, timed out, unreachable, or skipped (cooldown). The log prints Darkweb Engines — results: …; answered, no match: …. The empty-search error appends Engines — …, and, when every engine asked answered "no match" (results or no match only — "nothing parseable" is layout drift, not an answer), replaces the base text, which blamed flaky engines or the query, with "a real negative for these indexes". "Engines reached" in a result header counts the same set; an engine whose page could not be read is listed with the others that gave no answer. A result list names engines that were not searched. "Engines reached" counts the engines that answered (it was counted from the rows left after the cut).
  • A page served from another location is not results (a homepage's "featured" onions became query matches), and it is not a breaker win.
  • Topic before the cut. _darkweb_search_raw marks each row on/off topic and sorts before cutting to max_results. darkweb_research cut to max_sources×3 by agreement first, so on-topic rows further down a 28-host page were never considered.
  • One breaker failure per engine per call (_BREAKER_CALL). A 4-phrasing call queries each engine four times at once, and one bad Tor patch benched it for 15 minutes in a single call.
  • Smaller fixes:
    • URLs scanned from page text (the regex sweep) have &amp; collapsed and lose trailing punctuation (…&amp;raw=1. gave a 404); a closing ")" stays when the URL opened one. Only &amp;: a full unescape turned &section=2 into §ion=2 (legacy entities need no semicolon). An href is never decoded again — the HTML parser already did.
    • A :port and a subdomain stay part of the URL.
    • Any query value of a redirect wrapper that decodes to an onion URL is unwrapped, not just redirect_url/url/u/d — also when the wrapper sits on the engine's own onion (<engine>.onion/redirect.php?url=…).
    • Each attempt has its own clock (_ONION_TIMEOUT + 2 s). curl's timeout is a low-speed limit, so a stalled first attempt used the whole engine deadline.
    • A run with an engine in cooldown, or with an engine that timed out or was unreachable on any phrasing, is not cached (decided per phrasing — the merged outcome is each engine's best); the cache key holds max_results (research: max_sources).
    • An engine whose first attempt returned an unreadable page and whose second timed out reports "nothing parseable", not "timed out".
    • A binary or oversize onion page says so ("it is a file (application/pdf), not a page this tool reads") instead of "received status 200".
  • Torch stays in the fallback tier with its breaker. The repo has no measured replacement (tordex was 1/6 in the 2026-07-29 survey).
  • Pins: tests/test_4un_darkweb.py. tests/onion_v3.py builds checksum-valid test addresses, because "a" * 56 is now rejected.

darkweb_research: the model's pages, news first, fast failure, exact counts 2026-11-13 §4UN-darkres

Request 212e6a8c asked for "the latest news on the dark web". darkweb_search had found pages; darkweb_research ignored them, ran its own search and read shop pages ("residence permits for sale", a market page). Two pages were fetched at a time, and each dead onion held its slot for 35 s: four rounds, about 140 s. The distiller was then left "-5.6 s of budget" and declined. The reply said 5 of 6 sources had failed; the model's reasoning said 7 of 8.

  • urls (optional, at most 8). The pages the model already chose are read first, in order, and are never demoted or filtered. With a query, its search results fill the remaining max_sources slots and the backfill queue; without one, only the given pages are read and no search runs. Only http/https URLs on a v3 onion whose checksum holds are read (a bare <56 chars>.onion/… gets http://). Any other URL is never fetched: the report names it on a [SKIPPED URLS: … — reason] line (whitespace or a control character, a wrong scheme, not a valid onion address, over the 8-URL limit). The reason names the check that failed (onion_v3_problem, dr2): "wrong length: got N characters, a v3 address has 56", "not base32", "wrong version byte", or "the checksum does not match — at least one character is wrong (a typo or a deliberately altered address)". The vague "not a valid onion address" had the model distrust it, write its own faulty decoder and repeat what that decoder got wrong. A refused URL is never echoed whole (r2: an over-limit one too; r3: a percent-encoded %2eonion host too): an onion-like host shows the first 8 characters of its label then ….onion, another host its name only. Review r1 found that an echoed garbled address let the verifier treat a reply citing it as "seen in tool output" (a note, not a block), and that a newline inside a URL forged a ### SOURCE: block, a second count line and fake facts. A kept URL is rebuilt from its parts: scheme, lower-case host without a trailing dot, port, path and query, with no userinfo or fragment. Two spellings of one page are therefore read once. The cache key includes the given URLs. Pages read this way are ### SOURCE: blocks like any other, so link grounding counts them as read.
  • News before shops. When the query asks for news, an article, a report, a blog or an analysis (English, or Greek νέα / ειδήσεις / άρθρο / ανάλυση / αναφορά / ρεπορτάζ; accents ignored) and does not ask for markets, vendors, products, prices, buying or selling, rank_for_reading puts a shop or product page after the other pages in its topic group. A page counts as a shop page by its path (/product/, /shop/, /store/, /cart, /checkout, /vendor/, /listing/) or by "for sale", "add to cart" or "buy now" in its title or snippet. A price or an amount alone does not count ("Bitcoin falls below $60,000" and "500 BTC stolen" are news), and neither does /item?id= (r1). It is demoted, never dropped: when only shop pages exist they are still read. The word lists are tables in darkweb_search.py (_NEWS_INTENT_WORDS, _MARKET_INTENT_WORDS).
  • A dead onion fails at the first byte. _fetch_raw_html(…, first_byte=) waits _ONION_FIRST_BYTE_S (15 s, GHOST_ONION_FIRST_BYTE_S) for the status line and headers. A page that answers keeps the full read time for its body. The failure reads "no answer from … within 15s (timed out)". The httpx fallback can only bound the connect.
  • One retry after a dead first byte (live dr2, 2026-11-14). The Tor Project's onion, a valid given URL and the only page, timed out at the 15 s first-byte wait. The model's own retry a minute later loaded it in 2 s. A page that fails on the first-byte wait (_FirstByteTimeout; no other failure) is now retried once, straight away, on a fresh circuit (_fresh_circuit. Live proxies already carry an identity, because --anonymous is the default, and socks_url_with_identity returns them unchanged. So the attempt is folded into that identity with circuit_for_attempt (§4UN-read). A proxy with no identity gets a random tag. Review r3 found that the first version retried on the same circuit). The retry runs only while the URL's time and the phase's still cover a first-byte wait, plus _RETRY_READ_S (10 s), plus the distill reserve (55 s live). Given pages come first: a search-filled page is retried only while the phase also covers a retry for every given page not yet settled. A retried page is counted once in [SOURCES:].
  • Four at a time. _RESEARCH_FETCH_WIDTH = 4 (was 2). The old comment that "the 3rd and later onions were the starved ones" described per-URL clocks started at gather. Each URL's budget is now issued when it starts, so a wider gate does not starve the later ones. The distill plans declare the same width (concurrency=4), so each plan is sized for a shared node.
  • The distiller's time shortens only the wait for the first byte. With a distiller, the first-byte wait is the URL's budget minus 2 s minus _DISTILL_RESERVE_S (30 s), at least _FIRST_BYTE_FLOOR_S (5 s) and at most 15 s. A page that answered reads its body until the full read time (40 s) or the URL's budget minus 2 s, whichever comes first. A page still loading then is kept: the text that arrived appears under a [PAGE CUT OFF: …] line as raw text, counted as loaded (_fetch_raw_html(body_deadline=); a transfer error after some bytes arrived keeps them too). r2: the body stops 4 s before the fetch's own timeout (at least half the fetch time is kept for it). The response close waits at most _ACLOSE_WAIT_S (2 s), then the session closes it. On this path the HTML is stripped after the fetch's timeout instead of inside it, because a 2 MB page took 1.35 s. Together these keep a cut page from turning into a timeout. A page that used its whole time leaves no time for the distiller, so its raw text is kept, and the distiller is never planned on a negative clock. The limits reach _fetch_onion_text through a context variable (_PAGE_LIMITS), so its two-argument shape stays. Review r1 (M3) found that the first version capped the whole fetch, so a page answering at 8 s and done at 30 s was cut at 28 s and booked as a timeout.
  • Exact counts at the head. The report's first line is [SOURCES: tried N, loaded M, timed out K, failed F, skipped S]. Tried counts every fetch that started, backfills included. Skipped counts a given URL that was refused plus a source the phase deadline never started. The counts come from what this code recorded for each URL, never from page text. A timeout is a type (_FetchTimeout; curl error 28, or a *Timeout* exception class), never a word in the error text, so a URL path with "timeout" in it is not one. The [⚠ SOURCE FAILURES: X of N …] banner uses the same counts: X counts the URLs that timed out, failed or were not started before the deadline, and N counts the URLs tried plus those not started (r1). Before, it counted slots. A page line (or a summary line) that starts [SOURCES:, [SKIPPED URLS: or [PAGE CUT OFF: is quoted (neutralise_report_grammar).
  • Timing (test, scaled): 8 sources with 6 that never answer (read time 3 s, first byte 0.5 s). Before: two at a time, each dead one held 3–8 s, over 9 s in total. Now: about 1 s, and both live pages are distilled. Live, the same shape is about 30 s instead of 140 s.

The fetch-width declaration moved in tests/test_distill_budget_sizing.py, the schema check in tests/test_darkweb_search.py (query is no longer required for the research), and one banner total in tests/test_4nk_darkweb_research.py (it now counts URLs tried, not slots).
