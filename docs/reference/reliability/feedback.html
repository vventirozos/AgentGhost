core / feedback.py

Human outcome labels (2026-08-13, Track 1a of the outcome-supply plan): a 👍/👎 from the human who read the reply becomes a corrections-sidecar record, resolving a turn's outcome=unknown. Tests: tests/test_human_feedback.py.

Why

~57% of real turns end outcome=unknown (§4BC) and every measurement clock — experiment arms, the resolved-rate (and, until the lesson store was removed on 2026-11-06, lesson utility) — is gated on RESOLVED outcomes. The cheapest resolver is the human who just read the reply. This module is the one chokepoint that turns "request_id + thumb" into the same overlay record the user-correction promoter and the late verifier verdict already write, so every corpus reader (iter_trajectories, report_from_trajectories, the failure census, the experience index) picks the label up with zero new plumbing. (Reflection and the PRM/router trainsets, which also read it, were removed on 2026-10-11, §4NM; the failure replay and the regression seeds on 2026-11-05, §4SZ. A 👎 no longer starts a replay.)

Side effects, in order

  1. Corrections sidecar via collector.update_outcome (source human_feedback:<source>): positive → passed (never carries a reason — writer and overlay both enforce it), negative → failed with the note (redacted, truncated) as reason, or the self-describing default "human negative feedback".
  2. In-process cache (_recent_trajectories_for_correction): the cached trajectory is mutated and stamped human_labeled (snapshot walk — the cache is loop-owned; re-stamped even on idempotent repeats so a failed first stamp is repaired by the next click).
  3. One pretty_log line (👍/👎 icons) — the operator watches the stream.

No lesson credit any more (2026-11-06, §4TD). Until then the /api/feedback route also booked the label against the lessons the turn had been shown (_flush_stashed_lesson_outcome, on the event loop, because this function runs on a to_thread worker). The lesson store is removed and that step with it. What a thumb does is unchanged: the label is recorded, the diary row and the mood follow it, a queued correction for the turn is dropped, and a thumbs-down returns the hint below.

The thumbs-down hint is added at the route too (2026-11-05, §4SZ). apply_human_label returns no hint. When its result is ok, the signal is negative and the result is not an unchanged repeat, the route adds "hint" = core.owner_rules.FEEDBACK_HINT ("Noted. If there is something I should always do differently, state it as a rule — say: learn this rule: <the rule>") to the response. The label itself no longer starts anything that changes the agent: the failure-replay loop it used to seed was removed the same day. The web client shows the hint once per page load. See api.routes and Owner rules; pinned by tests/test_4sz_thumbs_down_hint.py.

Idempotent repeats (2026-08-13, from the first live test — three 👍 in 2s appended three rows): a repeat of the CURRENT label (same outcome, source, and redacted reason) is acknowledged with {"ok": true, "unchanged": true} and writes nothing (debug log only). The dedupe lives INSIDE update_outcome's lock (skip_identical=True → returns the truthy string "unchanged") — R2 review: a caller-side compare-then-write was a check-then-act race across concurrent executor threads. Switching signals — or a negative with a different note — still writes; last-write-wins stays the semantics.

Verdict-then-label ordering (R2): when the machine verdict landed FIRST, a human label also revokes any queued next-turn correction banner for the trajectory (_drop_pending_corrections_for; the banner used to apologize for an answer the user had just thumbed up). Follow-up tasks filed before the label STAND — logged, not reversed. (Until 2026-11-06 it also re-booked the lesson credit with the human sign; removed with the lesson store, §4TD.)

Authority: human labels outrank machine verdicts — at two layers

In-process: _human_label_locked (agent.py) gates the ENTIRE late-verdict consequence chain in _record_late_verdict — corpus backfill, the stream re-render, follow-up filing, and the next-turn correction banner all yield with one WITHHELD line (R1 review: the original backfill-only guard let the rest run, apologizing to the user for an answer they had just thumbed up). At the writer: the late-verdict sidecar append passes yield_to_human=True, and update_outcome refuses — inside its lock, against the file — to supersede a human_feedback:* record with a machine one. That closes the race the stamp can't see (the machine write is DEFERRED through a background thread, so it can be checked before the label exists yet land after it) and survives restarts and cache eviction. Among HUMAN sources (feedback, user-correction promotion, operator scripts) last-write-wins stands, mirroring the established user-correction doctrine.

Deliberately not wired (follow-ups, not oversights)

  • Calibration re-labels — removed in §4PJ (2026-10-16). From §4EE (2026-09-02) the label also went to CalibrationTracker.record_human_label and the Human Feedback line ended calibration relabelled or calibration unchanged. The calibration corpus and the composite confidence score it fitted were removed with §4PJ, so a thumb now writes the sidecar record only and the Human Feedback line has no calibration suffix.
  • Reaction removal — labels only accrete; a changed mind posts the opposite signal and last-write-wins resolves it.

Producers

  • Slack: 👍/👎 reactions on bot replies (slack_bot — owner or the reply's requester only).
  • Web UI: thumb buttons on agent bubbles (web_server).
  • CLI (source: "cli", 2026-08-27): /good · /bad [why…] on a streamed reply (cli). The only producer that refuses to label a cancelled or errored turn, and the only one that retries synchronously — including the TRANSPORT failure a restarting agent actually produces, which is ConnectionError and not the HTTP 503 a retry loop written for "the deploy window" naturally reaches for — and then reports whether the label landed. It is also the one where a negative's note (→ failure_reason) is routinely filled in.
  • Anything else that can speak POST /api/feedback (api.routes).
