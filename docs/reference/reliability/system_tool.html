2026-07-14 audit fixes

  • Null-valued profile keys no longer crash location lookup. _find_location_in_profile used data.get("root", {}).get(...) — a profile with an explicit "root": null (key present, value null) made the default-arg form return None and the chained .get raised AttributeError (crashing check_location, and silently killing profile-based weather lookup via the bare except). Now (data.get("root") or {}).
  • Unknown location gives a clear message, not failed: None. When the geocoder answers 200 with no results and both sources fall through, the tool now says could not find a location named 'X' (and tells the model not to retry the same name) instead of the opaque last_error=None string.
  • Tor mode detection accepts localhost/::1, not just the 127.0.0.1 literal (a socks5://localhost:9050 proxy was silently running in WEB mode — no identity rotation). The bare except: in the profile-location path was narrowed to Exception, and psutil.cpu_percent(interval=0.1) (a blocking 100ms sleep) moved off the event-loop thread. Covered by tests/test_tools_batch_audit_fixes.py.

Closed 2026-10-05 (§4LV): every HTTPS call now verifies TLS (verify=True). The record below is the earlier reasoning. Reviewed residual — verify=False on the HTTPS checks. The weather / 1.1.1.1 / check.torproject.org fetches disable TLS verification (a Tor-exit-compatibility choice). This means the Tor-anonymity confirmation is forgeable by a malicious exit and forged weather bodies enter model context. Left as-is deliberately: flipping verify on the LIVE Tor path risks regressing the weather/health tools against exits with cert-handling quirks (the usual reason it was set), the threat model (an adversary controlling the operator's own Tor exit) is narrow, weather text is already treated as untrusted external content (same trust boundary as web_search), and the wrong-anonymity-label consequence is low-stakes. Revisit if the endpoints prove stable with verification on.

Weather over Tor: a refusal is recorded, not swallowed 2026-09-09 §4FS

The same retry shape the download tool had in §4FR: a 401/403/503 from the geocoder, the forecast API or the wttr.in fallback over Tor rotated the identity and continued without touching last_error, so three refusals reported "Underlying: None". All six branches now record HTTP <status> from <server> before retrying, so the existing Tor-mode message ("the upstream weather APIs rejected the request") carries the status it saw. The server name is bounded to 40 printable characters (remote-controlled text the model reads), and a geocoder answer of "no such place" clears an earlier transient refusal so the model still gets "Do NOT retry the same name" (review, 2026-09-09). The sessions' verify=False was reviewed earlier and left as documented residual; unchanged here. Pins: tests/test_weather_tor_refusal.py.

Small-tools review 2026-10-05 §4LV

  • darkweb_research: a fetch that throws now reads Error: reading … failed — "Error reading …" matched no failure check, so it was summarised as page text, booked OK and cached for 300 s.
  • system_utility: every HTTPS call verifies TLS (8 calls had verify=False — any Tor exit could fake the weather or "Tor: Connected"); the wttr.in fallback is one bounded, control-free line; the full WMO table names drizzle, showers and snow (moderate rain is "Rain"); the place is shown with region and country. The health check gives the internet probe and the Tor check 10 s, never forces a new Tor identity on a timeout (it did, process-wide, 3×), and a failed probe over Tor says it is not proof the host is offline.
  • Unknown tool: the reply lists every tool (it cut at 40 — web_search fell off) and, for a member, only member tools; a member is never told to use execute.

Forecasts 2026-10-25 §4RE

The operator asked for forecasts (no API keys, through Tor). check_weather asked Open-Meteo for current conditions only, so "will it rain tomorrow?" had nothing to stand on. The same keyless /v1/forecast endpoint gives days and hours.

  • Every answer carries the outlook. The request adds daily=…&forecast_days=7&timezone=auto (_forecast_url). _open_meteo_report keeps the current lines (Condition/Temp/Wind/Humidity) and adds one line per day: condition, min–max °C, chance of rain, rain mm, maximum wind. Days are labelled "Today Sun 25 Oct", "Tomorrow Mon 26 Oct", then "Tue 27 Oct", from the forecast's own day order in the PLACE's time zone, never this host's clock, so the model does no date arithmetic. A normal answer is about 13 lines. A null reading is "?", never "None" (_num, _cond).
  • hourly=true (schema boolean; a string "true" is accepted, _wants_hourly) adds today and tomorrow every HOURLY_STEP_H (3) hours, from the current hour (the place's current.time) to the end of tomorrow: temperature, condition, chance of rain.
  • The fallback asks by coordinates. When the geocoder resolved the place, wttr.in is asked /<lat>,<lon>?format=j1. By name, its "Athens" was Athens, Georgia (US): 9–22 °C and sunny, while Athens, Greece had rain (measured over Tor). _wttr_report renders j1 in the same shape (3 days; hourly from its 3-hour slots). Every remote field is cut to one bounded control-free line (_wttr_text → _wttr_line). Without coordinates the report says the match was "by name only". A 200 that is not the j1 shape is a failed source, never a report.
  • One fetch path (_http_client: curl_cffi, else httpx) replaces the two duplicated ones. The geocoder's answer is kept across retries. Tor egress, identity rotation and refusal recording (§4FS) are unchanged.
  • Prompt cost: the schema and the one-line prompt hint changed, so the first message after the deploy re-processes the head once. Both are static text and identical on every request.

Pins: tests/test_4re_weather_forecast.py.

§4SY (2026-11-05): the health check reports the stores and services behind the agent

The operator: "it seems pretty limited to system metrics only, nothing about the agent's internals, memories, graphs, lessons, nothing about labs". The check reported the machine, Docker, the internet and Tor, then one line about the agent. In 30 days the owner called it 11 times; it returned about 430 characters. tools/health_internals.py adds six lines after the Agent Internals line, and the tool prints what is wrong as its third line.

  • It repairs nothing and probes nothing. Several functions named "check" or "reconcile" repair as they look (sync_owner_mirrors, reconcile_indexes, runs.reconcile, temp_documents.sweep); none is called. There is no model call and no network call. There is no sandbox exec, because an exec starts a stopped container: services are counted as registered and the line says their liveness was not probed. The container line says "started earlier (not probed now)", because the handle outlives a stopped container. The lab host is not contacted; the line says so. The lab inventory and the run registry are opened only when their database file exists, because opening one creates it. A test walks the module's syntax tree and fails if it names any of these writers or a file-moving call.
  • A damaged file is left as it is (reviews r1–r3). The profile reader (and, until its removal, the lesson playbook's), and the sandbox supervisors, set a corrupt file aside and carry on empty, so a check that read through them renamed the file and then reported "0 lessons". Every JSON file the module needs is looked at first: the profile (a dict), the document index (a list; a zero-byte index is what its store reads as empty), the owner-rules file (asked through core.owner_rules.damaged, the rules store's own read-only check, which never sets a file aside; until 2026-11-05 the replay loop's rule ledger, a list, stood in its place), and the two sandbox registries (dicts). A damaged one, or one holding the wrong JSON type, is written … file DAMAGED (reason), is a problem, and its reader is not called. The sandbox registries sit in a directory the sandbox can write, so each is read once, as its supervisor reads it: the last path component is never followed, the read is bounded at 8 MiB, undecodable bytes are replaced. The rows are counted from that one read and the supervisor's loader is never called, so there is no second read to race with; a registry that is a link is DAMAGED and its target is not read. Other reads go through each store's own reader, which may open its database as any read does.
  • A missing store file is a problem (review r3). The turn that asks for a health check has already read the profile to build its prompt, and that read sets a torn file aside, so the check usually finds nothing damaged. What it can still see is that the file is gone: the profile and the document index each create their file when the store starts and are written atomically. An absent profile was set aside by a reader or removed; an absent document index was removed (no reader sets it aside). It is written … file MISSING and its reader is not called. The file stays absent until the store's next save or a restart.
  • No file name and no row text reaches the report (reviews r2, r3). The first fix listed files a reader had set aside by name. A file in a sandbox-writable directory can be named anything: a name with newlines put a forged Problems found: none and an instruction on the third line, and a service called fix-corrupt-db raised a false alarm on every check. The listing was removed, and the backup folder's tag is no longer printed. What leaves the module is its own words, numbers, Python type names, and a project status when it is a plain word (anything else prints as ?).
  • What it cannot know. That a store lost data before this call and has saved since. Once the store writes again, its file is back, small and valid, and nothing durable records the reset. The agent log has the line from when it happened.
  • What counts as a problem. A state that is wrong whatever the workload: any store that did not load (in production a store is missing only after a boot failure), a reader that raised or answered with something that is not a number, a registry file that did not open, a damaged or missing store file, no embedding model, an unreadable scheduled-task store, a labs host with an empty key file, a sandbox that was cut off from the network, a sandbox that could not be confined to Tor while Tor-only mode is on, no store backup or one more than twice its 22-hour schedule old, Tor-only mode without its egress guard, a stopped idle scheduler, a missing memory bus, and the Docker, internet and Tor failures. Sizes and loads are reported and never judged. With --no-memory the memory line says "switched off" and adds only the fact ledger, which is wired whatever the flag says; the project store and the scheduler are judged as usual.
  • Not checked is not fine, and not a problem. A third list, Could not be checked, holds a part that does not answer in 4 seconds (a store may be busy), a slow Tor circuit, and a model node whose last known calls failed. The parts of a line read before a slow one are kept. The slow reader's thread cannot be stopped; it ends when its store answers.
  • A model node is never judged here. No node is tested live, and the circuit breaker is a memory of failures, not a reading of health: only a real call closes it (a keepalive success is not recorded; a keepalive miss usually is). Four reviews tried four rules on that state and each was wrong somewhere. Flagging open only missed a node still down after one availability check. Flagging open and half_open made a node that failed once three days ago a standing problem. Flagging neither left a node that was down right now out of the problems. Flagging by the age of the last failure called a node that had recovered "failing now" for up to three minutes. So the last known state is said, with its age, on the third line under Could not be checked, and the reader judges. A node that is down now appears there, not under problems. Testing a node live would be a separate check; it was offered as step 2 and not taken.
  • Every part answers for itself. A part that cannot be read is written UNREADABLE (reason) on its line and is a problem; the other parts still report. The five store sections are read side by side in threads.
  • Counts are checked by type. A count must be an int. A test double answers every call, and a mock printed as a number is a report nobody can read. A mocked sandbox manager is "not attached": the supervisors are built only over a real DockerSandbox.
  • The old Agent Internals line is kept word for word. Its graph count now counts current facts (valid_until IS NULL); it used to include every expired edge and so disagreed with count_edges().
  • Model-facing text. The HEALTH/DIAGNOSTICS rule told the model to report "ALL lines". It now asks for the Problems found line first and in full, then each section in a line of the model's own, or only the part that was asked about. Two neighbours said system_utility is "the MACHINE, not you" (the SELF SURFACE rule and the introspect description); both now say the check_health action is the health check of the machine and of the stores and services the agent runs on, to be called only for a health check or diagnostics, and not for how the agent is or how its learning is doing. The restriction names the action, because system_utility is also the weather and location tool. The HEALTH/DIAGNOSTICS rule lists the phrasings that mean a health check, including "is everything working?". The system_utility description is unchanged.
  • Not in this step (the operator chose step 1 only): live probes of the lab host and Whisper, stuck tasks, store sizes, log error counts, mirror drift, rule integrity, Slack bot liveness, TLS expiry, and the last run of each idle job.
