core / project_safety.py

Budget enforcement, human-gate postconditions, contradiction detection, and chat→project promotion heuristics.

No confirmations 2026-11-12 §4UJ

Operator: "i want all confirmations, everywhere to be removed. i don't wanna be asked for anything. that's why everything is sandboxed" (clarifying questions stay). This supersedes the preview/confirm_token, human-gate and gate-word sections further down.

  • manage_projects release / unrelease / delete run in the call; confirm_token is accepted and ignored. _lifecycle_confirmation only refuses a non-user turn (background, scheduled, probe — a probe may still act on its own probe-created project) and a request that read outside content.
  • project_safety.HUMAN_GATES_ENABLED = False: a HUMAN_GATE: postcondition never parks a task; is_human_gate_text keeps it out of text grading.
  • Gate words ("approve", "publish", "send", "confirm") no longer hold or park a task; the classifier answers only coding / research.
  • A constraint override (override={"constraints": "<why>"}) goes through in the owner's own turn and is recorded (constraint_override event + ledger line); an unattended turn still cannot go over a constraint.
  • Kept: an explicit kind: owner task (it needs something only the owner has), and the unattended verify / model-experiment holds (they are not approvals).

Budget knobs

Stored in the project's metadata dict (proj_metadata as check_budget receives it; persisted as the projects store's metadata_json column):

  • steps_cap / steps_used
  • runtime_cap_seconds / runtime_used_seconds
  • tool_call_cap / tool_call_used

Promotion thresholds

MIN_TURNS_FOR_SUGGESTION = 8; MIN_WRITES_FOR_SUGGESTION = 3; MIN_PLAN_NODES_FOR_SUGGESTION = 3. Promotion is suggested when (at least 8 user turns and at least 3 sandbox writes) or at least 3 plan nodes, and the conversation isn't already in a project (nor a turn that manages projects).

Human gate

Any postcondition prefixed with HUMAN_GATE: forces NEEDS_USER regardless of tool output. Used for irreversible actions (delete production data, send-to-customer, etc.). enforce_human_gate(task) returns the gate reason (the text after the prefix, or "human approval required" when empty); callers check it BEFORE marking DONE — a non-None result means the task transitions to NEEDS_USER instead.

Interactive close path enforced too (2026-07-20). The advancer already routed gated tasks to NEEDS_USER, but closing a gated task DONE interactively used to grade the gate text against the result summary and cascade a spurious FAILED up the tree (the result never echoes the gate). TaskTree.update_status / ProjectPlan.update_status (core.planning) now call enforce_human_gate on every DONE close and park the task at NEEDS_USER instead. Approval is a signal, never text similarity. Since §4SU Phase 0 (2026-11-02), approval is explicit only: human_approved=True. task_update passes it only in the owner's own turn, for a task that an earlier request parked (the human_gate_parked / human_gate_triggered event carries its request id req), and only when the owner's own message names it: an approval word plus the task's id (never its title: review r4, the model could rename it), holding nothing back (operator 11-02 "name it", after reviews r1–r3: "status?", "8080" and "go ahead, tell me the weather" each approved a deploy gate). A plain yes never approves; one message releases only the gates it names. See tools.projects. A postconditions rewrite keeps every HUMAN_GATE: entry. Deleting a task checks every open gated task in its subtree against the same release (review r2: deleting the parent removed the gate). The parent roll-up parks a gated parent NEEDS_USER instead of closing it and logs human_gate_triggered for it (reviews r1 and r2). The web console's PATCH (the owner's own click) passes it too. A second close in the same request, or any close from a scheduled, sub-agent or probe request, stays NEEDS_USER (audit A: two identical closes in one turn approved the gate). A close of a task already DONE proceeds to the normal postcondition gate. HUMAN_GATE: postconditions are excluded from the token-overlap check entirely — a gate can be neither satisfied nor failed by result text. Covered by tests/test_planning_gate_fixes.py.
