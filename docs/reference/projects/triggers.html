core / triggers.py — repeat-failure guard helpers

Decides when a tool call is the same failing action against the same target, so the turn loop can stop re-running a known failure.

Removed in §4PT (2026-10-17). This file used to hold a trigger bus (TriggerBus, TriggerEvent and the event types LoopDetected, ResourceExhausted, ExecutionAnomaly with their loop_event / resource_event / anomaly_event factories), a per-tool runtime budget (ToolRuntimeBudget), a streak counter (RepetitionCounter) and a ReplanBridge that asked an active project task to re-plan. All of it was removed at the operator's request. Across the whole log history the bridge made 2 re-plan attempts, both rejected, and 0 revisions; every host-resource event was log-only. See metacognition §4PT.

What is here now

SymbolRole
RecentFailureGuard(window=24, repeat_threshold=2)The pre-flight guard. A short rolling memory of recently FAILED calls, keyed by (tool, target, op) with the error cut to an 80-character lowercased prefix. Before a call is dispatched, would_repeat(tool, target, op) returns the earlier error if the same action already failed the same way at least repeat_threshold times; the turn loop then skips the call and hands the model that error. record() stores a failure, note_world_changed() forgets everything after a successful state-changing call, and reset() clears it at the start of each request.
primary_target_from_args(args)The value of the first known "target" argument (path, file_path, file, filename, url, selector, query, target), lowercased and trimmed, or "". Shared with the in-run no-progress loop-breaker in core/agent.py, so both agree on "the same target".
guard_key_target(primary_target, call_hash)The target half of a guard key. Uses the primary target when there is one; otherwise an args# SHA-1 of the whole call, so a retry with any changed argument counts as a different action.
looks_mutating_command(command)True when a shell command probably changes the world (kill, rm/mv/cp, sed -i, a service-manager start/stop, a plain redirect into a file) rather than just looking. A successful execute call that matches clears the guard. Quoted text is ignored, except the payload of sh -c '…'; kill -0 probes do not count.

The guard is switched by --enable-preflight-guard / --no-enable-preflight-guard (on by default) and does not depend on --enable-metacog. Full behaviour and history: Metacognition, section "Pre-flight repeat-failure guard". Tests: tests/test_preflight_guard.py.

History

A resource event is log-only 2026-09-16 §4HN

(The bridge and resource events were removed §4PT, 2026-10-17.) ReplanBridge._on_event used to treat every warning/critical event alike, so a host signal ("CPU 96%") could reset the active project task to PENDING with the host's CPU load as its failure reason. Measured over the log's lifetime then: 1,051 resource warnings, zero revisions from them, two revision attempts in total, both from loop triggers. From §4HN a resource event of any severity was recorded as noop:resource_log_only and never counted as a replan attempt.

2026-07-27 audit fixes

(Both pieces removed §4PT, 2026-10-17.)

  • LoopDetected fired on benign work and burned the active task's revision budget (MED, closed). RepetitionCounter.observe(fname) was keyed on the tool NAME alone and counted successes, so three reads of different files tripped it, and the ReplanBridge then used up one of the task's revisions. Observation was re-keyed on tool + args-hash.
  • ReplanBridge._revisions was unbounded (LOW, closed). It became a deque(maxlen=256).
