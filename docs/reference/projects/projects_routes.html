api / projects_routes.py

REST surface over the ProjectStore. Used by the Slack project commands and the web UI's Projects tab.

All endpoints require X-Ghost-Key.

Project endpoints

Method · PathBehaviour
GET /api/projectsList, optionally filtered by status.
POST /api/projects201 Create. Required: title; optional: kind (default GENERAL), goal, metadata.
GET /api/projects/{pid}Fetch.
PATCH /api/projects/{pid}Update title, goal, kind, status, metadata. metadata is shallow-merged into the existing blob (2026-07-20 — see below).
DELETE /api/projects/{pid}Soft delete (status=ARCHIVED). ?hard=true for cascade hard delete. Stops the project's services first (§4LZ; a hard delete also purges their state dirs); a hard delete also unlinks the project from the knowledge graph. Answers 204 with an empty body.
POST /api/projects/{pid}/switch?session_id=…Set the focus of the conversation named by session_id (query or JSON body; required, else 400). No other conversation changes, and the shared context is not touched (§4SX B0). Returns the project briefing.
POST /api/projects/{pid}/resume?session_id=…Same as switch, plus a project_resumed event.
POST /api/projects/{pid}/advanceRun one task-advancement cycle via advance_once() with a project-pinned tool runner; 503 when no runner can be built (2026-07-20 — see below).
GET /api/projects/{pid}/eventsList project events. Query: limit, type.

Task endpoints

Method · PathBehaviour
GET /api/projects/{pid}/tasksList with optional status filter.
POST /api/projects/{pid}/tasks201 Create. Body: description, parent_id, dependency_type=ALL, alternatives, postconditions.
PATCH /api/projects/{pid}/tasks/{tid}Update. Status transitions go through ProjectPlan.update_status() so postconditions / parent propagation fire.
DELETE /api/projects/{pid}/tasks/{tid}Cascade-delete descendants.

§4SU Phase 0 (2026-11-02)

  • PATCH /{pid}/tasks/{tid} with status=DONE is the owner's own click, so it passes human_approved=True: it closes a HUMAN_GATE: task directly. The agent's own closes need a later owner request (see tools.projects).
  • POST /{pid}/advance answers 409 while an unattended autopilot step is running on the project, the same rule as the tool's autoadvance (§4PG R1-1). It used to build in the same workspace beside it.

§4SU Phase 1 (2026-11-02)

  • The task id is canonicalised (a mixed-case id was a silent 200 no-op).
  • The fields other than status land before the status, so the close is judged on the task as the owner just edited it.
  • A DONE click runs check_close with actor="owner". It always closes (operator 11-02: "close, record why"); each gate it went over is logged as a close_override event (actor: owner) and an OVERRIDE <gate> on task <id> (by the owner, web console) ledger line. An overridden postcondition gate is not demoted to FAILED after. The check gets the task's and the project's constraints, so a constraints-evidence gate is recorded too; a re-click (or a result edit) on a task already DONE records nothing again and is never demoted to FAILED by a postcondition. The status write and the override records run in one worker thread, so a cancel cannot separate them (r3). The response carries not_closed [{task_id, status, why}] for any parent the click parked or the roll-up refused.

§4SU Phase 3 (2026-11-02)

  • The owner's DONE click over a constraint hold is recognised by wait_code == "rollup_constraints", not by the summary text, and the recorded reason comes from wait_why (core.task_wait). Task rows carry wait_on / wait_code / wait_why; the status names are unchanged.

§4SU Phase 2 (2026-11-02)

  • POST /{pid}/tasks takes kind and PATCH /{pid}/tasks/{tid} takes kind (see core.task_kind); an unknown kind is a 4xx.

Route hardening (2026-07-20)

  • /advance builds a real, project-pinned tool runner — or refuses. The route used to call advance_once with no runner, i.e. the degraded classify-only path, which marked a research leaf DONE having done nothing — theatrical completion on a network-reachable authed route. It now builds the SAME registry-backed runner the manage_projects autoadvance action uses: tools constructed from pinned_project_context (file writes resolve to projects/<pid>/), the run wrapped in pinned_event_project (workspace events stamp the advanced project, not whatever the chat side has active), plus the LLM classifier / code generator and the real coding executor. When no runner can be built the route returns 503 instead of failing open. The Slack advance command's async path (interface/slack_project_commands.py · advance_async) got the identical treatment — same pinned runner and pinned_event_project wrap, refusing with a tool runner unavailable warning reply (a chat surface has no status code). Covered by tests/test_slack_project_commands.py.
  • (§4SX B0: switch/resume now write the named session's focus row; GET /api/projects?session_id=… returns that session's current, and without a session id current is null. Delete clears every row on the project.) switch / resume / delete route through _set_current. A raw current_project_id attribute write skipped the conversation sentinel + workspace-model pointer + scratchpad snapshot/hydrate, so the next chat turn's reconcile silently undid the switch — and a delete left the sentinel naming the dead id, so reconcile reactivated the deleted project and the sandbox recreated projects/<deleted-id>/. All three now go through the projects-tool setter.
  • Canonical pids. Every pid-bearing route canonicalizes the path pid at entry (_canon_id: strip + lowercase — store ids are canonical); a case-mangled pid used to 404 on ownership checks and diverge the workspace path.
  • PATCH metadata merges, never replaces. ProjectStore.update_project is merge-by-default since 2026-07-20 inside one BEGIN IMMEDIATE txn — the blob carries system state (design ledger, config, step counters) that a whole-dict replace silently destroyed, so the documented budget-raise {"metadata": {"steps_cap": 100}} no longer wipes the rest. The store's metadata_replace=True escape hatch is for deliberate callers only and is not exposed over REST (ProjectUpdate has no such field).
  • Blocking store work is off-loop. PATCH /{pid}, DELETE /{pid}, and the task-status PATCH run their store calls via asyncio.to_thread: a DONE transition fires the workspace-cleanup sweep (a synchronous filesystem walk) from the store hook, and a hard delete rmtree's the workspace — neither may block the process-wide event loop. /events also clamps its limit (1…1000; a negative limit means "no limit" in SQLite).

Covered by tests/test_projects_api.py.
