core / project_advancer.py

Single autoadvance tick for long-running projects. Classifies the next task, runs one constrained step, and bookkeeps budget / runtime / contradictions.

API

Pacing — single turn vs. bounded batch (2026-06-20)

A user saying "proceed" / "next" is handled as a full agent turn (the agent writes files, runs, verifies — highest quality for one task). The batch case — "do the next 3 tasks", "proceed with all remaining tasks", "finish the project" — instead routes (via manage_projects action=autoadvance count=<N|"all">) to advance_many, a bounded loop of advance_once ticks. classify_advance_intent maps the phrasing to a count (ambiguous → 1, the safe default).

Why a loop instead of one big turn: each tick claims one leaf, runs one constrained step, and checkpoints status+result to the store, so per-tick context stays bounded no matter how many tasks run — the antidote to one chat turn grinding the whole tree and flooding the context window. The loop stops at the FIRST of: project_done · count_reached · needs_user (a human-gate task — only with stop_on_fail=True; the owner's batch goes past it, §4SR) · budget_or_inactive (step budget exhausted) · failed (a task FAILED, when stop_on_fail) · hard_cap (ADVANCE_ALL_HARD_CAP=40, a backstop for an uncapped project).

Coding executor (2026-06-20). A tick's coding path is the real build_coding_task: spec → write files → verify, finalized by _finalize_coding (success registers the produced files as deliverables + appends a ledger note + marks DONE; a failed build marks FAILED, which stops the batch loop for the user). This replaced the original single-command path that produced theatrical completion — a leaf marked DONE having written nothing (observed live: "create hello.txt" ran a web_search). The single-command default_code_generator remains only as a fallback when the executor is unavailable/crashes.

Classification (hardened 2026-06-20 after a live failure). In a batch over a browser-OS project, 9 of 10 build leaves ("File Explorer app", "Snake game") were classified as research and web-searched, marked DONE with no code — the small LLM classifier reliably mislabels build work as research. Fixes:

  • CODING projects bypass the LLM classifier entirely and use the deterministic keyword classifier with default="coding" — a leaf is coding work unless it carries an explicit research/needs_user verb. Only GENERAL projects consult the LLM.
  • Kind is inferred at create time (tools.projects._infer_kind): a build-flavoured title/goal (build / app / website / game / OS / single-file / …) creates a CODING project, so its leaves are treated as coding instead of defaulting to research.
  • No theatrical research. A coding leaf with no build path (no executor handled it, no command generated) now FAILS (stopping the batch loop) instead of being web-searched and marked DONE. And research briefs are no longer registered as deliverables in CODING projects (they were polluting cleanup's "kept deliverables").
  • Cumulative builds. _gather_project_files feeds the project's current workspace into the executor (existing_files) so a leaf EXTENDS prior files (single-file apps) instead of regenerating and overwriting them. At most 12 files are read, in walk order; since §4QA-d (2026-10-19) the files the task description names (path or basename) are read outside that cap (up to 6) and come first. Before, a 30-file project left a named target out. A named file past those 6 competes for a normal slot. The named files are chosen before anything is read (r21): every candidate is listed, exact-path matches go first, then basename matches, up to 6. Counting slots during the walk let a root-level package.json plus basename hits take the slot of the named zapp/package.json. Vendored directories (coding_loop._SNAPSHOT_SKIP_DIRS: node_modules, .venv, .git, __pycache__, .pytest_cache) are skipped. Other dot-directories, such as .github, stay readable. With a basename named, the walk no longer stops at 12, so node_modules/*/package.json could otherwise fill the named slots. An idle batch with open-but-held tasks (behind a BLOCKED/PAUSED dependency) stops with open_but_waiting, not project_done.

Covered by tests/test_advance_classification_fixes.py, tests/test_advance_pacing.py, and tests/test_coding_executor.py.

Strong code-file signal beats a research verb (2026-06-22). A residual hole in the keyword classifier: classify_task checks research keywords BEFORE coding ones, so a build leaf whose description also contained a research verb was still mis-routed. Observed live (project 33e23d50): the leaf "analyze training logs (analyze_results.py) — produce metrics summary… saved as results/report.md" hit analyze (research) and was web_searched into a phantom DONE, never building the script — the model later flagged it as "a phantom task… auto-researched but not actually built." Fix: when a description names a concrete source/artifact file (_STRONG_CODE_FILE_RE: .py .js .html .md .json …) AND carries a build verb (produce · build · create · write · generate · save · …), classify it coding ahead of the research check. needs_user still wins (checked first), so "publish report.md" routes to the human, and a file mentioned without a build verb ("investigate what config.yaml controls") stays research. Covered by test_classify_strong_code_file_beats_research_verb in tests/test_project_advancer.py.

Classification keywords

  • needs_user: decide · approve · choose · pick one · sign off · confirm · authorize · publish · announce · send · delete production · drop database — as whole words only (§4SR).
  • coding: implement · build · fix · debug · deploy.
  • research (default): research · investigate · compare · analyze.

Tick flow

  1. Load project plan; find next READY/PENDING leaf.
  2. Classify task type.
  3. Mark IN_PROGRESS.
  4. If needs_user: flip to NEEDS_USER, log event, return.
  5. Pick tool: coding → execute with code from the injected code_generator (or, if none, degrade to web_search — never the old inert "# Autoadvance stub" comment that marked the task DONE having run nothing); research → web_search.
  6. Run tool through the injected runner.
  7. Store result as a project artifact.
  8. Stricter completion: if the tool ran but returned an error or no usable output (_looks_like_failure — empty, or a first line starting ERROR: / Traceback), flip the task to FAILED and log autoadvance_failed instead of marking it DONE. The old path recorded DONE on any output, so a failed web_search still counted as progress (theatrical completion). The no-runner classify-only path used to still mark DONE — closed 2026-07-20 (see the fail-closed section below). (2026-06-22) _looks_like_failure now strips leading quote/paren/bracket punctuation before the prefix test: a transport failure surfaced as a stringified exception tuple ('error sending request for url …', '…'), whose leading (' hid the error marker, so an erroring search still marked its task DONE (observed live on project 33e23d50). Covered by test_looks_like_failure in tests/test_project_advancer.py.
  9. Check human-gate postconditions (project_safety) → flip to NEEDS_USER if any fire.
  10. Auto-research persistence (research tasks): when a research-classified task ran a real web_search and got usable output, that output is turned into a durable, summarised brief in the project workspace (research/<slug>.md) and indexed via project_research — no second search. The synthesised summary becomes the task's result_summary and the brief path is added to the step event + result. Best-effort: never breaks the tick.
  11. Detect contradictions with DONE siblings (detect_contradiction) and record each as a contradiction_detected project event. (Until §4NN it was also written to the separate contradiction log; that ledger was removed.)
  12. Mark DONE; increment steps_used; record runtime + tool_calls; stamp last_autoadvance_ts (drives round-robin project selection — see phase 2.95).

Per-task cost stamping (2026-07-18)

The tasks.actual_cost column existed since the schema's birth with no writer and no reader. Both finalize paths (coding — success AND failure — and the tool/research path) now stamp it with the tick's wall-clock seconds, alongside the existing project-level record_runtime. Read side: TaskTree.generate_retrospective() sums it into total_actual_cost_s, shown as "measured effort N min" in the terminal-state RETROSPECTIVE briefing section (core.prompts). A failed build is stamped too — the cost total reflects effort spent, not just effort that succeeded. Covered by tests/test_project_readside_plumbing.py.

Budget enforcement

_get_budget() reads steps_cap / steps_used from project metadata; _increment_budget() bumps after each tick. Checked via check_budget() across steps, runtime, and tool_calls.

AdvanceResult

AdvanceResult(ok: bool, task_id: str, classification: str, summary: str, artifact_id: Optional[str])

Async; tool_runner, llm_classifier, and code_generator are optional callbacks so the advancer can be tested without a real agent.

Autonomous idle advancement (phase 2.95)

advance_once was historically only reachable via the manage_projects tool or the HTTP /advance route — no idle phase ever called it, so the "self-advancing research loop" only advanced when a human or the model explicitly poked it. Under --autoadvance-idle, the idle scheduler's phase 2.95 (job project autoadvance (autopilot projects only)) picks one ACTIVE project (since §4LQ/§4MQ only one with metadata.autopilot on, via idle_candidates, stepped through advance_unattended) and runs a single tick during the 15–60 min idle window (30-min cooldown), building a registry-backed tool_runner from a pinned_project_context (a proxy that pins current_project_id to the target project — idle ticks carry no conversation, so the process-global id is parked and unpinned file writes landed at the sandbox ROOT, invisible to interactive sessions on the project; observed live 2026-07-08 with TinyAI's model/train/evaluate files), an LLM code_generator so coding tasks produce and run real code, and an LLM llm_classifier so task routing no longer depends on the brittle keyword buckets (a task like "design the schema" matches no keyword and used to default to research/web_search). Strictly bounded — one project, one tick per cooldown, on the same hard per-project budgets + human gates — and off by default in code (the live launcher passes --autoadvance-idle; autopilot is per-project opt-in).

Round-robin fairness. The project picked each tick is the one advanced least recently (by metadata.last_autoadvance_ts; never-advanced projects sort first). Previously the phase took actives[0], but list_projects orders by updated_at DESC and advancing a project bumps its updated_at, so the same project re-selected itself every tick and all other ACTIVE projects starved. This is what turns the dormant loop into genuine, fair background autonomy. Covered by tests/test_project_advancer.py and tests/test_project_mgmt_fixes.py.

Workspace pinning (2026-07-08): both autoadvance tool-runner construction sites — the idle phase-2.95 tick and the interactive manage_projects autoadvance batch — now build their tools via pinned_project_context(context, project_id), so file writes always resolve to projects/<id>/ regardless of what the racy process-global current_project_id says mid-run. Covered by tests/test_autoadvance_project_scope.py. Event-stamp pinning (2026-07-09): the sandbox pin covers only context.current_project_id; workspace events (command outcomes etc.) stamp from workspace_model.current_project_id, which an idle tick never set — so autoadvance outcomes were stamped with the LAST chat turn's project. Both sites now also wrap their runs in pinned_event_project(project_id) (a task-local ContextVar override in workspace.model). Covered by tests/test_workspace_event_stamping.py.

Fail-closed verify + no-runner refusal + fairness/runtime stamping (2026-07-20)

  • Verify is FAIL-CLOSED. New classify_verify_result(output) → "pass" | "fail" | "inconclusive": a verify command PASSES only on an explicit EXIT CODE: 0 that is neither execute's grep-no-match rewrite (EXIT CODE: 0 … NOT FOUND — for a verify like grep -q marker file that means the required marker is ABSENT) nor sandbox-egress-guard prose (SANDBOX EGRESS BLOCKED describes a command that never ran), and any output carrying no EXIT CODE: at all is also inconclusive. All three success-shaped outputs used to read as a pass under _looks_like_failure's interactive semantics and let the executor's _run_verify mark a task DONE on nothing. _verify_fail_closed_runner wraps the runner handed to the coding executor and rewrites an inconclusive execute result into an explicit ERROR (original output preserved below the marker, its EXIT CODE: banner neutralized so it can't smuggle a 0 past the prefix test) — the task retries with the real reason and ends FAILED, never DONE, on a verify that proved nothing.
  • No-runner ticks never DONE an execution-needing leaf. advance_once with no tool_runner (and nothing generated in-process) used to mark the leaf DONE with "(no tool runner)" — theatrical completion, observed via the runner-less HTTP /advance route. It now releases the claim (task back to PENDING), logs autoadvance_skipped, and returns classification blocked without charging a step; a properly wired tick can then take the leaf. (The introspective self-analysis path still completes in-process — it needs no runner.) The /advance route itself now builds a real project-pinned runner or refuses with 503.
  • Stale IN_PROGRESS claims are reaped at boot. advance_once claims a leaf by writing it IN_PROGRESS (atomically, under the per-project lock) before the multi-minute build/LLM awaits — and next_ready_leaf only considers PENDING/READY, so a crash or deploy-kill (plain SIGTERM, the standard workflow) between claim and completion left the leaf ineligible forever: the project sat ACTIVE while every later tick returned idle ("no READY/PENDING leaf"). ProjectStore.reset_orphaned_in_progress() (memory.projects), wired at boot in main.py before the advancer starts, resets IN_PROGRESS rows whose updated_at is older than 15 min back to READY — eligible again on the next tick — without yanking genuinely in-flight work in a live process. (The in-tick counterpart: a no-runner tick releases its own claim back to PENDING, previous bullet.)
  • Every tick stamps last_autoadvance_ts. _increment_budget stamps it on ticks that advanced a task, but the blocked (budget-exhausted / secondary-rails) and idle (no ready leaf) exits returned unstamped — so a permanently-blocked project stayed the min(last_autoadvance_ts) round-robin pick forever and starved every other ACTIVE project of idle ticks. _stamp_autoadvanced now rotates the project to the back of the queue on every tick that ran, without charging a step; the repeated budget_exhausted event is deduped against the newest one so re-picks don't flood the event log (and the digest built from it).
  • record_runtime fires on failed ticks too. A raising tool runner, a failure-shaped tool output, and a failed coding build all record their wall-clock seconds + tool_calls now — failed ticks burn runtime too, and the runtime rail (check_budget) must see them or a project can loop failures far past its runtime cap.

Covered by tests/test_advancer_fail_closed.py; the boot reaper by tests/test_projects_store.py.

Telling the user (autonomous-progress digest)

Background advancement updates the project event log (autoadvance_step, autoadvance_needs_user, human_gate_triggered) but on its own only logs to the operator stream — the chatting user was never told. core/project_digest.py closes that loop: on the next chat turn, core.agent.handle_chat builds a concise "while you were away" header from the events since the user last saw a digest and prepends it to the reply, flagging the tasks that now need their input. It is watermark-gated on the monotonic project-event id (so each batch shows exactly once; the first run baselines silently with no historical backlog), fail-safe (a digest error never breaks a turn), and triggered by background progress from any source — the idle phase, the tool, or the HTTP route. Covered by tests/test_project_digest.py.

Inter-project dependency deadlock + autoadvance mislabel (bug-hunt 2026-07-26b)

The inter-project dependency gate blocked a dependent project's autoadvance FOREVER when its dependency was deleted, archived, or failed — states that can never become DONE, so the block never cleared (silently; the operator saw the reason only on a manual autoadvance). Now a terminal-unsatisfiable dependency (missing / ARCHIVED / FAILED) is treated as cleared with a loud warning — the inter-project mirror of the intra-project rule that treats an unknown dep id as satisfied "so a bad reference can't deadlock the whole plan." Recoverable states (PAUSED / NEEDS_USER / BLOCKED) still legitimately block. Separately: an autoadvance tick logged autoadvance_step + work_log outcome="completed" even when update_status(DONE) silently DEMOTED the leaf to FAILED via a postcondition — corrupting the operator's "what did I do last night" ledger; the tick now reads the resulting status and logs autoadvance_step_failed / had_failures. Tests: tests/test_bughunt_fixes_2026_07_26b.py::TestInterProjectDepGate.

project_failed stop reason — no "done" over a FAILED ledger (2026-08-01)

advance_many's blocked exit mapped a FAILED project through _final_reason("project_done") — which only inspects this batch's advanced list. A fresh batch invoked on an already-FAILED project therefore reported project_done ("All tasks are complete — the project is done"), and the agent relayed the completion verbatim while the store said FAILED (Mini AI incident, request b7e516b9). Both exits are now honest: the blocked exit returns project_failed when the project status is FAILED and this batch advanced no failing task, and the idle exit (no ready leaf) scans the LEDGER for FAILED tasks before claiming project_done. The tool layer adds a do-not-report-completion blurb, marks the reason as stopped-early, and attaches failed_tasks (id/description/failure_reason) from the store so the model has something actionable even when the batch itself is empty. Tests: tests/test_project_ledger_integrity_fixes.py.

Constraints go through the shared normaliser 2026-08-11

Project metadata is model-written JSON, so {"constraints": "no external APIs"} is a legal shape — and iterating it raw yields 17 single-character “constraints” fed straight to the constraint gate. ProjectStore._constraint_list exists precisely because this shredding destroyed a constraint record once before; the advancer kept its own copy of the logic and so kept the bug. Three sibling call sites in tools/projects.py were already using the helper.

A crash does not downgrade to a weaker closer 2026-08-11

An exception inside coding_executor left cres = None and fell through to the generic single-shell-command path — which marks the leaf DONE on any output that is not ERROR:-prefixed and not a non-zero exit, with the verify gate, smoke gate, files-written check and constraint gate all bypassed. echo-shaped output closed a build task.

This was the third member of one family fixed the same day, alongside silently-dropped edits and the truncated-snapshot overwrite: a task reaching DONE on evidence that no work happened. A transient exception is a reason to stop, not to accept a lower standard of proof — the leaf stays open and the next tick retries it under the full gate set.

Only what was asked 2026-10-05 §4LP

advance_once(…, owner_requested=False), the idle loop, never claims a task the verifier filed on its own (_is_unrequested_task, through ProjectPlan.next_ready_leaf(skip=…)). The manage_projects autoadvance action and the API route pass owner_requested=True.

Unattended closes need evidence (operator: "go with your recommendations"). _unattended_close decides how a leaf closes when nobody asked for the run:

  • A task whose text mentions a check anywhere — verify/verification, test/testing/re-test, check, validate/validation, confirm, ensure, "make sure", QA, sanity, smoke-test, e2e (whole words: "Checkout", "Testimonials", "Latest", "Check-in" are not) — goes to NEEDS_USER, not DONE. Writing a file does not verify anything ("Verify full pipeline" had closed on "wrote index.html"). Four review rounds narrowed and widened a leading-verb rule and each round found real checks closed unattended or builds held; the rule now errs toward holding, because the owner's own run takes a held task back (below) and a wrong hold costs one look. The description is read up to 400 characters.
  • A research task whose web_search result did not persist as research also goes to NEEDS_USER.

Both the tool path and the coding path (_finalize_coding) use the rule. A held task is logged as autoadvance_needs_user with its reason, so the digest lists it under "need your input" and not as a failure. An owner-run advance closes DONE as before, and may take back what an unattended run held (result ending "not closed unattended"): for the claim, held tasks count as PENDING in memory only, so they join the normal ready-leaf pick — dependencies, leaf-only, no paused parent — in task order. Only the task actually claimed leaves NEEDS_USER (claiming it rolls the project from NEEDS_USER back to ACTIVE); the rest stay held, so the idle loop never rebuilds them, and a gate that stops the step changes nothing. A batch that stops with tasks waiting on the owner reports needs_user, never project_done, and the tool's reply lists them (needs_user_tasks).

idle_candidates(store) is the idle loop's project list: ACTIVE projects with metadata.autopilot only.

Multi-day work: bounded unattended steps 2026-10-08 §4MQ

A request that needs hours or days runs as a project on autopilot, one short step at a time. The idle loop's only entry is advance_unattended(context, project_id), which wraps advance_once(…, owner_requested=False) in its gates. It runs only on a project whose autopilot is on, so a paused project is never stepped by a scheduled task or sub-agent either. It runs one step per project at a time: a second concurrent step is refused, not charged. Every gate that stops work turns autopilot off, records why in metadata.autopilot_paused and a autopilot_paused event, and sends you one notification (severity notify: a Slack DM outside quiet hours) — only on the on→off transition, never again while it stays paused. The pause also appears in the next chat's "while you were away" digest. Only your own turn turns it back on.

  • Progress gate. A step moved forward only when the task it worked on is now DONE. A written file, a summary or a held task is not progress. After NO_PROGRESS_PAUSE_AT (3) steps in a row with no progress, autopilot pauses. A tick that claimed no task is not scored. A task held for you (NEEDS_USER) is neither progress nor failure: the hold already told you, and it stops the project.
  • Check-ins. After checkpoint_every steps that moved forward (default 10; 0 turns check-ins off), autopilot pauses so you can look before more runs.
  • Wall cap per step. A step that runs past UNATTENDED_STEP_TIMEOUT_S (45 min) is cancelled, and so is a step that raises. Only its own claimed task goes back to READY (advance_once(claim_sink=…) reports the claim), and the step is charged and counted as no progress. A step that finished during the cancel grace is scored as it ended, not charged twice. Cancelling does not stop a sandbox command already running; that command ends on its own timeout. A step that returns with its leaf still claimed has that leaf put back to READY too (§4MR). A crashed coding executor now reopens its task (it used to stay IN_PROGRESS, so no tick could retry it and the gate never paused).
  • A step lost to a restart is charged. metadata.step_in_flight carries the process's boot id. It is set before a step and cleared after it, but only by the step that set it. If a tick finds a marker from another boot, that process died mid-step: the step is charged and counted as no progress, and the boot reaper has already put its task back to READY. A marker from this boot means a step is still running. Your resume does not clear it (§4MR: clearing it let a second step run beside the first).
  • Unattended runtime allowance. Unattended steps add their wall time to unattended_runtime_seconds. Your own runs do not, and every resume resets it. At unattended_runtime_cap_seconds (set by action=budget runtime_cap_hours; default DEFAULT_UNATTENDED_RUNTIME_CAP_S, 6 h) autopilot pauses. The project's lifetime runtime_cap_seconds (an older knob that action=budget does not set, and no live project carries) is separate and would also limit your own runs.
  • Step budget. An exhausted steps_cap (it counts every advancer step, your batches too), or the lifetime runtime/tool-call caps, is a pause like the others: autopilot off, you are told once (§4MR — it used to block every tick silently with autopilot left on).

advance_many, the batch behind "do the next N" / "finish it":

  • A batch run by a scheduled task, sub-agent or probe goes through the same gates. It does not run when autopilot is off (autopilot_off), checks again before every step (so "stop all" stops it; a step already running finishes first), and stops with autopilot_paused when a gate pauses, or busy when another step on the project is running.
  • Any batch stops with step_crashed when a build crashes. It never reports project_done while a task is still IN_PROGRESS (in_progress).
  • Every batch stops before a step that would end inside the request's report reserve (deadline). It uses the longest step of this batch so far as the estimate, and FIRST_STEP_ESTIMATE_S (120 s) before the first step (§4MR: the first step used to run unchecked). It is still a lower bound: a short research step says nothing about a following build. Before this, nothing checked the clock between up to 40 builds in one tool call.

Fresh-eye review before production 2026-10-15 §4PG

Three readers (advancer and gates; coding executor and leaf; research, digest, routes, ledger) plus a corpus lens. No CRIT; twelve MAJOR, all fixed. The property: an unattended tick does only what the project's tasks say, inside its workspace, within the budget; stops rather than guesses; DONE only on evidence the tick produced; the owner is told.

  • DONE needs a verify that ran. A leaf that wrote files and said VERIFY: none (or re-quoted the contract, or VERIFY: true) closed DONE on its own SUMMARY. CodingResult.verified is set only when a verify command ran and exited 0; unattended, an unverified build is held NEEDS_USER ("built but no verification command ran"). The owner's own autoadvance still closes DONE.
  • A postcondition demotion is a failed step. update_status(DONE) demotes to FAILED on an unmet postcondition; the record said "completed". _finalize_coding reads the status back and books autoadvance_step_failed.
  • Research that did not land is held. A brief written from low-relevance or engine-failure output closed DONE; _research_output_usable holds it. Only line-anchored [Source: …] markers count as sources.
  • Nothing runs beside an unattended step. The owner's autoadvance refuses while a step of this process is live on the project (unattended_step_live); a same-boot marker older than the step cap is treated as lost (a failed _leave used to make the project "busy" for the process life).
  • No silent loops. A dependency-blocked project is stamped (the round-robin rotates) and logs autopilot_blocked once; a research write failure counts toward the no-progress pause and pushes once per task, not per tick; an error after a DONE leaf never reopens it; a failed unattended build pushes once through the activity ledger.
  • The owner's return is a deferral. A leaf whose LLM call was aborted for the owner's request raises BackgroundDeferred right after the reply (the executor re-raises it); the advancer classifies the tick deferred: leaf reopened, not scored, not charged — it used to become FAILED, or count as no progress until autopilot paused. The deferred attempt's files are remembered for the next invocation.
