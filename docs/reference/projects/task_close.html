core / task_close.py

§4SU Phase 1 (2026-11-02): one close check for a project task, used by every path that can close one DONE.

Why it exists

A task reached DONE four ways: the model's task_update (T), the web console's PATCH (H), the autonomous advancer's build and research closes (A), and the parent roll-up when its children finish (R). Each path had its own checks, in its own order, with its own outcome for the same defect. The 11-02 audit found a missing declared file refused on T, FAILED on A, and not checked at all on H and R. A model-experiment parent could close DONE through its children's roll-up with no kept transcript (the §4ST bypass).

The verdict

check_close(store, project_id, tree, task_id, *, actor, result, description, files, live_evidence, constraints, override, skip, single_task) returns a Verdict(ok, refused, waived, overridden). It has no side effects: nothing is registered, logged or written. It runs the mechanical gates in a fixed order (GATE_ORDER), and the first refusal decides:

  1. dependencies: a depends_on task is still open.
  2. deliverable: the declared file (→ path) is missing or hollow (task_deliverable).
  3. model_run: a model experiment with no kept probe_model transcript (§4ST).
  4. evidence: a visual task, or a task under constraints, closed with no result (sub: visual / constraints).
  5. postconditions: a postcondition the proposed result does not show. The tree's own check runs on a copy of the node, so the close is refused before it happens instead of demoted to FAILED after. A close with no result is judged on the stored result only when the system did not write it (review r1: a hold or a roll-up refusal quotes the postcondition it refused, and a bare re-close passed on that echo).

The check of a rolled-up parent runs on the event loop inside update_status (measured ~30 ms on a 3,000-file workspace). Review r1 moved the closes into worker threads; r2 found that this opened a cancel point between the status write and its records (overrides, events, budget), so they were moved back. A gate that crashes is logged and passes; the tree's own checks remain. Two steps stay with their owners after these: the constraint AUDIT (an LLM judgement, model path only, reported in the same refused shape as gate constraints) and the HUMAN GATE (a park in TaskTree.update_status, never a refusal).

A parent already DONE is never re-judged by a later child close (r1: a re-close undid the owner's override). Whenever it later reaches DONE with no result of its own, the refusal text is dropped (the ALL roll-up uses the children's results), and a child's system text (a hold, a refusal) is never read as the roll-up's evidence in any branch, ALL, ANY or BEST (r2, r3: a grandparent, then a BEST parent, passed on the echo). The whole of a held child's summary is dropped, not just its hold suffix. That fails safe: the owner then closes the parent too. A BEST parent picks its best child by the length of that text, not of the raw summary (r4: a longer gate text hid a real sibling). A parent refused again for a different reason is re-stated and logged again (r3); the same reason is not logged twice; the digest lists a waiting task once, and not at all once it has closed DONE (r7); a bulk close lists a parent once, and not once it really closed in the call (r4, r7). Known limits: an ANY parent copies the winning child's text even when it is system text (display only); a real result that begins "not closed:" is read as system text.

Overrides

override={gate: reason}. The model may waive only model_run and postconditions (MODEL_WAIVABLE) in this check. Its tool also reads override={"constraints": …} for the constraint audit, which is outside this check, and records it only when the task has files the audit would have read. A model_run waiver needs a reason of at least MIN_WAIVER_CHARS (12) and a call that closes one task; not_model_data is the old name for it. An override of any other gate is ignored and the gate refuses. The advancer and the roll-up cannot waive. Each waiver that ends in a real DONE is logged (close_override), written to the ledger, and returned in overrides.

Where it is called

  • tools.projects task_update: actor="model", in a worker thread; model_run is skipped on a re-close of a task already DONE; a refused re-close says the task stays DONE. The roll-up skips the dependencies and evidence gates: the children are the evidence, and a parent's own depends_on orders work but does not keep finished work open. This matches the behaviour before Phase 1.
  • api.projects_routes PATCH: actor="owner", after the other edited fields land, with the task's and the project's constraints; not on a re-click of a task already DONE.
  • project_advancer: _finalize_coding (skips dependencies, model_run, evidence: the build's own §4ST gate ran before) and the research close (skips dependencies, evidence).
  • planning: ProjectPlan installs tree.close_checker; the roll-up runs it with actor="rollup" (skips dependencies, evidence). A bare TaskTree has no checker and rolls up as before.

A constrained parent waits for the owner (operator 11-02)

Review r8 found that the roll-up runs this check but not the constraint AUDIT (an LLM judgement of the task's files, model path only), so a parent with constraints closed DONE unaudited; this predated Phase 1. Operator decision: "wait for the owner". After this check passes, ProjectPlan._rollup_close_check refuses a parent that has constraints (its own or the project's) and files the audit would read (its registered file artifacts or its declared deliverable, _files_for_task): NEEDS_USER "not closed: constraints: its files have not been audited against … — close it with task_update (that runs the audit) or by the owner's click". A fileless parent has nothing to audit and rolls up as before. No model call runs inside the roll-up. The model's own close audits the same files: the files it passes, the task's registered files and its declared deliverable (r9: the declared file was missing on that path, so the close skipped the audit). The owner's click over the hold is recorded as a constraints override. Cost (r9): in a project with constraints, a parent with a declared file stops once even when a child already audited that file.

One refused list (§4SU Phase 4, 2026-11-02)

task_update no longer returns the legacy per-gate keys. Every refusal is an entry in refused, and instruction_for(refused) is the only instruction. Its header now says: when a fix is yours to do, do it, then retry with status=done AND the result in the same call (a result-only call never closes); when the fix says stop, stop. A dependency that is itself waiting (NEEDS_USER or BLOCKED) gets the fix "tell the owner what it waits on and stop": "close it first" had pushed the model to force-close an owner wait (r3). Since r4 the fix names every open dependency by kind, one line each: failed, or BLOCKED by a failed child, i.e. the cascade's child_failed (it names the FAILED leaves to redo with status=PENDING and the BLOCKED leaves to raise with the owner, or says replan; a failed or blocked parent with no such leaf to name gets "replan it", never status=PENDING, which strands a non-leaf (r6–r8); r5: reviving a failed or nested-blocked parent stranded the work, since it is not a leaf); blocked for its own reason ("tell the owner and stop"); a hold ("held for the owner's own run"); an owner wait ("tell the owner and stop"); running ("wait for it"); open ("do it first"). The visual-evidence fix names a browser RENDER_CHECK line as evidence.

The deliverable gate is waivable, with a reason (§4UI, 2026-11-12)

  • MODEL_WAIVABLE = {"deliverable", "model_run", "postconditions"}. A deliverable or model_run waiver needs a reason of at least MIN_WAIVER_CHARS (12) characters and covers one task. The refusal text shows override={"deliverable": "<why, in a sentence>"}; the waiver is recorded with the other close overrides.
  • A rewrite that drops the declared path no longer re-appends "→ old path" when a deliverable waiver of 12+ characters is given in the call that first closes the task and uses the waiver (the waiver is recorded there); in any other call, or when the file exists and no waiver was needed, the old path is kept (review r1 MAJOR 2, r2 m2).
  • gate_model_run reads the kind through _trusted_kind (planned_kind).
  • The visual-evidence gate applies only to code: with a declared deliverable, only a code suffix (_VISUAL_CODE_SUFFIXES) needs a screenshot; with none, research and write tasks are exempt.

§4UL: the dependency fix says what to do (2026-11-12)

  • gate_dependencies' fix text no longer tells the model to stop or ask: a dependency held from an unattended run (wait_on="owner_turn") is "held from an unattended run — do it now (or task_update it back to PENDING)"; a BLOCKED one is "remove the cause yourself if you can, else say what only the owner can give"; one waiting on the owner "waits for something only the owner has — say what, in one line".
