Living projects and the change log

§4UM (2026-11-13): a project is an application the owner keeps changing. Finishing the plan leaves it open (“ready”); only the owner closes it; every change the owner asks for is one entry in the project's change log and the agent's own file PROJECT_CHANGES.md in its folder; every push to the project's kept lab is recorded with where it is live.

Why it exists

The owner built a webOS as a project, deployed it, then asked for a Tetris app. The work was done and pushed live (two lab puts into the kept lab), but the project had rolled up to DONE when its plan finished, and nothing about the Tetris request was stored on it: asked later what the project contained, the agent had no record of Tetris. §4UL's fix (a write into a DONE project reopens it with a “Change:” task) recorded only the ask, ignored changes to ACTIVE projects, churned DONE ↔ reopened, and never said what went live.

othersNEEDS_USER, FAILED, ARCHIVED, RELEASED…unchanged
  • ProjectStore.project_state(pid) derives it; planned_work_done(pid) is state == "ready".
  • The roll-up never sets DONE. When the last task closes DONE with no failures, _planned_work_finished moves a waiting/failed project back to ACTIVE (guarded on the status it read, so a concurrent ARCHIVE wins), sets metadata.planned_done_at once, logs project_auto_rollup {new_status: "READY"}, retires the constraints (they come back with new tasks) and fires the old DONE hook (the clean-up sweep, the “notify me when done” promise). New open work clears planned_done_at, so the next finish fires again. metadata.first_ready_at / first_ready_req are never cleared: they say the first plan was built, and by which request.
  • Only the owner closes. manage_projects update status=DONE is refused unless it is the owner's turn (a probe may close its own probe project). The close logs project_closed {by: owner, req}, and its result says “closed by the owner's request (DONE)” so a model that closes on its own reading is visible in the transcript and the log. A finished batch reports project_done with the text “the project stays OPEN (ready)”; a batch on a project the owner closed reports project_closed.
  • The who-may-act wall (_lifecycle_confirmation) runs for every release, unrelease and delete, whatever the state: a background, scheduled or probe turn, or a request that read outside content, cannot release or delete a ready project.
  • Release, the digest (“all planned work done (stays open for changes)”), the notify promise (a ready project captures “notify me when done”: it fires when the plan finishes after the ask, or a change is made after it), the defect report (“it's broken” on a ready project adds a FIX task), the inter-project dependency gate and the verifier's reopen budget treat ready as DONE was treated. Idle autopilot skips ready projects.

The change log

Table project_changes (one row per entry): kind (change or deploy), num (changes only, 1, 2, … per project), ts, req_id, ask, added / changed / removed (project-relative paths), summary, deployed, deployed_at, url, pushed, meta.

  1. Watch. An owner request watches a project from the moment it is in play: the focused project at the start of the request (begin_request_watch in handle_chat), and any other project the first time a hook names it. Watching takes a stat snapshot of the folder (path → size, mtime, ctime), skipping PROJECT_MAP.md, PROJECT_CHANGES.md, .git, node_modules, .deps, __pycache__, .venv/venv, .tox and dot-folders; env/ only when it holds pyvenv.cfg and target/ only when it holds CACHEDIR.TAG or .rustc_info.json (otherwise they are content, like build/ and dist/). At most 5000 entries, files and folders both counted, and one second (5 s for the walk at the flush). Over either, or a folder that cannot be read: no comparison; the project is not walked again for an hour, and a writing request still gets its entry, with the tool-reported paths and meta.folder_too_large (“files not all listed”). An entry that names no file at all needs real write evidence (round 4, write_evidence): a reported path, or a command whose write targets are known (_shell_write_targets) or an inline script it saves — a pinned pytest, ls or git status diffs the folder but alone never makes an entry. Round 5: a command whose events include a write (project_turns.shell_check_events: rm, a mutating git, a formatter, patch, inline code that writes) is evidence too, and so is a folder that could be compared at the request's start and no longer can at its end (it grew past the cap). What is left: a generator (make, npm run build, python gen.py) on a project that was already too large to compare — no entry, one INFO line “project X is too large to compare; a command ran that may have changed files — no change entry”. The hooks snapshot before the write: the file tool before its operation (both the source and the destination of a move), execute before the command runs (the pinned project's folder, and every projects/<id> the command or filename names).
  2. Collect. note_project_write records the paths the tools report: the file tool's write, edit, delete, move, rename and download; execute's shell write targets (a root run's projects/<id>/… paths, and, round 3, a pinned run's relative targets that exist after it); generate_image's saved render (logged, but a render alone never reopens a closed project: it may not be for the project); the lab tool's get (file or folder — a folder is prepared and noted once as a batch, note_change_writes) and screenshot (_ws_write, _ws_mkdir). Each of them also prepares (snapshots) before it writes. The download's file name comes from download_target_name, shared with the download itself; an unreadable URL is refused. Who counts: the owner's own turn, and a project task's turn run inside the owner's request (both keyed by the root request). Background, member, probe and simulated turns record nothing, with one exception: an unattended task turn on a project whose first plan was already finished before it (autopilot after ready) is its own entry, keyed by the task turn, with ask task: <description> and meta.source = "task". A RELEASED project records nothing (changes go to create_version).
  3. Only a request that wrote. The folder is diffed only when the request ran a writing tool on the project: the file tool's write/edit/delete/move (prepare_project_write, note_project_write) or execute for the pinned project or a project its command names. A lab put is not a folder write. A request that only read, searched or took a screenshot writes no entry and reopens nothing, whatever moved in the folder meanwhile.
  4. What is not the owner's. From the diff (never from a write tool's own noted path) the flush leaves out: files the system wrote or moved away (note_system_path: NEW browser screenshots and check files noted by turn_scratch, its trash moves, the workspace sweep and tidy, an image edit's joined reference picture, the research mirror — research/INDEX.md, main-loop-findings.md, briefs; a request's own registrations are kept apart from the global bounded list, so other requests' sweeps cannot evict them); a path another request's write tool noted during this request (a concurrent task turn); and anything that moved before this request's first writing tool (mtime/ctime, 1 s slack).
  5. Write at the request's end. handle_chat's finally calls flush_change_log(request_id, reply) before the deferred sweeps. For every watched project it re-snapshots the folder and diffs: added, changed (size or mtime moved), removed; a removed folder whose files the snapshot listed is not listed again. That is unioned with the noted paths (a noted path gone since is removed, or dropped if this request added it; a path noted as added before the snapshot saw it stays added). One entry per project that changed: ask is always the owner's message of the outer request (never a task turn's prompt), summary the reply the owner was shown, as plain text (≤ 300 characters): §4UM-s, _finalize_and_return leaves it in _CHANGE_LOG_REPLIES after reply smoothing and before the digests and the correction banner go on its head, and the finally takes it — never handle_chat's own final_ai_content, which is the text before smoothing (req 56dff518's change #2 read “Now let me upgrade the test hook…”, the narration written beside tool calls). A request with no shown reply at the finally (a stream, an error, a cancel) writes an empty summary; set_change_summary at the end of a stream fills it and re-renders. The entry's ts is when the files' content last changed: a diffed file's mtime when it moved during the request, its ctime only for content older than the request's first write (a rename, a cp -p). ctime alone also moves on a metadata touch (an xattr written when the file is opened, such as macOS com.apple.lastuseddate#PS, or a chmod), so it does not date a fresh write (req 56dff518's entry read 12:19, index.html's ctime, for files last written at 11:52). The exception keeps the live marks right: when a version of the project was cut between the content time and the ctime (_push_times, read once per flush: this request's pushes and another request's still pending, with a pending switch's before_t; a recorded deploy entry; a staged deploy in metadata.staged_deploys; unreadable counts as a cut), the file keeps the later time — content renamed into place after a push is not in that push, for _covered and record_deploy alike (both order changes by this time). Known limit: stat cannot tell a rename from a touch, so a file merely opened after a push in its window reads not live and is dated at the touch — wrong in the safe direction; the next push marks it. Whether a path is this request's at all still reads mtime or ctime. A DONE project reopens to ACTIVE with no task (meta.reopened_from) only at a write tool's noted path; a change only the diff saw is logged and the project stays DONE. An entry whose write fails stays pending (and on disk) and is retried at the next flush, three tries at most.
  6. A killed request. The accumulator (paths, pushes, ask; not the snapshots) is kept in pending_changes.json in the memory directory and cleared at the flush. At start-up recover_pending_changes writes what a killed process left, with meta.recovered; what the log already holds for that (project, request) — the change, the deploy, or both — is not written again, and the missing part is; the file goes only when every row was written (a failing row stays pending); a corrupt file is moved aside to pending_changes.json.bad with one warning.
  7. Not a change: the request that built the project's first plan (it created the project, or closed one of its tasks before the plan was ever finished). Once the first plan was finished by another request, a request that changes files is a change even when it adds and closes tasks for it.
  8. PROJECT_CHANGES.md is the agent's own file, starting with the line <!-- written by the agent: this project's change log (§4UM). Edits here are overwritten. -->. It is rendered after every write: newest first, the last 200 entries (older ones: action=changes), a uniquely named temporary file then an atomic replace, no symlink followed. A file of that name without the header is the project's own and is never written over (a warning is logged; the store still has the log). A project's own CHANGELOG.md is ordinary content: editing it is a change like any file. Deploys leave PROJECT_CHANGES.md out (DEPLOY_ARTEFACTS_TOP), so the owner's words never ship to the live site. The clean-up sweep keeps every file a change added or changed, the files a running request is still writing, and PROJECT_CHANGES.md once the log has an entry.

Going live

tools/labs.py calls _note_project_push after a successful push into a kept lab whose owner is project:<id> (looked up once per lab with GET /v1/labs/{id}), from owner or autopilot turns (not probes, not simulated turns):

actionmarks live
lab put of a fileits project-relative path, only when it goes into the app's member and under its workdir; a put anywhere else marks nothing
lab put of a folder"dir/" (every file under it), same member/workdir rule
lab deploy serving (ok or still starting)the whole project — the project folder or any folder inside it — marks every change made before it live, including changes that only removed files
lab deploy stagednothing yet: its time is kept (metadata.staged_deploys)
lab switchthe changes made up to the staged version's deploy time; with no staged time known, nothing (the live URL is still recorded)
a push from a folder outside the projectnothing is marked; the deploy entry and the live URL are still recorded

Inside a request the pushes collect with the writes; at the flush a change is deployed when every file it added or changed was covered by a push made after it was written (noted writes are ordered by sequence, diffed ones by mtime), and one deploy entry is written for the request's pushes. Outside a request (record_deploy) a whole push marks every undeployed change made before it; a file push adds to each change's pushed list and marks the change once all its files have gone. metadata.live = {url, lab_id, app, at, how, through}, never overwritten by an older deploy; live_info adds behind, the numbers of the changes not live yet. A lab keep ships no code and records nothing; a rollback is not recorded (the marks then overstate what is live).

What the model reads

  • The turn's briefing (build_project_briefing): a ready line (make changes straight in the files; the system logs them; tasks only for multi-step work; only the user closes), a closed line for DONE (a change reopens it), RECENT CHANGES (the last five entries), LIVE AT (with the changes it is behind) and FILES (on disk now), generated from the folder each turn (≤ 40 paths; dotfiles, node_modules, caches and build folders left out).
  • manage_projects: status/get/switch briefings carry project.state, state_note, recent_changes, files and live; list shows the state (ready after working); the read action changes pages the whole log (count, metadata.offset).

Backfill

scripts/backfill_project_change.py adds one past change (work done before the log existed). Every detail is an argument: --project --ask --added --changed --removed --summary --ts "YYYY-MM-DD HH:MM" --req, and --deployed --url --how --lab-id for a change that went live (a deploy entry at the same time, and metadata.live). --deployed without --url marks only that entry live. A project the old roll-up closed already reads ready, so --reopen is only for a project the owner closed (it is harmless otherwise). Dry run by default, with the database opened read-only; --apply writes, and refuses while the agent holds the memory directory (stop it, apply, start it). Idempotent: the same --req, or the same ask within 60 s of the same time, is reported as already there and nothing is written, unless --force. An older backfilled deploy never replaces a newer metadata.live.

Known gaps

  • A change made by a command in a project that was not focused and that the command does not name (projects/<id>) is not watched. A screenshot the owner asked to keep in the project, or a research brief, is the system's writing and is not listed. A diff-only change leaves a closed project closed. A folder over 5000 files lists only the noted paths. A killed request's recovered entry has the noted paths only (snapshots are not kept on disk).
  • A rollback, or a deploy outside the agent, does not update which changes are live.
