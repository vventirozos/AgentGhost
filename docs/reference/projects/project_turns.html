core / project_turns.py

§4UL (2026-11-12, operator decision 1A): an autopilot or owner-requested batch runs each project task as ONE full main-loop agent turn. The build executor is only the fallback.

Why it exists

Before §4UL a batch built a coding task with coding_executor.build_coding_task (the one-call spec executor, or the agentic leaf with four tools) and ran a research task as one web search. The owner's own chat turns did the same work with every tool, the project briefing and the close checks of manage_projects task_update, and did it better. Now the batch gives each task the same kind of turn.

One task, one turn

  1. project_advancer._advance_once_body claims the task (IN_PROGRESS) and classifies it as before.
  2. For coding and research, when wants_task_turn is true, run_task_turn_for_advance runs it. Other kinds (model runs, owner reviews) and holds keep their own paths.
  3. The turn is coding_loop.run_leaf_turn with allowed_tools=None (every tool), origin owner, unattended or probe, request id sub-ptask-<task>-<hex> and label ptask. Its context is the leaf's: project pinned (the briefing reaches the prompt), writes confined to the project, owner memory read-only.
  4. The prompt names the project, the task, its kind and declared file, and says how to close it: task_update status=DONE result=… deliverables=[…], or FAILED with the reason. Nobody is present, so it asks nothing.
  5. After the turn the advancer reads the task's stored status and maps it to an AdvanceResult (below).

Who the turn is

  • The owner's run (manage_projects autoadvance in the owner's turn, the console's advance) carries origin owner. The lab tool lets it deploy to and keep a kept (production) lab: the owner asked for the work. Its model calls are not background calls (the owner is waiting). It keeps what it starts, like any owner turn: no leaf tag, and nothing is destroyed at its end.
  • An unattended run (the idle loop, a scheduled batch) carries origin unattended. Kept machines are refused by the lab tool and the labs host. Idle autopilot's model calls go through the background lane (_BackgroundOnlyLLM); a scheduled or probe batch is itself a request, so its turns use that request's lane (review m1: in the background lane they waited on themselves). Its disposable labs and runs end with the turn (the leaf's end clean-up).
  • A probe's run keeps origin probe.
  • Every task turn has a sub- request id, so it is never the user for memory: knowledge_base forget and reset_all refuse it, in every run.
  • Inside the turn, manage_projects refuses actions that steer the whole project: autoadvance, autopilot, switch, create, delete, archive, resume, exit, budget, replan, create_version, release, unrelease, promote_from_context, task_delete, and (review M4) update, constraint_retire, clone, cleanup and set_dependency (REFUSED_PROJECT_ACTIONS, reason task_turn_scope). task_update may only name the turn's own task or a subtask under it; task_add may add a part under it (parent_id = the task or one of its subtasks) or a top-level follow-up, never under another task; task_decompose may only split the turn's own task (re-review m1). Ids are read the way the handler reads them (re-review M2): stripped and lowercased (memory.projects._canon_id), a JSON-list string in task_id expanded, task_ids as a list, a JSON-list string or a bare / comma string (tools.projects._coerce_str_list). Another project may only be read (_READ_ACTIONS: get, status, list, task_list, task_next, artifact_list, event_log, file_history, search, research_list, verify_release, and ledger / describe_file without their write arguments). research writes a brief into the project's workspace, so on another project it is refused (re-review m1). The checks live in _TurnWatch.scope_refusal. The wrapper is applied again after a tool-dict rebuild.
  • The owner's run acts with the owner's authority for a project constraint too: a stated exception (override={"constraints": …}) goes through and is recorded, as in the owner's own turn (tools.projects._owner_task_turn: a sub-ptask- id, scope origin owner, and a parent request that is the user's).
  • The turn's request id is recorded as running inside the request around it (memory.projects.set_request_parent); idle autopilot's turn has none.

Idle gating

The idle loop's executor is marked idle (mark_real_executor(_aa_build, idle=True) in agent.py). Its task turn starts only while llm_client.foreground_requests == 0. Otherwise the task goes back (release_claim) and the result is deferred, which is not a step. A turn whose model call is aborted for a user request (BackgroundDeferred, or [ATTEMPT_ABORTED_UPSTREAM] while the owner holds the slot) is also a deferral. A BackgroundDeferred / LaneDeferred raised in the turn's model call reaches the turn as agent.py's catch-all reply ("… (BackgroundDeferred) … [ATTEMPT_ABORTED_UPSTREAM]"). With no outer request it is a deferral even at foreground_requests == 0 (an outside call on the main slot, a kept slot, the owner's request ending before the unwind), never a model-server failure that rests autopilot. The marks come from the classes themselves (deferral_marks(), every subclass included), so a rename cannot drift (round 8). Only agent.py's whole phrase ("with the LLM (BackgroundDeferred)") together with [ATTEMPT_ABORTED_UPSTREAM] counts (is_deferral_reply), so a model reply that merely quotes the class name is not a deferral. The release reason says what happened: "deferred for the owner's request" only while foreground_requests > 0, otherwise "deferred (the main slot was busy)" (round 9).

At the turn's end, on every exit path (normal end, timeout, the owner's request taking the slot, a crash, a cancel: review M7, re-review m2), each refused DONE the turn did not follow with another close is settled by _settle_holds. It closed tasks the model had since failed, or the owner had moved, and its project-done sweep was lost.
  • A later task_update that went through with a terminal status (FAILED, BLOCKED, NEEDS_USER / WAITING, PAUSED, CANCELLED) drops that task's refusal, and that status stands. A non-terminal one (IN_PROGRESS / RUNNING, PENDING) keeps the hold (round 5 M1). Statuses are read as the handler reads them (WAITING → NEEDS_USER, RUNNING → IN_PROGRESS).
  • Only a task still open as the turn left it is held: the turn's own task still IN_PROGRESS, or a subtask it made still PENDING / READY. A task the owner moved during the turn keeps the owner's status.
  • Each task is held by its own verdict: in a multi-id DONE, a write / research task whose own verdict passed is not held as unverified; it was just not closed.
  • A held task waits as NEEDS_USER, owner_turn/unverified_build (or verify_task), with the turn's result text. If a check ran after the refusal but the turn never closed again, the hold says so honestly ("a check ran after the refused DONE but the turn never closed it again") with no re-check kind, so the owner's run re-judges it rather than re-checking files.
  • The hold keeps that task's files: its own DONE deliverables, plus files the turn wrote under the path the task declared (never every file the turn touched). They go in the autoadvance_needs_user event (files) and are registered as the task's artifacts, so the owner's run re-checks them (_recheck_held).
  • A task that has subtasks (the turn split it) is never parked, because a NEEDS_USER parent would hold every subtask (next_ready_leaf's blocked ancestor). Only the subtask the DONE targeted is held, and independent siblings go on.
  • The settle step is synchronous, so a cancel cannot cut it short. It runs before the step and runtime charges, so a failing charge cannot lose a hold (round 5). A cancel while the turn finishes still holds what is left. A store error on one task is logged and the others are still held. If recording the turn's outcome fails, the turn's task is released (release_claim), never left IN_PROGRESS.
  • Every subtask under the turn's task that this turn set IN_PROGRESS, and that is still IN_PROGRESS and not held, is released on every exit path, cancel included (round 5 M2). Before this, the boot reaper had to clean it up, and meanwhile the parent never completed and autopilot idled. A subtask another run claimed meanwhile (the owner's batch building it) is left to that run (round 6). A turn that sets its own task back to PENDING / READY after a refused DONE keeps the hold; an IN_PROGRESS the turn set earlier never covers the owner resetting it to PENDING (round 7). A task_update books each id the handler wrote at the status it ended at (its updated list: a DONE a close gate turned into FAILED is the turn's own FAILED close); an id it refused before writing books nothing (round 8).
What counts is decided by _TurnWatch.note. The gate guards an honest model's omission (it built and never ran anything), never an adversary (round 3 A):
  • A check is any allow-listed program that ran, anywhere in the command line: in a pipeline, after ; or ||, inside a for/if/while body, in bash -c '…', in $(…) or backticks. Its exit status does not matter (an honest model reads a failure); only a refusal before it ran does. Allow-listed: Python files, modules (not pip/venv/http.server/playwright) and inline code; node/deno/ruby/php/perl/java …; pytest, tox, make, compilers, test runners; npm test/npm run X, yarn/pnpm scripts, go test|run|build|vet, cargo test|run|build|check|clippy, dotnet test; bash file, ./file; uv run/poetry run, npx/npm exec, docker exec (judged on the rest); psql/sqlite3; curl/wget of a local address; and linters and type checkers (mypy, ruff check, flake8, pylint, eslint, shellcheck, htmlhint, tsc, node --check, php -l, black --check). Prefixes (env, sudo -u x, timeout 60, nice, VAR=x) are skipped (execute.strip_command_prefixes). Here-document bodies are data, unless a shell or an interpreter reads its script from one. Also checks: an execute of a file or of inline code that does not write files, a lab exec of an allow-listed command, lab http (any response) and lab screenshot, run collect/run logs, and any browser call but close.
  • Not a check: looking (ls, cat, grep, echo), installing (pip install, npm install, playwright install), copying or writing, --version/--help, git status, curl of a remote site.
  • A write (it voids an earlier check) is every file_system operation that is not a read (file_system._READ_ONLY_OPS) and was not refused: write, edit, replace, append / append_file / write_append, copy, download, move, rename, delete. A PARTIAL write (kept, syntax flagged) counts. An execute writes when a command names a target (_shell_write_targets, /dev/… aside), runs rm, patch, git checkout|reset|apply|…, edits in place (sed -i, perl -pi, ruby -i), runs a formatter (black, ruff format, prettier --write, gofmt -w …; a linter's --fix checks, then writes), or runs inline code that writes files (write_text, open(…, 'w'), to_csv, writeFileSync … in python -c, a here-doc fed to python / node, or execute content=): that is a write only, not a check. A script saved with filename + content writes and then runs. A write counts even when the command then failed. Prose (.md, .markdown, .txt, .rst, .adoc) is never a write that voids a check (the §4QB-c precedent). mkdir is not a write. A program's own output saved to a file (pytest > out.txt, … | tee run.log) is its log. What a lab exec writes is on the lab, not in the workspace.
  • Order inside one command counts: echo x > a.py && python a.py checks after its write; pytest && sed -i … a.py does not.
  • Lines (round 3 B, execute._shell_tokens): a backslash-newline joins two lines, and a newline right after &&, || or | continues the command; only a bare newline ends one.
A check that ran also clears the check-word hold. Research, and a task declared kind: write (a prose deliverable, round 3 E), need no run: with no check they are judged only by the check words.

Each turn charges steps_used and record_runtime, like a build.

Time

A turn gets GHOST_TASK_TURN_TIMEOUT_S (default 1800 s) and GHOST_TASK_TURN_MAX_TURNS (default 40) model turns, bounded by the unattended step's deadline (leaf_deadline_context) and by the time the owner's request has left, less 60 s for the batch's report. Below 120 s no turn starts, and the task goes back as out of time.

Switch

GHOST_PROJECT_TASK_TURNS (default on). Only an executor marked by mark_real_executor (build_coding_task, the idle _aa_build) runs tasks as turns, so a unit test's stub executor keeps its path. The suite pins the switch off (tests/conftest.py), and the §4UL tests turn it on.

Hooks in the same change

  • Program failures on a lab. A lab exec whose command ran and exited non-zero, and a run collect of a job that exited non-zero, are fix-and-retry steps like execute's (§4UI): a changed output is not a strike (agent._lab_program_failed). Refusals, deadline or cancel kills, lost jobs and the sandbox's own kills (124/137) still count.
  • Writes into a project's folder. file_system writes and edits, and an unpinned execute whose command writes under projects/<id>/, call tools.projects.note_project_write. Its note (a DONE project reopened) is added to the tool result. The written paths come from execute._shell_write_targets (review M6): redirect targets, tee files, the destination of cp/mv/install/rsync/git clone, sed -i/touch/mkdir/truncate operands, unzip -d/tar -C and tar -c…f, and (re-review m3) curl -o/--output (also in a cluster: -sSo), wget -O, dd of=, the ln link, cp/mv -t DIR, through a sudo -u x / timeout 9 / env prefix, and a redirect glued to a separator ((echo a)>f, a;>f). /workspace/projects/… and ~/projects/… are read as projects/… (execute.workspace_relative). A path relative to an earlier cd is not resolved against it. Here-document bodies are skipped. A path the command only reads (python projects/x/app.py 2>&1 | tail, cp projects/x/a /tmp/b, grep 'x >= 1' projects/x/app.py) is not a write. A pinned execute (run in the project's own folder) notes nothing.
  • DONE sweeps at the request's end. handle_chat's finally calls memory.projects.flush_deferred_sweeps(request_id). A task turn's sweeps are queued under the request it runs in (request_root), so they run at that request's end; idle autopilot's run at the turn's end (review M5).
  • The project-done promise. A "notify me when it is done" promise is delivered by the project-done hook when the project closes in idle autopilot's task turn (no request around it to deliver it), as for the idle loop itself (main._on_project_done, review M3). In the owner's run the owner's request delivers it.
  • Removed. The §4PN confirm-wait takeover (_confirm_wait_reply and its regexes), the NOT_ANSWERED_YET and CONFIRM_WAIT_REPLY_HEAD marks, and confirm_dead_end in the dead-end refusals went with §4UK's previews.
