tools / search.py

Anonymous web search via Tor, racing a wide engine set with one Tor circuit per engine, with operator sanitization, a short result cache, reformulated fallbacks and multi-source synthesis.

Tools

Engine race: one circuit per engine (Tor reliability, re-measured 2026-07-08)

Re-measured over Tor on 2026-07-08 (42 probes: 7 engines × 2 queries × 3 fresh circuits each): per-(engine, circuit) success is ~10% — brave 2/6, yahoo 1/6, mojeek 1/6, everything else 0/6 — and which engine wins flips from circuit to circuit. Even the trivial query python asyncio tutorial scored 1/21. Failures are driven by the exit IP's reputation, not the engine.

That kills the previous design: ddgs's multi-backend mode (backend="m,d,y,b,g") runs every engine through the one proxy set on the DDGS instance — so all engines shared a circuit and failed together whenever that exit was blocked (~90% of the time). Worse, with max_results=20 ddgs caps its internal fan-out at 3 concurrent engine workers, so the "5-engine breadth" was really ~3 engines on 1 exit.

_race_search_wave decorrelates the failures: one single-engine ddgs call per engine, each tagged onto its own Tor circuit (_proxy_for_attempt with a per-engine salt folded into the SOCKS username:password; Tor's IsolateSOCKSAuth maps distinct credentials to distinct exits). The first engine returning non-empty junk-filtered results wins the wave and pending losers are cancelled. That turns one correlated ~10% attempt into len(_RACE_ENGINES) independent tickets (~47% per wave); 2 waves + 2 reformulation waves ≈ 24 tickets ≈ 90%+ overall. A typical success now lands in ~2–5 s (the fast engines win fast); only a fully-blocked wave pays the ddgs timeout + a small grace (_RACE_WAVE_GRACE).

The race set was (mojeek, duckduckgo, yandex, brave, google, yahoo); since §4HR (below) _RACE_ENGINES = (duckduckgo, yandex, brave, yahoo). It is deliberately wide — at ~10% per ticket every fast-failing engine is a cheap independent lottery ticket. yahoo is back in (re-measured 2026-07-08: fails fast at ~1.4–2.2 s instead of hanging, and won a probe). Still excluded: wikipedia (reads region="wt-wt" as language wt and builds the non-existent host wt.wikipedia.org — always a ConnectError) and grokipedia (typeahead API, 0/6 on real queries). A per-engine StopIteration is converted to RuntimeError before it can cross the thread→Future boundary (PEP 479 corrupts asyncio future chaining).

Per-request timeout (measured 2026-06-11; per-engine 2026-07-15). The ddgs request timeout was previously a single 8 s, and that number caused a wave of failures of its own: measured over Tor, mojeek responds in ~10–18 s through a circuit while the others fail fast (~1–6 s). At 8 s, mojeek was killed mid-request (error sending request for url (mojeek…)), so every engine came back empty even on circuits where results were reachable. It is now per-engine (_engine_timeout): mojeek keeps the full _DDGS_TOR_TIMEOUT = 18 s (the reliable slow winner), while the fast engines get _DDGS_FAST_ENGINE_TIMEOUT = 12 s. Because a race loser's thread is uncancellable (it runs to its ddgs timeout on the dedicated _RACE_POOL), the shorter fast-engine ceiling frees that thread ~6 s sooner on a blocked wave without costing wins (a non-mojeek win arrives well under 12 s). The wave deadline is still sized off mojeek (_DDGS_TOR_TIMEOUT + _RACE_WAVE_GRACE). Covered by tests/test_search_tor_timeout.py.

Query sanitization

The DuckDuckGo / Yandex / Brave / Yahoo scraper backends do not honour Google-style operators the way a real search API does: at best they're ignored, at worst the whole query returns zero results. The LLM is nonetheless prone to emitting them (the tool descriptions previously even encouraged site:). _sanitize_query strips them at the boundary, before a Tor round trip is spent:

  • site: / inurl: / intitle: / filetype: / ext: operators (with their argument token).
  • Standalone boolean OR / AND (boundary-gated and case-insensitive, so an or buried inside a word survives, and dropping a stopword from natural prose is invisible to the scrapers).
  • Quotation marks (the words inside are kept).

If stripping would empty the query — a query that is nothing but an operator — the operand is mined for keywords rather than passed through raw (2026-08-15). This is a live fix: the model asked for site:reddit.com/r/lgbtgreece/comments/1voyjgf/is_nudism_safe_in_greece, stripping emptied it, and the old fallback handed the scrapers back the original — the one shape they cannot honour. That returned zero across four waves and two reformulations (one of them literally how to site:reddit.com/…), burned ~80 s, and the turn was refuted by the late verifier for never retrieving the content.

The operand is not noise; it is the query, spelled as a URL. _keywords_from_operand splits it and keeps the meaning-bearing parts — the example above becomes reddit lgbtgreece nudism safe greece, which is almost exactly the query that won (brave, 20 results) earlier in that same turn. It drops URL furniture (www, com, r, comments, index, html…) and opaque ids (1voyjgf) — the tokens that make a query unmatchable — and caps the result at 6 terms, since the module's own reformulation notes record that longer queries have near-zero organic hits anywhere. If the operand mines to nothing (a bare TLD, e.g. site:.org OR site:.gov) the original is still returned unchanged rather than sending an empty search.

Mining only happens on the empty-after-stripping path, so the ordinary keywords + site:x.com shape keeps its previous behaviour exactly. The tool descriptions in registry.py instruct plain keywords only to match.

Result cache

The model habitually fires many near-identical queries in one turn. A small in-process TTL cache (_SEARCH_CACHE, 300 s, 128 entries since 2026-07-26 (was 64), FIFO eviction) keyed on the normalized query serves the repeats from memory instead of re-paying the Tor round trip. Only successful results are cached — error strings never are, so a transient failure is always retried fresh.

Reformulation strategy

web_search since §4UN-web (2026-11-13): the list below is deep research's (_reformulate_query). web_search uses reformulate_keeping_meaning — see §4UN-web.

  1. Drop years / version numbers / numbers from the query (broaden).
  2. Long queries (>6 words): hard-trim to the first 5 words of the broadened form. A keyword-stuffed query has near-zero organic hits anywhere, so no circuit can save it — and "how to {query}" keeps every rare term and fails identically (observed live 2026-07-08: the only total strike-out of the session was an 11-word query whose reformulations both preserved all its rare terms). Short queries still get the question form ("how to X").
  3. Append tutorial / guide / example as padding when the above yield fewer than 2 variants.

Wave logging

Several searches can race concurrently in one agent turn, so every wave log line — winner (mojeek won wave 0 in 1.8s (10 results) ‹query…›) and failure — carries a truncated-query tag to keep interleaved output readable (an apparent "won wave 10" right before "ZERO results" is two different searches finishing together).

A failed wave emits one terse categorized line (operator request 2026-07-08 — even grouped exception reprs were a wall of text): wave 0 ‹postgresql 20 features…›: no winner — 5 empty; mojeek conn-error (since §4UN-web every category names its engines: duckduckgo+yandex empty; yahoo blocked). _failure_category collapses each losing engine into empty (bare count — it's the boring default), conn-error, or timeout (engines named); an unknown error keeps a 48-char snippet so a new failure shape is never hidden. The full sanitized per-engine detail (URLs stripped via _brief_engine_error) goes to logger.debug for forensics.

Relevance floor: liveness is not relevance 2026-09-15

The race declared a winner on the first non-empty batch, which tests whether an engine answered, not whether it answered this question. Live, yahoo won a wave in 2.6 s with eleven Microsoft-account support pages for a query about a Revolut breach; the reformulation wave never fired, because the wave was not empty. Measured over the recorded trajectory corpus (557 web_search calls), 38 — 6.8% — came back with not one query content word anywhere in the result set: Bing-homepage-quiz Reddit threads, NHL standings, printable coloring pages, AZLyrics, Domino's Pizza México, a Django CVE for a PostgreSQL release-date query.

_results_are_off_topic now treats such a batch as a loss rather than a win, so the remaining engines — and then the reformulation waves — still get their turn. It is deliberately the weakest rule that catches that population: a single query content word appearing anywhere in the batch passes. Three properties, each established by measurement before the code was written:

  • Unicode, not ASCII. The first draft tokenised with [a-z0-9]+ and scored every Greek query 0.0 — it would have rejected all eleven Greek searches in the corpus. Tokens are casefolded and NFKD-stripped of combining marks.
  • Short queries are exempt (_REL_MIN_QUERY_TOKENS = 3). Πεοτρόμπης, a misspelling, correctly returns Πετρόμπεης Μαυρομιχάλης — zero token overlap and the right answer. Spelling correction and rare-name lookups must survive.
  • Text-free batches are exempt (_REL_MIN_RESULT_CHARS = 80). A bare {"href": …} row with no snippet is an absence of evidence, not evidence of irrelevance; condemning it would judge a batch for what it does not contain.

Matching is a substring test over title + body + URL with all non-alphanumerics removed, because engine snippets arrive with whitespace collapsed out (RevolutconfirmscustomerDatabreach) — a \b-anchored rule sees no tokens there and would reject good batches.

Known reach limit, stated so this is not mistaken for a relevance ranker: a batch sharing one incidental word survives the floor. The yahoo/Microsoft batch above matched data and would still pass today. Every stronger statistic that was measured — per-result token counts, coverage ratios — also rejected genuinely good result sets (PostgreSQL 20 features roadmap 2028 → PostgreSQL: Release Notes matches exactly one token and is the correct answer), so the floor stops where it has no false positives across all 38 of its historical firings. A losing engine is categorised off-topic, kept distinct from empty: one says the circuit or engine failed, the other says the engine is useless for this query. Covered by tests/test_search_relevance_floor.py.

Output cleaning

_clean_for_cpp strips control characters and lone surrogates from every title and snippet. The brace/angle-bracket rewrite ({} → [], <> → ()) exists for the llama.cpp grammar parser and since §4PD runs only while that parser is attached (GHOST_TOOL_GRAMMAR, off by default): with it off, std::vector<int> and {"wal_level": "logical"} reach the model as written.

Stylometric egress scrubbing

Tor anonymises the network layer; it does nothing about the content layer. The agent's prose — politeness habits, first-person framing, punctuation idiosyncrasies, verbosity — is a stable author fingerprint that would otherwise egress verbatim to every search engine. utils/stylometry.py normalises the outbound query into a neutral keyword form before it leaves the box, under --anonymous (content anonymisation travels with network anonymisation).

  • scrub_query — deterministic, always-safe lexical pass used by web_search: peels stacked request/politeness frames ("please can you find me…", "I'm looking for…"), lowercases, drops trailing sentence punctuation, removes politeness tokens — while preserving every content keyword and in-word technical symbol (c#, c++, .net survive). Bare search/lookup are not treated as frames (they lead real content phrases: "search algorithms in python", "lookup table sql"); only the framed forms ("search for", "look up") are stripped. Gratitude tokens are stripped only from the query tail ("… thanks" goes; "thank you card template" survives intact). Idempotent.
  • neutralize_query — stronger tier used by deep_research (already LLM-heavy): re-authors the query into a neutral keyword search via Ghost's own upstream, falling back to scrub_query on any failure. No third party. §4SC-b (2026-10-29): off the main slot — chat_completion(..., use_worker=True, off_main_only=True). It runs inline on every anonymous deep_research and darkweb_search, and as a plain main call without the head it displaced the owner's conversation (request 72c2f05d: 41,742 tokens re-prefilled, 282 s); with every worker node failed the client raises (off_main_only) and the lexical scrub is the answer, never the main model. §4SC-c (review r2): bounded — require_healthy=True, timeout=total_budget=_NEUTRALIZE_TIMEOUT_S, the same 12 s as core.llm._ROUTE_TIMEOUT_S; before, the worker client's 1200 s default let a hung or unreachable Nova stall every anonymous search 20 minutes, and a node with its breaker open was still called. With no worker pool configured at all (worker_clients == []) the lexical scrub_query is used directly, without a call: the client's "requested but unconfigured pool" arm would otherwise have run the rewrite on main with no save hook. Pinned through the real client against a TCP server that never answers (tests/test_4sc_cut_write_slot.py; harness scripts/mutate_4sc.py K14–K15). §4SC-d (review r3): the call's whole budget is 6 s (total_budget=_NEUTRALIZE_BUDGET_S; timeout stays the 12 s route bound). A saturated Nova is not a breaker fault, so require_healthy lets the call through to the client's permit gate, which is sized from the budget — at 12 s the gate alone cost 9 s and an anonymous search up to 21 s; now the gate is ≤ 3 s (measured 3.03 s: no POST, the lexical scrub), and a hung node costs 5 s, the /props probe, with no room left for a POST. An open breaker means no call at all, pinned on behaviour (no POST, under 1 s). Harness K20 (head_saves).

Covered by tests/test_stylometry.py.

Per-identity Tor circuit isolation

Under --anonymous, each search also rides a distinct Tor circuit: helpers.socks_url_with_identity injects a SOCKS username:password into the proxy URL, and Tor's IsolateSOCKSAuth (on by default) maps distinct credentials to distinct circuits — so a colluding set of exit nodes / sites can't trivially link a sequence of different searches into one session. No NEWNYM thrash, no control port needed. Covered by tests/test_quick_wins.py.

The search path takes this one step further: _proxy_for_attempt folds a query hash, the wave index and a per-engine salt into the SOCKS tag, so within one wave every engine rides its own exit, and every wave rotates all of them. This serves reliability (uncorrelated engine failures, escape from a blocked exit) and anonymity (a single logical search isn't pinned to one exit, and no single exit sees the query hit every engine) at once.

This is also why the search path never calls request_new_tor_identity(): a global NEWNYM re-circuits all of Tor (slow) and fights the per-engine isolation above. The old behaviour — 3 attempts, each rotating the identity and sleeping 5 s, then two reformulations — could stretch a single failing search past 200 s. (Page fetches in helpers.helper_fetch_url_content still rotate on 503, where the exit node itself is rate-limited — that's the right place for it.)

The research outcome carries its status 2026-09-13 §4GI

deep_research returned the same success-shaped string whether 8 of 8 sources loaded or 0 of 8; ToolOutcome.coerce booked it OK (the Error: lines sit under a success head), so a Tor blackout was scored as a competent research call by strikes, competence, foresight and pre-flight — and fact_check then asked the model to verify the claim against a page of error lines and booked a second OK. DNS-leak fix on the page fetch (2026-07-14)

helper_fetch_url_content (the shared page fetcher behind deep_research and knowledge-base URL ingest) validated the target URL with the SSRF guard's DEFAULT resolve=True — a HOST-SIDE getaddrinfo of the hostname on EVERY fetch, leaking the DNS query for the very site being visited anonymously and defeating the DNS-over-SOCKS anonymity the Tor fetch exists to provide. Since the fetch always routes through Tor (resolution/routing happen at the exit node), the host lookup bought no protection and only leaked. It now passes resolve=not bool(proxy_url) — mirroring the browser/download tools' resolve=not anonymous handling; the literal-internal-IP string check still runs, and a no-proxy fetch keeps the resolve check. Also hardened: _filter_junk tolerates a result with an explicit href=None (previously it raised AttributeError, which at the try-guarded call site sank the WHOLE engine's result batch for that wave). Covered by tests/test_fetch_dns_leak.py.

Circuit rotation + pool headroom + None-trap (bug-hunt 2026-07-26b)

The per-fetch circuit tag folded in a per-MINUTE time bucket, so two same-query searches fired seconds apart inside one minute (a common immediate model retry) rode the SAME Tor circuits → the same blocked exits, partially defeating the fresh-exits design. Now a 100ms bucket: coarse enough that a synchronous wave's back-to-back calls stay on one circuit (the determinism the per-URL fetch relies on), fine enough that a retry seconds later gets a fresh circuit. The isolated race pool was also raised to 8 concurrent waves (was 4) — deep_research fans out AND swarm workers each search, so an over-subscribed wave sat QUEUED while its own deadline ticked, returning [] having made zero requests (the deeper fix is a cancellable racer). And the result formatter uses .get(k) or default not .get(k, default): a row with an explicit href=None but a valid url otherwise lost its source link.

Result-cache near-dup normalization + circuit rotation (2026-07-26c)

The in-process TTL search cache (300s, successes only — transient failures never cached) gained _norm_cache_key: trivially-varied repeat queries within a task ("python asyncio", "Python asyncio", "python asyncio?") now share one entry instead of re-paying the ~10%-per-exit Tor lottery; the cap rose 64→128 so a research-heavy task doesn't evict its own recent results. Separately, the per-fetch circuit tag moved from a per-MINUTE bucket to 100ms so a same-minute retry rides a genuinely fresh exit, and the isolated race pool grew to 8 concurrent waves. (Improvement #4 + deferred LOW.)

Async-drain fix on the page fetch (2026-07-28)

The 2026-07-26 streaming-cap rework in helper_fetch_url_content copied the sync drain pattern from the darkweb sibling (_fetch_raw_html, which correctly uses the sync curl_cffi.Session in a thread) onto the AsyncSession path — but AsyncSession responses deliver body chunks through an asyncio.Queue, so the sync iter_content() on them yields unawaited Queue.get() coroutines instead of bytes. Every 200-status page fetch on the primary (curl_cffi) path then died with can't extend bytearray with coroutine, burned all three Tor circuit-rotation retries, and returned an error string — which downstream summarize/distill stages processed as if it were page content. The only visible symptom was a single RuntimeWarning: coroutine 'Queue.get' was never awaited (Python dedups warnings per location, and it points at the except handler where the abandoned coroutine happens to be GC'd, not at the bug).

Fix: the curl_cffi path drains with aiter_content() (_drain_curl) and closes with aclose_curl_response (utils/helpers.py) — quit_now.set() (makes the curl write callback abort the transfer, so a capped/rejected multi-GB body isn't silently downloaded to completion) followed by await aclose(). The sync close() was ALSO a silent no-op on these responses (it reaps stream_task, which AsyncSession responses never set — they set astream_task), so the old reject branch never actually closed anything. The shared test mock (make_streaming_resp) now models the async response surface too — its list-backed sync iter_content is exactly what kept the suite green while prod was broken. Covered by the AsyncSession-path regression tests in tests/test_helpers_async.py (sync-drain tripwire, cap-abort, reject-branch abort).

Round 3: partial coverage is not a failed action 2026-09-13 §4GJ

§4GI made deep_research return PARTIAL when any source failed. Every consumer reads PARTIAL as a failure — ToolOutcome.is_failure is "status is not OK", so the turn books turn_has_failure, the strike ledger fires, and the trajectory corpus records the turn as unsuccessful. Measured on the live corpus (435 trajectory files): 37 research results, 14 carrying the source-failures banner, 0 all-failed — the worst real case lost 6 of 8 sources and still produced a report. So the PARTIAL arm turned a normal 7-of-8 research turn into a strike and never once caught the case it was built for. Partial coverage is now OK with the banner text unchanged (the model still sees which sources failed, and the reason code still carries it to telemetry); only the zero-fetched case — the real §4GI defect, where an all-failed research booked as a clean success — stays FAILED. fact_check follows, with one deliberate exception pinned separately: a verification call that never RAN stays PARTIAL, because that is half-done work rather than partial coverage. darkweb_search, the sibling one revision behind, got the same semantics.

Round 4: the failure marker was unanchored 2026-09-13 §4GK

A source block is a header line followed by the page's text, and a fetch failure writes Error: as the first line of that body. The rule asked only whether the string appeared anywhere in the block — which includes the page's own text. A successful fetch of a page quoting Error: division by zero — a tutorial, a bug report, a log excerpt, exactly the material research is pointed at — counted as a failed source; with a single URL that makes the success count zero, so the "nothing fetched is a failure" rule booked a complete report as a FAILED action, fired the strike ledger, and told the model no source could be fetched. The onion sibling spelled the loose rule while its own cache gate, thirty lines away in the same function, used the anchored one — two parsers disagreeing about one run. There is now a single authority and both call it.

A cached onion report also returned a bare string, dropping the partial-coverage status: the same query answered a clean OK from cache minutes after answering partial. The status is re-derived from the coverage banner the cached text already carries.

Dead weight in the race sized every failed wave 2026-09-16 §4HR

Seven days of live waves (09-09→09-16, 509 wins): yandex 386 (median 2.3 s), yahoo 77, brave 43, duckduckgo 3, mojeek 0, google 0. mojeek — the July 2026 "reliable slow winner" whose 18 s budget sized the wave deadline — conn-errored or timed out in 53 of the 56 no-winner waves. Because a wave ends only when its last engine gives up, every failed wave cost a median 18 s (n=56) while the actual winners answer in 2–3 s. yandex conn-error in 45 of those waves is circuit-dependent (it wins 76% of the time; wave 1 on fresh circuits recovered 46 wins) and is left alone.

mojeek and google are retired from _RACE_ENGINES (a ticket that never wins is not a ticket); the wave deadline is now _race_wave_deadline() = the slowest raced engine's timeout + grace (12 + 4 s, was 18 + 4), so a wave of fast failures ends when its last engine does. The slow tier in _DDGS_ENGINE_TIMEOUT stays for re-adding an engine after a fresh per-exit measurement. Pinned in tests/test_search_race_deadline.py. Not changed: search volume per task — on the run that prompted this the two failed waves cost ~40 s of a ~700 s excess; the rest was 30 searches.

Snippet whitespace (§4IO)

ddgs 9.x builds every result field by stripping each text() node and joining them with no separator, so the whitespace a page has around every <b> highlight is destroyed: "Saturn <b>orbits</b> the Sun" arrived as Saturnorbitsthe Sun — titles and bodies, every engine (Yandex highlights most, so it showed there first). Live cost: glued prose for the user and the judge, and the verifier's figure parser reading 29.45years. _patch_ddgs_snippet_join replaces BaseSearchEngine.extract_results at runtime, once, before the first engine call, with the same extraction and a join that keeps the nodes' own whitespace and collapses runs afterwards — and only while the installed library still carries the defective idiom (checked against its source); a release that fixes or restructures it leaves the patch inert and logs a WARNING so a regression is noticed rather than double-fixed. Pins: tests/test_search_ddgs_snippet_join.py (the defect reproduced on a synthetic item, the fix, the guard, idempotence, the call-site order).

§4PU (2026-10-17): a past year next to "today" is dropped

The model's training ends in 2025, so it sometimes adds "2025" to a question about today. This happens even though every turn shows it CURRENT TIME (live request 3c527b55 searched "VUAA Vanguard S&P 500 ETF price today 2025" on 2026-10-17). Before searching, search.drop_stale_year removes a year only when all of these hold:

  • The year comes right after a point-in-time word: today, tonight, now, currently, this week/month, or the Greek σήμερα, τώρα, φέτος. "Price today 2025" says two different dates at once. A year before the word is left alone, because it is usually a product, model or edition ("Hyundai Tucson 2025 now recall", "ISO 27001 2022 currently"). Only the copy right after the word is removed, so "Camry 2025 price today 2025" keeps the model year. "Current" and "latest" are not enough, because they describe a noun that can carry a real year: "SQL Server 2025 latest update", "current F1 season 2025", "Office 2024 current price".
  • The year is a bare token before this one. 2024-10, v2025, $2025 and 2025's are left as they are, and so is a date like "October 2025".
  • None of your recent messages (the last four, this one included) contains that year, even as "…of 2025." or "FY2025". "What version of postgres was released in 2023?" keeps 2023.
  • Nothing makes the year the subject of the search. The word right before it isn't a period or comparison word (for example since, in, of, for, from, until, vs, FY, tax, Q1–Q4, a month name, or Greek από, μέχρι), and the query has no comparison or period word anywhere (for example vs, versus, compared, annual, report, fiscal, tax, earnings, YTD, 10-K, results, season, edition, since). The full lists are _YEAR_ANCHOR_BEFORE and _YEAR_ANCHOR_ANY_RE in tools/search.py.
  • The query does not also name this year.

The rule is narrow on purpose. Two review rounds showed that a wider list of "now" words dropped years that mattered (product names, comparisons, seasons), while each patch for those missed real stale years. A year it misses is searched as before, but a year it drops by mistake gives a wrong search. A replay over the 3,828 logged search calls since August changes exactly one query: 3c527b55.

What was wrong. On success the tool returned the verify call's prose and dropped the research report: in four months of recorded turns (7 calls, 2 real) no result carried a link. The research half had no bound of its own: its page phase stops at 190 s, but the search waves before it, and anything that hangs outside that phase, did not. Each source of the research report that contributed (it loaded and its block holds facts) is a row N. <URL>, followed by an indented title: line when the search gave a title and an indented evidence: line with the head of the extracted evidence. factcheck_sources reads the report already in hand: no fetch, no model call.   • Review round 1. Principle: never discredit or lose a real fact — a missed tag is acceptable, a false one is not.
    • Number tags: a number is on the page when its digits appear anywhere in the page's digits-only text, or a written form of it (as written, separators dropped, the other decimal mark) is in the original text. A well-formed grouped number ("1 234 567") is one token; a number followed by a scale word or a percent is never tagged; dates and times are checked by their year. Table cells ("2021 345"), "In 2024, 120 people" and verbatim grouped numbers were tagged before.
    • Negative facts stay: "nothing relevant" is only NONE or a single short line that says no relevant/hard facts or no information about the query; an extract of more than one line never is. "No data was lost…", "The document does not require a visa…", "This page does not list any recall…" are facts.
    • The window budget is filled: after the scored windows (a scored window that does not fit is cut around its first term), the unpicked windows nearest the lead, the last cut to fit — never meaningfully shorter than the old head cut (fuzzed: at most 25 chars, a whitespace cut). Windows break at whitespace when a line has no newline.
    • The title cannot forge the date: date first, title quoted with | and " replaced.
    • The cap spares the authority: the top-ranked site, a site the query or question names (python → python.org), and official hosts (.gov/.mil labels, .edu, .int, docs./developer.) are not capped (round 2: capped at 4). registrable_domain keeps multi-tenant hosts apart (_MULTI_TENANT_SUFFIXES: readthedocs.io, github.io, gitlab.io, blogspot.com, wordpress.com, substack.com, europa.eu, …) and drops www..
    • Minors: the recheck runs finish_fn in a thread; PDFs parse one at a time (round 2: on their own executor, below); a thin page gets one fresh circuit; an empty extract (cut or not) degrades to raw text; the not-attempted mark is read from block_body; the fallback queries add a ≤6-word trim that keeps numbers, negations and distinctive words. Old pins: §4NJ's "The source does not mention OpenZFS." is now a fact; a fetch-racing fixture returns a typed FetchError.
  • Review round 2.
    • Refusals: a refusal is an info noun (facts, information, details, data, content) after "No", "There is no", "The text does not contain/include/…", "I could not find" — with at most adjectives (any, relevant, hard, …) before it, and after it only the end of the line, "was found (in the text)", or the query/topic named generically. "There is no hard limit…", "No hard cap…", "No relevant API changes…", "The document does not include data on 2024 sales" are facts.
    • Number tags: only numbers of 3+ digits (NOT_IN_PAGE_MIN_DIGITS; a page writes "twenty-five", "δώδεκα"), and never a number the query, question or claim holds (context: the extractor repeats it to say the page disagrees).
    • PDF parsing runs on its own one-thread executor (helpers._PDF_EXECUTOR), not the shared default one, under PDF_PARSE_TIMEOUT_S = 45 s → "PDF parse … timed out"; a read cancelled while queued is dropped. The 300-page refusal is gone (pdf_text reads the first 20 pages).
    • The cap: the top-ranked, named and official sites get RESEARCH_MAX_PER_FREE_DOMAIN = 4 slots, not unlimited.
    • An oversized scored window is cut at its first term found in folded text (_folded_find: "πυρκαγια" finds "πυρκαγιά").

After PDF_MAX_REPLACEMENTS (3) in the process, a hung reader fails the read at once: "PDF reader unavailable (a previous parse hung)". PDF_PARSE_TIMEOUT_S is 15 s, inside the 22 s fetch attempt, so the error says "PDF parse timed out". A read dropped by a replaced executor is a failed read, never a cancellation of its caller.
