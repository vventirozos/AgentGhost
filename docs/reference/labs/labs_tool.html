tools / labs.py

The lab tool: disposable machines on the labs host, for the system under test. 2026-11-04 §4SX Phase B

Why it exists

The sandbox (execute) is one container with no root, no extra ports and no network faults. Work like "run a Postgres 18 primary and a replica, kill the primary, watch the failover" needs real machines. The labs host runs the ghost-labs service (interface/ghost-labs/). It creates such machines from templates and removes them when their idle TTL runs out.

There are two places, and no routing flag between them (docs/labs/PLAN.md §4): build in the workspace (file_system, execute) and run the system under test in a lab. Labs vanish, so recipes and results must end up in the workspace (lab spec, lab get).

Configuration and visibility

  • --labs-host (env GHOST_LABS_HOST): the service's host:port. Unset means the tool is not advertised.
  • --labs-key-file (env GHOST_LABS_KEY_FILE, default ~/Data/AI/.ghost_labs_key, mode 0600): the file holding the API key, which is a copy of the labs host's /etc/ghost-labs/api_key. The key itself is never an argument, because args are recorded in last_config.json.
  • labs_configured(context) requires a host and a non-empty key file. Only real strings count (a mocked args is "unset"). Visibility depends on configuration only. If the host is down, the tool stays listed and answers labs_unreachable: changing the schema would re-prefill the cached head.
  • At boot, one line is logged in the background: host, version, ok, lab count and RAM. A host that is set but has no key logs a warning that the tool is hidden. A host that cannot be reached logs a warning that the tool stays listed (start_labs_boot_line; the task never raises). The system ready banner waits for this line for at most 12 s (main._wait_boot_lines, §4SY), so the banner follows it unless the host takes longer than that.

Any action except templates, create and list needs a lab_id that matches lab_[0-9a-f]{8}. Every action that names a member (exec put get member logs http) needs a member that matches the service's own name rule, ^[a-z][a-z0-9-]{0,30}$. Anything else is refused before a request. Both values go into URL paths. Review r1 CRIT: a raw member="../app/stop#" became POST /v1/labs/<id>/app/stop, a kept app's owner-only route. op is one of a fixed list. extend needs ttl_idle_s.

Read actions (READ_ACTIONS: templates list status logs http spec) stay open on a status question while work is live (agent._lab_is_read_call, at the _WORK_TOOLS refusal). In the loop's is_mutating reading they are not mutating (a duplicate read in one batch may be collapsed), and a successful read does not reset the pre-flight repeat guard; every other action does (_call_mutated_world). A dropped read is not reported as unapplied work. The other actions are work.

Batch order: lab calls run in the batch's concurrent, stoppable phase (a stop cancels a running exec and closes a waiting call unstarted), with written order kept only where one call depends on another (agent._batch_call_depends, wired by agent._wire_batch_waits; reviews r3–r6):

  • a put or get waits for an earlier execute (build, then upload; rm -rf out/, then fetch into it);
  • an execute waits for an earlier execute, lab get or lab put (a rebuild after put app.tgz cannot change the file mid-upload);
  • put/get calls keep their order across labs: get A dump.sql then put B dump.sql restores the new dump, not a stale one;
  • calls on the same lab keep their order (put run.sh → exec bash run.sh → get report.xml);
  • a list waits for any earlier changing lab call;
  • a create waits only for an earlier destroy (the room it frees — and so also for whatever that destroy waited on, such as an exec on the same lab); two creates (pg16 beside pg18) run side by side, and the host refuses one that does not fit; no call that names a lab waits for it (none can name the lab it makes), so an exec on another lab never waits out a readiness poll; a later list does wait for it;
  • calls on different labs otherwise run side by side.

Known gap, same as execute: file_system calls always run first, so a file_system read of a file a lab get fetches in the same batch reads the old file — read it next turn.

Failure accounting (review r3): a failing exec (non-zero exit) does not count as changing anything, so the repeat guard sees the same failure twice; an exec resets the guard only when its command changes things (the same test as execute); not_ready counts as in flux only while the member is coming up (an exited member stays not-ready until started); a get with no answer is FAILED (nothing was written to the workspace); "no answer" is not evidence; a lab listing retires an expired or host-changed lab quietly, and a later call on it says it is gone rather than "destroyed by expired". The "has no route" note on execute appears only when the command tries to reach a lab id over the network, never on a refusal. A stored "no exit code" row is unresolved for the offline readers too (r4). When a lab action is dropped at the finish line, the note says only the results shown above happened, and names any file change that did land (r5).

Who is asking: origin and owner

Both come from the request scope (core.request_scope, §4SX B0):

  • Origin is sent as the header X-Labs-Origin: owner → owner, probe → probe, and unattended, leaf or no scope at all → autopilot (fail closed). member is refused before any request: labs are the owner's machines. (Until 2026-11-05 a replay origin was refused here too; that origin was removed with the failure replay, §4SZ.) The service enforces its own rules per origin, for example "autopilot creates disposable labs only".
  • Owner is project:<id> when the request has a project, otherwise conversation:<key>. list filters by owner unless all_owners is set.

The exec result

[lab_3f2a9c01/db exit=0 0.4s]
EXIT CODE: 0
STDOUT:
PostgreSQL 18.1 …
  • The literal EXIT CODE: n line sits beside the header, because the outcome and claim parsers read that line. A non-zero code is failed (lab_exit_nonzero).
  • A timeout says TIMED OUT and carries no exit code (lab_timed_out).
  • Each stream keeps its last 6 KB, with a note saying how much was cut. A stream the service had already cut says so too. Output is capped here and is never exempted from the tool-output shield. Both streams together stay under the loop's context shield (16,000 chars). Above it the shield summarises from the first 15,000 chars and would lose stderr and the exit line (review r2). If a result is ever cut later anyway, the loop re-adds the EXIT CODE line for lab as for execute.
  • The timeout is clamped to the turn: whatever the request (or the leaf it runs in) has left, minus 60 s. The time comes from the deadline in force (utils.logging.request_remaining_s), else the coding executor's ceiling (_request_left_s), and never past leaf_deadline_context. A lab run earns no extension. The result says "timeout cut to N s". With under 5 s left, nothing runs (lab_no_time).
  • Every exec is appended to <memory_dir>/lab_transcripts/<owner>/<lab_id>.jsonl: command, exit code, timed_out, duration and the last 2 KB of each stream. A later task gate reads these.
  • When the labs host reports no exit code (and no timeout), the result is unresolved (lab_no_exit_code). It never prints EXIT CODE: None.
  • For the loop, only an exec result is program output (strikes.is_program_output, which keys on the exec header). Its last failure-word line is its error line, as for execute, and the evidence digest takes its tail. logs, status, http and spec return content: a Postgres log's ERROR: relation … does not exist is the log's subject, not a failed call (review r1, the §4KT class).

Errors

A service error is shown as LAB ERROR (<code>): <message>, followed by HINT: <hint> when the service sent one. Its reason code is lab_<code>. 400, 401, 403 and 404 (and owner_only / bad_request) are rejected; anything else (409, 422, 5xx) is failed. not_ready and busy are booked as a lab in flux (world_changed), so the pre-flight repeat guard never freezes a poll on a starting lab; so is an http probe that got no answer yet.

  • unknown_lab is enriched from the inventory: when the lab was destroyed and by whom, or that it expired. It always adds "create a new lab instead of retrying this id".
  • The service's extra fields are shown under the message: members, live_labs, templates, needed_mb, available_mb, state, field. A FastAPI body ({"detail": …}) shows its detail.
  • A failed connect becomes labs_unreachable (LabsUnreachable). The result names the configured host and says nothing ran there, not to loop, and not to fall back to the workspace.
  • Offline readers judge a stored lab row the same way (outcome_heuristics._lab_result_failed, also used by the evidence gate). A LAB ERROR (…) head is a failure, except no_answer. An exec is decided by its exit line or TIMED OUT header. Every other action is content (review r2).
  • A request that was sent and got no answer (a read timeout or a dropped connection) is no_answer (LabsNoAnswer). For a work action it is unresolved. For a read action, and for get (the workspace file is written only after an answer), it is failed, which is retryable and changed nothing. destroy's own pre-read getting no answer is reported as a read, because nothing was deleted. The result says what may have happened: for create, "the lab may have been created — run lab list before creating another"; for exec, "the command may have run". The service builds a lab even with wait:false, after a Tor wait of up to 120 s, so this is a real case after a host restart (review r1).

Inventory (memory/lab_inventory.py)

lab_inventory.db under the memory dir holds one row per lab the agent created: lab_id, owner, origin, template, label, purpose, host_id, created_at, destroyed_at, destroyed_by. It stores ids, never URLs. Rows destroyed more than 30 days ago are pruned on the next create. Every method swallows its own errors, so the tool works even when the inventory is unavailable. inventory_for(context) keeps one instance per memory dir.

Kept machines 2026-11-04 §4SX D3

A lab made inside a project can be kept: it stays up, gets a stable URL and runs one app. The actions are keep, deploy, rehearse, switch, rollback, backup, backups (read only), restore and app (with op start|stop|restart). No new schema fields: the arguments go in params.

  • Who may use them (_kept_refusal): the owner, plus a probe. Unattended, leaf and autopilot work never reaches them, and members do not have the tool at all. The host decides the probe tier: a probe may act only on a lab whose stored origin is probe (may_touch_kept, host labs.py). A probe's kept lab retires after 24 h.
  • keep needs params.app {name, member, port[, cmd]}. The tool reads the lab first and refuses a lab that is not owned by a project ("create the lab there first"). The lineage is always the project id: params.lineage is refused. The tool also refuses params.secret_values, since a secret's value must never pass through the model; only the names go in (params.secrets). It refuses an app name that a non-app run of the project already uses. When it succeeds, it records one app run per lineage/app (_record_app_run), and a second version of the same app adds no new row: it becomes the STAGED next version.
  • deploy sends params.folder (a /workspace/… path that must be inside the workspace) as a gzip tar (tar_folder). The tar is built with os.fwalk(follow_symlinks=False) and O_NOFOLLOW opens, so no symlink is followed, not even a symlinked child of the root. .env* files and DEPLOY_EXCLUDE directories (.git, node_modules, caches, venvs) are skipped. The limit is DEPLOY_MAX_BYTES (20 MB). Skipped links are named in the result. requirements {pip, apt} and data_seed pass through. A deploy whose app is not up afterwards is LAB ERROR (app_not_up). If the host does not answer, the outcome is UNKNOWN (unresolved), never a failure.
  • switch (params.from_lab) moves the stable URL to the staged version. A failed probe reverses it: LAB ERROR (switch_failed), "the old version serves again". rollback (optional restore_snapshot) moves the URL back within the rollback window.
  • backup / backups / restore (backup_id; the host takes a pre-restore backup first). rehearse runs a twin and probes it (LAB ERROR (rehearsal_failed)).
  • Every failure text begins with LAB ERROR (, so stored history reads it as a failure.
  • Secrets: values go only through the operator route PUT /api/operator/labs/{lab_id}/secrets (X-Ghost-Key, body {secret_values}, origin probe if the probe header is present). It answers names only and never logs a value.
  • Destroying a kept lab ends its app run (_end_app_runs) once no kept lab of the lineage is left.

Code review r1 (13 findings: 3 MAJOR, 10 MINOR — all fixed)

  • MAJOR, probe takeover. A probe could make a lab in the owner's project, keep it in the owner's lineage, and switch the owner's app to its code. The host now refuses a non-owner keep when any kept lab of the lineage is not the caller's own kind. switch checks from_lab and rollback checks switched_from. The agent lets a probe use kept actions only in a project a probe created (probe_created).
  • MAJOR, a probe fixture became permanent. A switch or rollback cleared the 24 h retire date. _live_retire now keeps it for probe labs. When a probe kept lab retires, the reaper removes its lease, Service, data and (for the last version) its lineage's secrets (retire_probe_lab).
  • MAJOR, a lost keep answer left the app unknown to run, the release gate and the down notice. A keep of an already-kept lab records its row. A keep with no answer re-reads the lab and records the row if the keep landed. The sweep adopts kept project labs that have no row (each lab is read once per process).
  • Tar: the folder is opened component by component from the workspace root (a swapped parent cannot redirect the walk). Files are opened with O_NONBLOCK and checked with fstat (a FIFO cannot hang the walk). An entry that vanishes mid-walk is skipped.
  • lab destroy of a kept lab sends include_kept, and sends drop_data only for the last version of the lineage. A project delete destroys the version holding the data last (host summary app_mounted).
  • Down notice: also for "no version serves" and for a host restarting seen twice. A probe's app never pages the owner.
  • A long kept action needs at least 75 s of turn time (otherwise no_time, and nothing is sent), and the whole call is bounded. run app ops with the host unreachable return RUN ERROR. params.secrets must be a list of names. An execute after a lab deploy in one batch waits for it. A keep whose first read gets no answer says nothing changed.

Review r2 of the fixes

  • A probe keeps only a lab of the probe project in focus.
  • Too little turn time is always an outcome (lab_no_time), never a crash, and this now covers backup too.
  • Host reaper: an exception on one lab never stops the tick. A probe's kept fixture retires without a final backup (a failing backup wedged the reaper), and its data, lease, Service and secrets go with it.

Walls

  • Workspace and browser cannot reach the labs host (UNIFIED §12 finding 8a). Before it runs, the registry's execute or browser refuses a call whose arguments name the configured host (lab_reach_refusal, lab_host_from_workspace). An IP matches anywhere. A host name matches only in a network shape (//name, @name, name:port), because a MagicDNS name is also an ordinary word (review r1). Other names for the same machine are not known here. An execute whose arguments name a lab id still runs, and its result gets a note: the command ran in the workspace, which has no route to the lab, so use lab exec (with_lab_id_note; the outcome is kept). The note avoids failure words, because it rides on successful execute output, which the loop scans for them (review r2: "cannot" made every exit-0 command that named a lab id a same-error strike).
  • No composed addresses. The only host-derived URL is the configured API base. Member URLs come from the API. A test fails if src/ contains a literal of today's hosts.
  • The key is redacted by value (distill.redact._labs_key_rule, read from GHOST_LABS_KEY_FILE or the default path) in every stored text, like the master key. parse_args exports the resolved --labs-key-file into GHOST_LABS_KEY_FILE, so a key file named only on the command line is redacted too (review r1).
  • Egress: lab is code (memory.egress): OUTBOUND_TOOLS["lab"] = "url_literals" and it is in CODE_TOOLS. The owner's identifiers inside URLs are scrubbed. After outside content, a command that would send uploads or memory files is refused, and so is a lab put of such a file: the put is itself the network step.
  • Outside content (utils.provenance.is_untrusted_source): an exec whose command fetches (curl, wget, git clone …), every http answer and every get arm the request's outside-content rules, as an execute curl does. status, list, logs and spec are the labs host's own records (review r2).
  • Probes destroy only their own labs. The service restricts only autopilot, so the tool refuses a probe-origin destroy of another owner's lab.
  • Replays cannot call it (isolation.REPLAY_FORBIDDEN_TOOLS), and their args copy has labs_host cleared. Members do not get it (_MEMBER_ALLOWED_TOOLS), and leaves do not get it in Phase B. (Composed macros could not use it as a step; the macro engine was removed in §4TA.)
  • No proxy, ever: the labs client is built with proxy=None and trust_env=False. The key goes only to a loopback, tailnet or private IP literal or a bare (dotless) name; anything else is refused before a request is built (key_refusal, see §4UD). Configure the labs host by its tailnet IP or its bare MagicDNS name.

End-to-end review r11 2026-11-05 §4SX-u

  • put/get never follow a link. The file is opened component by component from the workspace root with O_NOFOLLOW (_read_inside, file_system.write_bytes_nofollow_rel). A link planted during the 120 s host call wrote lab bytes onto the Mac, and a put could send a host file to a lab.
  • lab list asks before it retires. A live row the host leaves out is asked about (_settle_unlisted: GET, then the leftovers-only DELETE), and retired only when the host says it is gone with nothing left. A row made on another labs host, or seen while /v1/health does not answer, is shown and never retired, so project teardown still counts it. Only the owner's own lab destroy closes such a record, and the reply says nothing was deleted there.
  • A 404 is not "destroyed" for another host's lab (lab_on_other_host): the unknown_lab text names the host it was made on. A run on it is unknown, not lost, and its stop is FAILED.
  • Batch order: put/get/deploy move workspace files in written order across labs. Lineage actions (keep, deploy, rehearse, switch, rollback, restore, destroy) of two labs run in order (two destroys may still run side by side). switch B from_lab=A follows a call on A.
  • Walls: autopilot is refused everything but status on a KEPT lab, even its own project's (exec, put, get, logs, http). A probe touches only labs it made, for every action that names a lab. An ownership check that is not 200/404 says so, never "belongs to someone else".
  • Truthful texts: a destroy whose status check got no answer says nothing was deleted. A lab gone while starting is create_failed, not "expired". Evicted labs are recorded destroyed, and by whom. A kept destroy with leftovers ends its app runs.

That includes /etc/passwd, which becomes <project>/etc/passwd. Every reply shows where the file landed (shown_path, /workspace/…) and never echoes the spelling given (r15). .. out of the workspace is refused. An unattended build moves files only inside its own project. A deleted project's folder is never recreated, and a released project's is never written.

Review §4UD 2026-11-11 §4UD

An independent review of labs, the lab tool and the run registry: 4 MAJOR, 14 MINOR, 4 gaps. What changed, by mechanism.

The lab lock and a running command (F1)

A foreground exec held the lab's lock for its whole run, so a destroy or a member op answered busy for as long as the command ran. A leaf whose last exec was still running lost its leaf-end destroy and kept the lab for up to two hours. The host's lock (ghost_labs.labs.LabLock) now has two holder kinds: a state change, and a running command. An exec takes the lock, checks the member, then turns its hold into a "command running" mark.

Runs on a lab (F3, F5, F10, F11, G1)

  • $PORT: run start and restart of a lab server send env: {"PORT": port}. After LAB_SERVER_SETTLE_S (1.5 s) the port is asked once through /http. An answer gives [run x started …] Port N answers. No answer with the process running gives [run x launched …] NOT ANSWERING YET and one instruction: read the logs once. A process that already ended is a FAILED start with its output.
  • Lifetime: a lab job keeps timeout --foreground -k 30 2700. A lab server has no wrap: it runs until run stop or until its lab goes.
  • run url of a lab server reads the member's published ports from the lab detail and returns the port's URL, or "not published".
  • Expiry in the records: the lab inventory row stores expires_hard (the host's max_expires_at, or 72 h from create for a host that does not send it; cleared by lab keep). A lab run's row stores meta.expires_at. The briefing's RUNNING block marks a lab or a lab run past it ("not checked") with no host call. The mark never closes a row.
  • Output: a lab run's output is the last 6 KB of /var/log/lab/jobs/<job>.log. When that cut it, logs and collect say so and name the file. When the host answers unknown_lab, logs is refused with "its lab was destroyed" and collect carries the same note. The probe's status code decides this, never result text.

Across conversations (F4)

run status all=true lists every owner's live rows from the local registry, unprobed. run stop name=run_xxxxxxxx stops that row whoever owns it. Both need the owner's own turn (runs._owner_turn: origin owner); a member, a probe, an autopilot build and scheduled work are refused. The run id reaches across owners for stop only; logs, restart, collect and url stay by name. Nothing automatic ends a conversation's workspace server: a sweep by age was built and removed in the same review, because age from the start says nothing about use. In the all-owners view such a server older than OLD_CONV_SERVER_S (24 h) carries its age and the stop command.

One rule, one place

  • Batch order (F9): tools/labs.LINEAGE_ACTIONS = the kept actions that change something, plus destroy. core/agent.py imports it for both of its sets, so app and backup are ordered like the rest. Every run call waits behind every earlier lineage action in the batch, and a lineage action behind every earlier changing run: a run cannot be told from the kept app or from another version of its lineage. ORDER_CLASSES names a class for every action; a test fails when the schema has an action with no class, and another checks the whole action × action table.
  • Kept reads (F12): labs.kept_touch_refusal(origin, action) answers for lab logs and for run logs of an app run: autopilot reads status and address only. The host refuses logs, files, pages, screenshots and job answers (they carry output) of a kept lab for a caller that may not touch it; the agent turns that 403 into the same refusal for run logs and run collect.
  • Data of a kept lab (F13): labs.kept_destroy_params is the only code that asks for drop_data; the lab tool and project teardown call it. A host that names drop_data_guard in /v1/health is always asked, and keeps the volumes itself, under its app lock, while another kept version of the app exists. For an older host the list check stays.
  • The key (F14): labs.key_refusal, called in _call, accepts only an http(s) URL (the scheme compares case-insensitively) whose host is an IP literal in its canonical form inside an allow-list (_KEY_NETS: 127/8, 10/8, 172.16/12, 192.168/16, 100.64/10, ::1, fc00::/7) or a bare name matching ^[a-z][a-z0-9-]*$ that is not a scheme word (http, https). The URL is matched against one exact shape first (_KEY_URL_RE: http(s)://HOST[:PORT][/path], port 1–65535); the configured value is host[:port] or http://host[:port] and nothing is repaired. Refused: user:pw@host, HTTP:/10.0.0.1 and http:10.0.0.1 (a lenient parser read a host named "http"), link-local addresses (169.254/16 with the cloud metadata address, fe80::/10), dotted names, integer and hex addresses, and IPv6 forms that carry a public IPv4 address (6to4, NAT64, IPv4-mapped). A refused host is a configuration error: config_refusal logs one WARNING line per process, lab and run answer labs_key_refused (REJECTED), and destroy_leaf_labs sends nothing. The leaf sweep and the boot pass still stop the leaf's WORKSPACE runs (they need no labs host); the leaf's lab work is left, said once after SWEEP_MAX_TRIES passes. The client gets proxy=None, trust_env=False and follows no redirect.
  • Holds (F15): lab_tor_unavailable, lab_firewall_missing, lab_ports_exhausted and a create's lab_busy are holds: labs_not_ready lifts on a healthy /v1/health at least 180 s later, and labs_no_tor (from tor_unavailable) also needs tor: ok. needed_mb is a field of the refusal (LabReply.needed_mb), not parsed from text.

Smaller changes

  • lab status of a kept lab prints the app: state, URL, last error, whether this version serves or is staged, the version it was switched in from. The no-answer hints after keep, deploy and switch point there.
  • Times on another day print as YYYY-MM-DD HH:MM (_when).
  • ttl_idle_s that is not a whole number of seconds is refused with the value given, before any host call. A value above the lab's maximum is cut by the host on create as on extend; the result says "capped at N s".
  • lab http with no answer adds one line: bind to 0.0.0.0, and when the host saw a listener on 127.0.0.1 only, it says that waiting will not help and the result is booked as unchanged, so the repeat guard can stop a retry. An answer cut at the host's 15 s deadline is marked.

Old agent, new host and the reverse

Every new request field is optional and every new answer field is read with a default. A new agent on an old host: no features, so the list check decides drop_data; no max_expires_at, so 72 h; no output_truncated/log_path, so a tail that fills the cap counts as cut and the fixed path is named; a create above the maximum is still refused by the host; a destroy behind a running exec still answers busy and is asked again by the leaf sweep.

Cancel a running exec (F-B)

lab cancel lab_id=… [member=…] posts to the host's /v1/labs/{id}/exec/cancel. The host keeps a list of the foreground commands running on each lab (member, origin, tag, start time). A cancel only marks the commands the caller may end; each command's own exec thread then kills its process group by its pid file, looks whether the group is gone (kill -0, up to 2 s), and answers cancelled: true, killed: true|false, no exit code. The group is not signalled when the member was restarted since the command began (the job rule: a pid file from an earlier start names nobody). A cancel takes no lab lock; it waits up to 8 s for the commands it marked to say what became of them.

Folders (F-C)

lab put with a workspace folder as sandbox_path packs it with the deploy walk (tar_folder: directory file descriptors, no link followed, links/devices/pipes skipped and named, .env* and DEPLOY_EXCLUDE never sent) and sends it to PUT /v1/labs/{id}/tree. lab get asks the file route first; when the host answers kind: "directory" it asks GET /tree and writes every file under sandbox_path. The host sends regular files and folders; a hard link to a file it already sent from the same folder arrives as a copy of that file (Docker sends one name of a hard-linked pair as the file and the other as a link; each copy counts toward the content the host builds, at most file_max_bytes (20 MB, what the agent accepts), so many links to one large file are refused rather than built in memory), and symlinks, other links, devices and pipes are listed as skipped.

One write check, one writer. labs.write_refusal(context, path) is the per-path rule for every workspace write of the lab tool: inside the workspace; an unattended build only inside its project; never into a RELEASED project (file_system._released_write_block); never under a .git directory in any case or Unicode form (the rule file_system applies inline, compared with the same _fold). _ws_write and _ws_mkdir ask it and then open every component O_NOFOLLOW from the workspace root; the single-file get, screenshot and the folder get write through them and nothing else in tools/labs.py writes a workspace file (an AST walk over the module pins the list of writing calls by function). A folder get asks the check for every entry's final path before the first write: one refusal refuses the whole archive. Before that, the folder check ran once on the destination folder and the lab's entry names chose the real paths.
