core / model_profile.py

One profile per model: the sampler values, the thinking-off switch, the effort levels, the tokenizer and the reply room a model needs, in one place. Callers say what they want; the send words it for the model that serves the call.

Why it exists

The agent was built around Qwen3.8-27B. Its card's sampler values were constants in core/agent.py, its effort sentence a pattern in core/effort.py, its tokenizer a repository name in utils/token_counter.py, and enable_thinking was written at 32 call sites in 15 files. A trial of a model with another template (2026-11-22) ran with all of that still in force: side calls kept reasoning because the template has no enable_thinking, and the token counter was about 31% low because it counted with another vocabulary (that model needs about 45% more tokens for the same text). Nothing said so.

§4VM (2026-11-26) moves those facts into a ModelProfile. The built-in qwen38 profile carries the old values, so a Qwen main model receives the same requests as before.

Adding a model without code

Put a JSON file in system/model_profiles/ under the agent's home ($GHOST_HOME, or ~/ghost_llamacpp when that is unset), or in the directory GHOST_MODEL_PROFILES names. Any *.json entry counts (either case of the suffix; a byte-order mark is accepted). Files are read in name order at start, and again at the next model re-sync after the directory changed (a file added, edited or removed): adding a file for the model the server already runs is enough, within about a minute of the next head warm-up.

A file may start from any profile read before it with "extends"; every other key replaces that profile's value whole. A file with the SAME name as a known profile replaces it: what the file does not say stays as it was, including the match names (a replaced qwen38 is also the default). A file that extends a profile under another name does not inherit match. An entry that cannot be used (not a readable file, not JSON, larger than 256 KB, an unknown key, a value the checks below refuse) is skipped with one warning that names it and says why; the built-ins always load.

{
  "name": "example-9",
  "match": ["example-9"],
  "sampling": {"default": {"temperature": 0.7, "top_p": 0.8},
               "coding":  {"temperature": 0.2}},
  "think_off": {"reasoning_effort": "none"},
  "effort": {"levels": {"low": "low", "medium": "medium", "xhigh": "max"},
             "sentence_re": "\\[effort=(low|medium|max)\\]",
             "unmarked": "medium"},
  "tokenizer": null,
  "reply_reserve": 8000
}

Only sampler settings are accepted under sampling (SAMPLER_KEYS: temperature, top_p, top_k, min_p, the penalties, DRY, XTC, mirostat and the like), and only as numbers. A file cannot set messages, model or max_tokens. Also refused: a number that is not finite, a match piece shorter than three characters (a is in "Nova"), a think_off that sets enable_thinking to anything but false, a level pattern longer than 300 characters or without exactly one group, two effort levels given the same word (leave out the level the model does not have: the agent then does not send it and the template's default applies), and a tokenizer that is not {"repo": "org/name"} (never a path; the cache directory is the agent's choice, system/tokenizers-<name>).

Which profile the main model gets

  1. GHOST_MODEL_PROFILE=<name> names one: the operator's word. An unknown name is logged and ignored.
  2. The running server's model file (/props, model_path) fits a profile. Only the file's name is read, not its folder's.
  3. --model fits a profile.
  4. Otherwise qwen38. When the server named a model that fits no profile, one warning says so and names the directory a profile file goes in.

Among several fits the longest matching piece wins (qwen4 over qwen); at the same length an operator's file wins over a built-in, and between two operator files the earlier file name.

core/model_boot.py runs this at start and again from every head warm-up, loud or quiet (GhostAgent._model_resync, at most once a minute and for at most 30 seconds), so a model server restarted on another model is followed without restarting the agent. What a re-sync does depends on what the server says:

A re-sync that fails half-way puts the profile and the token counting back as they were and is tried again a minute later. A boot that fails still ends on the default profile with a tokenizer when one can be loaded and a budget that is not zero, and the first re-sync does the whole job again.

Intent in, the model's words out

Code that builds a request writes the agent's own two template switches: no_think_kwargs() for "do not reason" and a level from EFFORT_LEVELS under reasoning_effort. shape(payload, profile) rewrites them for the model:

thinking offunchangedreasoning_effort: "none"
effort xhighunchangedreasoning_effort: "max"
thinking off and a levelunchangedreasoning_effort: "none" (off wins)
one of the agent's levels the model has no word for—not sent: the template's own default applies

For a model whose words are the agent's, shape returns the caller's own object, so the request body cannot differ from before. Otherwise it returns a copy; the caller's payload is never edited.

core/llm.py calls it at every send: the four node pools through LLMClient._for_node with the profile of the model that node runs, and the main call and the main stream through shape_main. A node's profile: a node that is the main server itself (the vision pool points at it; compared by host, port and path, so localhost, a missing scheme or a trailing /v1 make no difference, while two paths on one port are two servers) gets the main profile; otherwise the model file its own /props named in the capacity probe; only when that fits no profile, its configured label; a node nothing is known about is sent the request as written. The places that post to a server without the client do the same: the head render and the members' head warm-up in core/agent.py, the effort lookup in core/effort.py, the direct call in api/routes.py, and the audio node's request in memory/audio_ingest.py (with the profile of the model that node's /props named). A test scans the package for a chat post that is not shaped.

Dialect: history, thinking tags, the soft switch (§4VO)

Three things the turn loop did in Qwen's way for every model. A profile's dialect now says what a model wants; the defaults are Qwen's and change nothing for it.

SettingQwen (default)A model with its own formats (Inkling 2)
history: how the model is shown its earlier tool calls and their resultstext: the call as <tool_call> text inside the assistant message, the result as a user message in <tool_response>. For Qwen that is its template's own wire form.native: structured tool_calls and role: tool messages; the server's template renders them in the model's own format. Only on the native-tools path.

Why history matters: on 2026-11-26, with Inkling 2 Mini as the main model, 10 of 45 tool calls arrived as Qwen-style text instead of native calls, starting at the third step of multi-step turns. The prompt does not teach that form on the native path; the history did, by showing the model two earlier calls written that way. In native form a past call is rendered by Inkling's template as its own content_invoke_tool_json message and a result as its own tool message (checked on the running server's /apply-template).

Details of the native rows (core/agent.py _native_history_row): a call the model wrote as text is removed from the assistant text, so it never reads the foreign form back as its own; the parse-error bookkeeping entry is not sent as a call; arguments reach the server as the text of a JSON object a strict parser reads: they are parsed and written again, and what is not such an object (a cut call, a list, NaN, a lone surrogate, nesting past any parser) goes as {"raw": "…"} — the server parses arguments before the template sees them and answers 500 to the whole request, on every later turn, for text it cannot read; prose that only mentions <tool_call> beside a real call is kept; a tool result keeps the same defusing of hostile text as before, and a channel member's caveat reaches it as a tool row. The same form is used for the receipts of a forced final answer and for the result kept by an overflow recovery. After a malformed call, such a model is told to make a structured call, not shown Qwen's text form.

Token counts: the model file's own tokenizer

A GGUF carries its whole vocabulary and merge rules. When the model file the server names is readable by the agent (the server on the same machine), utils/gguf_tokenizer.py builds the tokenizer from it and the agent counts with that: exact for whatever model is loaded, no download.

It is adopted only when its token ids equal the server's own (/tokenize, which touches no slot) on every one of fifteen check strings: prose, a tool schema, code, numbers and paths, CRLF and tabs, apostrophes, decomposed accents, Greek, Hindi, Thai, Arabic, Hebrew, Chinese, Japanese, Korean, full-width forms, emoji, zero-width characters, identifiers that are tokens themselves, camel-case words with long numbers, all-caps words with accented capitals, and Chinese words that are tokens only as a whole. Three things the file does not say are settled by that check: how text is split before the merges (three rules are known, SPLIT_RULES: letters with their combining marks as one word; letters alone; the GPT-4o rule, which also splits where the case changes and takes digits three at a time — in llama.cpp's own rewrite of it, where only ASCII letters have a case; the regex in the model's tokenizer.json differs on all-caps words with a non-ASCII capital and undercounted "MÜNCHEN CAFÉS" text by up to 11% until a reviewer found it against llama-tokenize), whether a piece that is itself a token is emitted whole without merging, and that the server does not normalise Unicode although the file's metadata says it does. What llama.cpp does for a vocabulary name is tried first (SETTINGS_FOR_PRE), then every other combination.

Checked on two models: Qwen3.8 (qwen35: marks, merged) against a live server, and Inkling 2 Mini (inkling2: GPT-4o rule, whole tokens) against the build's own llama-tokenize on the model file, 31 texts and 21,557 tokens with identical ids; for each model exactly one combination passes the fifteen check strings, and it is the one tried first. A reviewer compared 3.4 million tokens of real files for Inkling and 2.8 million for Qwen, 10,000 random strings per model and every code point: identical, apart from about 4,400 code points the tokenizer library classifies by a newer Unicode table than llama's (unassigned in Unicode 13; no effect on text in use).

The kept file's name includes the builder's version (BUILDER_VERSION): after a change of the rules a file built by older code is not loaded again — it would be re-checked only against the check strings, which a wrong tokenizer once passed. To check a new vocabulary or a changed rule against llama.cpp itself, run tests/test_4vm_model_file_tokenizer.py with GHOST_TOKENIZER_REF_BIN (a llama-tokenize binary; with -ngl 0 -c 64 it loads no weights) and GHOST_TOKENIZER_REF_MODELS (model files) set; without them that one test is skipped, and every other test takes its reference from the builder itself.

  • Reading the vocabulary of a 17 GB model takes about 4 seconds, once. The built tokenizer is kept in system/tokenizers-gguf/ (about 20 MB, the newest three), reloads in 0.2 s and is checked against the server again each time.
  • Another model file under the same profile gets its own tokenizer. A model file replaced in place under the SAME path gets a new one at the next agent start (the kept file is keyed on path, size and change time), not while the agent runs.
  • When it cannot be had (the file is on another machine, the gguf package is missing, the vocabulary is not byte-pair, the server's /tokenize does not answer, or no known split rule reproduces the server's ids) the profile's tokenizer is loaded instead. Only the last case is a warning; the others are logged at INFO. The boot line and /api/health (tokens.exact) say which tokenizer is counting.
  • GHOST_GGUF_TOKENIZER=0 switches it off.

Why it was built: the agent counted with Qwen/Qwen3-30B-A3B, a 151,669-token vocabulary, while the Qwen3.8 model the server ran has 248,320 tokens. The two share no ids; the counts agreed only roughly because both are byte-pair vocabularies. Measured 2026-11-26 against the live server: the old tokenizer was 0.6% low on a prompt, 2% on prose, 4% on code and 16% on indented JSON (the older vocabulary has merged tokens for punctuation followed by a line end that the newer one lacks). Built from the model file, the count matched the server's on 142,648 tokens of source, docs and JSON and on 40 edge strings.

The check against the server

Whatever tokenizer is in use, token_counter.calibrate sends one fixed sample (prose, a tool schema, code, a list with paths and numbers; 1,350 characters) to /tokenize and compares:

  • The model file's tokenizer: the counts are equal and exact is reported.
  • No tokenizer loaded: the estimate becomes the server's characters-per-token figure instead of the fixed 4.
  • A fallback tokenizer within 3% of the server: left alone; the measured difference is reported as drift.
  • A fallback tokenizer further off: its counts are multiplied by the measured ratio and one warning says the tokenizer is not this model's.
  • An answer no tokenizer gives (under 1 or over 12 characters per token, a ratio outside 0.5 to 2): not believed, said once, counts stay as they were.

The result is shown at start and in /api/health (model_profile.tokens).

The context budget

context_budget(flag, n_ctx, profile): --max-context is the ceiling. When the server's window minus the reply reserve (at most a quarter of the window) is smaller, the budget is lowered to that and a warning says so; it is never raised above the flag. --max-context 0 takes the budget from the server (65,536 when the server does not answer at start). A window under 2,048 or over 16,777,216 tokens is treated as not given, and a server that gives none leaves the budget where it is. The production pair, a 196,608-token window and --max-context 174000, is left as it is.

Limits

  • Still in Qwen's words for every model: two lines of the system prompt and the persona that mention <tool_response> output; the final-generation directive's "do not emit any <tool_call> blocks"; some messages the agent sends after a failure (a cut reply, a loop, the watchdog note) that name <tool_call> or </think>; the lazy tool grammar, which triggers on <tool_call> (only used with native tools off); the perfect-it follow-up (off by default), which builds its own history. A model's earlier reasoning is not sent back to it, though some templates (Inkling 2) could take it.
  • The re-sync runs when a head warm-up runs. The first request after a model server restart can still be served on the old profile and budget, and with the re-warm loop switched off (GHOST_MAIN_PREFIX_REWARM_S=0) there is no re-sync after start.
  • A node's first requests, before its capacity probe has read /props, are worded by its label only.
  • eval/verify_bench.py posts the verifier's requests to the judge it is pointed at as written: a judge on another model is benched in the agent's words.
  • The catch-all proxy route forwards an outside client's request body untouched.
  • The server's timeouts are per read, not in total; at start a server that drips bytes can hold the boot.
  • A model the server runs that fits no profile gets qwen38, not generic, because every main model this agent has run is a Qwen. Set GHOST_MODEL_PROFILE=generic for the neutral one.
  • The web menu shows the agent's three effort levels whatever the model calls them. A server default the template writes but that is none of those levels (Inkling 2's own 0.9 when the launcher sets none) is reported as unknown, not as medium.
  • A thinking-off call is booked as the unmarked level (medium). For Qwen that is exact; a template that writes its own text for "off" (Inkling 2 writes 0) renders differently from medium, so the server re-reads from that line on (about 130 tokens on Inkling) while the agent's level bookkeeping sees no change. The saved head is keyed on the rendered text and is never served for the wrong text.
  • The sampler values are the main model's. A side call sets its own temperature and is not changed.
  • With a fallback tokenizer, the 3% band is judged on one sample. Text unlike it (indented JSON) can be further off than the band while the tokenizer is left unscaled.
  • A change of model or window on the main server is noticed at the next head warm-up (the re-warm loop ticks every 10 to 120 seconds), not at once. A NODE's model is read once, at first contact: a node restarted on another model keeps its profile until the agent restarts.
  • GHOST_MODEL_PROFILE names the main model's profile only.
