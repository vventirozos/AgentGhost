interface / externals / image_generation / img_gen_server.py

Model & runtime

  • Qwen-Image-2.1: a 7B single-stream DiT + a Qwen3-VL-8B text encoder + a 16×/64-channel VAE, all quantized — DiT qwen-image-2.1-turbo-Q4_K_M.gguf (4.2 GB; base qwen_image_2.1-Q4_K.gguf until §4OY), encoder Qwen3VL-8B-Instruct-Q4_K_M.gguf (5.0 GB), VAE bf16 (0.7 GB). 9.3 GB of weights on an 8 GB box: they fit only phased (encoder → freed → DiT → VAE).
  • Each request runs sd-cli (stable-diffusion.cpp, CUDA sm_87) as a subprocess with --params-backend disk --max-vram 4.5 --diffusion-fa --vae-tiling; its model manager streams each model from the NVMe file (~2 GB/s, ~5 s per image) and frees it after use. Nothing stays resident between requests, so the node idles at ~50 MB instead of the 3.2 GB the diffusers pipeline pinned.
  • CFG is off by default (guidance_scale 1.0, the model's own default); a negative prompt is only passed when a caller sets guidance > 1, which doubles the runtime. The default negative prompt is empty.
  • Euler sampler with Turbo's fixed 8-sigma schedule (§4OY); before that, sd.cpp picked the resolution-dependent flow schedule.

Tunables (measured, §4JT — base model; Turbo values in the note above)

  • Sizes: default 768×512, per-side cap 768, area budget 768×512 px, sides snapped to /32. At this size one image takes ~3.3 min at 30 steps (768×768 would be ~6.7 min, 1024² ~15 min — the operator chose 768×512).
  • Steps: default 30 for a new image (indistinguishable from 40 on this model at this size), 20 for an edit; floor 15, cap 50 for a new image and MAX_EDIT_STEPS = 30 for an edit (anything higher is reduced); ~6 s per step T2I, ~28 s per step for an edit (CFG's two forwards) plus ~95 s fixed overhead — 654 s measured at 20 steps, 935 s permitted at 30.
  • Queued requests wait up to BUSY_WAIT_TIMEOUT (derived: 1200 − 935 − 30 = 235 s) for the GPU, then 503. A generation is killed after GEN_TIMEOUT_S = 1500 s. Prompts and negative prompts are capped at MAX_PROMPT_CHARS = 8000 (400 above), the body at 24 MB (413, before auth). The response carries seed, width, height and steps as rendered.

Boot & resilience

The port binds in ~1–2 s; readiness is established by a real 1-step 256² preflight generation in a background thread (~20 s including model streaming; measured 13 s and 20 s on restarts), so a node that says ready has proven the binary, the three model files, CUDA and the memory phasing. Requests get a clean 503 until then. A post-restart NvMap-teardown OOM retries up to 5× with 20 s backoff. One dedicated worker thread serialises all generation work.

The Tegra allocator trap. CUDA allocations on the Jetson fail with NvMapMemAllocInternalTagged error 12 while free still shows gigabytes "available", because reclaimable page cache counts as available and NvMap does not reclaim it on demand — and streaming 9 GB of model files is exactly what fills the page cache. Raising vm.min_free_kbytes makes sd-cli's own memory check refuse; a cgroup memory.high throttles the GPU allocations themselves (NvMap pages are charged to the process). What works: the node drops the page cache before each run and a sidecar (sudo -n sh -c 'while kill -0 <pid>; do echo 1 > /proc/sys/vm/drop_caches; sleep 1; done') keeps dropping it every second while sd-cli runs, exiting by itself when the pid is gone. It needs passwordless sudo on the node; without it the node logs a warning and runs unprotected.

Editing with a reference image (§4JV)

reference_images carries base64 PNG/JPEG/WEBP (a data: URI prefix is tolerated). The node validates them before taking the GPU lock — bad base64, a non-image, an oversized file (>12 MB) or too many references are a 400; a node without the vision projector answers 501. Each reference is written to a temp file and passed to sd-cli as -r, together with the Qwen3-VL projector (--llm_vision, mmproj-Qwen3VL-8B-Instruct-Q8_0.gguf, loaded only for edits since it costs encoder-phase memory). The prompt describes the change; the model preserves the rest, including people's identity. With no size requested an edit inherits its reference's shape (PNG IHDR), scaled into the budget and snapped to /32.

An edit needs true CFG, and the node turns it on by itself. Measured 2026-09-22: at the T2I default (guidance_scale 1.0, CFG-free) an edit reproduces its reference and ignores the instruction — three live attempts to change a sign's text, and a separate attempt to change a scene to night, all returned near-copies. At 4.0 the same prompt, seed and steps rendered the new text and left the rest of the scene alone: there is no unconditional branch to steer away from at 1.0, so the instruction has nothing to act through. resolve_guidance therefore returns EDIT_GUIDANCE (4.0) whenever references are present and the caller did not ask for a specific value; an explicit guidance_scale always wins. CFG doubles the work per step, so an edit also defaults to fewer steps (DEFAULT_EDIT_STEPS = 20) — about 11 minutes at 768×512.

Every reference is resized to the geometry the node will render (fit_reference). sd-cli VAE-encodes a reference at its own resolution and those latents join the DiT sequence, so an unresized 4000×3000 upload would push roughly 30× the output's tokens through a box that already peaks at 6.7 GB on a 768×512 edit. The output is capped either way, so a larger reference buys nothing and can only OOM. A reference that already matches passes through untouched; one Pillow cannot read is passed through unchanged so sd-cli fails loudly rather than the node silently editing something else.

Edit quality is seed-dependent, and the old fixed default was a bad draw. The first edits looked visibly worse than their source — softer, haloed, contrast crushed — and the obvious explanation (the 16× VAE encode→decode round trip an edit performs and a plain generation does not) turned out to be wrong. Still true regardless of seed: do not chain edits, since each one is another round trip.

Re-rolling the same seed with a tweaked prompt is not a substitute for an edit: measured on the same bakery→cafe change it renders at full quality in 200 s but produces a different composition (mean absolute pixel difference 30/255), because the prompt change moves the whole sampling trajectory. It is the right call for "another take on this idea"; only an edit keeps the actual picture.

The cap is one reference. A reference's latents join the DiT sequence, so an edit costs about (1 + refs) × a plain generation: measured at 768×512, one reference runs at 14.2 s/step (2.4× plain) with a 6.7 GB peak — ~8 min at 30 steps. Two references would push 4608 tokens through a box where 4096 (the 1024² run) already peaked at 6.7 GB. MAX_REFERENCES is a memory cap, mirrored by the agent tool.

Transparency — not available (measured 2026-09-22)

transparent: true wraps the prompt in the model card's RGBA recipe ("This is an RGBA image with transparency. … The image has alpha channel and the background is transparent."). On the 2026-09-22 sd.cpp build (6dcb5bb) the 4-channel PNG carried noise around opaque (background α≈248) — an fp16 overflow in the Qwen-Image-2.1 VAE (sd.cpp bug #2024, fixed by #2054). Since §4MH the node runs sd.cpp a1ded76 and the alpha decodes: measured 2026-10-07, a red apple on a fully transparent background (57% of pixels α<16, crisp edges). The PNG is returned untouched and the agent now advertises transparent.

Prompt handling

The text encoder is an LLM that reads the prompt as prose, so A1111 attention syntax ((x:1.4), [x]) would enter it as literal characters. The node flattens that syntax to plain words (strip_attention_syntax) in case a user types it; the agent no longer advertises it. Text meant to appear in the image goes in double quotes and renders legibly. Any language works, including Greek. Prompts are used in full — no 77-token truncation.

Auth (2026-07-15). The node binds 0.0.0.0 on the LAN and a generation monopolises the GPU for minutes, so /generate requires the fleet X-Ghost-Key (resolved from GHOST_API_KEY env, else ~/Data/AI/.ghost_api_key, else the server refuses to start — an explicit GHOST_API_KEY='' knowingly disables it on a trusted network). Auth is checked before the readiness gates, so an unauthenticated caller can never probe warmup/GPU state. Monitoring endpoints (/health, /ready) stay open. The agent stamps the key only on its image_gen httpx pool (llama.cpp pools don't check keys). Covered by tests/test_imggen_node_auth.py; the swap itself by tests/test_image_gen_model_swap.py.

Node review 2026-10-14 §4PB

  • References are letterboxed, never stretched. fit_reference scales a reference to fit the render size and pastes it centred on white when the aspects differ. A 960×1264 portrait with a 768×512 edit was drawn from a face stretched 0.76 → 1.5 (the §4JV docstring called that squash out and fixed only the no-size path).
  • The key is checked before the body. The pure-ASGI body-cap middleware answers 401 for /generate and /v1/images/generations before reading a byte; FastAPI used to buffer, JSON-parse and pydantic-validate a 24 MB body before the handler's own check (wrong key + wrong-typed body answered 422). Deploy: scp … ghost:~/Data/AI/ImgGen/server.py + sudo -n systemctl restart ghost-image-node; backup server.pre-4pb.bak.py.
  • Preflight errors. /ready and /generate pass _load_error through _public like /health (configured paths → basenames), and answer 503 while the background preflight is still retrying (_preflight_done; the agent client's 10/35 s warm-up backoff applies to 503), 500 only once every attempt is spent.
  • image_size does not decode pixels. It reads the header size and the EXIF orientation tag (5–8 swap width/height); ImageOps.exif_transpose decoded the whole reference on the event loop, before the GPU lock, concurrently with the running render.
  • Checked and sound (reviewer): client retry policy (4xx and timeouts never re-POST), disconnect cancel (process group kill, lock release), guidance validation and the negative-prompt-only-under-CFG rule, the size ladder, argv-only subprocess, temp-file cleanup, limits agreeing on both ends (8000 chars, 12 MB, one reference), response seed/width/height/steps. Timing table: a queued client gives up at 1200 s only when a slow render follows a late lock; the node kills that render on disconnect.

Node review 2026-09-24 §4KD

Confirmed and fixed (pins in tests/test_4kd_image_pipeline_review.py): negative_prompt was uncapped — under CFG (every edit) it goes through the quadratic attention-syntax parser on the GPU thread with the lock held and no timeout (0.9 s at 16 KB, 36 s at 100 KB, hours at the 24 MB body cap) — same MAX_PROMPT_CHARS 400 now; EXIF orientation was ignored — a phone portrait stored 400×200 with orientation 6 rendered landscape from a sideways reference — image_size and fit_reference transpose first and never pass raw bytes through when a transpose applied (sd-cli's stb decoder ignores EXIF too); a NUL in either prompt and a 20000² decompression bomb reached the GPU lock before failing as a 500 — both are 400s at decode time; any RIFF file passed as WEBP (a WAV reached sd-cli) — bytes 8–12 must say WEBP; negative and one-sided sizes were silently mapped to a legal shape — 400; error bodies (and /health's load_error) carried absolute server paths — basenames only. NOTEs kept: base64 with line breaks is refused; an empty prompt is a 400 now.

A client disconnect now cancels the render (operator request, same day). The render in flight is ONE handle (_RENDER: one GPU, one render at a time): run_sd_cli starts sd-cli in its own session and registers the process; the endpoint arms a fresh render (_arm_render), runs the GPU task and awaits it through _await_render, which polls request.is_disconnected() every second and, when the client is gone, kills the render's whole process group (cancel_current_render → killpg — killing only the leader left a child holding the stdout pipe and communicate() waiting for EOF), waits for the task to unwind so the GPU lock is released in order, logs GEN cancelled after Ns … GPU released and answers 499. A cancel that arrives before the process exists is not lost (the runner re-checks the flag right after Popen); arming clears a stale flag; a test client that cannot answer is_disconnected never cancels by accident. Pins drive a real subprocess (tests/test_4kd_image_pipeline_review.py §5).

Why the first deploy of this did nothing. The live test showed the client leave and the render run on. A 20-line probe under the same uvicorn/starlette proved is_disconnected() works — until a BaseHTTPMiddleware is in the chain, whereupon the endpoint's receive is the middleware's own and http.disconnect never reaches it. The body cap WAS that middleware. It is a pure ASGI middleware now (_BodyCapMiddleware: Content-Length refused before the app, a chunked body counted through a forwarding receive, 413 either way — the same two pins), and the second live test cancelled 1.6 s after the client left: GEN cancelled after 16.6s … GPU released, /ready true immediately.
