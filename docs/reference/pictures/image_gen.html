tools / image_gen.py

Image generation routed to the external GPU node (ghost: Qwen-Image-2.1 via stable-diffusion.cpp since 2026-09-22).

Turbo node (§4OY, 2026-10-14). The node now runs Qwen-Image-2.1-Turbo: one fixed 8-step schedule, CFG-free edits. The tool therefore never sends steps (the schema no longer offers it; a steps the model still emits is dropped), and every timing the model reads — tool description, seed, subjects, the system prompt, the subjects and edit notes — says about 1 minute for a new image and about 2 for an edit or a subjects render (measured ~70 s and ~2 min at 768×512). Older figures below (~3.3 min, ~8 min, 30/20 steps) are the base model's. Pinned in tests/test_image_gen_node_retune.py, tests/test_image_gen.py and tests/test_image_gen_model_swap.py.

Tool: image_generation

Auto-registered when context.llm_client.image_gen_clients exists.

  • Heals missing prompt by checking related kwargs (image, description, subject, text).
  • Never sends steps (§4OY: the Turbo node runs a fixed 8-step schedule; the schema has no such parameter).
  • Passes the requested size THROUGH untouched — the node owns geometry. It searches 246 legal sizes (multiples of 32, as sd.cpp requires for this model, within a 768×512 pixel budget) for the closest match inside a log-space aspect band, so 1920x1080 renders 736x416 (0.5% aspect error) and 2560x1080 renders 768x320 (1.3%). If no size is given the tool sends none and the node uses its default, 768x512. Until 2026-09-22 the tool first snapped to a five-entry ladder (512x768, 576x672, 608x608, 672x576, 768x512) — an SD1.5-era habit from when the node could only scale and clamp. It threw away precision before the node's search ever saw the request: 1920x1080 became 768x512, 15.6% off, and 2560x1080 was 36.7% off. _snap_to_bucket, _NODE_BUCKETS and _DEFAULT_BUCKET are deleted; tests/test_image_gen_model_swap.py and tests/test_image_gen_node_retune.py assert they cannot come back.
  • Passes seed and negative_prompt through when given (a list negative is joined; both are capped at 8000 characters with a note). The negative is read by the node only when a render runs with guidance above 1 — on Turbo that is only the collage ladder's third attempt (§4OZ).
  • Editing (reference_images, one filename; several are joined, see below): resolves the sandbox file the model names in any of the spellings it uses (gen_x.png, /gen_x.png, /sandbox/gen_x.png, the /api/download/… link it was shown), refuses anything outside the sandbox or missing before calling the node, sends it base64, omits the size so the edit keeps the reference's shape, and reads the actual size back from the returned PNG for the SUCCESS note. Synonyms the model hallucinates (reference_image, input_image, source_image, …) are healed. An edit takes about 2 minutes on the Turbo node (§4OY: one fixed 8-step schedule at guidance 1.0 — CFG-free, edits included; the base model needed guidance for edits and took ~8 minutes) and costs some fine detail to the VAE round trip, so the tool result tells the model to re-attempt at most once and never to chain edits.
  • Calls llm_client.generate_image({"prompt", "width", "height", …}); the transport allows 20 minutes — a new image takes ~70 s at 768×512 and an edit or subjects render ~2 minutes; a multi-subject render whose collage check re-renders can take up to three renders (the third at cfg 4, ~2× a render) plus a vision check after each. No tool-level timeout wraps the call (see §4QG for the node's own limits).
  • Decodes base64 PNG, writes to sandbox as gen_UUID.png.
  • Returns a markdown embed with a short alt text (![generated image](/api/download/gen_UUID.png)) — the giant raw prompt is deliberately kept out of the alt text.
  • Instructs the model to follow the embed with one or two short sentences describing what it generated, in its own words, so the user always gets a human-readable caption instead of a bare link.

A real person's likeness comes from pixels (§4JX)

Asked to put the Greek prime minister in space, the agent searched, downloaded a photo into the sandbox, ran vision_analysis describe_picture on it — and then called image_generation with a text prompt and no reference. The node logged refs=0 and returned a generic dark-haired man in an astronaut suit. The model cannot draw a likeness from a name or from a caption, however detailed, unless that person is saturated in its training data.

The cause was the advice, not the model: reference_images was described only as EDIT MODE … change an EXISTING image, so "put this person in space" never read as an edit. The description and the system prompt now state that a specific real person (or product, building, pet) must come from a photo, that a name or description yields a stranger, and that looking at a photo with vision_analysis is not passing it. With the same request afterwards the agent reached for the reference in 13 s (refs=1) and the result is recognisably him. Pinned in tests/test_image_gen_model_swap.py — asserting the claim ("must pass a photo", "never from a name", "generic stranger"), not the topic word, because a first draft of those pins passed against a mutant that replaced the steer with its opposite.

Acquisition was the weak link, and the cause was guessing. In that run the agent never obtained a usable portrait: it hand-built Wikimedia thumbnail URLs, and only some widths are pre-rendered — 800px-… and 640px-… return HTTP 400 while 500px-… returns 200 — so it fell back to screenshotting the Commons page, a 1280×2290 picture of a web page. It was never a Tor or host problem: the URL the page itself declares in og:image fetched 200 over Tor from both thumb. and upload. hosts. Fixed in the browser tool (§4JY): navigate and extract_text now return MAIN_IMAGE, a ready-to-download URL, with MAIN_IMAGE_SOURCE saying whether it came from the site's own og:image or from a rendered-size guess. See browser.

The tool fetches the subjects' photos 2026-10-07 §4MG

What went wrong. Asked for "Alexis Tsipras and Antonis Samaras kissing the socialist kiss", the agent's own thinking said I need to use the image_generation tool with reference images of both politicians … let me first find/download photos — and its next action was a text-only render. Two strangers. On "this is not tsipras or samaras" it guessed Wikimedia URLs (400 ×2), screenshotted the articles, found the real image URLs, downloaded both portraits — and passed only one, because the node takes one reference. Tsipras came out right; the other man was invented. It then "fixed" him by editing Samaras's portrait with "change the man on the right … keep the kiss scene": the edit sees only its reference, so the kiss scene never reached the model and the result was four podium portraits. The 30-minute budget ran out; the forced report showed no image and blamed "multi-reference" — there was none.

The fix: acquisition is the tool's job. A written rule ("a real person needs a photo") was already in both texts the model reads and it did not hold. Refusing a name-only call was rejected by the operator; instead the model lists the specific real people, places or products in subjects and tools/subject_photos.py does the rest:

  • Find. One Wikipedia API call over Tor per subject (generator=search&prop=pageimages, Greek-script names try el. first). The hit must be about the subject: every content word of the name must be in the article title (title_matches), and disambiguation pages are skipped. Live, "Antonis Samaras" returns the party's flag as hit #2. The reverse direction (title ⊆ name) was removed in review: "Alexis Tsipras and Antonis Samaras" matched "Alexis Tsipras" and would have rendered one man's photo as both. The article's own thumbnail URL is used — never a guessed width (§4JX: free-form widths 400). A search that could not reach the encyclopedia (network, non-200) is retried once on a fresh Tor circuit and then reported as SearchUnavailable: "NOT a missing photo — retry once", never "ask the user to upload one". The API is asked with the plain User-Agent curl/8.7.1 (LOOKUP_USER_AGENT), never a browser impersonation: on 2026-10-20 (request 52c9a5d2) a Chrome-impersonating client got HTTP 429 from Wikipedia on every Tor circuit, while the plain UA got 200 (no UA at all = 403). The UA is the most common generic one, so lookups stay unlinkable. A 429 is its own result: "the encyclopedia is rate-limiting the photo search (HTTP 429) … NOT a network problem … do NOT call image_generation again in this turn", and the failure reason (HTTP status / exception) is logged as a Subject Photo warning — before, every 429 read as "network / Tor" and was retried for nothing.
  • Download via the ordinary tool_download_file (Tor, SSRF guard, size cap) into the sandbox folder subject_photos/ as ref_<slug>.jpg (or .png), with a ref_<slug>.jpg.json provenance record (subject, article, URL). It is downloaded under a temporary name and promoted only when the WHOLE file decodes. A cached photo is reused only when its record names the same subject and it still decodes completely — a user's own file, another person whose name slugs the same, or a truncated download is fetched again (review).
  • Join and pad. One subject → its photo is the reference. Two or three → combine_side_by_side scales them to 1024 px high (a panorama is capped at 1.5× the height) and joins them left to right with a 16 px white gap into subject_photos/ref_combined_<hex>.jpg — the node accepts one reference (§4JW: a second OOMs), and one image carrying every face is the only way to put several real people in one scene. More than three is refused. The node stretches the reference to the render size without keeping its aspect (fit_reference) and, with no size, renders at the reference's shape, so the reference is padded with white to the render's shape: the requested width/height, or 3:2 with an explicit 768×512 for a joined strip when none was asked (a single photo with no size keeps its own shape). Measured on ghost, 2026-10-07 (before padding): the two Wikipedia portraits joined (1485×1024) plus the kiss-scene prompt rendered at 736×512, 20 steps, in 619 s — both men recognisably themselves (Samaras with his glasses).
  • Collage risk. The first live probe through the agent (probe-4mg-kiss) rendered both likenesses correctly but as a two-panel collage — the model copied the joined reference's layout. For several subjects the lead now says "Create ONE single photograph of ONE continuous scene … not a collage, not split panels" and the tool adds a negative prompt (collage, split screen, diptych, two panels, …), appended to any negative the model gave. Since §4OY Turbo edits run at guidance 1, where the node drops the negative prompt, so this half is inert until the ladder's cfg-4 attempt (§4OZ). The re-run (probe-4mg-kiss2, 673 s) was one scene with both men recognisable — one sample, not a rate.
  • Prompt. For one subject the tool prefixes "The reference photo shows A. Keep A looking exactly as in the photo … and place them in this new scene: "; for several, "The reference image is N separate photos side by side; left to right: A, B. Keep each of them looking exactly as in their photo … Create ONE single photograph of ONE continuous scene … The scene: ". If the lead pushes the prompt past 8000 characters, the prompt's tail is cut and the result says so. The model is told not to describe faces itself (live it wrote "Tsipras … with glasses" — Samaras is the one with glasses). Names arrive as a list, a JSON list string, or one string split on commas, semicolons, new lines and "and"/"&"/"και"; duplicates are dropped by slug.
  • No photo, no render — the user decides. If any subject has no usable photo the tool renders nothing, names it, and tells the model to STOP and ask for an upload or for consent to a generic stand-in; the error ends with a machine-readable [subjects: {"missing": […], "found": […]}]. Prose was not enough: live (probe-4mg-missing) the agent re-rendered with a generic violinist in the same request. So _missing_subject_block (core/agent.py) reads that tail — only on a row that IS the error — and, for the rest of the request, refuses an image_generation call unless it keeps every found subject and has a close respelling (similarity ≥ 0.75) of each missing one. A stand-in ("a man") or someone else is refused (review: a count-only rule let them through). The user's answer is a new request, which is never blocked. The photos are not fetched at all when the image node is offline.
  • Record. The SUCCESS result carries REFERENCE PHOTO: subject_photos/<file> — left to right: A (a.jpg), B (b.jpg). THIS WAS A NEW SCENE …, plus: never fix a likeness by editing one subject's portrait, and a wrong photo needs a MORE SPECIFIC name (the same name finds the same photo). The visual verifier reads the line and compares the picture against that photo (see verifier — likeness mode) — only when the image it judges is the generated one.

Edits say what the model saw. subjects with reference_images was an error until §4PA below (now the two combine). An edit whose reference is not a gen_* result adds "The model saw ONLY <file>: nothing from any earlier generated picture carried over". The self-correction rule in both texts now has the exception: "that's not X" is fixed by a new render with subjects, never by an edit.

The reply always shows the image. _unshown_image_note (core/agent.py) appends the last generated image's markdown line when a reply — streamed or not, forced report or not — displays none of the images generated in that request. Displayed means an /api/download/… link: a bare "saved as gen_x.png" shows nothing, and on the streamed path the check reads the VISIBLE text (tool-call markup scrubbed), not the raw stream (review). A file that no longer exists is not linked.

Privacy. subjects is a public search, so memory/egress.py treats it as outbound: the owner's street address is scrubbed from subjects (OUTBOUND_TOOLS), and after outside content entered the request an owner identifier in subjects is refused (SUBJECT_TOOLS in CONTENT_GUARDED_TOOLS). The prompt itself goes only to the owner's GPU node and is not checked. The tool is registered before the registry's egress wrap, so a caller that holds the tool callable is guarded too. Members (Slack channel members) may pass subjects (review: they were shown it and refused for using it, which steered to a name-only stranger). Pinned in tests/test_4mg_image_subjects.py and tests/test_4mg_review.py.

Two-panel outputs: a seamless composite and one checked retry 2026-10-14 §4OZ

What went wrong. Three two-subject renders on the morning of 2026-10-14 came out as side-by-side panels: each person in their own half, with a seam between them. The chain was the pipeline copying its own input. The node takes exactly ONE reference (a second OOMs, §4JW), so two subjects' photos were joined by combine_side_by_side into a white-framed strip, and the edit path reproduced that layout. The §4MG countermeasure was a lead sentence ("ONE single photograph of ONE continuous scene") plus an anti-collage negative prompt — and since the Turbo switch (§4OY) edits run at guidance 1.0, where a negative prompt is not used at all, half of that countermeasure is inert. The same morning's "Karl Marx hugging Yanis Varoufakis" (request 1602f750) came out as one scene through the same code, so the failure is a rate, not a rule.

  • A seamless composite was built and lost. The first idea was to hand the model nothing that looks like a frame: head-and-shoulders crops touching with a feathered seam and blurred margins instead of the 16 px white gap and white canvas. Measured against the strip on 10 ordinary two-person scenes (same seed per pair, straight to the node, judged by eye and by the vision node, which agreed on all 20): the composite came out as two panels 7/10, the strip 5/10 — and the composite's panels were near-copies of the portraits. An edit preserves what looks like a finished picture; the white frame is what tells the model these are separate photos to recompose. The composite was removed, not left behind a switch. Experiment data (references, outputs, judge rows, contact sheets, the script): system/eval/4oz/.
  • Look, then retry — a measured ladder. After a multi-subject render the tool sends the rendered pixels to the vision node with a fixed verdict-shaped question ("ONE continuous photograph, or a COLLAGE of separate pictures side by side?", JSON {collage, confidence, evidence}, thinking off, 120 s). While the answer is YES at confidence ≥ 0.7 it renders again, at most twice: attempt 2 with the same payload minus the seed (the node picks a fresh one, ~2 min), attempt 3 with the first render's seed (read back from the node) at guidance_scale 4.0 — the configuration §4OZ measured (§4QG; it used to draw a fresh seed) — true CFG, where the §4MG anti-collage negative prompt is actually read (~4 min). Each new picture is checked the same way; the last one rendered is the one saved and shown. If every attempt is panels the SUCCESS result carries a NOTE telling the model to say plainly that it is a two-panel picture and not to render again on its own; if a re-render fails or returns no image the previous picture is kept with a similar note and the ladder stops. A missing or unusable verdict (vision down, no JSON, "MAYBE", confidence below the floor) keeps the picture — an absent instrument never costs a render. One subject, plain prompts and edits are never checked. GHOST_SUBJECTS_COLLAGE_RETRIES: 0 = never check, 1 = reseed only, 2 (default) = reseed then cfg 4.
  • Record unchanged. The REFERENCE PHOTO: … THIS WAS A NEW SCENE record the agent parses for the likeness verifier stays first in the result; the panels note follows it.
  • Measured (2026-10-14, Turbo node, 768×512, straight to the node, 30 renders). Ten ordinary two-person scenes (chess in a park, a hug, a handshake, cooking, a tandem bicycle, coffee, walking a dog, dancing, arm wrestling, ice cream) with Wikipedia photos: the framed strip gave 5/10 two-panel pictures, the seamless composite 7/10. For the strip's five collages, a fresh seed at guidance 1 fixed 3/5 (121 s each) and the same seed at guidance 4 fixed 4/5 (222 s each) — different ones, so a reseed followed by a cfg-4 attempt cleared every collage seen. The vision judge agreed with a human reading on all 30 pictures. Expected cost: about half of two-subject renders pay one extra ~2 min attempt, and roughly a fifth of those pay a further ~4 min. Two side findings: the Serena Williams + Roger Federer pair rendered two Federers on the first try (a likeness miss the likeness verifier, not this check, has to catch), and "Napoleon Bonaparte" finds no photo because the article is titled "Napoleon" and title_matches needs every word of the name in the title.
  • Log line. The render line is now titled image generation and carries the WHOLE prompt (size=… | refs=… | prompt (N chars): …, no_truncate), in the file as well as the stream — the old image gen — Prompt: <30 chars>… hid what the model actually asked for (operator, 2026-10-14).
  • Pins. tests/test_4oz_subjects_collage.py (the strip stays and the composite is gone; retry with a fresh seed and the second picture saved; two collages → note, never a third render; clean/unsure/unusable verdicts and a dead vision node keep the picture; a failed or empty re-render keeps the first; single-subject and plain renders unchecked; the verdict parser accepts only YES/NO). 8 hand mutants of the new code, 8 killed.

`subjects` + one reference: a user's photo, or adding a person to a picture 2026-10-14 §4PA

What went wrong. A member uploaded a photo of one person and named another; the model passed the upload in reference_images and the name in subjects, and the tool refused: "cannot be combined — the node takes ONE photo". The refusal was a design shortcut, not a node limit: the tool already joins several photos into the one reference the node takes. Operator: combine them for ordinary requests, and make the two-turn flow work — turn one: make X and Y hug; turn two: add Z to the photo.

  • One image in reference_images joins the strip. With subjects present, the reference's bytes are no longer sent on their own; the file becomes one more panel of combine_side_by_side (3 panels at most, the upload counted; a non-image is refused before any lookup; a second reference was refused until the join).
  • Which panel it is depends on what the file is. A previously generated picture (gen_*.png) is the SCENE to keep: it goes FIRST and the lead reads "left to right: the existing picture, Z. The existing picture is the scene to keep: keep its setting and the people already in it exactly as they are … Create ONE single photograph … the existing picture with them added into it … The change: <prompt>". Any other file is a user's photo of a person: it goes LAST and the lead names it "the person in the uploaded photo".
  • Record and checks. The result's record reads left to right: existing picture (gen_aa.png), Z (ref_z.jpg) or …, uploaded photo (me.jpg), still first in the result and still parsed by the likeness verifier against the joined strip. Two or more panels get the §4OZ collage check and retry ladder. A reference on its own is still a plain edit (no lookup, no check).
  • What the model is told. The schema's reference_images text says the two combine and names both uses; the tool description adds "To ADD a real person to an existing picture ('now add Z'), pass the picture in reference_images AND the new name in subjects together"; the no-photo error now tells the model to pass an upload together with the remaining subjects.
  • Pins. tests/test_4oz_subjects_collage.py (§4PA section) + the rewritten §4MG pin: strip order for both cases, lead and record text, the limit counting the upload, two references refused, bad upload refused, collage check on subject+upload, upload-alone still an edit, schema text. Hand mutants: 5, all killed.

Several pictures in one call 2026-11-07 §4TO

What went wrong. Asked to put a face from one upload on a game cover from another, the model had no route: the node takes one reference and only subjects could join pictures. It wrote its own PIL montage (4 of 5 scripts failed), sent it as a plain edit, so no panel check ran, and cropped the two-panel result by hand. The request took 758 s.

  • Up to 3 files. reference_images takes 3 (MAX_JOINED_REFERENCES, the same limit as panels), counted with any subjects. The node still receives one image (MAX_REFERENCES stays 1). The same file listed twice counts once.
  • Default: a new scene. The files go through the subjects path: framed strip, "ONE single photograph" lead, §4OZ panel check and retries, and the REFERENCE PHOTO record. A generated picture goes first as the scene to keep.
  • keep_first: an edit of the first file. The first picture is scaled whole; the others are scaled to about its width and letterboxed, never cropped, because a crop can remove the face to copy. No size is sent, so the render takes the strip's shape; a size the caller asked for is dropped and the result says so. The lead asks for the left picture to change and the rest to stay. No collage check runs, since panels are the method, and the strip isn't written to disk, so it can't outlive the private uploads it holds.
  • The cut. crop_first_panel checks that the other panels' content still correlates with the reference, ignoring blank background. If it does, the cut goes at a run of flat columns near the predicted edge, or at the edge itself when the model painted the gap over. If it doesn't, the render is saved whole and the result says so. The check is a heuristic: a figure with nearly the same outline in the same place can pass it. So a cut also keeps the whole render as joined_*.png and names it in the result. The saved size is the size reported.
  • Size. The node's 768 px and 768x512 limits cover the whole strip, so the result is smaller than a plain edit: about 370x512 for a portrait cover, 485x320 for a 3:2 picture.
  • Checks. The result carries EDITED FROM: <first file>. The visual check uses it as the before image even when the user named another picture first, because that may be the face (_turn_edit_was_joined). The time estimate counts the panel ladder for a new scene and one render for keep_first.
  • Measured on the node (the real cover and face, 16 steps). "Create ONE single picture": two panels with no face swap, 6 of 6. "Edit ONLY the LEFT picture": change made, 5 of 5. Through the finished tool: cover 2 of 2, right subtitle on both; a two-person landscape 1 of 2, where seed 11 left the face unchanged in two runs. So a miss is still possible, and the result allows one re-attempt. Small text can also come out slightly wrong.
  • Pins. tests/test_image_join_references.py.

Fresh-eye review: generation, editing, multi-step edits 2026-10-14 §4PB

Three independent read-only reviewers (tool, agent loop, node + client) plus a 14-day log corpus lens (44 image turns, 9 with a tool error). Scope, threat model and out-of-scope are in the journal entry. What changed:

  • A failed photo download is transient, not "no photo of this person". fetch_subject_photo raises PhotoUnavailable (the article exists; the download or its bytes failed) and the tool answers like an unreachable search: "NOT a missing photo — call again once". Before, a 503 on the thumbnail told the model to STOP and ask the user to upload a photo of a famous person, and the agent's missing-subject block then refused the same name for the rest of the request. The three raise kinds in the fetch are enumerated by an AST pin.
  • The lookup takes the name as a title first. One titles=<name>&redirects=1 query per language: an exact title (ignoring a parenthetical qualifier) or a redirect FROM the typed name is the encyclopedia's own answer — "Napoleon Bonaparte" → "Napoleon". Only then the search, which now prefers an exact title over an earlier superset hit ("Kyriakos Mitsotakis" over "Konstantinos Mitsotakis"). title_matches lets ONE token of a multi-word name be one edit off when another token of 4+ letters matched exactly ("Zoi Konstantopoulou" → "Zoe Konstantopoulou", refused twice live); a single-token name still needs an exact token ("Obama" never matches "Osama bin Laden"). Table-pinned.
  • The article is on record. The SUCCESS result adds "Photos from Wikipedia: A → <article>; B → …" and, when a name matched a fuller title, "NOTE: 'Mitsotakis' matched the article 'Konstantinos Mitsotakis' — if the user meant someone else, retry with the full name." A cache hit logs its article too. The REFERENCE PHOTO record line the agent parses is unchanged.
  • Panels are never cropped. A panel wider than 1.5× the strip height is scaled to that cap and letterboxed; the old crop cut ~15 % off a 736×416 "scene to keep". A requested shape outside 1:4–4:1 is refused before any canvas is built (a 200000×1 ask spent 14 s allocating).
  • A picture from the root sandbox is found inside a project. _resolve_reference falls back to the root sandbox when the scoped one has no such file (the agent's own resolver already did); containment is checked against each root; the scoped file wins when both exist.
  • Each render leg books its own time. _render_leg appends per node call to RECENT_RENDER_SECONDS; the wrapper no longer books the whole call — a 3-render ladder had recorded one ~8-minute "edit", and the turn loop's deadline check then refused a 2-minute edit.
  • Transparency is read from the pixels (§4QG). The node writes RGBA for every picture (all 31 saved renders were colour type 6), so the colour type proves nothing. The tool decodes the PNG and calls the background transparent only when at least 5% of its pixels are clearly see-through (alpha < 16); ordinary renders have a minimum alpha of 183–253. Otherwise the result warns that the node returned an OPAQUE image. With a reference or subjects the flag is dropped with a note.
  • Arguments. subject (singular) beside a prompt is the subjects list (it was only a prompt synonym, so the named person became a stranger); a dict/int/bool subjects is an error; a non-dict node answer is the "no image data" error; the 3-subject limit error echoes at most five names and, for a gen_* reference, says to list only the NEW person; a negative prompt over 8000 characters is cut with a note instead of a node 400.
  • The scene keeps its shape. A gen_* reference with subjects renders at the picture's own size when none was asked (a portrait came back 768×512); the result says "built from the existing picture and the subjects' photos" and asks the model to describe the CHANGE.
  • An edit is judged before/after. A plain edit's result carries EDITED FROM: <file>; core/agent.py parses it (_turn_edit_reference) and the visual verifier gets the picture the edit started from as the before-image when the user gave no screenshot.
  • The clarify-first record is written for every image turn, in both finalize paths, and the helper also recognises the image tool by its result text (an alias name used to miss it).
  • Node (interface/externals/image_generation/img_gen_server.py): fit_reference letterboxes a reference whose aspect differs from the render instead of stretching it (a portrait upload with a landscape size was drawn from a 0.76 → 1.5 stretched face); the key is checked in the pure-ASGI middleware before a byte of the body is read (FastAPI parsed and validated a 24 MB body before the handler's 401); /ready and /generate scrub the preflight error like /health and answer 503 while the background preflight is still retrying (the client's warm-up backoff fits), 500 only when every attempt is spent; image_size reads the header and the EXIF orientation tag without decoding pixels on the event loop.
  • Docs and prompt text corrected: steps are never sent; the negative prompt is inert at guidance 1; the ladder numbers (cfg 4 fixed 4/5); the composite pins claim; the system prompt's "no truncation" (8000 characters).
  • Accepted as-is: clarify-first reads text only (a one-word follow-up with a photo gets the fixed question — §4NT design); no tool-level timebox beyond the node's queue bounds and the turn deadline; a client disconnect cancels the render on the node (§4KD) so no orphan renders.
  • Pins: tests/test_4pb_image_review.py; battery scripts/mutate_4pb.py (score in the journal).

Image pipeline review fixes 2026-10-21 §4QG

A four-slice review (photo search, the tool, the turn loop, the node) found 10 MAJOR and ~20 MINOR defects; all were fixed in one round.

Finding the subjects' photos

  • A failed or slow search is never reported as "no photo": any query that did not answer makes the result "unreachable" (or "rate-limited" on HTTP 429). Each subject has a 60-second lookup budget in total (LOOKUP_DEADLINE_S, §4QG-b); the fresh-circuit retry runs only with one full query timeout left. An expired cached photo is reused when its re-fetch fails transiently.
  • Names match on every word. One word may differ only by a spelling change: the word-final vowel (Zoi/Zoe, Alexei/Alexey), ph/f (Sophia/Sofia) or k/c (Nikos/Nicos) — never another letter (Mark/Mary, Paul/Paula, Jon/John, Bill/Bell, Joe/Joey) — and such matches rank last. A leading title (Dr, President, Prime Minister, κ., Πρόεδρος…) is ignored when two or more words remain. Initials "JK" match "J. K.", and ß matches ss.
  • A redirect from the typed name is the encyclopedia's own say-so and is trusted (Kate Middleton → Catherine, Princess of Wales; Meghan Markle → Meghan, Duchess of Sussex) unless it is a section redirect (tofragment: "Sasha Obama" → the family article), a "Family of / Wedding of / Death of…" article, or a surname-only page (§4QG-b: the first version refused formal and married names).
  • Transparent, palette or 16-bit photos are placed on white before joining or sending (they used to turn black).
  • A photo in a format the node cannot use (e.g. GIF) is treated as no usable photo and the format is named. A disk error says so and is not retried.
  • Cached photos are re-fetched after 30 days (CACHE_MAX_AGE_S); names longer than 60 slug characters get a hashed file name.
  • A string of names splits on commas, semicolons and new lines (Jr./II stay attached) and always on "and"/"&"/"και" (§4QG-b: "Τσίπρας και Σαμαράς" is two people — the original §4MG failure). A list is never split: put a band or brand in a list.
  • A singular subject used as the subjects list (subjects_arg()) is scrubbed and privacy-checked like subjects, and timed like it.

The tool

  • The turn loop's deadline estimate for a call with ≥2 photo panels is two renders plus one vision verdict (defaults 150 s per edit, 90 s per generate; the cfg-4 leg is timed under its own key). The ladder itself skips a re-render that would cross the report reserve and keeps the current picture with a NOTE (§4QG-b: the first version budgeted the worst case and refused every multi-subject render after a restart).
  • With no sandbox the tool refuses before rendering.
  • An unusable size (width without height, a non-positive part, an unparseable string) is not sent, and the result says so; px units and × are accepted.

Node failures and retries

The image node answers distinct codes: 504 = the render hit the node's 480 s hard limit; 507 = out of GPU memory; 422 = the model could not load the reference; 400 = a reference that cannot be decoded (checked before the GPU is touched); 500 with "do not retry" = a model file failed to load — the node then re-runs its preflight in the background and answers warm-up 503s until it passes (§4QG-b: it used to stay down until restarted); NvMap "error 12" is retried once before a 507, only if the first run died within 60 s (§4QG-c: two full runs would outlast the client timeout); the background re-check runs under the GPU lock (§4QG-c: a leftover cancel flag failed every attempt); a warm-up 503 is not a breaker fault; 503 "GPU busy" = queued longer than 690 s behind another render; any other 503 = warming up. The agent re-posts only warm-up 503s (after 10 s, then 35 s) and transient faults. Everything else is posted once, and the tool's error tells the model not to call image generation again with the same request. "GPU busy" doesn't count against the node's circuit breaker. Timing: 690 s busy-wait + 480 s render limit + 30 s margin = the client's 1200 s timeout. The agent treats the image node as one slot and doesn't probe it; a call waits up to 690 s for that slot instead of failing after 90 s, bounded by the request's time left before the report reserve, minus this render's own estimate (§4QG-c/§4QG-d), and the render time booked for later estimates is the node's own time, not the wait; the node also serves /props with total_slots: 1.

A transparent reference is flattened onto white. A reference within 2% of the render aspect is centre-cropped by a few pixels, anything further off is letterboxed on white. Only a cheap structural check runs before the request queues; the reference is resized under the GPU lock (§4QG-b: decoding beside a 6.8 GB render risked the OOM it was meant to avoid). A request whose caller disconnects while queued never starts. Startup runs a real 8-step render at 256×256 and checks the model files (~20 s); without the vision projector, edits answer 501 and text-to-image stays up. /docs and /openapi.json are disabled.

Transparency and edit timing (§4MH, 2026-10-07)

The node now runs sd.cpp a1ded76, which decodes the model's alpha channel, so the schema advertises transparent (boolean: a sticker, logo, icon or product cut-out on a really transparent background) and the SUCCESS note says the PNG has an alpha channel instead of warning that the background will be opaque. Edits and subjects renders take about 8 minutes (was ~11) thanks to the prefix KV cache; every timing the model reads (tool description, steps, seed, subjects, the system prompt, the subjects note) says ~8. Pinned in tests/test_image_gen_model_swap.py and tests/test_4mg_review.py.

The tool description and the system prompt teach the new backend's contract: write the prompt as natural-language prose in any language (Greek works); put text that should appear in the image in double quotes (it renders legibly); do not use A1111 attention-weight syntax — the model's text encoder is an LLM and would read (x:1.2) as literal characters (the old SD1.5 node parsed it; the new node flattens it defensively); and one image takes 3–4 minutes, so call the tool once and wait. The old advice — attention weights, 624×624 squares, "SD1.5 DreamShaper" — is gone from tools/registry.py and core/prompts.py; a pin fails if it comes back.

A looked-at picture is described from the look 2026-10-21 §4QJ

Why. Subjects renders are looked at already: the collage check (§4OZ) shows the vision model the picture before the reply.

  • The collage check also returns the scene. _COLLAGE_QUESTION asks for one more JSON field, scene: one plain sentence of what is visible, never guessing who anyone is. collage_verdict returns it as one line (whitespace collapsed, 400 characters at most); max_tokens 300 → 450 so a long scene cannot cut the JSON (a cut answer = no verdict = no retry ladder). Measured before shipping on the 30 §4OZ renders, old prompt vs new: the YES/NO verdict was identical on all 30, and the scene sentences matched the pictures.
  • The result carries the KEPT picture's scene. _seen is read from the verdict of the picture that is saved, on every exit of the ladder (clean, re-rendered, skipped for time, failed or empty re-render, panels every time). With a scene, the result says WHAT THE PICTURE SHOWS (the vision model looked at it): … and tells the model to describe the picture only from that line and say where it differs from the request. This replaces the "say what you ASKED for / you have NOT seen this image" sentence; it does not sit beside it.
  • Plain renders are unchanged. Nothing looks at them before the reply. A look costs about 30 s, because the vision call evicts the main model's cached context and the reply must re-read it (measured: 34 s reply turn after a look, 2.8 s without). The after-reply visual check confirmed 5 of 5 plain-render replies, so they keep the "NOT seen" sentence.
  • The two-panel backstop survives the scene line. _two_panel_note (core/agent.py) skips its note when the reply already says the picture is two panels (_TWO_PANEL_SAID_RE). Three review rounds each found a looser form of that check matching ordinary replies, which hid the note:
    • "side by side" / "δίπλα δίπλα", which is how people stand, and the scene line now feeds such phrases into replies;
    • "came out … side by side";
    • a bare "panel" ("a panel of judges");
    • "side-by-side photo", the user's own request;
    • "δύο εικόνες";
    • "a collage of postcards".
    It is now strict on purpose. Only an unmistakable phrase counts: "two (separate) (side-by-side) panels/halves", "two-panel", "side-by-side panels", "diptych", "δύο (ξεχωριστά) πάνελ", "δίπτυχο". A missed phrase only shows the note twice. A rare false match ("a sandwich cut into two halves") would still hide it.
  • A broken verdict JSON keeps the verdict. A quote inside the free text (the scene or the evidence) used to fail json.loads, which cost the verdict and with it the retry ladder. The two fields the ladder needs, collage and confidence (bare or quoted), are now read from the JSON object alone, never from a preamble. The scene is then unknown.
