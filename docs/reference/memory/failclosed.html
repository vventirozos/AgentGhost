memory / failclosed.py — FailClosedStore

A store that blocks its own writes after an unreadable read must be able to come back without a restart.

Why (§4FP, 2026-09-09)

Since 2026-10-11 (§4NN) there are three: contradiction_log was removed with belief versioning (its file stays on disk as data). The record below names the four as they were.

Four memory stores refuse to write after a read of their own file raises OSError — the file is PRESENT but unreadable (EIO, EACCES, ENFILE/EMFILE), so the on-disk state is probably intact and overwriting it with whatever is in memory would destroy it. That guard is right and it was measured: without it, adaptive_threshold's very next record() atomically overwrote the whole learned window.

The half that was missing is the way back. contradiction_log and profile re-read on every operation, so a successful read clears the flag by itself — documented there as "cleared automatically as soon as a read succeeds". adaptive_threshold and competence read only in __init__, so their flag was cleared only by a RESTART: one transient file-descriptor exhaustion stopped that store learning for the life of the process — days, here — announced by a single log line. The two broken stores' own comments cite the two working ones as sharing the discipline.

The policy, in one place

  • Retry the read that armed it, no more often than RETRY_EVERY_S (30 s): a store that saves on every observation must not stat a sick disk thousands of times a minute. The clock starts EXPIRED, so a blip lasting one write costs one write.
  • Recover only on a real read. The flag clears because the file was READ, never because time passed. A hook that raises leaves the store closed.
  • Lose nothing. Whatever accumulated while blind is merged onto the history it could not see, by a hook the store owns — only the store knows what merging its own state means. adaptive_threshold appends the blind observations after the reloaded window (chronological order); competence adds alpha-1 successes and beta-1 failures onto each disk cell so the 1.0 Beta prior is counted once, and merges samples separately because _Cell.n falls back to the mass and would hide a dropped counter for weighted records.
  • One ERROR per arming, not per retry. The retry clears _degraded so the reload can re-arm it and thereby report failure; a naive re-arm logs every 30 s for as long as the disk is sick. Re-arming during a reload is silent — and it must not reset the retry clock either, or the rate limit is dead (measured: 21 reads for 20 records).

The class, not the two sites

tests/test_failclosed_recovery.py enumerates every class in memory/ that arms a fail-closed flag, straight from the AST, and fails the suite for any that cannot clear it outside __init__. Fixing this shape site-by-site is exactly what let two of the four drift apart, and the guard is what makes a fifth store inherit the discipline rather than copy half of it.

The rest of the audit

Item 4 of the 2026-09-08 list swept every "arm after N failures" counter in the tree from the AST. The healthy ones are worth naming, because the point of the sweep is that most guards already do this right: NodeCircuitBreaker (open → cooldown → half-open → a success closes it, and it documents its own known limitation rather than hiding it), the darkweb per-engine breaker (same shape, with a "recovered — breaker cleared" line), the sandbox provisioning backoff (set before the installs, lifted on success), and the self-play cooldown (recomputed adaptively each cycle; removed with its slot on 2026-11-05, §4SZ). One more counter was repaired: manage_projects's duplicate-create loop counter was a LIFETIME total on the project record, so a project that saw three duplicates once kept the alarmed "STOP. This is retry #N" instruction and its operator WARNING for every duplicate create it ever saw again. It now measures a burst (_DUPLICATE_CREATE_LOOP_WINDOW_SECONDS, 10 minutes) and stamps the attempt it measures from.
