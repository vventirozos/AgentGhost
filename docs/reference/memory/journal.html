memory / journal.py — MemoryJournal

FIFO work queue drained in idle phase 1 by GhostAgent.process_journal_queue (core/agent.py).

Storage

JSON at path/memory_journal.json; atomic temp + fsync + os.replace (the fsync before the rename closes a torn-/zero-length-file window on power loss); threading.RLock. A sibling path/memory_journal.inflight.json stages a taken batch for crash recovery — see the TAKE / ACK lifecycle below.

Schema

[
  { "type": "smart_memory" | "post_mortem", "data": {...}, "ts": float },
  ...
]

smart_memory items run the owner-fact extractor. A post_mortem item used to write a lesson; its consumer was switched off in §4NC and removed on 2026-10-11 (§4NM), so such items get no model call.

Crash-safe TAKE / ACK lifecycle (2026-07-22)

pop_all() / drain() used to empty the on-disk queue in one atomic write and hand the items to the dream drain, which then spends up to ~90 s of LLM time per item. A deploy kill landing mid-drain raises asyncio.CancelledError — a BaseException the drain's except Exception never catches, with no finally — so up to max_capacity (50) buffered facts / lessons were destroyed silently: the file was already [], so nothing on restart could tell that anything had been lost.

The take now happens in two on-disk steps. pop_all() / drain() copy the batch to memory_journal.inflight.json before clearing the queue, then return the items exactly as before. recover_inflight() folds an orphaned staging batch back to the front of the queue and runs automatically on construction and on the first load() of the process, so recovery needs no cooperation from any caller. Rotation on the next take remains as a backstop for callers that never ack.

The drain acks per item (2026-07-29). The original design relied on rotation alone ("the current drain cannot ack"), which framed the replay window as one drain. In reality the window was unbounded: the idle loop only calls the drain when pending_count() > 0, so after the last drain of a busy period no further take ever rotated the staging file — the fully consolidated batch sat "in-flight" for hours, and recover_inflight() replayed it at every restart. The 2026-07-28→29 deploy cluster (six clean restarts in 50 minutes) re-consolidated the same items up to 6×. process_journal_queue now calls ack([item]) on every terminal disposition — consolidated, or deliberately dropped (retry cap / non-transient error) — while re-queued items (transient failure, user-return suspension) keep their staged copy as the crash backstop until the requeued copy is durably back in the queue file.

Net effect: crash / cancel mid-drain → only the unprocessed items come back on next boot (at-least-once for unfinished work, exactly-once for finished work); a completed drain leaves an empty staging file — no replay on restart, ever. A crash in the ~1 ms window between staging and clearing leaves an item in both files; recover_inflight() de-dups against the queue contents, so that window cannot double-deliver either.

ack() clears the whole staging batch, ack(items) clears only those entries (the partial form the drain uses), commit is an alias, and inflight() returns the un-acked batch for diagnostics. Partial ack is count-aware: keys are pure content and append does not de-duplicate, so a batch can stage byte-identical twins under ONE key — a set-based ack removed both staged rows when the first twin was consumed, leaving the second twin's ~90 s consolidation with no staging record (a kill in that window lost it outright, worse than never acking). Each acked occurrence now removes exactly one staged occurrence. Tests: tests/test_smart_memory_requeue.py ("TAKE/ACK lifecycle" section).

Upstream-transient classification widened (2026-07-22)

is_upstream_transient(exc) now decides in a fixed order, so a permanently-broken item can't retry until JOURNAL_MAX_RETRIES burns out on every drain:

  1. Structurally-definitive types short-circuit to False first, before any text matching — ValueError (which json.JSONDecodeError subclasses), TypeError, KeyError, AttributeError, IndexError, NotImplementedError — so a decoder error whose message happens to contain "timeout" can't sneak through.
  2. httpx types keep their authoritative meaning (5xx → transient, everything else incl. 4xx → definitive, no fall-through to the heuristics).
  3. Builtin transport failures — TimeoutError (which asyncio.TimeoutError aliases on 3.11+) and ConnectionError.
  4. Only then a message allow-list, for the plain RuntimeError / Exception that core.llm re-raises after exhausting its OWN retries ("Max retries exceeded", "the request did not complete", empty/non-JSON, and a 5xx rendered into a string) — while a 4xx-in-a-string stays definitive.

Those two llm.py RuntimeErrors were previously classified definitive, so the consolidation was dropped instead of retried.

Overflow spill — the buffer never drops (2026-07-23)

The drain runs only in idle windows (each consolidation spends up to ~90 s of LLM and must not compete with the user's live turn). Under sustained back-to-back load with no idle gap the hot buffer fills — and it used to silently drop the oldest items past the cap of 50 (~25 turns overflowed it; a Track-B ablation driver, firing hundreds of turns with zero idle, lost far more — found 2026-07-23 in the B4 pilot).

The logical queue is now overflow + hot (oldest → newest). append() past max_capacity (raised to 256) spills the oldest surplus to a sibling memory_journal.overflow.json instead of dropping it; load() still returns only the hot buffer, but pop_all()/drain() take overflow + hot so the next idle drain consolidates everything owed, oldest-first. push_front() (a drain requeuing work it couldn't finish) folds to the overflow head — drained first — and the old capacity-bounded _merge_front that discarded surplus is gone. Nothing here ever drops an item; the overflow is small text, unbounded in principle but drained by any idle gap in practice.

Consequence for the "is there work?" checks: the idle scheduler's phase-1 gate (memory-journal consolidation) (and, until its removal on 2026-10-11, the self-play loop's inter-cycle drain) now ask pending_count() (hot + overflow), not len(load()) — otherwise overflow-only work (a burst that spilled, or a preemption requeue) would sit undrained forever. Tests: tests/test_journal.py (burst-loses-nothing, push-front-to-overflow, crash-recovery-to-overflow), tests/test_memory_audit_fixes.py, tests/test_smart_memory_requeue.py.

API

MethodPurpose
__init__(path, max_capacity=256)Bind path, set the HOT-buffer cap. Surplus spills to memory_journal.overflow.json, never dropped.
append(item_type, data)Enqueue. On overflow, SPILL the oldest surplus to the overflow file (drained oldest-first) — lossless.
pop_all() / drain()Stage overflow + hot to memory_journal.inflight.json, then atomically clear both (used by the idle drain). Crash-recoverable — see the TAKE / ACK lifecycle above.
pending_count() -> intTotal owed a consolidation = overflow + hot. "Is there work?" checks MUST use this, not len(load()) (which sees only the hot buffer).
push_front(items)Re-queue items the drain couldn't finish to the overflow HEAD (drained first). Lossless — absorbs any amount, no tail-drop.
recover_inflight() -> intFold an orphaned staging batch back to the FRONT of the queue (de-duped against the queue). Automatic on construction + first load(); idempotent.
ack(items=None) / commitConfirm a taken batch is durably consumed so it won't replay: whole batch, or only items (partial ack). commit is an alias.
inflight() -> listItems handed out but not yet acked (diagnostics).
RetryableConsolidationError / is_upstream_transient(exc) / JOURNAL_MAX_RETRIESThe bounded re-queue contract for the drain loop (2026-07-09). A journal item is removed by pop_all() before processing, so a task failure after that used to be a permanent, invisible loss: an upstream 503 during the smart-memory consolidation was retried at the HTTP layer (worker failover + one 2s 5xx retry in the client) but on final failure the item was swallowed by a bare logger.error — and a main-node timeout got no HTTP-layer retry at all. Now run_smart_memory_task classifies upstream-transient failures (5xx / timeout / connection, via is_upstream_transient) and raises RetryableConsolidationError before any memory write; process_journal_queue catches it, re-queues the item with an incremented retries counter (visible WARNING + 🔄), and drops it — with a visible WARNING + 🔶 — only past JOURNAL_MAX_RETRIES (2). Definitive failures (4xx, parse errors) keep the old log-and-drop path since a re-run would fail identically. Tests: tests/test_smart_memory_requeue.py.
load()Read current journal without clearing.

Audit fixes (2026-07-26)

Undecodable ≠ empty. Both _read_inflight and _read_overflow turned a UnicodeDecodeError into "empty file" — recovery then unlinked the in-flight batch (no sidecar, no log) and the next spill atomically overwrote corrupt overflow bytes, contradicting the "never silently lost" contract. Both now route through the shared _preserve_corrupt() sidecar helper, which also logs LOUDLY when even the preserve fails (the old _quarantine_corrupt stayed silent in that case). Dedup vs retries: crash-recovery dedup keyed on an exact json.dumps of the entry, but the transient-retry path re-queues a copy with a mutated retries counter — a kill in that window folded both twins back in (double consolidation). _dedup_key() now strips retries before comparing. Tests: tests/test_memory_audit_fixes_2026_07_26.py::TestJournalCorruptionHandling.

Consolidation review (2026-10-31, §4SN)

Over 24 days the drain logged 348 items as "consolidated". 176 of them reached the extractor, and 5 facts were stored, 3 of them distinct. Each defect below was reproduced by a failing test first.

  • A worker outage no longer loses items. When every worker node failed, the extractor raised OffMainNodeUnavailable. That error isn't upstream-transient by message, so the catch-all swallowed it, the drain acked the item, and the log said "✅ consolidated 1 memory". It is now ConsolidationNodeDown (a RetryableConsolidationError). The drain pushes back the rest of the batch, spends no retry, and stops: "worker node unavailable — kept N item(s) for the next idle window". This matters most while Nova restarts or its model is being swapped. The worker pool books any failure (a 90 s timeout, a 4xx) as a node failure, so one always-failing item must not block the queue (review r1), and an outage must not drop items (review r2, r3). A failing item steps aside and the next item is tried; two failures in a row (no extraction between them, skipped items don't count) is an outage: the drain keeps everything and stops. After the loop, a stepped-aside item counts one node_down only when another item reached the model in that drain and the drain did not end on an outage. Past _NODE_DOWN_MAX (6) it joins the ordinary retry path and is dropped after JOURNAL_MAX_RETRIES. Nothing counts by time: a 6-hour age rule was tried and removed (it drained the journal in a long outage). A lone failing item waits for the next item, which every owner turn appends. node_down, like retries, is not part of the dedup key.
  • The summary counts what the model read. run_smart_memory_task returns extracted, skipped (stopped before the model) or failed. The line is "read N memories (M without an owner fact cue, not read)", plus a WARNING "extraction failed for N item(s) — dropped" when any failed.
  • Each owner message is extracted once. An item carries the last four messages, so the previous turn's sentence was extracted again. Live, "my dog's name is Bruno" was stored twice 5 s apart, and one memory-usage note went under two keys 4 s apart. Extraction, attribution and the pre-filter now read only the newest owner message (attribution.latest_owner_episode). Each item also records its own owner message (data.user, 500 chars). When that message isn't the newest one in the arc (the item was journalled before its own message landed), the item is skipped rather than re-reading the previous turn. The check applies the arc builder's own transforms, so a message that opens with fenced code still matches; a fence left unclosed by the 500-char cut is stripped too. An image turn's text is read through _msg_text on both sides. The pre-filter reads the whole message, continuation lines included ("Some notes:\nOur office moved to Patras.").
  • The "summary request" skip is gone. Any arc over 1500 characters whose text said "summary", "what is" or "recall" was never extracted, and that text included the assistant's reply. The extractor has read owner lines only since §4NG, so the skip was costing owner facts and protecting nothing.
  • Anchored to when it was said. Ages are anchored, and the auto fact stamped, from the item's ts, not the drain time.
  • A negation in the fact blanks the fact; it no longer ends the task. The early return skipped the profile write, so "I no longer drink coffee, I drink tea now" never wrote tea. A profile value that itself states a removal is not written.
  • One fact, one home. The extractor's free-form category folds onto the standard drawers (_extractor_category: "technical preference" → preferences, "family" → relationships …). A value a related field already holds is not filed again ("already in the profile as assets.dogs"). Related means the same subject (attribution.field_subject) and the same kind (two location fields) or a shared key word (dogs / dog_name). Review r2: father_name Kosmas skipped son_name Kosmas. Review round 1 found the "any field" rule skipped "we moved to Athens" because root.birthplace was Athens.
  • Corrections remove only what they are about. See attribution: "I'm not selling the BMW after all" deleted assets.vehicles "BMW 320d", and "I'm not going to Athens this weekend" deleted root.location.

Tests: tests/test_consolidation_review_1031.py. Battery: scripts/mutate_4sn.py.
