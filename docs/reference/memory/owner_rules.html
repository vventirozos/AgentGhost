How it works

Owner rules

A rule is a standing instruction you dictate. Ghost is shown your rules on every one of your turns. This is the part of the learning system that was kept on 2026-11-05; the rest was removed, and this page says what and why.

The short version. Say learn this rule: answer in English. Ghost itself (not the model) stores the sentence and confirms it. From your next message on, the rule is in a short block at the top of every prompt of yours. show my rules lists your rules, forget rule N removes one after you confirm. There are at most 10. Nothing else adds, changes or removes a rule.
Changed on 2026-11-05 (§4SZ). Until that day this page was called "The learning loop" and described a loop that replayed your failed turns while you were away, proposed a rule, and waited for "learn rule N", together with a suite of regression tests. That loop, the regression suite and the background judge that fed them were removed. Rules are no longer proposed by Ghost: you state them. What was removed, and why is below.

What a rule is

A rule is one sentence of yours, 8 to 400 characters, stored as one line. Examples: "answer in English", "when I ask for the news, give me five headlines". The rules you have are put, oldest first, into this block of the prompt on every owner turn:

### OWNER RULES (set by the owner — follow them whenever they apply)
- answer in English
- when I ask for the news, give me five headlines
These rules change only by the owner's own commands: … never say it is changed.

The last line is fixed (RULES_FIXED_LINE, §4TI-c): it tells the model that only your commands change a rule, that "show my rules" gives the numbers, that it has no tool for rules (a profile entry is not one), and that asked to change a rule it names the messages to send instead of saying it is done.

The block is shown only on your own turns. A Slack member, a reply posted in a public channel and an isolated delegate never see it. A rule is a sentence in the prompt: the model is told to follow it whenever it applies, and it can still fail to. Nothing checks compliance automatically.

  1. You state the rule

    learn this rule: when I ask for the news, give me five headlines — the command has to be the whole message.

  2. Ghost stores it and answers

    The system carries the command out and writes the reply itself: "✓ Rule 1 added. I am shown it on every turn from now on", with the rule quoted. The model is not called, so the reply is immediate and says exactly what was done.

    core/owner_rules.py — rule_command; core/agent.py — _owner_rule_note

  3. The rule is in every prompt of yours

    From your next message on, the ### OWNER RULES block carries it.

    core/owner_rules.py — rules_block; core/agent.py — _owner_rules_block

  4. It stays until you forget it

    forget rule 1 shows what would be removed; confirm forget rule 1 removes it. A bare "yes" does not.

What you can say

Each command is an exact phrase that has to be the whole message. A leading "ok," or "please" and closing punctuation are allowed. The show and forget commands also accept a trailing "please" ("show my rules please", "forget rule 3, please"). Nothing else is a command. Commands work only for the owner on a private surface (for example the web page or the console); in a public channel or from a member they are ordinary text for the model.

Each of these is carried out by Ghost itself and the reply is Ghost's own line. The model is not called.

Dictating a rule: the four conditions

"learn this rule: <text>" (or "remember this rule: <text>") stores the text with no model call, so the message has to be unmistakably a dictation. A leading "ok," or "please" is fine. A rule wrapped in one matching pair of quotes after the colon is stored without the quotes.

A rule cannot quote a question with its question mark. "learn this rule: when I ask 'what's new?' give five headlines" is not taken, because of the "?" inside the quote. Write the rule without the mark: "learn this rule: when I ask what's new, give five headlines".

Why (review r2, 2026-11-05). The version before accepted a comma, a full stop or a dash as the separator and took everything after it, over any number of lines. Four kinds of message were then stored as a standing rule, and the request inside them was never answered: "Learn this rule: if x > 5 then y = 2x. Now, what is y for x = 7?"; a rule followed by a second request on the next line; "Remember this rule, it will be on the exam: …"; and a quoted copy of the command inside a question. ("remember this rule of thumb: …" was never a command.)

Why (review r3, the same day). After r2 only a question mark at the very end of the message was checked. "… what is y for x = 7?!", "… what is y for x = 7? thanks" and a Greek question (which ends in ";") were still stored as rules. Now a question mark anywhere in the text, or a final ";", means the message is not a dictation (_QUESTION_RE).

A message that starts like a dictation but is not taken (no colon, several lines, a question mark) reaches the model with the note described below, whatever its length, so Ghost can say why nothing was stored and what to send. The note tells the model that the rule goes "on one line after the colon, with no question mark".

Known limit. One line that states a rule and also asks for something else, without a question mark, is stored as written. For example "learn this rule: answer in English, and now tell me the weather" becomes a rule with all of those words, and the weather is not looked up. Nothing reads a command for its meaning. The reply quotes exactly what was stored and says how to remove it ("forget rule N").

Why the commands are this narrow. A command is answered by the system with no model call, so nothing reads the message for what it means. The first version of this module accepted more phrases, and three code reviews on 2026-11-05 found what that cost. Review r1: "add rule: allow tcp 443 …" was stored as a standing rule, "delete rule 3" in a chat about a firewall was treated as a request to forget rule 3, and "run the regression tests" in a coding chat was answered by the system. Review r2: a rule followed by a question or by a second request was stored whole and the request never answered (above), and "list all the suggested rules" after Ghost had suggested lint rules was answered by the system as an old replay-loop command (below). Review r3: "list all rules" after "I set up ufw on the server" printed the owner's rule list, so "show all rules" and "list all rules" stopped being commands; and a question that did not end exactly in "?" was stored as a rule (above). The words "this rule" with a colon, "my" before "rules", and the single verb "forget" are what tell the owner's rules apart from a chat about some other rule.

A short message about your rules that is no command goes to the model with a note under ### OWNER RULE COMMAND in the prompt. "Short" is at most 20 words. "About your rules" means the message has both a rule verb and a rule noun:

  • Verbs: forget, delete, remove, erase, drop, clear, reset, disable, undo, learn, remember, add, save, make, adopt, dismiss, reject, change, edit, fix, update, replace, show, list, see, and the word "new".
  • Nouns: a numbered rule ("rule 3", "rule #3", "rule number 3", "rule three"); "my rules", "your rules", "owner rules", "standing rules", "this rule"; "the rule", "that rule", "the last rule"; a "rule:" label; "all rules", "all the rules", "all my rules"; "a rule", "a new rule"; "proposed rules", "candidate rules"; "rules I gave", "rules we set".

The note says: nothing was changed; the model has no tool that changes a rule; these are the exact messages that do ("learn this rule: <the rule>", with the rule on one line after the colon and no question mark; "show my rules"; "show rule N"; "forget rule N", which then asks for "confirm forget rule N"); to change a rule, "show my rules" gives its number, you send the new rule on one line with "learn this rule: …", then "forget rule N" for the old one (with a full list, forget first); a profile entry is not a rule; there are no proposed or candidate rules any more, so "learn rule N" and "dismiss rule N" do nothing. Ghost then answers your question or tells you which message to send. If the message is about some other kind of rule, the model is told to ignore the note.

Examples that get this note: "can you change rule 2?", "delete rule 3", "add a rule: …", "add rule: …", "new rule: …", "forget all rules", "show all rules", "list all rules", "forget the rule about news", "forget that rule", "delete the last rule", "erase rule 2", "reset my rules", "forget your rules" and "learn rule 3". A message that starts with "learn this rule" or "remember this rule" and is not taken as a command gets the note at any length. Longer messages get no note, whatever they ask. Instead, every turn that shows your rules ends the rules block with one fixed line: rules change only by "learn this rule: …" and "forget rule N", the model has no tool for them, a profile entry is not a rule, and asked to change one it names the messages to send and never says it is changed (§4TI-c, 2026-11-08: a 27-word "edit this rule, add … 1. … 4. …" got no note, and the model said "Done" after writing a profile entry while the rule stayed as it was; a matcher for long edits failed three reviews, so the operator chose the fixed line).

Examples that get no note: "my rules are working well" (no verb); "show me the rules" and "show rules" (no rule noun from the list); the old commands worded with "pending", "waiting" or "suggested" rules ("list my pending rules"); a message in Greek (the verbs and nouns are English); a message of more than 20 words, unless it starts like a dictation (the fixed line under your rules still applies).

History (review r3). Before r3 these natural ways to ask got neither a command nor the note: "new rule: …", "add rule: …", "forget the rule about news", "delete the last rule", "erase rule 2", "reset my rules", "forget your rules". The verbs erase, reset, disable, undo, fix, save and make, the "rule:" label, "that rule", "the last rule" and "your rules" were added.

A bare "yes" confirms nothing

After "forget rule N" (or "forget all my rules") Ghost waits 15 minutes for the exact message "confirm forget rule N" ("confirm forget all my rules"). If you answer with a short affirmation instead, nothing is removed. A short affirmation is a message of at most 6 words that starts with y, yes, yep, yup, yeah, ok, okay, sure, absolutely, proceed, I confirm, confirm, confirmed, do it, go ahead, please do, forget it, delete it, remove it, ναι, εντάξει or οκ.

While the preview is still waiting, that message goes to the model with a different note under ### OWNER RULE COMMAND: the system showed a preview of forgetting rule N and is waiting for the exact phrase; this message is not it, so nothing was removed and the model cannot remove it; if the owner is confirming, tell them in one sentence to send exactly "confirm forget rule N"; if they are talking about something else, ignore the note. So Ghost answers with the phrase to send.

Why: a bare "yes" may be answering something else in the conversation, so it must not delete a rule. And a model left alone with a "yes" after "Forget this rule?" could say the rule is gone when it is not.

When a preview is "still waiting". Both of these have to hold (_waiting_hint):

  • It is fresh: shown at most 15 minutes ago.
  • What it showed is still there. For "forget rule N": rule N still exists. For "forget all my rules": the rules that exist now are exactly the ones the preview listed.

So the note stops as soon as the forget is confirmed, and it stops when you add a rule after a "forget all my rules" preview. Before review r3 only the 15 minutes were checked. The preview stays in the file after its confirmation, so for the rest of the 15 minutes "ok thanks" told the model that rule 2, already forgotten, was waiting to be confirmed.

The order of the two notes. The preview note is tried first. A short affirmation sent while a preview is waiting gets the preview note, even when it names another rule ("ok, delete rule 1" while the preview of rule 2 is waiting). With no waiting preview, a short affirmation is treated like any other message: if it is about the rules ("ok, delete rule 2", "confirm delete rule 2", "confirm forget all rules") it gets the general note described above; otherwise ("yes", "ok thanks") it is an ordinary message with no note. Before review r3 a short message that opened with an affirmation got no note at all when no preview was waiting, even when it named a rule.

In the code: core/owner_rules.py (rule_command_hint(text, home), RULE_HINT, HINT_MAX_WORDS, _waiting_hint, PENDING_HINT, AFFIRM_MAX_WORDS), called from _owner_rule_note in core/agent.py.

Only your commands change a rule

  • One store. The rules live in one file, $GHOST_HOME/system/owner_rules.json. Until 2026-11-05 a rule was kept in two places (the lesson store and the replay ledger), and a check every few hours kept the two equal. With one file there is nothing to reconcile, and that check was removed.
  • The model has no tool for rules. It cannot add, edit or delete one. Only the messages in the table above do.
  • The memory tool's "forget" does not remove a rule. When you ask Ghost to forget something about a person or a topic and one of your rules mentions it (as a whole word; case and accents are ignored), the reply names that rule and points to "forget rule N".
  • The store never replaces a file it cannot read. See the next section.

A damaged rules file

If $GHOST_HOME/system/owner_rules.json is damaged or cannot be read, Ghost leaves it exactly as it is. The file is not renamed, not set aside and not overwritten. Until it reads again:

  • Every rule command changes nothing and replies with this line, where <why> is the kind of damage:

shown to me until it reads again. It is `system/owner_rules.json` under my data folder —
repair it, or remove it to start with no rules.

These are not damage:

  • An absent file. It means you have no rules.
  • A UTF-8 byte-order mark at the start of the file (some editors add one). The file is read as usual.
  • Exactly 10 rules. That is the limit, not above it.
  • A pending entry edited by hand (not an object with a number under at). It is ignored, so there is no preview to confirm.
  • A preview whose time is in the future or is not a usable time (NaN, infinity, a negative time, a whole number too large to be a clock value). It confirms nothing: a preview is valid from the moment it was shown until 15 minutes later, not before and not after (_fresh). Before review r2 a future time or a NaN in a hand-edited file confirmed for ever; before review r3 a number too large for a clock raised an error instead of being refused.
  • A next_n that is not a whole number, or not above the highest rule number. It is raised to one above the highest, so a number is never reused.
  • A rule text edited by hand to hold line breaks or control tokens. It is cleaned (one line, no <|…|> tokens) wherever it is shown: in the prompt block, in the list, in "show rule N", in the forget preview and in the "forgotten" line. The file itself is not rewritten for that.

History. The first version of this module (the same day, before review r1) set a damaged file aside and started with an empty list. The next "learn this rule" was then "Rule 1" again and the health check read "0 owner rules" as if nothing was wrong; and on a file it could not read it wrote a new file over the three rules that were there. That is why the store now changes nothing whenever it cannot read the file. Until review r2 a directory in the file's place read as "You have no rules" and the health check as fine. Review r3 added three kinds of damage: a rule number above 999,999, a rule whose text is blank (it would show as an empty line in the prompt block), and a key written twice.

In the code: core/owner_rules.py (_read, _why_invalid, _fresh, damaged, _refusal, _clean) and tools/health_internals.py (_learning).

When the file cannot be written

A different case: the file reads fine, but a command that has to save (adding a rule, a forget preview, a confirmation) cannot write it, for example because the directory is read-only or the disk is full. Ghost itself answers, with the name of the error:

I could not write your rules file (PermissionError), so nothing was changed. It is
`system/owner_rules.json` under my data folder.

The old file is intact, because a save writes a new file and renames it over the old one. "show my rules" and "show rule N" still work, since they only read. Before review r2 the error was swallowed: the message went to the model, which answered "learn this rule: …" with no idea that nothing had been saved.

In the code: owner_rules.rule_command (the OSError branch).

Known limits

  • One line with a rule and a second request is stored as written. "learn this rule: answer in English, and now tell me the weather" has a colon, one line and no question mark, so all of it becomes the rule. The reply quotes what was stored and how to remove it (above).
  • A rule cannot contain a question mark. Not even inside a quoted phrase: "when I ask 'what's new?' …" is not taken. Write the rule without the mark (above).
  • Only English phrasings are recognised. The commands are English, and a message about your rules in Greek gets no note. (A Greek "ναι", "εντάξει" or "οκ" after a forget preview does get the preview note.)
  • A command is carried out when it arrives, not when its turn starts. Ghost handles one request at a time. A command sent while another request is still running is carried out at once, and its reply waits for the running request to finish. If that wait is cancelled (you stop the request before it is answered), the change stays (the rule is added or removed) and its "✓" line is never shown. "show my rules" shows the real state.
  • A bare "yes" never confirms a forget, even when it is the obvious answer to "Forget this rule?" (above).
  • With no memory directory configured, no command runs. The rules file lives beside the memory directory. An agent started without one treats every rule command as an ordinary message. (Before review r2 an empty path made the file land in the directory the agent was started from.)

Commands that were retired

The commands of the removed replay loop and of the regression suite are not commands any more. The system does not answer them and they change nothing. Each is an ordinary message that reaches the model.

When such a message is short (at most 20 words) and names a rule number or "proposed" / "candidate" rules, the model gets the ### OWNER RULE COMMAND note described above. The note says that there are no proposed or candidate rules any more (the loop that proposed them was removed on 2026-11-05), that "learn rule N" and "dismiss rule N" do nothing, and which exact messages show or change a rule. Ghost's reply is the model's own, written with that note in front of it.

History. For a few hours on 2026-11-05, between the two reviews, the old rule commands were still matched and the system answered each with one fixed line saying the replay loop was removed. Review r2 found that this matcher also answered "list all the suggested rules", "delete all pending rules" and "replace rule 3 with rule 7" in conversations about other rules (lint rules Ghost had just suggested, a firewall). A command gets no model call, so nothing could tell the two apart. The matcher and its fixed line were removed. A note to the model costs a wrong match nothing: it ends with "if the message is about some other kind of rule, ignore this note".

The regression-test commands were never part of that matcher after review r1. "show test 3" and "run the regression tests" are things an owner says in a coding chat, the owner never kept a test, and review r1 found the system answering "run the regression tests" in such a chat.

What was removed on 2026-11-05, and why

The learning system was evaluated after the replay loop had been live for 27 days. One part had a measured effect: a rule the owner approved, shown on every turn. That part was kept, without the machinery that fed it.

What a 👎 or a correction does now: it is still recorded as your label on that turn. The label is read by the failure census (an operator report of how answers went) and by the index of graded past turns. It no longer starts a replay, and nothing is proposed from it. The web page answers a 👎 with a hint instead (next section).

The hint after a 👎

A thumbs-down alone teaches Ghost nothing any more; a rule you state does. So when a 👎 is recorded, the answer of POST /api/feedback carries one extra field, hint, with this text (owner_rules.FEEDBACK_HINT):

Noted. If there is something I should always do differently, state it as a rule — say:
learn this rule: <the rule>
CaseHint in the answer?
A 👎 that was recorded (a new label, or a 👍 changed to 👎)Yes
A 👎 repeated on a turn that already has a 👎 (the answer says unchanged)No
A 👍No
A label that failed (unknown request id, a member's turn, a bad signal)No

The web page shows the hint as a system line in the chat, once per page load, and only after the thumb you tapped is latched (so a hint that fails to parse cannot make a recorded label look lost). Reload the page and the next 👎 shows it again. Other clients receive the same field and may ignore it.

In the code: api/routes.py (feedback), core/owner_rules.py (FEEDBACK_HINT) and interface/static/app.js (sendFeedback, _ruleHintShown). The route is described on api.routes and the client on interface.server.

One side effect in the idle schedule: the idle window (which lets the 10 to 60 minute idle jobs run again during a long quiet stretch) now restarts every hour unconditionally and never changes the clock that records when you were last active. Before, the replay slot reset that clock when it finished. The helpers that existed only for that slot (_run_idle_job, _owner_active and IDLE_JOB_CAP_S in core/agent.py) were removed with it, and self_play was added to the retired phases of the activity ledger, so its old heartbeat rows are skipped by the liveness table. See Checking and learning.

Macros were removed: use a rule for a recurring bundle

Composed skills, also called macros, were named sequences of tool calls (the manage_composed_skills tool). They were removed on 2026-11-05 (§4TA). Nothing had proposed one since 2026-10-11, the 12 proposed ones were never approved, and of the 4 that were active three were never used. Their tool definitions cost about 1,650 tokens on every request.

For a bundle you ask for often, dictate a rule, and Ghost calls the tools itself. For example:

learn this rule: when I ask for my daily report, give me the weather, the news headlines and a health check

After that, "give me my daily report" makes Ghost call the weather lookup, the news_headlines skill and the health check, and answer from the three results. This was tested live before the macro engine was removed.

What else changed:

  • youtube_transcribe, the one macro in real use, is a built-in tool with the same name. Paste a YouTube link as before.
  • Custom tools are still created with create_skill and listed or deleted with manage_skills.

Details for maintainers: composed_skills (removed).

What this does not do

  • Ghost does not propose rules. If an answer was wrong and you want it handled differently, state the rule yourself.
  • A rule is a sentence in the prompt. The model can ignore it. There is no automatic test that a rule is followed.
  • Every rule costs prompt space on every turn. That is why there are at most 10, each at most 400 characters.
  • Rules are yours only. They are not shown on a member's turn or in a public channel, and a member cannot add one.

For the module-level detail: §4SZ on the agent page, core.feedback (the 👍/👎 labels). The record of the removed loop is kept on the agent page (the failure-replay loop, the earlier rule commands), each marked as removed.
