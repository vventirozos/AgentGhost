memory / adaptive_threshold.py — AdaptiveThreshold

Self-tuning recall acceptance threshold. Trades precision for recall based on observed usefulness. Not built in production: since §4LF (2026-10-04) it exists only with GHOST_ADAPTIVE_THRESHOLD=1, which the launcher does not set; recall runs on the fixed --smart-memory 0.9.

Storage

  • JSON at memory_dir/adaptive_threshold.json.
  • Atomic temp + os.replace; threading.RLock.

Load hardening (2026-07-22)

_load() distinguishes three outcomes rather than the old except Exception: pass that silently started from the initial threshold and let the very next record() atomically overwrite the intact file — the whole learned window gone, at no log level:

  • absent → keep the seeded initial threshold (normal cold start);
  • corrupt (bad JSON / wrong type / non-list window / undecodable bytes) → move the raw bytes to a timestamped adaptive_threshold.corrupt-*.json sidecar, WARNING, restart from the initial threshold;
  • present-but-unreadable (OSError — EIO / EACCES) → run on the initial threshold but set _degraded (logged at ERROR); while set, _save() REFUSES to write over the on-disk state.

Tests: tests/test_memory_store_durability.py.

State

{ "threshold": float, "window": [(score, was_useful), ...] }   # window cap = 100

WINDOW_SIZE = 100 · MIN_OBSERVATIONS = 20 before recalculation kicks in.

Recalculation rule

The threshold is set to 90 % of the minimum useful score, but never below the median of useless scores. It rises at most 0.02 per update (MAX_STEP_UP); falls are instant. With no useful observation, or 20 useless ones in a row (STARVATION_RUN), it decays ×0.98 per update. Floor 0.3, ceiling 0.95.

Known limitation — the learned threshold is dead weight under --smart-memory 0.9

The 2026-07-22 durability pass did not change the retention numbers — this is a documented caveat, not a change. Under the live flag the learned value is effectively inert: the consumer takes max(cli_selectivity, learned), so with --smart-memory 0.9 the effective bar is already >= 0.9; the learned value can never exceed 0.9 (the upward candidate is min(useful_scores) * 0.9 <= 0.9) and its update rule can only ratchet DOWN toward the 0.3 floor when the window starves — so it can neither raise nor lower the bar. Compounding it, was_useful is self-referential as wired in core.agent: the signal fed back is "the score cleared the bar", not "the memory was later retrieved and helped", so the loop measures its own gate rather than utility. The class becomes load-bearing again only for a selectivity below ~0.9. Changing the arithmetic alters what the agent remembers, so it is a retention decision that was deliberately kept out of a persistence fix.

Not the same axis as the 2026-07-24 outcome loop. The outcome-gated learning loop supplies exactly the "the memory was later retrieved and helped or hurt" signal this was_useful feedback lacks — but it applies it on the retrieval/utility axis (per-lesson succeeded/failed_retrievals → compute_lesson_utility → prune), NOT to this write-admission threshold. The two are deliberately separate: this class gates what enters smart-memory (a retention decision), and was left untouched. Wiring the real outcome signal into this gate remains a possible follow-up but is an operator-visible retention change, not part of the 2026-07-24 work.

Concurrency

threading.RLock guards both reads and writes. Writes are atomic via temp file.

…and the way back 2026-09-09 §4FP

The guard above is right and the audit kept it. What was missing is the DISARM. _degraded was cleared only in __init__, so one transient OSError — an EIO, an EACCES during a deploy, an ENFILE/EMFILE when the box runs out of descriptors — stopped this store writing for the life of the process, which for this agent is days, announced by a single log line. The sibling stores contradiction_log (removed in §4NN) and profile re-read on every operation and clear the flag by themselves; their comments cite each other as sharing one discipline, and two of the four had quietly drifted out of it.

The policy now lives in memory/failclosed.py: retry the read that armed it (rate-limited, and the clock starts EXPIRED so a blip lasting one write costs one write), clear the flag only when a read actually SUCCEEDS, and merge whatever accumulated while blind onto the history it could not see — history first, then the blind observations, which is just chronological order. A failed retry restores the in-memory state exactly and stays closed. Pins: tests/test_failclosed_recovery.py; battery 18/18.

Audit fixes (2026-07-26)

record() takes effective_threshold — the bar acceptance ACTUALLY gated on (max(cli, learned)). cleared_bar was computed against the learned value alone, so under the live CLI 0.9 / learned ≈0.6 split, scores in (0.6, 0.9) were score-rejects mislabelled "cleared the bar" and excluded from the median-useless clamp — blinding it to exactly the band that should raise the bar once the CLI value is lowered. Saves fsync before rename. Tests: ::TestAdaptiveThresholdEffectiveBar.
