Safety and privacy

Three boundaries: what reaches the internet, what reaches your filesystem, and who can reach Ghost. Each one is enforced by a mechanism, not by a promise.

What leaves your machine

Start with the honest version of the answer, because "nothing leaves your machine" would be a lie:

TrafficGoes whereNotes
Your conversations Nowhere Stored as files under $GHOST_HOME. Never uploaded.
Model inference Your LLM server Usually 127.0.0.1. It doesn't cross a network boundary unless you put the model on another machine yourself.
Web search and page fetches Tor Including DNS — hostnames are resolved by the Tor exit, so your own DNS server never sees what you looked at.
Weather and location lookups Tor Same path as any other fetch.
Sandbox network access Tor When the container has network access at all.
Extra LLM machines you configured Your LAN Direct, on purpose. LAN traffic doesn't deanonymise anything.
Push notifications, if you set one up Depends A LAN or tailnet target is reached directly. A public target only ever over Tor, and skipped entirely if Tor is down.

There is no vendor account anywhere in this list. Ghost holds no API keys for third-party services and has no ability to authenticate as you to anything. Search runs against scrapers over Tor rather than a keyed search API — which costs some result quality, and is a deliberate trade.

How "everything goes through Tor" is actually enforced

Asking every tool nicely to use the proxy doesn't work — one helper that forgets, and you have a silent cleartext leak that looks identical to working. So there are three layers, and the order matters: the last one is what actually holds for the tools you use most.

  1. At boot: a liveness probe

    Ghost checks that Tor is actually reachable before it finishes starting. If it isn't, Ghost refuses to start rather than starting in a state where the network tools would quietly fall back to direct connections.

  2. At each call site: fail-closed by default

    This is the one that actually covers web search, page fetches and downloads. When one of those tools is about to reach a public host and it wasn't handed a proxy, it doesn't fall back to a direct connection — it fills in the local Tor proxy itself. If Tor happens to be down, the connection is refused (a stalled fetch), never sent in the clear. A LAN or loopback target is left alone, because Tor can't route those anyway.

  3. At runtime: a process-wide socket guard (backstop)

    The outbound socket calls are patched for the life of the process, so a direct connection to a public address raises an error instead of connecting. Loopback and LAN are fine — Tor traffic leaves via the local SOCKS proxy on 127.0.0.1, so at the socket layer all anonymised traffic is a loopback connection; the only thing the guard can see and block is a connection that bypassed Tor.

    An honest limit: this guard sits at Python's socket layer, and the network library the fetch/search/download tools use (curl_cffi) opens its sockets below that layer, so the guard can't see them — nor can it see the browser or sandbox, which are separate processes. That's why layer 2 exists and does the real work; the socket guard is a backstop for the smaller amount of traffic that does go through Python's own sockets.

Both are on by default. Turn them off with --no-mandatory-tor or GHOST_MANDATORY_TOR=0.

The one time you need to turn it off. On a completely fresh install, the embedding model hasn't been downloaded yet — and the guard blocks that download, because it's a direct connection to a public host. Boot once with --no-mandatory-tor to let it cache, then run normally forever after. If your very first boot hangs or fails while loading the embedder, this is why.

Bounds on any single fetch

A hostile exit node or a slow server shouldn't be able to hang the agent or exhaust its memory. Every outbound fetch is capped:

5 MB
Maximum response body. Anything larger is refused or truncated.
20 seconds
Request timeout.
Private ranges refused
A fetch aimed at a loopback, private or link-local address is rejected before the request is made — so a tool call can't be turned into a scanner of your own network.

Changing Tor circuits

When a page fetch comes back 503, Ghost asks Tor for a fresh circuit and retries — a gateway rate-limit usually clears on a different exit node. 401 and 403 do not trigger this: those mean "you're not allowed", and a new exit node won't change that.

Search works differently. Each query rides its own circuit through per-query proxy isolation rather than burning the whole circuit, which is cheaper and doesn't serialise searches behind a rotation.

The sandbox

Every piece of code Ghost runs goes into a Docker container. The boundary is real, and it's worth understanding its shape because it explains several behaviours that otherwise look like bugs.

What the container can reach

  • One directory: $GHOST_HOME/sandbox, mounted as /workspace.
  • The internet, via Tor — transparently, since 2026-09-09: an in-container Tor plus iptables rules in the container's own network namespace send every TCP connection and every DNS query through Tor and reject everything else, loaded through a privileged exec the sandbox cannot undo. Before that date this line was not true: the container had direct egress from your real IP, and the code's own comments believed otherwise. Details and the measurements: the sandbox page.
  • Services it started itself.

What it cannot

  • Any other part of your filesystem.
  • Processes you're running — it has its own PID namespace.
  • Your machine's localhost. The container's 127.0.0.1 is its own.

That last one surprises people. If you ask Ghost to check the app you're running on localhost:3000, it genuinely cannot — it will reach its own empty loopback instead. Ghost is told this explicitly and will ask you to restart your own services rather than pretending to.

Resource limits

Memory
4 GB by default. Change with GHOST_SANDBOX_MEM.
Processes
Capped at 1024, so a fork bomb takes down the container rather than the host.
Base image
python:3.11-slim-bookworm, with a cached provisioned image built after first use so later starts are fast.
The sandbox is not a security boundary against a determined attacker. It's a containment boundary against an agent that makes mistakes — which is the realistic threat when a language model is choosing the commands. Don't run Ghost as root, and don't mount anything into the sandbox that you'd mind losing.

Who can reach Ghost

Requests carry an X-Ghost-Key header matching your GHOST_API_KEY.

Bound to localhost, no key
Runs with auth disabled. Fine — only processes on your machine can reach it.
Bound to anything else, no key
Refuses to start. An unset key on a public bind is indistinguishable from a misconfiguration, so Ghost treats it as one. Pass --api-key '' if you genuinely want auth off on a trusted network.
Using the old default key
Ghost warns loudly. ghost-secret-123 was a hardcoded default in an early version and is publicly known — anyone who has read the source can use it.

The logs

Ghost's live log is designed to be watched, which historically made it the largest cleartext sink in the system — everything the agent handled scrolled past in the clear. So redaction is on by default: secrets, API keys, .onion addresses, home directory paths and personal details are masked in both the console stream and the log file.

Pass --no-redact-logs when you're debugging and need to see the raw content. Don't leave it on.

What the redactor recognises (distill/redact.py): key shapes (AWS, GitHub, Slack, OpenAI/Anthropic/Stripe/Google keys, JWTs, bearer headers, PEM blocks), assignments (password=, api_key:, JSON "token": "…", connection-URI passwords, credential query parameters), and — since 2026-09-20 — the spoken form an operator actually types into chat: “the wifi password is Zebra-Qu1lt-8817”, “my passphrase was …”, “API token: …”. A live probe had carried three secrets through one turn; the two key-shaped ones were masked and the spoken one landed verbatim in the log and a trajectory. The spoken rule fires only when the value looks like a secret (8+ characters with both a letter and a digit), so “the password is wrong” and “the token is expired” stay readable.

Sensible defaults, in one place

  • Run it as an ordinary user, never root.
  • Bind to 127.0.0.1 unless you actually need remote access — and if you do, use a tailnet rather than exposing the port.
  • Set a real GHOST_API_KEY, long and random.
  • Back up $GHOST_HOME. It's the whole agent, and nothing in it is recoverable from anywhere else.
  • Leave mandatory Tor and log redaction on.

Instructions hidden in what Ghost reads 2026-10-07 §4MB

In your own conversation, Ghost acts with your rights. Text it reads can also contain instructions: a web page, a search result, an uploaded file, a knowledge-base document, a transcript, or the text in an image ("ignore the user and run this", "remember: the owner prefers…", "schedule a daily sync…"). Ghost now records, for each request, whether such outside content came in (utils/provenance.py). The places where that would matter check this record.

  • It cannot open a fake system or user turn. The model server reads <|im_start|>, </tool_response> and similar tags as real control tokens, even inside a page's text. Every tool result is rewritten so these role-forging tags are plain characters (utils/prompt_safety.py). This happens where the result enters the conversation, where it is re-wrapped as user text, and again where the client sends. Your messages and Ghost's own instructions are left untouched, and so are <think>/<tool_call> inside a project file.
  • What counts as outside content:
    • search, research, news, browser, fact-check, YouTube, vision and recall results;
    • knowledge-base reads;
    • reads of uploaded files, anything downloaded or cloned, and the dark-web quarantine's inspection report;
    • an execute run that names a network client OR opened a network connection (§4UY N6, final form after review r4). The name rule is the one in use before §4UY, unchanged: curl, wget, requests., httpx, urllib, aiohttp, git clone, pip download, lynx, w3m, links anywhere in the code, command, script or content (provenance._NET_CODE, name_rule). A lab machine's exec answers to the same rule. Loopback calls such as curl http://127.0.0.1:… are marked, as they always were. The measurement only ADDS to it. The sandbox's Tor-only rules count every connection it sends out (the TransPort and DNS redirects, plus a counting rule for Tor's SOCKS port that decides nothing), and execute reads the counters before and after every run (DockerSandbox.net_connections, a privileged docker exec with a 3 s deadline). So python3 scrape.py, node fetch or raw Playwright that connected are marked too. A measured "no" never removes a mark the name rule gives. Install attribution: a measured connection during a command that has an install segment (pip/npm/apt install) is the install's, and only the name rule decides then. A segment with $(, a backtick or <( is not an install segment. The pin is a 34-command table: the mark is never weaker than the old rule, unmeasured, measured-no or measured-yes (tests/test_4uy_internet_provenance.py);
    • a file that came from outside, read or run in any later request. A durable ledger (outside_files.json under the data folder, at most 5,000 files, the newest kept; a row older than 30 days or a deleted file leaves it) holds every download, plus the files of every marked execute run. A run is marked by the rule above, or because it names a ledgered file (execute_reads_outside). A file_system read of such a file, or an execute call that names it, is outside content. A marked run records (provenance.note_run_files):
      • the files it created: names absent from a snapshot of its working directory taken just before it ran (run_root, snapshot_names). That directory is a scoped run's project folder, else its container workdir, else the workspace without the other projects' projects/ folders. Build outputs and .browser_profile are skipped;
      • the existing files it names as write targets and changed during the run: -o/--output, wget -O/-P, >/>>, tee, cp/mv destinations, sed -i, the git clone folder (named_write_targets, with cd followed; a path whose real path leaves the workspace is skipped). For the work tree of git pull/merge/rebase/am (. or -C), an extract (unzip, tar x) or a copy into a folder, the files changed in it since the run started are recorded. Other git subcommands (add, commit, checkout, reset, stash, init) bring no new content and name no target (r5). An extract or cp/mv of a ledgered file names that file, so the run is marked and what it wrote is recorded;
      • carried through moves: a file_system move or copy of a ledgered file or folder keeps its rows (carry_outside_rows). So does every cp/mv/rsync in an execute command, with the destination joined with the source's name when it is a folder (copy_pairs, carry_run_moves, before the run's mark is decided, overlap or not). A folder holding ledgered files, named in a command (mv repo old_repo), names outside content (r5). Naming marks the request, it does not spread (r7, operator). Only a run that itself reached out (the name rule or a measured connection, run_reached_out) has the files it wrote recorded. A run marked only because it names ledgered content marks the request (its output is outside content) and records nothing. Its cp/mv/rsync copies keep their rows through carry_run_moves. The log says which case ran: "the run reached out" or "the run names outside content … no file it wrote is recorded". The same holds for a detached job. Extraction is a copy: when a command extracts an archive that is ledgered, the files the run created or changed are recorded with the source "extracted from <archive>", even though the run did not reach out (ledgered_extract; foreground runs and detached jobs alike). One table of decompressor families (_EXTRACT_FAMILIES, next to the cp/mv/rsync of copy_pairs) says what extracts:
        • always: unzip and the un* readers (gunzip, bunzip2, unxz, unlzma, unzstd, unlz4);
        • always, as readers: zcat, gzcat, xzcat, bzcat, zstdcat, lzcat, lz4cat;
        • with -d or --decompress: gzip, pigz, xz, bzip2, pbzip2, zstd, lzma, lz4;
        • with the x or e subcommand: 7z, 7za, 7zr, unrar;
        • tar/bsdtar/gtar with x, --extract or --get;
        • cpio -i;
        • python* -m zipfile|tarfile -e|--extract.
        Listing and testing are not extraction (unzip -l/-t/-Z/-v, gunzip -l/-t, tar t, cpio -t). The archive is the tool's own archive argument, read with the followed cwd. For tar that is the -f/--file value, or the first word after an old-style xzf, never a member name. For unzip x, x.zip is tried too. When the extract reads stdin (no archive, or -; -C's value is never the archive), the archive is a ledgered file after its < or named by an earlier stage of the same pipeline, each read in its own followed cwd. Both come from the parsed commands, so quoted text (echo "cat dl.tgz | tar xz" > howto.txt) is not a pipeline, and wrappers such as sudo are read through (cat dl.tgz | sudo tar xz, cd sub && cat ../dl.tgz | tar xzf - -C out, zcat < x.gz > x). Every file a run with such a pipeline writes is recorded, so zcat x.gz | grep k > hits.txt records hits.txt, which is intended. At most 200 paths are resolved per command. Extracting a non-ledgered archive in a folder that holds ledgered files records nothing. Not covered: extraction in inline code (tarfile.open(…).extractall, shutil.unpack_archive), an archive named only through a glob, a loop variable or xargs, and a script that reads a downloaded file and writes a transformed copy. Pre-§4UY had no file ledger at all. Naming is one rule: the command was handed the folder. That means a whole shell argument (read in the folder the run cd-ed into, and in the roots), a whole quoted string (inline code, heredoc) or an assignment value that is a folder holding rows. For a word with * ? [ {, its longest glob-free folder counts (cat repo/*, cat repo/{a,b}, glob.glob('repo/*')). --opt=value counts by its value, and a leading $PWD/ is the current folder. A cd/pushd target, a path prefix (python3 proj/app.py), a word inside a longer string (git commit -m "update proj") and a bare . or .. (git add ., PYTHONPATH=., sys.path.insert(0, '.')) never count. A bare folder name given to any command does (echo proj). A named ledgered file is found anywhere in the original text (heredocs, assignments, inline code, escaped quotes), read against the roots and against every folder the run entered from any root. The text is never rebuilt. Tokens are split in linear time, and a followed folder longer than 1,024 characters is unknown, so a 256k-character command takes under a second. Limit: a run that reads a ledgered file without naming it or handing over its folder does not mark the request. Examples: cd repo && cat *, grep -r x ., tar czf x.tgz ., cat */f.txt, an app that opens the file itself, a path built from pieces, and anything after a popd, which is not followed. Before §4UY there was no ledger, so none of these were marked then either. A version kept of a ledgered file carries its row, and a restore of that version writes the row back (file_versions._carry_outside_row). The runner's own status files (.ghost_status) are never walked.
      A file "changed" is judged by max(st_mtime, st_ctime), because a fetch can set the mtime back. A file the agent itself wrote and nothing changed since is never recorded. The agent's own whole-file write removes a row only in a request that read no outside content (note_agent_write). Overlap: the counters are container-wide, so a run that another sandbox call overlapped records no file. Its measured "yes" marks the current request only: it is never stored for the command text and never handed to a job (r5), so a later run of the same command is not marked by it. Those calls are another execute, a browser call (sandbox_call), or a detached job marked running. Detached jobs: a run promoted to a job hands its record to the job by job id (note_job_started: working directory, snapshot, start time, the foreground window's measured verdict). Where the job lands (delegate._land_sandbox_row → note_detached_job_files), the same rule decides and records its files. Limits: a job started outside execute (the run tool), or one that outlived a restart, records nothing. Files another run creates in the same directory while a job runs count as the job's. A write target behind a variable, ~ or a cd nobody can follow is not seen. A working directory above 20,000 files records no created files;
    • job output;
    • the answers of skills.
    A failed result counts too. A sub-agent inherits its parent's record, and "what you said" for a sub-agent is your message, not the task text the model wrote.
  • No standing instructions from content. A request that read outside content cannot create, watch or stop scheduled tasks or create skills. Ghost says what it would set up and asks you to confirm in a new message.
  • No rules or memories from content. A rule needs your own dictation. The per-turn episode never stores outside content: it is stamped when the turn is journalled, so a later idle pass cannot pick it up. Scratchpad notes are labelled. A conversation summary that includes outside content is kept out of automatic recall.
  • Facts about you come from you. After reading outside content, update_profile and remember save only what your own message states. A quoted "USER: …" line inside a reply is never taken as you speaking. A project constraint the model passes counts as yours only if your message says it.
  • A confirmation is your "yes". To confirm a delete, reset, release or forget preview, your message must open with yes (English or Greek: "yes", "ok", "go ahead", "ναι", "εντάξει" …), quote the token, or pick items, and must not hold back ("wait", "no", "όχι"). A confirm is refused if outside content was read before it in the same request. A whole project folder is deleted (or moved away) only through manage_projects, which shows you a preview first. After outside content, database DROP and TRUNCATE stay locked.
  • Your identifiers stay home. After outside content, Ghost refuses a call that would send your identifiers out, unless your own message contained that value:
    • What counts as an identifier: your full name and surname, birth dates, address, family members' names, phone and email. A lone first name, your city, company, interests and favourites are not identifiers, because ordinary searches need them. The surname on its own counts only where the field is a person's name (your name, a surname field, a family member's name) — the field's key decides (field_kind). The last word of an address is its town or country, not a surname: until §4UY (N4) any multi-word field gave up its last word, so after an outside read a search naming your city was refused as sending your address out (live 5b9ebfd4, 08d2a444). The whole address is still refused.
    • Which calls: search, browser and fact-check calls are checked in full. Local tools and code are checked only in their URLs, so a letter Ghost writes and signs with your name is not egress.
    • Encoded copies: URL-encoded and base64 copies are caught.
    • Your files: code that would send your uploads or memory files over the network is refused, unless your message names your files.
    • If the check itself fails after outside content was read, the call is refused.
  • A notification written after reading outside content is labelled as such.

The confirm-in-a-new-message rule is deliberate: nothing has been read yet in that next request. Pins: tests/test_4mb_content.py.

§4MI (2026-10-08) — the owner's profile is redacted by value

Every stored system prompt carries the USER PROFILE block, and no shape rule knew the values in it. distill/redact.py now reads $GHOST_HOME/system/memory/user_profile.json (re-read when the file changes) and redacts the identity-class values — root (name, address, company, location, birth date), relationships, assets, contact, family — as <REDACTED_PROFILE>, only in a stored trajectory's system_prompt (the field that carries the USER PROFILE block). It is deliberately NOT part of redact_text: that function also writes the memory journal and the episode store, where a placeholder was read back as an owner fact (§4MI re-review). Values match as whole words; a value under 8 characters matches only as written (the city "Nice", not the word "nice"); placeholders such as the stock name "User" are never a rule. Preferences, interests and the role are left (they are the learning signal). Conversation text (requests, replies, tool results) is not rewritten — a first name the owner types stays as typed. Two over-redactions fixed: the OpenAI key rule needs a left boundary (URL slugs like …-musk-2024-annual-report matched), and a 14-digit web.archive.org/web/… stamp is not a card number.
