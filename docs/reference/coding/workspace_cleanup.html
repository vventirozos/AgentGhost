core / workspace_cleanup.py

Mark-and-sweep of a finished project's scratch space. When a project completes, registered deliverables are kept and everything else under its workspace is deleted.

Why

While a project is in flight the agent litters its workspace (<sandbox>/projects/<id>/) with transient files — screenshots, helper scripts, downloaded fixtures, __pycache__, temp output. Historically these survived completion and accumulated. This module removes them automatically the moment a project reaches DONE, leaving only the files the user actually wanted.

The contract

When deliverables are registered, registered file artifacts are kept and everything else is deleted. Anything that should survive cleanup should be registered as a deliverable — either explicitly (the deliverables=[...] argument of the manage_projects task_update action, or ProjectStore.register_file_artifact) or automatically (the research subsystem registers each brief).

Empty-keep-set recovery (2026-06-20). Registration depends on the agent remembering to do it, and it doesn't always: a one-turn single-file build wrote index.html, marked its task DONE without deliverables=[...], and the old "nothing registered ⇒ everything is scratch" rule wiped the project's only file (observed live — the deliverable was gone before the verifier even loaded it). So an empty keep-set is now read as missing registration, not as permission to delete the workspace. The sweep recovers the deliverables (_recover_deliverables): it keeps — and back-registers — every non-debris, non-symlink file, and deletes only categorical debris (_is_debris: bytecode caches, .browser_profile/.browser_runner.py scaffolding, swap/backup files, dotfiles, temp_/tmp_/scratch_/debug_ names). Recovery is deliberately conservative — an image or stray file is kept rather than risk-deleted — because losing a real deliverable is far worse than leaving a stray scratch file. A workspace holding nothing but debris still nets an empty keep-set, so a lone __pycache__ is still swept. The summary gains a recovered list, and an operator WARNING fires so the missing registration is visible.

API

FunctionPurpose
sweep_project_workspace(store, project_id, *, dry_run=False) -> dictDelete every file under the project workspace not registered as a file artifact, then prune the directories left empty. Returns {project_id, status, deleted, kept, dirs_removed, freed_bytes, kept_referenced}. Never raises. dry_run=True reports what it would delete without touching disk.

Safety guards

  • Scoped — only ever walks <sandbox_root>/projects/<id>/; the project dir itself is preserved so a resume still has a workspace.
  • No symlink escape — the walk never follows symlinks; a symlink is removed as scratch but its target outside the tree is untouched.
  • Fail-safe — if the keep-set (the artifact list) can't be read, the sweep deletes nothing and returns status="skipped: artifact read failed".
  • Non-fatal — wrapped end to end; a cleanup failure can never strand a project mid-transition.
  • DONE only — never runs on FAILED / NEEDS_USER, which stay resumable (a revised task can roll them forward to DONE later), so their files survive.

Trigger wiring

The sweep is hung off ProjectStore.on_project_done, a hook fired by _fire_project_done exactly on the transition to DONE — from both _maybe_rollup_project_status (autonomous and task-driven completion both funnel through here) and a manual update_project(status="DONE"). main.py wires the hook to sweep_project_workspace when it constructs the store. Because every completion path ends at store.update_task → rollup, one store-level hook covers them all.

Partial keep-set recovery (2026-07-02)

Observed live (the chess-game build): the agent built four files but registered only one (js/game-state.js) as a deliverable. The old rule — "keep registered, delete everything else" — took that sparse keep-set at face value and deleted index.html and two of the three JS modules at the moment the project completed. The empty-keep-set recovery never fired because the keep-set wasn't empty; one registered file made the sweep destructive. (The build was reconstructed byte-faithfully by replaying the trajectory JSONL's recorded file_system writes/replaces — the trajectory log stores full content / replace_with payloads plus result text with anchored line ranges.)

The contract now treats registration as evidence of what IS a deliverable, never proof of what isn't:

  • Registered file artifacts — always kept (unchanged).
  • Empty keep-set — unchanged: _recover_deliverables keeps + registers every non-debris file, including ambiguous media.
  • Non-empty (partial) keep-set — new: _recover_unregistered_sources keeps + registers every unregistered source/document file (_is_source_like: code, markup, docs, config, text data — .html .js .py .md .json … plus Makefile/README-style names). Unregistered media/binary files (screenshots, renders) stay deletable — they are the scratch the sweep exists to remove; a media deliverable is protected by registering it. In the DONE sweep the debris classifier outranks the source classifier (temp_*.py, *.log, dotfiles still go) — a finished project's scratch is scratch. The idle tidy is the opposite on one rule only, see below. Recovery registers what it keeps, so the record becomes truthful and the next sweep needs no recovery pass. Operator-visible as a ⚠️ Cleanup … keep-set was PARTIAL warning; summary["recovered"] lists the saved files.

Rationale for source-vs-media asymmetry: losing a stray kept file is cheap; losing the build is catastrophic and non-obvious (it happens at the success moment, when nobody is watching for damage).

Recurring tidy — post-completion debris (2026-07-18)

The DONE sweep fires exactly once, on the transition — but verification and post-completion debugging keep producing screenshots and scaffolding after it. Live case: the game project rolled DONE at 21:41 and had six unswept screenshots by the next morning; the operator was deleting them by hand. tidy_project_workspace(store, project_id, min_age_hours=24, dry_run=False) is the recurring counterpart — safe on ANY project status, repeatedly. It deletes only: categorical debris (_is_debris) and unregistered media files (_MEDIA_SUFFIXES) that are older than the age gate, not in the keep-set, AND not referenced by any source file (_referenced_media — basename scan of source-like files ≤8 MB, streamed in 1 MB chunks (raised from 512 KB in §4GK; a file it cannot scan keeps every candidate), so a sprite sheet an index.html points at is treated as an asset, never a screenshot). Source/document files are NEVER deleted here regardless of registration — on a non-terminal project today's unregistered helper script may be tomorrow's deliverable; judging unregistered scratch scripts remains the DONE sweep's job. One workspace_tidy project event records what was removed.

Triggers: idle-scheduler phase 2.7d (job workspace tidy) (idle, every _WORKSPACE_TIDY_COOLDOWN = 6 h, walks all projects, 24 h age gate) and the explicit manage_projects action=cleanup (no age gate — the user asked now). Note the tidy walks only projects/<id>/ trees: stray directories at the sandbox ROOT (repo clones, ad-hoc analysis dirs) are the free-chat workspace and deliberately stay untouched.

Containment + never-debris guards (2026-07-20)

  • Path-escape containment (sweep AND tidy). Both walks now assert the resolved root is strictly inside <sandbox>/projects/ before touching anything (_escapes_projects_root): a project id bearing /, \ or .. — which made _project_dir resolve OUTSIDE the sandbox, so the walk would have deleted the parent tree — deletes nothing and returns status="skipped: path escape". Defense in depth: the tool boundary validates ids too, and any doubt (including an unexpected exception in the check) reads as an escape.
  • .git/ is never cleanup's to delete. _in_git_tree makes both the recurring tidy and the DONE sweep skip the whole subtree — files and legitimately-empty dirs (refs/tags, …) alike — because tidying an in-flight clone corrupts the repo. .git stays in _SCRATCH_DIRS only so the recovery passes don't register its internals as deliverables; the guard is what keeps the files on disk.
  • Config-dotfile variants are not debris. The kept-dotfile set now matches format variants too (_is_kept_dotfile: .eslintrc.json, .babelrc.js, .env.local) — real projects spell them that way, and the exact-match set classified them debris and deleted them.
  • The tidy's age gate covers ALL debris. Categorical debris used to be deleted at any age; on an ACTIVE project a fresh debris-shaped file may be an in-flight tool's live state (a dotfile being written, a log mid-append), so debris now gets the same min_age_hours grace period media always had. The explicit manage_projects action=cleanup still runs with no age gate — the user asked now.
  • _normalize_rel strips workspace/. Artifact payloads are reduced to the exact project-relative key the walk produces — now including a leading /workspace/ / workspace/ segment, and register_file_artifact stores the same normalized form (see memory.projects). An absolute /workspace/projects/<id>/x.png deliverable previously matched no walked rel and was deleted by the very sweep it was registered to survive.
  • The DONE sweep protects referenced media too. The tidy's _referenced_media scan now also runs in the sweep: an unregistered media file that a kept source file points at (sprite sheet, texture, favicon) is an asset of the build, not a stray screenshot — deleting it broke the deliverable the sweep had just protected. The summary gains a kept_referenced list; symlinks stay deletable.

Covered by tests/test_workspace_cleanup.py (path-escape id, git-tree, referenced-media, _normalize_rel) and tests/test_workspace_tidy.py (age-gate-on-debris, config-dotfile variants, path-escape id).

Tests

tests/test_workspace_cleanup.py — keep/delete split, nested deliverables, __pycache__ removal, dry-run, the three skip guards, symlink non-escape, path normalization, dedup registration, the end-to-end "complete a project → workspace swept" flow, and the partial-keep-set recovery suite (chess-scenario regression, idempotent re-registration, debris-outranks-source, registered-vs-unregistered media, dry-run no-registration).

Binary-deliverable partial-recovery (bug-hunt 2026-07-26b)

On a PARTIAL keep-set (some files registered), the DONE sweep deleted an unregistered data/binary deliverable — an app database (.db/.sqlite), trained model weights (.pt/.safetensors/.onnx), or a dataset (.parquet/.npy) — because the partial-recovery only rescued source-like files, and the empty-keep-set recovery (which keeps everything non-debris) doesn't run once ANY file is registered. A coding project's seeded data.db / model.pt vanished at the moment of completion when app.py alone was registered. The recovery now also rescues _is_data_deliverable files; media scratch (screenshots, renders) stays deletable. Tests: tests/test_bughunt_fixes_2026_07_26b.py::TestDataDeliverableRecovery.

Documents and files the project names are kept (§4SS, 2026-11-01)

Request b45ec99f compiled the project's final report.pdf (and a copy, report_pdf.pdf, 81,019 bytes each). It closed the task with a result ("Wrote report.pdf (81019 bytes)") but no deliverables=[...], so the project turned DONE with only some files registered. A .pdf is neither source-like nor a data deliverable, so the sweep deleted both 40 s later ("freed 162,038 bytes"), even though the goal itself said "deliver a final PDF report". Two rules now apply on a partial keep-set:

  • Rendered documents are recovered. _is_document_deliverable: .pdf, .docx/.doc/.odt/.rtf/.epub, .pptx/.ppt/.odp/.key, .xlsx/.xls/.ods/.pages/.numbers (case-insensitive). They are kept and registered like a recovered source file.
  • A file the project names is kept. _named_by_project reads the goal and every task's description and result_summary (_project_texts). _named_tokens splits that text once into path-shaped runs (letters, digits, _ . - /). Each / segment, minus trailing sentence dots, is a name, and each trailing chain of segments is a path. A file with an extension is kept when its basename is one of the names. A media file must be named by its path relative to the project, so "checked screenshot.png" keeps only a root screenshot.png, not every screenshot in the tree. A longer token never names a shorter file: "old_report.pdf", "final.report.pdf", "report.pdf.bak" and "report.pdf-old" do not name report.pdf. A name without an extension ("data", "results") is an ordinary word. Names are matched against files that exist, so text can only keep a file, never delete one. Debris and symlinks are never kept this way. The first version ran one regex per file over the whole text: the review measured 9 s for a 10k-file node_modules tree, on the event loop. Backslashes are read as / (Windows paths), text and file names are compared NFC-normalised, and only the last _PATH_CHAIN_MAX = 32 segments of one run are recorded as paths (a 10k-segment run built 150 MB of strings). Names with spaces ("Screen Shot 1.png") are not matched. _mark_removal now keeps up to _MARK_MAX_PATHS = 512 deleted paths per project (1,024 merged; was 64/128), so a sweep of 81 files no longer makes the reply call its last file "not created". The sweep reports what only this rule saved as summary["kept_named"]. The idle tidy applies the same rule to its media candidates, so a "→ assets/title.png" deliverable is not swept as a screenshot after 24 h. If the tasks cannot be read, the other protections still apply.

The removal mark (_mark_removal, above) is now read by the reply too. A link to a file a fresh sweep removed is no longer reported as never created: see core.agent §4SS. Tests: tests/test_4ss_b45ec99f_fixes.py.

The DONE sweep moves files to a trash (§4SU Phase 0, 2026-11-02)

The audit found that the sweep still lost real deliverables. A .zip, a font, audio, weights or a results/train.log named by no task were deleted, because recovery works from suffix lists and the reference check only knows images. The sweep no longer unlinks a regular file: it moves it to the host trash <memory_dir>/../project_trash/<YYYYMMDD>/<project>/<rel> (project_trash_dir, _to_project_trash). That is outside the sandbox and out of the snapshots (memory/snapshot.py skips project_trash). A name collision gets a .N suffix. A symlink is still only unlinked, and a file that cannot be moved is deleted as before. Day folders older than PROJECT_TRASH_KEEP_DAYS (30) are purged after each sweep (purge_project_trash). Each real sweep logs a workspace_sweep event (moved and deleted: up to 200 paths each, count, freed_bytes, trash). The move uses shutil.move, so a trash on another disk still works, so a lost file is traceable from the project's history; the b45ec99f PDF needed log forensics. The summary's deleted list now means "moved out of the workspace". A .log file that the goal or a task names ("wrote results/train.log") is kept as output, not debris.

Two lifecycles, opposite correct answers 2026-08-11

DONE sweep — the project is finished, so a scratch-named file is scratch and goes. Idle tidy — the project is still being worked on, and deleting debug_utils.py out from under a build that imports it is the harm. §4AT measured the tidy deleting debug_utils.py, temp_loader.py, scratch_notes.py, tmp_fix.py and .gitlab-ci.yml from ACTIVE projects, against this module's own stated contract.

_tidy_is_debris() is everything _is_debris() says, with one exception: a scratch NAME PREFIX alone cannot condemn a file that is source. Scratch dirs, scaffolding names, non-kept dotfiles and scratch suffixes all still outrank source-ness — so .browser_runner.py and __pycache__/*.pyc are still collected. ⚠ This took three attempts, each narrowing the scope. Inverting the precedence inside _is_debris broke the DONE sweep; a blanket “source-like ⇒ skip” in the tidy then kept browser scaffolding. The exemption belongs to one rule, not to the classifier and not to the caller.

Protection is case-folded, everywhere 2026-08-11

A deliverable registered assets/hero.png and written assets/Hero.png was unprotected and deleted — by the sweep and the tidy. On macOS those are ONE file, so nothing else in the stack surfaces the drift. _lower_keys() projects each protection set once per walk, applied at every membership site including the referenced-media check — half-applied is the failure mode. ⚠ A set subclass was tried first and was a landmine: update, |=, discard, clear, copy, union, -, &, ^ were all unguarded, several silently returning a plain set, and it missed _recover_deliverables entirely.

One payload, one key 2026-08-11

_normalize_rel now collapses repeated separators before stripping each prefix once, so a doubled slash cannot key a file differently from ProjectStore._normalize_rel_path. ⚠ A fixed-point loop was tried first and was worse: it also ate a project's legitimate top-level workspace/ directory, deleting the registered file inside it. A repeated real directory name is data, not a prefix to peel. The differential test GENERATES a prefix×tail cross-product (72 payloads) — its first version used 9 hand-picked payloads containing none of the divergent shapes.
