tools / execute.py

Sandboxed code execution with multiple validation guards and stateful Jupyter support.

Budget overrun is a PROMOTION, not a kill 2026-08-11

Every sandboxed run has a 600 s budget (_EXEC_TIMEOUT_S). Reaching it used to mean the process was killed, exit 124 came back, the turn loop scored a transient strike, and the model re-ran the identical command — the observed shape (a yt-dlp download over Tor) that turned ten minutes of loss into forty.

Since 2026-08-12 a run that is still WORKING is detached at 90 s, not at the budget: waiting out ten minutes to reach a decision that was obvious at ninety seconds is pure latency. The 600 s budget keeps its other job — killing a command that has gone quiet — so a silent, purely-computational run gets exactly the patience it always had. See sandbox.jobs for why those are two different questions, and why early promotion is only safe because a landed job wakes the model.

A run that is still ALIVE and still PROGRESSING at the budget is now DETACHED as a supervised job instead (sandbox.jobs owns the decision and the process; that page documents the progress discriminator and the lifetime cap). What this tool contributes:

  • The result is not a failure. It carries EXIT CODE: 0 (STILL RUNNING — promoted to background job …, NOT finished). The turn loop matches EXIT CODE:\s*(\d+), so the annotation rides after the digits and no strike is burned. This matters beyond the log: strike accounting feeds outcome labels (and, until §4PJ, calibration).
  • …and it says so in a way MACHINES can read. Success-shaped is exactly what a dozen other consumers must not take this for, so the first line carries the literal marker [SANDBOX JOB PROMOTED] — in the FIRST line, so it survives the [:120]/[:200] head slices those readers take — and each grader tests for it. Two of those decisions are consequential and unattended: the verify gate in project_advancer marks a project task DONE — a 600 s+ pytest would have passed it — and the acquired_skills TDD gate INSTALLS a skill. Foresight resolution (foresight removed 2026-10-11, §4NM) and the metacog competence record (removed in §4PJ, 2026-10-16) were skipped entirely: an unfinished command has no outcome, and recording either verdict would be a fabrication.
  • The re-run is foreclosed mechanically, not just in prose. An identical command that is already running as a job returns THAT job rather than starting a second copy — see sandbox.jobs.
  • The retry is foreclosed in words — "Do NOT re-run this command", the job id, how to poll (since §4SX D5 run(action='status', name='job-…'): the promoted job is recorded as a job run named after its id by runs.record_promoted_job; with no run row, the old jobs(action='status', job_id=…) wording), how to read the live log, how to cancel, and an explicit instruction to finish the turn and report rather than wait. The retry is the expensive half of the original failure, so this line is the fix, not politeness.
  • The workspace ledger records it honestly — exit 0 with the note "still running — promoted to background job <id>", rather than the failure label the strike accounting no longer takes.
  • A promoted ephemeral script is NOT deleted. The finally cleanup skips the file when the run was promoted — the detached process is still executing it (bash reads its script incrementally).
  • Stateful (Jupyter) runs opt out. A promoted cell would leave the kernel busy for every later cell, and its runner files are deleted on the way out.
  • Capability is declared, not sniffed. The promotable path is taken only when the manager sets supports_job_promotion = True; a hasattr probe would capture every MagicMock stub (it answers for any attribute) and unpack a mock as a 3-tuple.

GHOST_SANDBOX_JOBS=0 restores the old kill-at-the-budget behaviour exactly. Covered by tests/test_execute_job_promotion.py.

Scope-flap heal — file-not-found with NO project cwd (2026-07-18)

The /workspace→project remap heal is gated on the workdir kwarg — i.e. it is DISABLED exactly when a call ran without project scoping. Stateful sessions opt out of scoping by design (the kernel conn file is pinned to /workspace), and a transient scope clear does the same — so a relative python3 extract_data.py resolved against /workspace and died while the file sat in the project dir. Live request 9c9b75aa burned FOUR strikes on this one repeated infra failure (the model even ran pwd, saw the right cwd on a scoped call, retried, failed again). Now: file-not-found + no workdir kwarg + a canonical project id on the workspace-model mirror → one retry from /workspace/projects/<id>, with a note naming the mechanism ("this call opted out of project scoping — most often stateful=true") so the model stops guessing. Covered by tests/test_execute_path_and_exit1_heal.py (§5).

Heal-retry safety — never re-run a command that already ran 2026-07-22

The cwd-heals above re-run a command when its output looks like a wrong-cwd file-not-found. Two shapes were being re-run that must NOT be, because the command already executed and a second run would repeat its side effects (DB inserts, appends, API calls) or double a 600 s wall-clock:

  • Timeout kills — _TIMEOUT_KILL_CODES (124/137/143) are now excluded from both heal triggers. A command killed at its budget whose accumulated output happens to mention ENOENT (pip/wget noise) is no longer silently re-run for another full budget. Since 2026-08-11 exit 124 also means something narrower: the budget expired AND the command had gone quiet — no log growth and no movement in its own I/O counters — or the concurrency cap left no slot to track it in. A still-working command is promoted to a job instead, and returns exit 0 with a promotion banner.
  • Ran-then-missing-data-file — _looks_like_file_not_found now returns False when the output contains a Python Traceback: a traceback means the interpreter found and ran the script, so a "no such file" inside it is a runtime data-file error after side effects, not a wrong-cwd miss. A genuine wrong-cwd miss is a startup error (can't open file '…') with no traceback, so the legitimate heal is unaffected.

Covered by tests/test_execute_heal_timeout_guard.py. Paired with the sandbox exec-deadline + infra-error marking (an infrastructure failure now returns [SANDBOX INFRA ERROR — not your code] instead of a bare exit 1, which this heuristic also correctly declines to heal).

Tool: execute

Three execution modes selected from arguments:

1. Bash command (line 1095-1676)

  • §4UY C1: REMOVED. The rewrite below no longer exists — a command runs exactly as written (a cd to a missing folder fails and says so). It once turned cd /opt/scratch && rm -rf * into rm -rf * in the project folder; 0 firings in the log. History: auto-stripped invalid cd /sandbox / cd /home/user / cd /root / cd /app / cd /opt / cd /usr/src prefixes. (§4HZ, 2026-09-17) /tmp is no longer in that list — it exists in the container (request d594668e wrote /tmp/mars.json and downloaded to /tmp/grig_test.grib through it, then had cd /tmp && python3 download_grib.py silently rewritten to run from /workspace and concluded "the cd didn't take effect in the sandbox shell"; three turns). The strip is now also announced in the tool result ([SYSTEM NOTE: the leading `cd /sandbox &&` was REMOVED … ran from /workspace instead]) on both exit paths, not only in the operator's log — a silent rewrite reads as a broken shell. Pins: tests/test_execute_cd_strip_tmp.py.
  • Handles substantive inline -c scripts (≥120 chars, 2+ statements, or import+nested-quotes). The match fires after an optional command-separator prefix — cd <dir> && python3 -c "…", not only a start-anchored python3 -c — because the model almost always works inside a project subdir. (2026-06-30) Auto-convert, don't just reject. The block used to reject every substantive body and force the model to re-emit as file_system(write)+execute — a wasted turn each, fired on perfectly well-formed scripts (the operator saw a steady stream of 🛡️ Inline Script Blocked warnings on multi-statement one-liners and long bodies that would have run fine). Now a well-formed body is auto-converted into an in-sandbox file run: the body is extracted with shlex (byte-identical to bash's own unquoting) and shipped into the container via base64 (printf %s <b64> | base64 -d > /tmp/_ghost_inline_*.py && python3 /tmp/_ghost_inline_*.py), so bash quoting can't corrupt it. Any cd … && prefix is preserved so relative paths resolve as before; bash -c bodies convert to a .sh file. The auto-convert fires only when it is provably quote-safe: the captured body contains no unescaped copy of the outer delimiter quote (an escaped \" is fine — shlex unescapes it correctly). This precise check replaces the old import+both-quote-types heuristic, which over-blocked valid escaped bodies. Covered by tests/test_inline_c_autoconvert.py and tests/test_inline_c_guard_cd_prefix.py.
  • Still hard-BLOCK (no auto-convert) only for the two shapes a redirect genuinely helps: a body with an unescaped nested delimiter quote (the real bash-split corruption shape) or that shlex can't parse / has a trailing pipe-or-redirect we won't faithfully reconstruct — re-emitting cleanly via write+execute is the fix; and an acquired-skill call wrapped in -c (see next bullet).
  • Acquired-skill invocation nudge (2026-04-24). When the blocked body looks like a failed attempt to call an acquired skill — from X import X where module and symbol names match, or acquired_skills/X.py in a subprocess call — the SYSTEM BLOCK error appends a targeted HINT: pointing at the canonical invocation: "Acquired skills are TOP-LEVEL TOOLS. Invoke it directly as X(...)." This shortcut exists because after the skill-storage relocation (skills live under $GHOST_HOME/system/memory/acquired_skills/, not inside the sandbox), the LLM can no longer see the skill via ls and its first instinct is often to wrap the call in python -c / subprocess. Hint fires only on the narrow patterns above; a body that blocks for a non-skill reason keeps the generic message, and an unrelated quote-safe body now auto-converts and runs (no block at all). Covered by tests/test_acquired_skill_invocation_nudge.py.
  • Executes via sandbox_manager.execute(bash -c ...) with the 600 s _EXEC_TIMEOUT_S budget.

Exit 137 four seconds in is not a timeout §4HZ · 2026-09-17

Exit 137 is SIGKILL, and two hands send it: timeout -k 5s once the 600 s budget expired, and the kernel OOM killer at any moment. _format_error named the timeout for both. Request 0e6cf008: a plot script over a 7.4M-point grid died with 137 after 4 s (212 s the first time) under a 4 g sandbox, was told "timed out / killed after 600s — shrink the workload", and the model spent four turns timing imports and roots_legendre before guessing memory on its own. The elapsed time (_dt) was measured on the very line the code was classified and never passed in.

Now _format_error(…, elapsed_s=_dt): a 137 that lands more than _OOM_KILL_MARGIN_S (30 s) under the budget (_kill_is_oom) is reported as (KILLED after 4s — far under the 600s budget: out of memory, not the time limit) with a hint that names the cap (GHOST_SANDBOX_MEM, the same env the sandbox layer reads) and says what actually helps — chunking, no full-grid temporaries, subsample before plotting, del, float32. 124 (timeout's own code) and 143 (its SIGTERM) keep the timeout wording; so does a 137 at the budget. The banner line avoids the words "timeout"/"timed out" on purpose: the strike classifier (tool_failure._RETRYABLE_PATTERNS) strips the hint block but reads the banner, and an OOM is deterministic — it must not spend the 4-strike transient budget. Pins: tests/test_execute_oom_vs_timeout.py.

The status the run reported beats the 0 the shell returned §4HZ · 2026-09-17

The model ends commands with ; echo "exit=$?" or echo "=== exit: $? ===". The LAST command is then an echo, bash returns 0, and the tool logged execution ok · exit 0 over a Python traceback followed by exit=1, over bash: line 1: 1008 Killed timeout 400 python3 … (an OOM mid-run), and over ERROR: No matching distribution found … === exit: 1 ===. Measured on 2026-09-17: the strike counter fell from 4/6 to 1/6 on one such line, System 3's chosen recovery ("capture the full pip output") was booked a success while changing nothing, and 8 of the day's 30 "execution ok" lines carried failure text (2.1% of all such lines since 2026-08-04). Pipefail cannot see it — there is no pipe.

§4UY C9/C10: superseded by the one exit-status rule in §4UY — no output text is read as a status any more. History: _self_reported_exit(command, code, output) adopted the status the run itself reported when the shell's is 0, on two literal signals: the command text contains $? and the output carries an exit=N / exit code: N line with N ≠ 0 (the last such line wins — a multi-probe script summarises with its trailing echo); or bash's own job line bash: line N: <pid> Killed (→ 137). A command without $? is untouched: cat crash.log printing "exit=1" is data. _normalise_exit is now the normaliser — pipe forgiveness (§4GE) first, then the self-report, then pipe forgiveness again on the echoed code (under pipefail $? is the pipeline's raw status, so | head -1; echo "exit=$?" reports a SIGPIPE'd producer) — and every adoption of a model-shell result in tool_execute (primary run, scope-flap heal, /workspace remap, root retry) goes through it. Pins: tests/test_execute_self_reported_exit.py (real bash + the container's literal strings + an AST enumeration of the adoption sites that fails on a fifth un-normalised one).

A pipeline's failure is the pipeline's failure 2026-09-09

The shell now runs bash -c 'set -o pipefail; …' (one home, _bash_c, used by the primary run and the project-path remap retry). Request e0f4a8bd ran python3 probe.py 2>&1 | head -200 twice; probe.py raised a Traceback both times and the tool logged execution ok · exit 0, because bash returns the status of the LAST command in a pipeline and head succeeded. The 6-strike budget was never charged, the failure taught the model nothing, and the log printed a status beside its own contradiction.

The exemption that keeps it honest. Naive pipefail breaks the far commoner <producer> | head -N, where the closing pipe KILLS the producer. On the development host standard tools report 141 (SIGPIPE) and Python 120 (a failed stdout flush at shutdown), so a code-only exemption looked sufficient — and passed every test.

⚠ The host lied, and only the real container said so. Run inside the live sandbox (Debian, bash 5.2, CPython 3.11) the same truncated pipeline exits 1: Python raises BrokenPipeError as an ordinary uncaught exception, which is indistinguishable by exit code from a script that genuinely failed. A code-only exemption would therefore have turned every truncated … | head in production into a strike — trading a silent-failure bug for a loud false-failure one. So the second signal is the runtime NAMING the broken pipe (BrokenPipeError / Broken pipe / SIGPIPE) in output that is captured anyway: a real ModuleNotFoundError through | head keeps its strike, a pipe closed by head does not. Both the primary run and the remap retry pass their output. Verified by running all nine cases inside the live container. Pins: tests/test_execute_pipefail.py (42 — every shell claim executed against a real bash, plus the container's measured shapes replayed end to end); battery 18/18.

Path & exit-code healing (2026-07-02)

Four fixes from the 2026-07-01 chess-game trace (rounds a4e1b33d / a4a2ce04 in ghost-agent.log), where the agent looped 10+ turns on files it had just written. All covered by tests/test_execute_path_and_exit1_heal.py.

  • File-run path derives from the healed host path. execute(filename=...) used to derive the container-side run path with a hand-rolled strip (lstrip("/") + drop a sandbox/ prefix) that had diverged from _get_safe_path's healing: filename="/workspace/game.py" under an active project WROTE <proj>/game.py but RAN python3 -u workspace/game.py → ENOENT, every retry identical. The run path is now host_path.relative_to(sandbox_dir), so write and run always target the same file (sandbox/foo.py symmetry included — the old code stripped that prefix on run but not on write).
  • /workspace → project-workdir remap fallback. When a project is active, file_system heals /workspace/game.py into the project dir, but a shell command's absolute /workspace/game.py stayed at the sandbox root — so file read succeeded while python3 /workspace/game.py ENOENT'd, an asymmetry the model cannot see. Now, if a project-scoped shell command fails with a file-not-found signature and references /workspace (word-boundary match, and not already the scoped dir), it is retried once with /workspace remapped to /workspace/projects/<id>. On success the result carries a [SYSTEM NOTE: … remapped …] so the model learns the real layout; on failure the ORIGINAL error (the path the model asked for) is kept. Commands with no /workspace reference keep the pre-existing root-cwd retry.
  • grep-family exit 1 with no output = "no matches", not a strike. grep/egrep/fgrep/zgrep/rg/pgrep exit 1 to mean "no matches" — the agent loop scored that as an execution failure (Strike 1/6 … [SYSTEM ERROR]: Process failed (Exit 1) with no output, observed on a grep that was correctly proving a fix had landed). Exit exactly 1 with no output (including the docker layer's [SYSTEM ERROR]…with no output. sentinel), where the LAST pipeline segment's command is in the grep family, now returns a success-shaped result (EXIT CODE: 0) stating that exit 1 meant NOT FOUND. Genuine grep errors (exit 2, stderr output) still fail.
  • Inline -c auto-convert keeps cwd import semantics. python -c "…" puts the CWD on sys.path; the converted /tmp/_ghost_inline_*.py file run put /tmp there instead, so a body importing a module in the working directory (from chess_engine import Board) failed with ModuleNotFoundError — only BECAUSE of the conversion. The converted python run now carries PYTHONPATH="$PWD${PYTHONPATH:+:$PYTHONPATH}"; bash -c conversions are untouched.

2. File execution (line 1677 on)

  • Validates extension: only .py, .sh, .js.
  • Syntax check via sanitize_code().
  • Forbidden module guard: rejects imports of native tool modules (knowledge_base, execute, web_search, …).
  • HTML guard: HTML/CSS detected in a .py file → redirect user to file_system.
  • "Stubbornness" guard: skip rewriting an unchanged file.

3. Stateful Jupyter (line 1827 on)

  • Boots persistent ipykernel_launcher if not running — decided by _kernel_alive: the connection file exists AND KERNEL_LIVENESS_PROBE (pgrep -f '[i]pykernel_launcher') finds a process. Until §4GI (2026-09-13) the probe was a bare pgrep -f ipykernel_launcher, which matched its own timeout … sh -c wrapper (exit 0 with no kernel, verified live): a stale .kernel.json — the bind mount survives every container restart — read as alive forever and every stateful run failed "Kernel did not become ready". The bracket idiom matches the kernel's argv but not the literal in the wrapper's argv (memory the-probe-carries-its-own-pattern); pinned with a simulated process table.
  • Wraps via jupyter_client.BlockingKernelClient.
  • Calls kc.wait_for_ready(timeout=10) BEFORE kc.execute() — without this, is_alive() false-negatives for ~1 s after start_channels() while the heartbeat channel hasn't exchanged yet. The runner's except queue.Empty branch reads is_alive() as a "kernel died?" probe, so every FIRST stateful execute of a session used to emit [SYSTEM ERROR: Kernel Terminated Abruptly (Did the script call os._exit()?)] even though the script hadn't run. wait_for_ready closes the race; a genuine launch failure surfaces as a distinct [SYSTEM ERROR: Kernel did not become ready within 10s] message so reflection can distinguish launch failure from runtime crash. Covered by tests/test_execute_jupyter_wait_for_ready.py.
  • Streams stdout / stderr; detects 5-min timeout or mid-execution kernel death.

Output handling — one policy + spill-to-file (2026-07-07)

Truncation is owned by the sandbox layer via one shared helper, utils.text_truncate.truncate_head_tail(text, budget, label) (head 25% / tail 75% by default — tracebacks print the exception at the end). Before, four call sites each had their own budget and message shape (docker 256 KB, execute.py's dead 512 KB layer that never fired behind docker, file_search 40 KB, browser 64 KB); at --max-context 240000 docker's 256 KB was the only real gate, so one noisy pip install / test run could inject ~70 K tokens that then persisted in history and re-prefilled every subsequent turn.

The execute tool now runs in spill mode (DockerSandbox.execute(spill_large_output=True)): the returned view is small (~24 KB head+tail) and the FULL output is written to a workspace run-log .ghost_runs/run_<n>.log (disk-bounded, 10 MB ceiling) with a pointer telling the model to inspect it via file_system (operation='search' for lines, operation='read' with start_line/end_line). Truncation becomes an affordance instead of information loss. Both the script path and the bare-bash path (which previously had no tool-level trim at all) use it. Non-execute callers of sandbox_manager.execute (ripgrep search, find, browser) keep the legacy 256 KB head+tail and do not spill. The dead 512 KB execute.py layer is removed. Covered by tests/test_execute_output_spill.py.

Safety guards summary

  • Forbidden imports — regex rejection in Python source.
  • HTML/CSS guard — detects and rejects.
  • SQL — out of scope: there is no local database (SQL runs on a lab machine, §4SX E).
  • Inline script handling — auto-converts substantive -c usage to a base64-transported file run; hard-blocks only unsafe/skill-wrap shapes.
  • Output truncation — head + tail capping.

Import guards relaxed off the small-model era (2026-06-22)

Both import-related guards over-fired on a strong model's legitimate code:

  • Inline -c: an import is no longer a block trigger by itself. The real corruption mode is NESTED QUOTES in the inline body mangled by bash escaping, so an import only triggers the block when the body ALSO mixes both quote types. A clean probe like python3 -c "import sys; print(sys.path)" — which the block message itself used to advertise as allowed, a self-contradiction — now passes. (2026-06-30 superseded) the 120-char / 2-semicolon / import+nested-quote cases no longer redirect at all when they're quote-safe — they auto-convert to a file run (see the Bash-command guards above). Only an unescaped-nested-quote body, an unparseable/piped form, or an acquired-skill wrap still blocked — and since 2026-07-14 an unescaped-nested-quote python body is rescued too when its raw captured text parses as valid Python (see the AST-rescue section below); the remaining hard blocks are non-Python/piped forms, syntactically-invalid bodies, and skill wraps.
  • Native-tool import blocklist narrowed. The generic names file_system (a very common module name), scratchpad, recall, replan were REMOVED — they collide with local modules (a local file_system.py helper was getting hard-blocked). browser is KEPT (a prominent native tool the model does hallucinate importing, with a dedicated guard test). The other unambiguous tool names (knowledge_base, web_search, vision_analysis, …) remain. Covered by tests/test_inline_c_guard_cd_prefix.py and tests/test_acquired_skill_invocation_nudge.py.

Sandbox egress guard — the agent's own ports (2026-07-05)

The sandbox container has its own loopback, so 127.0.0.1:8000 in there is NOT the agent's API and :8088 is not the upstream LLM. Three separate incidents (2026-07-02, 07-04, 07-05 request C5) followed the same script: the model curl-tests the port from inside the sandbox, reads the connection failure as "the server is down on the user's machine", and writes a mock/stand-in server — the forbidden engine. The CRITICAL SANDBOX FACT prompt rule did not prevent the third incident (the model quoted it in its own thinking, then trusted its curl anyway), so the probe itself is now intercepted.

tool_execute scans BOTH the shell command and inline code content for (127.0.0.1|localhost|0.0.0.0):(8000|8088) before any execution. A hit returns a ground-truth explanation (🛡️ Sandbox Egress Guard log line) instead of running: the servers are fine on the host, a failure in here proves nothing, verify via the browser tool or ask the user, bind a different port (e.g. 8081) for genuine in-sandbox servers, and NEVER write a mock. Returned as a plain instruction — not an EXIT CODE failure — so it teaches without burning a strike. Deliberately narrow: colon-forms only (an nc -z 0.0.0.0 8000 without a colon passes — acceptable false negative; the guard exists to break the curl-misdiagnosis chain, not to firewall). Covered by tests/test_sandbox_agent_port_guard.py.

Host-process blind spot (2026-07-08)

The sandbox has its own PID namespace: a process the USER started on the host (their python app.py) is invisible and unkillable from inside. A pkill -f app.py therefore succeeds — exit 0, no output, nothing killed — and the model concludes it restarted the server, then keeps debugging against stale code (observed twice in the chess session). Same family as the loopback blind spot: the exit code lies, so the tool must tell the truth. A name-based kill (pkill/killall/kill $(pgrep …)) now appends a ground-truth note to the result on BOTH outcomes — the "successful" one is the dangerous case — telling the model to ask the user to restart the process instead. The execute schema warns up front. Covered by tests/test_host_process_and_verdict_clarity.py.

Egress guard: usage-context matching (2026-07-08)

The agent-port egress guard previously blocked any command or content mentioning 127.0.0.1:8000/:8088. Observed false positive (chess session): a heredoc writing a file whose text legitimately references the agent's API was blocked — composing with the pre-flight guard to leave the model zero legal write paths. Shell commands are now judged by _command_probes_agent_port: heredoc bodies are stripped (they are data, not execution) and a network-client token (curl/wget/nc/requests/urllib/httpx/…) must co-occur with the URL. Direct probes stay blocked, including after a heredoc; echo/sed text manipulation is allowed. Inline content (code that executes) keeps the strict any-match rule, and the guard message now names the legal path for file-writing (file_system write / heredoc). Covered by tests/test_guard_box_fixes.py.

2026-07-14 audit fixes

  • Root-anchored files run via container-absolute paths. file_system's 2026-07-14 root-anchoring means _get_safe_path can legitimately resolve a filename to the OUTER sandbox root under a project-scoped session (e.g. /workspace/x.py whose file exists only at the root). The scoped relative_to then raises, and the legacy lstrip("/") fallback minted a phantom workspace/x.py relative path → ENOENT from the scoped cwd. Such files now run as /workspace/<rel> — cwd-independent, and the same file the read/write touched.
  • Not-found retries keep spill_large_output (both the /workspace-remap retry and the root-cwd retry previously dropped it — a noisy retried command dumped its full output into context, the exact flood spill mode exists to prevent), and the root-cwd retry now announces it ran from the sandbox ROOT so the model stops re-issuing scoped-relative paths.
  • Script-branch workspace gate implemented. The command-outcome capture comment claimed parity with the bash branch ("failures always, successes only when >5s") but no gate existed — every fast successful script run was recorded with duration 0.0, spamming the activity ledger. The branch now times the run and applies the same gate with the real duration.
  • Loopback ground truth on run-existing-file (non-blocking). The egress guard vets command and inline content, but a script WRITTEN earlier (file_system writes are deliberately ungated) and executed by name was never checked — and hard-blocking would seal off legitimate apps that reference the agent's URL by design. The run now proceeds, but when the loaded source matches the probe signature (agent-port URL + a network client) the result carries a SANDBOX LOOPBACK BLIND SPOT note, cutting off the "connection refused → write a mock server" misdiagnosis chain without any false-positive blocking.

Covered by tests/test_execute_audit_fixes.py.

Remap teaching note rides FAILED runs too (2026-07-17)

The /workspace→project-scope remap retry appended its "reference project files by BARE relative path" SYSTEM NOTE only on exit-0 runs. Req A3: both early remapped runs failed for their own reasons (the model's parser crashing on assembly expressions), so the model was never told its paths were being rewritten and misaddressed /workspace for all 22 turns — five silent heals, zero learning.
