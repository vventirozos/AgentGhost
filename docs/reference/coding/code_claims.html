core / code_claims.py — did this turn RUN what it wrote?

The claim-keyed arm of the unverified-write guard (§4PH, 2026-10-15): a reply that says the code works, was tested or passes is checked against the turn's own write/run ledger, whatever the last tool was.

Why it exists

Until §4PH the one mechanical guard between a coding turn and a false "it works" was _is_unverified_mutation(last_tool) in core.agent: it fired only when the turn's LAST action was a successful whole-file write. A trailing ls, a read-back of the file, python --version — anything — cleared it, and nothing anywhere read the reply's own claim. Reproduced by the §4PH readers: write 3,000 chars → execute ls → "I tested it and it works" shipped clean (no note, no failed label, the project work_log said completed with the claim as its note); a file whose only run FAILED with a traceback shipped under "all tests pass". The corpus agreed: of 82 owner replies claiming works/tested/verified, 27 ran nothing; 1 of 158 coding turns ran a test runner; both released apps carried demonstrable bugs behind "Verified: calendar render".

The ledger

FunctionBehaviour
code_evidence(tools_run)key (basename, case-folded) → {path, write_idx, run_idx, run_ok, via}. Writes: a file_system SUCCESS confirmation (write / append / edit / replace shapes, via the same anchored parser the FILE-ARTIFACT check uses), a shell heredoc / redirect / tee inside an execute command, or execute(filename=, content=). Runs: an execute whose command, filename, args or ephemeral script text names the file (an import x counts as x.py), a test-suite run (is_suite_command) for every non-web file, a browser / vision_analysis call whose url/path names a page. ORDER matters: only a run AFTER the last write counts, a run before the final edit tested an older version. A detached (promoted) run is neither a pass nor a failure.
unbacked_code_writes(tools_run)(never_run, failed_last) — code files whose final version nothing ran / loaded, and those whose last run after the final write failed (exit ≠ 0, a declared failed status, a browser STATUS other than OK).
claims_code_works(reply)The first affirmative works / tested / verified / passes phrase ("it works", "all tests pass", "tested, works", "I ran it", "works as expected", Greek "δουλεύει" / "το έτρεξα"), or "". A negation, conditional or future in the same clause ("could not test", "untested", "should work", "cannot confirm it works", "if the tests pass") is not a claim.
unbacked_claim_note(reply, tools_run, forbids_running)The note and failed label for a claim with no backing run — ONE wording for both delivery paths: "⚠ Unverified claim: this reply says "…", but app.py was written this turn and never run. Treat it as UNTESTED…" (or "…the last run of app.py after it was written FAILED. Treat it as BROKEN until a run passes."). A request that said "don't run it" is said, not failed (§4KW) — but the claim is still named as unbacked.
unbacked_claim_directive(reply, tools_run)The in-loop repair directive, naming the file: run it or its tests (load a page), read the result, fix or say so, then answer naming what was run.

Where it is wired

  • _unverified_mutation_note(last_tool, request, tools_run, reply) — when the last-tool shape does not fire, the claim arm runs over reply. Finalize passes its final content, the stream drain its accumulated content; both append the note and stamp the trajectory failed with UNVERIFIED_MUTATION_REASON (a prior a late PASS may lift). The streamed project work_log now books the same turn verifier:failed too (it booked "completed" with the claim as the note).
  • _run_internal_turn (the in-loop repair gate) — unbacked_claim_directive over the delivery view forces the "actually RUN it" re-entry on both verdict branches; after the repair round the post-loop note re-reads the ledger, so an ls in reply to the directive still lands the note.
  • No size or shape exemption: the operator's 2026-09-23 decision (no footer on a correct small write; targeted edits exempt) was about a write with NO claim. A reply that affirmatively says "tested" about a 400-byte run.sh nothing ran is a false statement at any size. A write with no claim and a trailing tool is unchanged.

The reader's round (r3)

A fresh reader of the diff found the first cut over-eager in both directions, all reproduced and fixed: the detector matched mechanism prose ("This works by splitting…", "a regex which works on both") and honest reporting ("I ran the tests and 2 of 5 failed") — now `that|which` are not subjects, a mechanism preposition after "works" disqualifies, and "I ran/tested X" needs an outcome word; the ledger missed python -m app, python -c 'import calc; …', uvicorn main:app and a load of the served root — now imports are read from the command, -m and mod:app targets map to mod.py, a root URL names index.html; and a collected job's banner (under the "Collected N finished job(s)" header) must still yield its exit code to _exec_ok (see tool_failure). One battery mutant proved equivalent (the "run before the last write" guard — a later write replaces the record) and the dead guard was removed.

Residuals

  • Two files with the same basename in different directories share a key (a run of either backs both).
  • A run is identified by NAME: python3 app.py that imports a changed util.py backs app.py only; a suite run backs every non-web file written. A page is backed by any OK load of its basename.
  • The detector reads English and a little Greek; a claim phrased some other way is not caught (fail-open: a missed note, never a false one on a backed file).
