core / code_claims.py — did this turn RUN what it wrote?

The claim-keyed arm of the unverified-write guard (§4PH, 2026-10-15): a reply that says the code works, was tested or passes is checked against the turn's own write/run ledger, whatever the last tool was.

Why it exists

Until §4PH the one mechanical guard between a coding turn and a false "it works" was _is_unverified_mutation(last_tool) in core.agent: it fired only when the turn's LAST action was a successful whole-file write. A trailing ls, a read-back of the file, python --version — anything — cleared it, and nothing anywhere read the reply's own claim. Reproduced by the §4PH readers: write 3,000 chars → execute ls → "I tested it and it works" shipped clean (no note, no failed label, the project work_log said completed with the claim as its note); a file whose only run FAILED with a traceback shipped under "all tests pass". The corpus agreed: of 82 owner replies claiming works/tested/verified, 27 ran nothing; 1 of 158 coding turns ran a test runner; both released apps carried demonstrable bugs behind "Verified: calendar render".

The ledger

FunctionBehaviour
code_evidence(tools_run)key (normalised workspace path, case-folded — §4UY) → {path, write_idx, run_idx, run_ok, via}. Writes: a file_system SUCCESS confirmation (write / append / edit / replace shapes, via the same anchored parser the FILE-ARTIFACT check uses), a shell heredoc / redirect / tee inside an execute command, or execute(filename=, content=). Runs: an execute whose command, filename, args or ephemeral script text names the file (an import x counts as x.py), a test-suite run (is_suite_command) for every non-web file, a browser / vision_analysis call whose url/path names a page. ORDER matters: only a run AFTER the last write counts, a run before the final edit tested an older version. A detached (promoted) run is neither a pass nor a failure.
unbacked_code_writes(tools_run)(never_run, failed_last) — code files whose final version nothing ran / loaded, and those whose last run after the final write failed (exit ≠ 0, a declared failed status, a browser STATUS other than OK).
claims_code_works(reply)The first affirmative works / tested / verified / passes phrase ("it works", "all tests pass", "tested, works", "I ran it", "works as expected", Greek "δουλεύει" / "το έτρεξα"), or "". A negation, conditional or future in the same clause ("could not test", "untested", "should work", "cannot confirm it works", "if the tests pass") is not a claim.
unbacked_claim_note(reply, tools_run, forbids_running)The note and failed label for a claim with no backing run — ONE wording for both delivery paths: "⚠ Unverified claim: this reply says "…", but app.py was written this turn and never run. Treat it as UNTESTED…" (or "…the last run of app.py after it was written FAILED. Treat it as BROKEN until a run passes."). A request that said "don't run it" is said, not failed (§4KW) — but the claim is still named as unbacked.
unbacked_claim_directive(reply, tools_run)The in-loop repair directive, naming the file: run it or its tests (load a page), read the result, fix or say so, then answer naming what was run.

Where it is wired

  • _unverified_mutation_note(last_tool, request, tools_run, reply) — when the last-tool shape does not fire, the claim arm runs over reply. Finalize passes its final content, the stream drain its accumulated content; both append the note and stamp the trajectory failed with UNVERIFIED_MUTATION_REASON (a prior a late PASS may lift). The streamed project work_log now books the same turn verifier:failed too (it booked "completed" with the claim as the note).
  • _run_internal_turn (the in-loop repair gate) — unbacked_claim_directive over the delivery view forces the "actually RUN it" re-entry on both verdict branches; after the repair round the post-loop note re-reads the ledger, so an ls in reply to the directive still lands the note.
  • No size or shape exemption: the operator's 2026-09-23 decision (no footer on a correct small write; targeted edits exempt) was about a write with NO claim. A reply that affirmatively says "tested" about a 400-byte run.sh nothing ran is a false statement at any size. A write with no claim and a trailing tool is unchanged.

The reader's round (r3)

A fresh reader of the diff found the first cut over-eager in both directions, all reproduced and fixed: the detector matched mechanism prose ("This works by splitting…", "a regex which works on both") and honest reporting ("I ran the tests and 2 of 5 failed") — now `that|which` are not subjects, a mechanism preposition after "works" disqualifies, and "I ran/tested X" needs an outcome word; the ledger missed python -m app, python -c 'import calc; …', uvicorn main:app and a load of the served root — now imports are read from the command, -m and mod:app targets map to mod.py, a root URL names index.html; and a collected job's banner (under the "Collected N finished job(s)" header) must still yield its exit code to _exec_ok (see tool_failure). One battery mutant proved equivalent (the "run before the last write" guard — a later write replaces the record) and the dead guard was removed.

§4UU (2026-11-17): what counts as a run

  • Segments. A command is split per line and on && || ; |; each segment is a run, a check (syntax / lint: node --check, py_compile, bash -n, tsc --noEmit, linters) or a read (cat grep head ls curl test echo …). Only run segments credit a file; a check sets checked, and the note says "only syntax/lint-checked, never run". Before, any command naming the file counted (node --check app.js backed "it works").
  • Page checks. A file_system row carrying the system's [PAGE CHECK] ✓/✗ … Ran: … line counts as a run (or a failed run) of every file listed, right after its own write.
  • Checklist. A checklist check row counts as a run of the files its chosen items' checks ran.

See build mechanics.

§4UY (2026-11-18): paths, project runners, masked runs, one claim rule

§4UX-2 found the ledger and the detector masking each other: the ledger called code that ran "never run" and credited runs that proved nothing, while the detector missed the model's real words. Fixed together:

  • Keys are PATHS. _norm: workspace-relative, /workspace/, projects/<id>/, ./ and .. resolved, case-folded. A command's cd DIR is followed (cd backend && node index.js runs backend/index.js; it never backs frontend/index.js); an unknowable cd $X falls back to a suffix match.
  • Project runners credit their folder, like a suite: cargo run/test, go run/test ., make run/test, node ., npm start/test/run X (not run build/lint), python -m pkg (also pkg/__main__.py), a built binary ./app. A suite credits the files under ITS folder (cd frontend && npm test does not back backend/app.py).
  • The run tool is a run (the foreground-server block sends servers there): a server that started, a job collected (its exit decides); a job only started is no result yet; a lab run is not a run of a workspace file.
  • A written shell script runs what its text runs (bash run.sh, ./run.sh, by the same segment rule); an execute(filename=, content=) script credits what a shell text runs, or what code IMPORTS / EXECUTES — a name that merely appears in it is not a run. A heredoc body written to a file is data; one fed to an interpreter (python3 - <<EOF, cat <<EOF | python3) is the program.
  • Not runs: a compile or build (gcc, javac, rustc, cargo build, go build, bare make) is a check; any --help / --version / -h on the run is a read; a run whose status is MASKED by || (pytest || true) credits nothing.
  • A clean page load runs the scripts the PAGE loads — the <script src> of the page's text as this request wrote it (edits applied), resolved against the page's folder; a localhost page by suffix (its server root is unknown); a page on another host is not ours; a page whose text is unknown credits no script. Before, every written .js under the page's folder (or a front-end folder) counted.
  • One claim rule. claims_code_works: a clause asserting verification or a working state (tested / verified / confirmed / validated with live- / smoke- / end-to-end prefixes; works / working / runs fine; a test / check / suite / build that passes, is green, succeeds; N passed; a run that went successfully / cleanly / without errors), unless the clause carries a negation / conditional / future, or a failure word not itself negated ("2 of 5 failed" is honest; "no errors", "0 failed" are not failures). The detector also feeds checklist.presents_as_finished.

Pins: tests/test_4uy_code_claims.py (every non-guard row fails on the pre-§4UY module).

§4UY review rounds 2–5 and the live replay

  • Pages read from the workspace. A clean load or interact of a page whose text this request did not write whole (an edited index.html, one written in earlier requests) reads the page as it is in the workspace now: the request's project folder (its scope, or a projects/<id>/ its calls named), then the workspace root. A served page is looked for at the root and above the folders of the code the request wrote. A page key never leaves the workspace. A page written in parts (append=true) keeps every part's text.
  • Round 4: credit leans conservative. The note is advisory, so when the ledger cannot tell whether a file ran it does NOT credit it (a false "never run" costs a re-run; a false credit hides a broken file). Removed: the access-log credit (a log line cannot say which server, run or version — cat old_access.log printed the same line).
  • file_system paths are keyed the way file_system resolves them: /webos/index.html is webos/index.html; the host's own sandbox path is stripped.
  • Round 5: a run credits what it RUNS. The head when it is a code file (./run.sh), or the script an interpreter is given (its first non-option argument, through uv/poetry run, npx tsx, deno/bun run; go run a.go b.go); every other file it names is an argument (python3 lint.py main.py runs lint.py; "$(cat other.py)" runs nothing; $(find . -name app.py) in the script position does). A suite / project runner credits only files of ITS language under its folder: pytest / python -m → .py; npm / node / jest → .js .mjs .cjs .ts(x); go → .go; cargo → .rs; make → nothing by itself. String literals and comments of inline code run nothing (print('import app'), // require('./util')); an [interpreter, path] list counts only as a call's argument (FILES = ['python3', 'x.py'] is data).
  • Built binaries: running a binary a build of this request made (./app, ./a.out, ./x.bin) credits the sources that build command NAMED, written before it: gcc -o app main.c → main.c (not a tool.c beside it); gcc / clang without -o write a.out; go build -o app . names the .go files directly in that package folder. A build that names none (make, cargo build, cmake --build, go build ./...) credits nothing. java Main runs Main.java (java -jar names no class). spec_from_file_location / SourceFileLoader load a file by path.
  • A written program run here credits only what one of its process calls runs as interpreter + path in that same call (subprocess.run(["bash", "ft/backup.sh"]), os.system("node x.js")), resolved against the run's folder. A script name it only quotes (a tar or deploy list) or builds at run time (os.path.join(HERE, "backup.sh")) is not credited.
  • A page read from the workspace is opened O_NOFOLLOW|O_NONBLOCK and read only when it is a regular file (a FIFO planted at the path blocked the open; a link led out of the workspace) — execute.read_status_file's rule.
  • Not runs: python -m pip|venv|ensurepip|http.server (read by the module), make clean / cargo clean, npx kill-port|serve|http-server; a command the validator refused before it ran (SYSTEM BLOCK … was not run, a REJECTED status) is no run — not a failed one.
  • A file written into the machine's own folders (/etc, /usr, /root/.* …) configures the machine; it is not tracked. /tmp and workspace scripts are.
  • A stored interact booked PARTIAL only because the model's own evaluate threw counts as a load, as browser.py §4RJ now reports it (a timed-out evaluate stays a failure).
  • The detector again reads the pre-§4UY forms: "everything is verified", "it is fully functional", "the app has been tested". A bare "validated" is not a claim (forms validate input); "the script has been validated" is. A bare "working" is progress narration; only the predicate ("it's working", "working fine") is a claim.

Residuals

  • Conservative credit leaves real runs "never run" (accepted, live replay): make && ./greet (make names no source — its echoed cc … greet.c line is not read); cargo build && ./target/debug/app (use cargo run); a module a run script imports; apps a page loads through a manifest / dynamic import; a script a harness runs by a path built at run time. Run or load them by name to back a claim.
  • A suite run behind a shell keyword (2026-11-18 live run) — is_suite_command reads lower-case do / then / else / time / if / while / until, ! and { heads: for i in 1..10; do python -m pytest -q test_tags.py | tail -1; done (ten green runs) was "never run" and forced a repair round. Case-sensitive, so a capitalised sentence in a heredoc ("Then pytest …") is not a run.
  • A suite or project runner backs every file of its language under its folder, used or not. A localhost page is matched by path suffix, so two written pages with the same tail both count.
  • A page read from the workspace is its text at reply time, not at the load: a <script src> added after the last load counts as loaded. A request with no project scope and no projects/<id>/ in its calls looks only at the workspace root.
  • A ; chain's exit is its LAST segment's: a deliberate error case run last (app.py add …; app.py remove zebra 99, exit 1) reads as a failed run of the file. Mask the expected failure (|| true, ; echo $?) to keep it a run.
  • A backgrounded run (python3 app.py & sleep 1; curl …) still counts as a run of its file with the command's own status (the smoke test's).
  • The detector reads English and a little Greek; a claim phrased some other way is not caught (fail-open: a missed note, never a false one on a backed file).
