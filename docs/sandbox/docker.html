sandbox / docker.py — DockerSandbox

Long-lived Docker container that hosts every tool call. Workspace bind-mount, optional Tor, resource limits, output capping.

execute_promotable(cmd, …) 2026-08-11Same run, one difference: a command still ALIVE and still PROGRESSING at the budget is detached as a supervised job instead of killed (see sandbox.jobs). Provisioned packages

Preferred: build ghost-agent-base:latest via the authoritative Dockerfile one-shot; the runtime wrapper then only verifies and reuses it.

scripts/build_sandbox_image.sh
# reads sandbox/Dockerfile, runs a Chromium smoke test at the end,
# ~5 min on a warm docker cache
  • apt: sudo · git · nodejs · npm · postgresql-client · tor · ripgrep · sqlite3 · libpq-dev · iproute2. (iproute2 provides ss — socket/port inspection, added 2026-07-12.)
  • pip: numpy · pandas · scipy · matplotlib · seaborn · plotly · scikit-learn · yfinance · beautifulsoup4 · networkx · requests · pylint · black · mypy · bandit · dill · ipykernel · jupyter_client · pytest · pytest-asyncio · psycopg2-binary · asyncpg · sqlalchemy · tabulate · sqlglot · playwright · html2text · lxml · pysocks · flask · python-chess.
  • web/app hosting (2026-07-12): flask + python-chess (imported as chess) preinstalled, and iproute2 for ss. Added because "host a web app / chess service" requests otherwise ran pip install flask python-chess mid-task — a ~24 s serial install thrash observed live on the chess-hosting flow, right on the critical path of a manage_services start.
  • browser: Chromium installed via python3 -m playwright install --with-deps chromium. The --with-deps is the key — it installs the system libs (libnss3, libatk1.0-0, libdrm2, …) that headless_shell dynamic-links against. Without them, the binary exists but can't launch; self-play would rediscover this at task time and burn ~100 s re-installing via playwright install chromium (no deps) before failing again. Baked into the Dockerfile so it can't be skipped.
  • PyTorch (2026-06-22): torch preinstalled from the CPU wheel index (--index-url https://download.pytorch.org/whl/cpu) — the default wheels pull ~2 GB of CUDA the sandbox can't use. Added because every "build/train a model" project hit ModuleNotFoundError: torch and ran a ~300 s pip install torch mid-task, often tripping the execute timeout (observed live: the PetAI training task). Non-fatal: a machine that can't reach the torch CDN still gets a working sandbox (the agent falls back to a runtime install), so a torch flake can't poison provisioning of everything else.

Provision marker is versioned (/root/.supercharged.v9)

The runtime gate in ensure_running checks TWO things, not one:

  1. test -f /root/.supercharged.v9 — the version-bumped marker. Older images (missing the current marker) are treated as un-provisioned, forcing a clean reinstall on next boot; e.g. a v3 image re-provisions to pick up iproute2/flask/python-chess.
  2. _chromium_binary_present() — find /root/.cache/ms-playwright -type f \( -name headless_shell -o -name chrome \) -print -quit. Defends against the silent-failure mode where a prior install exited 0 but the binary isn't actually on disk (network flake, mid-extract disk-full, etc.).

If the marker is present but the binary is missing, the gate logs ⚠ Provision marker present but Chromium binary missing. Reinstalling... and re-runs the full install. Post-install, _chromium_binary_present() is checked AGAIN before the marker is touched — fail-loud: the v4 marker is never set unless the binary actually verifies on disk, so a failed install cannot silently poison future boots.

Bump the marker (in both sandbox/Dockerfile AND sandbox/docker.py) any time the install surface genuinely changes — e.g. .v4 (2026-07-12) added iproute2/flask/python-chess. The meta-tests test_v4_marker_gate_name_pinned and test_provisioning_bakes_ss_flask_chess_and_stays_in_sync assert the two files agree on both the marker and the package set.

Bumps upgrade IN PLACE from the previous marker (2026-09-09, §4FR; v6 added file, v7 added xxd after the live check found the model's chain pipes through it too; v8 added lsof and dnsutils, the only other commands the trajectories show the model reaching for; v9 added iptables for the Tor-only egress rules). v6 adds file: the model verifies a download the standard way, file x.pdf, and the missing binary turned a successful 16 MB fetch into exit 127, a failure banner and a strike (request d50a34bd). Every earlier bump made the next request pay a full provision — ~5 minutes of apt, pip, torch and Chromium. Now an image carrying the PREVIOUS marker and a working Chromium gets only the delta (apt-get install -y file), the binary is PROBED with command -v file before the new marker is written (the v2 lesson: a marker asserts what somebody checked), the old marker is removed, and the image is committed. Any failure falls through to the full provision, which installs the same package list and now also removes the superseded marker. The delta obeys the same provisioning backoff as the full install — armed pessimistically before the apt call, cleared on success — so a broken mirror is not hit with a 600 s install on every command while the provision lock is held (review, 2026-09-09). Pins: tests/test_sandbox_v6_file_upgrade.py.

Covered by tests/test_sandbox_chromium_gate.py (13 cases including binary-present/absent probes, legacy-marker handling, post-install verification refusing to mark a broken image, Dockerfile-level assertions about --with-deps, and the docker.py↔Dockerfile package-sync check).

Service ports (2026-07-11)

Supervised long-lived services (see sandbox.services / the manage_services tool) run detached inside this container. In bridge mode (the macOS default) they'd be unreachable from the host, so container creation publishes a small loopback-bound range — GHOST_SANDBOX_SERVICE_PORTS, default 8100-8104, empty string disables — letting the OPERATOR open http://127.0.0.1:<port> in their own browser (or put it on the tailnet with tailscale serve — see services → Remote access). For the bridge-publish to forward, the service must bind 0.0.0.0 inside the container, so the manager exports HOST=0.0.0.0 alongside PORT; a loopback-bound app is reachable in-sandbox but not from the host. Host mode (the Linux default) needs no publishing (the service binds host ports directly). Ports 8000/8080/8088/9050 are never publishable (agent API / NetMon / upstream LLM / Tor). Publishing is a convenience, not a dependency: if a host process already owns one of the ports, containers.run is retried without published ports (warning logged) rather than failing the sandbox — in-sandbox consumers (browser, execute) reach the service on the container's own loopback regardless. Only takes effect when the container is (re)created.

Lazy re-init after a failed boot 2026-08-26

Boot-time init in main.py is one-shot, and the DockerSandbox constructor pings the daemon. When the agent boots seconds before the docker socket answers (the 08-26 incident: agent up at 08:11:52, OrbStack's socket answering at ~08:12), the constructor raises, context.sandbox_manager is never assigned, and every execute/browser call returns "Sandbox manager not initialized" until the next restart — 7 hours that day, while hourly isolated bench runs proved docker had recovered minutes after boot.

Two module functions in sandbox/docker.py close the gap:

  • register_lazy_sandbox(context) — called once at boot (inside the find_spec("docker") branch, before the construction attempt) to mark the live context as eligible. Stores a weakref identity, not a flag: a copy.copy'd isolated-replay context — which sets sandbox_manager=None deliberately for network=none replays — is a different object and can never resurrect a sandbox isolation detached. A docker-less install never registers.
  • ensure_sandbox_manager(context) — the resolver registry.py calls for execute/browser (off-loop, via asyncio.to_thread; the constructor ping blocks). Fast path is an attribute read. When the manager is None and the context is the registered one, it attempts one construction per 60 s backoff window, guarded by a non-blocking lock (a second concurrent caller returns None instead of queueing a duplicate ping). A cheap socket-existence pre-check (DOCKER_HOST, /var/run/docker.sock, the OrbStack/Docker-Desktop sockets on macOS) skips the attempt entirely when no endpoint exists, so a wedged daemon's client timeout can only be paid once per window, never per tool call.

On success the new manager is assigned back onto context.sandbox_manager and Sandbox Recovered is logged — so file_system, manage_services, the tree lister and the job reaper all recover on the same turn without their own wiring. ensure_running is deliberately not called on this path: execute() runs it before every command, so the container provisions itself on first use. Failure keeps the exact pre-existing error contract (None → "Sandbox manager not initialized"), only shorter-lived. Tests: tests/test_lazy_sandbox_reinit.py (identity guard, backoff, write-back, and concurrency pins — all mutation-checked).

Reliability hardening 2026-07-22 sandbox review

  • Client-side exec deadline (was: infinite hang). docker-py's exec output read blocks in poll.poll() with no timeout, so a wedged daemon hung the calling worker thread forever — and the provision execs run while holding the provision lock, wedging every other turn's execute with zero log output. All exec_run calls now go through _exec_run(cmd, deadline_s), which runs the exec on a daemon thread and joins with a deadline: on expiry it abandons the blocked worker and raises SandboxDaemonTimeout, so the lock releases and the agent surfaces a clear error. The per-command exec passes timeout + 60 s (the command self-limits via the in-container timeout); everything else uses a generous GHOST_EXEC_DAEMON_DEADLINE (1200 s) that only fires on a true wedge, never on a slow install.
  • Infra failures are marked, not blamed on the model. An exec that fails for an infrastructure reason (wedged daemon, remove-while-exec race, provision-backoff refusal) previously returned a bare exit 1, so the model debugged its own code and burned strikes. The output is now prefixed [SANDBOX INFRA ERROR — not your code] (which also keeps execute.py's file-not-found heal from firing on it).
  • Stopped containers RESUME instead of destroy+reprovision. close(remove=False) merely stops the container, but ensure_running could only adopt a running one — so an RSS-watchdog restart force-removed and recreated it, discarding every in-sandbox service and all runtime apt/pip state (the "fast resume" the docstring promised never existed). _try_resume_stopped now start()s a merely-stopped/paused container and re-probes before the recreate path.
  • Adopted-container published ports read from reality. When the agent adopts a container it didn't create (routine after a plain-kill deploy, or a 409 name-race, or the port-conflict retry), _published_service_ports is now derived from the live HostConfig.PortBindings (empty on the portless retry) instead of being left stale/None — so the remote-access hint can't point the operator at a foreign process's port. See services → Remote access.
  • Spill-log counter survives restarts. _spill_counter (class attr, reset to 0 on every plain-kill deploy) is now seeded past any existing .ghost_runs/run_N.log on first use, so a truncated-output pointer from a prior session isn't clobbered by a new run_1.log.

Covered by tests/test_docker_review_fixes.py. The paired execute heal-retry safety (a timeout-killed or already-ran command is no longer re-run) is in tests/test_execute_heal_timeout_guard.py.

Egress: transparent Tor, enforced in the container 2026-09-09 §4FU

What was true before. Measured from inside the live container: a plain request left from the operator's real IP — bridge networking, no proxy variables, no Tor process, DNS through the host's resolver. The host's egress guard exempted the sandbox on the belief that "its egress is enforced by the sandbox's internal Tor daemon"; that daemon never ran (under host networking it could not bind, under bridge it was never started with a usable config). Across the trajectory corpus the model reached the network from the sandbox 161 times (125 curl/wget, 19 pip, 12 Python requests, 3 apt, 2 git), each from the real IP; and a fetched page can tell the model to run a command that posts data somewhere, which then leaves from the real IP past every host-side guard.

The design (operator's option 1, hybrid). sandbox/tor_egress.py holds the configuration as data; DockerSandbox._enforce_tor_egress() sequences it, once per container generation, AFTER provisioning:

  1. an in-container Tor from /etc/tor/torrc.ghost, started as root and dropping to debian-tor, with TransPort 9040 and DNSPort 5353 beside its SocksPort;
  2. iptables rules in the container's OWN network namespace (the only place the original destination of a redirected connection survives): every TCP connection to the TransPort, every DNS query to the DNSPort, Tor's own traffic (matched by uid) and loopback exempted FIRST, everything else — other UDP, ICMP, all IPv6 — REJECTed;
  3. loaded through a privileged docker exec: the container runs with Docker's default capability set, which lacks NET_ADMIN, so a command the model runs, root or not, cannot flush the rules (verified: "needs NET_ADMIN");
  4. the rules go in BEFORE Tor is known to be up — fail-closed: until it bootstraps, and if it ever dies, nothing leaves the sandbox at all;
  5. a verification request with no proxy flags to check.torproject.org must answer IsTor: true; a false is logged as a LEAK at ERROR.

Provisioning stays direct — apt, pip and the Chromium download run before the rules, which is what the old design wanted — but a runtime pip install or apt by the model now goes through Tor (slower). Under host networking the enforcement is not applied and says so once: rules in a shared namespace would rewrite the host's traffic. Names OrbStack's resolver used to answer for the container (host.docker.internal) no longer resolve, since DNS goes through Tor; nothing in the sandbox relied on them. The spike on the live container that settled the design: bootstrap in 16 s; curl and raw urllib both IsTor: true on different exits; host example.com resolved; UDP to port 123 and IPv6 blocked; pip download six succeeded over Tor. State is exposed as _egress_state (enforced / blocked / unavailable). Pins: tests/test_sandbox_tor_egress.py.

§4FW (2026-09-10) — a RESUMED container is a new generation. "Once per container generation" was implemented as once per CONTAINER, on the create path. A container START is the real unit: docker start gives a stopped container a fresh network namespace (the GHOST_TOR rules live there and are gone) and none of its processes (the in-container Tor is not running). _try_resume_stopped — the common path after every deploy, since the agent is restarted by killing it and the container outlives that — reported the container ready and returned before the enforcement. Measured 13 minutes after a restart: empty nat table, {"IsTor": false} from inside, the host's real address. It self-healed at the next ensure_running past the readiness TTL (which falls through to the tail and enforces before the command runs), so agent-issued commands were in practice protected; what stayed exposed is what the resume path exists to preserve — in-sandbox services and promoted jobs resume with the container and reach the network with no rules. Fix: one guarded entry point _enforce_egress_once() called by BOTH paths, with the resume clearing the generation flag first (a start is a new generation; unpause keeps namespace and processes, so it is an idempotent re-apply). An AST pin requires every function that starts or creates the container to call it and asserts it still sees both known paths. Pins: tests/test_sandbox_resume_egress.py.

The first live run found two defects in the sequencing, both fixed the same evening. (1) The "is Tor already running" check was pgrep -f 'tor -f /etc/tor/torrc.ghost', run inside an sh -c wrapper whose own command line carries that literal — so it matched the wrapper (root), the start was skipped as "already running", the running-as-debian-tor check read the wrapper's owner, and the sandbox sat fail-closed with the rules in and no Tor. The pattern is now anchored on Tor's own command line (TOR_PROC_PATTERN = "^tor -f …"; the wrapper's begins with sh), and a pin runs the pattern against the wrapper's own command line. (2) The bootstrap poll greps the notice log, and the container's filesystem outlives a restart while its processes do not — the previous Tor's "Bootstrapped 100%" line would pass the poll before this Tor had a circuit. A FRESH start now truncates the log first (never when Tor already runs). Live after the fix: "Tor-only egress ENFORCED" 5 s after the rules; through the agent and from inside, curl and raw urllib both IsTor: true; DNS resolves through the DNSPort; UDP, IPv6 and a root iptables -F all blocked; Tor runs as debian-tor; marker v9.

Tor superseded 2026-09-09

The former "the container starts a tor daemon and outbound HTTP is routed through it" block described a daemon that never actually ran (see the egress section above for the measurement). tor_proxy in the constructor is now the switch for the transparent enforcement; the once-per-container-generation attempt discipline (_tor_attempted) is unchanged.
