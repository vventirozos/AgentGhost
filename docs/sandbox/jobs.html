sandbox / jobs.py

Promoted long-running sandbox commands (2026-08-11): an execute run that is still working after 90 s is DETACHED as a supervised job instead of blocking the turn — and the model is woken with its result when it lands.

Why

Hitting the execution budget used to be pure loss, three times over. A live example (2026-08-11) is the canonical shape: a yt-dlp download over Tor was killed at the budget, and the model immediately re-ran the identical command.

  • The work is destroyed. The process is killed at the budget and everything it had done is discarded.
  • The retry multiplies it. Exit 124 arrives with no explanation the model can act on, so it runs the same command again — turning ten minutes of loss into twenty, thirty, forty.
  • The learning signal is poisoned. A non-zero execute exit is scored as a transient strike, and strike accounting feeds outcome labels and calibration. A legitimately-long task is not a failure; counting it as one corrupts more than the log.

Promotion fixes all three at once, and the tool decides, not the model: it happens on OBSERVED duration and OBSERVED progress, so nothing depends on the model predicting how long yt-dlp takes over Tor.

What the model sees

Two shapes. A fresh promotion (each ▎ bullet is emitted as ONE line; they are wrapped here to fit the page):

--- COMMAND RESULT --- [SANDBOX JOB PROMOTED]
EXIT CODE: 0 (STILL RUNNING — promoted to background job job-1a2b3c4d, NOT finished)
STDOUT/STDERR:
▎ Still running at 600s — promoted to background job job-1a2b3c4d. Do NOT re-run
  this command — it was NOT killed and is still working.
▎ Poll it with jobs(action='status', job_id='job-1a2b3c4d'); read its full result
  with jobs(action='collect', job_id='job-1a2b3c4d') once it finishes. Cancel it
  with jobs(action='cancel', job_id='job-1a2b3c4d').
▎ It keeps running in the sandbox (up to 44 more minutes, then it is reaped) and
  survives this turn; its live output is in '.jobs/job-1a2b3c4d.log'
  (file_system operation='read').
▎ FINISH YOUR TURN NOW: state plainly that the work is STILL RUNNING in the
  background and where its result will appear — do not wait for it here, do not
  claim it finished, and do not promise to report back later (nothing runs after
  your reply).
--- output so far ---
[download]  42% of 700MiB …

And, when the model re-runs a command that is already a job, the supervisor hands back the SAME job rather than starting a second copy:

--- COMMAND RESULT --- [SANDBOX JOB PROMOTED]
EXIT CODE: 0 (ALREADY RUNNING as background job job-1a2b3c4d, NOT finished)
STDOUT/STDERR:
▎ NOT re-run: this exact command is ALREADY running as background job job-1a2b3c4d
  (started 2100s ago). A second copy was NOT started — it would compete with the
  first for the same sandbox CPU.
…

Both quote the REMAINING lifetime (truncated, never rounded up — so a fresh 45-minute promotion reads as "44 more minutes") and the original command's age, not the configured TTL or the duration of the call that hit the guard.

EXIT CODE: 0 is deliberate: the turn loop matches EXIT CODE:\s*(\d+) on execute results and treats anything non-zero as a failure + a strike. The annotation rides AFTER the digits so that parser keeps working, and the banner carries the honesty the code cannot — the command has NOT finished.

How it works

Mechanics mirror services.py, the proven pattern for detached container processes.

  1. The command ships as a SCRIPT through the bind mount (/workspace/.jobs/<id>.cmd.sh) so no shell quoting can corrupt it. The script records its own pid, runs the command, and publishes the exit code to <id>.exit via tmp+rename.
  2. It launches under setsid nohup … &, so it re-parents to the container's PID 1 and its recorded $$ IS the session/process-group leader — kill -- -<pid> reaps the whole tree.
  3. Python polls the HOST side of the bind mount (no docker round-trip per tick): tight at first so a 50 ms ls stays a 50 ms ls, then relaxed. One combined probe — liveness AND the I/O counters — runs inside the container at 2 s and then every 30 s, late on purpose so the overwhelming majority of commands (which finish in under two seconds) never pay for a round-trip they do not need. The liveness half is what makes a runner that was SIGKILLed — and therefore never wrote a sentinel — return immediately instead of blocking for the rest of the budget. A probe that FAILS is "unknown", never "dead": reading a docker hiccup as death once deleted a live job's log and left its process running untracked.
  4. The runner script carries a last-resort timeout -k 5s <budget + TTL>s (probed with command -v, so an image without coreutils still runs). The classic path's in-container timeout survived the agent process dying; without an equivalent, a deploy-by-kill mid-run would leave an immortal process with no registry row, no TTL and no reaper.
  5. From 90 s onward (promote_after_s()), re-checked at every probe: still alive AND still progressing → promote. A command that is demonstrably working stops making the turn wait long before the budget.
  6. At the budget (600 s), and only then: a command that has never shown progress is killed with exit 124, exactly as timeout would have. The two thresholds answer different questions — see below.

Registry state lives in <host_workspace>/.jobs/registry.json — host side of the bind mount, so a job promoted before an agent restart is still visible and still reapable afterwards.

Two thresholds, not one

Promotion happens at 90 s; the kill still happens at 600 s. Collapsing them would break one case or the other:

AsksWhy not the other number
promote_after_s()
90 s		 "This is long-running — stop making the turn wait for it." Blocking a turn for ten minutes to reach a decision that was already obvious at ninety seconds is pure latency: the operator waits, and so does the model.
the exec budget
600 s		 "This has gone quiet — give up on it." Killing at 90 s would make a silent, purely-computational run die 6.7× sooner than before promotion existed — a regression dressed up as a speed-up.

Promoting early is only safe because a landed job RE-ENGAGES the model. Nothing else resumes a turn once it ends, so without that, an early promotion on a pytest or pip install — commands whose output the model NEEDS to continue — would end the turn and strand the work until the operator spoke again. The reaper therefore wakes the model with the job's result (main._resume_after_job), through the same handle_chat entry point and the same internal job- request class that scheduled tasks use. If auto-resume is ever disabled, raise GHOST_SANDBOX_JOB_PROMOTE_AFTER_S back toward the budget.

The wake carries three guards: it stands down while a user request is in flight (turns are serialized, so waking would make a live user queue behind autonomous work — the rule scheduled tasks already follow), it fires once per job, and it is rate-capped at 12/hour — a woken turn can promote another job, which lands and wakes again, and the counter is the backstop on that recursion.

The two rails

1. Progress, not merely liveness

Without this the feature is just a slower timeout. A job earns promotion only if, within the progress window (progress_window_s(), default 120 s, additionally clamped to half the budget), EITHER:

  • its combined stdout/stderr log GREW — tracked host-side off the bind mount during the poll loop, so it costs no container round-trip. A command that has written nothing at all never qualifies, at any budget; or
  • its own I/O counters moved — rchar + wchar summed across every process in the job's SESSION, from /proc/<pid>/io (setsid makes the recorded pid the session leader, so its children are included and nothing else is). This is what lets a SILENT downloader promote.

Attribution is the subtle part, and the first implementation got it wrong. It asked "did a file under the workdir change recently" (a find -mmin probe), and a live test then promoted a genuinely wedged sleep 300 — because a different job was writing into the same shared /workspace. Workdir mtimes attribute to nobody; per-process counters attribute to the job that earned them.

The test is for a CHANGE, not an increase: the sum spans a whole session, so a child exiting removes its counters and the total can fall. Either direction means the tree did something; a total that has not moved at all is the wedge. When /proc cannot be read the signal abstains (no evidence, never false evidence) and log growth alone decides — degrading to the pre-2026-08-11 behaviour rather than promoting blindly.

CPU time is deliberately not a signal. A spin-loop is exactly the wedge that must die at the budget, and it burns CPU by definition. The accepted cost is stated plainly rather than implied away: a long, silent, purely-computational run that neither prints nor touches a file is killed — the same outcome it got before this feature existed. The accepted false POSITIVE is the mirror image: a retry storm, or a process polling a held lock, does I/O — so it promotes, and the lifetime cap is what bounds it.

2. A separate lifetime cap

A promoted job is reaped at job_ttl_s() (default 45 min, clock starting at PROMOTION) whether it has finished or not, so the unbounded wait is removed rather than moved into the job layer. Reaping runs from three places, none of which depends on the model asking: the jobs tool reconciles before every answer, a background sweeper in main.py runs every 60 s, and boot reaps before reporting what carried over.

Where a landed job surfaces

Nothing re-engages the model after a turn ends, so a job that finishes while nobody is looking has to be answerable rather than pushed:

  • jobs(action='status') / collect — the reconcile runs before every answer, so the exit code and output are current. A FAILED job still returns its output; a bare "exited 1" would leave the model nothing to act on but the long command it was told not to re-run.
  • introspect action='activity' — the 60 s sweeper writes each landed job to the activity ledger under the job phase, which is what answers "what happened while I was away". The operator's live log stream gets the same line, but that stream is watched, not queried.
  • The job's own log file stays in .jobs/ until the row is trimmed, so file_system can read the FULL output — the landed result inlines only the last 80 lines.

The promotion banner therefore tells the model to state plainly that the work is still running and where its result will appear — NOT to promise to report back, which is a promise nothing in the system can keep and which the pending-promise guard would (correctly) reject.

Configuration

VariableDefaultEffect
GHOST_SANDBOX_JOBS1 Kill switch. 0 restores the pre-2026-08-11 behaviour exactly: every run goes through timeout -k 5s and a budget overrun is killed.
GHOST_SANDBOX_JOB_PROMOTE_AFTER_S90 How long a command must run before it is eligible for promotion. Bounded to [5 s, 1 h]. Distinct from the exec budget, which is when a command that never progressed is killed.
GHOST_SANDBOX_JOB_TTL_S2700 Promoted-job lifetime cap. Bounded to [60 s, 6 h]; an unparseable or out-of-range value falls back to the default rather than disabling the rail.
GHOST_SANDBOX_JOB_PROGRESS_WINDOW_S120 How recently progress must have been seen to earn promotion. Bounded to [10 s, 1 h], and clamped to half the budget — a window at or above the budget would silently degrade the rail from "recently" to "ever".
GHOST_SANDBOX_JOB_MAX3 Concurrent promoted jobs. At the cap a would-be promotion is KILLED instead — an untracked detached process is worse than a timeout.

Kill safety

Every signal this module sends is gated, because the number it signals is not trustworthy on its own: the registry lives on the bind mount, so the very commands this module supervises can write it.

  • An UNSTAMPED row is never signalled. A row without a container-generation stamp used to get "the benefit of the doubt" — which turned the TTL reaper into an arbitrary in-container session-kill primitive: a planted row naming any live pid, with a deadline in the past, killed that pid's whole session on the next sweep. Verified against a real container (an unrelated setsid'd service tree died). Every row this module writes is stamped, so an unstamped one is forged or ancient — neither earns a signal.
  • A pid floor of 1. In POSIX kill -- -1 means "every process the caller may signal" — NOT "process group 1" — so a pid of 1 TERMs and then KILLs the whole container: every service, every other job, tor. Verified in a live container: the shell issuing it did not survive to print its next line. 0 is nearly as bad (-0 is the caller's own group). Both are refused, loudly.
  • Registry rows are untrusted input. .jobs/registry.json lives on the bind mount — inside the sandbox, writable by the very commands this module supervises. So the fields a kill is built from are validated on READ: a row without an integer pid above 1, or without a numeric deadline, is dropped with a warning. (A missing deadline used to read as 0 — "expired in 1970" — which is instant expiry AND an instant kill: a fail-dangerous default for a missing field.)
  • Container generation before any signal. A recreated container invalidates every recorded pid, and fresh containers hand out LOW pids — so a stale row very plausibly points at a supervised service or another job. Expiry and cancel both check the generation stamp FIRST and mark the job lost rather than signalling. services.py had to learn the same lesson in 2026-07.
  • A kill is verified. cancel re-probes the pid and returns a boolean; a process that survived TERM+KILL leaves the row RUNNING and says so, because reporting a cancel that did not happen hides a live process.
  • Scope is SESSION or PPID-ANCESTRY, and the shell is the portable one: dash (the container's /bin/sh) parses -- as a pid, so kill -TERM -- -123 fails with "Illegal number" and sends nothing — the group-kill half was dead in production until that was measured. A descendant that merely changes process group (GNU timeout does) is reached by the session scan; one that also re-parents is reached by the ancestry walk. Known limit, measured: a descendant that fully DAEMONIZES (setsid … &) re-sessions and re-parents to PID 1, erasing every link — no scan can reach it. The classic timeout path leaks the identical process, so this is a property of the sandbox, not of promotion; execute's backgrounded-server guard is what addresses that class, by refusing the command up front.
  • The exit sentinel carries a nonce. It is written into a directory the supervised command can write, so a bare exit code was forgeable — and creatable BY ACCIDENT: one echo 0 > .jobs/<id>.exit, or any command that wipes .jobs/, made execute report EXIT CODE 0 in 0.0 s for a command that kept running, with no row, no TTL and no reaper. The nonce is minted host-side per job and only the runner quotes it back.
  • The jobs directory itself is containment-checked. Hardening the cleanup paths alone left the wider door open: every file this module writes and deletes derives from <host_workspace>/.jobs, which the sandbox can replace with a symlink. Measured: that redirected host writes and deletes into an arbitrary directory at the agent's uid. It is now refused unless it is a real directory inside the sandbox root.
  • Registry fields are validated on READ, not trusted at use: a non-finite deadline_at (NaN/Infinity parse as floats and pass a <= 0 test) would be an unbounded lifetime; an unknown state — a single trailing space — let a row opt out of reaping entirely.

Failure modes it is built against

  • A job that finishes mid-reap. The reap reads the exit sentinel, then probes liveness. A job exiting between those two steps was marked lost — destroying its exit code and output. The sentinel is now RE-READ (with a short grace) before that conclusion. The grace is skipped on a container-generation mismatch, where no new sentinel can appear.
  • A partially-visible exit sentinel. Written tmp+rename in the container, but a bind-mount read can still catch an empty file; an unparseable read means "not finished yet", never "exit 0".
  • A recycled pid after a container recreate. Every entry carries the container generation. A mismatch means the job is gone — the pid number is never trusted, and never signalled.
  • Model-supplied job ids. Ids reach this module from the jobs tool and are interpolated into file paths, so the job-<8 hex> shape is enforced (not assumed), on the registry read as well as at every entry point.
  • Registry growth. Terminal rows are bounded (20, oldest dropped with their logs). The registry is a worklist, not an archive — but a landed job is NOT forgotten on the spot: that would delete the log the promotion banner just told the model to read.
  • An orphan created by the orphan-preventer. Everything between launch and the registry write runs with a live detached process and nothing tracking it, so any failure there (a wedged daemon, a raise from the registry save) kills the process before re-raising. Likewise a probe failure is "unknown", never "dead" — the earlier code returned exit 137, deleted the log out from under a live writer, and neither killed nor tracked the process.
  • A re-run that doubles the load. The banner tells the model not to re-run a promoted command; the supervisor makes it true. An identical command+workdir that is already RUNNING as a job returns THAT job instead of starting a second copy — the strike counter that used to bound such a loop is, by design, no longer there.
  • Files the caller owns. An execute(content=…) run generates an ephemeral script the detached process is still executing, so the tool cannot delete it on the way out. The path is handed to the supervisor and persisted on the row, so it is unlinked when the job ends — even across a restart.

Not a service

manage_services is for a long-lived LISTENER the model starts deliberately, with a port lease and an indefinite lifetime. A job is a one-shot COMMAND the model ran in the foreground that simply took longer than the budget: no port, a hard TTL, and a result to collect. Neither replaces the other.
