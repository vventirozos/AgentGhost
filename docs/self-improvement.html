How it works

How it improves itself

Two separate things: a check that runs on every answer, and a set of background passes that only run when you've left it alone.

To be clear about what this isn't. None of this retrains the language model. The model file never changes. What changes is what Ghost remembers, what it has learned to avoid, and a few small local models it trains itself for scoring and routing. Everything happens on your machine.

Part one: checking its own answers

The failure this exists to catch is specific and common: a model announces "I've created the file and it works" when nothing ran, or answers a subtly different question than the one you asked. It reads confidently either way, which is what makes it dangerous.

So before an answer is final, a second pass reads it against the evidence the tools actually produced.

  1. The evidence is collected

    What the tools returned this turn — command output, file contents, what the browser saw. Not the model's description of them; the actual results.

  2. Two questions, in this order

    First: does this answer the question that was asked? Second: is it supported by the evidence? Alignment comes first deliberately — "you asked for code and got a number" is a worse failure than a wrong number, and a check that only looks at correctness misses it entirely.

  3. A verdict, with a confidence

    Confirmed, or refused. A cheap local judge does the first pass; if it refuses, the main model re-examines the case, and its verdict wins. That second look exists because the cheap judge refuses more often than it should.

  4. If refused with high confidence — repair

    Ghost gets a bounded number of attempts (one by default) to fix the answer with the critique in hand, rather than shipping something it just failed. Error messages and aborts are never "repaired".

  5. Whatever happens is recorded

    A refused answer also un-learns anything it taught. If Ghost recorded a lesson during a turn whose answer got refused, that lesson is removed — otherwise a single bad turn poisons future ones.

Streaming answers are checked late

If the reply streams word by word, the text has already reached you by the time the check finishes. Blocking would buy nothing. So the check runs in the background and, if it refuses, you get a correction notice at the top of the next reply. It's not silent — but it is after the fact.

When you correct it yourself

Telling Ghost it got something wrong is a much stronger signal than anything it can generate on its own, and it's treated that way: the turn gets marked as failed, and it goes into the material the background passes learn from. It needs both a recognisable correction phrase and genuine overlap with the previous message, so an ordinary follow-up question isn't mistaken for a correction.

Part two: what it does while you're away

A background loop wakes up periodically and checks whether it's allowed to do anything. Two rules govern all of it:

  • It never interrupts you. If a request is in flight — even paused between model calls — every phase is skipped.
  • Each phase needs both idle time and a cooldown. "It's been quiet for an hour" isn't enough if that phase already ran twenty minutes ago.

So on a busy day, almost none of this runs. That's intended.

One consequence is easy to misread. Most phases only run while you've been idle between fifteen and sixty minutes; past that the window closes. What re-opens it is self-play finishing — it is the only phase that resets the idle clock, which is what lets a three-hour or six-hour cooldown matter at all during a long absence. Turning self-play off with --no-self-play therefore does far more than its name suggests: nothing re-arms the window, so after the first hour away, every other phase is gated out too and only journal consolidation keeps running. Treat that flag as "most of the idle machine off", not "self-play off".

If you use --bio-time-scale to exercise these loops quickly: it now divides the phase cooldowns and the loop's own tick interval as well as the idle windows. Until 2026-08-08 it only compressed the windows — the cooldowns kept their real durations, so a phase with a three-hour cooldown could fire at most once no matter how many accelerated epochs a run claimed to cover. The helper meant to scale them existed and had a passing unit test, but nothing ever called it. Any measurement taken with this flag before that date covers roughly one epoch per phase, whatever it says.

There is a floor on how far you can compress time

Accelerating the clock only works while the compressed window stays wider than the work. The gates shrink when you raise the scale; the work doesn't. A dream is a real model call and takes something like a minute whether the scale is 1 or 60.

At --bio-time-scale 60 the window for the middle phases is 45 seconds — narrower than a single dream. What was actually observed, tick by tick:

idle 1..10s   nothing eligible yet
idle ~11s     dream starts — and runs for ~60 real seconds
idle ~71s     the 15–60s window has already closed
              self-play (no upper bound) fires and resets the idle clock
idle 1..10s   …and round again, forever

The middle of the window is never sampled, so reflection, post-mortems, skill extraction, the PRM and router retrains, calibration, the tidy pass, both narrative consolidations, stale-question surfacing and project auto-advance can never run — and they report zero firings, which reads exactly like "we measured them and they did nothing."

Practical rule: keep the scale at 20 or below (a window of at least ~2 minutes). The agent now warns loudly at boot if the scale you chose makes the window narrower than the work, and names the phases that would silently never fire. Every ablation number recorded before 2026-08-09 measured dreaming and self-play only.

  1. After ~2 minutes — file away what just happened

    Things noted during the conversation are sitting in a queue. This pass works through them and decides what's worth keeping, then writes it into long-term memory. Until this runs, something you just mentioned may not be findable.

  2. After ~10 minutes — consolidate memory

    The project calls this the dream cycle, or REM. It reviews recent memories, merges duplicates, generalises repeated patterns into something reusable, and tunes how much each memory store is trusted for different kinds of question.

    It skips itself when there's nothing new, and backs off further each time it skips — so a quiet afternoon doesn't produce a log full of "nothing to do".

  3. After ~15 minutes — review what went wrong

    Recent failed turns get re-read and critiqued, and what comes out of that becomes lessons. Around the same window, Ghost also updates its running first-person account of what it's been doing, and its record of what changed in your files.

  4. Every couple of hours — extract reusable skills

    Looks across successful runs for a procedure that keeps recurring and turns it into a named, reusable skill instead of something re-derived every time.

  5. Every few hours — retrain its own small models

    Two little local models: one that scores whether a partial plan looks like it's going somewhere, one that routes requests to the cheapest machine that can handle them. Both are trained on Ghost's own recorded turns. Skipped entirely when nothing new has been recorded since the last retrain.

  6. After ~1 hour — practise

    Self-play. Ghost generates a challenge for itself, attempts it, scores the result, and keeps what it learned. It aims at the areas where it's least certain rather than picking at random, and the interval adapts: when practice is producing something, it comes back sooner.

Times are how long you've been quiet. Each phase also has its own cooldown between runs.

Two more that are off by default

Post-mortems
Reads the entire transcript of its worst failed runs and files a classified defect report: I chose badly, a setting allowed this, or a tool is broken. The last kind can carry a proposed test and patch — stored for a human to read, never applied automatically. Turn on with --postmortem.
Advancing projects on its own
When idle, push one active project forward by one step without being asked. Runs on hard per-project budgets with human gates. Turn on with --autoadvance-idle.

What all of this is actually reading

Every one of those passes reads the same thing: a trajectory — one JSON line per turn recording what was asked, which tools ran in what order, what came back, and how it ended. They're written append-only to $GHOST_HOME/trajectories/, redacted on the way out, and if the write fails the turn carries on regardless. A logging failure must never break a user request.

That one log is the input to five different consumers, each asking a different question of it:

Reads trajectories to askProduces
What went wrong in this turn?A lesson.
What about the agent itself made this fail?A classified defect report.
Which procedures keep recurring?A new reusable skill.
Does a half-finished plan look like it's going somewhere?A trained step-scorer.
How hard is this request likely to be?A trained router.

How a skill gets extracted

Worth spelling out, because "the agent learns new abilities" is vague and the actual rule is not:

  • Only turns that passed are considered, and only those using two or more tools — a one-tool solve isn't a reusable procedure, it is the tool.
  • Turns are grouped by the exact sequence of tools they used. A group becomes a candidate only once several distinct turns support it, so one lucky run can't become a skill.
  • The exemplar kept is the one with the fewest tool calls, ties broken by speed — the shortest validated path, not the first one found.

Skills are also re-tested later rather than trusted forever. A skill is only as good as the moment it was learned, and tools get renamed, libraries upgrade, and the model itself drifts. Re-verification decides whether each one stays active, gets deprecated, or is kept under watch.

The two small models it trains

Both are plain logistic regression in numpy, saved as JSON. That's a deliberate ceiling: they're trained on a few thousand of the agent's own turns, which is not enough data to justify anything bigger, and a model you can read as a list of weights is one you can debug.

The router in particular is built to fail safe — a low-confidence prediction escalates to the full pool rather than gambling on the cheap path. The worst it can do is fail to save you a call. It never blocks a request.

It tunes its own prompts — offline, and against a baseline

Three prompts are treated as optimizable rather than hand-written and final: the one that breaks a request into sub-tasks, the one that picks a tool, and the one that critiques a failed turn. An optimizer rewrites them from the agent's own successful turns.

This runs offline, when you start it — it's not one of the idle-time passes. Tuned prompts land in $GHOST_HOME/system/optim/ and are picked up at the start of the next session.

  1. Build a training set from turns that worked

    The request is the input, the validated final answer is the target. Filtered hard on passed — feeding an optimizer failed examples defeats the point.

  2. Optimize against the local model

    The optimizer points at the same local model the agent already uses. There's no teacher model and no external endpoint — consistent with the rest of the project, and a real constraint on how good the result can get.

  3. Stop early, on purpose

    Capped at 16 iterations. Longer optimization runs drift toward gaming the metric rather than doing the task — measured elsewhere at a 26% → 58% rate of that between 10 and 100 steps. The cap is the mitigation; raising it needs a stronger held-out test first, not just patience.

  4. Beat the hand-written prompt, or don't ship

    The tuned version is A/B'd against the existing one. Losing means it isn't promoted. The hand-written baseline is the thing to beat, not a formality.

Two things this got wrong, which are worth knowing. For a while the optimizer wrote tuned prompts to disk that nothing ever read — it was write-only, and the loop only closed once the loading side was built. Separately, a promoted prompt turned out to have won on one scoring metric and to lose on a better one, so it had to be un-promoted. The lesson that stuck: when you change the metric or the gate, re-score the incumbent too — otherwise you're comparing a new candidate against a champion that was never measured the same way.

The harder question underneath

Optimizing a tool's description assumes the tool boundaries are right and only the wording is off. If the model keeps confusing the same two tools, "the description is unclear" competes with "the boundary is in the wrong place" — and better prose can't fix the second one.

Measured 2026-08-05 by replaying 67 held-out choices from live traffic against the shipped descriptions: the agent picks the correct tool 82% of the time (55 of 67, with none failing to replay). The 12 misses land on 12 different tool pairs — not one pair occurs twice. Two of them are stalls where it picked no tool at all.

So on this sample there's no evidence that any particular boundary is mis-drawn; the errors look scattered rather than systematic. But 12 misses spread over sixteen tools is also too few to rule out a boundary problem — that pattern is what you'd see either way. The question stays open, and it needs a wider corpus rather than a better argument.

Seeing what actually happened

All of this is invisible by design — routine background work doesn't interrupt your conversation. To see it, ask.

"What did you do while I was away?"
Reads the background activity ledger — which passes ran, what came out of them, over whatever window you name.
"What have you learned this week?"
Reads the lesson list back. This is a real read of stored records, not the model recalling from context.
"Is your learning actually working?"
Health telemetry for the learning loop itself: are lessons being used, are the retrains succeeding, is the confidence calibration fitting. This is the page to check when you suspect a subsystem has quietly stopped running.
"What have you found broken in yourself?"
The post-mortem defect queue, if you have post-mortems enabled.
The characteristic failure mode here is silence. A learning pass that has stopped running looks exactly like a learning pass with nothing to do — both produce no output. If you want to know whether this machinery is alive, check biological_watchdog_alive on the health endpoint and ask for the activity ledger. Don't infer it from the absence of errors.

Turning parts of it off

Every phase has an off switch, mostly so you can measure whether it's earning its cost.

FlagTurns off
--no-dreamMemory consolidation. Leaves reflection and self-play running.
--no-self-playPractice. Leaves the rest running.
--no-reflectionReviewing failed turns.
--no-trajectoriesRecording turns at all. This also disables reflection, since it has nothing to read.
--no-verifierThe self-check. Not recommended outside an experiment — see below.
--no-memoryEverything. Ghost becomes a plain chat wrapper.
Why --no-verifier exists. When the check runs late (on a streamed answer), it can't change what you already read — its only payoff is cross-session, by scrubbing bad lessons and queueing a correction. That's a real benefit but not an obvious one, and it costs a full extra model call per turn. The flag exists so you can measure the difference rather than assume it.
