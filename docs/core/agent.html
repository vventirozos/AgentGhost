core / agent.py

The reasoning loop. Drives streaming chat completion, parses tool-call XML, dispatches tools, and re-injects results.

Purpose

GhostAgent is the orchestrator that the FastAPI route hands a chat payload to. It owns the turn loop: it asks the upstream LLM for a streaming completion, watches the stream for <tool_call> XML blocks, parses arguments, runs the tool against the registry, captures output, and folds the result back into the conversation as a tool message. Sampling temperature, top-p, and the size of the "thinking" budget are all derived dynamically from a query classifier.

Thinking-loop guards relaxed for a strong model (2026-06-22)

Several reasoning guards were tuned for a weaker model that looped easily, at an explicitly "acceptable false-positive risk." For a capable reasoning model those false positives — guillotining legitimate long derivations — outweigh the benefit, so they were loosened (the genuine-runaway backstops remain):

  • Hard length-abort 64 K → 200 K chars. Between 32 K (where loop-checking starts) and 200 K, the stream is aborted ONLY when _detect_thinking_loop actually fires — so a hard algorithm/proof/debug problem that legitimately needs >16 K thinking tokens can finish. 200 K is the pathological-runaway ceiling.
  • Loop detector (300/150/2) → (500/200/3). Now needs ~600 chars of genuine repetition (3× a 200-char window) before firing, vs the aggressive ~300 chars (2×150) that could trip on reasoning restating a constraint or invariant. The tool-call-collapse probe + the 200 K ceiling stay as fast backstops.
  • Thinking-cap force-stop 2 → 3 events — one more grounding nudge before aborting the attempt, now that detection is conservative.
  • Cross-turn repetition Jaccard 0.7 → 0.85 — focused iterative work (refining the same function, debugging the same test) opens consecutive turns with ~0.7 vocabulary overlap; only ~0.85+ is a true restart-the-same-derivation loop.

Covered by tests/test_think_enumeration_loop.py, tests/test_cross_turn_repetition.py, tests/test_smart_problem_solving.py.

Streaming loop: per-token cost bounded (2026-07-07)

The streaming consume loop did O(buffer) work on every token — over a long thinking stream that is O(n²) CPU plus GBs of transient string allocation on the single event loop (a plausible contributor to the RSS ratchet, since malloc_trim is Linux-only and a no-op on this Darwin host). Four sites, all bounded with zero change to detection behavior:

  • Stop-marker scan. The </think / <tool_call check lowercased the entire accumulated buffer per chunk. It now scans only a len(token)+16-char tail (_tail_has_stop_marker) — a marker straddles at most one chunk boundary, so the tail is sufficient, and the display latches stop_printing on first sight anyway. Quoted-mention guard (2026-07-29 log audit): reasoning that QUOTES the rule text — the constraint says "Emit EXACTLY ONE `<tool_call>` block" — used to latch the mute mid-sentence, silently dropping every later thinking token of the turn from the log (visible as thinking lines cut right before a backtick). A marker immediately preceded by a backtick or quote character is treated as a mention, not a stream transition; a real transition later in the same stream still latches. Tests: tests/test_log_audit_fixes_2026_07_29.py::TestQuotedMarkerMention.
  • Tool-call-collapse probe. _detect_tool_call_loop ran two full-buffer re.findall scans per content chunk; TOOL_CALL_LOOP_PROBE_EVERY existed but was never consulted. Now gated on a next_tool_probe cadence (every 200 chars).
  • N-gram loop detector. Once thinking passed 32 K, _detect_thinking_loop (an O(buffer) buf.count(tail) over up to 64 K chars) ran per token — the boundary branch ignored the next_loop_probe cadence that the periodic probe already used. The per-token boundary branch is removed; the detector runs once per THINKING_LOOP_PROBE_EVERY (500) chars at all sizes, so early loops are still caught within 500 chars and the 32–64 K "extend if diverse" window falls out implicitly. Only the extended hard cap keeps an explicit per-token length check (cheap).
  • Final-generation scrub. The XML-scrub re.sub re-ran over the whole answer per content chunk. It's now skipped entirely until a < actually appears (_scrub_seen_lt) — the common tag-free final answer emits raw tokens in O(1)/chunk; the full sub only runs once real XML is present.

Covered by tests/test_streaming_dequadratic.py; the unchanged detector functions and cap-escalation behavior stay green under tests/test_thinking_loop_guards.py and tests/test_thinking_cap_escalation.py.

Risk-governor checkpoint answers are not reply text 2026-09-15

History (2026-10-11, §4NM). The risk governor was removed on 2026-10-11. The structural-first scrub below stays, because any protocol exchange with the loop (steers, breaker reports) has the same shape.

When the risk governor fired it injected a numbered checkpoint as a user message: state what is CONFIRMED vs ASSUMED, name the SINGLE smallest check that would distinguish them, or STOP and report. The model answers it in ordinary prose — and because that answer is emitted on an iteration which then calls more tools, it lands in final_ai_content like any other working narration. Live (req 4b518a82) five such answers stacked up and shipped as the opening third of a forensic report, which then restated all of it in its own sections; the narration smoother trimmed 209 of 11,498 characters. The user never asked the question, so the answer is a protocol exchange with the loop, not a deliverable.

The removal is structural first, lexical last. A segment is recorded as a candidate only when (1) a steer has fired this turn, and (2) the iteration emitting it went on to call tools — which makes it provably not the final answer — and only then is (3) its shape tested, by is_governor_checkpoint_answer, which requires two distinct directives of the steer to be addressed. That ordering is what keeps a deliverable's own "Confirmed: … Not confirmed: …" section safe: it is written on the last iteration, so it is never a candidate, and it addresses only one directive anyway. At finalize, drop_checkpoint_segments removes the recorded segments by exact substring, never by resemblance, and fails open in both directions — a segment a later stage rewrote is skipped, and a removal that would empty the reply is refused (a turn that complies with "STOP and report" has the checkpoint as its entire answer, and the user must still receive it). The steer's vocabulary is owned at the producer (core/risk.STEER_DIRECTIVE_TERMS) and pinned in sync, so re-wording the steer cannot silently strip the smoother of its ability to recognise the answers. Replayed against the live reply: 2,359 characters removed, report intact. Covered by tests/test_governor_checkpoint_scrub.py.

Multi-turn reply smoothing (2026-07-17)

The turn loop appends every iteration's visible text (ui_content) to final_ai_content, so a multi-tool fix used to arrive as stacked working narration ("Let me fix both:", "Now add the resize logic in openWindow:") with the summary stated twice — once before a verify/restart step, once after (operator report: the WebOS minesweeper turn). The system prompt's execution-mode rule already forbids narrating during tool use (and was sharpened: no summaries until the whole task is done, never restate one); the model doesn't reliably comply, so core/reply_smoothing.smooth_reply() cleans the DELIVERED reply deterministically in _finalize_and_return, right after the adjacent-duplicate collapse and BEFORE the verifier gate (the verdict judges the text the user actually receives). The live stream is untouched — narration keeps serving as progress; only the persisted/delivered reply (session store, Slack, trajectories, banners) is smoothed.

  • Gate: only turns with ≥2 non-synthetic tool runs — conversational and single-tool replies are never rewritten.
  • Shape 1 — connective narration: a non-final paragraph ≤300 chars opening with a progress connective. Fences and list items are exempt. Since §4FV (2026-09-10) the connectives are two classes: an agent-voice beat (Let me / Let's / I'll / I will / I need to / Time to / Good, / Okay / Alright / Great, / Perfect,) is dropped on sight — the model narrating its own next move can never be an instruction addressed to the user; a bare temporal lead (Now / Next, / Then / First,) is dropped only when a later prose paragraph RESTATES it, the same evidence shape 3 requires. A temporal lead sitting on an agent beat ("Now let me fix both:", "Then I'll restart it") is still a beat: the lead is stripped and the rest re-tested, so the 2026-07-17 coverage survives the narrowing.
  • Shape 2 — superseded summary group: a ':'-lead-in plus its list items whose content words are ≥55% Jaccard-covered by a later group of comparable size (≥60%) — the pre-verification summary; the last statement wins. Groups containing fences are never dropped.
  • Shape 3 — stale announcement (2026-09-09, §4FR): a non-final paragraph ≤300 chars containing a sentence that announces work in the progressive behind a lead adverb ("… Now ingesting into the knowledge base.", "Next, indexing…") is dropped when a LATER paragraph reports that verb as done (ingested / ingestion / downloaded). Only then: an announcement nothing later completes may be the truth ("Now ingesting in the background — I'll report back") and stays. Request d50a34bd's reply opened with exactly this beat — the model's turn-3 progress line, delivered as the first sentence of a finished job — and shape 1 could not see it because the connective was the paragraph's SECOND sentence. The lead adverb is required (a bare gerund is a subject: "Testing is complete."), a verb followed by an auxiliary is a statement, and verb morphology is naive on purpose (stem + ed/d/ion): "running" → "ran" never matches, so the paragraph is kept. Fail-open like the other two. Pins: tests/test_reply_stale_announcement.py.
  • Fail-open: fenced blocks are split-atomic (blank lines inside a fence don't split it), the final block is never dropped, and an over-scrub that would empty the reply returns the original. Idempotent.

One treated view, every consumer 2026-09-10 §4FV

_finalize_and_return scrubs and smooths final_ai_content IN PLACE, so on the non-streaming path every consumer after it reads the delivered text by construction. The streamed drain had no such variable: §4FS treated only the trajectory copy and handed the rest of the drain the raw accumulator. Eight readers on the common (web-UI) path were learning from, or judging, text the user never received — the hedge auto-scan, the smart-memory arc, the (since-removed) post-mortem, the episode record, the hydration judge, the project work_log, the calibration sample and the promise backstop's headline. §4FT listed six of the eight; the hedge scan and the backstop were not on the list.

reply_smoothing.treat_reply(text, n_real_tools=…) is now that missing variable, computed once at the top of the drain from the same effective-content base the trajectory uses (so the scrub-fallback sentence, not tag soup, is what every consumer stores) and read by all of them. It is idempotent, fail-open (a treatment that raises leaves the raw text rather than costing the turn its record), and it owns the SMOOTHING_MIN_TOOLS threshold and the count_real_tools synthetic filter so no caller can spell the gate differently.

Three readers stay on the raw accumulator, each marked at its site and enumerated by an AST pin that fails when a fourth appears: the <think> extraction that feeds the web UI's monologue box (those blocks live inside the paragraphs smoothing drops), the streamed verifier's claim (the live stream showed the narration, so the verdict judges what was delivered — the record keeps what the turn said; this is the one place the two legitimately differ), and the treated view's own base. The session store is unaffected: it persists the concatenated SSE chunks, i.e. the transcript the user read.

Of 27 bare temporal-lead paragraphs, 24 are still dropped because the reply restates them; the three now kept are a joke line, a task-status statement and one genuine beat ("Now restarting the server:") — the accepted residue.

Grammar-constrained tool calls (2026-07-17)

core/tool_grammar.py builds a llama.cpp GBNF grammar from the registry's tool schemas (memoized on the same frozen signature as the XML-schema serialiser) and the payload attaches it LAZILY on every non-final tool turn: grammar + grammar_lazy + a PATTERN-type trigger on \n<tool_call> (newline-anchored so a tag QUOTED inline in thinking can't arm it — the think-strip incident shape). Dormant through reasoning and prose; from the trigger on, only valid framing, known tool names, known parameter names, enum-legal values and numeric-legal integers can decode — the malformed-call strike class dies at the sampler. Validated live before wiring: full 39-tool grammar compiled server-side; action='bogus_action' was coerced to a legal enum (value rules are deliberately TIGHT — whitespace padding gave the sampler an escape hatch and it stalled on tabs). String values use a </parameter> prefix-exclusion chain so file content with markup keeps working; required-ness stays with the tool layer. Paired with --no-native-tools in the launcher: the upstream parser (two corruption shapes on VALID output: merged multi-tool args 2026-07-05/AF, value duplication AF/43) is retired and the agent's own robust XML parser consumes the output. The XML schema block returns to the prompt (~7K tokens, absorbed by the stable-prefix prefill).

Status: OPT-IN (GHOST_TOOL_GRAMMAR=1), default OFF — first production request (req 9f1c3173) exposed a thinking-turn blind spot the probes missed (they ran with /no_think): the model DRAFTS the literal <tool_call> inside its reasoning block, the pattern trigger armed mid-think, and generation died at <tool on every retry — a hard-fail loop. Re-enable only after the trigger is upgraded to llama.cpp's think-aware PATTERN_FULL semantics (capture-group marks where constrained text begins, anchored past </think>) and validated on a THINKING turn. --no-native-tools stays: the XML parser path was the pre-native default and is verified live post-restart. The planner hits the same token cap — and the obvious salvage is the dangerous one 2026-08-11

History (2026-10-11, §4NM). The strategic (System-2) planner was removed on 2026-10-11, together with scripts/planner_nothink_bench.py; a second pass the same day deleted the inline planner code itself — --use-planning, PLANNING_SYSTEM_PROMPT, salvage_truncated_plan, the per-iteration prefix snapshot and the GHOST_PLANNER_MAX_TOKENS / GHOST_PLANNER_NO_THINK / GHOST_PLANNER_TIMEOUT knobs described below (none is read any more). The salvage lesson is kept as a record; core/planning.py's project TaskTree is a different thing and is live.

The strategic planner runs at max_tokens=4096 with a tree_update that grows with the task list. On req 6e9efd6a it hit finish_reason: length seven times in one request, each at exactly 4096 completion tokens. extract_json_from_text returned {}, so the whole plan was dropped — thought, tree and focus — and the log read No thought provided. / Plan Updated. Focus:  with nothing naming the token cap as the cause. The loop carried on unguided; the request ran 40 minutes.

Salvaging naively would have been worse than the bug. _repair_truncated_json closes dangling braces, so a tree_update cut mid-object comes back complete-looking with tasks silently missing — and task_tree.load_from_json would adopt it as the plan of record. Measured on those seven payloads: one repaired into a root task with zero children (the entire plan, gone), and another into a plausible 8-node tree that was still incomplete — the kind no eyeball catches. There is no way to tell from the repaired dict alone.

_complete_object_for_key(raw_text, "tree_update") is the discriminator: it scans the raw text and requires the object's depth to return to zero, so closed ⇒ trustworthy, cut ⇒ None, with no guessing. salvage_truncated_plan() returns (salvaged, whole_tree); the planner takes thought / next_action_id from the first and tree_update only from the second, keeping the previous turn's tree when the new one was cut. On the seven live payloads that recovers the thought every time, keeps 2 intact trees, and discards 5 damaged ones.

The diagnostic itself was lying twice, which is why this took a hunt. extract_json_from_text warned “malformed JSON-like content” — a phrase that describes a syntax error and points the reader at the parser rather than the token budget. Two fixes: a truncation now reports TRUNCATED JSON — N unclosed brace(s) and names max_tokens/finish_reason as the place to look; and the “this looked like JSON” gate is no longer '{' in text, which fired a WARNING on any prose containing braces. Of the 9 warnings in that request, 2 were a markdown reply quoting a CSS rule (#session-modal { z-index: 1001 }) whose real payload rode tool_calls and never intended JSON at all. Braces inside an inline code span are now masked before that decision, and brace-scanning ignores braces inside string literals so a value like "use {this}" cannot make a complete object read as truncated.

⚠ The first discriminator shipped here was wrong, and the existing suite caught it. It required a quoted key, on the reasoning that real JSON has one and a CSS rule does not. But { thought: missing-quotes, next_action_id: !!! } — a model emitting the plan with unquoted keys — is a genuine malformation that must warn, and it is structurally identical to { z-index: 1001 }. Nothing inside the braces separates them; the surrounding context does. A pre-existing pin on that exact shape failed, which is the whole argument for keeping tests that assert a warning still fires.

Truncated-answer auto-continuation

The streaming consume loop records the last non-null finish_reason seen on the upstream stream. When a text turn (no <tool_call> / <function> in flight) ends with finish_reason == "length", the answer was cut off at the model's token cap — shipping it would hand the user a mid-sentence reply, which the Verifier correctly REFUTES (truncated output, and any explicit question left unanswered).

Instead of surfacing the fragment, handle_chat transparently continues the generation: it replays the request with the partial answer as a prior assistant turn plus a "your reply was cut off — continue from exactly where it stopped, don't repeat anything" instruction, and appends the result to full_content. This repeats until the upstream returns a non-length finish or MAX_TRUNCATION_CONTINUATIONS (3) round-trips are spent — the bound prevents a model that mis-reports length on every reply from looping forever. The continuation payload drops tools/tool_choice so it can only produce prose, and strips any <think> prelude the continuation emits before appending. Turns that produced a tool call are unaffected — those go through the parse/retry path, not this user-facing-prose path.

Mid-stream aborts fold into the same path 2026-07-22. When the upstream stream aborts mid-answer (an idle stall, a mid-stream break, a connect failure), _do_stream_chat_completion emits a data: {"error": …} frame (no "choices") then [DONE]. The turn-loop drain previously parsed only frames containing "choices", so it silently dropped the error frame and finalized the half-generated full_content as if it were a complete answer — feeding a truncated reply to the verifier and memory with no signal it was cut off. The drain now detects the error frame (sets stream_errored, logs a Stream Aborted warning) and folds it into _truncated_text_turn alongside finish_reason == "length", so an aborted stream triggers the same continuation attempt rather than shipping a silent partial. The streamed final-answer path logs the abort too (its verifier gate already REFUTEs the partial). Covered by tests/test_agent_stream_bg_fixes.py.

Turn flow

Figure 2 — Per-turn dispatch within GhostAgent.handle_chat.

Trivial-request fast path

A bare greeting or acknowledgement ("hi", "thanks", "ok cool") cannot benefit from memory hydration, tool schemas, the planner gate, or KV-cache rebuild — yet it used to traverse the entire turn loop. handle_chat intercepts these via _handle_trivial_chat, which issues a single tool-less LLM call against a pared-down "lite" system prompt (persona + user profile only) and returns the reply directly, collapsing ~2.5 s of work into one short request.

The gate is deliberately strict: _is_strict_trivial_chat matches the message against a small allowlist of greeting/ack tokens and phrases, and hard-rejects anything containing ?, /, file extensions, or other action signals. Missing a real greeting costs one extra request; intercepting a tool-bearing request would break the response — so the gate errs toward falling through. Since §4QN (2026-10-22) the memory-hydration gate uses the same strict check: the loose ≤5-word is_trivial_greeting flag had skipped every memory tier for short questions ("where do i live ?", "what's my dogs name ?", "news"), which the profile in the system prompt masked but the lessons, experience and history tiers could not reach; hydration costs about 0.6 s.

Reasoning-model handling. The upstream is a Qwen-style reasoning model. Left unconstrained on a 256-token budget it spends the whole budget inside a <think> block and returns an empty content field, which previously made every greeting decline and fall through to the slow path. The fast path therefore suppresses chain-of-thought on both switches the model honours — the chat_template_kwargs={"enable_thinking": False} flag and the portable /no_think soft-switch appended to the user message — and uses the NON_THINKING_GENERAL_PARAMS sampling profile.

Extraction is robust to either response shape: it reads message.content and folds in any separate message.reasoning_content field, then strips <think>…</think> (closed or unclosed) before deciding whether a visible reply survived. Only a genuinely empty result, a missing LLM client, or an upstream error makes the path decline and fall through to the full turn loop.

Concurrency

Single-task asyncio. The streaming generator is consumed inside the FastAPI request task; tool execution is awaited inline (the tool itself may use threads / subprocess). The agent does not spawn parallel turns — concurrency lives in MemoryBus (parallel hydration) and LLMClient (parallel pool dispatch).

Turns are serialized — agent_semaphore = Semaphore(1) (2026-07-07, was 10). Per-turn state lives on the singleton context: last_user_content (read mid-turn by the intent gates in tools.projects and tools.memory) and current_project_id (drives project-scoped sandbox writes). Two concurrent turns therefore clobber each other's scope — the concrete hazard being an APScheduler cron job that fires handle_chat mid-user-turn and switches the active project, landing the user's uploads/writes in the wrong sandbox with plausible-looking logs. There is one upstream llama slot, so concurrent turns mostly just interleave waits anyway; serializing costs almost nothing and closes the whole state-corruption class. Complementarily, a scheduled job defers (skips this firing, re-fires next tick) when a user request is live — tools.tasks.should_defer_scheduled_task — so an idle autonomous tick never makes a user wait behind it. (If real per-turn concurrency is ever needed, the correct fix is moving those two fields to contextvars, not raising the semaphore back up.) Covered by tests/test_turn_serialization.py.

Two placement defects closed 2026-09-04

A measurement pass over seven days of live traffic found the stack was prefill-latency bound, not throughput bound: the GPU was busy ~5% of the time (2.96 h prefill + 5.54 h decode over 168 h) while median time-to-first-token was 52.6 s — 72% of a request's wall clock. Prompt-cache hit rate was already 77.5% (prompt_tokens_cached_total 24.1M vs prompt_tokens_total 6.98M), so the remaining loss was concentrated in a few structural misses. Two were placement defects, both invisible to behavioural tests because the model received identical information either way — it simply had to be re-prefilled.

(1) The final-generation turn dropped payload["tools"]. The Ornith/Qwen chat template renders the # Tools block before the system text, so removing the tools key leaves a common prefix of nineteen characters (<|im_start|>system\n) — the entire prompt, at its largest of the whole request, re-prefills from token 3 on exactly the turn the user is waiting for. Live proof (req 5d15ffb9, a two-turn greeting): turn 1 = 27,152 prompt tokens with tools; turn 2 = 6,568 tokens fully re-prefilled in 5.8 s, and 6,568 + ~21,400 tokens of tool schemas reconstructs turn 1's 27,152 — the drop was the whole cost. The schemas now stay attached and suppression rides tool_choice: "none", which renders a byte-identical prompt to "auto" (verified against the live template through /apply-template: both 14,955 characters, common prefix 14,955), because the template branches on the presence of tools alone. force_final_response continues to drop any tool_calls a non-conforming server might still emit, so behaviour is unchanged and the re-prefill goes to zero. This is the same defect the pin above closed for tool_header_block; it reached the prompt through the native tools channel instead.

(2) _compose_injection folded the volatile block into an existing message. Of its three branches, turn 1 and "last message is not a user message" appended the <system_state_update> block as its own trailing message, but "last message is a later user message" prefixed it onto that message. That third branch is the common agentic case, because the request builder translates every role:"tool" result into a role:"user" <tool_response> message — so on nearly every turn ≥ 2 the block was folded into the newest tool result. Since req_messages is rebuilt clean from messages at the top of every turn, the folded block is absent from that same message next turn: the cache diverges there rather than at the genuinely-new content, and re-evaluates the tool result it had already paid for. Measured over an 8-turn request at live median block sizes, rendered through the real chat template: 9,232 → 5,721 re-prefilled tokens per turn (−38%). The block is now appended on every branch. The emergency context-overflow recovery was hardened alongside it: it picks the last substantive user message, so it retries against evidence rather than against timestamp bookkeeping.

A defect inside the fix. Keeping the schemas attached means a final-generation turn now sees the tools it is told not to call, and tool_choice: "none" suppresses only the parsed call — measured against the live server, llama.cpp returns tool_calls: [] and leaves the <tool_call> XML in content, which this agent's own XML parser then turns back into calls. The streaming scrubber was already gated on is_final_generation, but the dispatch drop guard tested only force_final_response. Those differ — is_final_generation is force_final_response OR required_tool == "none" — so the two halves of one promise disagreed and a planner signalling through required_tool alone could dispatch a tool on a turn declared text-only. Both halves now use the wider predicate.

Both are pinned by tests/test_prefix_cache_placement.py, whose assertions are written in the cache's own vocabulary rather than the fix's. The tools pin executes the production if statement, extracted from handle_chat by AST — a hand-written miniature of the payload block (as in tests/test_native_tools_flag.py) passes with or without the fix, which is why the defect survived so long. The placement pin asserts that cache loss does not scale with the size of the preceding tool result; an earlier draft asserting "the volatile block sits on the last message" was vacuous — a folded block also sits on the last message, and the mutant survived. Ten mutants (revert either fix, invert tool_choice, re-pop tools, fold onto the pinned message, empty or drop the volatile block, copy the tail into it, narrow either half of the suppression predicate) are all killed — mutation score 10/10.

Not fixed here, and worth knowing when reading latency numbers: the llama-server launcher had a bare # comment line inside its backslash continuation, which silently terminated the command and dropped -np 1, -t 10, --jinja and "$@". The server therefore auto-selected four slots, 81% of slot selections fell to selected slot by LRU instead of LCP-similarity, and the ~25.5k-token static head was evicted constantly — which is what turned a greeting into a 30.7 s cold prefill. The launcher now builds its argv as an array and echoes it before exec, so the flags actually used are on the record in Logs/llama-server.log.

Repeated-identical-failure breaker (2026-06-07)

The structural strike count (execution_failure_count, cap 6) decays by 1 on any successful tool turn. That decay let a specific loop run unbounded: an agent that oscillates "same failing read → auto sandbox-listing (succeeds) → same failing read …" never accumulates strikes, because each interleaved success cancels the prior failure. Observed in production — a fresh project whose stale workspace narrative kept asserting a prior project's index.html existed; the model re-read the missing path every other turn and burned all 40 turns without progress.

The fix tracks failures by a (tool | whitespace-normalised error) signature (_note_repeated_failure). When the SAME structural failure recurs ≥3 times in a request, the loop is recognised: the success-decay is frozen (persistent_failure_seen) so the recurring failure now accumulates to the strike cap and the loop-breaker fires, and the model is told ONCE — clearly — to stop retrying the identical action, that the live tool result and sandbox listing are authoritative over any stale context / memory / DYNAMIC SYSTEM STATE hint, and to pick a different action (create the missing file, or choose an existing one). Paired with the file_system loop-breaking "not found" message that gives the model the same exit at the tool layer. Covered by tests/test_not_found_loop_breaker.py.

The freeze is reversible (2026-06-11): 3 consecutive clean tool successes unfreeze the decay — a genuine pivot produces them, while the fail→auto-list→fail oscillation never can. Signature counts are kept, so the same failure recurring re-freezes on its very next occurrence. Previously the freeze was permanent for the request, which trapped multi-step tasks whose step 1 looped before steps 2..n succeeded. Same audit also made every tool-argument parse-failure site log a WARNING naming the tool (no more silent except: pass dispatching empty args), and bounded turn-loop journal appends with a 10s timeout (_journal_append_safe) so hung journal I/O can no longer park the event loop until the watchdog's opaque activity-timeout. Covered by tests/test_core_loop_defect_fixes.py.

This loop-detection state — the failure/action signature dicts, the freeze flag + warned set, and the clean-success counter — is encapsulated in StrikeLedger (core.strikes), so the turn loop holds one ledger instead of five interacting locals. The raw strike counters (execution_failure_count / transient_failure_count) stay in the loop because they are cross-cutting (strike caps, mid-loop caps, System-3 pivot triggers). The ledger's behaviour is covered by tests/test_strike_ledger.py.

Pre-flight guard: lifecycle + signature keying (2026-07-30)

Solar-sim postmortem: manage_services start failed twice on an occupied port, the model then correctly remediated (killed the port holder via shell, confirmed the port free) — and the guard blocked every subsequent start attempt across three consecutive requests, including on a different port and with a different command. Each request then died at the 2-block budget. Root causes and fixes, all in core/triggers.py + the dispatch loop:

  • Self-deadlock — no world-changed reset. A blocked call never dispatches, so it can never prove the fix worked; once armed, the guard stayed armed forever (reset() had zero callers — the 2026-07-18 world-changed fix only reached StrikeLedger). Now a successful state-mutating call clears the guard via note_world_changed(): any file_system mutation, any mutating manage_services action (start/stop/restart/stop-all), or an execute command matching looks_mutating_command — a heuristic that catches process kills (kill/pkill/fuser -k, but not kill -0/pkill -0 liveness probes), file-mutation verbs, service-manager mutating subcommands, and bare stdout redirects (but not 2>/dev/null-style fd redirects, which would clear on nearly every probe). Two precision rails keep probe-heavy sessions from disarming the guard: mutation verbs must sit at command position (so grep -rn 'mkdir' src/ and ls release.tar.gz mention verbs as data, not commands) and quoted segments are stripped before matching (awk '$3 > 100' is a comparison) — except a sh -c '…' payload, which is itself a command and gets its own scan. The reset is deliberately global and deliberately permissive: a false clear costs one extra real attempt (fresh identical failures re-arm at the threshold); a false block is the deadlock this fixes. The mutation hint is computed at dispatch time (args in scope) and acted on only when the call succeeds — where "succeeds" is execute-aware: shell results carry an EXIT CODE: banner instead of an Error: prefix, so the world-changed branch parses it (same notion as the execute strike path). Without that, a failed remediation (kill against a stale pid: exit 1, nothing killed) would have counted as a successful mutation and cleared the guard. The asymmetry is deliberate: execute failures are still not recorded into the guard — repeated identical shell failures are the strike ledger's and System-3 pivot's crisis signal, and blocking the re-issue pre-dispatch would starve the pivot (test_system3_crisis_pivot caught exactly that when recording was tried).
  • Key collapse — signature fallback. primary_target_from_args recognises none of manage_services' identity args (name/port/command), so every start of every service shared the key (manage_services, "", start) — a changed-port or changed-command retry was "the same action". guard_key_target(primary, a_hash) now falls back to a short SHA-1 signature of the full canonical call (args#…) when no primary target exists, making the block message ("re-running it UNCHANGED will fail the same way") literally true: only byte-identical re-issues match. Check site and record site key through the same helper.
  • Stale cross-request memory. The guard lives on the agent instance (it must survive turn boundaries) but entries only aged out by new failures pushing them off the deque — two entries from a 16:51 request still hard-blocked the first attempt of the 17:02 request. The guard is now reset at request start (next to strikes = StrikeLedger()); cross-request pathology remains the offline post-mortem fingerprint's job.

Honest-failure rule — a broken tool is not a broken turn (2026-07-31)

Operator decision. resolve_turn_outcome ranked a STRUCTURAL execution failure above every other signal, so a turn whose only tool call failed and whose answer honestly reported that failure ("that file does not exist") was recorded FAILED — even with the verifier CONFIRMING the answer at 100%. That labelled truthful failure-reporting as bad behaviour in the corpus that feeds the Reflector, PRM and skills-auto, in calibration, and in the operator's log line: precisely the incentive gradient that produces fabricated success. Rules 3 and 4 are now swapped — a verifier PASS outranks the structural signal. The environment failed; the turn did not.

What did NOT change (the guardrails that keep this from becoming "giving up is fine"):

  • A REFUTED verdict still beats everything — priority 1, untouched.
  • A shape-heuristic FAILED (runtime abort marker, 4× selector thrash, 3× identical tool error, aborted browser sequence) is still never upgraded: that failure is behavioural, not environmental, however honestly the reply describes it.
  • An execution failure with no verdict at all still lands FAILED.
  • The verifier's own priority-1 request-alignment check still refutes a reply that does not answer what the user asked, so an off-topic non-answer cannot ride this rule to PASSED.

Both delivery paths. The sync path folds the verdict in at write time. …narrowed: an unacknowledged total failure may not pass (2026-08-04)

Operator decision — "add the shape rule, structural failure shouldn't pass". The 2026-07-31 rule above assumed a CONFIRMED verdict meant the reply had handled the broken tool honestly. Request 03b96c28 disproved it: the user asked for a line count of a file outside the sandbox; file_system, execute and file_system all failed; the reply was the single character 0; the cheap judge REFUTED it correctly at confidence 1.0; _escalate_refute sent it to the main model, which overturned to CONFIRMED; and the honest-failure rule rewrote the corpus label failed → passed. A fabrication was laundered into a positive training example by the rule built to protect honest ones.

The rule. When every tool call in a turn failed AND the final reply never says so, a passed verifier verdict does not lift the structural FAILED — regardless of which model produced that verdict. It is a SHAPE rule: no model is asked anything. It lives as resolve_turn_outcome rule 2b, with the detector in outcome_heuristics.unacknowledged_total_failure.

  • ALL, never ANY. A turn where one tool fails and the agent recovers through another and answers correctly is a GOOD turn and still passes. A turn with no tool calls is never flagged.
  • The acknowledgment check is what preserves the 07-31 rule. "That file does not exist", "returned zero results", "the tool does not support that action" — all still PASS. Judged on content, never length: a two-word "not found" acknowledges; a five-paragraph reply that never mentions a problem does not. One extra escape: when the user's own request pins the reply text ("just reply with exactly the word: NOPE") and the reply is that literal, the acknowledgment lives in the request — that is the 07-31 rule's own live-validation probe, and it still passes. "reply with just the number" names a format, not a literal, so it does not license the fabricated 0.
  • Non-manufacturing. The rule can only WITHHOLD an upgrade, never invent a FAILED. It applies only to a turn that is already structurally failed (execution_failed at write time, or a failure_reason of structural failure on the late path). A turn whose strike ledger is clean keeps its PASS even if the corpus text sniffer thinks every result looks like an error — which bounds the cost of that sniffer's known false positives (an EXIT CODE: 1 banner nested deep inside an otherwise successful tool payload).
  • Refute still outranks it, and a shape-heuristic FAILED is still never upgraded.

§4OJ-c (2026-10-13): quote checking is the default, streamed replies included

The operator made quote checking the default: "make quote checking the default". The route puts the eligibility key on every chat request body. handle_chat sets the mode: inline for a non-streamed reply (failed specifics marked where they stand) and append for a streamed one. In append mode, text already on screen is never rewritten.

  • quote_bound.MarkerFilter is an append-only state machine.
    • Text passes through. It holds only what could still become a marker: trailing spaces, a "(", or a "[" that may grow into [src:.
    • A marker ends at the first "]" after a closing quote mark of the opener's kind, so an apostrophe never closes a "…" quote.
    • A marker is abandoned at a newline, at 450 characters, or when a new [src: starts. The text after its last closing quote is given back.
    • Only ``` fences opened at the start of a line protect code. A lone backtick (Don`t) never shows a raw marker.
    • Every marker is recorded with its quote, its position and whether it was abandoned. The closing line checks exactly what was hidden.
  • Final text. strip_view(text, final=True) is the same machine run to the end, so the streamed text and the final text are identical by construction.
  • Reply tap. The tap feeds each generation's new text to one machine (ReplyTap.quote_view).
  • Streamed final. filter_sse wraps the streamed-final frames:
    • content deltas go through the machine;
    • finish and usage frames are held until after the rest and the closing line;
    • an orphan </think> outside code restarts the machine;
    • the closing line is never placed inside an open fence.
  • Finished strings. A finished-string reply of a streamed request goes through check_reply_append: the machine's text plus the closing line. It extends what the tap showed, so nothing is retracted.
  • Logging. Each streamed reply logs "Quote Bound … N marker(s) · M claim(s) not verified".

How it was made safe. Eight fresh-reader rounds found defects in each previous version.

  • A regex view recomputed on every delta shrank when a quote held a "[" or a backtick closed later. Text was lost (CRIT), which is why it became a state machine.
  • Quotes containing quote marks, apostrophes and page references broke the marker boundaries.
  • Reasoning before </think>, a fence closing exactly at the end of the reply, and frame order after the finish frame each caused errors.

The fuzz checks 30,000 random token strings fed in 1–4 character pieces. It finds 0 differences between streamed and final text, 0 markers outside fences, and 0 changes to text without markers.

  • The check: _ends_on_announced_work reads the reply's last line and judges its last sentence with the same narration rule §4IW uses (reply_smoothing.narration_only). It does not fire on a list step, on code at the end, on a promise for later ("I'll check it tomorrow"), or on a creative request. It runs only on turns where no tool ran; after a tool ran, the trailing-promise guard still owns the shape.
  • What happens: the loop keeps the answer, minus its promise sentence, and gives the model one more round. The model makes the call and adds only what it found, or says in one sentence that it did not do it. One nudge per request, shared with the other two guards. The extra round costs one model call, plus the search if one runs, and only on these turns.
  • Interplay: if a verifier repair later asks for a standalone reply, the kept answer is dropped first, so it does not ship twice. If the turn ends in the no-answer fallback, the kept answer stays at the top. On a streamed turn, the first reply is pulled back while the extra round runs, and the final text is the kept answer plus the addition.

§4PM (2026-10-16): the census's other instruments

Still a measurement only: nothing here changes a reply. The §4PL census counted detectors. It could not say whether a task got done, it booked guard refusals as tool failures, and it could not see greetings or why a turn never arrived. These additions to core/failure_census.py fill those gaps.

  • Guard refusals are not failures. Each tool call gets one class: ok, failed, guard, asked_user, partial or unresolved (tool_class). A live call answers by its ToolOutcome status and reason code. A stored call answers by its text: the idempotency guard, the pre-flight guard, the egress scrub and the probe blocks are guards. A memory or project change still waiting for your "yes" is asked_user, and a turn whose last such call is that wait reads as not done. A page the site blocked, a repeated fetch, a disabled or unknown tool and an empty write are not guards: they are the call's own result or the model's mistake. A live call and the stored copy of the same call get the same class. The error-streak detector now counts only real failures; guards and questions to the user neither break nor extend a run. A partial result counts as a failure for the streak, the same as its stored copy. Over 14 days, 33 guard refusals and 8 confirmation waits had been counted as failures.
  • Per-task outcomes. Each turn gets a kind, chosen in this order: image, build, project, research, memory, other tool, no tool. Each kind gets a mechanical outcome from the agent's own checks: an image link that reached the reply (delivered) or not (made_not_shown); a code file that ran after its last write (ran_ok), never ran or failed its last run; research that brought back evidence or none; project and memory calls that were ok, failed, mixed or only blocked. An outcome is not a grade. "Delivered" says the image arrived, not that it was good.
  • Turns that had no row. A greeting answered by the trivial fast path writes no trajectory; it now writes a fast row so the count exists. (§4PY: an owner rule or test command answered by the system writes a command row instead, counted on its own report line, "owner commands answered by the system".) An undelivered turn is reported with its cause, read off its own marker line, and with how long it ran first.
  • Latency and tokens by kind: p50 and p90 duration and median input and output tokens per task kind.
  • The reaction judge on no-tool turns. The idle slot runs the same judge (up to 6 per pass, NOTOOL_CAP_PER_PASS) on turns that ran no tool, into its own file system/selfplay/reaction_verdicts_notool.json. The failure-replay seeds and the regression suite read only the tool-turn file, so they are unchanged. The report labels these as the judge's, never as yours. The second pass is skipped when the owner stopped the first.
  • The gold sample. Every 14 days you draw it by hand (--draw-gold; the report prints when it is due): 30 delivered owner turns at random, graded blind by someone who did not see how they were made. Each packet holds the question, the conversation's earlier turns within the hour, every tool call with what it returned, and the reply, with your identifying details redacted. It holds no label, verdict or trajectory id. The grader is a fresh agent given the brief, or you. The report then shows how many WRONG or PARTIAL replies each signal caught, and how often each fired on RIGHT ones, one source at a time: the code detectors, the machine label, your 👎, the reaction judge and the task outcome. A graded sample stays in the report after its turns leave the 14-day window. When the last graded sample is older than 14 days the report prints GOLD SAMPLE DUE. Since §4QY the grader also gives each item one kind (image, build, bookkeeping, status, knowledge or chat), and ingest keeps it.
  • Why knowledge answers fail (§4QY). --draw-split takes every knowledge turn in the newest graded sample that was graded WRONG or PARTIAL and puts it in one bucket.
    • A means no lookup brought back evidence, in this turn or in the earlier turns the gold packet shows. This is read straight from the stored tool calls. A failed or empty search ("No results", a bot check) counts as no evidence. Recall (your own facts) is not evidence about the world.
    • The other turns become blind packets in split/pool. Each holds the question, the earlier turns with their tools, the full text of every tool result (taken from the §4LH full-results file, because a trajectory row keeps only 4,000 characters), the reply and the grader's reason. Readers sort each packet into B (the faulted specific is in no tool result), C (it is in one, so the source was wrong) or OTHER.
    • --ingest-split r1 r2 counts an item only when every reader rated it and they agree. It refuses a reader file with no usable rows, and it refuses a split whose grades changed after the draw. It applies the rule pre-registered in the journal: A becomes a candidate only at 20 % or more; the largest bucket names the next lever, with ties going to B, then A, then C. It writes split/result.json. Decide only on a result marked complete (two or more readers, nothing unread, nothing missing).

§4PL (2026-10-16): the silent failure census

A measurement, not a behaviour: core/failure_census.py counts which mechanical failure detectors fire on the owner's real turns, and how often the owner's own signals agree. It changes no reply and calls no model. Before it, two features had been justified by failure rates measured on older history; the second (§4PK, an evidence hold on no-tool answers, rolled back the same day) met a model that had mostly stopped making that mistake.

  • Live rows (owner turns only, redacted, rotated at 4 MB) in $GHOST_HOME/system/census/turns.jsonl, keyed by the trajectory's req_id: the quote checker's full result, from finalize and from the streamed filter (quote_bound.filter_sse(…, on_result=…)); and the no-tool detector run over the whole context the turn was given (the composed prompt is stashed per request in context._census_ctx). Neither can change the reply.
  • Offline: scripts/failure_census.py --days 14 joins trajectories, the verdict sidecar, the corrections sidecar (the owner's 👍/👎 and corrections) and the reaction judge's cache, prints a table and saves system/census/report-<date>.json.
  • Detectors: unverified quotes; specifics with nothing behind them, live or "latest" questions, and claimed checks on turns that ran no tool (the §4PK trigger, used only to count); mechanical verifier refutes; streaks of failed tool calls; a FAILED corpus label.
  • Counting: owner turns only, undelivered replies left out. Each detector is counted on its own population ("not measured" is never "did not fire"). The no-tool detectors over history are an approximation (a stored turn keeps 8,000 characters of the prompt and no earlier turns) and are labelled so. Your labels and the reaction judge's (an LLM; tool turns only until §4PM) are separate columns. A first version had seven measurement errors that a fresh reader found; journal §4PL lists them.

§4PH (2026-10-15): how the agent writes code in an interactive turn

Four fresh-eye readers over the coding turn (the workflow and its prompts; execute and how its result is read; the verifier's mechanical claim arms; a blind quality grade of the two released apps) and a 158-turn corpus. The finding that organises the rest: nothing read the reply's claim. The only "did you run it" guard keyed on the LAST tool (_is_unverified_mutation), so write → ls → "tested, it works" shipped clean, and a file whose only run FAILED shipped under "all tests pass"; the prompts told the model the opposite of "run what you wrote" (execute "ONLY AS A LAST RESORT", rule 8b "do NOT save or run it", rule 9 "EXIT CODE 0 → stop"); and the exit code itself was laundered by || true / ; echo done, by a None status from docker, and by a backgrounded &. Corpus: 82 of 158 replies claimed works/tested/verified, 27 of them ran nothing; 1 of 158 ran a test runner; both released apps (a calendar that draws May 31 as the 30th and accepts 2025-13-28; a chess coach whose recovery path calls a method that does not exist) passed release behind "Verified: calendar render".

  • Shared caveat literals (§4QO) — core/receipt_marks.py is the one home of the markers a tool result carries (the image tool's "You have NOT seen this image", introspect's "Health: NOT checked", the confirm gate's "the user has not answered yet", the health check's head, the write tool's LINK CHECK head, the §4PN reply's head); the tools import theirs from it. The turn RECORD built on them was measured null (paired blind grading, RIGHT +2.4 / WRONG +2.4) and removed on the operator's word.
  • The claim arm — core.code_claims: a ledger of code files written this request (file_system confirmations, execute heredocs/redirects, execute(filename, content)) and the last run after the last write (an execute naming the file, a suite run, a page load). _unverified_mutation_note(…, reply) falls through to it on both delivery paths; the in-loop repair consults unbacked_claim_directive on both verdict branches and the directive names the file. The streamed work_log books the unverified turn verifier:failed (it booked "completed" with the claim as its note).
  • The absence refute — _is_removal_capable(name, content, args): an execute is removal-capable by WHAT IT RAN (rm/mv/unlink/rmtree/git clean…), not by its name; write → python report.py no longer disarms the missing-file refute. A row without arguments keeps the fail-open reading.
  • Same-error loops — strikes: the error-line fingerprint drops numeric literals (an assertion whose values move every rewrite, a traceback line number) and keeps the quoted literal of a No module named-class line; the futility counters judge a failing count-less run by that fingerprint, not by its whole output.
  • Exit codes — execute: a ; / || / newline list whose last member exited 0 over a traceback or a pytest failure summary is reported as EXIT CODE 1 with a note; a missing docker status is 1 with a note (the sandbox layer also polls for the exit the daemon records a moment after the stream ends); a 124 far under the budget is named as the command's own timeout; a backgrounded & process gets a "only STARTED" note; the broken-pipe text arm forgives only an exit 1; PIPESTATUS reports the first failing stage. tool_failure: the job banner counts only at the start of a result; the budget kill is a strike, not a transient; [SANDBOX INFRA ERROR is the transient.
  • The standing rules — prompts and the registry: execute is "the way to CHECK code you wrote"; rule 8b returns a SNIPPET as source but RUNS a saved file; rule 9 says EXIT CODE 0 is the shell's last command; the stale "the verifier will REFUTE it" is gone. .sh files get bash -n at write time. request_forbids_running no longer reads "never execute anything downloaded" as "don't run it".
