core / feedback.py

Human outcome labels (2026-08-13, Track 1a of the outcome-supply plan): a 👍/👎 from the human who read the reply becomes a corrections-sidecar record, resolving a turn's outcome=unknown. Tests: tests/test_human_feedback.py.

Why

~57% of real turns end outcome=unknown (§4BC) and every measurement clock in the learning stack — experiment arms, lesson utility, the resolved-rate — is gated on RESOLVED outcomes. The cheapest resolver is the human who just read the reply. This module is the one chokepoint that turns "request_id + thumb" into the same overlay record the user-correction promoter and the late verifier verdict already write, so every corpus reader (iter_trajectories, report_from_trajectories, reflection, PRM/router trainsets) picks the label up with zero new plumbing.

Side effects, in order

  1. Corrections sidecar via collector.update_outcome (source human_feedback:<source>): positive → passed (never carries a reason — writer and overlay both enforce it), negative → failed with the note (redacted, truncated) as reason, or the self-describing default "human negative feedback".
  2. In-process cache (_recent_trajectories_for_correction): the cached trajectory is mutated and stamped human_labeled (snapshot walk — the cache is loop-owned; re-stamped even on idempotent repeats so a failed first stamp is repaired by the next click).
  3. One pretty_log line (👍/👎 icons) — the operator watches the stream.

Lesson credit happens at the ROUTE, not here (R1 review): _flush_stashed_lesson_outcome spawns loop-bound background work, and this function runs on a to_thread worker — calling it here popped the stash and then lost the write. The /api/feedback route flushes on the event loop after a successful non-repeat label.

Idempotent repeats (2026-08-13, from the first live test — three 👍 in 2s appended three rows): a repeat of the CURRENT label (same outcome, source, and redacted reason) is acknowledged with {"ok": true, "unchanged": true} and writes nothing (debug log only). The dedupe lives INSIDE update_outcome's lock (skip_identical=True → returns the truthy string "unchanged") — R2 review: a caller-side compare-then-write was a check-then-act race across concurrent executor threads. Switching signals — or a negative with a different note — still writes; last-write-wins stays the semantics.

Verdict-then-label ordering (R2): when the machine verdict landed FIRST, a human label also (a) re-books the lesson-outcome set with the human sign — _flush_stashed_lesson_outcome retains flushed trigger sets in a bounded ring and books a compensating observation on a sign change (a wash beats a bias; not a reversal, the counters are additive) — and (b) revokes any queued next-turn correction banner for the trajectory (_drop_pending_corrections_for; the banner used to apologize for an answer the user had just thumbed up). Machine lesson retraction and follow-up tasks filed before the label STAND — logged, not reversed. Calibration re-labeling from human labels remains deferred.

Authority: human labels outrank machine verdicts — at two layers

In-process: _human_label_locked (agent.py) gates the ENTIRE late-verdict consequence chain in _record_late_verdict — corpus backfill, the stream re-render, lesson retraction, follow-up filing, and the next-turn correction banner all yield with one WITHHELD line (R1 review: the original backfill-only guard let the rest run, apologizing to the user for an answer they had just thumbed up). At the writer: the late-verdict sidecar append passes yield_to_human=True, and update_outcome refuses — inside its lock, against the file — to supersede a human_feedback:* record with a machine one. That closes the race the stamp can't see (the machine write is DEFERRED through a background thread, so it can be checked before the label exists yet land after it) and survives restarts and cache eviction. Among HUMAN sources (feedback, user-correction promotion, operator scripts) last-write-wins stands, mirroring the established user-correction doctrine.

Deliberately not wired (follow-ups, not oversights)

  • Calibration re-labels — record_late_verdict_correction is source-ranked for the verifier; human labels need their own source rank in the calibration store, a schema decision, not a bolt-on.
  • Reaction removal — labels only accrete; a changed mind posts the opposite signal and last-write-wins resolves it.

Producers

  • Slack: 👍/👎 reactions on bot replies (slack_bot — owner or the reply's requester only).
  • Web UI: thumb buttons on agent bubbles (web_server).
  • CLI (source: "cli", 2026-08-27): /good · /bad [why…] on a streamed reply (cli). The only producer that refuses to label a cancelled or errored turn, and the only one that retries synchronously — including the TRANSPORT failure a restarting agent actually produces, which is ConnectionError and not the HTTP 503 a retry loop written for "the deploy window" naturally reaches for — and then reports whether the label landed. It is also the one where a negative's note (→ failure_reason) is routinely filled in.
  • Anything else that can speak POST /api/feedback (api.routes).
