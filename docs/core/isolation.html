core / isolation.py — running the agent against a detached copy of itself

One recipe for "run this, for real, but where nothing it does can reach the operator's world": a detached context, a throwaway workspace, a fresh sandbox with no network. Extracted 2026-08-22 from self-play, which is where it grew — one production incident at a time.

Why it is a module

The recipe used to live inline in Dreamer.synthetic_self_play: three method-local façade classes and about ten = None assignments scattered through 150 lines. That was fine while self-play was its only user. It stopped being fine when two more arrived — the Imagine speculative fork and the Dream replay engine — because a recipe kept in three copies drifts, and the copies that drift are the ones nobody is looking at.

It was also effectively unpinned. The tests that guarded it asserted that certain strings appeared in the method's source. A source-window assertion passes just as happily when the class it names has been gutted; every one of those pins is now an executed test in tests/test_isolation_replay.py.

The two tiers

A copy.copy(context) shares every handle on the live context. The inventory below is what an isolated run drops, and every entry is a leak somebody already shipped.

FloorISOLATION_NULLED_ATTRSself-play and replayproject scope, workspace model, profile, scheduler, journal, trajectory collector, episodic store, memory bus, and the secondary modules that carry their own llm_client (verifier, uncertainty, MCTS, hypothesis, frontier) plus the outer self-play loop handles

Self-play invents a challenge; a replay re-executes a recorded real episode, so its blast radius is the operator's world rather than a made-up one. That is the whole reason for the second tier — without it a replayed episode could page the operator on Slack or append to the agent's diary.

Isolation versus fidelity

Detaching is not free. A counterfactual replay exists to measure what the agent would have done, so anything gratuitously nulled changes the thing being measured. The rule drawn here: null what writes production state or reaches outward; keep what only reads or computes. prm_scorer, complexity_dispatcher and metacog are deliberately kept, and that decision is pinned so it cannot be reversed by accident.

Read-only memory façades

Deny-by-default whitelists over the vector, skill and graph stores, moved verbatim out of self-play. Anything not explicitly whitelisted raises AttributeError rather than falling through, so a store growing a new mutator cannot silently bypass the wrapper.

Two subtleties worth keeping in mind:

  • A read that bumps a counter is a write. search / search_advanced are forced to record_retrievals=False. Before that, every self-play hydration booked phantom retrieval credit on the production store — one episode reached a retrieval count of 690, stretching its ranking half-life about sevenfold, self-reinforcing.
  • last_playbook_triggers is off the whitelist on purpose. The sim read path stamps nothing, so a passthrough served the last real user turn's lesson set to a synthetic run. The sim-side attribution channel is hydrated_triggers.

These are the strict counterpart to memory/readonly.py, which the delegated sub-agent uses: that module intercepts writers by name and proxies everything else; this one raises on anything unlisted. Both doctrines are deliberate and neither replaces the other.

The façade is also what tells foresight that a run is a simulation — the prediction hook asks context.skill_memory.is_read_only, and a simulated prediction updates neither the ledger nor the precedent index.

Forked workspaces

fork_workspace(src) copies a workspace into a throwaway directory so a branch that was never chosen cannot mutate the real one. rsync when it is on PATH (fast, and it handles symlinks, sockets and fifos), shutil.copytree otherwise — the fallback is not an optimisation detail, it is what makes this work on a box without rsync.

It returns a ForkResult, not a bare path, and the field that matters is complete. A replay graded against a partial workspace produces a verdict about a world that never existed, so "the copy is not faithful" has to be something a grader can read — a log line is not a signal anything consumes. Three things set it false:

CauseWhy it happens
over the byte ceilingThe sandbox is where the agent builds things. FORK_MAX_BYTES (512 MB) refuses rather than stalling its caller on a downloaded checkpoint; the measuring walk stops as soon as the limit is passed, because a size check that itself walks 40 GB is not a guard.
rsync exit 23 / 24Routine, not exceptional: 23 is one unreadable file (the sandbox runs as root, so its files land in the bind mount root-owned), 24 is a file that vanished mid-copy. macOS 15+ ships openrsync, which returns 23 for a single permission error after copying everything else correctly. Treating these as failure threw away a 99%-complete copy and re-did the whole tree through the slower, unbounded fallback — so they now mean "usable but incomplete".
rsync timeoutRefused outright. Falling back after a 300 s timeout would mean a second, unbounded attempt at the same tree.

The prefix matters more than it looks. FORK_PREFIX starts with tmp because sandbox/docker.py classifies a container's mount as a throwaway per-solve workspace by exactly that test, and that classification is the only thing that reclaims a container whose run died to a SIGKILL — the one case a finally block cannot cover. The container sweeper reclaimed the container and nothing reclaimed the directory, so sweep_fork_workspaces() now runs beside it at boot, on the same 30-minute age floor.

Two containers, one name

A container's name is md5(workspace)[:8]. Distinct forks get distinct names, but two protections were missing once a replay could be provisioning its own sandbox while the live agent runs:

  • Reclaim only your own mount. The provision path force-removes whatever holds the name it wants. It now refuses when that container mounts a different workspace — a 32-bit collision is remote, but the blast radius is destroying the live sandbox mid-turn.
  • Owner labels. The orphan sweeper's only identity check was "not my container", so a fork container belonging to a run in flight in another process became a reap candidate the moment it passed the age floor — and per-solve candidates got no liveness check at all. Containers now carry ghost.owner_pid and a boot stamp; the sweeper spares one whose owner is still running. The boot stamp is what stops a recycled PID from reading as a live owner, which is the shape of the stale-lock incident this box has already seen once.

Tool containment

Detaching handles closes the durable-write paths that go through the context. It does not close the ones that go around it, and those are all tool-shaped. REPLAY_FORBIDDEN_TOOLS is the deny list, and it is a strict superset of both existing precedents — subagent.py's FORBIDDEN_TOOLS and the self-play list in dream.py — because it is applied to the workload with the largest blast radius. It also covers several that neither sibling denies: manage_composed_skills, notify_operator, jobs, deploy, rotate_secrets, knowledge_base.

It is a containment list, not a fidelity list. An episode whose recorded trajectory used one of these is not replayable and must be dropped at selection time — running it with the tool denied produces a verdict about a crippled agent, which is worse than no verdict.

Restriction needs three gates, and any one alone is bypassable: disabled_tools (the only lever that filters the schema the model is shown), a narrowed available_tools, and _subagent_allowed_tools on the context so a dispatch miss cannot heal the dict back to the full registry. IsolatedRun.build_agent() applies all three and fails closed; the third is set on the context by the context manager itself, so a caller that builds its own agent still gets the rebuild guard.

build_agent(extra_forbidden=…) denies more tools for one leg only — the tool_ablate perturbation — through the same three gates rather than a fourth mechanism, so an ablation can never be weaker than a denial. What it records is ablated_tools: the requested names that were dispatchable before the restriction and not already contained. Two distinctions are load-bearing there. Asking allowed_tools afterwards can only ever answer “yes, they are gone”, because the second pass removed them by construction — the question worth recording is whether they were there. And a name in TOOL_DEFINITIONS proves only that a tool is advertised; whether the leg could have called it is the dispatch dict. An ablation that removes only some of its targets, or an advertised name the agent could not dispatch, has taken away no capability — the caller marks that leg applied = False, because a perturbed arm that kept the capability is the control arm wearing a label.

Two escapes no deny list could have closed

  • memory_dir is repointed into the fork, not nulled. The acquired-skill manager is built at tool-table build time — before any tool is dispatched — from context.memory_dir; it creates directories and writes a registry on construction, and after three failed calls it moves the operator's live skill file into acquired_skills/retired/. Nothing downstream of dispatch reaches that. The fork-local directory is seeded with a copy of the acquired and composed skills, so the isolate keeps the shape of the real one without being able to write to it.
  • job_registry is detached, because execute — a tool a replay must keep — is handed the registry on every call, and a command that outruns its budget writes a row into it. Fifty slots, FIFO: a replay's rows evict the operator's real jobs from their own status surface. Job promotion is also turned off on the fork's sandbox, since a promoted job outlives its command but not the context that would tear its container down.

Network isolation is Docker's job

eval/network_guard.py is best-effort and blind to subprocesses and curl_cffi. The isolation that actually holds is the container's network mode, so isolated_replay_context asks for network="none" at container-create time.

It is passed explicitly, as a DockerSandbox(..., network=...) argument, not through GHOST_SANDBOX_NETWORK: that variable is process-global, and a live turn creating its own container while a replay was running would inherit the replay's isolation. The same override also drives binds_host_netns(), so the create path and the service-binding path cannot disagree about what network the sandbox is on. The Tor proxy is withheld from a networkless container for the same reason — in a namespace with only loopback the sandbox would spawn a Tor daemon that can never bootstrap.

It covers the container, and only the container. Everything the agent's own process does — every LLM call, every search, every fetch — is a different boundary, and the tool deny list above is what closes that one. Conflating the two is the easy mistake here; IsolatedRun.network_isolated exists so a grader can tell whether a replay's failure was the perturbation under test or simply the absence of a network the original episode had.

Using it

async with isolated_replay_context(context, network="none",
                                  source_workspace=live_ws,
                                  label="dream-replay") as run:
    agent = run.build_agent()            # containment applied, or it raises
    await agent.handle_chat(body)        # run.workspace is the fork
    out, code = run.sandbox.execute("python3 check.py", 30)

On exit the sandbox is closed with remove=True and the workspace is deleted — including when construction itself fails. That is not a detail: ensure_running has five reachable raise sites, and at the point they fire a container exists and the docker client's sockets are open. With construction outside the try, an unattended nightly batch leaked a container, roughly eleven unix sockets and a temp tree per item, which is the [Errno 24] Too many open files failure with a scheduler behind it. Closing rather than removing the container directly is deliberate for the same reason: a sandbox that failed midway through provisioning has no .container attribute but does have a container, and close() looks it up by name.

Failure surfaces as IsolationUnavailable, distinct from an error inside a replay: the caller should skip the work, not record a verdict. A failed provision also arms a module-level backoff, because every isolated run builds a fresh DockerSandbox — docker's own provisioning backoff is an instance attribute and gives no protection across runs, so a nightly batch would re-pay the same failing multi-minute install on every item.
