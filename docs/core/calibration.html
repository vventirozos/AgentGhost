core / calibration.py — Calibration Spine

Closes the loop on confidence: pair each turn's composite confidence with the realized outcome, measure Brier / ECE, and re-fit τ + weights + λ to the data. Roadmap phase 2.5.

The problem it closes

The composite confidence was computed every turn but never checked against what actually happened. The threshold τ = 0.55 and the entropy/competence weights 0.5 / 0.5 were asserted constants — so "the agent is 80 % confident" had no demonstrated relationship to the turn succeeding 80 % of the time. The calibration spine turns that assertion into a measured, self-correcting loop.

The three jobs

  1. Measure. Every metacog turn produces a confidence reading paired with the realized outcome, appended to $GHOST_HOME/system/calibration/calibration.jsonl; from that we compute a rolling Brier score mean((C − outcome)²) and an Expected Calibration Error over a 10-bin reliability table.
    • Logprob-optional confidence. The composite is computed at turn finalization for every full-loop metacog turn — not gated behind the streaming is_final_generation+stream_response branch (which many turns never enter) nor behind a populated token-entropy window. The entropy term is used when the per-token window observed tokens and is neutral (0.5) otherwise, so on speculative-decoding / MTP / no-logprobs upstreams (where the per-token logprob stream is sparse or absent) competence + verbalised-uncertainty drive the score and a sample is still recorded. Verified live on the MTP llama-server: samples land with entropy_component=0.5, competence driving C.
    • Outcome signal. A turn is a negative (0.0) on a structural tool failure, a verifier REFUTED verdict (≥0.7), or a next-turn user-correction promotion (the strongest "confidently wrong" signal — recorded against the prior turn's stashed confidence); otherwise 1.0. Real negatives are what stop the fit from bailing single-class on free-form chat (which is otherwise almost all "clean").
  2. Self-tune. Once ≥ 40 samples (both outcome classes present) accumulate, an idle-time grid search re-fits the entropy/competence weights, the verbalised-uncertainty penalty λ, and the decision threshold τ to minimise Brier. The threshold is then chosen to maximise Youden's J on the "predict success when C ≥ τ" decision.
  3. Unify. The recorded sample carries the verbalised-uncertainty pressure alongside the objective entropy/competence components, so the formerly-disjoint "the agent said it was unsure" track and "the generation/domain was uncertain" track are fit together.

Design non-negotiables

  • Local-only, pure stdlib. math + json only — no numpy, no hosted scorer, no outbound traffic.
  • JSONL / JSON on disk. Append-only history, atomic param writes (.tmp + os.replace), schema-versioned (ghost.calibration.v1).
  • Fail-safe. A recording or fit failure is logged at debug and never breaks a turn; load_params returns None on any problem so a corrupt file degrades to the hardcoded defaults.
  • Bail-on-thin-data. Below 40 samples, or with only one outcome class present, fit returns None and writes no params — a confidently-miscalibrated threshold is worse than the neutral default (same posture as prm.trainer).

Observability

Refits emit metacog calib log lines (📐 icon) with the fitted threshold/weights/λ/Brier. tracker.stats() exposes {samples, brier, ece, fitted, threshold, w_entropy, lambda_uncertainty} for introspection.

Entropy de-degeneration (2026-07-27)

1179 of 1180 recorded samples carried entropy_component=0.5 — the finalize fallback hardcoded neutral entropy, and the only path observing real logprobs (the client-SSE stream) rarely runs: every sim/self-play/CLI turn takes the agent's INTERNAL upstream stream, which never requested logprobs. With 2 distinct entropy values, w_entropy was unfittable (the fit's own DEGENERATE flag). The logprobs opt-in is now hoisted to cover the internal stream — FINAL generations only: llama-server hard-rejects logprobs on tools+stream payloads (live 400 caught on the post-deploy probe), and tools are attached exactly on non-final turns, so tool turns keep neutral entropy by design. The final-generation stream observes chunks into an EntropyTracker (sparse MTP logprobs — ~1 chunk in 7 on the live upstream — are fine; the reading averages observed tokens) and stashes a req-id-tagged _entropy_norm_pending that _record_calibration_safe consumes in place of the old hardcoded 0.5.

Coverage is structurally sparse — root cause established by live probes: with --native-tools ON (default since 2026-07-17) the server withholds logprobs on every tool-attached turn, and most interactive answers land ON a tools-attached turn (the model answers directly rather than transitioning to a forced final generation). The lone real-entropy sample in the corpus is dated 2026-07-18 — the native-tools toggle window. Real entropy therefore flows only on forced final generations, truncation continuations and SSE final streams. Watch entropy_distinct_values; if still <3 by ~2026-08-10, retire w_entropy (already 0-weighted — no behavioral change either way). Tests: tests/test_calibration_entropy_wiring_2026_07_27.py. Superseded the same day — see the n_probs sidestep below: the tools-attached gap is closed, so the ~2026-08-10 check flips its expectation: coverage should CLIMB (entropy_observed_pos/neg in the learning-health report), and a flat 0 now means the probe broke again, not that the corpus can't produce entropy.

2026-07-27 (later) — n_probs sidestep: tool-attached generations observe entropy

The server constraint was re-read at the source (llama.cpp master server-common.cpp / server-task.cpp, matching the live b10090 build): the 400 guard fires only on the OAI logprobs flag, while the streamed chat formatter attaches OAI-shaped logprobs to a chunk's last delta whenever the slot sampled with n_probs > 0 — it never re-checks the request flag. The llama.cpp-native n_probs field rides the server's pass-through parameter copy straight to the sampler, so n_probs + tools + stream streams logprobs chunks. Verified against the live server: the chunks parse through extract_top_logprobs → EntropyTracker unchanged (probs/delta alignment is imperfect under tool parsing — irrelevant for entropy, which needs only the top-K distributions, not their text alignment).

  • entropy.request_logprobs(payload, top_k=5, native_nprobs_ok=…) owns the field selection: no tools → portable OAI logprobs/top_logprobs; tools attached → native n_probs. The OAI flag is NEVER set alongside tools — that 400 breaks the generation, not just entropy.
  • Self-healing: if a future upstream rejects n_probs, the stream-abort handlers on BOTH stream paths latch context._nprobs_rejected, so it costs one generation, not every one. Kill switch: GHOST_ENTROPY_TOOLS_NPROBS=0.
  • MTP sparsity is unchanged: probs arrive on target-sampled tokens only; the tracker reads over observed tokens.

2026-07-27 — the entropy signal was structurally unfittable

Measured live: 1200 of 1201 stored samples had entropy_component exactly 0.5 and the fitted w_entropy was 0.0 — the confidence composite had been running on competence alone.

Root cause (confirmed by instrumenting the running agent): llama-server rejects logprobs on tools + stream payloads (HTTP 400, re-confirmed against the live server), and the turn loop attaches tools on every non-final generation. The probe showed final=False tools_in_payload=True → request_logprobs=False for an ordinary turn, so the overwhelming majority of turns observed no token logprobs at all. Those turns recorded the neutral 0.5 stand-in as though it were a measurement. With zero variance in the entropy column, any w_e > 0 could only drag composites toward 0.5 — so the grid search was guaranteed to pick 0 forever. It was not a tuning problem; the data made the parameter unlearnable.

  • Readings and samples now carry entropy_observed, separating "the model was genuinely 50/50" from "no logprobs came back". Legacy records default to False, which is the truthful reading of what they were.
  • Missing-feature renormalisation. A sample with no observed entropy is scored on competence ALONE rather than blended with the stand-in — see _composite_for, which mirrors CompositeConfidence.score exactly so the fit optimises the same formula the agent evaluates. This is what lets a weight learned from the observed minority coexist with a logprob-less majority: an earlier version that fit on the subset and applied it to everything drove Brier from 0.075 to 0.219.
  • The weight only moves with evidence. Below _MIN_ENTROPY_SAMPLES observed samples of both outcome classes, w_entropy stays pinned at 0 and the reason is logged, rather than a weight being "fit" on fiction. FittedParams gained n_entropy_observed so the state is visible.
  • Logprobs are now requested whenever the payload carries no tools — the previous gate also required is_final_generation, which is strictly narrower than the server's real constraint and cost coverage for tool-free non-final generations.

Verified across four regimes: all-neutral → w_e=0 (no regression); observed+informative → w_e=1.0 (previously impossible); observed-but-noise → w_e=0 (declines to use noise); mixture → w_e=1.0 with Brier 0.093 instead of 0.219. Tests: tests/test_calibration_entropy_observed.py (15).

2026-07-27 (later 4) — probability recalibration, and the diagnosis it produced

The composite was measured against the only baseline that matters — always predicting the base rate:

PredictorBrier
Raw composite0.0656
Always predict the base rate (0.961)0.0374

As a probability, the confidence number was worse than a constant. The weight search decides how to COMBINE signals but cannot set their level, so a two-parameter Platt stage (p = sigmoid(a·composite + b)) now runs after the weight fit, with the raw and base-rate Briers persisted alongside it so the comparison can never be lost again.

On the live corpus the map is REJECTED — and that is the finding

An initial measurement suggested the composite had real ranking ability (AUC 0.679) and that recalibration would beat the baseline by 18%. That was an artefact: it was computed on the stored composite, which mixes two scoring regimes. Recomputed leak-free from the stored components, AUC is 0.473 — below chance. The optimiser therefore converges to a ≈ −0.08: a negative slope that would INVERT the agent's confidence ordering, and a near-flat one that would collapse every turn onto the base rate, leaving below_threshold permanently inert. Calibrating noise is not an improvement, so the guard refuses any fit with slope below 0.5 and logs why. The machinery engages the moment a predictive feature exists — pinned by a test using an informative-but-compressed corpus, where it is adopted and beats the base rate.

The rejection is now visible in every status surface (2026-07-29): FittedParams.map_status records what happened to the map — applied | rejected_inverted (slope ≤ 0) | rejected_step (slope > 50 backstop) | discarded_worse (calibrated Brier no better than raw) — persisted in calibration_params.json (legacy files load as applied) and threaded into the idle-refit metacog line (previously refit=ok in the very cycle whose map was REJECTED — now refit=map_rejected_inverted), the boot loaded=startup line (map=…), the activity-ledger record, and tracker.stats(). Tests: tests/test_log_audit_fixes_2026_07_29.py::TestCalibMapStatus.

Feature health: 0 of 3 inputs are alive

Recalibration cannot fix a score with nothing in it. Measuring each input for whether it varies AND separates the outcome classes:

FeatureDistinct valuesSeparation (success − failure)
entropy_component2+0.0002DEAD — upstream refuses logprobs on tools+stream
competence_component270−0.0008DEAD — varies plenty, predicts nothing
uncertainty_pressure10.0DEAD — the tracker logged 2 records in 20 days

This is now reported every run by learning-health telemetry (features: 0/3 live — NONE discriminate), so a dead input is visible immediately rather than inferred from a bad Brier months later. Note that "few distinct values" is NOT the death test — a two-valued feature that splits the classes cleanly is useful, whereas competence has 270 values and separates by −0.0008. Separation is what counts.

Consequence: the binding constraint on this subsystem is feature quality, not label supply and not calibration. Competence is a per-DOMAIN historical average, so it is nearly constant within a domain and cannot discriminate individual turns. A useful confidence score needs an input that varies per TURN.

Fitting notes

  • Newton/IRLS, not gradient descent. GD was still at a = 1.28 after 4000 steps and only reached its optimum near a = −0.08 after ~60000 — values on opposite sides of the safety guard, so an under-converged run would have adopted a map the converged fit rejects. The answer must not depend on the iteration budget. IRLS converges in under 20 iterations (0.04 s on 1208 samples).
  • Unweighted. Class-balancing was tried first, on the theory that 96% positives would drown the minority; but balancing optimises a reweighted distribution, so the probabilities describe a 50/50 world that does not exist and the unweighted Brier got worse. Imbalance is handled by the threshold search (Youden's J), which weights sensitivity and specificity equally regardless of prevalence.
  • The threshold is selected on the CALIBRATED scores, so it lives on the same scale below_threshold compares against.
  • domain is finally recorded on each sample — it was computed for the competence lookup and then dropped, so all 1208 stored samples carried domain="" and per-domain reliability was impossible.

2026-07-27 (later 7) — second review pass: six defects in the same day's work

All six were introduced the same session and all were invisible to a 142-green calibration suite, because each needs a corpus shape the tests never built. The theme is worth keeping: every one of these safety mechanisms was written from intuition rather than measurement, and every one was wrong in a way only a numeric probe reveals.

  • The "ridge" was not a regulariser. Added to the Hessian diagonal only, it is Levenberg damping — it changes the step size but not the fixed point. On linearly separable data the unpenalised optimum is at infinity, so the slope grew with the iteration budget (a = 51 → 207 → 233 at 5 → 50 → 200 iterations), directly falsifying the docstring's own guarantee. The L2 penalty now enters the GRADIENT too, making it a MAP estimate; verified budget-independent at a = 20.76.
  • And that diverged map was adopted. brier_cal <= brier_raw is computed in-sample on the very points the two-parameter map was fitted to, so it is nearly always true. Confidence collapsed to the step predicate competence < 0.5499 with a reported Brier of 0.0. A _MAX_SLOPE backstop now rejects it.
  • The slope floor was scale-blind and justified by a false claim. The comment said a flat map "would leave the gate inert"; measured, the below-threshold decision set is bit-identical before and after (412 vs 412), because Platt is strictly monotone for a > 0 and τ is refit on the same scale. Rejecting a = 0.296 threw away a real 0.069 Brier improvement and changed no decision. Only INVERSION (a <= 0) and DIVERGENCE (a > 50) are rejected now.
  • w_effort == 1.0 was silently dropped (the bound was exclusive while the grid reaches exactly 1.0), leaving the scorer on the previous fit's effort weight — evaluating a formula the fit never saw, under a Platt map fitted on different composites.
  • The map's intercept floored the composite. Applying Platt AFTER the outcome penalty made sigmoid(b) an absolute floor: with a fitted b = 0.27, even outcome_penalty = 1.0 bottomed out at 0.566, so below_threshold was unreachable for every possible input — while the comment directly above promised a REFUTED verdict "must pull the reading below threshold regardless". The penalty now applies after the map, on the probability scale, and reaches 0.
  • The stored composite column mixed scales (raw before a fit, mapped after, re-scaled at every refit), so the reliability table, ECE and reported Brier compared different populations — the same turn binned [0.2,0.3) pre-fit and [0.6,0.7) post-fit. ConfidenceReading now carries raw_pre_penalty_composite and both record sites persist that, giving the column one stable meaning. _best_threshold's degenerate fallbacks likewise returned raw-scale constants into a mapped caller; they now return the median of the supplied scores, which is scale-free.

None of these were ACTIVE in production — the map is currently rejected on live data, so they were latent — but they would have activated the moment the turn-effort feature earns its weight, which is exactly when nobody would have been watching. Tests: tests/test_calibration_review_fixes.py (19).

2026-07-27 (later 9) — graded outcome labels and sample provenance

The binary label — 0.0 if (exec failure | verifier REFUTED | budget exhausted) else 1.0 — had two defects. It was 96.1% one class, and it asked "did anything visibly break" rather than "was the answer good": a turn that hit one tool error, RECOVERED, and answered correctly scored 0.0, identical to a refuted answer. That is a mislabel, not a strict label.

Provenance first

Every sample now carries source — turn for the graded proxy, user_correction for ground truth. This landed BEFORE any new signal tier on purpose: without it, mixing tiers is irreversible, because you can never audit which tier is noisy nor drop one without discarding the whole corpus. Legacy rows default to turn, which is what they were.

Grading, with measured constants

grade_turn_outcome() maps a finished turn onto [0, 1]. The numbers are measured rather than chosen: across 302 verdict-bearing trajectories the agent passed 251, so an unverified-but-clean turn scores 0.83 — the observed P(good | checkable) — instead of asserting 1.0. Claiming certainty for a turn nothing checked is precisely the verification theatre this project keeps rediscovering. Verifier PASSED/FAILED remain the hard 1.0/0.0 anchors; execution failures subtract 0.15 each down to a 0.15 floor (0.0 is reserved for "checked and WRONG"); budget exhaustion scores 0.2, since the agent itself flags that reply PARTIAL.

Two supporting changes were required, and either one missing would have silently defeated the feature:

  • Binarisation removed from BOTH the write and read paths. 1.0 if outcome >= 0.5 else 0.0 would have crushed every graded label straight back to two values — re-creating the exact constant column the grading exists to remove.
  • Class-presence gates generalised to VARIANCE in fit() and _fit_platt. "Are both binary classes present?" is the wrong question once labels are continuous: a graded corpus can carry real signal with every sample above 0.5, and the old gate would have refused to fit it at all. For 0/1 labels the tests are identical (variance is zero exactly when one class is missing), so binary corpora behave as before.

Measured — and it contradicted the hypothesis

Replaying the real production mix (1028 turns, 726 of them unverified) through the real feature and the real fit:

LabelDistinct valuesVarianceBrier vs base rate
Binary20.09860.0666 vs 0.0986 — beats by 33%
Graded80.04460.0395 vs 0.0446 — beats by 11%

Grading gives a far richer target but a smaller edge over the baseline. The reason is that the binary label is partly CIRCULAR with the turn-effort feature: effort counts tool calls and repeats, tool errors drive both the effort signal and the binary label, so the model was partly predicting itself. Grading weakens that near-tautology, which lowers the apparent win — the 33% was flattering and 11% is the honest number. It shipped anyway, because a correct label with a smaller flattering metric is worth more than an incorrect one with a bigger one.

Standing caveat: the graded label is a PROXY for process health, not correctness. If the ground-truth tier (user corrections) ever stops flowing, the agent is calibrating purely against its own notion of a tidy turn — which is what it already over-indexes on. Provenance is what keeps that checkable.

2026-07-27 (later 10) — Tier 2 redesigned from evidence: failure reports

The plan was to loosen this classifier's phrase-plus-rephrase requirement to phrase-only. Measurement killed that design. Across 246 eligible triples in the stored session history the classifier fires on zero — while 20 of them (8.1%) unmistakably report that the delivered work is broken:

"game.js:45 Failed to load frame definitions: TypeError: …"
"Failed to load resource: the server responded with a status of 404"
"it still does the same. the game never starts"

There is no phrase to loosen. A pasted traceback contains no rebuttal and shares no tokens with "build me a game", so neither signal can fire. The classifier is not malfunctioning — it is structurally blind to how corrections actually arrive, which is roughly one turn in twelve of GROUND TRUTH.

The same measurement killed a second idea from that plan: "repeat request = implicit negative". Eleven near-identical re-asks exist and they are dominated by a daily-briefing habit ("hello ghost, what's new today?"). Labelling those negative would have fabricated failures.

classify_failure_report()

Single-signal by design — a pasted traceback is unambiguous in a way a bare "no" is not.

  • Diagnostic: tracebacks, exception classes, HTTP 4xx/5xx, "Failed to load", "is not a function", file.js:NN. Bare error/errors is deliberately excluded — it false-positives on "zero console errors".
  • Breakage, split by strength. STRONG ("doesn't work", "still does the same", "won't start") versus WEAK ("fix it/that/this"), which is genuinely ambiguous: a complaint in "doesn't work, please fix it", but forward-looking instruction in "perfect, fix it exactly like that next time".
  • Praise veto, scoped to WEAK evidence only. This scoping is load-bearing. A first version vetoed on any affirmation and silently ate "the minesweeper right click doesn't work though, but the rest looks good" — a real defect report with a polite softener. Mixed messages are the COMMON shape, and an over-aggressive guard that discards real signal is the same class of bug as a tolerant parser that inverts a verdict. A softener does not cancel a named breakage; a hard diagnostic outranks any amount of politeness.

On the real corpus: 20/246 detected, 0 false positives, 0 vetoes needed — the veto guards only hypotheticals, which is what a guard should do.

Wired calibration-only, on purpose

Unlike an explicit correction this does not mark the trajectory FAILED, because that feeds reflection → lessons → the playbook, where a false positive poisons retrieval (this module's own docstring warns of exactly that). A calibration sample is numeric, provenance-tagged and filterable back out; a bad lesson is not. Recorded at source="failure_report", grade 0.15 — a notch above an explicit correction's 0.0, since the human is reliable that something is broken and slightly less so that THIS turn broke it. The fingerprint stash is consumed, so a report and a correction on one turn cannot double-count.

Two bugs surfaced only in live testing, both invisible to 9584 green tests: the tier sat behind a trajectory-cache lookup that returned first (disabling it on exactly the long tool-heavy turns most likely to draw a complaint), and a stash gate written for binary labels (>= 1.0) stopped matching once the graded label scored clean turns at 0.83 — neither change wrong alone, only in composition.

2026-08-01 — Tier 3: retroactive negatives from reopened work

A task a turn closed DONE being later REOPENED is a delayed negative on that turn — the closing was premature. Both halves of the signal already existed (the reopen transition and the closing turn itself); what was missing was the JOIN. Three pieces close it:

  • Closing stamp. ProjectStore.update_task stamps the closing turn's request id (request_id_context) into a new tasks.closed_req_id column on the transition to DONE (idempotent migration; "SYSTEM" — boot reaper, maintenance — stays blank, and a re-asserted DONE never steals the original close). Calibration samples symmetrically gained a req_id field, populated by the Tier-1 end-of-turn record — that pair is the join key.
  • Reopen hook. The TASK-level DONE → open transition (regardless of project status — a task revived on a still-ACTIVE project is just as much a delayed negative as one that fires project_reopened) logs a task_reopened event and fires ProjectStore.on_task_reopened(project_id, task_id, from_status, closed_req_id) — same outside-the-lock, fully-guarded discipline as on_project_done; wired in main.py.
  • Retro writer. CalibrationTracker.record_task_reopened_negative(closed_req_id) finds the closing turn's source="turn" sample by req_id and re-records its own stored components — the feature side is byte-identical, only the label differs (the no-leakage rule) — at source="task_reopened", grade 0.15 (_TASK_REOPENED_GRADE, same strength as a failure report: attribution equally loose, a reopen can also mean scope growth). Idempotent per closing turn (a DONE→open→DONE→open cycle labels each distinct closing turn once), and skipped when the closing turn's own label was already negative — Tier 2's no-double-counting rule.

Measured supply is deliberately acknowledged as MARGINAL (~7 reopen events / 20 days at design time, §4E) — this tier exists because it costs one column and one hook, not because it moves the fit alone. The durable req_id join also removes Tier 3's dependence on the 32-entry in-memory fingerprint stash: a reopen can arrive days and several restarts after the close. Tests: tests/test_task_reopened_tier.py.
