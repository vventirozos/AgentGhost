core / autonomous_activity.py + utils/notify.py

The agent's "mouth" (2026-07-11): a structured ledger of autonomous outcomes + an all-phase "Background activity" digest + outbound push notifications. Closes the biggest open loop of the 2026-07 feature survey — the agent did real work while idle but had no way to tell anyone.

Why

Before this module, 12 of the 13 idle phases surfaced their outcomes only as pretty_log lines on the console; the post-mortem defect queue had no surfacing at all; and scheduled turns (cron jobs that fire a full handle_chat) discarded their final content — only pass/fail reached the workspace ledger. Only project autoadvance had a user-facing digest (core.project_digest), and even that was pull-only. Blocked needs-user project tasks accumulated silently until the operator happened to open a chat.

The ledger

ActivityLog — append-only JSONL at $GHOST_HOME/system/autonomous_activity.jsonl. One record per operator-relevant autonomous outcome: {ts, phase, summary, severity, meta}. Two severities:

  • info — digest-only (dream ran, PRM refit, …).
  • notify — digest plus immediate push + the external-consumer feed (needs-user project tasks, scheduled-turn conclusions).

Fail-safe by contract: record()/read_since() never raise into a caller — a broken ledger must never break a turn or an idle phase. read_since(offset) is byte-offset watermarked, only consumes complete lines (a partially-written tail is left for the next read), skips corrupt lines, and silently re-baselines on a stale offset.

Producers

  • Idle phases — GhostAgent._record_autonomous_activity is called at each phase's completion point in _biological_tick: dream, reflection, post-mortem (when defects were queued), skills_auto (when something graduated), PRM/router/calibration (on successful hot-swap), stale open questions, self-play.
  • Project advancer — _record_needs_user_activity pushes severity=notify records for autoadvance_needs_user / human_gate_triggered outcomes (all three sites). The digest renderer excludes the project phase (DIGEST_EXCLUDED_PHASES) because the project digest already renders those — the record exists purely for push.
  • Scheduled turns — main._run_proactive_task now captures handle_chat's returned content and sinks it via record_scheduled_result() (severity=notify — a cron job's whole point is "tell me what you found"). Failures are recorded too.
  • The model itself — the notify_operator tool (tools/notify_tool.py, added later on 2026-07-11) lets the agent DELIBERATELY push one short line (severity=notify, phase agent_message) when asked to "report back in Slack" / "notify me" or when long background work concludes. Rails: 500-char clamp, 12/hour rate limit, and an honesty contract — the confirmation names only the delivery channels that are actually live (push transport configured? has the Slack consumer ever polled?) instead of claiming "sent to Slack" blindly. Delegated sub-agents can NOT reach this tool (not in their allowlist — the main agent reports; a delegate paging the operator is spam surface). Tests: tests/test_notify_operator.py (14).
    Finish-line guard (2026-07-13, req 11fe11d8): the model can PLAN the notify call in its reasoning and then finalize without making it — the user's one explicit delivery requirement silently dropped (the verifier confirms such turns: the deliverable itself is fine). The turn loop now detects an explicit notify-me ask in the user text (_user_asked_for_notification — narrow by design; negations and questions about Slack don't arm it) and, when a turn is about to ship its final response with notify_operator never called, injects ONE steer toward the call (never against a force-finalising loop-breaker; one-shot per request). Tests: tests/test_notify_finish_guard.py.
    Bug hunt (2026-07-14): (a) the 12/hour rate limit consumed a slot in _rate_limited() BEFORE the record was written, so a failed write still burned budget — split into a check (_rate_limited) and a commit (_note_sent, called only after a successful write); (b) push egress classification (utils/notify.py url_needs_tor) diverged from the egress guard's LAN-suffix list — a .home/.arpa target was called "direct" here but BLOCKED at the socket under --mandatory-tor, silently dropping the push. Now both share the guard's constants; (c) the fire-and-forget send_soon task is retained (asyncio holds only a weak ref → possible GC-drop mid-push).

Consumers

  1. Next-turn digest — _finalize_and_return renders unseen records as a "Background activity while you were away:" header (after the project digest), watermarked at $GHOST_HOME/system/activity_digest.json; first run baselines silently. Each item is clamped to 140 chars so the whole block stays under the 1500-char bound _strip_leading_banners peels — a longer block would break the correction-fingerprint peel (the 2026-07-07 bug class). The banner-peel loop allows up to 5 stacked blocks now (correction + clarifying + project digest + activity digest + headroom).
    Notify-only since 2026-07-17 (operator decision). The banner renders severity="notify" records only (severities=(SEVERITY_NOTIFY,) at the call site): scheduled-task conclusions, deliberate notify_operator messages, failures. Routine info-severity maintenance (dream/REM, PRM / router / calibration retrains, self-play, skills graduation) had every post-idle reply opening with a wall of refit bullets the operator already saw on the live stream — it no longer auto-surfaces anywhere in chat. The watermark still advances over info records (seen-but-silent), and identical (phase, summary) repeats collapse into one (×N) line. The info records remain reachable on demand — see consumer 4.
  2. Outbound push — utils.notify.OutboundNotifier, wired as the ledger's on_notify callback in main.py. Transports: --notify-webhook (JSON POST) and/or --notify-ntfy (ntfy text POST), env fallbacks GHOST_NOTIFY_WEBHOOK/GHOST_NOTIFY_NTFY. Egress posture: loopback/RFC1918/Tailscale-CGNAT/LAN-suffix targets connect directly (the egress guard allows them); PUBLIC targets are only reached through the Tor SOCKS proxy (upgraded to socks5h:// so DNS resolves inside Tor); with mandatory-tor and no proxy, a public target is skipped outright. Best-effort: one retry per transport, failures logged and swallowed — the durable record is already in the ledger.
  3. External deliverers — GET /api/notifications/pending?consumer=NAME returns undelivered notify-severity records + a watermark; POST /api/notifications/ack advances the per-consumer watermark (stored in $GHOST_HOME/system/notify_consumers.json). A consumer that never acked is baselined to end-of-ledger (no historical replay). The Slack bot (interface/externals/slack_bot) runs a notification_poller when GHOST_NOTIFY_SLACK_CHANNEL is set — poll → chat_postMessage → ack, so a crash re-serves rather than drops.
    Wedge fixed 2026-07-13 (both halves). The pipeline was silently dead 2026-07-11→13: (a) server — read_since's limit bounds scanned lines, so a poll window full of info-severity records (dream/self-play spam) returned [] without ever reaching the notify records beyond it; pending now scans forward in 200-line chunks (≤50/poll) until it has limit notify records or EOF, and limit is a soft bound — whole chunks are kept, since truncating mid-chunk would advance the watermark past records never returned; (b) bot — the poller only acked non-empty responses, so the empty-but-advanced watermark was never persisted and every poll re-scanned the same window forever. The bot now acks every response that carries a watermark (still after delivery, so at-least-once holds) and logs delivered N notification(s) so a silent pipeline is diagnosable. Backlog proof at fix time: 4 stranded records (2 days) arrived in one DM.
    Ack clamp (2026-07-14 bug hunt). The wedge above had a twin on the CLIENT side: /ack stored the posted watermark verbatim, so a value past EOF (client bug, or a stale large value replayed after a ledger truncation) permanently wedged the consumer — every /pending then returned nothing and re-echoed the huge watermark, so no future record was ever served. Ack now clamps to [0, current_offset()].
  4. On-demand report (2026-07-17) — introspect action='activity' (tools/introspect.py → render_activity_report): the model-facing answer to "what did you do while I was away?" now that maintenance is silent in the banner. ALL severities, newest first, timestamped ages, (×N)-collapsed; hours window (default 24, cap 336) and limit (default 30, cap 100). Reads the whole ledger from byte 0 (≈100KB/week — cheaper than a second watermark) and does NOT consume the banner watermark: it is a read, not an ack. Branches BEFORE the tool's self_model gate, so it works with selfhood disabled; the registry passes context through for get_activity_log.

Internal-request gate

Turns the agent fires at itself (req_id prefixes sched-, job-, sub-; see INTERNAL_REQUEST_PREFIXES) skip BOTH digest blocks — an internal turn consuming the watermark would silently eat the operator's next "while you were away" report. This also fixed a latent bug where a cron turn consumed the project digest watermark.

Tests

tests/test_autonomous_activity.py — ledger roundtrip / offsets / corruption / partial-tail, watermark + consumer semantics, digest rendering incl. the banner-strip contract, the notify-only severity gate + ×N dedupe + on-demand report (2026-07-17; introspect action='activity' coverage lives in tests/test_selfhood_introspect_tool.py), scheduled-turn capture, notifier egress routing + MockTransport delivery, the /api/notifications endpoints, and source-inspection wiring checks for main.py / agent.py / project_advancer.py / the Slack poller.

Promised-notification backstop at finalize (2026-08-01, req 50855398)

When the user explicitly asked to be notified ("notify me in slack when you're done") and the turn ends WITHOUT a notify_operator call, core/agent.py's _notify_promise_backstop writes the notify-severity record directly at finalize — model not involved. The in-loop finish-line guard (2026-07-13) steers the model once but deliberately stands down on force-finalising ends (strike cap, think-loop halt) — which is exactly when the promise matters most: the incident request died at strike 6/6 after 1789s, the notification never fired, and the verifier late-refuted the turn for that alone. The backstop fires on any non-internal end (aborted OR steer-ignored), labels the outcome honestly ("Task stopped early after repeated failures — …" vs "Done — …"), stamps req_id so the same turn's digest doesn't echo it, and respects notify_operator's 12/hour budget. Review-pass hardenings (same day): the failure label keys on the strike count, never force_stop (terminal-tool successes set it — "stopped after failures — Dream cycle complete" was the bug shape); simulation turns (skill_memory.is_read_only) never page the operator; an ERRORED notify_operator call does not count as promise-kept; and the STREAMED final path (the web UI always streams) carries its own twin wiring next to the streamed trajectory/work_log block. Tests: tests/test_req50855398_fixes.py.

Notify promise persists on the PROJECT (2026-08-01, req 5299219b)

"proceed with all tasks, notify me in slack when you're done" died 3.9s in when a restart landed mid-turn. The ask lived only in that request's text: the follow-up "resume … proceed" requests completed the project and no ping fired — the per-request detector and the finalize backstop only read the CURRENT message. An explicit notify ask is a delivery requirement on the work, not the message: core/notify_promise.py now persists it in the project's metadata (notify_on_done) at REQUEST START — before the first LLM call, so an early death can't lose it — exactly the pattern stored constraints already use. It fires when the project reaches DONE/FAILED, from whichever path gets it there: both finalize twins (with model-notified dedupe — a successful notify_operator call or a fired per-request backstop consumes the flag silently) and main.py's on_project_done hook for idle-loop completions (which stands down while a foreground request is active). The flag is consumed with an ATOMIC metadata pop (BEGIN IMMEDIATE read-modify-write), so a hook/finalize race delivers exactly once; a rate-limited attempt LEAVES the flag for a later one. Records use the project phase: Slack/push delivery via the consumer feed, no double-render in the chat banner (project digest covers that surface).

Review-pass hardenings (same day): the settle fire runs for INTERNAL turns too (a cron or sub-agent turn that completes the project keeps the user's promise — only capture is internal-gated, so a delegated prompt echoing "notify me…" can't store a promise nobody made); an ACTIVE stored promise suppresses the per-request backstop (its "Done —" would be premature mid-project and guarantee a double ping at settle time); the streamed twin fires against the drain-snapshot project id, never the live pointer a concurrent turn can re-point; and a failed ledger write RESTORES the consumed flag for a later retry. Known residual: a project rolled to FAILED by the idle loop delivers on the next foreground turn touching it (the store's done-hook fires only on DONE by design). Tests: tests/test_notify_promise.py (13, incl. the request-52 replay).

No-op consumer acks skip the write (2026-08-01)

save_consumer_offset returns early when the stored watermark already equals the new value. Idle pollers (slack, web-ui) re-ack an unchanged watermark every ~30s; each ack rewrote notify_consumers.json — pointless fsync churn around the clock, and it kept the file's mtime permanently fresh, which destroyed the documented wedge diagnostic ("stale notify_consumers.json mtime = wedged consumer", 2026-07-13 postmortem). The Slack bot additionally skips the ack HTTP call itself when the watermark hasn't moved (see the bot page); this store-level guard covers every other consumer. Tests: tests/test_autonomous_activity.py::test_save_consumer_offset_skips_noop_writes.

The idle-attempt heartbeat — idle_attempts.json (2026-08-30, §4DY)

The ledger on this page records outcomes: a phase writes a row when it did something. That is the right contract for the digest, and it leaves one question unanswerable — did this loop run? A loop that ran and correctly declined looks exactly like one that never ran.

Measured 2026-08-30: the learning-health view printed ✗ DEAD router_train 0/24h 0/7d while the loop had run thirty minutes earlier and logged “the labelled corpus is 89% the same as the last look … not re-running the same test on the same evidence”. Its last ledger row was its last real retrain — exactly what the ledger promises. “Produced nothing” was being rendered as “is dead”, and negative_controls — genuinely stale — sat in the same alarm list, which is how a column gets learned-ignored.

A second signal answers the other half. It lives beside the ledger at $GHOST_HOME/system/idle_attempts.json and is deliberately not more ledger rows: a skip per idle cycle would add ~30 rows/day to a file that never rotates, and would blur the outcome contract.

Outcome classes — only declined suppresses

ValueMeansSuppresses the DEAD alarm?
enteredthe phase started work; the outcome is unknownNo
declinedit ran and producing nothing was correct (skip-if-unchanged)Yes
failedit raisedNo

⚠ The first version stored a bare timestamp stamped at entry. A loop that crashes on every cycle was then byte-identical to one that declined, and the view asserted “a healthy outcome-free run” about a permanently broken loop — a false green, which this subsystem treats as worse than the false alarm it replaced. The stamp is written where the phase enters its work, so entered is exactly what a crash leaves behind.

File contract

{"router_train": {"ts": 1788068709.49, "result": "declined"}}

A bare float is the pre-outcome-class format written by the first generation. It cannot prove a run declined, so it is read as entered and never suppresses. Rows with a non-finite, boolean, or unparseable ts are dropped individually — one bad row must not discard the others.

Recency is bounded on BOTH sides

attempt_suppresses_alarm() requires -60s ≤ (now − ts) ≤ alarm_window. The lower bound is the point: a one-sided test let any future stamp — an NTP step back, a hand-edited file, a JSON Infinity literal — suppress the alarm forever. The 60 s of slack absorbs the fact that the consumer captures now and then reads the file.

Writing

record_attempt() holds a module lock, writes through a pid+uuid temp with write_text_nofollow, and os.replaces it in. A pid-only temp name collides between threads of one process (8×30 stamps recovered 0 of 240 and left the file unparseable) — the same §4BW shape sandbox/services.py and sandbox/jobs.py already fix. An unreadable file is refused, never overwritten: falling back to {} would destroy every other phase’s stamp.

What the operator sees

A suppressed row is stated, not silently dropped — a zero with the alarm withheld is indistinguishable from a zero nobody looked at:

    router_train    0 /24h    0 /7d   periodic
        └ RAN 0.5h ago and produced nothing — this loop records an
          OUTCOME, and declining is a healthy outcome-free run.

negative_controls was reclassified EXPECT_PERIODIC → EXPECT_ON_OUTPUT in the same change: it runs on a seven-day interval judged against a 24 h alarm window, so a healthy weekly loop alarmed six days in seven. Its real liveness signal is its own state file, which core/liveness.py::_negative_controls_probe already reads.
