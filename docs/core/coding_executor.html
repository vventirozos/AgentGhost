core / coding_executor.py

The real per-task coding executor for autonomous batches: build one leaf for real — write files, verify — instead of marking shallow work done.

Why

When advance_many runs a batch ("proceed with all remaining tasks"), each coding tick used to generate a SINGLE shell command. That produced theatrical completion: a leaf marked DONE having written nothing — observed live, where "create hello.txt" was classified as research, ran a web_search, and was reported complete with no file on disk. This module makes a coding tick actually build.

What it does

build_coding_task(context, description, *, tool_runner, ledger="") is bounded by design — the task tree already decomposes the work, so this just builds ONE leaf well:

  1. Spec — one LLM call returns a JSON object: files (each a path + FULL content), an optional verify shell command, a one-line summary, and a one-line ledger fact. The project's design ledger AND its current files (existing_files, gathered by project_advancer._gather_project_files) are fed in, with an instruction to EXTEND those files rather than recreate them — so a single-file app accretes across tasks instead of each task overwriting the last. The project's research briefs (research_context, gathered by project_advancer._gather_research_briefs) are fed in too, as a READ-ONLY PROJECT RESEARCH reference block (2026-06-22) — so the build follows the design decisions the agent researched instead of ignoring its own work; these are explicitly framed as "NOT files to edit" and kept out of existing_files.
  2. Write — each file via the file_system tool (operation="write"), capped at MAX_FILES (16) / MAX_CONTENT_CHARS (400k) per file.
  3. Verify — runs the verify command via execute; a failure (per project_advancer._looks_like_failure) fails the build.
  4. Returns a CodingResult (ok, summary, files, ledger_note, detail).

Don't clobber prior work (2026-06-20)

A later failure: on a single-file app each task REGENERATED the whole file with write and OVERWROTE the previous task — three tasks "completed" left a 2.7KB shell with neither the File Explorer nor the Snake game, and frontend tasks (no shell verify) had no gate to catch it. Three defences:

  • Non-regression guard — a full-content rewrite of an existing file is REFUSED if the new content is materially smaller (<85%) or drops the file's existing structural identifiers (HTML ids, function/class names, CSS selectors). It must be a SUPERSET.
  • Edit, don't clobber — a file entry may carry edits ([{"find":…,"replace":…}], {"after":…}, or {"before":"",…}) applied via file_system operation="replace", so a feature is ADDED to an existing file without re-sending it. A non-matching edit fails the task.
  • Append (the easy incremental primitive, 2026-06-20) — a file entry may carry "append":""; the executor writes old + new. It's a strict superset (can never regress), and the model emits ONLY the new snippet. This was added because re-emitting a whole ~8KB file choked the small model on task 2 of a live single-file build — it returned an EMPTY spec twice and the task failed. With append/edits the model only produces the delta. Existing files are now shown to the model as compact head+tail EXCERPTS (not full content), and the prompt steers hard toward append/edits over full content.

No per-task render (correction). An earlier version headless-rendered each HTML task and failed it on an uncaught JS exception. That was wrong for incremental builds: no intermediate task produces a complete working page — the shell exists before the apps, an app before the next — so rendering each tick failed legitimate in-progress work. Observed live: the Core-shell task built real files (a 799B index.html + script.js + 7.7KB style.css), then a render of the app-less shell "crashed" on a not-yet-defined reference, the retry returned an empty spec, and a good task was marked FAILED. The render gate was removed; the non-regression guard is the real protection, and a shell verify still hard-gates runnable code. Whole-app rendering belongs to a final verification task, not to every tick.

Retry with feedback. A refused write or a failed verify is regenerated ONCE with the exact failure reason fed back, then the task fails. Single-file projects (detected from the goal in advance_once) pass single_file=True to strengthen the "grow the one file" steer.

Recover the spec from the reasoning channel (2026-06-22)

A live failure mode killed 5 coding leaves in one project: every attempt logged coding_executor: no file spec parsed (len=0) with an EMPTY raw window, and advance_once marked the task FAILED with "model produced no file spec for the task". The cause was not the model — it was _generate_build_spec reading only message.content. Reasoning models (Qwen via llama.cpp) emit their chain-of-thought in a separate reasoning_content field; when the think block consumes the whole max_tokens budget without closing, the parser routes EVERYTHING — including the JSON build spec — into reasoning_content and leaves content empty. The executor saw "" and gave up.

The fix mirrors the established pattern in agent.py (~L2973) and project_research.py: when content yields no usable spec, fall back to reasoning_content (then to the two channels concatenated, for a spec split across the </think> boundary). A genuinely empty response (upstream contention) still fails — but only after the fallback was tried, and the diagnostic now logs BOTH channel lengths (content=N reasoning=M) instead of a misleading empty window. Covered by test_build_recovers_spec_from_reasoning_content and siblings in tests/test_coding_executor.py.

Think-ate-the-budget: one no-think retry (2026-07-06)

The reasoning-channel fallback above only helps when the JSON spec actually made it into reasoning_content. The worse shape (observed live 2026-07-06, twice in one project: content=0 reasoning=40–62k chars) is the model spending the ENTIRE 16384-token budget on think-prose and never starting the JSON at all — each occurrence a ~5-minute generation lost, logged as extract_json_from_text: malformed JSON-like content followed by no file spec parsed. _generate_build_spec now detects exactly this signature (no usable spec AND empty content AND non-empty reasoning) and retries ONCE with thinking disabled, using the established no-think recipe from project_research._llm_call/dream.py: the /no_think soft-switch, the chat_template_kwargs {"enable_thinking": false} hard-switch, and a system nudge. Attempt 1 keeps thinking ON (design depth is worth it when it works); prose-in-content failures do NOT trigger the retry (that's the normal feedback loop's job). Covered by test_think_only_response_retries_once_without_thinking and test_prose_content_does_not_trigger_nothink_retry.

Already-built leaf: empty files + a verify (2026-06-22)

When a task's deliverable was already written by a prior interactive turn, the autoadvance tick re-picks the task and the model — correctly — returns a spec with "files": [] and a "verify" command ("nothing to write; just check it runs"). The executor used to reject empty files as "model produced no file spec" and FAIL the task (observed live: the Model Architecture task FAILED in autoadvance though model.py existed and ran). Now an empty file list with a verify RUNS the verify: it passes → the task succeeds (no files written); it fails → the task fails with the real verify error fed back to the retry, not the generic no-spec message. Empty files AND no verify still fails as before. Covered by test_empty_files_with_passing_verify_succeeds and siblings in tests/test_coding_executor.py.

Capacity caps raised off the small-model era (2026-06-22)

An audit for leftovers tuned to a weaker model surfaced several caps that were starving or fragmenting code from the current strong model:

  • MAX_ATTEMPTS 2 → 4 and MAX_FILES 8 → 16. A capable model often fixes a verify failure on attempt 3-4; the hard stop at 2 turned a recoverable build into a batch-halting FAILURE. And a single "scaffold the app" leaf can legitimately emit a dozen+ files, which 8 silently dropped.
  • Append/edits steer rebalanced. The spec prompt previously pushed append as "STRONGLY PREFERRED" and told the model to "avoid edits" — biasing toward additive-only changes (you cannot append your way to a bug fix or refactor). It now picks by INTENT: adding → append; changing existing code → edits.
  • IIFE auto-wrap made conservative. _isolate_scripts wrapped EVERY appended inline <script> in an IIFE to prevent cross-block identifier collisions — but that SILENTLY scoped away intentional globals, breaking <button onclick="startGame()"> wired to a top-level function startGame() with no error the model could see. Wrapping is now SKIPPED when the body exposes a global (window.x = …) or declares a name referenced by an inline on*= handler; self-contained blocks are still isolated. Covered by tests/test_coding_executor_accretion.py.
  • Spec max_tokens 8192 → 16384. This is the one call that emits a COMPLETE file as embedded JSON content; at 8192 (~24-32 KB) it was 12× below the 400 KB a file may be, and a reasoning model spends part of the budget in reasoning_content before the JSON starts — so a new full file + think preamble could truncate into invalid JSON.
  • Existing-file excerpt 800/400 → 2000/1000, block cap 12 KB → 40 KB. An 800/400 head+tail of a grown index.html hid the middle, where an edits find/replace anchor often lives, so the model guessed an anchor that byte-failed. With a 65 K-token context the prompt budget easily affords real structural visibility.
  • Oversized full content now FAILS, not silently sliced. A file over MAX_CONTENT_CHARS used to be content[:cap] — a hard cut mid-code that wrote broken output. It now returns a "split across multiple files" failure, mirroring the append path's "never truncate" stance. Covered by test_oversized_content_fails_loudly_not_silently_truncated.
  • Single-command fallback max_tokens 1024 → 4096 (project_advancer.default_code_generator) — that command "may invoke python3 -c", so it can carry a whole inline program that 1024 tokens truncated mid-script.

Empty upstream responses ≠ "no file spec" (2026-06-22)

A fully empty completion (content=0 reasoning=0) is upstream contention/overload, not the model failing to produce a spec — feedback retries can't fix it. Previously each empty response consumed a full feedback-retry, so a 2-task autoadvance hammered the server with 8 instant empty calls and then mislabeled the tasks "model produced no file spec", dumping the agent into a long manual repair. Now _generate_build_spec returns (spec, was_empty); on an empty response the executor backs off (_EMPTY_BACKOFF_S) and retries, capped at MAX_EMPTY_RETRIES (2) separately from the normal MAX_ATTEMPTS, then fails with an honest "LLM returned empty responses (Nx) — likely upstream contention, not a code problem; retry later". Covered by test_empty_response_fails_with_honest_contention_message and test_empty_then_valid_recovers_after_backoff.

Fail loud, not shallow

If the spec is empty, a write is refused/rejected, or verify fails, the build returns ok=False. advance_once._finalize_coding then marks the task FAILED, which stops the batch loop so the user can take the hard task themselves — the opposite of silently marking it done. On success it registers the produced files as deliverable artifacts (so cleanup keeps them) and appends the ledger note. Covered by tests/test_coding_executor_accretion.py.

Wiring

Passed as coding_executor=build_coding_task into advance_once / advance_many from both the manage_projects autoadvance tool path and the idle autoadvancer (agent.py phase 2.95). It is NOT an open-ended agent loop — one spec call, N writes, one verify — so per-tick context stays bounded however many tasks the batch runs.

Background lane (2026-06-22). build_coding_task takes is_background, threaded into the spec-generation chat_completion. The IDLE autoadvancer sets it True (along with its classifier + code-generator calls) so its ~8K-token spec call goes through the client's background lane — waiting for foreground to clear and capped concurrency — and a user who starts typing mid-build isn't stuck behind it. The user-initiated manage_projects autoadvance tool leaves it False (foreground): the user is actively waiting on that batch. Covered by test_spec_call_is_foreground_by_default / test_spec_call_uses_background_when_requested.

Tests

tests/test_coding_executor.py — happy path (write + verify), verify-failure, write-rejection, empty spec, no-verify, markdown-fenced JSON, unavailable executor, and the advance_once integration (DONE + artifacts + ledger on success, FAILED on a broken build), plus the classification fix that routes file/build leaves here.

Post-build gates (2026-07-08)

Two gates run after the spec's own verify succeeds, both feeding the build-retry loop on failure (chess-session post-mortem: a build passed every mechanical check while violating the user's core constraint and shipping three crash-on-first-touch bugs):

  • Smoke gate (core/build_gates.smoke_gate): py_compile every written .py; when a Flask app is detected, sweep its routes with test_client (no server process): parameterless GET routes must not 5xx, POST routes get an empty JSON body and may 4xx but must not 5xx. The generated script self-bounds with SIGALRM(45s) so an import that starts a blocking server can't wedge the sandbox exec.
  • Constraint gate (core/build_gates.constraint_gate): one background LLM audit of the files the task produced (files_from_specs) against the project's stored constraints — judgement-based, unlike the evidence-based DONE-gate in tools/projects.py. A confirmed violation becomes retry feedback quoting the constraint + evidence. The same gate guards the interactive manage_projects task_update→DONE path (refusal with an explicit CONSTRAINT-OVERRIDE: escape hatch for user-approved exceptions).

Both gates fail open on infrastructure errors — a broken gate must never block builds. Covered by tests/test_build_gates.py (including an end-to-end run of the real smoke script against a Flask app with a 500-ing route) and tests/test_probe_before_hypothesis.py (wiring pins).

Write-time syntax signal consumed (2026-07-14)

file_system's write/replace paths append ⚠ SYNTAX CHECK FAILED: … (ast/node-backed, HTML <script> blocks included) to an otherwise-successful result when the file left on disk does not parse. The interactive loop reads that warning in-context — but this executor discarded it: _looks_like_write_error only inspects the result's head. Observed live (first build after the check came alive in production): a 6-task autoadvance batch rewrote index.html five times, every write was flagged with the same Identifier 'WebOS' has already been declared, every task still closed DONE, and the broken build was only caught when the final turn browsed the page.

_syntax_fail_reason(path, out) now extracts the diagnostic and all three apply paths (append, full-content write, edits — the last edit's result reflects the final on-disk state) surface it as an apply failure: the file stays on disk (file_system semantics unchanged), but the build's retry-with-feedback loop gets the exact line to fix and steers the retry toward edits. On exhausted attempts the task fails honestly via _finalize_coding — stopping the batch — instead of piling more features onto a file that doesn't parse. Fails open when the checker produced no warning (unknown extension, node absent). Covered by tests/test_autoadvance_syntax_gate.py.

Anchored success/error classifiers (bug-hunt 2026-07-26b)

_op_ok was "success" in out[:200] — a SUBSTRING test. The file_system no-match message embeds the filename (… NOT found in 'payment_success.html'), so a FAILED replace on any *success*-named file (common in web deliverables) had "success" land in the window and counted the un-applied edit as applied — closing the coding leaf DONE with the file unchanged. Now anchored on the SUCCESS head (head.startswith("success")), matching the sibling _looks_like_write_error, whose own "security error" in head substring nit (misclassifying a successful write to a security error handler.py) was anchored to startswith in the same pass. Tests: ::TestOpOkAnchored.

Never corrupt a working Python file (2026-08-01, "Mini AI" incident)

Autoadvance re-picked a task whose deliverable an interactive turn had already built and verified (the ledger still said PENDING), and the spec appended a SECOND full implementation into the working core.py. Python appends have no isolation (unlike HTML's IIFE-wrapped scripts): the merged file hit a SyntaxError at line 379, three repair attempts failed against it, the task was marked FAILED and the project rolled up FAILED — all while a working file had existed on disk minutes earlier. Three defenses, all pre-write (the post-write syntax signal catches damage only after the working file is already gone):

  • _py_append_guard — an append to a parsing .py file is refused when it re-defines top-level def/class names already present (a duplicate implementation, not an extension), when it adds a second if __name__ == "__main__" block, or when the merged result would not ast.parse. A broken base keeps the old flow (mid-repair files need appends).
  • Overwrite guard — full-content replacement of a parsing .py file with content that does not parse is refused before the write; the working file survives on disk and the retry gets the exact diagnostic.
  • Verify-only path is first-class — the spec prompt (system rules + an ALREADY ON DISK steer rendered by _render_already_built when the task description names files that already exist) tells the model to return {"files": [], "verify": "…"} when the deliverable already works. _generate_build_spec's _usable now accepts a verify-only spec, so it can't be clobbered by the reasoning-channel fallback or steered into re-implementation by the retry loop; build_coding_task's existing no-files path honours the verify and closes the task without rebuilding. A verify-only spec whose verify is kill-shaped (pkill/fuser -k/…) is refused with feedback rather than skip-passed: with no files, the verify is the ONLY check, so the _run_verify "skip, the files may be good" rationale doesn't apply (review pass, same day).

Tests: tests/test_project_ledger_integrity_fixes.py (guards, disk-survival end-to-end, verify-only survival, ALREADY-ON-DISK steer).

Double-escaped spec content: bounded pre-write repair (2026-08-01, req 50855398)

The spec model sometimes emits a file as a one-line JSON-escaped string that survives extraction verbatim — every newline a literal \n pair. Writing it lands a broken file the retry loop demonstrably cannot fix (live: three attempts on data_generator.py, all still escaped, task FAILED). _apply_file's full-content path now runs _maybe_unescape_double_escaped: trigger only on the exact shape (.py, ≤2 real newlines, ≥5 literal \n, original does NOT parse), decode only the common escapes (\n \t \r \" \' \\ — not unicode_escape, which mangles UTF-8), and accept the repair ONLY when the result ast.parses — a tolerant repair must bound its OUTPUT, not just its trigger. On any miss the original is written and the (now shape-naming) syntax feedback drives the retry. Tests: tests/test_req50855398_fixes.py.

A failed replace now names the reason it actually failed 2026-08-11

Every non-SUCCESS replace was reported to the model as “anchor not found” — a diagnosis, not an observation, and often the wrong one. That string is prefixed with YOUR PREVIOUS ATTEMPT FAILED: into the next attempt's prompt, so a wrong label steers every retry at the wrong hypothesis. Live on one request: a syntax-regression rollback (REJECTED: that replace would introduce a syntax error … unexpected indent) was relabelled “anchor not found”, and the model spent 20 minutes and 14 attempts hunting for a better anchor while the defect was its replacement's indentation.

_replace_failure_kind() classifies the observed rejection: syntax rollback, ambiguous anchor, genuine anchor miss, marker leak, blocked write. An unrecognised shape returns a neutral phrase rather than the most likely guess — the caller appends the tool's raw text anyway, so saying less beats saying something false. Pinned in tests/test_audit_4at_round3_fixes.py.

Two ways a task closed DONE claiming work that never happened 2026-08-11

Dropped edits. edits apply only when the path is in the prompt snapshot, and that snapshot is hard-capped at 12 files. An edits entry for an unsnapshotted file fell through to the content branch, found None, and returned “skipped, not a failure” — zero tool calls, no reason, nothing in written. A sibling entry that did apply then made the spec look successful. It now returns an explicit reason naming the file and the cap.

Edits beyond the snapshot are read, not refused (§4QA-d, 2026-10-19). That reason told the model to “name it in files so it is read first” — a read that did not exist, so every retry failed the same way (live: task 43c19f8b7511 edited tools/run_harness_on_outputs.py in a 30-file project and closed FAILED). An edits entry for a file outside the snapshot is now read from disk first and its edits applied. Edits are exact-match, so a guessed anchor writes nothing; the path goes to touched, so the next attempt's prompt shows the file. A missing file returns “does not exist … write it with content”; an unreadable one returns a reason. Never silence. The snapshot itself now keeps the files the task names (see project_advancer). Tests: tests/test_4qa_unsnapshotted_edits.py.

A full overwrite past the snapshot is guarded too (review r19). A content entry for a file outside the snapshot had no baseline, so the non-regression and Python-parse guards were skipped: a 6 KB module with 200 defs was replaced by 22 bytes. It is now read first. A missing file is a new file. A read that answers Error: … (too large, budget, permission) refuses the overwrite: “use edits”. So does a --- p SAMPLE ONLY reply: a large long-line file exists even when no full text comes back (r20). Any other reply is not a file_system read result and keeps the old no-baseline path. _read_live_file also treats file_system's sandbox-ROOT fallback (“NOTE: … serving the file at the sandbox ROOT”) as missing. That root file is not this project's: as a baseline it refused a new main.py as a shrink, and an append built on its content. A whole read of a big root file answers “Error: … too large” without that note, so an error reply is probed with a one-line ranged read (_is_root_fallback), which carries it (r21). edits to a project file too large to read (or SAMPLE ONLY) are applied without a copy, since exact-match edits need none. Before, they were refused with no way for a retry to succeed. The task-named-file pattern now also finds a name that ends a sentence (“… into recursive_harness.py.”) one written ./app/main.py (r24) and a dot-path such as .github/workflows/ci.yml. A ../lib/util.py name is outside the project, so it is not taken as lib/util.py (r25).

Rewrite judged against a prefix. _gather_project_files truncates silently, so a 300 KB index.html snapshotted at 4 KB made a 20 KB full rewrite look like growth (20000 > 4000×0.85) and the non-regression guard waved through the loss of 280 KB. For .py the truncated prefix usually fails ast.parse, which disables the overwrite guard entirely. Truncated entries now carry SNAPSHOT_TRUNCATED_MARK, and a marked baseline forces a live re-read — refusing if the re-read fails, because a refusal costs one retry and a wrong pass costs the file.

⚠ The marker has one definition, imported rather than copied — producer/consumer drift is the defect class this module already carries scars for. ⚠ The first pass marked only the budget-exhaustion branch; the per-file truncation fires first and far more often, and only a producer-side pin caught it (mutation-testing showed removing the marker reddened nothing).

Executor chosen by leaf shape 2026-09-08 · §4FL

The seam at the top of build_coding_task asks coding_loop.executor_kind(context, project_id, description=, existing_files=). Precedence: GHOST_CODING_EXECUTOR → the project's metadata.executor (either value) → the shape rule (leaf_shape: the leaf names an existing file, by path or basename as a whole word, whose content holds ≥ GHOST_LEAF_GROW_LINES = 80 lines; the largest named file decides) → spec. A routed leaf logs "routing leaf to the agentic loop — it extends app.py (279 lines …)". The leaf bench pins its control arm to metadata.executor = "spec" since the default would otherwise route its growing leaves to the loop. See coding_loop.

Think policy, kept rejections, append rollback, two pre-write guards 2026-09-03 · §4EI

Request 463111ad (an Elden Ring tracker, 7 leaves, autoadvance count=all) ran 49 minutes and closed 3 DONE / 3 FAILED with a page that was mostly unreachable. Every mechanism below is a fix for one thing that run did, and each has a pin in tests/test_coding_executor_think_policy_and_append_guards.py that fails on the old code.

Think policy. The coding model drafted the whole file inside its think block, so every leaf hit the 30K reasoning ceiling (removed since, §4SD) with zero content (6 of 6 thinking attempts, ~115 s each), and only the no-think retry ever produced a spec. Thinking still earns its cost on a model that plans in 3–15K, so the executor now adapts instead of switching: after GHOST_CODING_THINK_SKIP_AFTER (default 2) consecutive aborted think phases — an exact n-gram loop or the whole budget eaten with no content (the 30K ceiling was a third, until §4SD) — the spec call starts with thinking disabled (_spec_nothink_call: the same /no_think + enable_thinking=False recipe the retry used). One clean think phase resets the streak; a restart resets it too. The streak is kept per LLM client (weak-keyed), so the one production client adapts once per process while test doubles never see each other. §4FJ disarm path (2026-09-07). "A clean think phase resets" could never fire once the streak had tripped — no think phase ran any more — so the no-think regime was sticky until a restart, and the single-file leaf bench measured that regime at 2/6 DONE against 6/6 for think-with-fallback in the same process (§4FI). Now, after GHOST_CODING_THINK_PROBE_AFTER (default 3) no-think spec calls — or immediately after a verify failure on a spec that was built no-think — ONE spec call thinks again as a probe: a clean probe resets the streak (thinking is back), an aborted probe extends the no-think window by another PROBE_AFTER calls. 0 or negative disables probing (the pre-§4FJ sticky behaviour). The probe, the reset and the verify-triggered probe are logged at WARNING so they show in the operator stream. Pins: tests/test_4fj_think_probe_and_workspace.py (the window, a clean and an aborted probe, the knob, and the verify hook at its real call site in build_coding_task). 0 = never think on spec calls; a negative value = never adapt. The system hint also tells the model not to draft file contents in its thinking. A no-think first call that comes back reasoning-only is not retried with the same recipe.

Rejected output is kept. Four of the run's five no-think retries returned complete specs (server-side truncated = 0, tail "ledger":"…"}) that the parser rejected, and neither the 400-char log preview nor four live reproductions could say why. When no usable spec is parsed, the raw content and reasoning channels are now written verbatim to $GHOST_HOME/system/coding_executor_failures/ (newest UNPARSED_SPEC_KEEP = 30 files survive; nothing is written when GHOST_HOME is unset or the upstream reply was empty), and the warning names the file. Two related tightenings: _usable no longer accepts a files entry with no content/append/edits (the truncation repair salvages [{"path": …}] out of a broken spec, and accepting that skipped the retry and the dump), and _generate_build_spec honours its own contract by returning {} on every failure. In extract_json_from_text, a brace-unbalanced text that ends with } is now reported as UNBALANCED (a quote or escape inside a string desynced the scan) instead of "TRUNCATED … cut off at max_tokens" — the old message sent the reader to the token budget when the defect was inside a string.

Append rollback. A syntax-failed append used to stay on disk with feedback "fix it with edits"; the model answered with another append, the file grew 18K→22K, and the same line failed four times. An append is a pure addition, so the pre-append content is a complete known state: the executor now writes it back (_restore_file), marks the snapshot authoritative, and the feedback says the append was reverted and asks for the whole block again. If the restore write itself fails, the old taint→edits flow applies unchanged. New files and content rewrites keep the taint flow (there is no prior state to restore). Already-broken base: if the diagnostic's line number lies before the appended block's start line (_syntax_error_before_block / _appended_block_start_line: the </body> line for HTML, two past the last non-blank line otherwise), the file was broken before this append — no revert, and the feedback says "line N is in the EXISTING file". A line inside or after the block is the block's fault (an unterminated construct is reported at the next token, in the tail the append pushed down) and reverts. The helper reads the reason _syntax_fail_reason already produced, not the raw tool result.

Two pre-write guards (append and content). (1) Placeholder elision: a line that is only .../…, bare or in a //, /* */ or <!-- --> comment, in an HTML/JS/TS/CSS file is refused before the write, naming the line — the Talismans leaf shipped two such lines and failed its own syntax check on every retry. Python is exempt: ... is a valid statement there; an inline prose ellipsis (Loading...) is not a whole line and passes. (2) Duplicate routing key: an HTML append whose top-level element carries an id or data-* key the file already has (or that the fragment uses twice) is refused, because selectors and routers match the first element — two leaves appended a second <section data-section="bearings"> that the SPA could never show, and both closed DONE. Nested duplicates (a data-item inside a new section) are allowed, and the guard is HTML-only.

Spec structure repair (the rejection cause, proven by the kept files). The live proof's kept outputs showed why complete-looking no-think specs failed: not quote escaping but three structural slips at the files boundary — (i) …"},"path":…, the { opening the next entry dropped; (ii) a top-level key ("verify"…) emitted while the files array is still open, the ] dropped; (iii) the output simply ending with files and the top object open, ]} never emitted (finish reason stop). Braces balance in (i) and (ii), so the scan said "malformed" and every salvage failed. _repair_spec_structure re-parses, and at the parser's own error offset — only when the misplaced token is a known spec key and the string-aware container stack matches — inserts exactly the dropped character(s), then requires a strict json.loads to a dict; an unchanged text is never returned as a repair. It runs last in _parse_spec_channels, the one extraction chain the streamed call and the retry now share. Pinned on the six real files in tests/fixtures/spec_structure_4ei/ (one inserted character each for 1–4 and 6; two { plus ]} for 5). The sixth shape — the } closing the last file entry dropped before ] — came from a post-deploy sanity leaf on the thinking path, which the grammar below cannot cover; the repair is what keeps that path honest.

JSON grammar on the no-think call. The repair handles three known shapes; the grammar removes the class. _spec_nothink_call now sends llama-server's OpenAI-compatible response_format (the client posts the payload dict as-is, so no passthrough was needed): by default a json_schema named build_spec built from SPEC_JSON_SCHEMA, which is deliberately loose — it requires only the shape that failed (a files array of objects, each with a path) and allows extra keys and any edits item shape, so it cannot starve a legitimate spec. The server compiles it to GBNF and constrains every sampled token, so a dropped {/] and the ```json fence become impossible. Thinking calls never carry it (a think block is not JSON), and the main turn loop is untouched. GHOST_CODING_SPEC_JSON_GRAMMAR: unset/1 = schema, object = shape-free json_object, 0 = off. A backend that errors while the grammar is on gets exactly one retry without it, so the grammar can never fail a leaf by itself; with the grammar off a failing call is not retried. Proven against the live server through the executor's real prompt builder: 4 of 4 usable specs in 12–22 s, no repair needed, including three runs of the history task that had been rejected 5 of 5 times without it.
