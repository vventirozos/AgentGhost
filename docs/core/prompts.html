Native tool_call corruption root cause — the header split (2026-07-31)

Symptom: the "Repaired corrupt native tool_call(s): upstream merged a multi-tool reply into one call's arguments" repair guard fired 18 times in one 2.5 h log window — effectively on every reply that stacked two tool calls (browser+vision, read+read). The repaired first call sometimes carried leaked XML (</parameter> </function>…) as an argument value, producing garbage-path tool failures and spurious strikes.

Root cause (controlled ablation against the live upstream, llama.cpp b10180 + template froggeric-v21.3): a two-call demand is parsed cleanly with simple schemas, with the real registry schemas, streamed (proper per-call index deltas), and even with an attribute-dialect example planted in history — but corrupts 8/8 deterministically the moment the full QWEN_TOOL_PROMPT rides in the system slot, which the native path did (only the schemas were swapped for a pointer; every XML format rule stayed). Taught two dialects at once — the agent's <function name="…"> attribute style and the template's <function=…> equals style — the model emits a hybrid, and the server's incremental parser swallows everything after the first parameter into that argument value: one merged call, the exact repair-guard signature. Removing the XML block flips the same demand to 13/13 clean.

The repair guard is now a TRIPWIRE. With the root cause fixed (and a 6-probe battery including explicit parallel-call demands producing zero fires), a repair fire no longer means "the usual upstream flakiness" — it means a novel corruption shape, and the raw pre-repair snapshot is its only record. The log line says so explicitly, because for months this read as background noise and got scrolled past. The fire is also filed in the background-activity ledger under phase native_tool_repair (queryable via introspect action='activity') at INFO severity — durable and answerable after the fact, without interrupting the operator over a single repaired call.

Fix: the native branch splices QWEN_TOOL_PROMPT_NATIVE (no XML format instruction at all), the legacy branch keeps QWEN_TOOL_PROMPT (there the XML rules are the parser contract), and SYSTEM_PROMPT's CRITICAL INSTRUCTION became path-aware instead of unconditionally ordering "XML tags". The agent's XML parser and the repair guard remain as fallbacks for stragglers — the prompt just no longer teaches the dialect that broke. Covered by tests/test_native_tool_header.py; contract reversal recorded in tests/test_context_compaction.py::test_native_tools_drops_xml_format_scaffolding.

Project working memory — DESIGN LEDGER & DONE SO FAR (2026-06-20)

The dominant cost on long projects was a fresh turn re-deriving the project's shape — re-listing the sandbox, re-reading files — because the briefing only carried the task tree and the last few events, never what had been built or how it worked (observed live: one "proceed" turn spent ~96 s reconstructing state before doing any work). The briefing now carries two compact, durable layers so the next turn inherits that knowledge instead:

  • DESIGN LEDGER — durable facts the agent records (file layout, key function/API names, conventions) via manage_projects action=ledger ledger="…" or a ledger="…" on a DONE task_update. Stored in project metadata, bounded (ProjectStore.LEDGER_MAX_LINES/MAX_CHARS), dedup'd against an identical trailing line, and written WITHOUT logging an event (_write_metadata) so it doesn't spam RECENT EVENTS. The briefing surfaces the last _LEDGER_BRIEFING_LINES (20).
  • DONE SO FAR — the max_done_tasks most-recently-completed tasks plus the one-line result_summary the agent wrote on completion (the DONE-gate already forces a result). "What exists and where", auto-derived — no new agent behaviour required.

The ONE TASK rule now tells the agent to read these before re-reading files, and to record durable decisions in the ledger as it goes. Covered by tests/test_project_working_memory.py.

Project working memory II — RECENT WORK LOG & STUCK TASKS (2026-07-18)

The 2026-06-20 layers cover work done inside tasks. The 2026-07-17 overnight session exposed the complement: once the game project rolled to DONE, an entire evening of debugging (6 requests) plus the next morning's root-cause fix wrote nothing to the store — the model has no open task to task_update, so the voluntary write-back path never fires — and the 06:20 turn re-read every file and re-derived the bug from scratch. Two new briefing sections close the gap:

  • RECENT WORK LOG — the last max_work_logs (5) automatic per-request records written by the finalize chain (work_log events: request head · files touched · tool counts · verifier-aware outcome · head of the final answer). Deterministic — requires no model cooperation — and rendered for DONE projects too, which is precisely when it is the only record. Header tells the model to trust it before re-reading files.
  • STUCK TASKS — FAILED/BLOCKED tasks with their failure_reason (≤max_stuck_tasks, 4). Previously invisible: the OPEN filter excludes both statuses and DONE SO FAR only shows DONE, so "work pending because it failed" never reached the model at all.

Write side and defect-reopening live in core.agent / memory.projects. Covered by tests/test_project_work_log.py.

Project working memory III — DELIVERABLES, RETROSPECTIVE, DREAM DIGEST (2026-07-18)

Same session, the remaining write-only records gained read sides in the briefing:

  • DELIVERABLES — the deduped file manifest from kind='file' artifacts (ProjectStore.list_deliverables), ≤max_deliverables (12) paths comma-joined + "(+N more)", with a pointer to manage_projects action=artifact_list for per-task detail. Previously these were registered on every DONE task purely as the cleanup keep-set — the model re-listed the sandbox to learn what its own project had built.
  • RETROSPECTIVE — rendered only for terminal-status projects (DONE/FAILED/ARCHIVED): TaskTree.generate_retrospective()'s summary line, up to 3 what_failed entries with reasons, and the measured-effort total from the (now written) actual_cost column. Computed lazily from task rows — nothing persisted, always current. The generator previously had no caller at all.
  • LAST DREAM DIGEST — one line from the newest dream_digest event ("what did I do last night"), which was reachable only via a manual event_log call — i.e. never.

Covered by tests/test_project_readside_plumbing.py.

Project pacing — ONE TASK AT A TIME (2026-06-20)

The project briefing previously opened with a PARALLEL TASK EXECUTION — HARD RULE that told the agent to scan the whole task tree and stack every finishable task into one reply ("project-of-N tasks completes in ~2-3 turns"). On large projects that floods the context window, and it steamrolled any user instruction about how to advance. It is replaced by a ONE TASK AT A TIME rule:

  • Advance exactly the NEXT TASK, one per turn — never stack several tasks' work into a single reply.
  • After create / task_decompose, STOP and present the plan; do not begin executing.
  • Wait for an explicit user go-ahead ("proceed", "next task", "continue") and honor the pacing/ordering the user asks for.
  • Each go-ahead does one task, closes just that id with task_update … status=DONE (plus its deliverables), reports, and stops.

The create and task_decompose actions of manage_projects reinforce this by returning a stop-and-await agent_instruction. The idle autoadvancer (agent.py phase 2.95) already runs a single advance_once tick per cooldown, so autonomous advancement is one-task-at-a-time too. Covered by tests/test_project_pacing.py.

ONE TASK AT A TIME — now ENFORCED, not just prompted (2026-06-22)

The rule above was advisory text only — nothing in the interactive turn loop enforced it. Observed live: "start task 1" ran the model through 8 tasks in a single request. Two things defeated the prompt: (1) build_project_briefing is rebuilt and re-injected on every loop iteration, so the instant a task closed, the briefing re-advertised NEXT TASK: [the next one] — the model read that as its new assignment; (2) the turn only ends when the model volunteers a tool-free answer, and nothing forced it to after a task closed. The model even wrote the correct plan ("mark Task 1 DONE and wait for direction") then overrode itself on the next iteration.

Two code-level teeth, both in agent.py's turn loop, gated on the user's go-ahead NOT being a batch ask (project_advancer.classify_advance_intent → one vs n/all):

  • Hard stop on close. When a tool result shows a task actually closed to DONE (_manage_projects_closed_a_task reads the store read-back {"updated":[{"status":"DONE"}]} — a DONE-gated/held update does NOT count), the loop sets force_final_response, so the turn converges to a summary and waits.
  • Stop re-dangling the next task. Once a task closed this request, the briefing is rebuilt with suppress_next_task=True: the NEXT TASK pointer is replaced by a hard "you completed a task this turn — STOP and wait" note (open tasks are still listed for awareness). Removes the contextual pull that overrode the rule.
  • Honest stop message (2026-06-22). A model that still emits a tool_call after the turn was finalized has it stripped by the text-only stream scrubber, which then emits a fallback. When the cause is this gate (a task just closed), _scrub_fallback_message returns "✅ Task complete — say proceed / next to continue…" instead of the generic "I prepared a tool call… please rephrase", which had misled the user into re-issuing a request that already succeeded; the operator log drops from ⚠ Stream Scrub Fallback to an informational One Task / Turn line. The generic message still applies to a genuine planner/model routing mismatch.

Net: "start task 1" / "proceed" / "next" advance exactly one task and stop; "do the next 3" / "finish the project" are batch intents that still run multiple (routed to the autoadvance tool). Covered by tests/test_one_task_per_turn.py and the suppress_next_task cases in tests/test_project_pacing.py.

Reliability around "start task N" (2026-06-22)

Two more fixes that made single-go-ahead project flow robust, both observed failing live in one session:

  • Enumerated batches. "proceed with task 3 and 4" now parses as a 2-task batch (classify_advance_intent), so the one-task gate doesn't stop after task 3 and leave task 4 half-done.
  • Conversation-scope escape hatch. The chat API ships no stable conversation id, so a project bound to one conversation got parked for later turns whose first-message fingerprint differed — the agent then spun (manage_projects get ×3 → loop breaker → scrub fallback). tools.projects.reconcile_conversation now keeps/activates a project when THIS request's user message names it by title or id (_message_references_project), overriding the mismatch.
  • Host-path scrub. A recalled memory / scratchpad note / workspace narrative could carry a host-absolute sandbox path (/Users/…/Data/AI/Data/sandbox/projects/<id>/…); the model used it in cd and ENOENT'd inside the container (host ≠ /workspace), burning strikes. agent._scrub_host_sandbox_paths rewrites such prefixes to the container /workspace form in the injected DYNAMIC SYSTEM STATE.

Covered by tests/test_one_task_per_turn.py, tests/test_project_conversation_scope.py, and tests/test_sandbox_path_scrub.py.

Tool-orchestration routing rules (SYSTEM_PROMPT)

A block of MANDATORY TRIGGERS in SYSTEM_PROMPT maps user intents to specific tool calls so the LLM doesn't improvise. Current rules include:

  • SLEEP / REST → dream_mode
  • SELF-PLAY (one-shot) → self_play — for "practise", "train", "do self-play" (single cycle).
  • SELF-PLAY (continuous) → self_play_loop — for "continuously", "in a loop", "back to back", "until I tell you to stop". stop_self_play on explicit user stop while running.
  • LESSONS SURFACE → list_lessons — for "what have you learned today/so far/this week", "show me your lessons", "show me the lesson playbook". Picks scope ∈ {today, week, all, self_play_only} from phrasing. A LESSON is a mistake-and-fix the agent has internalized — distinct from a SKILL (a tool).
  • SKILLS SURFACE → manage_skills(action="list") — for "show me your skills", "list your skills", "what skills do you have", "show me your custom skills". A SKILL is a TOOL or set of tools, NOT a lesson. The historical "skill playbook" wording was the conflation that misrouted skill queries to list_lessons; both the tool description and this rule now disambiguate.
  • KNOWLEDGE & RAG → recall first.
  • WEB FACTS → web_search first; fact_check / deep_research only for complex verification.
  • SYNTHESIS OVER LARGE DATA FILES → execute a digest script, not whole-file file_system(read) (see below).

Report-path steering — synthesise data files via a digest script (2026-06-23)

The per-batch read budget stops the context-overflow crash by refusing later whole-file reads once a turn's budget is spent — but the model only avoids the dead-end if it reaches for a script BEFORE hitting the limit. Observed live: asked to write report.md synthesising three experiment JSON files, the agent read them in parallel and overflowed a 131 K window at 136 K tokens. A new SYSTEM_PROMPT bullet (SYNTHESIS OVER LARGE DATA FILES) makes the right move explicit: when writing a report/summary/analysis that synthesises result files (JSON/CSV/logs), do NOT pull them in with file_system(operation="read") — execute a short script that loads them, computes only the digest needed (key stats, aggregates, top-N, anomalies; ≤~50 printed lines), and write the report from that digest. For a quick peek use operation="inspect"; to scan one genuinely large file use operation="read_chunked" / "search". The rule names the overflow it prevents and says to act before the read limit, so the model connects it to the budget refusal it would otherwise hit. Covered by tests/test_report_synthesis_steering.py.

Specialist rule deconfliction (2026-06-12)

SPECIALIST_SYSTEM_PROMPT carried two imperatives a small model resolved the wrong way: rule 8b ("give me the SQL" → the reply IS the code; do NOT save it with file_system) and the execution rule NATIVE TOOLS FIRST (use file_system write for native file tasks). Observed live: a "Just give me the SQL, no explanations" request produced an unrequested migration.sql write — twice. NATIVE TOOLS FIRST is now explicitly subordinated to 8b: it picks WHICH tool once tools are warranted, it does not make tool use warranted.

Self-play challenge-gen hardening (SYNTHETIC_CHALLENGE_PROMPT)

The challenge-generation system prompt carries explicit rules to prevent LLM-generated validators from being unwinnable:

  • Float formatting — always convert both sides to float() with tolerance before comparing; never compare round() output with f-string output directly.
  • Unit suffixes — if an expected field carries a %, $, ms, or comma-thousand separator, strip it before float()/int(). Includes a concrete WRONG/RIGHT example of the float('60.00%') bug.
  • One convention per field — either string equality with the suffix kept, or numeric tolerance with the suffix stripped. Never mix.
  • Mental self-test — the generator is told to trace the validator against a hypothetical solution.py that echoes its own expected output; every parse/comparison line must succeed.

When FrontierTracker reports all clusters saturated, the dream loop additionally injects a CURRICULUM DIVERSITY REQUIREMENT block telling the generator to pick from {concurrency, algo, regex_parse, sql, bash} and forbidding another data-analysis / CSV-groupby shape.

PARTICIPANT MODE — "you play against me" (2026-07-02)

Observed live: asked for a chess game "where YOU will play against me — don't come up with some random AI", the agent built a single-file HTML page with an embedded minimax engine. The only deliverable pattern it knew for "game" was artifact with an AI inside (the PROJECT MODE GATING rule even lists "a one-file game" as its canonical one-shot example); nothing framed the agent itself as a runtime participant, so "the AI opponent will be me" rationalised into "I'll code a small engine". The TOOL ORCHESTRATION section now has a PARTICIPANT MODE (YOU ARE A PLAYER) trigger, directly under PROJECT MODE GATING:

  • Coding a minimax/random/any algorithmic opponent when the user said YOU should play is named a FAILURE, in those words.
  • The prescribed shape: authoritative game state in a workspace file (chess/state.json, FEN + history) · validate each user move with python-chess via execute (pip install python-chess in the sandbox if missing) · the agent CHOOSES its own reply move by reasoning, one chat turn per move — it may list legal moves programmatically but never delegates the choice.
  • An HTML board is optional and render-only: it may display state and collect the user's move; move-selection for the agent's side happens at runtime. A UI that wants live agent moves calls POST /api/game/move (see api.routes).
  • Sandbox-loopback clause (added after a second live violation, 2026-07-02 evening): diagnosing the user's "Could not reach API (Load failed)" from inside the code sandbox, the agent probed 127.0.0.1:8000 (the container's loopback, not the host's), concluded no server existed, and wrote its own api_server.py — with random.choice(legal_moves), the exact forbidden engine, reframed as a "mock". The rule now states: the agent's own API is NOT reachable from inside the sandbox at 127.0.0.1:8000; unreachability there is never evidence the server is down; a mock that picks moves IS the forbidden engine regardless of name; and game UIs must be opened served by the agent (/api/download/projects/<id>/…/index.html, same origin as the API) — a file:// open cannot fetch the API.

Briefing: EXPLICIT USER CONSTRAINTS section

build_project_briefing renders the project's metadata.constraints (captured by manage_projects) as an EXPLICIT USER CONSTRAINTS (MUST HOLD…) block above the design ledger, every turn — a constraint stated once and never re-surfaced lost to reinforced skill priors within a single reasoning pass. Covered by tests/test_project_constraints.py.

The compiled system prompt: SYSTEM_PROMPT_COMPILED (§4FF, 2026-09-07) — RETIRED 2026-09-21 (§4JG)

⚠ Retired. The full banded instruction-following bank (2026-09-20, 95 complete pairs on the live agent) measured no difference between the compiled prompt and SYSTEM_PROMPT: 87/95 vs 87/95, paired McNemar 6 vs 6 discordant, p = 1.0; easy 42/42 vs 40/42, tool 15/16 vs 15/16, deep 12/12 vs 12/12, hard 18/25 vs 20/25 (p = 0.73), zero narration beats and zero tool-syntax leaks on either arm. A second prompt variant carried for no measured gain is a liability, so the constant, the probe-only selector branch in GhostAgent._select_system_prompt and the X-Ghost-Prompt-Variant route header were removed; scripts/if_bench.py runs one arm and refuses a variant that does not exist. The method stays as the one seam a future A/B reattaches to. The history below is kept as the record of how the question was asked and answered.

SYSTEM_PROMPT is 129 sentences / ~4.2k tokens with ~39 imperative rules (~53 caps imperatives), 76% of it the TOOL ORCHESTRATION list. arXiv 2607.19257 measures perfect compliance on Qwen 35B at 72.5% with 10 rules, 10.0% with 40 and 0.0% with 80, with plain text beating markdown at high counts; arXiv 2608.02639 recovers +11 pp on the weakest model with an instruction compiler (cluster, merge, precedence); arXiv 2604.20911 finds omission rules decay to 10% by turn 16 on Qwen 3.5. Six weeks of real turns showed the cost: 23 explicit-constraint violations, 55 narration leaks, 8 tool-syntax leaks, 7 raw dumps.

SYSTEM_PROMPT_COMPILED is the same policy compiled to 12 numbered rules (an explicit format constraint in the current message wins; no facts you did not retrieve; counts come from tools; native tool calls only; never echo the state; files; projects; participant mode; images; memory) plus ONE routing table — a lookup, not a rule list — in plain text, at under 60% of the length. It never replaces the constant: every prefix-cache, warmup and GEPA-loader pin reads SYSTEM_PROMPT. It is selected per request by GhostAgent._select_system_prompt(body), which today serves it only to a DIAGNOSTIC PROBE that sent X-Ghost-Prompt-Variant: compiled (the route reads that header inside its probe branch only, and the agent re-checks the probe prefix) — the seam a live arm would use later. Two pins keep the two prompts in step: the compiled one names every tool the control routes, and its caps-imperative count stays under a third of the control's.

Provable before any live flip: scripts/if_bench.py drives a bank of format-constrained requests (seeded from real turns: "just the number", "one word", "reply exactly with X", yes/no, JSON only, Greek, N bullets, and tool-then-format items) through the live agent as probes, once per variant per repeat, with deterministic checkers over the reply and an exact McNemar over the paired items; it also counts narration beats and tool-call XML in replies. Tests: tests/test_4ff_prompt_variant.py.

The bank was measuring the wrong band 2026-09-13 §4GJ

The §4FF pilot read compiled 0.962 vs control 0.923 at p=1.0 — a bank at ceiling decides nothing. Graded against the live corpus with the shipped turn_state_check (1,883 user requests; 273 carry a mechanically checkable constraint), the reason is visible: the violation rate is 14% on zero-tool requests and 48% once one or two tools run, and 21 of the old bank's 27 items were zero-tool — it lived in the easy band. Worse, line_cap, the most-violated family after strict JSON (9 of 24 real requests), was absent from the bank entirely, while strict JSON (69% of real constrained requests) had three easy items.

The bank is now 36 items in three bands: easy (21, the §4FF items kept as a regression anchor), tool (8, in the 48% band) and deep (7, constraint stated once up front then four to nine sandbox steps). Deep items are self-seeding — they create the data they measure and delete it — so ground truth is deterministic and the bank neither depends on nor pollutes workspace state; they use only execute and file_system, because an item that needs the network measures capability, not instruction-following, during a Tor blackout. Every hard checker is anchored on the fact the task computes, so a cap cannot be satisfied by a dodge ("Done.", "0", "N/A"): a pinned table runs seven dodges past every deep checker. --bands selects a subset through the extracted select_items seam, and both if_bench.py and if_bench_combine.py report by_band with per-band pass rates and per-band McNemar — a saturated anchor band must never carry a flat deep band into one pooled "no difference" (the §4CE shape). Honest limit: the corpus contains zero constrained requests at seven or more tool calls, so §4FF's "depth ≥ 7" is built but not corpus-validated; what the record supports is "any tool work triples the violation rate". Tests: tests/test_if_bench_bank.py, tests/test_if_bench_combine_bands.py. Not yet run live — it costs real inference and is the operator's call.

Run live: every band at ceiling 2026-09-14 §4GU

72 pairs, two repeats, both variants: 0.972 vs 0.972 overall, p=1.0, and the band that was built to break the ceiling read 1.000 in BOTH arms. The two failures were the SAME item in both arms and both repeats — words-1, "Explain recursion in at most 12 words", answered in 12–14. The honest reading is about the instrument: the bank cannot discriminate these two prompts at this size, which is "no measurable difference AND the instrument is saturated", not "the prompts are equivalent". The one item that discriminated names the shape that was missing: a constraint whose violation is cheap to state and hard to satisfy.

A fourth band, banded by CONSTRAINT rather than by tool regime 2026-09-14 §4GX

The three existing bands stratify by tool regime, which is the axis the corpus said predicts failure (14% at zero tools, 48% at one or two). §4GU measured all three at ceiling anyway, and the single discriminating item was zero-tool — so the regime axis was not the binding one for these two prompts. The new hard band (15 items) is stratified by constraint family instead, and is the only band that deliberately spans both regimes: ten zero-tool items, three tool items, two deep items.

The family is the shape the model has to give something up to satisfy, rather than one it emits correctly by habit: tight word caps (8, 7, 10 words on questions that want a paragraph), exact word counts (not ceilings — a cap can be met by saying less, an exact count cannot be met by saying less or more), bans on the words the natural answer reaches for first ("explain DNS without using name, domain or address"), a per-line budget over an exact line count, a word budget inside a JSON field, and the same budgets stated once and then buried under sandbox work.

Every new checker carries a floor or a content anchor, because the cheapest way to obey a budget is to answer nothing and the cheapest way to obey a ban is silence: a pinned table runs seven dodges ("", "0", "Done.", "N/A", "None", "OK", "Yes") past every hard checker. The bans cover inflections — an item whose ban is walked around by adding an s measures nothing. And needs_tools is now pinned against the request text itself rather than by a count: an item that says "run this in the sandbox" while flagged zero-tool would be selected by --no-tools into a bench that cannot do the work, and would score as an instruction-following failure that is really a bank bug.

Ran live, 30 pairs, 0 errors: control 0.767 vs compiled 0.600, exact McNemar b=7 c=2, p=0.18. §4GU's whole 72-pair bank produced disagreements: []; this band produced nine out of thirty. It is not at ceiling, and for the first time the bench has a direction — it favours the CONTROL prompt. At p=0.18 that is a signal to power, not a verdict to act on.

And the per-item breakdown is the sharper finding. Every discriminating item is zero-tool (h-words-1/2/3, h-exact-2, h-comp-1, h-json-1, h-lines-1), and every tool-regime item in the hard band sits at ceiling in both arms — which agrees with §4GU, where the tool and deep bands read 1.000/1.000 over 72 pairs. Twice measured on two different banks: for these two prompts the tool-regime axis does not discriminate. The 14%/48% corpus statistic that motivated the regime bands is about the agent's failures in general, not about where these two prompts differ. Two items sat at the floor in both arms: exact word counts defeat the model either way (a capability limit, not a compliance one), and h-ban-2 turned out to be a bank bug — it asked "describe what a compiler does without using compile" and both arms failed on the word compiler, the subject the question itself names. An item whose only failure mode is disputable measures nothing; it was reworded, and the instruction now states what the checker enforces.

The way to power this is more DISTINCT items, never more repeats of the ones that worked — the bench unit is the distinct prompt, the trap that once turned p=0.0003 into p=0.88. Ten fresh zero-tool items in the same family were added and run as a pre-registered replication, with the prediction (control-favouring, b > c) written down before the run rather than read off it.

The replication, and what it says 2026-09-14 §4GY

Ten fresh zero-tool items in the same family, authored and pinned before any of them was run. 20 pairs, 0 errors: control 0.650, compiled 0.650, exact McNemar b=2 c=2, p=1.0. The pre-registered prediction — that the calibration set's control-favouring direction would reappear — failed. Pooled across both runs (a caveated secondary, since the first set's items were the ones being selected on) b=9 c=4 over 50 pairs, p=0.27. There is no difference here to act on.

The instrument, however, is real, and that is the deliverable. 0.65/0.65 is nowhere near ceiling; four discordant pairs came out of twenty, against zero out of seventy-two for the whole §4GJ bank in §4GU. The difference between that "p=1.0" and this one is the entire point: the first was a bench that could not lose, this is a bench that can and simply did not. A "no difference" from a saturated instrument is not evidence; a "no difference" from an instrument with 13 discordant pairs across 50 is.

The failures are the proof that it measures what it claims. h-words-5 answered "Merge sort is O(n log n); bubble sort is O(n²)." in BOTH arms — nine words against an eight-word cap, a genuine one-word overrun on a correct answer. h-json-2 (compiled) returned seven words inside a six-word field budget. Compliance failures on correct content: exactly the class the band was built for, and exactly what the old bank could not see.

Standing conclusion. Two independent banks and 122 paired comparisons have now failed to separate SYSTEM_PROMPT from SYSTEM_PROMPT_COMPILED on instruction following — the first because it could not, the second because there was nothing to find at this size. The compiled prompt's case rests on its other measured property (§4GU: 5.0 s faster per reply, median −4.9 s, faster on 62 of 72 pairs), not on compliance. A future flip should be argued on latency and re-checked on the hard band, never from a saturated pass rate.

Tests: tests/test_if_bench_bank.py (391, including a compliant/violating pair per item and the checker-property class). Battery: scripts/mutate_4gx.py, 12 mutants plus a no-op control (survived) and a known-bad control (killed) — 13 of the 13 that must die, died — among them "an exact count becomes a ceiling", "a ban stops covering inflections", "the per-line budget stops binding on every line" and "the hard band drifts to zero-tool only". The items are calibrated live before any verdict is read off them: an item that passes 100% or 0% in both arms discriminates nothing, and shipping a bank without measuring that is how §4FF and §4GJ both ended at ceiling.

Rule 5 — LANGUAGE 2026-09-21 §4JN

Operator: "while speaking to the agent in English, the agent sometimes translates my search to Greek — why?" Measured on the recorded turns (July–September): 18 of 167 English requests that searched issued at least one Greek-script query — every one a Greece-local subject (restaurants near home, Greek people and institutions), the model's own retrieval judgment from the profile's Athens, Greece and from watching English queries fail ("jiujitsu north athens" returned Missouri, Tbilisi and Athens GA; the next query was Greek). No rule, tool hint, lesson or code asked for it. Where it went wrong: proper names translated ("Anatolia College" → "Ανατολικό Σχολείο", which does not exist) and mixed-script queries (46 of 983). The user-visible side effect: 14 of 2,112 English requests were answered mostly in Greek (0.66% on prose lines; quoted headlines excluded) — the reply drifting into the sources' language. There was no language rule anywhere, and the trivial-chat path has its own short prompt with none either ("hello there" → "Γεια σου!").

Now: SYSTEM_PROMPT rule 5 under COGNITIVE ARCHITECTURE — reply in the language the user wrote in, whatever the sources' language (quote a source in its own language only when the quote is the point); search in whichever language finds the sources — a Greece-local subject usually in Greek — but never translate a proper name, and one script per query. The trivial-chat prompt gained "in the language the user wrote in". Measurement: scripts/measure_reply_language.py --since 2026-09-21 reports query-switch, mixed-script and reply-mismatch rates against the pre-rule baseline (query switch 10.8%, mixed 4.7%, reply mismatch EN→EL 0.66%, EL→EN 4.3%). Pins: tests/test_reply_language_rule_2026_09_21.py (the rule reaches the model's system message on both prompt paths — a consumer pin, not a grep; the measurement's classifier on the shapes it counts). The query switch itself is not the target: for Greek-local subjects it is the right move; the proper-name translation, the mixed scripts and the reply drift are.
