core / imagination.py — the gate that ships before the planner

Decides, per (tool, tclass) bucket and from ledger data alone, whether foresight precedent is good enough to steer with. It is the only reason any Imagine steering site is allowed to exist — and as of 2026-08-22 it says no, for every bucket.

⚠ PARKED — measured, §4CS 2026-08-24. Live: 754 ledger rows, 63 buckets, zero enabled — 57 thin, 6 without a denominator. Every bucket's why reads "needs N more", which is indistinguishable from a gate merely waiting for data. It is not waiting.

1. The incumbent passes its own checker. Every field of the three largest buckets was recomputed by hand from the raw ledger and matched what build_gate wrote, verdicts included; and the enabled path is reachable — synthetic buckets at (fail_n 10, precision 0.90) and (30, 0.80) both enable. At the FLOOR (fail_n 10, precision 0.60) the interval test binds and the bucket does not, exactly as this module's own docstring warns. Re-run it: scripts/measure_foresight_gate.py.

2. The denominator is not the binding constraint. Predicted-fail rows arrive at 0.77/day across all buckets, so the best-placed bucket (deep_research|other, 4 of 10) is about five weeks from min_fail_n — not years. What never arrives is the PRECISION.

3. The index is ANTI-PREDICTIVE. Pooled over every steerable row in the ledger it scores 1/14 = 0.071, Wilson 95% CI [0.013, 0.315] — entirely below the 0.60 bar. Rows the index claims will FAIL fail 7.1%; rows it claims will succeed fail 10.6%. The spread is −0.035 against a +0.10 bar: the sign is wrong. Brier skill is negative in 14 of the 18 buckets that have a denominator — the probabilities are worse than a constant at each bucket's own base rate.

Why that is decisive rather than merely discouraging: _evaluate_bucket rejects on precision < min_fail_precision before the interval test, so a bucket whose true precision is under the bar cannot enable at ANY n. Time-to-qualify is not long — it is UNDEFINED unless the index itself improves. More traffic does not fix this.

build_gate now emits a discrimination block carrying the pooled numbers and this verdict, surfaced on the idle-phase summary and in the LOOP YIELD row. It is DERIVED, so it flips on its own the moment predicted-fail rows start failing more than predicted-ok ones. Tests: tests/test_4cs_foresight_gate_parked.py (10 tests, 10 mutants, 10 killed).

Why the gate comes first

Two negative results from the literature are load-bearing for the whole Imagine phase: an agent offered a simulation tool uses it under 1% of the time and gets worse, and a planner gated on a model's self-reported confidence is gated on nothing. So imagination has to be forced into the loop rather than offered — and gated on measured historical accuracy rather than on a model saying it feels sure.

This project's own history says the same thing more sharply. MCTS turn-start was disabled precisely because its value function scored the model's self-prediction of un-executed actions. Foresight was built to be the grounded replacement, and its verdict on the live ledger has been "underpowered-promising" for weeks — never "measured usable". The gate is what turns that sentence into a per-bucket boolean that code can read.

What "the index claimed this will fail" means

This looks like a detail and it decided the phase's headline number.

Foresight's probability is Laplace-smoothed: p_fail = (fails+1)/(support+2). So

p_fail >= 0.5   ⟺   2(f+1) >= n+2   ⟺   2f >= n

The prior's mean is 0.5, so it contributes exactly zero shrinkage at the decision boundary — the test reduces to a bare majority on raw counts, inclusive of the tie. A cell that has seen 2 failures in 4 tries reads p_fail = 0.5000 and was scored as a failure claim. Measured on the live ledger over the 24 rows the old rule admitted:

SubsetnReally failedPrecision
all p_fail ≥ 0.52460.250
ties, exactly 0.5000950.556
strict, > 0.51510.067

Coin-flip cells were 37.5% of the "predicted-fail" population and carried all of its apparent precision. The index's real failure claims are right 6.7% of the time — below the ~10% base rate. And support=3 and support=4 are the two most common values among predicted-fail rows, so the tie is the modal case, not a corner.

claims_failure() is therefore strict (2·fails > support) and works on the raw counts the ledger row already carries — which also sidesteps the four-decimal rounding of p_fail, where at support ≈ 10⁴ a strict minority rounds up to 0.5000. All three readers — the gate, the pre-flight steer and foresight.ledger_stats — share the one definition.

…and it is measured over the population the steer will touch

The steer additionally requires exact-or-class basis, support ≥ 3, at least two real failures, and a non-empty error head. Certifying precision over every row carrying a claim would be certifying a statistic about rows nothing acts on — and on live data that is the more precise subset, so the gate would read better than the mechanism it authorises. is_steerable_row() is one predicate, shared by the gate and the consumer, for exactly that reason.

The bar

A bucket is enabled only when all four hold. Each one is a separate lesson, and the order below is the order a reader should think about them — the first failure wins the bucket's why string, so the message always names the binding constraint.

ConditionDefaultWhy it is there
resolved rows in the bucketn ≥ 30The same "no verdict on thin data" floor the whole-ledger backtest uses.
rows where the index claimed p(fail) ≥ 0.5fail_n ≥ 10The steer only ever acts on that subset, so its accuracy is the statistic that matters — and a precision of 1.00 over three rows is not a measurement. This is the denominator floor; it is checked before the precision is even looked at.
precision on those rows≥ 0.60A pre-flight steer costs a model round-trip. Below this it interrupts more good calls than bad ones.
discrimination within the bucketspread ≥ 0.10, intervals disjointOverall accuracy is the wrong statistic: the base failure rate is about 10%, so "always predict success" scores 90%. What matters is whether the predicted-fail rows fail more than the predicted-ok ones, by a margin, with disjoint anytime-valid intervals.

The thresholds are recorded into the gate file. A gate on disk always names the rules that produced it — otherwise a threshold change silently re-reads a file that means something nobody chose.

Allow-list, not deny-list

gate_allows(tool, tclass) answers False for a missing file, an empty file, a truncated file, a document of the wrong shape, an unknown bucket, an enabled that is truthy but not exactly True, and any exception on the way. There is no path through it that opens a bucket by accident. The write is atomic, so a reader can never catch a half-written allow-list that happens to parse.

The threshold was not relaxed to make the feature turn on. The gate stays closed, it says per bucket exactly why (and how many more rows it needs), and it re-opens on its own when the data changes.

Saying why it is closed

Every bucket carries a why. A gate that reports only false is unmeasurable: nobody can tell "no data yet" from "measured dead", and those lead in opposite directions — one says wait, the other says redesign. The health surface (introspect action='learning') shows the histogram, which today reads 57× thin bucket; 6× no denominator.

Where it runs

Biological phase 2.7e, in the 15–60 minute idle band beside the other calibration siblings, on a 24-hour cooldown. Pure file I/O and counting — no model call, milliseconds. It is registered as PERIODIC in the liveness registry, so a week with no rebuild reads as an alarm rather than as silence.

It runs even when GHOST_IMAGINE is off, and that is deliberate: a closed gate is a measurement, and the question "has the precedent index become good enough to steer with yet?" should keep being answered while the feature is disabled. Otherwise the day it becomes usable never arrives. The master flag gates the consumers, not the instrument.

The first consumer: the pre-flight steer (I1)

Today the foresight_note arm appends precedent to a tool result after the call has already failed. The pre-flight steer moves the same knowledge before dispatch: the call is not run, the model is handed the precedent, and it gets one revision.

It lives in GhostAgent._imagine_preflight_note, hooked in as a sibling of the repeat-failure guard in the tool loop — deliberately at the point where the coroutine has not yet been created. In the foresight prediction loop further down, "do not dispatch" would mean closing an un-awaited coroutine and threading a second kind of placeholder through the batch-dedup machinery. At the guard's position it is the same shape every other pre-dispatch rejection already uses: emit a synthetic tool message, continue, and control returns to the model.

Five gates, in cost order, so a disabled deployment pays almost nothing per call:

  1. GHOST_IMAGINE (default off) and GHOST_IMAGINE_PREFLIGHT;
  2. the loop guard — once per argument hash, at most twice per request. Without the first half a model can re-propose the identical call forever and the turn never acts; without the second, a model that revises into a second flagged call chains;
  3. gate_allows(tool, tclass) — the measured allow-list above, which enables nothing today, so this whole path is inert by construction;
  4. the precedent itself: exact or class basis, support ≥ 3, at least two real precedent failures, p(fail) ≥ 0.5, and a non-empty error head to actually tell the model;
  5. the imagine_preflight experiment arm. Control dispatches unchanged and is still trigger-marked, so the two arms' trigger rates stay comparable — the metric only means anything on the triggered subset.

Two properties that are easy to get wrong and are pinned:

  • A deferral is not a failure. execution_failure_count and last_was_failure are untouched. A deliberate steer charged as a strike would spend the turn's error budget on its own advice, and six strikes ends the turn.
  • A deferral is synthetic. The message pairs with a tool_call in the reconstructed trajectory exactly like a real result, and its label would be inverted — a deferral on a repeatedly-failing target reads as a success. Its marker is registered with foresight.is_synthetic_result, which is what stops a steer from teaching the very index that produced it.

The consistency ratio

scripts/foresight_backtest.py --consistency is the phase's go/no-go number: over the steps imagination actually re-ranked, the fraction where the branch it preferred was the one that worked. Per-step accuracy is a lying metric for a planner, because errors compound — a ranker that is 90% right per step is wrong most of the way through a ten-step trajectory.

It counts only discriminating pairs. A pair where both branches passed says nothing about the ranking, and including it drags the ratio toward whatever the base pass rate happens to be.

It also refuses a verdict it does not have the power for. Against a null of 0.50 (the estimator is conditional on exactly one branch passing, so a coin flip is the null), reaching 80% power at the 0.70 bar takes 49 discordant pairs; via this project's own anytime-valid interval it takes about 80. Below that floor it prints the point estimate, says how many more pairs are needed, and exits with a distinct code. Before that guard, a single pair at ratio 1.000 exited as PASS — the §4CE shape, sitting inside the very feature whose gate exists because "a subset of 1 with precision 1.00 is not evidence".

The instrument is currently unarmed, and says so with its own exit code rather than printing a number derived from an empty file. Its data source is the regret ledger, which is written by the nightly block that re-executes a rejected branch and grades it — a component that does not exist yet. Three exit codes, not two: unarmed, underpowered and a real verdict are different facts, and a loop polls the code rather than the prose.
