Durable sessions & real turn cancellation

core/sessions.py · core/turns.py — 2026-07-11. The two things that stood between this agent and being a daily driver: conversations that survive a device switch, and a way out of a wedged turn that doesn't involve restarting the process.

1. Durable server-side conversations

The gap. History was entirely CLIENT-carried — the web UI's localStorage, a Slack thread, or a manual workspace/save zip. Switch device or clear the cache and the conversation was gone; each client held a different fragment, so a conversation started in Slack could not be continued in the web UI. Ironic, given cross-session MEMORY is this agent's proven strength (Track B: 98% recall vs 0% control) — the memory substrate persisted while the conversations themselves did not.

The shape. One JSON file per session under $GHOST_HOME/system/sessions/: {id, title, created_at, updated_at, messages}. Sessions live entirely in the API layer — the chat route merges stored history into the request before handle_chat and appends the turn after it returns — so the agent's turn logic is untouched by this feature.

The merge contract (merge_history)

Pass session_id in the /api/chat body and the SERVER becomes the source of truth for history. It tolerates both client styles, which is what makes adoption incremental:

⚠ Rewritten 2026-08-17/18 (§4BU). The thin/fat classifier this section used to describe is GONE, along with the "used as-is rather than appended" rule and the "everything past the stored prefix" slice — that slice was itself the doubling defect (it re-appended already-stored messages whenever the merge inserted anywhere but the end).

There is now one rule and no thresholds: longest-common- subsequence alignment of (role, content) against the stored history, then stored, plus whatever of incoming is not already accounted for. Two invariants hold by construction — nothing stored is ever dropped, and nothing already stored is appended twice. Client-side assistant messages are dropped from the persisted tail (assistant turns originate server-side); in the cap-evicted PREFIX, which reaches the prompt only, a complete reply is kept and only a stub the client itself marked *[Aborted]* is dropped. A tool result whose calling assistant was dropped goes with it, because an orphaned tool_call_id is persisted and then poisons every later turn.

merge_history_detail() returns (merged, new_tail); the route persists the TAIL, never a slice of the merged list. The reply is persisted even when the tail is empty (a client re-sending an already-stored history used to have its reply discarded forever). Omit session_id and behaviour is exactly as before (fully client-carried), so every existing client keeps working untouched.

Bounds & safety

  • Session ids are opaque tokens ([A-Za-z0-9_-]{1,64}) — a path-traversal guard, since the id names a file.
  • 200 sessions (least-recently-updated evicted); 400 messages per session (the most RECENT system messages (§4BU: keeping the oldest evicted the CURRENT prompt) + the newest tail kept, mirroring the agent's own 500-message cap).
  • Malformed messages are dropped rather than persisted (a corrupt session would otherwise poison every future turn that loads it); tool-call plumbing (tool_calls / tool_call_id / name) IS preserved so a resumed conversation's tool pairing stays intact.
  • Every method degrades (None / [] / False) rather than raising into a request; a corrupt file reads as absent.
  • The streamed-final-generation path bypasses the finalize tail, so the route reconstructs what the user saw from the SSE deltas (_sse_delta_text) — without it a session would record the user's message and no reply.

1b. Hydration tier (2026-07-14)

Stored sessions are now a retrieval source, not just replay state: SessionStore.search_messages(query, limit=5) keyword-searches the most-recently-updated _SEARCH_MAX_SESSIONS (50) sessions and feeds MemoryBus._fetch_session as the fifth hydration tier (see bus). Fail-safe — returns [] on any error. Tests: tests/test_session_hydration_tier.py.

2. Real turn cancellation

The gap. Turns are globally serialized (agent_semaphore = Semaphore(1), #22), so ONE wedged turn blocks the web UI, Slack, and the autonomous project-advance ticks at once — and there was no way out: the interface's /api/chat/cancel only cancels the proxy's buffered stream, so the agent kept working and kept the lock. The only real remedy was restarting the process.

The registry. core.turns.TurnRegistry gives every in-flight turn an identity (its req_id), a handle on its asyncio task, and a cooperative cancel flag. A turn registers itself before acquiring the semaphore, so a request QUEUED behind a runaway turn is cancellable too.

GET /api/turnswhat is running and for how long, plus anything queued behind it — this is how you see WHY the agent appears unresponsive
POST /api/turn/cancel{request_id?, hard?} — request_id defaults to the running turn

Cooperative vs hard

  • Cooperative (default). The flag is set; the turn loop notices at its next boundary, raises TurnCancelled, and handle_chat catches it and returns whatever partial work exists (a clean stop, not a crash). Exiting through there unwinds the async with self.agent_semaphore, so the global turn lock is released — which is the entire point.
  • Hard (hard=true). The asyncio task is cancelled outright. This is the guaranteed release for a turn wedged inside a long upstream call that never reaches a boundary.
  • A queued turn is always hard-cancelled — it has no partial work and no boundary to reach, and killing it is strictly better than letting it start.

req_id collision handling (2026-07-14 bug hunt)

req_id can be a CLIENT-supplied X-Request-ID (the route reads the header), so two overlapping requests can carry the same id. The old registry overwrote the live entry unconditionally and popped by key, so /api/turns hid the first turn, cancel("X") flagged the SECOND turn (cancelling B killed running A), and A's finally evicted B's entry. Fixed: register() never clobbers a live entry — it uniquifies the new key (X#2, …) and handle_chat adopts the effective id; unregister() is IDENTITY-CHECKED (pops only if the stored object is this turn). Tests: tests/test_turn_registry_collision.py.

Streaming tail stays cancellable (2026-07-15)

The STREAMING final-generation path returns a generator from inside the semaphore block, so the actual upstream stream runs while the client drains it — after handle_chat's finally has already run. That finally unregistered the turn the instant the generator was returned (before a single token streamed), so the tail was invisible to /api/turns and uncancellable. Fixed: the streaming path wraps its generator so the unregister is DEFERRED into the wrapper's own finally (runs when the drain completes), and the stream loop now checks is_cancelled each chunk — a cooperative cancel stops emitting mid-stream and finalization still runs on the partial text.

The agent_semaphore is deliberately not held across the drain (diverging from the original fix sketch): stream_chat_completion already counts foreground_tasks for the whole stream, so the single upstream slot isn't stolen, whereas holding the permit until the generator drains would couple turn serialization to client read speed — a stalled reader would block every later turn, a worse failure mode than the one being fixed. Tests: tests/test_streaming_tail_cancellable.py.

2026-07-27 audit fixes

  • merge_history compounded the whole conversation every turn (HIGH, closed). The fat-client detection required the stored history to be an exact prefix of the client's replay; on any divergence it fell through to stored + incoming, so the entire replay was appended again — and append_turn stored it. Measured: 5 → 11 → 19 → 29 messages over four turns (quadratic), until the 400-message cap filled with duplicates and the LLM context was dominated by repeated history.
  • Two realisable triggers, both permanent once hit: (a) an aborted stream — the server persists the full reply before streaming, so a client that disconnects mid-reply keeps a truncated copy and every subsequent turn diverges; (b) the message cap — once a session exceeds MAX_MESSAGES_PER_SESSION the stored copy loses its oldest messages, so the client's replay can never prefix-match again.
  • ⚠ The fix described here — "tolerate divergence in at most the final message; treat the replay as authoritative and REPLACE the stored copy" — was itself removed in §4BU. A one-message tolerance means the SECOND aborted stream in a session breaks detection permanently, and "replace the stored copy" is a licence to delete durable history: a stale tab missing middle messages had them deleted. Both were reproduced. The current design (above) never replaces and never drops; it appends only the unmatched tail. Regression tests: tests/test_sessions_merge_properties.py (property-based, driving the real SessionStore.append_turn with append-only clients) and tests/test_sessions_and_cancel.py.

The stream prefix length 2026-09-29 §4KP

A streamed reply can open with the stream prefix — the prior turn's text and a one-shot correction banner — which is not that generation's text; a re-render cuts leaked reasoning only AFTER it. The chat route persists the prefix length with the reply (append_turn(..., prefix_len)) as the assistant message's prefixLen; _clean_messages keeps it only on an assistant message, as an int within the content's length. GET /api/sessions/{id} returns it, so a reply adopted from the server (another device, a session switch, a reconcile) re-renders with its banner. It is a CLIENT key: the route passes the merged history through model_messages, which drops it, before the agent sees it. Matching (_msg_key) is role + content, so it never affects the merge.

§4PP (2026-10-16): Slack's conversation key is not a session

The Slack bot sends session_id: "slack:<thread or dm>:<user>" so the agent can keep a state of work across the turns of one thread or DM (§4OE-1). The bot sends the thread's history itself, so the server store has nothing to add. The chat route passed the id to the session store anyway; its colons fail the store's id charset, so every owner Slack turn logged "session NOT persisted … this conversation is not durable". That was a false alarm: nothing was lost. The route now leaves ids that start with slack: out of the session store (routes.is_conversation_key_only), and the agent still receives the id for the state of work. Making the store accept the id would have been worse: every DM would merge one rolling 400-message history into each DM request. The warning now means what it says: a web conversation that is not being saved. Pins: tests/test_4pp_temp_documents.py.

Stopping a running tool (step 5). POST /api/turn/interrupt with {"session_id"} stops the tool call or calls the conversation's turn is waiting on right now. The turn goes on, and the model reads that the user stopped them. The sender is checked like the inbox: same conversation and same kind, never a member or a Slack conversation. The route answers 200 with the tools running when the stop arrived (a call that already finished is not listed). A file operation (any file_system call, reads and deletes included) is never cut: it finishes, and its real result, or its error if it raised, reaches the model with a note that the user asked to stop while it ran (review s5-r9: a stop that landed on a batch's only call, a write, had left no trace for the model). The note goes into the model's copy of the tool message only. The result and the turn's own record of its tool calls are untouched, so the failure context, the outcome preview, the verifier and the empty-reply fallback (which quotes the last tool result to the user) see the real result only (s5-r10 to r13: a note put in a shared value reached each copy of it, and each fix missed one). The trajectory row records what the model saw, so it keeps the note at the end of that result; its readers judge a result by its head. A prompt rebuilt after a context overflow keeps only the newest substantive tool result; when that result is a hit call's, it carries the note, every time: the record row of a hit call holds the note in an internal key, like the other internal keys on those rows, and the rebuild re-adds it (s5-r15: matched by call id, a stream that left the id empty put the note on another call, and a second rebuild lost it). A batch-dedup copy of such a call carries the note too, like its original. The route answers 404 when this sender has no running turn, and 409 when nothing is running, a stop was already sent for this batch, or the turn is being cancelled. Stopping the whole turn stays /api/turn/cancel. §4SB: the route interrupts the tools of every running turn of the sender (a draining tail may run a tool too); and stopping the whole turn now interrupts first — a typed stop word, and the Stop button on a running owner or probe turn, call interrupt_tools and then cancel, so the sandbox job, browser runner or download is killed instead of running on to its budget while the turn waits to unwind; the reply names them in interrupted (log: 🛑 [rid] stop button: <tools>).

How it works: each tool batch gets a utils/tool_stop.ToolStop. Each call runs inside _stoppable_call, which binds the stop in a ContextVar for that call alone, so its task and worker threads see it and the loop's own context never does. It also notes when the call really started and while it runs, and never starts a call once the stop is requested. The batch waits for its calls with _gather_stoppable; with no stop bound (feature off) this is exactly gather(…, return_exceptions=True). On a stop:

  • Calls that finished before the stop keep their results. A call the stop reached is stopped, whatever it returns: one that swallowed its cancel, one its killer made return its own error before the batch's next poll, one that raised its own cancel. The stop records the calls running at that moment.
  • Calls still running are cancelled. The batch waits up to STOP_GRACE_S (20 s) for them to unwind, and a browser call holds its profile lock until its runner returns.
  • Calls that have not started never run. That covers a vision_analysis read waiting for the other calls, a later call in an in-order chain, and any file call after the one in progress. A file operation in progress is never cut; its result or error carries the stop note.

Three tools really stop their work, and say so only when the kill is confirmed:

  • a sandbox job: the supervisor's poll loop kills its process group, and the call returns exit 130;
  • the browser runner: while its call holds the profile lock, the only runner in the container is this one, so it is killed by its exact command line (python3 -u .browser_runner.py …, nothing that merely names the file);
  • yt-dlp: the transcription download polls each second and kills its session.

A worker thread notices the stop at its next poll, after the batch has moved on. Each killer therefore arms while it can still act, and the batch waits up to KILL_CONFIRM_S (8 s) for armed killers to settle before it writes the results. The browser kill retries for a runner that was just launched, and a browser call reached after the stop never launches one. The model then reads one of three results. "INTERRUPTED BY THE USER … and it was stopped" is used only after a confirmed kill. Otherwise it reads "… its output was discarded; work it started may still finish in the background". A call that never began gets "NOT RUN". §4SB: a stopped call that had started (killed or not) also says "Files it was writing may be incomplete — check them before relying on them." — a script cut while writing a report, or a download, leaves half-written files, and the model is told to check them, not trust them. Each result tells the model not to run the call again unless the user asks. It is an UNRESOLVED ToolOutcome with reason user_interrupted, so it is neither a success nor a failure:

  • It is never memoised, so the user's later re-run really runs.
  • It is never recorded as applied, so a re-sent setter is not refused as "already applied".
  • It is never a passing run for the code-claims ledger.
  • It draws no strike. Every reader of "unresolved" asks tool_stop.is_user_interrupted (the reason, or the text of a stored row) first, so it is never "still running": the multi-call summary lists it as STOPPED BY THE USER, never as SUCCEEDED; the project work log marks the command "[stopped by the user]"; Perfect-It skips a turn whose tool call the user stopped (it is not a finished task); the empty-reply fallback opens "The user stopped the last tool call…", never "Process finished successfully."; a batch-dedup copy of a stopped call reads its original's kill; the code-claims ledger does not count a stopped page load as a run of the page; the evidence gate and the turn-state check count a stopped retrieval as empty ("stopped by the user"), not as evidence; the edit-churn brake, the constraint steer, the no-progress breaker and the search counters ignore a stopped call; the census reads a stored stopped row as unresolved, not as a success.

Kills are recorded per call (the batch index, a second ContextVar), never per tool name: two calls of one tool, one killed, are reported apart. Background work a call spawns (spawn_bg, e.g. a delegated sub-agent) never inherits the call's stop. A call that ran may have changed something before it stopped (world_changed). Other tools (search over Tor, deep research, image generation) are cancelled on the asyncio side only. The image node does stop its render when the request disconnects, but that is not confirmed back, so the wording stays "discarded". Pins: tests/test_tool_interrupt.py.

CLI (step 6b). In the interactive CLI (interface/externals/cli/ghost) the reply streams on a background thread, and the main thread keeps a live prompt under prompt_toolkit's patch_stdout. Completed blocks print into the scroll as before. The final transcript matches the old path line for line. Enter while a turn runs posts the line to /api/turn/inbox, and the CLI shows the result by path:

  • inject: a dim "queued: …" line.
  • status: the system's answer, shown under the question.
  • cancel: the Ctrl-C path. The partial reply is kept and the undelivered texts go back into the prompt. §4SB: when the inbox answered a typed stop with path: cancel naming this turn (r2: by request_id or any of request_ids, a #n reuse suffix allowed) and no reply text had arrived, the hand-back line says "the agent received the stop and cancelled the turn before replying" — the agent received it for sure; the "may or may not have received it" hedge stays for every case the CLI cannot know (a stop that named another turn, Ctrl-C, a lost cancel answer).
  • queue: held, then sent as a normal message after the reply (but only after a normal reply; see below). A stop or hold word is never held: the agent's own lists are copied into the CLI and pinned equal to _STOP_RE and _DENY_RE. §4SB r2 narrows what counts (_hold_word): a whole-line stop word always; the deny words ("no", "nope", "wait", "hold on", "stop", "cancel", "abort", "όχι", "μη(ν)", "άκυρο", "περίμενε"…) only when the line is nothing but such words and punctuation ("wait, no", "no.", "hold on", and — r3, which dropped an r2 word-count cap that let it through — "no no no no"). "no sugar", "stop the backup job", "cancel that" and "ok no problem" are ordinary text, held and sent after the reply. The notice names the word ("after «wait» nothing typed this turn is sent on its own"), and (r4) a hold word typed during a turn also pulls the re-send chain still waiting in the outbox — an earlier turn's leftovers and held lines — back into the prompt, first, named "with the N still waiting to be sent": sent on, it would out-run the «wait». The chain is appended to the waiting prompt buffer, never prepended (r5, review MAJOR): the busy prompt commits the restored lines by position, so a prepend put the chain into the slots the prompt already showed and dropped it at the commit. Such a word may be answered queue because the turn has not registered yet or waits behind the lock, and sent later it would be a new request, so it goes back into the prompt. And if any line typed during the turn is a stop or hold word, every held line of that turn comes back too, typed before the word as well as after it, named in one notice, never sent on its own (operator decision, review r8: a stop or hold sent later means something else). An HTTP error, or a connection that was refused or timed out while connecting (never sent), is held the same way. Any other failure, such as a read timeout, may come after the agent already took the line, so the line is never sent again on its own: it goes back into the prompt with "the agent did not answer — it may have received this".
  • Another turn: the agent routes a line to the conversation's latest running turn, which may be an earlier one still finishing. If the answer's request_id is not this turn's (a probe prefix and a #n reuse suffix are allowed), the CLI says so and keeps streaming. An inject was accepted by that turn, which may act on it, so it is not put back during the turn: the notice says the earlier turn received it. This client cannot see that turn end (another client may stop it and take its inbox), so unless that turn's undelivered or the leftovers return it, the line comes back at the end of this turn, named "may or may not have read", even after a clean reply. A status answer was not accepted, so the line goes back into the prompt. A stop word is echoed (never put back) and the CLI cancels this turn by its own id. The earlier turn's undelivered comes back named ("the earlier turn's unread messages: «…»"), minus any line already sent as a message in this turn or the one before it, one for one (a message the CLI sent as restored lines joined by newlines counts line by line). A line typed during this turn is never dropped by that match: the earlier turn accepted it, so it comes back.
  • No inbox: the feature is off (queued messages are off), or an older agent answers 404. The line is never sent on its own, because a "stop" or "wait" would arrive later as a new request. It goes back into the prompt after the reply instead, as the CLI behaved before.

After each reply the CLI takes /api/turn/inbox/leftovers. A leftover is sent after a clean reply, and goes back into the prompt otherwise (§4SB r2, operator: "both are correct depending on the case"; until then rule r4 never sent one). The agent accepted it, but no turn read it. After a clean reply it is sent as a normal message through the outbox, in typing order with the held lines, with a notice naming it ("not read by the agent — sent now: «…»"); the server backdates each re-sent message to its accept time (note_handed_back), so a "yes" cannot confirm past a later "wait" — that is what makes the send safe. After a stop, an unclean end or a lost leftovers answer it goes back into the prompt in typing order, named ("not read by the agent — back in the prompt"). A stop or hold leftover is never sent, and once such a word was typed or handed back in the turn, every line of that turn comes back, before it as well as after it, named ("not sent — «wait» was typed during the turn; back in the prompt: …") — and with it (r4) the whole re-send chain still waiting in the _outbox, which is listed first. Leftovers that are sent go into the _outbox in typing order with the held lines and leave one at a time, each as its own turn. Typing order (_in_typing_order): a text typed twice gets each occurrence's own index, and a returned text takes the last unmatched occurrence (r4: the agent reads in order, so the earlier occurrence is the read one; identical texts are order-indifferent among themselves); an item not typed this turn (another client's, an earlier turn's) comes first. Known limit (r5): the typed list mixes held, injected and restored lines, so a text typed as a held line and again as an inject the turn read hands the held one the inject's later slot — identical texts, order only. Hand-backs follow one rule (review r10): a duplicate is acceptable, a loss is not. Each line the agent accepted during the turn is tracked as a typing until it is back in the prompt. A list the agent returns (a cancel's undelivered, the leftovers) is matched one for one, in typing order, onto those accepted typings, which are then back. Every returned text is put back, matched or not, so another client's identical line is never lost, and a line put back after a timeout may show twice. A local hand-back ("may or may not have read") puts back only the accepted typings no list has returned, so the same accepted typing never shows twice. Sent after the reply: held lines (those that never reached the agent, or that the inbox queued for a reason other than the feature being off) and, since r2, the agent's leftovers.
