Durable sessions & real turn cancellation

core/sessions.py · core/turns.py — 2026-07-11. The two things that stood between this agent and being a daily driver: conversations that survive a device switch, and a way out of a wedged turn that doesn't involve restarting the process.

1. Durable server-side conversations

The gap. History was entirely CLIENT-carried — the web UI's localStorage, a Slack thread, or a manual workspace/save zip. Switch device or clear the cache and the conversation was gone; each client held a different fragment, so a conversation started in Slack could not be continued in the web UI. Ironic, given cross-session MEMORY is this agent's proven strength (Track B: 98% recall vs 0% control) — the memory substrate persisted while the conversations themselves did not.

The shape. One JSON file per session under $GHOST_HOME/system/sessions/: {id, title, created_at, updated_at, messages}. Sessions live entirely in the API layer — the chat route merges stored history into the request before handle_chat and appends the turn after it returns — so the agent's turn logic is untouched by this feature.

The merge contract (merge_history)

Pass session_id in the /api/chat body and the SERVER becomes the source of truth for history. It tolerates both client styles, which is what makes adoption incremental:

⚠ Rewritten 2026-08-17/18 (§4BU). The thin/fat classifier this section used to describe is GONE, along with the "used as-is rather than appended" rule and the "everything past the stored prefix" slice — that slice was itself the doubling defect (it re-appended already-stored messages whenever the merge inserted anywhere but the end).

There is now one rule and no thresholds: longest-common- subsequence alignment of (role, content) against the stored history, then stored, plus whatever of incoming is not already accounted for. Two invariants hold by construction — nothing stored is ever dropped, and nothing already stored is appended twice. Client-side assistant messages are dropped from the persisted tail (assistant turns originate server-side); in the cap-evicted PREFIX, which reaches the prompt only, a complete reply is kept and only a stub the client itself marked *[Aborted]* is dropped. A tool result whose calling assistant was dropped goes with it, because an orphaned tool_call_id is persisted and then poisons every later turn.

merge_history_detail() returns (merged, new_tail); the route persists the TAIL, never a slice of the merged list. The reply is persisted even when the tail is empty (a client re-sending an already-stored history used to have its reply discarded forever). Omit session_id and behaviour is exactly as before (fully client-carried), so every existing client keeps working untouched.

Bounds & safety

  • Session ids are opaque tokens ([A-Za-z0-9_-]{1,64}) — a path-traversal guard, since the id names a file.
  • 200 sessions (least-recently-updated evicted); 400 messages per session (the most RECENT system messages (§4BU: keeping the oldest evicted the CURRENT prompt) + the newest tail kept, mirroring the agent's own 500-message cap).
  • Malformed messages are dropped rather than persisted (a corrupt session would otherwise poison every future turn that loads it); tool-call plumbing (tool_calls / tool_call_id / name) IS preserved so a resumed conversation's tool pairing stays intact.
  • Every method degrades (None / [] / False) rather than raising into a request; a corrupt file reads as absent.
  • The streamed-final-generation path bypasses the finalize tail, so the route reconstructs what the user saw from the SSE deltas (_sse_delta_text) — without it a session would record the user's message and no reply.

Endpoints

POST /api/sessionscreate (optional title); a client may equally just POST /api/chat with a fresh session_id

1b. Hydration tier (2026-07-14)

Stored sessions are now a retrieval source, not just replay state: SessionStore.search_messages(query, limit=5) keyword-searches the most-recently-updated _SEARCH_MAX_SESSIONS (50) sessions and feeds MemoryBus._fetch_session as the fifth hydration tier (see bus). Bounded by design: per-file mtime cache (unchanged sessions are never re-parsed), a 2s summaries memo (one glob scan per hydration, not per sub-query), 240-char snippets, and a ≥2-distinct-term floor for multi-term queries so one shared common word can't surface an unrelated conversation. Fail-safe — returns [] on any error. Tests: tests/test_session_hydration_tier.py.

2. Real turn cancellation

The gap. Turns are globally serialized (agent_semaphore = Semaphore(1), #22), so ONE wedged turn blocks the web UI, Slack, and the autonomous project-advance ticks at once — and there was no way out: the interface's /api/chat/cancel only cancels the proxy's buffered stream, so the agent kept working and kept the lock. The only real remedy was restarting the process.

The registry. core.turns.TurnRegistry gives every in-flight turn an identity (its req_id), a handle on its asyncio task, and a cooperative cancel flag. A turn registers itself before acquiring the semaphore, so a request QUEUED behind a runaway turn is cancellable too.

GET /api/turnswhat is running and for how long, plus anything queued behind it — this is how you see WHY the agent appears unresponsive
POST /api/turn/cancel{request_id?, hard?} — request_id defaults to the running turn

Cooperative vs hard

  • Cooperative (default). The flag is set; the turn loop notices at its next boundary, raises TurnCancelled, and handle_chat catches it and returns whatever partial work exists (a clean stop, not a crash). Exiting through there unwinds the async with self.agent_semaphore, so the global turn lock is released — which is the entire point.
  • Hard (hard=true). The asyncio task is cancelled outright. This is the guaranteed release for a turn wedged inside a long upstream call that never reaches a boundary.
  • A queued turn is always hard-cancelled — it has no partial work and no boundary to reach, and killing it is strictly better than letting it start.

req_id collision handling (2026-07-14 bug hunt)

req_id can be a CLIENT-supplied X-Request-ID (the route reads the header), so two overlapping requests can carry the same id. The old registry overwrote the live entry unconditionally and popped by key, so /api/turns hid the first turn, cancel("X") flagged the SECOND turn (cancelling B killed running A), and A's finally evicted B's entry. Fixed: register() never clobbers a live entry — it uniquifies the new key (X#2, …) and handle_chat adopts the effective id; unregister() is IDENTITY-CHECKED (pops only if the stored object is this turn). Tests: tests/test_turn_registry_collision.py.

Streaming tail stays cancellable (2026-07-15)

The STREAMING final-generation path returns a generator from inside the semaphore block, so the actual upstream stream runs while the client drains it — after handle_chat's finally has already run. That finally unregistered the turn the instant the generator was returned (before a single token streamed), so the tail was invisible to /api/turns and uncancellable. Fixed: the streaming path wraps its generator so the unregister is DEFERRED into the wrapper's own finally (runs when the drain completes), and the stream loop now checks is_cancelled each chunk — a cooperative cancel stops emitting mid-stream and finalization still runs on the partial text.

The agent_semaphore is deliberately not held across the drain (diverging from the original fix sketch): stream_chat_completion already counts foreground_tasks for the whole stream, so the single upstream slot isn't stolen, whereas holding the permit until the generator drains would couple turn serialization to client read speed — a stalled reader would block every later turn, a worse failure mode than the one being fixed. Tests: tests/test_streaming_tail_cancellable.py.

2026-07-27 audit fixes

  • merge_history compounded the whole conversation every turn (HIGH, closed). The fat-client detection required the stored history to be an exact prefix of the client's replay; on any divergence it fell through to stored + incoming, so the entire replay was appended again — and append_turn stored it. Measured: 5 → 11 → 19 → 29 messages over four turns (quadratic), until the 400-message cap filled with duplicates and the LLM context was dominated by repeated history.
  • Two realisable triggers, both permanent once hit: (a) an aborted stream — the server persists the full reply before streaming, so a client that disconnects mid-reply keeps a truncated copy and every subsequent turn diverges; (b) the message cap — once a session exceeds MAX_MESSAGES_PER_SESSION the stored copy loses its oldest messages, so the client's replay can never prefix-match again.
  • ⚠ The fix described here — "tolerate divergence in at most the final message; treat the replay as authoritative and REPLACE the stored copy" — was itself removed in §4BU. A one-message tolerance means the SECOND aborted stream in a session breaks detection permanently, and "replace the stored copy" is a licence to delete durable history: a stale tab missing middle messages had them deleted. Both were reproduced. The current design (above) never replaces and never drops; it appends only the unmatched tail. Regression tests: tests/test_sessions_merge_properties.py (property-based, driving the real SessionStore.append_turn with append-only clients) and tests/test_sessions_and_cancel.py.

The stream prefix length 2026-09-29 §4KP

A streamed reply can open with the stream prefix — the prior turn's text and a one-shot correction banner — which is not that generation's text; a re-render cuts leaked reasoning only AFTER it. The chat route persists the prefix length with the reply (append_turn(..., prefix_len)) as the assistant message's prefixLen; _clean_messages keeps it only on an assistant message, as an int within the content's length. GET /api/sessions/{id} returns it, so a reply adopted from the server (another device, a session switch, a reconcile) re-renders with its banner. It is a CLIENT key: the route passes the merged history through model_messages, which drops it, before the agent sees it. Matching (_msg_key) is role + content, so it never affects the merge.

§4PP (2026-10-16): Slack's conversation key is not a session

The Slack bot sends session_id: "slack:<thread or dm>:<user>" so the agent can keep a state of work across the turns of one thread or DM (§4OE-1). The bot sends the thread's history itself, so the server store has nothing to add. The chat route passed the id to the session store anyway; its colons fail the store's id charset, so every owner Slack turn logged "session NOT persisted … this conversation is not durable". That was a false alarm: nothing was lost. The route now leaves ids that start with slack: out of the session store (routes.is_conversation_key_only), and the agent still receives the id for the state of work. Making the store accept the id would have been worse: every DM would merge one rolling 400-message history into each DM request. The warning now means what it says: a web conversation that is not being saved. Pins: tests/test_4pp_temp_documents.py.

Queued messages: a message sent while a turn runs 2026-10-29 · ON

Turns share one model slot, so a second generation cannot run beside the first. core/queued_messages.py routes a message that arrives while this conversation's turn is running. The system routes it without the model, checking in this order:

#CheckPath
1Not the turn's own sender: another conversation, or another kind of sender (owner vs probe). This is checked first, so a stop word or a status question from anyone else never reaches the turn. Every miss gets the same reason, so the reply does not reveal that someone else's turn is live. Member turns and Slack conversations (slack: session ids) have no inbox (operator, 2026-10-28: Slack stays as it is), so such a message always waits for its own request. A member stays a member when probed.queue
2Empty, or longer than MAX_TEXT (8,000 characters) after the surrounding whitespace is stripped. The route posts that same stripped text, and the inbox refuses anything longer, so a message is never cut.queue
3The whole message is a stop word: stop, cancel, abort, σταμάτα, άκυρο. "cancel that" is not one, because it may name a background job. This also works on a turn whose streamed final is draining. A turn still waiting for the turn lock is not reached: cancelling one ran its cleanup beside the running turn (review r5: a member turn's scope and read budget were reset). A hold still withdraws its yes (below).cancel (cooperative; returns undelivered)
4A status question and nothing else ("how's it going?"). With anything more ("how's it going? btw use metric units", or a digit, symbol or emoji such as "are you done? 🛑") it is an instruction and goes to the model as an inject. Only spaces, punctuation and invisible characters count as nothing more.status: the system answers from the registry with elapsed time, step, the tool running now and for how long, and tool calls finished
5A rule command (the system answers those at the start of a request)queue
6The turn no longer accepts messages (its loop has exited)queue
7Everything else, including a bare yes or noinject

The queued row's label. The model reads an injected message as a user row that starts with QUEUED_LABEL ("[Sent by the user while you were working]") and then the user's text. Every detector the loop uses to recognise its own rows (steers, tool results, the state block) is anchored at the start of a row, so none of them can take a queued row for one of its own, whatever the user typed. Rounds 1–3 of the review used a word filter for this instead, which sent such text back as a normal message; it leaked in every round (zero-width characters, combining marks, markdown) and was removed. Only owner and probe turns have an inbox, and the same text sent as a normal message reaches the model the same way. The system knows a queued row by its _queued key, never by the label; stored history keeps the user's own text without it.

Queue means the client sends the message normally, and it runs after the turn (the behaviour before this feature).

Where an inject is read. The loop drains the inbox right before it rebuilds the request for the model. That point comes after every exit of the step (strike cap, force_stop, terminal tools), and nothing between it and the model call leaves the loop, so a drained message is one the model reads. The context-overflow recovery rebuilds the prompt from a few rows: the request, the newest tool result (cut), the turn's queued rows and an alert. The request is the row handle_chat marked with a _request key, carried as the model saw it (images as native parts or the saved-file pointer, captured before the injected blocks), and the loop keeps that marked row afterwards, cut as sent. Before 2026-10-28 the recovery guessed the request from rendered text, and in the launcher's layout it never carried it: on the first turn it took the pinned <session_context> head, later the tool result, a steer, or on a second overflow the first recovery's own alert (operator: fixed for every request, not only queued ones). Compaction keeps the marked row: the summarising prune keeps it beside the conversation's first message (it had summarised a follow-up request away), and the deterministic ladder and the tail cap protect it as the current request instead of the newest user row, which can be a steer, an effort note or a queued message. Queued rows are protected too (r7: they lost the protection they had as the newest user row): the summarising prune keeps them in both of its branches (r8: the few-rows branch dropped them and the main branch summarised them, or dropped them when the summariser failed, while they stayed booked as read). The main branch keeps the newest queued rows up to 8,000 characters, each measured as at most 4,000 (what the overflow recovery would send) but kept whole, stopping at the first that does not fit (s3-r7); the tail cap shortens a kept row, with the paste note, only when the size needs it (r11: cutting it here lost its end for good, since the pruned list replaces the loop's messages). Older ones go to the summary; when the summariser fails every queued row is kept, and an error after a summary came back (the episode archive) is no longer reported as a failed summary (r10/r11). Kept rows sit among the anchored findings in the order they were written, before the recent window (r9/r10: placed after a later finding, a queued instruction read as the newest one). L3 never cuts them, and the tail cap cuts one only as a last resort, as a paste. The text guess remains only as the fallback when the row is gone anyway (a request larger than the whole window, pre-existing). The mark is removed from the caller's message dicts when the turn ends, and the one upstream sender built from the loop's own rows (best-of-N) strips internal keys. Only the server marks rows: _queued, _request and _rendered sent by a client are dropped at request start, and persistence never stores them. Queued rows are carried because they were already booked as read: the newest first, up to 8,000 characters in all, each cut at 4,000 with a truncation marker; later steps carry every queued row again. The inbox closes when the loop exits, before finalize (the verifier and Perfect-It run there). It also closes in handle_chat's finally, before a streamed final drains. A message accepted but never read becomes a leftover for that conversation and kind of sender. Leftovers are kept in memory: at most MAX_PENDING per conversation, 64 conversations, for 30 minutes. A restart drops them. The client takes them from /api/turn/inbox/leftovers and sends them normally.

What the model is told (step 2). Every line that names the request reads one request-scoped record of the messages delivered so far (queued_messages.delivered(), a ContextVar that handle_chat starts empty at registration and restores in its finally; the drain adds each text). Before anything is delivered the wording is exactly as it was. After: the state block no longer says the user "sent NOTHING new" or quotes the request as "(unchanged)" — it says the user sent N messages while the model worked (the rows starting with the label), that they are part of the request, and how they combine with it (a correction or change replaces what it contradicts, an addition is done as well, a message saying stop or "instead" wins). The same sentence (added_line) follows "THE REQUEST YOU ARE ANSWERING" in every alert built by _which_request_line (forced reports, the budget and deadline alerts, the report-written alert, the thinking-loop steer) and the AUTO-DIAGNOSTIC REMINDER; the refute directive no longer says "no new message has arrived". In the unpinned layout the state block folds onto the newest user row, which can be the queued row: its carrier label then says it is the user's mid-turn message, part of the request, instead of pointing away from it. The verifier's request view and the tool-output summariser's "The user asked" use current_ask (the request, then each added message). The state block's held first copy (§4RC anchor) keeps its original words — it sits before the queued row and was true when shown; only the trailing block changes. The thinking-loop no-think retry matches its steer by exact text; it accepts the steer as built for any number of messages delivered so far, so a message drained right after the steer keeps the retry (review s2-r1: it was lost). The streamed final drains after handle_chat's finally: the stream re-enters the request's deliveries (set_delivered) with its other contextvars, so its forced-final retry and verifier still name them. In the unpinned layout a tool row's label also names the added messages; the queued-row label is used only once something was delivered (a request that merely starts with the label text is still the request). The added sentence says that a yes or a confirmation sent this way confirms no pending preview, so the model asks for it again (the confirm gate reads the request's own message, and refuses the request that showed the preview); a request that started — registered, or, re-sent from a hand-back, was first accepted — before a preview was stored cannot confirm that preview either (_started_before_preview, s2-r3: a mid-turn yes handed back and re-sent confirmed a preview made after it was typed; this also covers a yes sent while the preview's turn was still running); with several messages it adds that an older one may survive only in a summary. The first message's label never changes within a request (a queued row is never the first message; s2-r2: a request starting with the label text flipped it — a re-prefill). The verifier's request view fits its 4,000-character cut with the request keeping at least half the room and the added messages the rest, newest first, each cut at its end (s2-r2: a pasted log pushed the request out); once anything was delivered, the rules the request itself triggers stand down for that turn — the word, line and sentence caps, strict JSON, an exact phrase, a number-only answer, the reply-language rule and the "a source you actually read" rule (also in the claim-binding class checks): the request's constraints are no longer known (a later message may replace a cap, scope it to one part, or ask for more), and three rounds of merging the texts each misread one of those (first cap wins, newest cap wins, the two-part rule, pasted logs; s2-r1…r4). The checks that do not read the request keep running — the no-answer fallback, a raw tool dump, narration only, empty evidence — with the request and its additions, which there can only excuse (s2-r5: with the LLM judge off they are the only text verdict). The vision verifier judges a picture against the request and its additions; the pre-send regeneration "in the user's language" stands down like its turn-state twin; the claim-binding topic check reads the user's words without current_ask's own header (s2-r6: the header's 'added'/'work' became subject words). The vision verifier's symptom is cut to its 1,000 characters with the additions kept inside (s2-r7). The finalize start-with hoist — which deletes text — reads only a project's stored start-with once something was delivered (s2-r7: the request's own deleted text an addition asked for); placing a correction or digest below an opening the reply does start with still follows the request's phrase (s2-r8: clearing it buried the opening). The EXPLICIT USER CONSTRAINTS block and the one-shot constraint steer say, once something was delivered, that they come from the first message and a later message replaces what it contradicts; the added sentence says it too, for the step that first reads the message (the block is built before the drain). The tool-output summariser gets the request whole and the additions bounded to 2,000 characters, newest first, saying how many earlier ones are not shown. Previews carry a monotonic stamp, so the "started before the preview" check compares one clock (s2-r4: a wall-clock step skewed it).

Compaction and fallbacks (step 3). A row the user sent mid-turn (_queued) is never taken for the request. Every reader that fell back to "the newest user row" finds the turn's marked request row (_request) first, and without the mark (it is removed when the turn ends, before a streamed final records) skips queued rows: the trajectory's recorded request and its step count, the link-grounding haystack (this turn's narration before a queued row no longer vouches for an invented link), the prior-turn evidence when the request text matches no row, and the assistant text before this turn (queued_messages.request_row_index for the shared case). The L4 emergency prune — whose output replaces the turn's messages — keeps the marked request and the queued rows (newest first within the summarising prune's 8,000 characters, each whole, stopping at the first that does not fit so no kept row is older than a dropped one) beside the newest user row, instead of the newest user row alone. (Level 4 is not reached in production today: the loop calls the ladder with max_level=3.) When the summarising prune lifts the request out of the middle beside the goal, the summary row under it says it may include turns from before that request, not only work done on it, so earlier turns do not read as steps on this request (one wording, true after any number of prunes; the archived episode keeps the plain summary). The summarising prune keeps the newest queued rows verbatim within the same budget and stops at the first that does not fit, so every summarised queued row is older than every kept one, an earlier summary row is never anchored (it goes back to the summariser, s3-r8: anchored, it sat below the new summary), and no finding or tool result older than the newest summarised queued row is anchored or hoisted below the summary either (s3-r9) — nothing kept below the summary is older than a summarised message the user sent mid-turn (an ordinary user row from an earlier turn does not move this cut: that ordering is older than queued messages, and the summary's note already says it may hold turns from before the request). When the summariser fails nothing was summarised: every queued row is kept, the anchors are picked as without queued rows, and an earlier summary's text stays in the failure row (only real summary text — an earlier failure's error is not carried, s3-r11; read from the summary row's own _summary_text key, never from its content — by the failure carry and by the next summariser alike (s3-r13) — which the tail cap may cut or a tool row may imitate — the _summary keys are stripped from client rows like _queued, s3-r12). A summary of another member's labelled words carries the mark _foreign, so a later prune that re-summarises it is not archived into the owner's memory either (§4KY, s3-r14), and a middle holding only a failure row that carried nothing is not sent to the summariser (it is an error, not history), which then carries the same note when the request was lifted (s3-r7: skipping a long row kept an older "use A" below a summary holding the newer "instead use B"). A blank summariser reply counts as a failed summary on every request: every queued row is kept, nothing is archived, and the row says the summary was unavailable (s3-r5). Link grounding leaves the text of every assistant-role row after the request out of its haystack — the summary and the assistant-role [ANCHORED] rows included: they copy this turn's narration, and their text prefix is one the model can write (s3-r2). Tool rows stay in: they copy tool output.

The owner's words and recording (step 4). A message the user sent mid-turn is recorded; it opens no gate. utils/provenance.note_added_user_message keeps it per request, and added_user_messages() reads it back. Every gate that grants something reads the request alone, like a confirmation. That covers the owner-fact gate (refuse_unless_user_said), the egress gate (an identifier or "my files" may leave), a project constraint's origin, "keep this video", a dictated lesson, the lesson generality text, the notify steer and backstop, the recent user messages (the stale-year rule, "call it Snake") and the project-build fallback. A mid-turn yes never confirms a preview of the same request. Why: in s4-r3 and s4-r4 each widened gate opened on a mid-turn refusal ("don't send my files anywhere!", "never open that site again", "don't ping me"). Keyword gates match the refused word, and the statement parser accepts reported speech ("my friend says I have diabetes"). Only these read a mid-turn message:

  • the fact ledger's "you said" label;
  • a "no", which withdraws this conversation's live previews (it only ever withdraws);
  • the project-create gate, which refuses when the request or any mid-turn message says not to create a project (deny only: nothing sent mid-turn reverses such a "no", s4-r2);
  • the sampler, which treats every step after a delivery as a tool step;
  • the graders of a past turn: a turn whose trajectory carries extra.queued_messages (queued_messages.changed_mid_turn) is recorded but never graded, judged, replayed or promoted. Its request alone is not what it answered. The census leaves its no-tool detectors unmeasured and the gold sample never draws it, though it stays the earlier context of the turn after it. The reaction judge and the two shadow judges (rubric, knowledge) skip it, and replay refuses it. A correction on the next turn never promotes it to FAILED, and once its trajectory is recorded the correction judge is not called (a streamed turn records late; the promotion re-checks). s4-r6…r8 tried to fit the messages into each reader instead. Each reader got them wrong in its own way: the judge's next message, head cuts, redaction lengthening a fitted text, a mid-turn "how are you doing?" muting a detector, and the next turn's walk taking the mid-turn row for the whole request.

Within the turn, the smart-memory arc, the photo-name lookup and _users_own_texts skip queued rows. Clarify-first reads the request alone: a one-token follow-up still gets its clarifying question even when a longer message arrives mid-turn (s4-r6: a stand-down lifted the block on "no, don't make another image"). On the next turn the message is an ordinary earlier user row of the conversation, as it would have been had the user waited. A new request under a reused request id starts with no additions. A sub-agent's trajectory records only what it received itself (s4-r1). The turn-scratch cleanup reads the request plus the added messages of the root request (_request_with_added). The trajectory keeps user_request and adds extra.queued_messages from its own request only. Kept as they are on purpose: reply language and the request rules (they stand down after a delivery, step 2), constraint extraction (the constraint block says the user may have changed them; merging texts flip-flopped), recall (the model can call it), images (the inbox takes text).

Confirmations. A bare yes is injected, not queued. Inside the request that showed a preview, a yes can never confirm it. Queued, it would run after the turn and could confirm a preview the user had not seen when they typed it. The other way round, a message that holds or refuses ("wait — keep project X", "stop", "no") withdraws confirmations by time (tools.memory.note_queued_withdrawal): the owner's hold is noted for its conversation when the inbox accepts it (monotonic clock), whatever path it takes and whether or not a turn is running, and every owner request of that conversation that registered before it (note_request_start, noted at registration, before the turn lock; removed when the turn ends) can no longer confirm (_confirm_allowed refuses). That covers the running turn, one whose streamed final is draining, and a "yes" queued behind the turn lock; a request sent after the hold is untouched. Review r5 found that routing the hold to one turn missed the others. Holds from another conversation, a member, or a probe count for nothing (only the owner can confirm). A message handed back keeps its accept time. Messages a turn accepted but never read go back to the client to send as normal requests (leftovers, the undelivered of a stop or of /api/turn/cancel). The server remembers when the inbox accepted each one (note_handed_back, owner only, 30 minutes), and a request that re-sends one starts at that time (note_request_start matches its text, case- and accent-folded, text parts of an image message included; each hand-back of the same text keeps its own time and is used once, oldest first — r8: "yes", "yes", "wait" let the second re-sent yes through). So a "yes" sent before a "wait" still loses to it when it comes back as a new request (review r6/r7: deciding by the text which messages look like a yes missed qualified yeses, long ones and the pasted token). Backdating only ever removes authority. Every stop word is also a hold ("σταμάτησε" stopped the turn but withdrew nothing, r7), and so is pressing Stop (/api/turn/cancel on an owner turn, r8). A refused re-send is told that a hold came after the user first sent it. Injection can only take authority away.

Registry. ActiveTurn carries kind (who an inbox post must be), inbox, accepting, and progress fields (step, tools_now, tools_since, tools_done). find_running(session_id, kind) finds the running turn of the conversation for that kind of sender, never through current(). It also finds a turn whose streamed final is draining, so a stop word or a status question still reaches it.

Session. The agent records the messages the turn read in body["_queued_delivered"], and the chat route stores them before the reply, as [u1, q1, reply]. The route first pops any client value of that key: a client could otherwise store forged rows (a system row in the middle of the history) or crash the persist. The row's _queued and _queued_at keys are dropped by the per-step request rebuild, which keeps only role and content. The adaptive best-of-N path (off by default, GHOST_TTS_ADAPTIVE_BON) sends raw rows.

Stopping a running tool (step 5). POST /api/turn/interrupt with {"session_id"} stops the tool call or calls the conversation's turn is waiting on right now. The turn goes on, and the model reads that the user stopped them. The sender is checked like the inbox: same conversation and same kind, never a member or a Slack conversation. The route answers 200 with the tools running when the stop arrived (a call that already finished is not listed). A file operation (any file_system call, reads and deletes included) is never cut: it finishes, and its real result, or its error if it raised, reaches the model with a note that the user asked to stop while it ran (review s5-r9: a stop that landed on a batch's only call, a write, had left no trace for the model). The note goes into the model's copy of the tool message only. The result and the turn's own record of its tool calls are untouched, so the failure context, the outcome preview, the verifier and the empty-reply fallback (which quotes the last tool result to the user) see the real result only (s5-r10 to r13: a note put in a shared value reached each copy of it, and each fix missed one). The trajectory row records what the model saw, so it keeps the note at the end of that result; its readers judge a result by its head. A prompt rebuilt after a context overflow keeps only the newest substantive tool result; when that result is a hit call's, it carries the note, every time: the record row of a hit call holds the note in an internal key, like the other internal keys on those rows, and the rebuild re-adds it (s5-r15: matched by call id, a stream that left the id empty put the note on another call, and a second rebuild lost it). A batch-dedup copy of such a call carries the note too, like its original. The route answers 404 when this sender has no running turn, and 409 when nothing is running, a stop was already sent for this batch, or the turn is being cancelled. Stopping the whole turn stays /api/turn/cancel.

How it works: each tool batch gets a utils/tool_stop.ToolStop. Each call runs inside _stoppable_call, which binds the stop in a ContextVar for that call alone, so its task and worker threads see it and the loop's own context never does. It also notes when the call really started and while it runs, and never starts a call once the stop is requested. The batch waits for its calls with _gather_stoppable; with no stop bound (feature off) this is exactly gather(…, return_exceptions=True). On a stop:

  • Calls that finished before the stop keep their results. A call the stop reached is stopped, whatever it returns: one that swallowed its cancel, one its killer made return its own error before the batch's next poll, one that raised its own cancel. The stop records the calls running at that moment.
  • Calls still running are cancelled. The batch waits up to STOP_GRACE_S (20 s) for them to unwind, and a browser call holds its profile lock until its runner returns.
  • Calls that have not started never run. That covers a vision_analysis read waiting for the other calls, a later call in an in-order chain, and any file call after the one in progress. A file operation in progress is never cut; its result or error carries the stop note.

Three tools really stop their work, and say so only when the kill is confirmed:

  • a sandbox job: the supervisor's poll loop kills its process group, and the call returns exit 130;
  • the browser runner: while its call holds the profile lock, the only runner in the container is this one, so it is killed by its exact command line (python3 -u .browser_runner.py …, nothing that merely names the file);
  • yt-dlp: the transcription download polls each second and kills its session.

A worker thread notices the stop at its next poll, after the batch has moved on. Each killer therefore arms while it can still act, and the batch waits up to KILL_CONFIRM_S (8 s) for armed killers to settle before it writes the results. The browser kill retries for a runner that was just launched, and a browser call reached after the stop never launches one. The model then reads one of three results. "INTERRUPTED BY THE USER … and it was stopped" is used only after a confirmed kill. Otherwise it reads "… its output was discarded; work it started may still finish in the background". A call that never began gets "NOT RUN". Each result tells the model not to run the call again unless the user asks. It is an UNRESOLVED ToolOutcome with reason user_interrupted, so it is neither a success nor a failure:

  • It is never memoised, so the user's later re-run really runs.
  • It is never recorded as applied, so a re-sent setter is not refused as "already applied".
  • It is never a passing run for the code-claims ledger.
  • It draws no strike. Every reader of "unresolved" asks tool_stop.is_user_interrupted (the reason, or the text of a stored row) first, so it is never "still running": the multi-call summary lists it as STOPPED BY THE USER, never as SUCCEEDED; the project work log marks the command "[stopped by the user]"; Perfect-It skips a turn whose tool call the user stopped (it is not a finished task); the empty-reply fallback opens "The user stopped the last tool call…", never "Process finished successfully."; a batch-dedup copy of a stopped call reads its original's kill; the code-claims ledger does not count a stopped page load as a run of the page; the evidence gate and the turn-state check count a stopped retrieval as empty ("stopped by the user"), not as evidence; the edit-churn brake, the constraint steer, the no-progress breaker and the search counters ignore a stopped call; the census reads a stored stopped row as unresolved, not as a success.

Kills are recorded per call (the batch index, a second ContextVar), never per tool name: two calls of one tool, one killed, are reported apart. Background work a call spawns (spawn_bg, e.g. a delegated sub-agent) never inherits the call's stop. A call that ran may have changed something before it stopped (world_changed). Other tools (search over Tor, deep research, image generation) are cancelled on the asyncio side only. The image node does stop its render when the request disconnects, but that is not confirmed back, so the wording stays "discarded". Pins: tests/test_tool_interrupt.py.

CLI (step 6b). In the interactive CLI (interface/externals/cli/ghost) the reply streams on a background thread, and the main thread keeps a live prompt under prompt_toolkit's patch_stdout. Completed blocks print into the scroll as before. The open block and the spinner are drawn by prompt_toolkit as part of the prompt (not by a rich Live, whose cursor-up erase would hit the prompt), in a frame it erases when it exits. The final transcript matches the old path line for line. Enter while a turn runs posts the line to /api/turn/inbox, and the CLI shows the result by path:

  • inject: a dim "queued: …" line.
  • status: the system's answer, shown under the question.
  • cancel: the Ctrl-C path. The partial reply is kept and the undelivered texts go back into the prompt.
  • queue: held, then sent as a normal message after the reply (but only after a normal reply; see below). A stop or hold word is never held: the agent's own lists are copied into the CLI and pinned equal to _STOP_RE and _DENY_RE. Such a word may be answered queue because the turn has not registered yet or waits behind the lock, and sent later it would be a new request, so it goes back into the prompt. And if any line typed during the turn is a stop or hold word, every held line of that turn comes back too, typed before the word as well as after it, named in one notice, never sent on its own (operator decision, review r8: a stop or hold sent later means something else). An HTTP error, or a connection that was refused or timed out while connecting (never sent), is held the same way. Any other failure, such as a read timeout, may come after the agent already took the line, so the line is never sent again on its own: it goes back into the prompt with "the agent did not answer — it may have received this".
  • Another turn: the agent routes a line to the conversation's latest running turn, which may be an earlier one still finishing. If the answer's request_id is not this turn's (a probe prefix and a #n reuse suffix are allowed), the CLI says so and keeps streaming. An inject was accepted by that turn, which may act on it, so it is not put back during the turn: the notice says the earlier turn received it. This client cannot see that turn end (another client may stop it and take its inbox), so unless that turn's undelivered or the leftovers return it, the line comes back at the end of this turn, named "may or may not have read", even after a clean reply. A status answer was not accepted, so the line goes back into the prompt. A stop word is echoed (never put back) and the CLI cancels this turn by its own id. The earlier turn's undelivered comes back named ("the earlier turn's unread messages: «…»"), minus any line already sent as a message in this turn or the one before it, one for one (a message the CLI sent as restored lines joined by newlines counts line by line). A line typed during this turn is never dropped by that match: the earlier turn accepted it, so it comes back.
  • No inbox: the feature is off (queued messages are off), or an older agent answers 404. The line is never sent on its own, because a "stop" or "wait" would arrive later as a new request. It goes back into the prompt after the reply instead, as the CLI behaved before.

After each reply the CLI takes /api/turn/inbox/leftovers. A leftover is never sent on its own (operator rule, review r4, for both clients): the agent accepted it, but no turn read it. It goes back into the prompt in typing order, with a notice naming it ("not read by the agent — back in the prompt"). Hand-backs follow one rule (review r10): a duplicate is acceptable, a loss is not. Each line the agent accepted during the turn is tracked as a typing until it is back in the prompt. A list the agent returns (a cancel's undelivered, the leftovers) is matched one for one, in typing order, onto those accepted typings, which are then back. Every returned text is put back, matched or not, so another client's identical line is never lost, and a line put back after a timeout may show twice. A local hand-back ("may or may not have read") puts back only the accepted typings no list has returned, so the same accepted typing never shows twice. Only held lines are sent after the reply: those that never reached the agent, or that the inbox queued for a reason other than the feature being off. Sending them needs positive evidence (operator rule, review r5): the turn ended normally, with the stream's own [DONE], a non-empty reply and no stop signal, and the leftovers call answered HTTP 200 with a body. Per-turn state is reset at the very start of the turn, before anything can escape, and anything that escapes the stream counts as unclean, whatever the stream had recorded. Any other ending puts back into the prompt everything typed during the turn that is not known to be read: held lines, and the lines the inbox accepted, named. That covers an empty reply (a hard stop of a turn that streamed nothing sends only [DONE]), any stop, an error, a lost stream, and a leftovers answer that never came or was not a 200. After any stop, the lines the inbox accepted always come back, deduplicated against the cancel's undelivered: even an answered cancel proves nothing, because another client's cancel may have emptied the inbox into its own answer (review r6). A line the agent did read may therefore come back; the notice says the agent "may or may not have read" it. That covers Ctrl-C, a stop word, a turn that errored, and a turn stopped elsewhere (web Stop, /cancel). A stop made elsewhere ends the stream normally, so the CLI reads it from the reply: the reply ending with the agent's _(Turn cancelled: …)_ note, or a hard stop's retract with no reply after it. A clean reply with no text (tool- or image-only) is not a stop, and neither is a reply that merely quotes the note. A stop made elsewhere is always announced. The messages this client sent to the turn are named and put back, because the other client got the undelivered list and this one cannot tell what was read. They come back in the order they were typed, together with any held messages still waiting from earlier turns. The agent hands leftovers out as it answers, so that request gets a 30-second read timeout, and a failure is always reported ("messages sent during the turn may not have been read"), never silent. When the agent cannot be reached, they come back only after a later reply in the same conversation: leftovers are kept per session, so /new, /clear and /resume leave them behind. The agent clears a turn's inbox as it cancels, so a message the turn accepted and had not read exists only in the cancel's answer. If that answer is lost (a read timeout, or a second Ctrl-C), the CLI names every message it sent to that turn, puts them back into the prompt ("the agent may or may not have read" them), and a later leftover of the same line comes back as well (a duplicate, never a loss). A cancel that never left (connection refused) says the turn was not cancelled. One Ctrl-C handler per turn (review r12): from sending the message (an outbox line is taken off the queue only inside it) until the turn is settled, one deferring SIGINT handler is in place, so a Ctrl-C never interrupts the CLI's bookkeeping. It is counted, and the stream loop and the settle read it as a stop. A Ctrl-C pressed while one of the short requests is on the wire (an inbox post, the leftovers, the stop's own cancel) therefore waits until it answers, so no text is lost. For a hung agent, Ctrl-C can give up these waits. During an inbox post a second Ctrl-C does it, and the line goes back into the prompt. During the stop's cancel any further Ctrl-C does it, and the CLI prints "cancel not confirmed" (the cancel has a 3 + 10 second timeout). If the cancel's answer had already arrived, it is used, so nothing it handed back is lost (review r15). The leftovers wait (at most 3 + 30 seconds) is given up by two Ctrl-Cs pressed during it; a Ctrl-C that stopped the turn does not count toward them. A stop or an error that came before any reply text puts the message back into the prompt, named "the agent may or may not have received it". If the agent refused the request with an HTTP error status, it says "the agent did not take it" instead. If the cancel then finds no running turn and the stream had delivered nothing yet (no text, reasoning, retract or tool status), the CLI says the agent may not have registered the turn yet and may still run it, rather than "already finished" (reviews r15, r16). Known limit: a stop made elsewhere before any output ends with only [DONE], which looks exactly like a clean tool- or image-only reply. That message is not put back, because Enter would re-run a finished request; it stays in the scrollback. Once the cancel has answered, its wait is over: a Ctrl-C while its undelivered are handed back is only counted (review r14). Closing stdin mid-turn also stops the turn. Every line in hand stays on the client object until the step that puts it in the prompt or sends it has completed: held lines, leftovers the agent handed out, accepted lines not yet returned, the prompt's handed-back text, and the message being sent. So if anything still escapes, they all go back into the prompt, named, before anything is printed. Nothing is sent and nothing carries into the next turn. A Ctrl-C counted before the request leaves means it never leaves (review r13): the CLI prints "⛔ stopped — not sent" naming it, asks for no leftovers (there was no turn), takes it out of the history and puts it back where it came from, the prompt or the head of the queue of held messages (which then comes back into the prompt, in order). The same undo runs in classic mode if the request never left. A SIGINT that reaches the busy prompt itself is handled like the Ctrl-C key. Only the turn whose prompt is running can end it: a stream thread that outlived its stop cannot end the next turn's prompt. In the busy prompt, Ctrl-C's /api/turn/cancel undelivered also goes back into the prompt. With GHOST_CLI_BUSY_PROMPT=0 it does not: that path never posts to the inbox, so anything there came from another client on the same session. /interrupt calls /api/turn/interrupt: 200 names the stopped tools, 409 says nothing is running, and 404 says there is no running turn (or that the feature is off). Esc is not bound, because it is the prefix of Alt+Enter and of the arrow keys, and stopping a tool cannot be undone. Other slash commands typed during a turn go back into the prompt and wait for the reply. One-shot mode (-p, piped stdin) is unchanged. GHOST_CLI_BUSY_PROMPT=0 restores the old blocking stream. Pins: tests/test_4rz_cli.py.

Web client (step 6a). The interface proxies /api/turn/inbox, /api/turn/inbox/leftovers and /api/turn/interrupt like /api/turn/cancel (interface key required, the agent's status and body passed through). While this tab's chat turn streams, Enter posts the composer's text to the inbox instead of /api/chat (the send button stays Stop). The page acts on the path. inject: a dim user bubble labelled "queued", above the reply being streamed. status: the answer as a note. cancel: handled like Stop. queue: the bubble moves below the reply, labelled "sends after this turn" (so does a tab with no session id). The rule: a duplicate is acceptable, a loss is not (review r6a7, the same rule as the CLI). So the page keeps no read/unread accounting: no dedup, no "visibly held" check, no counters. A clean end is a stream that reached [DONE] with no error frame and a reply with text: not reasoning only, and not (or not ending with) the agent's cancel note _(Turn cancelled: …)_. After a clean turn that accepted an inject, the page adopts the agent's session copy, which stores the injects the turn read as user rows ([u1, q1, reply]), and keeps the reply's 👍/👎 key by role and content. Only a clean end sends held texts on its own. Everything else is handed back. All of these go to a tray above the composer, never into the composer itself: held texts after an unclean end; every text accepted during an unclean turn, or during a clean turn whose leftovers call failed ("the agent may or may not have read these"); an inject accepted after its turn settled; a Stop's undelivered; the agent's leftovers; and texts the inbox refused (feature off) or never answered. The draft that Retry/Edit is about to replace goes there too ("your draft before Retry/Edit"). The tray is kept in localStorage for 7 days, one key per item (ghost.queued.restore.item.<id>, the item naming its session). The older single map is migrated on every read: an item with text is kept whatever its shape (a missing id is derived from the item, the same on every run, so a retried migration never copies it again; a missing time is the migration time, and a re-run skips the item by its id, so it is never copied and expires 7 days after the last migration attempt that stored it; when storage is so full that the confirmed list cannot be written, a dismissed one of these can come back once), ids localStorage has held are skipped, and the old key is removed only once every item is kept, in its own key or in sessionStorage. A write to the old key by a tab still on old code triggers that re-read. It shows the session on screen, plus anything kept while the tab had no session id. An add writes only its own key and an Insert or Dismiss removes only its own key, so no write ever rewrites another tab's item, even when a browser serves a tab a stale cached copy. Ids are random (crypto.randomUUID). When localStorage refuses an item, the item is kept in sessionStorage (so a reload keeps it) and retried on every read. The tray then says that this conversation's items cannot be saved, or that other conversations have unsaved items and should be opened before the tab closes. Every retry drops unsaved items that localStorage has already held (the last 500 such ids are kept), so neither a duplicated tab nor an old-code tab brings back a dismissed item. The tray is shown at load, on every session switch, and when another tab changes it. Its notes wait until a session is bound, and it is an aria-live region. Each item has Insert (into the composer at the caret, the owner's own action, and out of the tray) and Dismiss. One note per batch says why the items came back. Nothing leaves the tray implicitly, so Retry/Edit, a voice or upload send, and typing never touch it. Leftovers are asked for only once the turn is over, and they go to their own session's tray even if the owner switched meanwhile. A turn the page lost (unknown), or a failed leftovers call, leaves its session's leftovers owed. Debts are kept per session in localStorage and asked for when a session is shown (at load and on a switch), at the next turn's start, and when a recovery ends. An empty answer keeps the debt while the old turn may still run. It is settled by an answer with texts, by a recovery confirming the end, by a later clean turn on that session, or after the agent's 30-minute TTL. A new turn starting does not settle an older lost turn (a recovery may own it): its texts go to the tray and its leftovers become owed. Settles run one at a time. Sending held texts waits until no turn runs. A Stop whose cancel gives no answer within 20 s settles as unknown. The agent's leftovers carry no accept time or id, only texts. A tool button ("stop the running tool") shows during a chat turn once the agent has answered as on, and calls /api/turn/interrupt. Pins: tests/test_4rz_web_client.py (the proxies, and the page's handlers run under node against a fake DOM).
