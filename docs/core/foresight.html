core / foresight.py — a shadow world model over tool calls

Predicts each tool call's outcome before it runs, then grades the prediction against what actually happened. Phase 1 is strictly shadow: no steer, no veto, no consumer — an instrument measuring whether this agent's environment is predictable enough for foresight to earn one. (Not the workspace subsystem, which is a descriptive state tracker — this one is predictive.)

The gap it measures

Every quality mechanism in the stack is retrospective — the verifier, auto-repair, strikes, loop-breakers, reflection, postmortem all fire after the damage. The risk governor cannot fire before step 6 by construction, and the measured depth curve (17.8% failure at step 1 → 60.6% at step 12) is the price of stepping blind. MCTS turn-start was parked with the comment "OFF until it has an execution-grounded value fn" — its lookahead scored the model's self-prediction of un-executed actions. A transition model built from executed outcomes is the grounding it was parked to wait for.

The training signal costs nothing: predict → execute → compare is self-labelling on every tool call, sidestepping the negative-label supply problem (§4E) that constrains every other learning signal here.

How it predicts (counting, not an LLM)

Retrieval over the agent's own executed transitions, three-level backoff, most specific level with support ≥ 3 wins; Laplace-smoothed failure rate (fails+1)/(n+2). Microseconds per call, zero LLM cost. An LLM-assisted predictor is a later phase if the counting floor proves out.

LevelKeyExample
exact(tool, op, normalized target)file_system | read | src/x.py

Target classes: file extension (ext:py), URL scheme (scheme:https), command head for execute (cmd:python3), dir, redacted, other. A call with no supported level still yields a record (basis:"none") — coverage is measurable, and the resolution becomes the first observation. Cells are LRU-bounded (4096/1024/512 per level).

Where it hooks (agent.py dispatch pipeline)

Two guarded blocks inside _dispatch_and_process_tool_batch: predictions are minted after the batch's metadata is assembled and before Phase-1 mutations run; each is graded in the results loop where the dispatch verdict lands. Batch-dedup placeholders carry no prediction, so a collapsed duplicate is never double-graded. Both blocks are try/except-bounded — a prediction that fails to record must never break a turn.

Invariants

  • One failure definition. The live grade is the dispatch loop's verdict ORed with the shared corpus sniffer (outcome_heuristics.looks_like_tool_error — the prefix check alone misses execute's non-zero EXIT CODE: banners), and trajectory seeding labels with the same package's tool_call_failed. Live rows and seeded rows cannot disagree about what "failed" means; the fence test pins this.
  • Simulation gate. Dream/self-play/subagent turns (read-only skill store) are flagged at predict time; their resolutions update nothing — not the ledger, not the index. The §4J lesson (self-play wrote the production calibration corpus) applied at build time instead of found live.
  • The instrument stays shadow; consumers are arm-gated. Nothing in this module alters dispatch, ordering, budgets, or prompts. The ONE live consumer — the foresight_note arm (see below) — was unlocked by the Phase-2 verdict, ships only as a core/experiments.py arm, and touches only the text of a result that had already failed. Any further consumer must clear the same gate on the live ledger.
  • Applications, not loads. Telemetry counts resolved predictions off the durable ledger (the activation-counter lesson: an artifact on disk with zero applies is a dead read-site).
  • The ledger is durable, so its error strings are redacted like every other durable corpus write (recordings day-files are unredacted by design; this is not one of them).

Seeding

The first prediction of a process kicks off a one-shot daemon thread that seeds the index from the trajectory corpus (newest days first, user_request turns only, capped at 20k calls) — day-one predictions carry real support instead of waiting weeks for live accrual. Self-play and reflection trajectories are excluded as synthetic.

Reading it

introspect action='learning' renders the FORESIGHT block (rows, coverage, accuracy, predicted-fail precision, basis mix, seed state). The verdict belongs to the Phase-2 gate, not that screen:

PYTHONPATH=src python scripts/foresight_backtest.py          # human
PYTHONPATH=src python scripts/foresight_backtest.py --json

The backtest buckets resolved rows by claimed p(fail) and measures each bucket's actual failure rate: DISCRIMINATES needs a ≥ 0.10 spread and disjoint anytime-valid intervals between best and worst usable buckets (≥ 30 rows each, Bonferroni-corrected) — the same bar the depth curve passed and the router backtest applies. Exit codes: 0 discriminates, 1 flat/insufficient, 2 no ledger.

If the verdict is FLAT, the plan STOPS — that is a result, not a failure. This project's history is full of signals that looked usable and measured dead (uncertainty_pressure: 2 distinct values across an epoch; competence separation 0.0023). A consumer built on a flat signal would be another dark module.

Phase 2 result (2026-08-05) and the one consumer it unlocked

The offline replay — run twice, before and after a fresh-eye review fixed two instrument defects that both biased toward a false FLAT (execute had no target so the highest-variance tool collapsed into one cell; seeding ingested never-executed guard rejections with inverted labels) — returned DISCRIMINATES both times. Post-fix: 3,558 graded predictions, actual failure rate monotone in the prediction (0.036 → 0.119 → 0.233 → 0.346 → 0.778), spread 0.310, best/worst intervals disjoint, exact-basis accuracy 0.964 (n=1,835), Brier 0.066.

That unlocked Phase 3: the foresight_note experiment arm. On a FAILED call whose prediction had exact/class basis, support ≥ 3, and at least 2 real precedent failures (the raw cell count carried on the prediction — a Laplace inversion was measured to drift at high support), the treatment appends: "[FORESIGHT] N of M similar past calls failed like this; most common error: … address that cause — do not retry the identical call." The trigger condition is arm-independent at any instant (both arms read the same pre-note-graded index; a working treatment can still drift the trigger rate over time — watch the arm counts), the fired key is context-mutating (Phase 2b fixture isolation), and GHOST_FORESIGHT_NOTE=0 kills it.

The note never reaches the corpus. A second fresh-eye round found that recording the note verbatim would have un-labelled treatment-arm repeated failures — the growing "N of M" counter made three identical retries look like three distinct errors to the same-error-3× outcome rule (FAILED on control, UNKNOWN on treatment), biasing the experiment's own headline metric. strip_foresight_note() now removes the block at trajectory reconstruction, so the corpus stores what the tool returned, not what the treatment decorated onto it. The foresight ledger itself always graded pre-note. Read the arm verdict in the triggered-only block of the experiment report; the live-ledger backtest remains the confirmatory instrument for prediction quality itself.

What the numbers claim (and don't)

  • Accuracy/precision in learning-health are ledger-tail aggregates — screening numbers, not the gate.
  • The ledger only sees calls that reached the dispatch pipeline; pre-flight-blocked calls are invisible to it (they never executed, so there is nothing to grade).
  • A turn that crashes mid-batch drops that batch's unresolved predictions — the ledger undercounts by design rather than fabricating a resolution.
