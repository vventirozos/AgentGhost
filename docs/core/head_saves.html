Head saves: the model's memory of a prompt, kept on disk

core/head_saves.py plus the slot bookkeeping in core/agent.py and core/llm.py. How the agent avoids re-reading the same 28,000 tokens every time something else used the model.

Why it exists

Every owner request opens with the same head: the tool definitions and the system message, about 28,213 tokens. Before the model can answer, llama-server has to process those tokens into its internal state (the KV cache plus the hybrid model's recurrent state). On the 27B main model that takes about 166 seconds.

llama-server runs one slot (-np 1). Whatever ran last owns that state. A background job, a channel member's message, a different conversation or a restart replaces it, and the next owner request would pay the 166 s again. A long conversation is worse: everything past the head (often 5–40k more tokens) is lost too.

llama-server can write the slot's whole state to a file and read it back (POST /slots/0?action=save|restore). A save of the head takes about 0.7 s and 1.7 GB; a restore takes 0.4–0.8 s. Head saves decide what to save, when to put it back, and whose the slot is in between.

Correctness never depends on these files. llama compares the exact tokens of every prompt with what the slot holds and reuses only the matching prefix. A wrong or stale file costs time (the rest is re-processed), never a wrong answer.

Who owns the slot

The agent keeps one record of the conversation that last used the slot (llm._slot_session, plus the request holding it in llm._slot_request). Every request carries a conversation key: the client's session_id (the web client mints a new one on /clear; Slack sends slack:<thread>:<user>), otherwise a fingerprint of the first message.

  • Who becomes the owner: an owner request's main call that opens with the head. Background calls, probes (probe-*), scheduled tasks (sched-*), job resumes (sub-*, job-*) and channel members never own the slot.
  • How long it owns it: with GHOST_CONV_KEEP=1, until another call needs the slot. There is no timer: the conversation is saved to disk first, and only then is the slot given up.
  • Without the conversation switch: ownership lasts GHOST_SLOT_KEEP_S (600 s) after the last call, then the re-warm tick puts the head back (§4RP).
  • Every head restore clears the owner. The record lives in process memory, so an agent restart forgets it. After a restart the head comes back as usual.
  • The record can outlive the state (§4RW review): the owner's reply can finish draining while another call takes the slot. When a call that does not open with the head ran since (_head_displaced), the owner's next request is treated as not holding the slot: its conversation file (or the head) is restored. A save that waited while the owner's own reply finished still saves: that is the same conversation.

When something is saved

  1. The owner head: after a warm-up that had to process the head from scratch, or when no file exists yet for this head. Only while no request or main-slot stream is live. llama writes a .part file, and it becomes the head only if llama saved exactly the warm-up's token count. A save that llama ran after a request had already taken the slot is thrown away.
  2. A head with no file yet (an effort level or profile never saved; §4RW): the warm-up first restores the newest head saved by this server (newest_head_for). The effort sentence closes the system block, so the two heads differ only in the tail. llama goes back to that file's checkpoint ~1,024 tokens before its end and re-reads from there, about 1k tokens instead of 28k. The new file is then saved. Live 2026-10-27: the owner picked xhigh, and without this the next re-warm processed all 28,251 tokens (167 s) while a member's request waited.
  3. The members' head at a member's request (§4RW): when a member's first call finds no members' file, the agent first sends the members' head alone to llama (the warm-up's own payload, 1 token generated) and saves it as kind member. Then the call goes on from it. The request would have processed that head anyway, so the cost is the save (~1 s), once. If the slot stays busy, less than 60 s of the request's deadline is left (MEMBER_HEAD_MAKE_MIN_S), llama gives no token count, or the slot moved on, nothing is saved and the call processes the head as before. Before §4RW the file was made only in a quiet gap, after a member request since the agent's last boot, and that never happened on 2026-10-27.
  4. The members' head in a gap: at the start of a re-warm tick, once a member request has run since boot (or a members' file exists), only when nobody has sent anything for 600 s and no conversation owns the slot. The tick processes the members' head (~50 s), saves it, then restores the owner head straight away.
  5. A conversation (GHOST_CONV_KEEP=1): just before any of these would replace it:
    • a call of another conversation, or of a request that owns nothing (a probe, a scheduled task);
    • any call of a channel member's request on the main slot, whatever it opens with (§4RW review: before, only a call that opened with the members' head saved it);
    • any background main call (a deferred verdict, a replay, a sub-agent; LLMClient.before_background_dispatch);
    • gap work (the members' head refresh, a head with no file yet).
    Saved only when the owner's call was the last one on the slot, only once per state, and only if it holds at least CONV_MIN_PAST_TOKENS (1,024) tokens past the head. Fewer tokens re-read faster than a save plus a restore.

When something is restored

  1. At llama start. bin/start-llama-server.sh runs head_saves.py --restore-on-start in the background. It waits for /health, picks the newest owner head saved by the same model, build and chat template (/props), and restores it while llama has served nothing yet. This covers restarts, crashes, reboots and an agent that is down.
  2. Before a request's first main call (_slot_switch_before, through llm.before_main_dispatch):
    • its conversation has a file and is not in the slot → the conversation is restored and resumes at its last message;
    • no file, and the slot holds something else → the head is restored, and the request re-reads its part past the head;
    • the slot already holds this conversation → nothing happens.
    The hook waits for llama's slot to go idle (polling /slots, up to BEFORE_MAIN_DISPATCH_S, 150 s). A failure or timeout never fails the call: llama then re-processes from its nearest checkpoint.
  3. Before a channel member's request: the members' head is restored when the slot holds anything else (_member_head_before).
  4. On a re-warm tick: the head is restored over a slot that nobody owns. If the slot is busy, unreadable or a request is live, the tick sends nothing and retries later (deferred).
  5. After an outside call (a client outside the agent on the same slot, §4RQ): the next main call that opens with the head restores it.

When the effort level changes (§4RW-f)

The effort sentence closes the system block, so each level has its own head (28,213 tokens at medium, 28,251 at xhigh). A conversation built at one level leaves a prompt at another level about 28.2k tokens in. That is past every checkpoint the conversation has, so llama could only re-read it from token 0 (~170 s plus the conversation).

  • The same conversation at a new level. Its first call no longer counts as "the request that holds the slot". The agent makes the head plan for the new level, a template render that does not touch the slot. It then restores that level's head, or the nearest saved head when the level has no file yet. Only the conversation is re-read. The 📀 line names it: "restored the head before this conversation at xhigh effort … it re-reads its part past the head".
  • A conversation file saved at another level is left on disk (🧳) and the head of this level is restored instead. Each conversation file records the level its state was built at, which is not the level of the request that displaced it.
  • Levels are read from what is rendered and sent, never from the last pick:
    • a head plan's level comes from its own render (level_in_render);
    • a call's level comes from its payload (_call_level);
    • a thinking-off turn (the report turn, the loop-retry turn) writes no sentence, so it is the medium head whatever the pick;
    • Default is the server's own level (reasoning_effort_default), so moving between Default and that level changes nothing;
    • while the server's level is unknown, nothing counts as moved and no file is refused, and a conversation saved then carries no level.
  • The re-plan for a new level sets that level on the warm-up's own level-free payload. It renders it (no slot use) and is tried once per request and level. The once-per-request decision does not hold across a level change: xhigh, then a thinking-off turn (medium), then xhigh again in one request restores the head each time the level moves, and never twice at one level. A probe on an effort arm counts at the arm's level. The level of a head is read from its system block only, at its last match.
  • Not covered: llama restarted onto a template without levels while the agent keeps running with GHOST_REASONING_EFFORT=1. The agent keeps the old server level, and picked levels then look like changes. The launcher does not produce this combination.
  • Not covered: a call cancelled after the switch let it through (before llama ran it) still counts as the slot's level. The next call at the previous level then restores the head once more than needed.

A picture look inside a request (§4RW-g)

The image tool looks at every render (GHOST_RENDER_LOOK=1), and so does vision_analysis. Both run on the vision pool, which is the main server (http://127.0.0.1:8088), so the look replaces the request's conversation in the slot.

  • Before: the client ran the switch only for calls marked main, so nothing saved the conversation. The request's next call then found its restore already decided for the request. Live probe (2026-10-27): the reply after the look re-read 30,112 tokens from token 0, which took 179 s.
  • Now:
    • The client calls before_side_main_dispatch for a foreground call whose pool's every node is the main server.
    • The agent (_side_call_before) saves the conversation when the request holds the slot, and keeps the owner.
    • The request's next call that opens with the head restores it (🔙 "restored from disk"), whatever the request decided before.
    • A conversation too short to save (under 1,024 tokens past the head) gets the head back instead ("before this request after its own picture look").
    • Each head call after a look restores again, and the next look saves again. Several looks inside one image call (the collage check, then the look) cost one save, because the first one already displaced the slot.
    • A request without a conversation key (a probe, a scheduled task: sched-, sub-, job-) has nothing to save. Its next head call after the look gets the head back (📀 "restored the head before this request after its own picture look") and re-reads only its part past the head (§4RW-g b). Before: 30,109 tokens re-read from token 0, 179 s.
    • A channel member's look (§4RW-g c): members' turns are not saved, so nothing is saved. The member's next call gets the members' head back (📀 "restored the members' head before a channel member's request after its own picture look") and re-reads its own part. The members' head is otherwise restored once per request; after a look it is restored again, but only when a main-slot call ended after the look began (members' calls never open with the owner's head, so the displaced flag cannot tell). Live before: slack-7e's call after its look re-read 16.6k tokens, 94 s.
    • A look that fails or times out counts as displacing the slot, so the next call still restores what was saved. When the failure came before llama ran it, that costs a ~1 s restore of an intact slot; when the save before it was also skipped, the conversation is re-read from the head.
  • Not covered:
    • a call marked main that does not open with the head (it goes through the switch, which keeps the request's own conversation as it is);
    • a worker or critic call that falls back to the main slot when its own pool is down (the pool is checked as configured, not as served);
    • cost: the visual verifier's pixel check falls back to the vision pool when the critic fails, and inside a live request it then pays a conversation save (seconds, up to tens under swap) before its verdict.

Why a follow-up does not re-read its conversation

Restoring a conversation only helps if the next request's prompt starts exactly like the saved one. Two things make that true:

  • A stable first message (GHOST_CONV_KEEP=1 with GHOST_STATE_ANCHOR=1). The first user message carries only the tool header and one fixed label. Everything that changes per request (memory recalled for it, the persona, workspace notes, the thinking depth) goes into the <system_state_update> block at the end of the prompt.
  • llama's own checkpoint at the last user message. llama b11669 saves a checkpoint where the prompt's last user message starts, which for the agent is that state block: exactly where the next request's prompt departs from this one. With --ctx-checkpoints 12 the checkpoint survives a request of a few tool turns.

Measured live on 2026-10-27:

  • A same-conversation follow-up reused about 28,880 tokens (f_keep 0.973) and processed only 806.
  • The owner's conversation 63f8b051 was saved (32,775 tokens, 2.85 GB, 1.0 s) when a probe needed the slot.
  • The owner's next request in that conversation restored it in 0.8 s.

Files on disk and cleanup

  • Directory: $GHOST_HOME/system/head_saves (~/Data/AI/Data/system/head_saves). It must also be llama's --slot-save-path; llama accepts only a file name, not a path.
  • Names: head-<key>.bin (llama's state) and head-<key>.json (token count, size, kind, server identity, saved time).
    • A head key hashes the server identity (model file, build, chat template) and the head as llama renders it, so a profile, tool or effort change makes a new file.
    • A conversation key is c plus a hash of the server identity and the conversation key, so the same conversation always overwrites its own file.
  • Cleanup is by count, not by age. Every save first runs prune(), which keeps the 3 most recently used owner and members' heads and the 6 most recently used conversations, and deletes the rest. "Used" means saved, or restored (a restore touches the .json; §4RW review: by save time alone, a 4-conversation rotation deleted the file about to be restored). Unfinished .part files older than an hour are deleted too. Worst case on disk: three owner heads (~5 GB), three smaller members' heads and six conversations (up to ~24 GB), about 30 GB.
  • A restore does not delete its file. A conversation's file stays until 6 more recently used conversations push it out, however old it is.
  • Restore time grows with the file: the client waits max(30 s, 10 s per GB) (restore_timeout_s). A conversation restore that still timed out is checked after llama goes idle: if the slot holds the file's token count, it landed and is kept, and the head is not restored over it.
  • A conversation save needs 20 s of its deadline (CONV_SAVE_MIN_S) or it is not posted, so a multi-GB write is never cut short and left as a .part file.
  • Mismatches: a restore whose token count is not the saved one deletes the file. An error from llama keeps it, because the warm-up that follows re-processes and overwrites a bad file.
  • Files from another model, build or template are never restored (the key and identity differ), and the count rule removes them in time.

Troubleshooting

  • A follow-up still re-read its whole conversation. Find the request in llama-server.log and compare n_past/f_keep with the prompt size. Usual causes:
    • an image in the prompt (llama makes no checkpoints then);
    • history rewritten (the 500-message window, or a compression summary once a conversation is over its budget);
    • a very long request that pushed the state-block checkpoint out of the 12 kept.
  • 📛 restore failed (TimeoutError). Usually memory pressure: a 1.7–4 GB read under swap. Check vm_stat/swap. The call still runs; it only re-processes.
  • 🕒 deferred, many ticks in a row. Something keeps the slot busy or unreadable (a long background stream, a stuck request). The line shows how many ticks in a row.
  • The head is re-processed after every llama restart. Check that --slot-save-path points at the head_saves directory and that head-restore: appears in llama-server.log. A new model, build or template means the first warm-up has to make a new file.
  • Disk use. ls -la ~/Data/AI/Data/system/head_saves; at most 3 files of each kind. Deleting them is always safe: the next warm-up re-processes the head and saves it again.

What it does not cover

  • The owner record lives in process memory, and an agent restart does not save the conversation that held the slot. After a restart a conversation's next request restores its file as last saved, which may be some turns old: llama re-processes from where that file and the request part. The boot warm-up restores the server-default level's head, whatever level was last in use. (§4RW-e: llama restarting under a live agent clears the record — prompt_tokens_total fell, or llama has served nothing.)
  • "The slot holds the head" compares token counts, not tokens. A different prompt of the same length passes the check, and llama then re-processes from where they differ.
  • A profile or effort change has no head file until the owner has been idle 600 s.
  • Two conversations taking turns each pay a save and a restore (~1–2 s) on every switch.
