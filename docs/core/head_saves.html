Head saves: the model's memory of a prompt, kept on disk

core/head_saves.py plus the slot bookkeeping in core/agent.py and core/llm.py. How the agent avoids re-reading the same 28,000 tokens every time something else used the model.

Why it exists

Every owner request opens with the same head: the tool definitions and the system message, about 28,213 tokens. Before the model can answer, llama-server has to process those tokens into its internal state (the KV cache plus the hybrid model's recurrent state). On the 27B main model that takes about 166 seconds.

llama-server runs one slot (-np 1). Whatever ran last owns that state. A background job, a channel member's message, a different conversation or a restart replaces it, and the next owner request would pay the 166 s again. A long conversation is worse: everything past the head (often 5–40k more tokens) is lost too.

llama-server can write the slot's whole state to a file and read it back (POST /slots/0?action=save|restore). A save of the head takes about 0.7 s and 1.7 GB; a restore takes 0.4–0.8 s. Head saves decide what to save, when to put it back, and whose the slot is in between.

Correctness never depends on these files. llama compares the exact tokens of every prompt with what the slot holds and reuses only the matching prefix. A wrong or stale file costs time (the rest is re-processed), never a wrong answer.

Who owns the slot

The agent keeps one record of the conversation that last used the slot (llm._slot_session, plus the request holding it in llm._slot_request). Every request carries a conversation key: the client's session_id (the web client mints a new one on /clear; Slack sends slack:<thread>:<user>), otherwise a fingerprint of the first message.

  • Who becomes the owner: an owner request's main call that opens with the head, or that shares the head's tools under another system text (the owner on Slack: a public system text over the same tool block, llm.shares_head_tools; §4SA). Before §4SA such a call restored the head but never owned the slot, so the owner's every Slack message re-read the system text and the whole thread. Background calls, probes (probe-*), scheduled tasks (sched-*), job resumes (sub-*, job-*) and channel members never own the slot; a member's call never does whatever its tools (the role decides, not the prompt's shape: requester_is_member sets the moved-on mark, which refuses ownership — r2 removed a second role check on ownership as redundant).
  • How long it owns it: with GHOST_CONV_KEEP=1, until another call needs the slot. There is no timer: the conversation is saved to disk first, and only then is the slot given up.
  • Without the conversation switch: ownership lasts GHOST_SLOT_KEEP_S (600 s) after the last call, then the re-warm tick puts the head back (§4RP).
  • Every head restore clears the owner. The record lives in process memory, so an agent restart forgets it; since §4SA the shutdown first saves the conversation that owns the slot, when no turn or stream is on it (see below). After a restart the head comes back as usual, and that conversation's next request restores its file.
  • The record can outlive the state (§4RW review): the owner's reply can finish draining while another call takes the slot. A stream that opened before the slot changed hands (llm._slot_changed_at, stamped on a release, a conversation restore and a change of owner; §4SA review — the old "used after it opened" guard was dead once a release had cleared the owner) never takes the slot back, and (r2) writes no mark at all from its stale payload — not the head mark, not the moved-on mark, not the call-end time (round 1 still did, and the new owner's next save then read "a call ran since" and skipped). The re-warm's own release (release_slot_session(stamp=False)) is not a change of hands: it runs with nothing live, and a request whose stream opened during the re-warm's call still takes the slot. When a call that was not this conversation's own ran since (llm._slot_moved_on, §4SA), the owner's next request is treated as not holding the slot: its conversation file (or the head) is restored. A save that waited while the owner's own reply finished still saves: that is the same conversation.
  • Two marks, two questions (§4SA): _head_displaced keeps its old meaning, "is the head in the slot" (the re-warm tick's question). _slot_moved_on says "did the slot's last call belong to the owner's conversation": a head-opening or tools-sharing foreground call, no; a background call, a channel member's call whatever its tools (the role check, on the flag too), a game move or an outside call, yes (the save's and the switch's question). Before §4SA the save and the switch read the head mark, so the owner on Slack's state, which has no head, counted as moved on. A conversation file records head_in_slot in its meta and the restore sets the head mark from it, so a state without the head is saved and restored like any other. The restore's "already in the slot" claim (the slot still holds what the last save wrote) needs the same conversation, the same token count and, since r2, the same file — the level's — as that save.

When something is saved

  1. The owner head: after a warm-up that had to process the head from scratch, or when no file exists yet for this head. Only while no request or main-slot stream is live. llama writes a .part file, and it becomes the head only if llama saved exactly the warm-up's token count. A save that llama ran after a request had already taken the slot is thrown away.
  2. A head with no file yet (an effort level or profile never saved; §4RW): the warm-up first restores the newest head saved by this server (newest_head_for). The effort sentence closes the system block, so the two heads differ only in the tail. llama goes back to that file's checkpoint 1,028 tokens before its end (its checkpoints: at the start of the last user message, and 1,028 and 4 tokens before the end; b11960) and re-reads from there, about 1k tokens instead of 28k. The new file is then saved. Live 2026-10-27: the owner picked xhigh, and without this the next re-warm processed all 28,251 tokens (167 s) while a member's request waited.
  3. The members' head at a member's request (§4RW): when a member's first call finds no members' file, the agent first sends the members' head alone to llama (the warm-up's own payload, 1 token generated) and saves it as kind member. Then the call goes on from it. The request would have processed that head anyway, so the cost is the save (~1 s), once. If the slot stays busy, less than 60 s of the request's deadline is left (MEMBER_HEAD_MAKE_MIN_S), llama gives no token count, or the slot moved on, nothing is saved and the call processes the head as before. Before §4RW the file was made only in a quiet gap, after a member request since the agent's last boot, and that never happened on 2026-10-27.
  4. The members' head in a gap: at the start of a re-warm tick, once a member request has run since boot (or a members' file exists), only when nobody has sent anything for 600 s and no conversation owns the slot. The tick processes the members' head (~50 s), saves it, then restores the owner head straight away.
  5. A conversation (GHOST_CONV_KEEP=1): just before any of these would replace it:
    • a call of another conversation, or of a request that owns nothing (a probe, a scheduled task);
    • any call of a channel member's request on the main slot, whatever it opens with (§4RW review: before, only a call that opened with the members' head saved it);
    • any background main call (a deferred verdict, a replay, a sub-agent; LLMClient.before_background_dispatch);
    • gap work (the members' head refresh, a head with no file yet);
    • a foreground call of the request's own that does not open with the head: its picture look (§4RW-g), since §4SC its cut-write continuation (§4OB) and since §4SC-b the fact-check verify call, a probe_model call on main and the research summary on the user's turn (each side_main=True) — the client's side path saves the conversation first and the request's next head call restores it;
    • the conversation's own change of effort level (§4SA): the slot holds it at the old level, so it goes to disk at that level before the new level's head is restored (📼 "saved to disk before this conversation's change to xhigh effort"); the file is that level's own and records the level its state was built at. Before, the state was discarded unsaved, and when the level came back the file restored was as old as the last displacement (live 2026-10-28 08:36→08:39: three requests stale).
    Saved only when the slot's last call was this conversation's own (_slot_moved_on false), only once per state, and only if it holds at least CONV_MIN_PAST_TOKENS tokens past the head: 3,072 (env GHOST_CONV_MIN_PAST_TOKENS; 1,024 until §4SA, when a 1.4k-token tail that re-reads in ~8 s cost a 2 GB write, and twelve one-shot conversations wrote ~25 GB in 30 min on 2026-10-28). Fewer tokens re-read faster than a save plus a restore.
  6. A conversation at the agent's shutdown (§4SA, GhostAgent.save_slot_conversation_at_shutdown): main.py's lifespan shutdown calls it after the aborted-turn stamping, once the idle loop is stopped and the re-warm tick task (context._rewarm_task) is cancelled (a tick must not post between the idle check and the save), and before the LLM client closes. The conversation that owns the main slot is written (📼 "saved to disk before the agent's shutdown") when no turn is running, no stream is still open on the slot, and the slot's last call was the conversation's own; bounded by SHUTDOWN_CONV_SAVE_S (25 s: uvicorn's 6 s and the four 5 s drains leave ~34 s of launchd's 60 s ExitTimeOut; a 3 GB save is 1–11 s live). The wait for the conversation lock is bounded too — a background call's save may hold it for a minute — by wrapping the whole call in SHUTDOWN_CONV_SAVE_S + 1 s ("another save held the lock to the deadline", durable log). Before, the record died with the process and the boot warm-up restored the head over the unsaved conversation (live 2026-10-29 06:11: a 2.3 GB state lost; a fix day has 8–20 restarts). A turn in flight at shutdown is not saved: the slot holds that turn's state, stamped aborted.

When something is restored

  1. At llama start. bin/start-llama-server.sh runs head_saves.py --restore-on-start in the background. It waits for /health, picks the most recently saved owner head (by save time, not last use; operator, 2026-10-27) made by the same model, build and chat template (/props). It prunes other identities' files, then restores that head while llama has served nothing yet. This covers restarts, crashes, reboots and an agent that is down.
  2. Before a request's first main call (_slot_switch_before, through llm.before_main_dispatch):
    • its conversation has a file and is not in the slot → the conversation is restored and resumes at its last message;
    • no file, and the slot holds something else → the head is restored, and the request re-reads its part past the head;
    • the slot already holds this conversation → nothing happens (one exception, off by default: GHOST_CONV_HEAD_FIRST_CALLS).
    The hook waits for llama's slot to go idle (polling /slots, up to BEFORE_MAIN_DISPATCH_S, 150 s). A failure or timeout never fails the call: llama then re-processes from its nearest checkpoint.
  3. Before a channel member's request: the members' head is restored when the slot holds anything else (_member_head_before).
  4. On a re-warm tick: the head is restored over a slot that nobody owns. If the slot is busy, unreadable or a request is live, the tick sends nothing and retries later (deferred). A slot a conversation holds is left alone quietly, even without the head in it (the owner on Slack, §4SA review): no displacement is named and nothing is re-planned every period, from the first tick on (r2: before the head reference exists too). The reason goes to the durable log once per distinct reason, then at debug (§4SA: the same reason tick after tick made 150 lines in two days); under GHOST_CONV_KEEP it reads "a conversation holds the slot (it goes to disk before anything replaces it)", not "inside its idle window", because there is no window.
  5. After an outside call (a client outside the agent on the same slot, §4RQ): the next main call that opens with the head restores it.

When the effort level changes (§4RW-f)

The effort sentence closes the system block, so each level has its own head (28,213 tokens at medium, 28,251 at xhigh). A conversation built at one level leaves a prompt at another level about 28.2k tokens in. That is past every checkpoint the conversation has, so llama could only re-read it from token 0 (~170 s plus the conversation).

  • The same conversation at a new level. Its first call no longer counts as "the request that holds the slot". The agent makes the head plan for the new level, a template render that does not touch the slot. It then restores that level's head, or the nearest saved head when the level has no file yet. Only the conversation is re-read. The 📀 line names it: "restored the head before this conversation at xhigh effort … it re-reads its part past the head".
  • The old level's state goes to disk first (§4SA): when the slot holds this conversation at the level it is leaving, _slot_switch_before saves it at that level (📼 "saved to disk before this conversation's change to xhigh effort") before it restores the new level's head; the file is that level's own (one per conversation and level, §4SA review) and records the level. Before, the slot's state was discarded unsaved, so when the level came back the file restored was as old as the last displacement — live 2026-10-28 08:36→08:39, three requests stale. When the level comes back, that level's file is restored and resumes at its last message.
  • A conversation file saved at another level is left on disk (🧳) and the head of this level is restored instead. Each conversation file records the level its state was built at, which is not the level of the request that displaced it.
  • Levels are read from what is rendered and sent, never from the last pick:
    • a head plan's level comes from its own render (level_in_render);
    • a call's level comes from its payload (_call_level);
    • a thinking-off turn (the report turn, the loop-retry turn) writes no sentence, so it is the medium head whatever the pick;
    • Default is the server's own level (reasoning_effort_default), so moving between Default and that level changes nothing;
    • while the server's level is unknown, nothing counts as moved and no file is refused, and a conversation saved then carries no level.
  • The re-plan for a new level sets that level on the warm-up's own level-free payload. It renders it (no slot use) and is tried once per request and level. The once-per-request decision does not hold across a level change: xhigh, then a thinking-off turn (medium), then xhigh again in one request restores the head each time the level moves, and never twice at one level. A probe on an effort arm counts at the arm's level. The level of a head is read from its system block only, at its last match.
  • Not covered: llama restarted onto a template without levels while the agent keeps running with GHOST_REASONING_EFFORT=1. The agent keeps the old server level, and picked levels then look like changes. The launcher does not produce this combination.
  • Not covered: a call cancelled after the switch let it through (before llama ran it) still counts as the slot's level. The next call at the previous level then restores the head once more than needed.

A picture look inside a request (§4RW-g)

The image tool looks at every render (GHOST_RENDER_LOOK=1), and so does vision_analysis. Both run on the vision pool, which is the main server (http://127.0.0.1:8088), so the look replaces the request's conversation in the slot.

  • Before: the client ran the switch only for calls marked main, so nothing saved the conversation. The request's next call then found its restore already decided for the request. Live probe (2026-10-27): the reply after the look re-read 30,112 tokens from token 0, which took 179 s.
  • Now:
    • The client calls before_side_main_dispatch for a foreground call whose pool's every node is the main server.
    • The agent (_side_call_before) saves the conversation when the request holds the slot, and keeps the owner.
    • The request's next call that opens with the head, or shares its tools (the owner on Slack, §4SA review), restores it (🔙 "restored from disk"), whatever the request decided before.
    • A conversation too short to save (under CONV_MIN_PAST_TOKENS, 3,072 tokens past the head) gets the head back instead ("before this request after its own picture look"; §4SC-c: a side call other than a look is named — "after its own fact-check-verify call").
    • Each head call after a look restores again, and the next look saves again. Several looks inside one image call (the collage check, then the look) cost one save, because the first one already displaced the slot.
    • A request without a conversation key (a probe, a scheduled task: sched-, sub-, job-) has nothing of its own to save; when a conversation owns the slot, its look saves that conversation first (📼 "saved to disk before a request's picture look"; §4SA review r2), as before any other displacement. Its next head call after the look gets the head back (📀 "restored the head before this request after its own picture look") and re-reads only its part past the head (§4RW-g b). Before: 30,109 tokens re-read from token 0, 179 s.
    • A channel member's look (§4RW-g c): members' turns are not saved, so nothing is saved. The member's next call gets the members' head back (📀 "restored the members' head before a channel member's request after its own picture look") and re-reads its own part. The members' head is otherwise restored once per request; after a look it is restored again, but only when a main-slot call ended after the look began (members' calls never open with the owner's head, so the displaced flag cannot tell). Live before: slack-7e's call after its look re-read 16.6k tokens, 94 s.
    • A look that fails or times out counts as displacing the slot, so the next call still restores what was saved. When the failure came before llama ran it, that costs a ~1 s restore of an intact slot; when the save before it was also skipped, the conversation is re-read from the head.
  • Not covered:
    • a call marked main that does not open with the head (it goes through the switch, which keeps the request's own conversation as it is);
    • a worker or critic call that falls back to the main slot when its own pool is down (the pool is checked as configured, not as served);
    • cost: the visual verifier's pixel check falls back to the vision pool when the critic fails, and inside a live request it then pays a conversation save (seconds, up to tens under swap) before its verdict.

A cut write's continuation inside a request (§4SC)

A write the output limit cuts is continued by the system (§4OB): write_continuation.continue_cut_write calls the model round by round through _call_watching_stop, with a small prompt of its own — thinking off, no tools, never the head. Each round runs on the main slot and replaces the request's conversation there, exactly as a picture look does.

  • Before: the continuation went through the ordinary foreground path, which saves nothing for a call that does not open with the head. Request 72c2f05d's continuation destroyed a 51,604-token state, and the next turn re-prefilled 41,742 tokens in 282 s. llama-server cannot park a prompt state larger than --cache-ram (2 GB, about 31k tokens at the current KV size), so once the slot's state is past that size any side call on it is a full re-read.
  • Now: _call_watching_stop calls chat_completion(..., side_main=True). In LLMClient.chat_completion a foreground side_main call that is not off-main (and names no other pool) takes the side path: _side_call_what is set to "this request's cut-write continuation", _before_side_main_dispatch runs the agent's _side_call_before hook — the conversation in the slot is saved to disk first and the marker _side_call_rid set — and the name is cleared again in a finally. The request's next call that opens with the head restores the conversation (_slot_switch_before via _after_side, 🔙 "restored from disk"). A save and a restore cost about 1–2 s each.
  • The hook's log line names what displaced the slot: 📼 "saved to disk before this request's cut-write continuation in 1.1s (…) — its next request restores it". Without a name from the client it says "this request's picture look" (§4RW-g). No new log line kind.
  • Everything else of §4RW-g holds: owner requests that hold the slot only; a conversation under the 3,072-token floor gets the head back instead; a request without a conversation key saves the owner's conversation if one owns the slot; a member's turn saves nothing; a round that fails still counts as displacing the slot.

Pins: tests/test_4sc_cut_write_slot.py.

The other foreground calls without the head (§4SC-b)

A review of §4SC asked what else a request runs on the main server without opening with the head. Each displaced the conversation exactly as the continuation did; all take the side path now, named by their task_label, or left main altogether:

  • stylometry.neutralize_query (the anonymous query rewrite of deep_research and darkweb_search, inline on every anonymous search): off main — use_worker=True, off_main_only=True; without a worker the client raises and the lexical scrub_query answers, never the main model.
  • tool_fact_check's verify call: stays on the main model as a side call (📼 "saved to disk before this request's fact-check-verify call").
  • probe_model on main inside a live turn: a side call ("… before this request's probe-model call"); a background probe parks behind its request as before, and the worker leg never touched main.
  • project_research._llm_complete on the user's turn: a side call ("… before this request's research-summary call"); in the background it parks as before.
  • The §4MD truncation continuation (a reply cut at max_tokens, continued as plain text) keeps the tool list with tool_choice: "none", so it opens with the head: popping tools had made it a non-head call that destroyed the conversation and re-prefilled the whole prompt minus the tool block (the template renders tools first). A payload without tools carries neither tool_choice nor parallel_tool_calls.

The side hook's save uses the caller's window (late) as its bound; the state's size estimate applies only when no window is given (a background call's hook) — a 118 s window had been capped at 60 s, which timed out a multi-GB save. The name in the 📼 line is a ContextVar (llm.side_call_what(), set from the label in chat_completion), not a client attribute: two requests' side calls on one client would read each other's name across the hook's await. Known open: a worker-pool call (compaction, the shield) that falls back to main on a worker outage runs no hook. Pins: the §4SC-b block of tests/test_4sc_cut_write_slot.py. Reviewed again in §4SC-c: the rewrite's bound, the unconfigured pool, the fact-check wait, the continuation's tool call, the restore line. And in §4SC-d: the rewrite's whole budget, the open breaker, a cut inside an opening tag, an off-main-only pool on the main box.

Review r2 of §4SC-b (§4SC-c)

A second reading of the §4SC-b fixes, against the client's own defaults and the continuation's new payload. Six findings, all fixed:

  • The anonymous query rewrite is bounded. stylometry.neutralize_query (off main since §4SC-b) inherited the worker client's 1200 s default: a hung or unreachable Nova stalled every anonymous deep_research / darkweb_search for 20 minutes before the lexical scrub answered. It now calls with require_healthy=True, timeout=total_budget=_NEUTRALIZE_TIMEOUT_S — the same 12 s as core.llm._ROUTE_TIMEOUT_S (imported, one truth; 12.0 when the client cannot be imported) — so a hung Nova costs an anonymous search 12 s, and a node with its breaker open is not called at all. (§4SC-d: the whole budget is now _NEUTRALIZE_BUDGET_S, 6 s, below; the POST bound stays the 12 s.)
  • No worker pool: the lexical scrub directly. With worker_clients == [] (no --worker-nodes) the client's "requested but unconfigured pool" arm would have run the rewrite on main with no save hook — the §4SC-b sentence "with no worker the client raises" held only for a configured pool whose nodes all failed (off_main_only). neutralize_query now returns scrub_query without calling the client when the pool is an empty list.
  • The fact-check wait covers the side hook's save. tool_fact_check's outer wait_for around the verify call had the call's own budget (_FACTCHECK_VERIFY_S, 150 s), leaving nothing for the hook's save of a multi-GB conversation that runs inside that wait. The outer wait is now _FACTCHECK_VERIFY_S + BEFORE_MAIN_DISPATCH_S.
  • A continuation that answers with a tool call leaves the cut answer cut. Since §4SC-b the §4MD truncation continuation carries the tool schemas (tool_choice: "none"), and the model can still answer a cut prose reply with a call — message.tool_calls, or <tool_call / <function in its text; appended, the cut answer became a tool turn on a reply the user had already seen as prose. The pre-loop gate (a text turn only) now applies to every continuation round: such a round sets _cut_unrecovered and the reply ships as the cut text plus the truncation note (§4MD M1), never as a tool turn.
  • A tool-less head's continuation is a side call. A request whose payload carries no tools cannot open with the head, so its continuation passes side_main=True (side_main=not cont_payload.get("tools")): the conversation is saved first, as before the cut-write continuation. With tools it opens with the head — the main path, no hook.
  • The restore line names the side call. The 📀 "restored the head before this request after its own …" line said "picture look" for every side call; _side_call_before now stores the name it saved under (_side_call_what_last, from llm.side_call_what()) and the restore reads it: "restored the head before this request after its own fact-check-verify call", "… cut-write continuation", "… probe-model call", "… research-summary call". A look still says "picture look".

Pins: the §4SC-c block of tests/test_4sc_cut_write_slot.py — among them a pin through the real client against a TCP server that accepts and never answers (the lexical scrub comes back within the 12 s bound and the POST carried a budget) and one with no worker pool (main is never posted, no hook runs). Harness: scripts/mutate_4sc.py K14–K19 (K14 the unbounded rewrite, K14b a call despite an open breaker, K15 the unconfigured pool on main, K16 a continuation's tool call appended, K17 the fact-check wait without the save, K18 the restore line always "picture look", K19 a tool-less continuation as a plain main call).

Review r3 of §4SC (§4SC-d)

A third reading found no MAJOR ("ship with follow-ups"); four MINORs and one follow-up, all taken:

  • The anonymous query rewrite's whole budget is 6 s. §4SC-c bounded stylometry.neutralize_query with timeout=total_budget= the 12 s route bound. But a saturated Nova is not a breaker fault: require_healthy lets the call through to the client's permit gate, which _do_chat_completion sizes from total_budget — at 12 s the gate alone cost 9 s and an anonymous search up to 21 s before the lexical scrub answered. Now total_budget=_NEUTRALIZE_BUDGET_S (6.0): the gate is ≤ 3 s (measured 3.03 s against a worker whose one slot is taken: no POST, the lexical scrub), the POST ≤ 6 s, and timeout stays _NEUTRALIZE_TIMEOUT_S, the 12 s route bound. A hung node now costs 5 s — the /props probe, which leaves the 6 s budget no room for a POST at all. A scrub is not worth more.
  • An open breaker means no call at all — pinned on behaviour, not on the flag: a node whose breaker is open (3 recorded failures) is never POSTed to and the scrub comes back in under 1 s; before, only the require_healthy=True argument was asserted.
  • A stream cut inside an opening tag is a call turn, not prose. The §4MD truncation continuation's pre-loop gate looked for <tool_call / <function whole, so a reply cut at max_tokens inside the tag ("Let me look that up.\n<tool_ca") read as a text turn: continued, the seam and the call JSON shipped raw. The gate then also rejected a dangling opening tag at the end of the text (<[a-z_]{0,9}$ — the §4SC-d rule; §4SC-e replaced it, since any < near the end of a legitimate cut answer matched too), and the per-round continuation gate (§4SC-c) rejects the closing forms too (tool_call>, </function): a continuation of "…{"name": …}\n</tool_call>" carries no opening form and was appended. Why a follow-up does not re-read its conversation

Restoring a conversation only helps if the next request's prompt starts exactly like the saved one. Two things make that true:

  • A stable first message (GHOST_CONV_KEEP=1 with GHOST_STATE_ANCHOR=1). The first user message carries only the tool header and one fixed label. Everything that changes per request (memory recalled for it, the persona, workspace notes, the thinking depth) goes into the <system_state_update> block at the end of the prompt.
  • llama's own checkpoint at the last user message. llama b11960 (b11669 at the time of the measurement; the rules below are verified in b11960's source) saves a checkpoint where the prompt's last user message starts, which for the agent is that state block: exactly where the next request's prompt departs from this one. It also saves one 1,028 and one 4 tokens before the prompt's end, none after an image chunk, and when 12 are full (--ctx-checkpoints 12) it erases the oldest first. The checkpoint at the state block survives a request of a few tool turns.

A long request's follow-up (§4SA, off by default)

Because the oldest checkpoint goes first, a request of many main calls can push out the checkpoint at its message. Its follow-up then matches the slot up to that message, finds no checkpoint there, and llama re-reads from token 0, head included (~166 s plus the conversation). With GHOST_CONV_HEAD_FIRST_CALLS=N (0 = off), a follow-up of the same conversation whose previous request made at least N main calls (llm._slot_request_calls) restores the head first instead of resuming from the slot (📀 "restored the head before this conversation's next request (its last made 14 calls, past llama's 12-call checkpoint span) … it re-reads its part past the head") and skips its own, older, conversation file: only the conversation is re-read, not the head with it. The conversation meta records calls (the main calls of the request that built the state) and rid (that request), so a file whose calls ≥ N is left on disk too (🧳 "not restored — its last request made 14 calls, past llama's 12-call checkpoint span; the head instead"): it holds the previous request's last 12 checkpoints exactly as the slot did. A file saved by the same request (before its own picture look) is exempt: it extends into that request's next prompt whole, no checkpoint needed. The per-request call counter resets on every release and on every conversation restore. Status: off until measured; a live probe sets it.

Measured live on 2026-10-27:

  • A same-conversation follow-up reused about 28,880 tokens (f_keep 0.973) and processed only 806.
  • The owner's conversation 63f8b051 was saved (32,775 tokens, 2.85 GB, 1.0 s) when a probe needed the slot.
  • The owner's next request in that conversation restored it in 0.8 s.

Files on disk and cleanup

  • Directory: $GHOST_HOME/system/head_saves (~/Data/AI/Data/system/head_saves). It must also be llama's --slot-save-path; llama accepts only a file name, not a path.
  • Names: head-<key>.bin (llama's state) and head-<key>.json (token count, size, kind, server identity, saved time).
    • A head key hashes the server identity (model file, build, chat template) and the head as llama renders it, so a profile, tool or effort change makes a new file.
    • A conversation key is c plus a hash of the server identity, the conversation key and, when known, the effort level (conv_key(identity, session, level); §4SA review): the same conversation at the same level always overwrites its own file, and each level has its own. One file per conversation made every level flip overwrite the other level's state (A→B→A re-read the whole conversation). A save keys by the slot's level (_slot_level); a restore tries the level's file first and falls back to the plain key (a file saved before §4SA, or at an unknown level), to which the level check below applies. The meta also records conv, the level-less conversation key: prune() counts conversations for the 6 kept (a pre-§4SA file is its own), so one conversation's per-level files do not crowd out other conversations; the byte budget still counts every file.
  • Cleanup is by count, not by age. Every save first runs prune(), which keeps the 3 most recently used owner and members' heads and the 6 most recently used conversations (counted by the meta's conv, so a conversation's per-level files count once), and deletes the rest. "Used" means saved, or restored (a restore touches the .json; §4RW review: by save time alone, a 4-conversation rotation deleted the file about to be restored). Unfinished .part files older than an hour are deleted too, and so are .json metas whose state file is gone and leftover .json.tmp files of the same age. Conversations also have a byte budget, CONV_BYTES_MAX (24 GiB). The oldest are deleted until the rest fit, but the newest conversation is always kept. Before this budget (2026-10-27), six conversations near the 196k context could reach about 60 GB. Given the running server's identity (model file, build and chat template), prune() deletes every save made on another one, because its key can never come up again. Only the llama-start helper passes an identity, read from /props just before it restores, so a model or build change frees the old files at the next llama start. A save never passes one: its caller's identity can come from a plan read before a llama restart on another model, and pruning by it would delete the running server's files (fresh-eye review 2026-10-27). Each file is handled on its own, so one that the other process deleted meanwhile skips only that file. Before deleting, prune checks that the file's last use hasn't changed since it ranked the files. A file saved or restored again meanwhile, by the other process or another thread, is left for the next prune. When pruning drops a key, it never deletes that key's .part file, because llama may be writing a re-save into it right now. The stale-.part sweep deletes old ones. A save whose meta cannot be written (for example, a full disk) deletes the new state and reports failure instead of raising. A state file whose meta is missing can never be restored, so it never takes a head's place: it is deleted after an hour, and until then it is a save still in progress. The byte budget counts only the conversations it keeps, so dropping a big one leaves room for an older, smaller one. Worst case on disk: three owner heads (~5 GB), three smaller members' heads, and the conversations (≤ 24 GiB, or one larger conversation), about 32 GB. The directory needs no manual cleanup. It is also left out of the store snapshots (memory/snapshot.py, 2026-10-27).
  • A restore does not delete its file. A conversation's file stays until 6 more recently used conversations push it out, however old it is.
  • Restore time grows with the file: the client waits max(30 s, 10 s per GB) (restore_timeout_s). A conversation restore that still timed out is checked after llama goes idle: if the slot holds the file's token count, it landed and is kept, and the head is not restored over it. A restore replaces the slot's prompt tokens, so /slots n_prompt_tokens follows a restore (verified in b11960's source, §4SA; an earlier note that it showed only the last completion's prompt was wrong).
  • A save's bound grows with the state too (§4SA): head_saves.save_timeout_s(n_tokens) = max(60 s, 10 s per estimated GB), the state estimated at ~35 KB per token plus 12 × 150 MiB of checkpoints, and never more than the request's deadline allows; a background call's save, which has no request deadline, gets the state's own bound capped at BEFORE_MAIN_DISPATCH_S − CONV_SAVE_WAIT_S − 15 s (75 s; before: the 60 s idle-wait cap cut an 80 s save, and the file llama went on writing was never kept). Under 20 s of that (CONV_SAVE_MIN_S) the save is not posted, so a multi-GB write is never cut short and left as a .part file. Before, a flat 60 s could time out a multi-GB write under memory pressure while llama kept writing.
  • Mismatches: a restore whose token count is not the saved one deletes the file. An error from llama keeps it, because the warm-up that follows re-processes and overwrites a bad file.
  • Files from another model, build or template are never restored (the key and identity differ), and the count rule removes them in time.

Troubleshooting

  • A follow-up still re-read its whole conversation. Find the request in llama-server.log and compare n_past/f_keep with the prompt size. Usual causes:
    • an image in the prompt (llama makes no checkpoints then);
    • history rewritten (the 500-message window, or a compression summary once a conversation is over its budget);
    • a very long request that pushed the state-block checkpoint out of the 12 kept (GHOST_CONV_HEAD_FIRST_CALLS, off by default, restores the head first for such a follow-up).
  • 📛 restore failed (TimeoutError). Usually memory pressure: a 1.7–4 GB read under swap. Check vm_stat/swap. The call still runs; it only re-processes.
  • 🕒 deferred, many ticks in a row. Something keeps the slot busy or unreadable (a long background stream, a stuck request). The line shows how many ticks in a row.
  • The head is re-processed after every llama restart. Check that --slot-save-path points at the head_saves directory and that head-restore: appears in llama-server.log. A new model, build or template means the first warm-up has to make a new file.
  • Disk use. ls -la ~/Data/AI/Data/system/head_saves; at most 3 owner heads, 3 members' heads and 6 conversations (each a .bin and a .json), the conversations also under CONV_BYTES_MAX. Deleting them is always safe: the next warm-up re-processes the head and saves it again.

What it does not cover

  • The owner record and the effort level live in process memory and are not persisted. Since §4SA the shutdown saves the conversation that holds the slot (when no turn is running and no stream is open on it, within 25 s), so after a restart that conversation's next request restores a file as new as its last turn; a turn in flight at shutdown is not saved, and such a conversation's file is as old as its last save. The boot warm-up restores the server-default level's head, whatever level was last in use, and the next request restores its conversation file over it. (§4RW-e: llama restarting under a live agent clears the record — prompt_tokens_total fell, or llama has served nothing.)
  • "The slot holds the head" compares token counts, not tokens. A different prompt of the same length passes the check, and llama then re-processes from where they differ.
  • A profile or effort change has no head file until the owner has been idle 600 s (probes do not move the slot's gap clock, §4SA; the idle scheduler's clock still counts them).
  • Two conversations taking turns each pay a save and a restore (~1–2 s) on every switch.
