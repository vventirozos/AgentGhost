core / regression.py

§4NE (2026-10-10): the owner's regression suite. The owner's own failure evidence becomes test cases the owner approves; kept tests are re-asked after every code change and daily, and a failure is reported. Tests: tests/test_4ne_regression_suite.py.

Why

The §4NA–§4ND reviews measured every autonomous producer of lessons, skills, routing and calibration, and switched most of them off: none could show it made real turns better. The one improvement signal that held up was the owner's own judgement. This module does not try to make the agent better by itself; it makes regressions visible, so a change to the code or a candidate rule is checked against the questions the owner already said were answered wrong.

Where the feedback comes from

  • Candidates (candidates): owner turns from the last CANDIDATE_DAYS (14) through iter_teachable(consumer="frontier"), so member and probe turns never count. Evidence is either a human 👎 (outcome_source starting HUMAN_SOURCE_PREFIX, outcome failed), or the reaction judge's verdict True together with the owner's next message. A verifier refute alone is not evidence. Only replayable (read-only) requests qualify, because a test run is a probe and cannot write.
  • Drafting (_draft): the main model, in the idle slot, writes an expectation and up to a few checks from the request, the old reply and the evidence. clean_checks keeps only known kinds with short bounded values; a draft with no checks is no draft (undraftable).
  • Approval: the proposal is an activity notification that opens with its commands, like candidate rules. Nothing runs until the owner keeps it.

Checks

Deterministic, on the reply text and the turn's recorded tool calls (evaluate). No model judges a test.

Owner commands

Owner turns only (request_kind == "owner", not a public surface), routed from agent._owner_rule_note. The command must be the whole message ("keep test 3 for the exam" is ordinary chat). The answer is the agent's own outcome line, prepended as a banner, as with rule commands.

  • keep test N — the test becomes kept (refused when it has no checks). On a kept test it adopts a waiting redraft; it says so when the redraft is still being made, and "already kept" otherwise (no suite-wide re-run). "show test N" and the list show a waiting redraft.
  • edit test N: <what a right answer must do> — the next idle step redrafts the checks from the owner's words and shows them. A kept test stays in the suite on its current checks meanwhile; "keep test N" adopts the redraft, and an unadopted redraft lapses after PROPOSAL_TTL_S with the test still kept (r4). Any other test goes to edited and comes back as a proposal.
  • forget test N — state forgotten; it never runs again.
  • show test N, show regression tests — read them.
  • run regression tests — every kept test is due at the next idle slot.

The suite-wide commands name the regression tests because "run tests" and "list the tests" are ordinary coding requests (r1). A numbered command is ordinary chat while no regression test exists at all.

The idle step

advance(agent, ctx, home) runs in the self-play slot right after the failure-replay step, through _run_idle_job(…, "regression"), so the owner arriving stops it. One unit of work per slot, in this order:

  1. expire proposals older than PROPOSAL_TTL_S (7 days);
  2. redraft one edited test from the owner's words;
  3. run due tests — kept tests not yet run on this code (code_fingerprint: a hash of the path, size and mtime of every .py file in the package, taken once when the agent process loads the module, so it is the code that is running), or not run for RUN_EVERY_S (24 h), or all of them after "run regression tests"; at most MAX_CASES_PER_RUN (2) per slot, no more than the replay loop's own budget for one capped idle job. Each result is saved as it finishes, so a cut keeps what ran. The owner arriving stops the run (a cancel note anywhere in the reply, even after partial output, means "stopped", never a failed check). A run that breaks (an error, not a failed check) is recorded as "could not run" — shown that way in "show test N", never as FAIL — and is not retried until the next day or deploy. A test the idle job's time cap cuts MAX_STARTS (2) times is booked "could not run" too, so one slow test cannot hold the rest of the suite and every new proposal behind it; a stop for the owner's arrival is not counted (owner_stopped, also called by the agent when it cancels the job for the owner; it forgives only a run started in the same step, so an earlier cap strike stays counted). A cancel note counts only where the agent puts it — a line in the reply's last paragraph — not when a reply quotes it. A failure is notified; an all-pass run is logged as info;
  4. otherwise draft one new proposal, unless MAX_OPEN_PROPOSALS (3) are already waiting. A case written for the same failure while the draft was being made is not added twice, and a re-asked request (same_request) is one test. When the model cannot be asked (busy, timeout) nothing is decided: that failure waits DRAFT_BACKOFF_S (1 h), doubling up to a day, while other failures are drafted (r4: a fixed try limit turned "busy" into "undraftable" for good). Only a draft with no usable checks is set aside as undraftable.

No data home means no store: the step returns "".

Test runs are probes, held read-only

A run is handle_chat with request id probe-rt-<n>-<run>. It runs unattended, so it is held read-only at tool dispatch and keeps the owner's project binding exactly like a failure replay: failure_replay.is_replay_request covers both prefixes (UNATTENDED_PREFIXES). The original turn being read-only is not enough, because on replay the model may pick any tool (r1, CRIT). The probe prefix keeps it out of every teaching reader, the outcome ledgers and owner memory, like the failure-replay runs. The run's tools are read back by that id (_tools_for, the one documented include_probes=True opt-in here). A cancelled run raises, so it is not booked as a failure.

Candidate rules are run against the suite

In failure_replay a candidate rule that fixed its own failure also runs the kept tests with the rule in place (run_suite(…, rule=…, record=False); the trial is not written into the tests' history). If that run is cut twice, the rule is still proposed and says its tests could not be run; a run the owner interrupted before any test finished is simply retried without spending one of the stage's tries, and errors are named ("could not run: test 2"), never folded into the pass count. The proposal then says your tests with it: 4/5 pass, FAILING: test 2, so the owner sees what a rule would break before saying "learn rule N".

Store

$GHOST_HOME/system/regression/cases.json: {"cases": [...], "meta": {...}}. Every read-modify-write goes through update(home, fn) under one lock, so an owner command and the idle step never overwrite each other. The draft (a model call) happens outside the lock; the write re-checks state.

Case states: proposed → kept | edited → proposed | forgotten | expired; undraftable when the model gave no usable checks. An edit whose words cannot be drafted leaves the test exactly as it was (checks and state — a forgotten test stays forgotten) and tells the owner; a newer "edit test N" made while a draft is in flight wins.

opened_domain values are stored as bare hosts (https://www.PostgreSQL.org/docs → postgresql.org); a value with no dot, with spaces, or a bare TLD is dropped, since no page could match it or every page would.

An undraftable case was never shown to the owner, so it does not block a new failure on the same request, and it does not make numbered commands suite commands. The same failure with the same evidence is not redrafted (r3: newest-first candidates put it first every slot, starving older failures); new evidence on it reopens it.

What it does not do

  • It never changes the agent. A failing test is a report to the owner, not a trigger for an automatic fix.
  • It never runs a request that can write (files, memory, messages).
  • It does not judge answers with a model: a check a program cannot run is not a check.
