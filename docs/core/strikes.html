core / strikes.py — StrikeLedger

Request-scoped loop-detection accounting for the turn loop: bundles the failure/action signature tracking and the decay-freeze decision the reasoning loop used to juggle as bare locals.

Why it exists

The reasoning loop in core.agent historically tracked its loop-safety state as five interacting locals — two signature dicts (repeated_failure_sigs, repeated_action_sigs), a persistent_failure_seen freeze flag, a persistent_warned_sigs set, and a consecutive_clean_successes counter — mutated across several hundred lines. StrikeLedger (2026-06-11) pulls that cohesive bundle into one object so the loop holds a single ledger.

Scope is deliberately narrow. The ledger owns the signature tracking and the freeze decision. The raw strike counters (execution_failure_count / transient_failure_count) stay in the loop because they are cross-cutting — strike caps, the mid-loop cap, and System-3 pivot triggers all read them, so folding them in too would touch dozens of sites for no clarity gain.

The same error under exit 0 (§4IB, 2026-09-17)

Request 21b295ef: twenty turns of Grid('reduced_gg, npoints=127') variants, every run printing cannot build grid without 'type', every run exit 0 — the script wrapped the call in try/except and printed ERR: {spec!r} -> {e}. note_failure saw no failure; note_action skips execute (a mutating tool); and even keyed on the result, the output carried a catalog of memory addresses that differed on every run, so no two results could share a fingerprint. The planner said "I've spent 25+ turns on this" and kept going until the proxy cut the request at 1800 s.

The signal is the error line: error_line(output) (the LAST line naming a failure — a traceback ends with the exception that matters), normalise_volatile() (addresses 0x…, ≥16-hex ids, clock times, dates, pids, /tmp names and the quoted thing-tried collapse; counts and line numbers stay), and error_line_fingerprint(). The execute branch counts it under execute | <command head> (same error) | fp — the head (command_head from foresight), not the heredoc that changed a little each turn. EXECUTE_SAME_ERROR_STEER=3 appends a SYSTEM ALERT (change approach — read the library's source/tests in the sandbox — or stop and report the blocker); EXECUTE_SAME_ERROR_HARD_STOP=5 forces a final generation that reports the blocker (what was tried, the exact error, what would unblock it) — a report, not an abort marker: a clear "this is what fails and why" is a valid deliverable. Pins: tests/test_execute_same_error_breaker.py. The strike line itself now previews the line that names the failure (failure_preview: last failure-naming line, else the tail) instead of the head of the output — an ls listing was the whole strike line while ModuleNotFoundError sat at the end (tests/test_strike_failure_preview.py).

No-progress remedy: read/write tools

Tripping the breaker is only half the story — the other half is the remedy. For an ordinary re-observation loop (re-screenshot, re-read the same file with nothing left to do) the first-trip remedy sets force_final_response: drop the toolset and finish the turn as plain text. For a tool that both reads and writes through one dispatch name that remedy is destructive — the loop is the agent re-reading to orient itself before performing the write it was actually asked to do, and forcing a text-only turn bars that pending mutation forever.

Regression fixed: a request to reconfigure a composed skill looped on manage_composed_skills(action="list"), the breaker force-finalised at 3×, and the model's follow-up action="define" was then scrubbed by the final-generation stream guard — the change silently never landed. For is_readwrite_loop_exempt tools the breaker now still steers the model off the wasteful re-read but keeps tools available so the write can complete; the ≥5 hard stop remains the backstop. The companion fix on the dispatch side adds manage_composed_skills's define/approve/delete actions to the is_mutating set so a real mutation is never mistaken for a no-progress read.

StrikeLedger API

MethodBehaviour
note_failure(fname, error)Record a structural failure. Freezes decay once the same failure recurs 3×. Returns (sig, count, is_persistent, is_first_warning) — is_first_warning is True exactly once per signature so the loop emits the "stop retrying" steer a single time.
reset_clean_streak()Break the consecutive-clean-success streak. Called on ANY failure (transient or structural) — decay only unfreezes after a run of UNINTERRUPTED clean successes.
note_clean_success()Record one clean, non-mutating success. Returns True if this unfroze a detected loop (3 consecutive clean results = a genuine pivot). Signature counts are kept, so the same failure re-freezes on recurrence.
note_action(fname, target, result_fp)Record a successful action's fingerprint; returns (sig, count, tripped).
note_world_changed()Clear every accumulated no-progress observation. Called by the dispatch pipeline when a file_system mutation SUCCEEDS — see below.
decay_frozen (property)True while success-decay should be suppressed. The loop gates its execution_failure_count decrement on not decay_frozen.
_strike_synthetic(fname, reason) (loop closure)Not on the ledger — a closure inside _dispatch_and_process_tool_batch that every loop-minted rejection which counts a strike must call: it bumps the batch's binding-failure count (which blocks the batch-tail decay), resets the clean streak and records the signature via note_failure. See below.

World-changed reset (2026-07-18)

A successful file_system mutation now clears the no-progress observation ledger (note_world_changed()) and the once-per-signature steer set. Rationale: re-observing after an edit is verification of the change, not thrash — even when the observation comes back byte-identical, because the fix may target a deeper page state than the one being re-observed (a landing page is unchanged while the level-select flow behind it was repaired).

Regression fixed: in the 2026-07-17 overnight session every fix-verify turn (requests 26/3B/72/1E/91) ended with the post-fix browser navigate killed by "repeated 2x with no new info", and in request 3B the verifier gate then REFUTED the turn precisely because the evidence only showed the pre-fix page load — the auto-repair round's evidence-gathering navigate was itself cut by the breaker. Two guards fighting. The reset is scoped to file_system mutations on purpose: execute probes stay exempt, so a probe loop that keeps returning identical results still trips the breaker (the steer message explicitly tells the model to probe — resetting on probes would nullify the trip).

A companion guard in the dispatch pipeline (core.agent) collapses byte-identical read-only calls within one batch: the tool executes once and the result is fanned out to every duplicate tool_call_id. The no-progress ledger still counts each repeat, so detection is unchanged — only the wasted executions go away (observed: one 2026-07-17 batch carried 144 identical file_system reads; the breaker aborted correctly, but only after the sandbox ran all 144). Mutating duplicates are never collapsed — a repeated write can be intentional.

The reversible freeze

Freezing the success-decay lets the recurring failure accumulate to the strike cap (otherwise an interleaved success — e.g. the auto sandbox-listing after a failed read — cancels the strike and the cap never fires). Before 2026-06-11 the freeze was permanent for the request, which trapped multi-step tasks whose step 1 looped before steps 2..n succeeded. Now note_clean_success unfreezes after UNFREEZE_AFTER_CLEAN_SUCCESSES (3) uninterrupted clean results — a real pivot produces them, the fail→auto-list→fail oscillation never can.

Synthetic rejections reach the ledger 2026-09-13

The loop mints rejections of its own — unknown or disabled tool, unparseable call, bad JSON arguments, a blocked empty write, a participant-constraint block, an invocation error. Each incremented execution_failure_count, but only the invocation-error site also told the ledger (the 2026-08 fix). The batch tail decays the counter whenever every dispatched call succeeded and the ledger holds no failure, so [hallucinated_tool, read] netted to zero strikes on every turn: the 6-strike cap and the same-failure breaker never saw the model's most persistent mistake, and the 40-turn budget was the only stop. One closure now does the three things at all seven sites and prints the same "Same … ×N — freezing strike decay" operator line the real-failure classifier prints on the first persistent repeat, and tests/test_synthetic_strike_ledger.py enumerates the sites from the AST (a synthetic append that increments the counter without the closure reddens it; the enumeration is itself shown to fire) and drives the real loop with a real ledger: the strike survives a clean read in the same batch, three identical rejections freeze decay, and a clean batch still decays a real strike. 11 mutants killed (PROJECT_JOURNAL §4GG).

Repeated-mutation breaker — RETRACTED (§4FD → §4FH, 2026-09-07)

An identity-keyed breaker (tool, action, target — result ignored) shipped here for a few hours and was pulled by the same day's verification pass. Its premise was request fb705dcf "clicked #launchBtn ten times"; the fact check showed every one of those clicks had file edits between it and the next — an edit→verify cycle, not an ungrounded repeat — and a corpus replay of the shipped key measured 28 of 1,067 real requests false-steered and 11 false-stopped (reads, green test re-runs, id-keyed task updates collapsing to one key) against 3 rows of the target class. A guard with no measured true positive does not ship. The ledger, helpers and loop wiring were deleted; the deletion is pinned in tests/test_4fh_mutation_breaker_retracted.py. The no-progress breaker above and the edit-run futility breaker remain the loop guards.

Tests: tests/test_strike_ledger.py (behaviour, incl. the world-changed reset) and tests/test_core_loop_defect_fixes.py (turn-loop wiring). The no-progress / not-found breakers it feeds are covered by tests/test_no_progress_loop_breaker.py and tests/test_not_found_loop_breaker.py; batch dedup and the dispatch-side reset by tests/test_dispatch_pipeline_extraction.py.

A doubled call in one batch is not a loop 2026-09-16 §4HP

Live (req 1234e131): turn 9 issued four parallel browser calls with one URL listed twice. Both succeeded with identical text, and the no-progress breaker (threshold 2, keyed tool | target | result-fingerprint) read them as "repeated 2x with no new info" and forced the text-only conclusion — barring the plan's last step (write the report and PDF). The model attempted the write anyway; the call was scrubbed and §4HF's retry delivered the report inline. A no-progress loop is re-observing after seeing the result; two calls in one batch never saw each other. 5 of the 63 historical 2x trips were this shape.

StrikeLedger.begin_batch() opens a per-batch set; the turn loop calls it once at the top of each results batch. note_action reports a signature already noted in the current batch with its current count and tripped=False, without advancing it. The same signature in the next batch still counts (a genuine cross-turn repeat trips as before), a different target or a different result is its own observation, note_world_changed still forgets everything, and a caller that never opens a batch keeps the old counting. Pinned in tests/test_breaker_batch_duplicates.py.

The error is the exception, not the label in front of it (§4IE, 2026-09-17). Second re-test of the IFS/Oxford ask (probe ifs18371…): 36 execute runs, most of them probe harnesses printing one line per attempt — dict npts=31: ERR RuntimeError: SpecError: [pl], ERR dict nxacc=16: RuntimeError: SpecError: [pl] — all exit 0, all the same dead end. The labels are UNQUOTED, so the quoted-literal collapse never applied and every run fingerprinted as a new error: no steer at 3, no report at 5, 39 turns to the reserved report. exception_signature(line) now cuts the error line at its first exception name (_EXC_TOKEN_RE: RuntimeError, eckit.SpecError, ModuleNotFoundError…) and error_line_fingerprint hashes that; a line naming no exception (not found, a traceback header) is kept whole. Pins: tests/test_same_error_probe_labels.py.

A rewrite that reproduces the error is not progress (§4IG, 2026-09-17). Fourth re-test (probe ifs19450…): six runs ended in the identical RuntimeError: SpecError: [pl], yet the same-error breaker never fired — each run followed a NEW probe file (probe6.py … probe19.py) and StrikeLedger.note_world_changed, right for the no-progress class where a mutation makes a re-observation legitimate, wiped the same-error count with every write. It now keeps the signatures is_same_error_signature recognises (target ending in SAME_ERROR_TARGET_SUFFIX): that count grows only when the same error line recurs, and a rewrite that fixed it produces a different line. Pins: tests/test_same_error_survives_writes.py.

The same-error count is keyed on the error, not the command head (§4IK, 2026-09-18). Ninth live run of the IFS ask (probe ifs04495…): the identical RuntimeError: SpecError: [pl] ended four python3 … runs and three for f in …; do python3 …; done runs. Keyed on <head> (same error) that was two signatures — the steer fired twice, the five-run report tier never did. The dispatch site now keys the class on SAME_ERROR_TARGET_SUFFIX alone (the error fingerprint is the identity) and records the heads seen in strikes.exec_error_heads for the log line and the steer ("Same error 5x from python3, for"). The §4IG write-survival rule is unchanged (it reads the suffix). Pins: tests/test_same_error_keyed_on_error.py (steer at the 3rd and report at the 5th run across mixed heads through the live dispatch; the ledger holds ONE signature; AST: the site passes the suffix, not an f-string).
