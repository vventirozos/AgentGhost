core / coding_loop.py — the agentic coding leaf

§4FL (2026-09-08): selected by LEAF SHAPE by default — a leaf that extends an existing file of GHOST_LEAF_GROW_LINES (80) lines or more runs this loop; a fresh or small leaf keeps the spec executor; metadata.executor (agentic|spec) and GHOST_CODING_EXECUTOR override both ways; GHOST_LEAF_ROUTE_BY_SHAPE=0 turns the rule off. The rule is the bench's finding, not a flip: parity on small fresh leaves three times, 23/24 vs 15/24 (p = 0.0078) once the file grows, with the spec failures beginning at ~100 lines; the loop costs ~2.4× the wall time per leaf, so the cheap path stays where it wins. Pins: tests/test_4fl_shape_routing.py.

A bounded edit-test loop for one autonomous project leaf: the model edits files with file_system and runs them with execute on an isolated, project-pinned context, then hands back a verify command; the existing gates decide. Selected by GHOST_CODING_EXECUTOR=agentic or a project's metadata.executor; default remains the spec executor (§4FG, 2026-09-07).

Why it exists

coding_executor.build_coding_task is one spec call that returns whole files as JSON, then N writes and one verify. §4EI measured what that costs on the live model: files drafted inside <think> until the reasoning ceiling fires, structural slips at the files boundary, and a grammar-constrained no-think retry — the exact quadrant arXiv 2604.03616 measures as worst (JSON-required output costs 3–9 pp on Qwen3 and a grammar does not remove it). Three of six leaves failed in a 49-minute run. The shape the literature measures for small open models is the opposite: the model edits and runs, iterating on the witness (Claw-SWE-Bench, arXiv 2606.12344: apply failures 69.1% → <1.5% once the model edits files and the runner exports the patch; Cursor: model-specific edit shapes gave an order of magnitude fewer tool errors; arXiv 2607.26117 / 2609.02892: a fresh attempt with a concrete witness beats repair conditioned on the failed attempt).

How a leaf runs

  1. snapshot_workspace hashes every file under the project workspace.
  2. run_leaf_turn builds build_leaf_context — a copy of the live context that KEEPS sandbox_dir and current_project_id (so paths resolve inside the project), wraps memory read-only, nulls the workspace model / journal / scheduler / profile / bus, sets task_kind="leaf" and turn_origin_label="leaf" (no user-population ledger admits it), and contains the tool surface to file_system + execute the same fail-closed way run_subagent does. A GhostAgent runs one bounded turn loop on it (GHOST_LEAF_MAX_TURNS 14, GHOST_LEAF_TIMEOUT_S 600), thinking on.
  3. The prompt carries the task, the ledger, the existing file list, research briefs, the single-file steer, and the contract: end with VERIFY: <command> (or none) and SUMMARY: <line>. parse_leaf_reply takes the LAST occurrence of each.
  4. Files touched = diff_snapshots(before, after) — never the model's claims. A leaf that changed nothing inside the project workspace is a failed attempt even if it named a passing verify (§4FH: the second pilot's six "DONE" leaves had written at the sandbox root — the conversation reconciler inside handle_chat had parked the pin because a leaf has no conversation binding; the reconciler now honours _leaf_pinned_project, and run_leaf_turn fails closed if the pin did not survive the turn). With is_background the leaf's model calls ride the client's background lane.
  5. Gates, unchanged and in order: the verify command through the fail-closed runner (_run_verify), smoke_gate, constraint_gate over the written files.
  6. On failure, a SECOND attempt starts fresh with the failure's witness (verify output head) in its prompt; two failures return CodingResult(ok=False) with the attempt trail in detail. An attempt that changed nothing and gave no verify is a failed attempt, not a pass.

_finalize_coding consumes the result exactly as before (ok, files, ledger_note), so DONE/FAILED semantics, artifact registration and the work log are untouched.

Proving it: the leaf bench

scripts/leaf_bench.py creates two scratch CODING projects through the API (one with metadata.executor = "agentic", one without), adds the same small verifiable leaves to each (a module plus its pytest, a CLI plus a test, a Flask health endpoint…), drives POST /api/projects/{pid}/advance one leaf at a time, records DONE/FAILED and wall time per leaf, repeats, and reports an exact McNemar over the paired leaves — then hard-deletes both projects. Replicates ≥3× because agentic evaluations vary run to run even at temperature 0 (arXiv 2602.07150). §4FI — the deciding suite: --suite app is the §4EI shape — one single-file Flask expense app (app.py) grown over six dependent leaves (skeleton → CRUD → inline HTML page → summary/month filter → CSV export/import → JSON persistence via create_app), every leaf adding routes and tests to the SAME file, so the spec executor must re-emit an ever larger file whole while the loop edits in place. The six small leaves (--suite small) sat at ceiling for both arms three times. Leaves depend on each other, so run whole repeats; progress is written to <ledger>.progress.json (read with scripts/runstatus.py). One ledger per repeat is combined by scripts/leaf_bench_combine.py (pairs by ledger × rep × leaf, both executors required; exact McNemar, per-leaf DONE counts and mean seconds, the disagreements). Pins: tests/test_4fi_bench_scripts.py.

Tests: tests/test_4fg_coding_loop.py — contract parsing, workspace diff, executor selection, the success path (files from the diff, verify through the runner), the fresh-attempt-with-witness policy, the no-files-no-verify failure, the constraint gate over written files, the isolation shape, and the executed dispatch seam at the top of build_coding_task.

Round 3: the workspace snapshot hashed through links 2026-09-13 §4GJ

snapshot_workspace walked the workspace with a bare os.walk and hashed every file it listed. os.walk declines to descend a linked directory but still lists a linked FILE, so the snapshot hashed whatever the model pointed at — and this snapshot is what decides whether a leaf attempt changed the workspace (§4FH made an empty diff a failed attempt). It now uses walk_nofollow plus a descriptor-relative read, so a link is never listed and never read. See the symlink class.

Round 4: the snapshot could take the loop down 2026-09-13 §4GK

The workspace snapshot is best-effort by contract — its result decides whether an attempt changed anything, and a failure should degrade to "nothing seen", not end the run. The dir-fd guard fails closed with a value error on a platform without descriptor-relative syscalls, and a value error is not an operating-system error, so it propagated straight out. The loop is now guarded. Separately, the walk it depends on used to truncate silently when the process ran out of descriptors, so the snapshot reported "the attempt changed no files" and discarded good work; that walk now raises on exhaustion instead of treating it as a swapped entry.

Round 7: unknown is not passed 2026-09-14 §4GK round 7

Round 6 stopped a failed reading of the workspace being mistaken for "the attempt changed nothing" — and did it by falling through with an empty written-list. Every gate downstream is guarded on that list, so the verify step, the smoke gate and the constraint gate all became no-ops and the attempt was returned as a success with no files and no gates; the project layer then marked the task done with no artifacts. That is worse than the discard it replaced, and it is the task-reaching-done-on-evidence-that-no-work-happened shape this project has hit before. An unknown reading is now a RETRY: the next attempt re-snapshots, and the loop's existing exhaustion path reports honestly if it never clears.

A reading that half-failed is not a reading that succeeded 2026-09-14 §4GQ

Round 8 over the §4GK scope, run the way R3 says to run it: the previous round's fixes are the least-reviewed code in the tree. Two findings here, both inside round 7's own fix.

A file the snapshot could not read was silent. snapshot_workspace marks a failed WALK with _SNAPSHOT_INCOMPLETE — that was round 5's fix — and dropped a failed FILE READ with a bare continue. So a leaf that writes a file the snapshot cannot read produced a reading in which that file is simply absent: indistinguishable from "that file did not change", and therefore ungated, unregistered and unmentioned. The per-file branch marks the snapshot now, exactly as the walk does.

And the unknown-reading branch fires only when the reading found NOTHING. diff_snapshots deliberately returns the real paths it did see, so a walk that failed HALFWAY yields a non-empty written, skips the retry branch, runs its gates on the visible subset and returns an ordinary success. Retrying there would be worse — the next attempt's before absorbs the files this one wrote, so they would never be reported at all. Two changes instead: the reading is re-read once before any of this (the failure is in the snapshot, not in the attempt, and a descriptor squeeze is transient), and if it is still partial the result SAYS so, in the ledger note and in the detail.

Pins: tests/test_4gq_round8.py; battery scripts/mutate_4gq.py — 6 mutants + 4 controls, 6/6 killed. The battery's per-file controls earned their place immediately: the first run reported 10/10 KILLED because a fixture in the new pin file del-eted ServiceSupervisor.host_dir instead of restoring it, breaking 43 tests in every run including the controls.

The git tool was added here, and REMOVED 2026-09-23 §4KB round 5

LEAF_ALLOWED_TOOLS briefly included git so the leaf could read its own patch and checkpoint working code. It is back to ("file_system", "execute"). Four review rounds over the §4KB change set produced nine sandbox escapes and every one of them came from the git tool: a .git file, core.worktree, core.hooksPath, .git/commondir, objects/info/alternates (single, nested and quoted), a symlinked object store, diff.external and filter.*.clean. Each fix closed a vector; the next round found another, because .git is a configuration surface that names programs to run and the model can write files.

The one payoff that justified it — handing a real patch to the verifier (§4GW) — was never wired, and workspace_patch() itself turned out to carry none of the hardening (it executed diff.external in testing). The leaf reads its diff through execute, as it did before. What was KEPT is the part that is useful without the tool: file_system refuses to MUTATE any path with a .git component, so the agent cannot corrupt a repository by hand.
