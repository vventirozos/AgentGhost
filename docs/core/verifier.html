core / verifier.py — Verifier

Reflective self-evaluation: a separate LLM call (worker pool when possible) confirms / refutes the agent's conclusion before it reaches the user.

Routing

Tries llm_client.route(task="VERIFY", max_tokens=2048, ...) against the worker pool first — both cheaper and a different "perspective" than the foreground model. Falls back to a direct foreground call if the worker pool is empty or its circuit is open. When a dedicated critic pool is configured (--critic-nodes) it takes precedence over both, with its own budget (GHOST_CRITIC_CALL_TIMEOUT, default 120 s).

Verify-sized worker budget (2026-07-16). The worker-route call used to inherit route()'s default _ROUTE_TIMEOUT_S (12 s — sized for sub-second routing chores). A verdict takes 7–11 s uncontended on the live worker (Gemma 4 E4B), so any contention on the node pushed it past the ceiling: Nova: ReadTimeout → no gate verdict → a hallucinated answer shipped unchecked (req 738c/35, the "Everest pizza" turn), caught only by the late async verdict a full turn later. _call_llm now passes its own budget — _VERIFY_WORKER_TIMEOUT_S, default 45 s, env GHOST_VERIFY_WORKER_TIMEOUT — through route(timeout=…). The loop-exit repair budget (25 s) and the late-verdict handler already tolerate a verdict that lands after the reply, so the longer ceiling costs the user nothing; a genuinely sick node still fails bounded. Covered by tests/test_verify_worker_timeout.py.

Two-stage claim verification: forced identification → adjudication (2026-07-18)

The single claim prompt asked one yes/no-shaped question — "is this reply acceptable?" — and that shape is dominated by a default-answer prior: the judge model often carries the signal that a specific fact is unsupported yet never surfaces it, because nothing forced it to look at that fact. This is the mechanism identified in "Mechanisms of Introspective Awareness" (arXiv:2603.21396): detection-willingness gates suppress latent detection, and forced identification extracts substantially more signal than detection-willingness allows — at the price of false positives if used alone (ungated enumeration hallucinates problems).

verify_claim therefore now runs two calls by default (GHOST_VERIFY_TWO_STAGE, on unless =0, read per call so it can be flipped without a restart):

  • Stage 1 — _VERIFY_ENUMERATE_PROMPT: no verdict asked. The judge MUST name 1–3 of the reply's weakest fragments (exact quotes), each classified as alignment / support / constraint / artifact. Suspects are sanitized (_sanitize_suspects: max 3, 300 chars/field, unknown labels degrade to support) so a runaway response can't blow the stage-2 prompt.
  • Stage 2 — _VERIFY_ADJUDICATE_PROMPT: re-embeds claim + evidence + the numbered suspects and adjudicates EACH as real-problem vs. false-alarm under the strict rubric — this is where FPR control lives. It keeps the classic prompt's dismissal rules (all tool outputs judged together; one failed tool doesn't refute what another supports; paraphrase/rounding ≠ fabrication; blank request voids alignment) plus one drawn from the evidence-packer incident: truncated-but-consistent evidence is grounds for UNCERTAIN at most, never REFUTED. Output is the standard verdict JSON, so _build_verify_result, the ≥0.7 consumption gates, repair, and the late-verdict handler are all unchanged.

Fail-safe: unparseable stage 1, an empty suspects list, or unparseable stage 2 → fall back to the classic single prompt, so the pipeline is never less available than before (worst case: one bounded extra call). The adjudicated suspects ride along on VerifyResult.suspects for logging/bench use.

Stage-call payload discipline (measured on the live judge, 2026-07-18). First probes against Nova (Gemma 4 E4B heretic) showed a 60-token verdict costing 600–1200 completion tokens / 30–90 s — three separate failure modes: a nondeterministic <|channel>thought reasoning prelude on the adjudicate prompt, pretty-printed/fenced JSON, and looping the same verdict to the token cap (the server runs repeat_penalty=1.0). The stage calls therefore carry: the no-think soft+hard switch (/no_think + enable_thinking=False, same idiom as the critic path; kill switch GHOST_VERIFY_STAGE_NO_THINK=0), stop: ["\n"] (a minified answer is one line, so any newline is either the natural end or a malformed answer — both cut instantly), a "MUST start with {" prompt line, and a tighter output cap (GHOST_VERIFY_STAGE_MAX_TOKENS, default 1024). After the fix: enumerate ~41 tokens / 3–5 s, adjudicate ~63 tokens / ~4 s, 100% valid JSON over repeated probes. Deliberately NOT response_format=json_object: grammar-constrained sampling made this judge MORE verbose (41 → 786+ tokens, truncating at the cap). A malformed stage answer fails fast (~3 tokens) into the classic fallback. The classic path's payload is untouched (it remains the deployed baseline — measured at ~637 tokens / 42 s on the same judge, i.e. brushing the 45 s worker timeout).

Discipline nearly cost the catch rate — caught and fixed by the bench (2026-07-18). The first disciplined version (terse 1–3 suspects, 63-token adjudication) measured TPR 0.42 vs classic's 0.75 on the live A/B: the terse stage 1 named one trivial suspect and missed the injected fabrication entirely, and stage 2 only adjudicated named suspects. Three fixes recovered it: stage 1 must name EXACTLY 3 suspects with at least one word-by-word-checked specific fact; stage 2 fills a per-suspect "checks" array BEFORE the verdict fields (structured deliberation inside the JSON, replacing the free-form thinking the no-think switch removed); and stage 2 may flag real problems beyond the suspects list. Re-measured: TPR 0.75 / FPR 0.0 at ~16 s per verdict — classic's catch rate at ~2.5× its speed (classic: 0.6–0.75 at ~40 s). Remaining blind spots are judge-level (Gemma 4 E4B), shared by every arm: injected diff-markers never caught (0/6 across all configs), single-digit number swaps (34→35 °C) usually missed, and truncated evidence still draws spurious REFUTEs (the packer shape — rubric wording alone does not fix it). Small-n caveat: 2 seed cases; the full 12-case A/B (~90 min on nova) is the calibration baseline to run before/after any judge-model change.

Cost: one extra VERIFY-route call per claim-shaped verdict (the code and visual paths are unchanged) — and with the stage discipline the two-stage pipeline measured faster end-to-end than one classic verdict, because the classic prompt puts no ceiling on judge verbosity. Each call keeps its own bounded timeout (GHOST_VERIFY_WORKER_TIMEOUT, 45 s); with critic/async mode the calls are invisible to the user. Covered by tests/test_verifier_two_stage.py.

Judge-model selection — the 45-second envelope (2026-08-05)

The cheap judge's false-refute churn (FPR 0.31–0.385 on the bench; ~84% of live refutes overturned on escalation at ~8–18 main-slot calls/day) motivated a judge-model search. Two hard requirements fell out, and they pull against each other:

  • Rule application. The E4B carries the adjudication rubric but cannot apply it — two GEPA prompt rounds were cleanly rejected by the private gate (−0.131, −0.119), and the 2026 judge literature finds models under ~12–14B cannot leverage added judge guidance at all. Bigger, or judge-trained, is required.
  • The latency envelope. A verdict must fit GHOST_VERIFY_WORKER_TIMEOUT (45 s) under the worker node's normal contention — and a timed-out cheap leg silently falls through toward the main model, converting the "cheap" judge into foreground load. Measured on the shared 16 GB M4: Gemma 4 12B runs 40–70 s/verdict once live worker traffic evicts the rubric from the server's prompt caches (the making room for prompt cache entry log line is the tell) — measured out on this hardware, independent of its accuracy. The E4B fits with room to spare (7–11 s uncontended); a dense 12B does not.

The deployment shape that reconciles them: a dedicated critic pool. The verifier only rides the worker route when --critic-nodes is unset. Running a judge-trained 8B (its rubric internalised in the weights — shorter prompts, faster prefill, evaluator-tuned FPR) as a second llama-server on the worker box, wired as --critic-nodes, leaves the E4B doing everything it measurably wins (general worker tasks, audio) while adjudication gets a model built for it — and a dedicated server also ends the prompt-cache eviction war. Dual-server residency on a 16 GB box needs the wired-limit + small-compute-batch recipe and a real-decode health probe (/health answers while Metal-OOM decodes fail); the full recipe lives in PROJECT_JOURNAL §6 2026-08-05 (evening).

Measured verdict (2026-08-05, both arms benched): Selene-1-Mini does NOT clear the bar — rejected. Raw judge: FPR 0.543 on clean trials (worse than the E4B's 0.31–0.385), degraded-evidence FP 0.667, TPR 0.663, balanced 0.534. Production-shaped pipeline arm: FPR 0.000 only because the escalation washed 82 false refutes in 340 trials at one main-model call each, TPR dragged to 0.471, balanced ~0.70 vs the 0.766 incumbent. Evaluator training made the judge strict, not calibrated — it would increase the escalation bill it was meant to shrink. Operationally it passed everything else: zero timeouts at the 45 s bound (682 route calls), so the dedicated-critic slot works and awaits a genuinely calibrated candidate.

The transferable finding is about the escalation layer, not the judge. Overturn attribution on the pipeline run: 13 overturns rescued clean trials, 23 destroyed correct refutes (14 artifact_leak, 7 fact_swap, 2 fabrication) — the credulous main-model overturner eats true catches from any judge in the cheap seat, which is the same conclusion the live escalation audit and the 84%-overturn record keep pointing at. The next verifier round should make the overturner earn its overturns (verdict-tier routing / evidence-quoting requirements), not change the judge again.

Fault-injection calibration bench (2026-07-18)

The verifier's catch rate was previously unmeasured — its blind spots (the WEB-EXEC fail-open, the evidence-packer truncation refutes) were each found reactively, in production. src/ghost_agent/eval/verify_bench.py + scripts/verify_bench.py make it a measured component: take known-good (claim, evidence, context) triples, inject a KNOWN corruption, run verify_claim against the live judge endpoint, and report detection at a controlled false-positive rate (the injection methodology of arXiv:2603.21396, applied at system level). "Actionable" rates use the same ≥0.7 confidence gate as the production repair/consumption sites, so the bench reports what the agent would actually have acted on.

Fault library (typed, each with an expected verdict): fact_swap (a number the claim shares with the evidence is perturbed), fabrication (concrete fact appended that appears in no output), wrong_topic (donor case's claim swapped in — the alignment failure), silent_failure (evidence replaced with a 403/empty/timeout body under an unchanged success claim), artifact_leak (SEARCH/REPLACE markers injected into the reply — the 2026-07-14 parser-leak shape), constraint_violation (request gains "answer with a single word only") — all expected REFUTED — and evidence_truncation (evidence hard-cut under a still-true claim, expected NOT refuted: the packer-noise robustness class).

Case sources: a hand-authored seed set (scripts/verify_bench_cases.jsonl, 21 cases across the live task mix) plus real turns minted from GHOST_LLM_RECORD day-files — extract_cases_from_recordings inverts the rendered claim prompt using the live template's own literal segments, so recorded VERIFY calls become bench cases for free (and extraction survives template edits).

Prompt A/B arms: --two-stage both runs every trial under the two-stage prompt AND the classic prompt (toggled via GHOST_VERIFY_TWO_STAGE, restored afterwards), producing per-fault TPR/FPR deltas — the measurement that says whether the two-stage change actually pays.

The escalation axis: which verdict pipeline was measured (2026-08-04)

The gap. Production runs verify as TWO models — a cheap judge on the worker route, then a MAIN-model re-adjudication. The bench's single-endpoint HttpChatClient exposes no critic_clients and no worker_clients, so _escalate_refute returned immediately ("main model already judged it") and every bench number scored the cheap judge standalone. Measured on $GHOST_HOME/system/llm_recordings (2026-07-30..08-04), joining recorded verify prompts on the claim and reading which model served each verdict: 50 cheap-judge refutes reached the main model and 42 (84%) were overturned; the durable log's own GhostAgent lines read 80 overturned / 19 stood = 81% over a longer window. So a raw-arm false-alarm rate is an upper bound on production's, not production's.

The fix. EscalatingChatClient reproduces the production topology with two endpoints and no new verifier code: route() → the judge (where _call_llm sends the cheap leg), chat_completion() → the main model (where force_main=True lands), plus a truthy worker_clients so the escalation has a cheap route to have escalated from. Its route() degrades to fallback instead of raising, exactly like LLMClient.route, so a sick judge node falls through to the main leg as it does live. Both legs carry the verifier's OWN bounds (45 s route, 90 s main) — the main-leg timeout was arriving via _bounded_fallback_kwargs and being swallowed.

Two directions, four arms

Escalation is two-directional since the CONFIRM escalation landed, and the directions are independent, so an arm that names only "escalated" can mislead in either direction:

directionfires oneffectmoves
_escalate_refuteany cheap REFUTEDmain model re-adjudicates; its verdict winsFPR and TPR
_escalate_confirma HIGH-STAKES cheap CONFIRMED (a tool failed this turn)verdict never flips; confidence capped to 0.6, below every ≥0.7 gatethe actionable false-CONFIRM rate only

The CONFIRM direction fires only when the caller passes high_stakes=, and run_trials never did — so it was structurally dead in the bench even with the two-leg client installed, the same shape as the missing worker route. Bench cases now carry the flag: BenchCase.high_stakes is tri-state (None = derive, an explicit bool pins the case), and derivation runs looks_like_tool_error — production's own sniffer, not a second copy — over each segment of the packed evidence digest. Segmenting matters because that sniffer only scans the first 120 characters for its text markers, so one blob check sees only the first tool's head: measured on the 86-case mined pool, segmented 14 (16.3%) vs blob-only 10 (11.6%). It is an honest lower bound — the digest is budget-truncated, so a failed tool trimmed out entirely is invisible.

Derivation is resolved per trial, after the fault. That is deliberate: silent_failure replaces the evidence with a tool error under an unchanged success claim, which IS the population _escalate_confirm exists for, and it is what makes the hand-authored seed set exercise the direction at all (0 of 21 seed cases are naturally high-stakes; 70 of 107 silent_failure trials are — not 107, because one of the three injected failure bodies is (empty output), which production does not class as an error either).

So the arm has four values — raw_judge, judge+escalation(refute), judge+escalation(confirm), judge+escalation — and only the last is production-equivalent. A stale reader comparing arm == "judge+escalation" therefore fails on a half-escalated run instead of silently accepting it.

# raw judge (cheap judge standalone — neither direction can fire)
PYTHONPATH=src python scripts/verify_bench.py --base-url http://100.83.184.117:8088 --two-stage both

# judge+escalation — the pipeline production acts on (both directions)
PYTHONPATH=src python scripts/verify_bench.py \
    --base-url http://100.83.184.117:8088 \
    --main-base-url http://127.0.0.1:8088 --two-stage both

# one direction at a time, for an ablation
GHOST_VERIFY_ESCALATE_CONFIRM=0 PYTHONPATH=src python scripts/verify_bench.py ...

The report refuses to mix them. Two headline numbers are emitted under arm-qualified keys, each keyed on the direction that can actually move it — never a bare fpr, so a stale reader gets a KeyError rather than a wrong number:

  • fpr_raw_judge / fpr_escalated — clean trials refuted. Keyed on the REFUTE direction only: _escalate_confirm provably never emits a REFUTED, so it cannot move FPR or TPR, and keying on the full arm would be false precision that blocks a legitimate comparison.
  • false_confirm_actionable_raw / _escalated — corrupted trials that came back CONFIRMED, with the ≥0.7 actionable rate. This is what the 0.6 cap removes, and the bench reported it nowhere at all before.

report["provenance"]["escalation"] records the arm, a per-direction block (live / enabled / why-not / high-stakes trial count), which pool supplied the cheap route, and both endpoint/model identities; metrics["escalation_events"] counts refutes overturned, confirms withheld, and confirms eligible — the last because withheld == 0 otherwise reads the same whether the main model agreed every time or the direction was never invoked. All three are read off the verdicts, so "the direction fired" is evidence rather than inference. A live confirm direction with zero high-stakes trials is called out explicitly — that run measured nothing about it. Pre-2026-08-04 bundles carry a bare fpr and render as arm UNRECORDED; they are not back-dated to "raw".

A cheap-leg timeout is not a verdict

When route() fails it returns fallback, _call_llm falls through to the direct call, and that call lands on the main model. The trial still produces a verdict — the strong judge's. That is production-faithful, but a run that scores it as a cheap-judge verdict is reporting a blend it never names, and the failure is real: the durable log carries 9 worker node failed — Nova: ReadTimeout events, 5 of them at exactly +12.0/12.1 s, dead on _ROUTE_TIMEOUT_S. (Verify passes its own 45 s budget rather than that 12 s ceiling, so the bench's exposure is smaller — but "smaller" is an argument, not a measurement.) EscalatingChatClient therefore counts every cheap-leg call and logs failures at WARNING, not debug; provenance.escalation.route_health carries route_calls / route_failures / route_timeouts / route_empty_replies / fell_through_to_main, the rendered report leads with a loud warning when any call fell through, and optimize_verifier --incumbent-only both records the block and prints a "this baseline is a BLEND, re-record it" warning to stderr.

The bench cannot write to the production ledger

verifier.record_escalation() appends to $GHOST_HOME/system/verifier/escalations.jsonl, the §4F false-positive watch ledger — and the bench drives _escalate_refute hundreds of times per run in the operator's shell, where GHOST_HOME is exported. Folding bench refutes on curated fault cases into that ledger would corrupt the exact rate it measures (the same shape as self-play writing the production calibration corpus). The gate is a required live-turn req_id, which the bench never has. Verified from the bench side with a control: five bench escalations create no ledger file at all, while a record_escalation(trace={"req_id": …}) immediately after writes one row — without that control, "no file" would also pass if the ledger were simply broken. Fenced by test_a_bench_escalation_never_reaches_the_production_ledger.

Outputs verify_bench_out/<UTC-ts>/results.json + report.md (per-fault table + headline TPR/arm-qualified FPR, paste-able into the journal). The bench talks only to the judge endpoint and, on the escalated arm, the main model it escalates to — never the live agent or its data. Covered by tests/test_verify_bench.py (fault applicability, extraction round-trip, scoring math incl. the 0.7 gate, env hygiene of the arm runner), tests/test_verify_bench_case_pool.py, and tests/test_verify_bench_escalation_arm.py (the arm label is checked against OBSERVED call sequences through the real Verifier, so a change to the escalation predicate fails a test instead of mislabelling a report).

The mined case pool

The volume lives in $GHOST_HOME/system/eval/verify_bench_cases_mined.jsonl (86 cases), kept out of the repo because it derives from live user turns. It is the CLI's default pool; --no-mined reproduces the seed-only pool, whose private tier is too coarse to resolve a 0.02 ship gate.

# regenerate the pool (nothing else in the repo could, before 2026-08-04)
PYTHONPATH=src python scripts/verify_bench.py --refresh-mined

# clean measurement AFTER an optimize_verifier run
PYTHONPATH=src python scripts/verify_bench.py --tier private --two-stage both

Why --refresh-mined exists: the pool is a durable artifact, so before this it silently kept whatever extraction and redaction bugs were live on the day it was minted — it was still serving a case whose evidence had been mangled by a credit-card false positive. The refresh refuses to write a zero-yield mint or one that shrinks the pool by more than half (--force overrides): silent extraction failure is this pipeline's characteristic bug, and overwriting the pool with its output takes the private tier back to 4 cases.

Why --tier matters: optimize_verifier.py trains on the public tier of this same pool, so the default --tier all measures partly on cases the optimizer has already seen. The loader prints how many public-tier cases it pulled in; use --tier private for a post-optimization number.

Provenance (report["provenance"]) is what makes two runs comparable: case-set sha256, case count, duplicate-id count, the fault set and its hash, the judge endpoint + model, the escalation arm (raw judge vs judge+escalation, with both routes' endpoint/model), GHOST_HOME, and the enumerate / adjudicate / classic template hashes. Compare two reports only when it matches — two runs over the same pool against the same judge are still not comparable if one escalated and the other did not.

Streaming turns now get a (late) verdict too (2026-07-18)

The gap: the gated verdict was invoked only from _finalize_and_return — the non-streaming finalization chain — so every STREAMED answer (the web interface, project auto-advance turns) shipped unverified, silently: no verdict, no unverified-mutation check, no log line. Found when the operator asked why a project turn had no verdict: the late recorder logs every outcome yet the log had none, and a kill -USR2 task dump showed no verdict task alive. Verdicts had only ever fired for non-streaming clients.

The fix: the streaming closure's post-drain bookkeeping now spawns _compute_verifier_verdict as a background task and attaches the late-verdict handler. Design points:

  • Always late, regardless of GHOST_CRITIC_ASYNC: the text has already streamed, so an inline verdict could never amend it — blocking would buy nothing and cost stream-close latency. Zero added latency for the client.
  • force_correction=True: a streamed reply never carries an inline **Verifier note:**, so a high-confidence late REFUTED must queue the next-turn correction banner even outside async-critic mode (the recorder previously queued only when GHOST_CRITIC_ASYNC=1). The banner already surfaces: _take_active_correction prepends it at the next stream start. Lesson retraction and trajectory backfill run as before.
  • Eager captures: the outer finally deletes messages/tools_run_this_turn before the stream drains, and the old snapshot (messages[-10:]) loses the FIRST user message — which is exactly what _conversation_fingerprint keys the correction on (a mismatched fingerprint silently drops every correction). The gate captures a full shallow copy and computes the fingerprint at closure-creation time.
  • Noise control: skipped when the turn carried no substantive tool (toolless chat would add a no-op task and a "no verdict" line per message), and the claim strips <think> blocks so streamed reasoning doesn't eat the 2000-char claim budget.

Two streamed sub-paths (live finding, 2026-07-18). A streamed client request finalizes one of two ways: spontaneous-final turns (the model answers with no further tool calls — most interactive asks) exit through _finalize_and_return and re-stream the buffered answer, so they always had the gate (validated live: a weather test drew a genuine LATE REFUTED (90%) from the two-stage judge for citing the wrong station's data); forced-final turns (the loop forces a final generation — project auto-advance) stream live through stream_wrapper, which is the path this gate covers. Because the gate's first deploy was silent on those turns and logger.debug is captured nowhere at the running log level, every branch of the gate is deliberately LOUD: each skip reason (empty claim after think-strip, no substantive tool, no verifier attached), the deferred-spawn success, and the spawn failure all log at INFO/WARNING — a gate whose skip reasons are invisible cannot be distinguished from a gate that never ran.

Covered by tests/test_streaming_verifier_gate.py (force-correction semantics, handler threading, source-level wiring pins for the eager captures, and the every-branch-is-loud pin).

Bookkeeping state is never a verdict (2026-07-18)

Live wrongly-refuted regression (req 4836cc14): the user asked to restart the service; the agent restarted it and said so; the judge REFUTED (90%) with "the project is already complete — 14/14 tasks done" — the manage_projects ledger listing rode along in the multi-tool evidence window and the judge used task-ledger state as a verdict on an operational reply. Worse, that refute queued a correction banner which led the next turn, driving more "corrective" work that got refuted the same way — the verifier fed a churn loop (report → defect-reopen → --autoadvance-idle grind → rollup → refute → banner → repeat).

Both the classic claim prompt and the stage-2 adjudication now carry the dismissal rule: project/task bookkeeping state ("all tasks done", "project complete", "nothing left to do") is NEVER by itself grounds for REFUTED — an operational ask (restart/check/fix/run) is judged on its own evidence, and completion-state suspects are false alarms unless the request explicitly asked about completion. Validated against the live judge: the exact failing shape (seed case service-restart-done-project) is now CONFIRMED at 1.00 on both prompt arms. Two system-side brakes accompany it: identical correction banners dedup per conversation (_record_late_verdict), and defect-reopens on a DONE project are capped (_DEFECT_REOPEN_CAP per rolling 24 h, atomic metadata counter; past the cap the report logs a WARNING instead of re-entering the grinder). Covered by tests/test_project_work_log.py (cap + window), tests/test_streaming_verifier_gate.py (dedup), tests/test_verifier_two_stage.py (prompt pins).

JSON parse robustness

The verifier strips any <think>…</think> blocks the worker model emits, then attempts: direct parse → reversed greedy match → final greedy match. Returns None if no parse succeeds — callers treat None as "skip verification" rather than "verdict unknown".

Concurrency

Async; safe to call concurrently per request because the underlying httpx client per node already pools connections.

Executed-code reconstruction from tool_call_id

When the verifier gate in handle_chat classifies a turn as code-shape (last substantive tool was execute / postgres_*), it calls verify_code_output(code, output, intent). The code slot MUST be the actual program that was submitted.

Prior to the fix, the call site at agent.py:4835 passed code=tool_name — literally the string "execute". With nothing real to audit, the verifier LLM hallucinated plausible-sounding rejections ("appears to be a directory listing", "missing expected field") and emitted REFUTED (95%) verdicts on CORRECT turns. The user then saw Verifier note: … contradicting their right answer.

The fix is _reconstruct_executed_code(messages, tool_msg) in agent.py: walk messages backwards from the tool result, match tool_call_id to the assistant's tool_calls[i].function.arguments, and extract content / code / script_content / text / command / cmd (first non-empty wins). Capped at 4000 chars. When the lookup fails — malformed arguments, missing id, non-dict messages — the gate falls back to verify_claim, which doesn't need a code slot.

Covered by tests/test_verifier_code_reconstruction.py (14 cases including dict-vs-string arguments, alias preference, traversal past unrelated messages, oversize cap, identity-based dedup on duplicate tool-call ids).

Gate authority: REFUTED / unverified-mutation lower confidence (2026-06-07)

The gate used to be advisory-only: a high-confidence REFUTED verdict appended a **Verifier note:** to the reply but otherwise let the turn finalise as a success, and the finalize confidence reading — competence-driven — still read C ≈ 0.92–0.96, below=no. So the agent could mark a broken build "done" with high confidence (observed: a request that finished "REFUTED (95%)" on a game that did not run, and another that finalised an untested file write with the gate skipped at C=0.96).

The gate now has teeth without re-running the whole turn (which would double latency):

  • REFUTED ≥ 0.7 already sets verifier_backfill = ("failed", …); the finalize confidence block now reads that and passes outcome_penalty = 0.8 into CompositeConfidence.score(), pulling the reading below threshold so below=yes and the calibration spine records a "confidently-wrong" negative.
  • Unverified mutation — when the verifier is unavailable (v_result is None) and the turn's final substantive action was a successful file_system write/replace (_is_unverified_mutation), the turn is marked outcome="failed" with an honest "⚠ Unverified — run/preview it before relying on it" note, rather than a silent success. This is the untested-write case.

Net effect: a refuted or untested result no longer reports high confidence and is recorded as a failed outcome, so downstream task-completion logic stops marking broken work "done". Covered by tests/test_verifier_gate_teeth.py.

Autonomous repair re-entry (SHIPPED 2026-06-10)

The full autonomous repair re-entry — re-running tool turns against the verifier's critique — is now implemented (it was previously deferred as needing a core-loop refactor). When the verifier returns high-confidence REFUTED on the final answer (or the turn finalised on an unverified file_system write), the agent gets up to GhostAgent._MAX_VERIFIER_REPAIRS (default 1) bounded in-loop re-attempts to FIX it instead of only annotating and shipping.

  • The repair reuses the EXISTING for turn loop: at the normal-success finalisation (the if not tool_calls: branch) the verdict is computed, and on refute/unverified the critique is injected as a user message and the loop continues — no ~3,900-line re-indent.

  • Anti-loop accumulators and strike caps are PRESERVED across repair (bounded); only force_final_response is reset on re-entry. The trajectory records once, post-loop, on the final answer.

Async-critic repair — bounded verdict await at loop-exit (2026-07-07, #18)

The repair above originally fired only in SYNC mode. In production the launcher runs GHOST_CRITIC_ASYNC=1 (verdict on the off-host critic-nodes model), which used to skip the in-loop verdict entirely — so a REFUTED answer shipped with only a next-turn correction note. Because the critic runs on a second model, waiting for it briefly costs the MAIN inference slot nothing. So async mode now AWAITS the verdict at loop-exit for a bounded budget (_critic_repair_await_budget, default 25s, GHOST_CRITIC_REPAIR_BUDGET overrides, 0 disables) when the last tool is substantive and the deterministic unverified-mutation guard hasn't already tripped. If the verdict lands REFUTED within the budget, the same in-loop repair fires and the corrected answer REPLACES the refuted one; the verdict is cached so the post-loop gate doesn't recompute it. On timeout it falls back to the pre-2026-07-07 defer path (ship + queue a next-turn correction; the background verdict still scrubs poisoned lessons). This closes ledger item #4 as landed (sequential repair, critic-judged) — parallel best-of-N was rejected as strictly worse on a single-slot box. Covered by tests/test_critic_async.py.

Visual verification — closing the pixels gap (2026-06-08)

The text verifier audits words: it checks whether the agent's reply is on-topic and supported by tool output. For a visual bug report ("the blocks look transparent", "the layout is broken") that is structurally blind — the truth lives in the rendered frame, so a self-claim like "I split the meshes to fix it" passes as CONFIRMED while the screenshot still shows the defect. This was the live-log failure where a still-broken game was confirmed at 90%.

verify_visual(symptom, claim, after_image, before_image=None) closes it by looking at the actual pixels via the vision node (_call_llm_vision → chat_completion(..., use_vision=True); it does NOT use the text VERIFY worker pool, which isn't multimodal). When a before image is available the model does a before/after comparison, which is far more reliable than judging a fresh frame cold.

Verdict semantics — claim vs. pixels, not symptom-presence. The judgement is whether the agent's RESPONSE is honest about what's on screen: a "fixed it" claim while the image is still broken (or blank / stuck on a loading screen) → REFUTED; a claim that matches the pixels → CONFIRMED. Crucially, an honest "it's still broken, I couldn't fix it" is ACCURATE and stays CONFIRMED — the gate catches false success, it does not punish truthful failure reports. (Validated live: false-fix claim on a red circle → REFUTED 1.0; honest "still red" → CONFIRMED 1.0.)

Start/menu screen = not running (2026-06-09). The prompt now treats a visible start menu, a "Click to Play"/"Start"/"Press to start" button, an instructions modal, or a loading screen as proof the app has NOT started — it is showing its MENU, not its running state. A claim that the app/game "works", "renders correctly", "is fully functional", or "is playable" made over such a frame is REFUTED. This closes the live hole where the agent screenshotted a Minecraft clone with its "Click to Play" modal still up (blocks visibly broken behind it) and the claim was CONFIRMED at 90%; the browser tool's PRE_INTERACTION signal flags the same state in the tool evidence.

  • Gate (cheap, no LLM). _is_visual_intent(user_text) — keyword/extension match — keeps the extra vision call off the ~99% of turns that aren't about how something looks.
  • Evidence. _select_visual_evidence(messages, …, sandbox_dir) picks before = an image the user referenced, and after = a screenshot the agent produced this turn. If the only image in play is the user's own (the agent never re-rendered), after is None and the check is skipped — no post-fix evidence means no verdict. Container paths (/sandbox/…, /workspace/…) and bare filenames resolve to host paths via _resolve_image_path. Provenance beats name-matching (2026-07-31): paths appearing as an out_path in this turn's tool calls (native JSON args or XML parameter form, including interact sub-actions) are RENDERED by the agent and count as after-evidence even when the user's message names the same filename ("save it as functest_visual.png") — the old resolved != before_img exclusion classified exactly that render as the user's own image and skipped the gate (probe req 68033190). When the "user's image" turns out to be a file the agent wrote this turn, before clears to None: the user was naming the output, not referencing a pre-existing symptom shot.
  • Override. A confident (≥ 0.7) visual REFUTED overrides an optimistic text CONFIRMED — pixels win over the self-claim — and flows into the same verifier_backfill / outcome_penalty = 0.8 machinery above. Visual UNCERTAIN never overrides; a visual verdict only fills in when the text path produced none.
  • Conservative by construction. No browser / unreadable / oversized image → None (skipped, no penalty): the agent is never punished for infra it can't control. The vision model is itself fallible, so the bar to penalize is the same 0.7 used everywhere else.

Thinking suppression (2026-07-31) — the gate was silently inert on thinking vision models. Refute escalation: screen cheap, confirm expensive (2026-07-26e)

Symptom: web-research turns were being LATE REFUTED for correct answers — "the claim labels PostgreSQL 18.4 as the latest stable version without explicit confirmation from the tools" (90%), and a PDF-ingest turn refuted at 100% for stats the tool had literally printed.

Root cause (measured, not guessed): VERIFY rides the worker route, which on this box is Gemma 4 E4B — a 4B model — while the main box runs Qwen3.6-35B. Replaying three cases against both judges: the 4B scored 1/3 (it refuted a correct entailed superlative, and called 49152 bytes "not exactly 48 KB" — wrong arithmetic), the 35B scored 3/3, including correctly refuting a fabricated version. The prompt was never the problem; the judge's capability was. Prompt-only iteration was tried first and produced only partial improvement, which is what motivated measuring the model.

Fix: the cheap judge still screens every turn (no added latency, no main-slot contention on the common path), but a REFUTED verdict is now re-adjudicated on the MAIN model before it is allowed to act — _escalate_refute + force_main routing that bypasses both the critic pool and the worker route. On disagreement the strong model wins; on any error the original verdict stands, so escalation can only ever REDUCE false refutes, never make the gate less available. Cost is one main-model call on the rare refute path only. This matters because a false REFUTE is expensive: it scrubs the turn's lessons, files follow-up tasks, shows the user a correction banner, and marks the trajectory failed — poisoning the corpus every downstream learner trains on. Every one of those actions is gated on REFUTED specifically, so an overturn to CONFIRMED or UNCERTAIN is a safe outcome. Kill switch: GHOST_VERIFY_ESCALATE_REFUTE=0.

Confirm escalation: the other direction was ungated (2026-08-04)

Symptom (measured over the live stores, not inferred): escalation was one-directional by construction — _escalate_refute returns immediately on anything that is not REFUTED. Over the recorded window that is 50 REFUTED escalations (84% overturned by the main model) against 0 CONFIRMED escalations. Two further measurements make the asymmetry load-bearing: the ≥0.7 consumption gate is a no-op on the cheap judge — 130 of 130 recorded cheap verdicts came back at 0.9 or 1.0, so nothing was ever filtered by it — and since the 2026-07-31 honest-failure decision a CONFIRMED outranks a structural execution failure (resolve_turn_outcome rule 3 before rule 4). Result: 61 of 1488 live trajectories (4.1%) are outcome=passed with a failed tool call in the turn, each certified by a cheap 4B judge that nothing checked.

Still load-bearing after the 2026-08-04 shape rule. That rule (rule 2b) withholds a PASS only from the narrow subset where every tool call failed and the reply never said so — 8 of 1488 live trajectories. The far larger "some calls failed, the reply reads clean" population is exactly what this escalation exists for, and no shape rule can reach it: it needs a model to read the answer against the evidence.

Fix: a CONFIRMED is re-adjudicated on the main model when the caller marks the turn high-stakes — agent._turn_had_tool_failure(tools_run_this_turn), i.e. some tool actually failed, which is exactly when the verdict is what keeps the turn out of a FAILED label. The trigger is computed inside _compute_verifier_verdict, the one place every verdict is produced, so it cannot be live on the finalize path and dark on the in-loop/streamed ones. Firing rate on the live corpus: ~4% of turns, about two extra main-model calls a day — less often than the refute escalation it mirrors.

Deliberately NOT symmetric: a refute is punitive (auditor note to the user, lesson retraction, FAILED corpus label, auto-repair round), and "the strong judge would not confirm this" is weaker evidence than "the strong judge says this is wrong". So when the main model declines, the verdict KEEPS its CONFIRMED label and its confidence is capped at 0.6 — below every ≥0.7 consumption gate, the same idiom as _WEB_EXEC_SKIP_CONF_CAP. The turn is then recorded as unverified: no fabricated PASSED, no manufactured failure. On any error, an unparseable strong verdict, or a missing cheap route the original verdict stands (3 of 10 live replays came back unparseable — those are no-ops). A verdict already overturned by _escalate_refute is never re-escalated. The withheld case sets confirm_withheld, the mirror of escalated_overturn — both now recorded in the escalation ledger below (the to_dict() keys they were originally written to never reach production; see the next section).

Replay evidence: 10 of those live cheap CONFIRMEDs re-run on the 35B — 6 agreed, 1 was overturned (an explicit output-format constraint the cheap judge missed), 3 unparseable. Kill switch: GHOST_VERIFY_ESCALATE_CONFIRM=0 restores the exact one-directional behaviour. Default ON, because the failure it prevents (a fabricated success taught to every downstream learner) is durable while its own worst case is a turn recorded as unverified. Tests: tests/test_verifier_confirm_escalation.py (22).

The escalation ledger: where the watch metrics actually live (2026-08-04)

Symptom. escalated_overturn (the §4F false-positive watch metric) and its twin confirm_withheld were "persisted" into VerifyResult.to_dict() — a serializer with zero production callers (AST sweep of src/: the only to_dict reads belong to other classes; nothing in the turn loop ever calls the verifier's). The fix was recorded as done; it was inoperative.

Why not the trajectory record, the obvious candidate. On the STREAMED delivery path _record_turn_trajectory runs in the SSE drain before the stream verifier gate spawns the verdict at all — so a turn_facts stamp (the right tool for a fact known mid-turn) cannot carry a late verdict's flags there, and the web UI always streams. Stamping it anyway would have produced the usual defect: live on one path, dark on the other, with the darkness invisible because "no flag" and "no escalation" look identical.

Fix. One append-only JSONL at $GHOST_HOME/system/verifier/escalations.jsonl, written at the point the escalation RESOLVES — inside _escalate_refute / _escalate_confirm. That is path-independent by construction: finalize, in-loop auto-repair, and the streamed late verdict all funnel through those two methods. One line per escalation: {ts, kind: refute|confirm, route: claim|code, outcome: overturned|upheld|withheld|unavailable, cheap_verdict, cheap_confidence, strong_verdict, final_confidence, req_id, trajectory_id}. req_id/trajectory_id are threaded down as call ARGUMENTS from _compute_verifier_verdict (never read off the context — on the streamed path this code runs after the turn semaphore is released, the lesson core/turn_facts.py exists for), so every row joins back to the trajectory corpus.

Both outcomes are recorded, not just the interesting one. The watch metric is a RATE; a ledger of numerators cannot produce one — which is why "84% of refutes are overturned" previously needed hand-run log archaeology. unavailable (the strong model errored or came back unparseable, so the original verdict stood) is recorded too: a call was spent and changed nothing, and an escalation that silently no-ops is indistinguishable from one that never ran.

Read it with: jq -r '.route+"/"+.kind+"/"+.outcome' $GHOST_HOME/system/verifier/escalations.jsonl | sort | uniq -c — the cheap judge's false-positive rate is overturned / (overturned + upheld) within kind=refute. Kill switch: GHOST_VERIFY_ESCALATION_LOG=0; default ON, because the write is one short line on the rare escalation path (not per verdict), it never raises, and the whole finding is that the metric had nowhere durable to live. The file rotates to .jsonl.1 past 4 MB — rotation, never truncation.

Bench and self-play are excluded, deliberately. A row is written only when the caller supplies a live-turn req_id. scripts/verify_bench.py and optimize_verifier.py drive verify_claim through a two-legged client precisely so _escalate_refute fires — dozens of times per run, in a shell where GHOST_HOME is exported — and self-play/dream turns run the whole turn loop on a shallow-copied context. Either would corrupt the exact rate the ledger measures; the simulation gate is the same skill_memory.is_read_only marker the calibration corpus uses, for the same live reason (§4J). Tests: tests/test_verifier_escalation_ledger.py (36).

Code-path refute escalation: measured, and deliberately left OFF (2026-08-04)

verify_claim escalates REFUTED verdicts to the main model; verify_code_output never did, and the execute-shaped turns it judges are exactly the ones carrying structural failures. The gap was real. The fix was not — measured before changing anything:

  • system/llm_recordings/ 2026-07-30 → 08-04 holds 19 code-auditor verdicts, all on the cheap route: 12 CONFIRMED, 7 REFUTED, and 0 main-model code-auditor calls — proof the escalation never fired here.
  • All 7 cheap REFUTES replayed on the main 35B with the identical prompt and payload, twice: 14/14 upheld, 0 overturned.
  • Same recordings, claim path: 42 CONFIRMED vs 8 REFUTED main-model adjudications = 84% overturned. The instrument is calibrated; the rate simply does not transfer.
  • Mechanism, not luck: claim-path false refutes are DERIVED-FACT failures (49152 bytes → "48 KB", "the latest PostgreSQL is 18.4") needing world knowledge the 4B judge lacks. Every live code-path refute was a CONSTRAINT/COMPLETENESS failure ("didn't run step 3", "didn't start with the mandated phrase", "only one of the two price checks") — a text comparison the small judge gets right.
  • Cost if enabled: one main-model call per refute at 7–26 s measured, on the latency-visible in-loop auto-repair path; and 2 of the 14 replays returned EMPTY at the classic 2048-token budget (finish_reason=length — the 35B thinks), i.e. ~14% pure waste.
  • Population: 10 code-shaped refutes in 1488 live trajectories over 28 days (99 verifier refutes total), so the replayed sample is a large fraction of the whole population.

Disposition: wired, default OFF — GHOST_VERIFY_ESCALATE_CODE_REFUTE=1 enables it. When on, it re-judges with the CODE prompt (re-asking the claim prompt would adjudicate a different question) and composes with the confirm escalation exactly as the claim path does — an overturned refute is never re-escalated. The escalation ledger labels the code route either way, so the decision stays measurable without another bespoke probe. Tests: tests/test_verifier_escalation_ledger.py::TestCodeRefuteEscalation.

Claim fairness: head+tail packing + system-note stripping (2026-08-01, req 56221fad)

A 5,737-char reply drew a 90% LATE REFUTED whose three reasons were all instrumentation artifacts. The claim passed to the judge was a blunt final_ai_content[:2000]: it cut mid-sentence (judged as "truncated response"), hid the closing "✅ Ledger updated" confirmations (judged as "does not confirm project update"), and hid the mandated opening phrase sitting at char 2253 of the assembled reply. Two changes:

(a) pack_claim (module-level in core/verifier.py, used inside verify_claim): claims over 2000 chars keep their first 1200 and last ~700 chars around an explicit "[… ~N chars of the reply omitted here — mid-answer elision by the audit packer, NOT a truncated response …]" marker. Openings carry constraint compliance, tails carry confirmations; the middle is what a judge can spare. Idempotent — packed output re-packs to itself, so agent-side callers may pass full or packed text.

(b) strip_system_notes (core/reply_smoothing.py): the judged claim is the MODEL-AUTHORED reply. Finalize-appended notes — the ⚠ Unverified mutation note, the Plan-check note, the uncertainty risk summary, the prepended correction banner — are ours; judging them made the verifier refute its own INCOMPLETE disclaimer as "does not confirm the update". _compute_verifier_verdict strips them from the claim, the evidence packer's claim_text, verify_code_output's response and verify_visual's claim. The hedge auto-scan strips them too — it had flagged the Unverified note's "I cannot confirm it works" as a 40% assumption, which the risk summary then re-rendered into the reply as a garbled self-echo footer.

Follow-up filer filter: refute issues matching truncat|internal system message|system noise are packaging artifacts, never project work — they still surface via the correction banner but are no longer filed as "Verifier follow-up" tasks (the incident filed "Truncated response" onto the project's books).
