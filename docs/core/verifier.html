Coverage: what it is, and what it has to carry (2026-09-04, §4EP)

63% of the calibration corpus is the unverified-prior placeholder (§4EO) because most turns never get a verdict. Measured on the live log, of 160 finished origin=user turns 73 (46%) were skipped by this gate — and 71 of those 73 ran no tools at all. They are conversational or knowledge answers with no tool output to judge against; this verifier is evidence-grounded, so it genuinely cannot rule on them.

Coverage alone is the wrong target

The obvious response — extend the verifier to tool-free turns — was measured before it was built, and it does not work. On the live verdict population (n=402, 57 negatives), growing the corpus with CONFIRM-only labels shrinks the observed Brier delta by 2–16× across six seeds, because every added row is one the base-rate predictor already gets right: the effect collapses as fast as the interval does, and the comparison stays unresolvable at every size. Growth at the existing class mix leaves the effect intact (0.16–1.22×).

So the requirement is not coverage, it is negative-carrying coverage. A route that can only confirm buys a better-looking percentage and nothing else — and a route that refutes on absence of supporting memory is the false-negative trap this module already carries a truncation guard for. Pinned in tests/test_correction_adjudication.py.

Correction to an earlier reading: a single bootstrap of the live corpus suggested that same-mix growth at 2× would become resolvable. Across seeds that replicates about one time in three and is not a finding; only the confirm-only collapse is robust.

The tier that was nearly dead

user_correction is ground truth — the human said the answer was wrong — and it is the strongest NEGATIVE the system can obtain. It produced zero rows in the whole epoch. Over 1601 consecutive live turn pairs the promotion rule fired twice; 12 more cleared Signal A (the correction-opener regex) and were blocked by Signal B, a Jaccard overlap between the current message and the previous user request.

Hand-labelling those 12 found 6 genuine corrections ("No, that's wrong … the correct answer is Canberra", "no I was asking about the mysql problem") against 6 that merely open with "no": a topic change, a permission grant, an answer to a yes/no question, and one message asserting a false premise about the agent's own history. So Signal A alone is ~50% precise — dropping the conjunction would have poisoned the corpus, and keeping it costs ~70% of the tier.

No lexical signal separates the two classes. Measured on those 12: Jaccard(current, prior reply) is 0.000–0.167 for real corrections and 0.000–0.108 for the rest, fully overlapping; "did the reply end with a question?" is 4/6 in both classes — exactly zero information. The property is semantic, so Signal B is now a judge: does this message assert that the assistant's previous answer was wrong? asked of the reply, which is the parameter classify_user_correction had reserved for it since it was written.

Signal C — the rebuttal clause (§4IA, 2026-09-17). The live miss: the reply said "eckit is ECMWF's internal C++ library"; the next message was "eckit is not internal and you can request gribs from mars as a public user". No anchored phrase (Signal A) and Jaccard 0.1 with the prior request (Signal B), so the turn stayed passed until the human clicked 👎 forty minutes later. rebuttal_clause(current, prev_reply) finds a clause of the form subject · negation · object — every alternative in the negation list negates (is not, doesn't, never, …; a first draft admitted the bare copula and turned "leonidas was born march" into a rebuttal) — whose subject and object content tokens both appear in the reply, within the first 600 chars. Measured over 1,490 consecutive live pairs: 7 candidates (0.5%), five of them genuine. It is a candidate gate, never a promoter: is_correction_candidate() (phrase or clause) is the one gate in front of the judge, and a clause promotes only on contradicts=True; without a judge it never does, while A+B keeps its pre-§4IA behaviour. Pins: tests/test_user_correction_rebuttal.py.

  • Signal A remains the cost gate. It fires on 0.9% of live turns, so the judge costs about one call per 114 turns. has_correction_phrase is the single authority both the gate and the promotion read.
  • The judge decides when it rules. A semantic read of the actual reply outranks a token-overlap guess; the lexical test is not consulted alongside it.
  • None is not False. Every failure path — no verifier, no client, timeout, unparseable reply — returns None and restores the pre-§4EP lexical behaviour. The change can only ADD promotions, never silently remove one. False (a judge looked and said no) is a stronger answer and does suppress.
  • The affirmation veto still wins over a yes: praise that opens like a correction is never promoted, whatever the judge said.

Refute-capable coverage for tool-free turns (§4EQ)

The 46% gap above is closed the only way the measurement allows: a route that can refute. core/memory_claim_check.py checks age claims in a tool-free reply against the birth dates §4EL anchored in the profile — and it is refute-only by construction, not by policy:

  • A contradiction returns an issue. A match returns nothing — not CONFIRMED, not UNCERTAIN. The turn stays a placeholder exactly as it is today, so every label this route can ever add is a NEGATIVE, the scarce class (57 of 402 verdict rows). The module exports no way to express a pass.
  • Absence returns nothing either. The check fires only where BOTH a claimed value and a stored comparand exist, so "the store does not mention it" can never become "the answer is wrong". The refute-on-absence trap is made structurally impossible rather than guarded after the fact.
  • Arithmetic, not a judge. An age against a stored birth date is a computation: no model call, no prompt to be argued out of, and it cannot hallucinate a contradiction. §4EL anchored those dates so the value could be recomputed; this is the first consumer that recomputes one in order to CHECK something.

The tolerance is deliberately generous. A claim of N units admits a true age from one unit below to two above. The live case it exists for: a child of 5 months 23 days, where the store's own _age_phrase renders "5 months" and the user called it "about 6 months" — both right, and a pedantic check would have written a 0.0 on one of them. It still refutes what it is for: "9 years old" against a true 5.9 months is off by a factor of 18.

Binding is confined to one line. Distance alone was run over the 1977 replies in the trajectory store and produced three hits — all three false, every one a markdown list or table where subjects and ages interleave and the nearest name by character count belongs to the previous row ("| Vasilis | 1980-01-29 | 44 years |" bound Vasilis's age to Thodoris). A line is the unit these replies are organised in.

The subject is the name the phrase is predicated of — not the nearest one (§4FN round 3). Three review rounds of "the nearest name within N characters" each moved the defect instead of removing it: a nearby name captured any age at all ("Thodoris's laptop is 3 years old" and "Leonidas has a cot that is 20 years old" were REFUTED), while one word between a name and its own age ("Thodoris — now 9 years old, Leonidas — now 5 months old") handed the age to the other child; and the tie rule, the punctuation cue and the 60-character window turned out to be three redundant guards, any of which could be deleted with the suite green. The rule now reads the grammar the distance was a proxy for: the closest name before the phrase on its line is the subject when everything between them is a link — a copula, an age cue ("age", "aged", "'s age is"), a hedge ("about", "now", "currently"), punctuation (memory_claim_check._SUBJECT_LINK_RE) — and nothing else, and when the name does not close a list ("Thodoris and Leonidas: 9 years and 5 months old" is two ages, temporal.conjoined_subject). One word outside the link ("'s laptop", "goes to a school that", "and Maria") leaves the phrase unbound, which costs a label the route never had. The one backward form is the agent's own disambiguation, a bracketed name right after the phrase: "9 years old (Thodoris) and 5 months old (Leonidas)". There is no window and no tie any more — nothing left to calibrate. Names are Unicode, so a Greek-spelled profile entry is a subject. After the rules: zero refutations across the same 1977 replies, while the contradictions still fire.

What the link must not admit (round 4). A fourth reviewer generated 63 phrasings of its own and executed them; seven false-refute classes came out of the whitelist itself, and each is now a rule with a two-direction pin: tense — "was", "turned", "turns", "at", "in", "on" were links, so "Thodoris was 4 years old when you moved" and "Leonidas turns 7 months old on October 12" were compared with today (the marker can sit before the name, so the whole LINE is read, temporal.tense_marked, by the checker and by the writer, which had stored "born ~2021-03" for a child born in 2016); "of" — the age of "the father of Thodoris" belongs to the noun before "of", in a reply and in a stored value; a bare possessive — "Thodoris's 5 month old brother" (only "'s age" links); the forward candidate outranking the phrase's own bracket — "9 years old (Thodoris), 5 months old (Leonidas)" (a bracketed name is an annotation of the phrase before it, never the subject of the next; a markdown link is not an annotation); decimals — "9.5 years old" read as five and "5.8 months" (the checker's own rendering) as eight, fixed in the shared number token so the writer stops at them too; week and day claims compared on the calendar-month scale ("26 weeks" for 25 weeks 1 day refuted) — now on their own scale, with five percent slack for a large count; and bare digits as links ("| Thodoris | 2 | 3 years old |" is a count of bikes) — only date SHAPES link. Also from round 4: "1 year old" admitted a newborn (the lower bound is never below half the count); a name with two stored dates decides nothing; a sentence opener before a comma ("Yes, Thodoris") is not a list — a comma joins two names only for the checker (which knows its names) and the reader (the last defence for stored values), never for the writer; the plural guard reads the whole line, not 80 characters; and every word left on the link list has a catalogue pin that fails the suite if a word is added without one.

The consumption guard had to widen, or this was dead code. It read last_tool is not None — false for every verdict this route can produce, since the route exists for tool-free turns. The verdict would have been computed, logged and consumed by nothing. verdict_is_consumable now asks the question the guard meant: tool evidence answers "applicable", and so does a produced REFUTED. A tool-free CONFIRMED/UNCERTAIN is not consumable — the memory route never emits one, so such a value would be a verdict from somewhere unaccounted for, and it fails closed.

Expected yield, stated honestly. Against the whole historical corpus this route refutes nothing, because the agent's age arithmetic has so far been right. It is a guard that fires when that stops being true, not a source of label volume. What it changes is that a tool-free turn is no longer unfalsifiable. Pins: tests/test_memory_claim_check.py (24); mutation battery 16/16 killed.

The judge against 121 human labels 2026-09-08 · §4FN

Measured: of 121 human-labelled turns (2026-08-13 → 09-08) the verifier had a verdict on 37 (24 agree, 13 disagree) and none on 84. Three of the six false REFUTEs were one parser bug — a compound age ("5 months and 23 days old") read as its tail ("23 days old"); memory_claim_check._age_claims now takes compounds first, as one claim (in months — see below). Routing

Tries llm_client.route(task="VERIFY", max_tokens=2048, ...) against the worker pool first — both cheaper and a different "perspective" than the foreground model. Falls back to a direct foreground call if the worker pool is empty or its circuit is open. When a dedicated critic pool is configured (--critic-nodes) it takes precedence over both, with its own budget (GHOST_CRITIC_CALL_TIMEOUT, default 120 s).

Verify-sized worker budget (2026-07-16). The worker-route call used to inherit route()'s default _ROUTE_TIMEOUT_S (12 s — sized for sub-second routing chores). A verdict takes 7–11 s uncontended on the live worker (Gemma 4 E4B), so any contention on the node pushed it past the ceiling: Nova: ReadTimeout → no gate verdict → a hallucinated answer shipped unchecked (req 738c/35, the "Everest pizza" turn), caught only by the late async verdict a full turn later. _call_llm now passes its own budget — _VERIFY_WORKER_TIMEOUT_S, default 45 s, env GHOST_VERIFY_WORKER_TIMEOUT — through route(timeout=…). The loop-exit repair budget (25 s) and the late-verdict handler already tolerate a verdict that lands after the reply, so the longer ceiling costs the user nothing; a genuinely sick node still fails bounded. Covered by tests/test_verify_worker_timeout.py.

Two-stage claim verification: forced identification → adjudication (2026-07-18)

The single claim prompt asked one yes/no-shaped question — "is this reply acceptable?" — and that shape is dominated by a default-answer prior: the judge model often carries the signal that a specific fact is unsupported yet never surfaces it, because nothing forced it to look at that fact. This is the mechanism identified in "Mechanisms of Introspective Awareness" (arXiv:2603.21396): detection-willingness gates suppress latent detection, and forced identification extracts substantially more signal than detection-willingness allows — at the price of false positives if used alone (ungated enumeration hallucinates problems).

verify_claim therefore now runs two calls by default (GHOST_VERIFY_TWO_STAGE, on unless =0, read per call so it can be flipped without a restart):

  • Stage 1 — _VERIFY_ENUMERATE_PROMPT: no verdict asked. The judge MUST name 1–3 of the reply's weakest fragments (exact quotes), each classified as alignment / support / constraint / artifact. Suspects are sanitized (_sanitize_suspects: max 3, 300 chars/field, unknown labels degrade to support) so a runaway response can't blow the stage-2 prompt.
  • Stage 2 — _VERIFY_ADJUDICATE_PROMPT: re-embeds claim + evidence + the numbered suspects and adjudicates EACH as real-problem vs. false-alarm under the strict rubric — this is where FPR control lives. It keeps the classic prompt's dismissal rules (all tool outputs judged together; one failed tool doesn't refute what another supports; paraphrase/rounding ≠ fabrication; blank request voids alignment) plus one drawn from the evidence-packer incident: truncated-but-consistent evidence is grounds for UNCERTAIN at most, never REFUTED. Output is the standard verdict JSON, so _build_verify_result, the ≥0.7 consumption gates, repair, and the late-verdict handler are all unchanged.

Fail-safe: unparseable stage 1, an empty suspects list, or unparseable stage 2 → fall back to the classic single prompt, so the pipeline is never less available than before (worst case: one bounded extra call). The adjudicated suspects ride along on VerifyResult.suspects for logging/bench use.

Stage-call payload discipline (measured on the live judge, 2026-07-18). First probes against Nova (Gemma 4 E4B heretic) showed a 60-token verdict costing 600–1200 completion tokens / 30–90 s — three separate failure modes: a nondeterministic <|channel>thought reasoning prelude on the adjudicate prompt, pretty-printed/fenced JSON, and looping the same verdict to the token cap (the server runs repeat_penalty=1.0). The stage calls therefore carry: the no-think soft+hard switch (/no_think + enable_thinking=False, same idiom as the critic path; kill switch GHOST_VERIFY_STAGE_NO_THINK=0), stop: ["\n"] (a minified answer is one line, so any newline is either the natural end or a malformed answer — both cut instantly), a "MUST start with {" prompt line, and a tighter output cap (GHOST_VERIFY_STAGE_MAX_TOKENS, default 1024). After the fix: enumerate ~41 tokens / 3–5 s, adjudicate ~63 tokens / ~4 s, 100% valid JSON over repeated probes. Deliberately NOT response_format=json_object: grammar-constrained sampling made this judge MORE verbose (41 → 786+ tokens, truncating at the cap). A malformed stage answer fails fast (~3 tokens) into the classic fallback. The classic path's payload is untouched (it remains the deployed baseline — measured at ~637 tokens / 42 s on the same judge, i.e. brushing the 45 s worker timeout).

Discipline nearly cost the catch rate — caught and fixed by the bench (2026-07-18). The first disciplined version (terse 1–3 suspects, 63-token adjudication) measured TPR 0.42 vs classic's 0.75 on the live A/B: the terse stage 1 named one trivial suspect and missed the injected fabrication entirely, and stage 2 only adjudicated named suspects. Three fixes recovered it: stage 1 must name EXACTLY 3 suspects with at least one word-by-word-checked specific fact; stage 2 fills a per-suspect "checks" array BEFORE the verdict fields (structured deliberation inside the JSON, replacing the free-form thinking the no-think switch removed); and stage 2 may flag real problems beyond the suspects list. Re-measured: TPR 0.75 / FPR 0.0 at ~16 s per verdict — classic's catch rate at ~2.5× its speed (classic: 0.6–0.75 at ~40 s). Remaining blind spots are judge-level (Gemma 4 E4B), shared by every arm: injected diff-markers never caught (0/6 across all configs), single-digit number swaps (34→35 °C) usually missed, and truncated evidence still draws spurious REFUTEs (the packer shape — rubric wording alone does not fix it). Small-n caveat: 2 seed cases; the full 12-case A/B (~90 min on nova) is the calibration baseline to run before/after any judge-model change.

Cost: one extra VERIFY-route call per claim-shaped verdict (the code and visual paths are unchanged) — and with the stage discipline the two-stage pipeline measured faster end-to-end than one classic verdict, because the classic prompt puts no ceiling on judge verbosity. Each call keeps its own bounded timeout (GHOST_VERIFY_WORKER_TIMEOUT, 45 s); with critic/async mode the calls are invisible to the user. Covered by tests/test_verifier_two_stage.py.

Self-consistency on the adjudication — routed by difficulty (§4BR, 2026-08-16)

The verifier's miss side is 0.218 false-CONFIRM, and A1 measured that the judge's own confidence carries no information about it (AUC 0.5087 — chance). So the usual "act when the model is unsure" lever does not exist here. Cross-sample disagreement is a signal the judge does express and the confidence field does not: three identical repeat runs of the real path (2026-08-10, cache off) disagreed on 2 of 12 trials, both artifact_leak (36% of the miss mass) and in both the majority verdict was the correct one, while clean never varied — so the FPR gate survives.

_adjudicate_self_consistent samples stage 2 n times and takes the majority. GHOST_VERIFY_SELF_CONSISTENCY is the global default (unset ⇒ 1 ⇒ byte-identical to the single-sample path, capped at 5, even values rounded down since an even vote has no majority). Since §4BR it is also reached per-turn by the verify_depth arm — see experiments — which raises it to 3 on turns the complexity router called confidently hard.

  • Sequential, not concurrent — and that is a measurement. This ran under asyncio.gather with a comment asserting that serial sampling would multiply latency by n. Timed against the live critic on the real 2,285-token adjudication prompt: 1 sample 10.8 s, 3 sequential 17.8 s (10.3 / 2.7 / 4.7), 3 concurrent 24.9 s. llama.cpp keeps a per-slot prompt cache, so repeating the same prompt on the same slot skips the prefill, while concurrent samples are dealt to different slots and each re-prefills. The parallelism was being bought with cache misses.
  • Early stop. The vote is drawn until decided, not until the budget is spent: once the leader's margin exceeds the samples left, no remaining draw can change the winner. At n=3 the common case (first two agree) costs 2 samples. The bound is strict (>, not >=) because a runner-up drawing level produces a tie, and ties resolve to sample 1 — a loose bound changes verdicts at n=5.
  • The winner is the first agreeing sample in draw order — deliberately not an order statistic on confidence, in either direction. Taking the most confident agreeing sample makes majority-of-k a max-of-k on confidence, lifting verdicts over the 0.7 action threshold; the "lower median" that replaced it is the minimum whenever k=2, which is the modal case under the early stop, and suppresses corrections just as reliably. Draw order has no rank in it: when the vote is unanimous the returned object is literally control's own sample.
  • Two stop conditions protect the inference slots. If a sample comes back on the main route (the cheap pools fell through — live, --critic-nodes and --worker-nodes are the same box) the vote stops at that sample rather than serializing n calls on the single foreground slot. Separately a whole-vote wall-clock budget (GHOST_VERIFY_VOTE_BUDGET, default 60 s, 0 disables) bounds the partial-outage case that the route guard cannot see — critic timing out at 120 s while the worker still answers keeps route="worker", and three samples would cost 3×165 s. Note it prevents starting a sample, so the true bound is the budget plus one per-call bound. Both stops log at WARNING: they are the decision rule's abort signals, and the live agent runs at INFO.
  • Attribution. self_consistency_n / _agree / _drawn (parsed, agreeing, attempted) are declared fields on VerifyResult, appear in to_dict, and are written to the verdict sidecar as sc_n/sc_agree/sc_drawn. They are published out of band by the sampler as well, because the result object is not a reliable carrier: the escalation ladder builds replacement objects (five sites), and when every sample fails to parse there is no object at all — verify_claim falls back to the classic prompt and would otherwise file a turn that paid for three samples as a control turn that never voted.

Covered by tests/test_verify_self_consistency.py and tests/test_verify_depth_routing.py.

Score-token probe — confidence sharpening (§4F Phase 3a, §4BF Track 2 flip i)

The two-stage judge's confidence SATURATES (mean 0.92–0.99 on the standing bench), so the ≥0.7 actionable gate barely discriminates. GHOST_VERIFY_LOGIT_EXPECT (default OFF, read per call) adds one bounded probe after adjudication on CONFIRMED/REFUTED verdicts only (UNCERTAIN is excluded — the acceptability scale doesn't map onto "cannot judge"): a 0–9 rating prompt on the cheap pool (max_tokens=4, top-10 logprobs via entropy.request_logprobs), whose digit-mass expectation (_digit_expectation) becomes p(acceptable) ∈ [0,1]. The probe never changes the verdict. Its consumer is the §4BL verdict-gated CONFIRM cap (cheap pass only — MAIN two-stage results under the §4BK kill switch are never capped): a CONFIRMED result whose reading falls below GHOST_VERIFY_PROBE_CAP_T (default 0.966, frozen on the corrected pass-through, leakage-excluded design half of the flip-i data — the §4BL R1 review caught the first freeze optimizing on overturn-carried phantom readings) has its confidence capped at GHOST_VERIFY_PROBE_CONF_CAP (default 0.6 — below every ≥0.7 consumption gate); REFUTED gets its reading recorded and nothing else (§4BJ measured the probe erring toward "acceptable" on genuinely-faulty claims). This REPLACED the original w-blend (GHOST_VERIFY_LOGIT_EXPECT_WEIGHT, now vestigial): the §4BI foreclosure proved no light symmetric blend can move the judge's quantized {0.9, 0.95, 1.0} confidences across the 0.7 gate (and the 2026-07-30 w=0.5 A/B had already collapsed actionable TPR to 0.347). Rule: system/eval/probe_redesign/DECISION_RULE.md. ⛔ OUTCOME (2026-08-14): NULLed by the held-out validation half and RETIRED. Judge-model selection — the 45-second envelope (2026-08-05)

The cheap judge's false-refute churn (FPR 0.31–0.385 on the bench; ~84% of live refutes overturned on escalation at ~8–18 main-slot calls/day) motivated a judge-model search. Two hard requirements fell out, and they pull against each other:

  • Rule application. The E4B carries the adjudication rubric but cannot apply it — two GEPA prompt rounds were cleanly rejected by the private gate (−0.131, −0.119), and the 2026 judge literature finds models under ~12–14B cannot leverage added judge guidance at all. Bigger, or judge-trained, is required.
  • The latency envelope. A verdict must fit GHOST_VERIFY_WORKER_TIMEOUT (45 s) under the worker node's normal contention — and a timed-out cheap leg silently falls through toward the main model, converting the "cheap" judge into foreground load. Measured on the shared 16 GB M4: Gemma 4 12B runs 40–70 s/verdict once live worker traffic evicts the rubric from the server's prompt caches (the making room for prompt cache entry log line is the tell) — measured out on this hardware, independent of its accuracy. The E4B fits with room to spare (7–11 s uncontended); a dense 12B does not.

The deployment shape that reconciles them: a dedicated critic pool. The verifier only rides the worker route when --critic-nodes is unset. Running a judge-trained 8B (its rubric internalised in the weights — shorter prompts, faster prefill, evaluator-tuned FPR) as a second llama-server on the worker box, wired as --critic-nodes, leaves the E4B doing everything it measurably wins (general worker tasks, audio) while adjudication gets a model built for it — and a dedicated server also ends the prompt-cache eviction war. Dual-server residency on a 16 GB box needs the wired-limit + small-compute-batch recipe and a real-decode health probe (/health answers while Metal-OOM decodes fail); the full recipe lives in PROJECT_JOURNAL §6 2026-08-05 (evening).

Measured verdict (2026-08-05, both arms benched): Selene-1-Mini does NOT clear the bar — rejected. Escalation discipline (2026-08-06) — overturns must be earned

Built the morning after the measurement above. The root defect it closes: the refute escalation re-adjudicated from scratch — the main model never saw the cheap judge's issues, and, being the author of the claim under audit, it confirmed its own work nearly always. Three mechanisms, all fail-closed, each with a kill switch:

  • The rebuttal burden (GHOST_VERIFY_OVERTURN_QUOTE, default OFF since 2026-08-06 — it lost to the legacy pipeline on the same seeds). The escalation prompt now presents the refute's numbered issues under third-party framing ("you are NOT defending the claim") and may overturn only by, per issue: an evidence quote — validated by Unicode-folded, normalized containment, or (v2 calibration) a verbatim common core of ≥ 15 characters when the quote's edges were trimmed or lightly paraphrased; pure paraphrase still fails — or a known FP-class from the FP-trap taxonomy (subjective_gloss, derived_value, paraphrase, formatting_or_style, instrumentation_echo, version_labeling, extra_detail, and — v2 — truncated_evidence, because a budget-truncated digest cannot host a quote for a span it cut, which is where the v1 ON-arm's 0.818 degraded-evidence FP came from). Coverage is enforced: the validated rebuttals' issue indices must cover every issue (with a count fallback when the model returns no usable indices), so one valid rebuttal cannot overturn a multi-issue refute. A concession, an unknown class, a fabricated or short quote, missing coverage, a missing/NaN confidence, an UNCERTAIN verdict, or unparseable output → the refute stands. Also a deliberate semantic change: an unearned UNCERTAIN from the main model used to replace the refute; that dodge lane is closed — only an earned CONFIRMED overturns. Same call count as before, strictly more informed. The code-path escalation (default off) keeps its injected re-adjudication and is exempt from tier routing. Honest limits, stated: the machine validates containment and coverage — a quote's relevance to its issue remains model-asserted (any sufficiently long evidence span passes containment), and evidence is partially attacker-controllable (web content), so the burden raises the cost of a lazy overturn; it is not a security boundary against evidence-resident injection.
  • Verdict-tier routing (GHOST_VERIFY_TIER_ROUTING, default OFF, same gate). A refute whose every stated issue is a digit-free gloss-shaped objection is downgraded to UNCERTAIN with no main-model call at all — ledger outcome downgraded. The classifier was calibrated against 20 real overturned-refute issue texts from the live log (three shapes: meta-language objections, the quoted-pleasantry shape that dominates live false alarms, instrumentation echoes) with zero false downgrades of substantive issues; anything carrying a digit escalates, so "0 mm is not 'no rain'" gets the rebuttal treatment rather than a free pass. Worst case of a wrong downgrade is an unverified turn — UNCERTAIN fires no punitive path.
  • Soft-overturn cap. An overturn earned only by FP-classes (no validated quote) keeps CONFIRMED but is capped to 0.6 — below every ≥0.7 consumption gate — so a soft overturn records the turn as unverified instead of laundering a clean pass (the req 03b96c28 class).

Arithmetic before opinion — the objection check (2026-08-06)

Four escalation-policy arms failed the ship gate because they were all arbitrating opinions. The cheap judge says "wrong", the main model says "fine", and any policy that trusts one loses whatever the other was right about — so the rebuttal burden, tier routing and their calibrations all slid along a single FPR↔TPR trade curve (0.591 → 0.717 → ~0.73) without crossing it.

What broke the deadlock was a measurement, not a design. Collecting all 145 distinct false-alarm objections across the completed arms showed that 43% are not matters of opinion at all: the largest file is 18,433 bytes, not exactly 18 KB is 18433 ÷ 1024 = 18.0; 396,000 vs 396,960 is a rounding; humidity 28% is not in the evidence is settled by searching the evidence. Those are the systematic classes the small judge gets wrong and that two GEPA prompt rounds could not fix — they need float() and in, not a better model.

Provable objections are settled with no model call and are protected from the overturner — which is where its heaviest measured damage lived (fact_swap, artifact_leak, fabrication). Measured cost of being wrong: 2 hardened false alarms and 1 erased catch. The evidence packer — the third subsystem (2026-08-06)

Three benched arms of escalation policy kept leaving one column untouched: degraded-evidence false refutes at 0.485–0.625. The cause was not the judge or the escalation but the packer that builds the digest: _collect_verifier_evidence assembled its output with body[:granted] — silent, head-only truncation. A live judge therefore received tool output cut mid-stream with no indication it had been cut, and if the claim's supporting span sat past the cut, X is not in the evidence was a literally correct observation about a mutilated digest. The rubric's long-standing rule — truncated output consistent with the claim is UNCERTAIN at most, never REFUTED — had nothing to trigger on.

  • Truncation is now marked, self-describing and machine-detectable (evidence_was_truncated()): how much was shown of how much, and that absence is not proof of fabrication.
  • The packer keeps what the claim leans on. When the claim's significant tokens appear past the cut, _slice_evidence_body keeps a head window plus the best claim-overlapping later window rather than the head alone. The marker and separator are inside the granted budget, so the assembled digest still cannot exceed the caller's cap.
  • A mechanical guard replaces the prose rule. _guard_truncated_absence downgrades a REFUTED to UNCERTAIN before escalation when every stated issue is an ABSENCE complaint over a marked-truncated digest — no LLM call. Contradictions, constraint violations and machine-noise allegations are untouched: those are judgeable on a partial digest. Kill switch GHOST_VERIFY_TRUNCATION_GUARD=0.

The absence-vs-contradiction classifier was calibrated on the bench's real degraded-arm issue texts and separates cleanly (all four real absence complaints match; all five real contradiction complaints do not).

The ledger gains a rebuttal field (quote/fp_class on overturns; invalid/concede/coverage/unparseable on refusals) and the outcome vocabulary gains downgraded, plus truncation_guard, mechanically_upheld and mechanically_dismissed; scripts/escalation_audit.py reads both, and learning-health renders the downgrade count per arm. The bench now emits the ship-gate metrics this work is judged by: overturn_rescues / overturn_damage (and the downgrade twins) in escalation_events — the 2026-08-05 ad-hoc attribution, formalized. Covered by tests/test_escalation_discipline.py; the escalation-arm fences were updated to the contract (a bare CONFIRMED from the main leg no longer overturns anything, and the fences prove it).

The CONFIRM direction fires only when the caller passes high_stakes=, and run_trials never did — so it was structurally dead in the bench even with the two-leg client installed, the same shape as the missing worker route. Bench cases now carry the flag: BenchCase.high_stakes is tri-state (None = derive, an explicit bool pins the case), and derivation runs looks_like_tool_error — production's own sniffer, not a second copy — over each segment of the packed evidence digest. Segmenting matters because that sniffer only scans the first 120 characters for its text markers, so one blob check sees only the first tool's head: measured on the 86-case mined pool, segmented 14 (16.3%) vs blob-only 10 (11.6%). It is an honest lower bound — the digest is budget-truncated, so a failed tool trimmed out entirely is invisible.

Derivation is resolved per trial, after the fault. That is deliberate: silent_failure replaces the evidence with a tool error under an unchanged success claim, which IS the population _escalate_confirm exists for, and it is what makes the hand-authored seed set exercise the direction at all (0 of 21 seed cases are naturally high-stakes; 70 of 107 silent_failure trials are — not 107, because one of the three injected failure bodies is (empty output), which production does not class as an error either).

What a verification says in the log

Until 2026-08-10 the verifier logged a verdict only on escalation events — the interesting exceptions. A routine verify ran, decided, and said nothing. That was masked while critic compute — Routing verification fired 1652 times per 4000 log lines; once those were demoted to DEBUG (41% of the log, carrying no information) the subsystem went silent. The log swung from "1648 announcements, 6 outcomes" to almost nothing, and neither is a usable view.

Every verification now emits one line carrying what it CONCLUDED — verdict, confidence, elapsed, and which mechanism settled it:

verify  REFUTED conf=0.95 12.4s · objection upheld
verify  CONFIRMED conf=0.88 8.1s · escalation OVERTURNED

Those marks are the same rescue/damage counters the bench reports in aggregate (objection_upheld, truncation_guarded, escalated_overturn, confirm_withheld, tier downgrade) — previously visible only as a 433-trial total, now per turn. A None result logs SKIPPED rather than nothing, because silence would read as "the verifier never ran".

It is a wrapper, not a line per return. The implementation has eight return points; a log call at each is how a logger ends up incomplete — the same "one logger, complete" lesson recorded for the escalation double-count. verify_claim now times and delegates to _verify_claim_impl, so exactly one outcome is emitted whichever path fires, including early bail-outs. The public signature is unchanged, which matters because verify_bench.verify_claim_accepts_high_stakes introspects it to decide whether the CONFIRM-escalation direction can fire at all.

Level follows who is asking, the same rule as the LLM routing lines: a background verification (self-play, REM, failure-dimension tagging) is plumbing at DEBUG; a request-scoped one is what the operator is watching, at INFO. So the outcome line does not reintroduce the idle-loop flood it replaced. A failure inside the logging is swallowed — instrumentation must never be able to fail a turn — while a genuine error from the verification itself still propagates.

Rule 3 and the bare-word allegation

The objection check's rule 3 asks a question that needs no model at all — is the alleged machine noise literally in the claim? — and it is gated behind _is_noise_allegation, which requires a noise word next to "artifact"/"marker" because those are ordinary English ("the wrong build artifact" is a content objection). Sound in general, and it hid a measured defect: the cheap judge's issue text for this fault class is frequently the bare word artifact, which fails the gate. Rule 3 never armed, the objection escalated unresolved, and the strong model dismissed a complaint that carried no argument — "All suspects are false alarms." 23 of artifact_leak's 58 trials were overturned, every one wrongly, dragging its catch rate to 0.431 when the cheap judge had actually achieved 0.828.

The fix is narrow: the ambiguity the gate protects against cannot arise once the claim is known to contain the markers, so when _claim_noise_markers finds them, a bare artifact word is accepted as the allegation. The conservative half is untouched — fences are still stripped first, +++/--- still count only in diff-header shape, and a bare "artifact" on a clean claim still escalates. Measured by paired McNemar on a strict replay (judge held fixed, so the delta is attributable to code): balanced 0.8130 → 0.8251, refute 0.7424 → 0.7667, non-refute unchanged, 8 trials fixed / 0 broken, p=0.0078.

A stronger variant was measured and REJECTED, and the reason is worth keeping. Upholding whenever the claim contains markers — regardless of how the issue was worded — scores better on the bench's balanced metric (0.832, p=0.0225) but raises FPR 0.121 → 0.138 and degraded-evidence FP 0.111 → 0.133, because it also protects wrong refutes on clean claims that happen to contain marker-like text. Weighting the two error types by base rate, it wins only above ~40% corrupted; the bench is 76% corrupted by construction and production is nowhere near that. A fault-injection bench's class mix is not production's, so a balanced score on it can rank a change backwards — check the decision against a realistic base rate before shipping.

Making a re-bench cheap — so the number stops going stale

A full live bench is hundreds of judge calls plus a main-model adjudication on every REFUTED — roughly 90 minutes. Nobody pays that on each code change, so in practice the last number gets quoted long after it stopped describing the system. That is not hypothetical: the 2026-08-04 baseline (balanced 0.766) was measured on the worker route, and since 2026-08-06 production's cheap judge rides the critic branch. The file and the deployment were never the same system, and nothing said so.

The remedy is not "re-bench more often" — it is to make staleness computable, so a re-bench happens exactly when one is owed:

TierCommandCostAnswers
0scripts/verify_bench_status.py~0s, no LLMdo I owe a re-bench at all?
1verify_bench.py --cache-mode readseconds–minutesdid my change move the number? (judge held fixed)
2verify_bench.py --cache-mode offfullwhat is the number today?

Tier 1 and Tier 2 answer different questions and must never be confused. A replayed report measures the CODE against a frozen judge — every difference is attributable to your change, which is exactly what you want when attributing a delta, and exactly wrong as a statement about current quality, because holding the judge fixed also hides its drift and sampling variance. provenance.cache.measures therefore labels each report live judge, code-vs-frozen-judge (replayed), or MIXED live/replayed — NOT a clean attribution. Measured on a 16-trial slice: 4m27s live → 3.0s replayed (59/59 cache hits), with verdicts, confidences and every escalation flag bit-identical.

The cache is content-addressed on everything the endpoint sees, so a changed prompt, model or endpoint misses by construction — a stale answer cannot be served to a new question. Two subtleties were found by measurement rather than reasoning:

  • The packer nonce made the cache useless and said nothing. agent._PACKER_NONCE is a uuid4 minted at import and embedded in the evidence-truncation marker (…[PACKER CUT#53d14ea5: 237 of 309 chars shown]). It must stay unguessable — a bare substring test is forgeable by evidence the agent itself read — but it makes every prompt containing a truncated digest unique per process. First strict replay: 16 of 69 calls missed, exactly one per trial. Production is untouched; the nonce is normalised out of the cache key only, by a pattern narrow enough that it cannot collapse two genuinely different prompts.
  • "MIXED live/replayed" was two different situations wearing one label. A run interrupted and resumed minutes later blends a live half with a cached half that is equally current — a perfectly good absolute measurement. A run padded out of a week-old cache blends in answers from a judge that may since have moved. Both printed the same label, so provenance.cache.replay_age_s now reports the oldest and newest age of the responses actually replayed, and a reader can tell a resume from a stale top-up.
  • A strict miss is swallowed into a null verdict. The verifier treats the raised KeyError as an unparseable judge reply, so a replay that did not replay looked like a run with a few "skipped" trials and printed its scores normally. Strict misses are now counted, dumped to strict_cache_misses.json, warned about, and exit code 3.

The fingerprint gained the component that was missing. bench_provenance recorded templates and flags but never the code — so a change to _escalate_refute, the truncation guard or the objection parser moved every number in the report while provenance stayed byte-identical. It now carries a code block with two separate semantic digests: verifier (the system under test — a change there is a result) and bench (the ruler — a change there is not). Both are AST digests with docstrings stripped and positions dropped, so comments and reformatting are invisible while any change to logic or constants is not; on a codebase this heavily commented, a raw file hash would cry wolf until it was ignored.

The oracle reports three states, not two. UNKNOWN is not CHANGED: a baseline recorded before a field existed cannot be compared on it. The first version counted those as drift and reported 15 stale components where 2 were real — a checker that cries wolf gets ignored, which is worse than no checker. Fields absent on either side are listed as uncomparable. Each real drift is labelled with the cheapest restoring action, and anything unclassified fails safe (demands the expensive path).

Read the interval, not the point. The baseline file's smallest_resolvable_delta is 0.5/min(class n) — the effect of one flipped trial, i.e. quantization. Read as statistical power it understates the real 95% half-width by about 6×: at 54 non-refute / 166 refute trials, balanced 0.766 carries a 95% CI of [0.707, 0.825], so a 0.0093 "resolution" invites shipping pure noise. verify_bench_status.py prints the honest interval and flags the quoted figure.

Compare PAIRED, or you cannot resolve anything real. That ±0.05 half-width means two runs treated as independent proportions can only settle changes larger than about 0.1 — bigger than almost any improvement worth shipping. But both runs score the same cases under the same faults, so the trials pair up, and scripts/verify_bench_compare.py applies McNemar's exact test to the trials that actually changed. Concordant trials carry no information about a difference and are correctly ignored, so an 8-0 split stays decisive whether it sits among 10 unchanged trials or 500. The test is the exact two-sided binomial rather than chi-square, which is unreliable at the discordant counts this bench produces. Three refusals keep it honest: it refuses to compare runs whose provenance says they measured different systems (unless you name the difference with --expect-differs, which is how you legitimately A/B one component), it withholds a balanced figure when one class has no trials rather than printing a raw score wearing a balanced label, and it reports too-few-changes as a power limit rather than as "no effect".

Streaming turns now get a (late) verdict too (2026-07-18)

The gap: the gated verdict was invoked only from _finalize_and_return — the non-streaming finalization chain — so every STREAMED answer (the web interface, project auto-advance turns) shipped unverified, silently: no verdict, no unverified-mutation check, no log line. Found when the operator asked why a project turn had no verdict: the late recorder logs every outcome yet the log had none, and a kill -USR2 task dump showed no verdict task alive. Verdicts had only ever fired for non-streaming clients.

The fix: the streaming closure's post-drain bookkeeping now spawns _compute_verifier_verdict as a background task and attaches the late-verdict handler. Design points:

  • Always late, regardless of GHOST_CRITIC_ASYNC: the text has already streamed, so an inline verdict could never amend it — blocking would buy nothing and cost stream-close latency. Zero added latency for the client.
  • force_correction=True: a streamed reply never carries an inline **Verifier note:**, so a high-confidence late REFUTED must queue the next-turn correction banner even outside async-critic mode (the recorder previously queued only when GHOST_CRITIC_ASYNC=1). The banner already surfaces: _take_active_correction prepends it at the next stream start. Lesson retraction and trajectory backfill run as before.
  • Eager captures: the outer finally deletes messages/tools_run_this_turn before the stream drains, and the old snapshot (messages[-10:]) loses the FIRST user message — which is exactly what _conversation_fingerprint keys the correction on (a mismatched fingerprint silently drops every correction). The gate captures a full shallow copy and computes the fingerprint at closure-creation time.
  • Noise control: skipped when the turn carried no substantive tool (toolless chat would add a no-op task and a "no verdict" line per message), and the claim strips <think> blocks so streamed reasoning doesn't eat the 2000-char claim budget.

Two streamed sub-paths (live finding, 2026-07-18). A streamed client request finalizes one of two ways: spontaneous-final turns (the model answers with no further tool calls — most interactive asks) exit through _finalize_and_return and re-stream the buffered answer, so they always had the gate (validated live: a weather test drew a genuine LATE REFUTED (90%) from the two-stage judge for citing the wrong station's data); forced-final turns (the loop forces a final generation — project auto-advance) stream live through stream_wrapper, which is the path this gate covers. Because the gate's first deploy was silent on those turns and logger.debug is captured nowhere at the running log level, every branch of the gate is deliberately LOUD: each skip reason (empty claim after think-strip, no substantive tool, no verifier attached), the deferred-spawn success, and the spawn failure all log at INFO/WARNING — a gate whose skip reasons are invisible cannot be distinguished from a gate that never ran.

Covered by tests/test_streaming_verifier_gate.py (force-correction semantics, handler threading, source-level wiring pins for the eager captures, and the every-branch-is-loud pin).

Gate authority: REFUTED / unverified-mutation lower confidence (2026-06-07)

The gate used to be advisory-only: a high-confidence REFUTED verdict appended a **Verifier note:** to the reply but otherwise let the turn finalise as a success, and the finalize confidence reading — competence-driven — still read C ≈ 0.92–0.96, below=no.   • REFUTED ≥ 0.7 already sets verifier_backfill = ("failed", …); the finalize confidence block now reads that and passes outcome_penalty = 0.8 into CompositeConfidence.score(), pulling the reading below threshold so below=yes and the calibration spine records a "confidently-wrong" negative.

Finalize-burst stagger — verify vs hydration-judge (2026-07-16)

Visual verification — closing the pixels gap (2026-06-08)

The text verifier audits words: it checks whether the agent's reply is on-topic and supported by tool output. For a visual bug report ("the blocks look transparent", "the layout is broken") that is structurally blind — the truth lives in the rendered frame, so a self-claim like "I split the meshes to fix it" passes as CONFIRMED while the screenshot still shows the defect. This was the live-log failure where a still-broken game was confirmed at 90%.

verify_visual(symptom, claim, after_image, before_image=None) closes it by looking at the actual pixels via the vision node (_call_llm_vision → chat_completion(..., use_vision=True); it does NOT use the text VERIFY worker pool, which isn't multimodal). When a before image is available the model does a before/after comparison, which is far more reliable than judging a fresh frame cold.

Verdict semantics — claim vs. pixels, not symptom-presence. The judgement is whether the agent's RESPONSE is honest about what's on screen: a "fixed it" claim while the image is still broken (or blank / stuck on a loading screen) → REFUTED; a claim that matches the pixels → CONFIRMED. Crucially, an honest "it's still broken, I couldn't fix it" is ACCURATE and stays CONFIRMED — the gate catches false success, it does not punish truthful failure reports. (Validated live: false-fix claim on a red circle → REFUTED 1.0; honest "still red" → CONFIRMED 1.0.)

Start/menu screen = not running (2026-06-09). The scratch file is not a deliverable 2026-08-26

The refute. A live request built a glass-morphism web OS. The agent wrote webos/index.html (25KB), syntax-checked its JS, screenshotted the desktop, opened the calculator and computed 5+3=8 in a headless browser — and the turn was REFUTED (0.9) for a claimed-but-missing deliverable, overriding a text verdict of CONFIRMED (0.95). The "missing deliverable" was probe.py: a scratch script the agent wrote, ran, and then deliberately deleted. The answer never mentioned it — _claimed_deliverable_files returns an empty list for that reply. The whole refute came from the mutated half of the union.

The mechanism. The mutated-file selector matched any quoted token containing a dot, in every file_system SUCCESS message — and SUCCESS: Deleted 'probe.py'. is one. A tidied-up temp file was therefore collected as a produced artifact, re-read, and found missing. Three properties turned one bad verdict into a trap:

  • tools_run_this_turn accumulates across the whole request, not one turn, so a scratch write at step 5 of 16 poisoned the verdict at step 16, the auto-repair round, and the post-reply async re-verify.
  • The auto-repair round was unwinnable by construction — no amount of re-checking can make a deliberately-deleted file reappear. The bounded repair attempt was spent for nothing.
  • The execute tool's inline-python -c block message prescribes file_system(write, path="probe.py") as the sanctioned workaround. The agent was refuted for obeying another subsystem's instruction.

The late REFUTED would have backfilled a correct turn into the learning corpus as a FAILURE and scrubbed its lessons; only the operator's human label (_human_label_locked) withheld it. Without the thumbs-up this would have been silent label noise.

The path ledger

_fs_path_ledger replaces both selectors' regex scan. It returns (left behind, retired) — the paths a request produced and did not remove, and the paths it produced and then removed — parsing the file tool's confirmations with one anchored pattern per message shape rather than hunting for quoted tokens. Deleted 'x' retires; Renamed/Moved 'old' to 'new' retires the old and produces the new; Downloaded 'url' to 'file' and Copied 'src' to 'dest' produce only the destination; the write/replace family produces the path its own pattern captures. Order is respected both ways — a path written, deleted, then written again is a deliverable again.

The key is normalised, not literal. _get_safe_path resolves /workspace/x, ./x and x to the same file, and the write confirmation prints two spellings while the delete prints one. String-equal bookkeeping therefore let the incident reproduce verbatim whenever the model spelled the delete differently from the write — 35 real writes in the trajectory corpus carry a /workspace/… spelling. Keys are prefix-stripped and case-folded (the sandbox is a bind mount on a case-insensitive host FS), and a removed directory retires everything produced beneath it, because a scratch directory is the same tidy-up idiom.

Only the confirmation line is parsed. Everything after the first newline is the tool echoing the edited source back (POST-EDIT VIEW, REPLACED BLOCK, a syntax-error excerpt), whose quoted strings are code. That guard overlaps the patterns' positional anchoring (re.match at offset 0) and the SUCCESS fast-path. Two of the three individually suffice — the line split and the anchoring; the SUCCESS fast-path alone does not, since with the other two gone an echoed SUCCESS: Deleted '…' in the body is found and retires a live deliverable. So removing the split or the anchor alone fails no test, and that survival is redundancy rather than missing coverage. The behaviour is pinned directly, and its failure world is constructed, not observed: the file tool is confined to the sandbox and cannot reach this repo, and no file in the live sandbox contains such a string. What is verified is the mechanism — a replace whose echoed block carries a confirmation line does retire a live deliverable once the guards are gone.

Suppression is visible, not silent

Dropping a path must not quietly disarm a check. WEB-EXEC has no claim-prose leg — the written list is its only input — so a turn that renamed its only page to index.html.bak would have skipped the probe and its inconclusive confidence cap, certifying at full confidence a build whose entry page is not on disk. _retired_entry_pages reports exactly that case and the probe runs anyway, returning None for an empty list — the existing inconclusive path, which arms the 0.6 cap. It is deliberately narrow to .html/.htm: a tidied-up scratch .js must not cap a turn whose deliverable was never a web page.

On the FILE-ARTIFACT side, retired paths are passed to _verify_file_artifacts as soft and checked for emptiness only, never absence. Absence is what "removed" means; but a removed path that is back on disk was re-created by a route this parse cannot see (a shell rewrite through execute), and a re-created deliverable that landed empty is a real defect the old parse caught. That arm is kept rather than discarded with the rest.

Two fixes to the re-read itself

  • A produced directory is present, not missing. Copied 'webos' to 'backup' and Renamed/Moved 'build' to 'dist' name directories; the checker accepted only is_file(), so every such op refuted. This was a regression the shape-aware branches introduced — a dotted-token parse never saw a bare directory name.
  • The basename fallback will not certify a different file — and the rule is SYMMETRIC. rglob(basename) took the first filesystem hit with no path check, so a claim of webos/index.html was reported clean by a stale backup/index.html. A hit must now match the claim as a suffix in either direction. Both directions occur: the hit may be deeper (a bare deep.txt claim answered by sub/deep.txt), or the claim may be deeper — projects/<pid>/app.html resolved against a host_dir that already IS the project directory, because project_scoped_sandbox hands the check the scoped path while the model spells its paths from the sandbox root. A one-sided rule shipped first and was a critical live regression: rglob only yields basename-matching hits, so requiring the on-disk path to reproduce the claim's whole parent chain made the fallback dead code and refuted 39% of the turns this check runs on (measured with the fallback root disabled; with it supplied the two mechanisms are substitutes) — files sitting right there on disk, the very bug this change was fixing, pointed the other way. It also silently disarmed the directory rule above for every project-scoped op, and it turned the claim extractor's harmless over-captures (a /api/download/… markdown link tail, a host-path echo) into refutes. What stays rejected under the symmetric rule is a hit under a different parent, which matches in neither direction.

Known limits, written down

The ledger sees only what the file tool reports. A file removed by a shell rm through execute reproduces the original false refute by a route with no confirmation message; every item once listed here is closed: the shell-rm route and the sweep race by §4DI's removal-aware downgrades (see "Absence is removal, not non-production" below), the scoped-root anchoring by §4DH's fallback root, and the [FAILURE BANNER] drop by the ledger reading past the banner. The last is a project-binding defect whose safe fix needs a recency gate like _locate_entry_page's — widening the search root without one would trade a false refute for a false confirm.

The refute wording was also corrected — it said "the answer claims deliverable file(s)" about paths the answer never mentioned — and the log line, which truncated the reasoning mid-filename (missing: probe.), now keeps 260 characters, enough for the realistic four-path refute (233) though not for eight project-scoped ones.

The tripwire that did not trip

Each shape having its own anchored pattern means rewording a message in file_system makes the parser go silently blind to that op while the check keeps reporting "clean". The first tripwire written for that compared the static prefix of each SUCCESS: literal — and a prefix stops at the first {, while every pattern depends on text after it. Rewording Wrote {n} chars to into Wrote {n} bytes into, which blinds the ledger to every write and takes both overrides down with it, left the tripwire green alongside 761 other tests.

It compares behaviour now: TestProducerParserParity walks tools/file_system.py with ast, renders each SUCCESS: f-string with placeholder values, and requires the parser to match it and capture the right slot. Five real rewords that previously passed now all trip. The two instruments are also cross-linked, because they fail in complementary directions — the AST walker cannot see comments and the prefix scan can, so moving a template into another module while leaving a comment behind kept the prefix set equal while the walker lost the emitter. Every pinned prefix must now head a rendered message, and every rendered message must have a pinned prefix.

What further review rounds found

The one-sided suffix rule above was caught by an independent lens, not by the suite. Later rounds found, in the fix's own new code: an internal error inside path resolution being read as missing — so a bind mount vanishing mid-read produced the same false refute the change exists to remove (it fails open now, and says so); a directory named report.pdf satisfying "I generated report.pdf"; an empty __init__.py, whose emptiness is correct, driving a repair round whose only escapes are corrupting or deleting it; the union deduplicating on the raw spelling while the ledger keys are normalised, so one file could occupy two of the eight slots and evict a genuinely corrupted index.html; and prose claims, which the extractor emits up to eight of, starving that same union of every slot.

The half nobody was looking at

The most valuable finding came from the lens told to ignore everything the others had covered. _claimed_deliverable_files carries two filters — a URL check and a system-path check — and both were unreachable code. The capture group began at [A-Za-z0-9], so a captured name could never start with /, and the :// was always consumed by the gap before it. So Wrote /etc/hosts.conf yielded etc/hosts.conf, Generated … https://example.com/guide.md yielded example.com/guide.md, and a /api/download/… markdown link — which report_pdf instructs the model to emit — yielded api/download/…. Each went into the hard, absence-refuting leg. Two of the three FILE-ARTIFACT refutes recoverable from the record were exactly this, on turns that ran no file tool at all. The two tests naming those guards passed because their fixtures contained no completion verb, so the claim regex never fired: two named guards, zero coverage, and tests certifying them.

The capture now admits a leading slash and a URL scheme, which makes both filters live, and HTTP routes are excluded outright. All of this sits upstream of the ledger work: the change had reasoned carefully about dedup, caps, roots and soft paths while the other half of the same union went ungated.

The resolver, restructured

Patching each symptom stopped working, so _verify_file_artifacts was rebuilt around one call and one verdict. It takes extra_roots (the un-scoped sandbox, tried when a path does not resolve under the project dir), file_claims (which paths the prose named), and a report dict. The fallback root is not a free second search: the basename rglob runs on the primary root only, and a hit under a different projects/<id>/ is rejected on every branch. Without that, any basename collision — 12% of files in the live sandbox share one — let a sibling project's file certify this turn's claim, or let a healthy namesake rescue a genuinely corrupt local file.

Directory-ness and empty-by-design both key off the claim's source rather than its spelling. A prose claim always names a file, so a directory can never satisfy one; a ledger entry legitimately names directories, and Copied 'src' to 'backup.old' must not refute for containing a dot. An empty __init__.py nobody claimed is correct; one the answer describes as carrying content is a defect.

report exists because None means "no override", which covers both "every path checked out" and "nothing could be opened" — and logging them alike turned an unmounted workspace into a positive claim about files the check never read.

Measuring the mechanism

The verdict sidecar now records which override produced a verdict. This check has been overriding the text judge since 2026-07-16 with no durable trace: the sidecar kept verdict and confidence, the trajectory kept neither, and the only record was a log line in a file that holds about a day. The one question that matters — how often the override is right — could not be asked of the record at all.

Mutation-verified with scripts/mutate_fs_ledger.py: 92 single-edit mutants, 90 killed; the two survivors are redundant guard pairs, each proven by a multi-edit mutant that strips every copy at once — both killed. That distinction matters: a single-edit survivor means the guarantee has more than one implementation, not that it is untested, and the only honest way to tell those apart is to remove them together. The harness runs three test files, because a keyword added to _verify_file_artifacts broke two stubs in a third — the TypeError was swallowed by the block's blanket except, both tests kept passing, and a harness scoped to two files could not see it.

The harness itself had to be rebuilt twice. Its restored: verified by hash line was a tautology — it hashed the snapshot it took at start-up, so a mutant already in the tree was snapshotted as pristine, faithfully restored, and certified clean. It now keeps the pristine bytes in memory, holds a lock file, traps signals, times out, and states what it actually compared. What this machinery actually reaches

A final review round measured every mechanism against the 1,855-record corpus rather than against its own rationale, and the answer is worth recording plainly. Two arms carry the change: the ledger arm (fires on 123 records) and the retired list (1 — the incident itself). Under the current extractor the prose arm fires on 64 records (23 plain prose + the 41 restored download-route claims) and contributes a file the ledger also lacks on 7 — and as of 2026-08-27 it is emptiness-only (see below), so those are soft checks, not refute exposure. (The pre-§4DH extractor fired on 28; the growth IS the restored route coverage.) That is not an argument for deleting them; each closes a shape that a fresh-eye lens produced on demand, and the two arms that matter were themselves invisible until an incident produced them. It is an argument for reading the ⚠ comments as design rationale rather than as incident reports, and this page now marks which is which. The honest summary: the mechanism that fixed the reported bug is about thirty lines — the ledger, the retired list, and the emptiness-only arm — and most of what surrounds it defends shapes the record has not yet produced.

Every round's criticals were inside the previous round's fixes, six times running. The last round found two live defects created by the round before it: the original bug still reachable through the project-scoped write spelling (the confirmation prints the model's filename AND the resolved rel_str, and the model deletes by the second — 39% of real write confirmations print such a pair), and a foreign-project guard that, on an unscoped turn, refused to let any project directory answer at all, refuting a turn whose own ledger entry for the same file resolved clean in the same call.

Prose is not absence-grade evidence (2026-08-27)

The deferred fixes, taken together. Every false FILE-ARTIFACT refute attested in the record was a prose capture — a host-path echo, a download link, another tool's output quoted in the answer — refuting a turn on the ABSENCE of a file it never really produced, often on turns that ran no file tool at all. Meanwhile prose contributed a file the ledger lacked on 7 of 1,855 records. So the arm is demoted, not deleted: the hard, missing-refuting list is built from tool confirmations alone, and prose claims ride the soft (emptiness-only) arm. A claimed file that exists at 0 bytes still refutes — prose keeps its teeth for the defect class it actually catches — and a written file that is gone still refutes through the ledger. This buys the whole false-refute class for the price of an absence check that fired usefully on ~0.4% of records.

Absence is removal, not non-production (2026-08-27, §4DI)

The ledger's two stated limits are closed by one reframe: a SUCCESS: Wrote … confirmation is the production evidence, so a later absence proves only that something removed the file. The two removal routes that leave no file_system confirmation — a later shell/script step, and a workspace sweep racing the re-read from another request — downgrade the missing-refute to a logged skip (skipped_removable in the report, a WARNING in the stream). Both are evidence-gated: order for the shell route (_keys_removable_after_write — an execute that ran before the LAST write of a file proves nothing and those keys still refute; a shell run is recognised by the record's own execute-result markers, not a tool-name list — the first gate listed a read-only reporting tool and let arbitrarily-named composed skills walk past), and the removal's own store-stamped mark for the sweep/delete routes (_mark_removal in workspace_cleanup and the hard-delete path in the project store: a per-project capped dict carrying the DELETED FILE LIST — a mark must name the file, or a tidy that removed one stale screenshot would "explain" a missing app.py; recency-gated at 15 minutes; dry-runs never arm it). Refute escalation: screen cheap, confirm expensive (2026-07-26e)

Symptom: web-research turns were being LATE REFUTED for correct answers — "the claim labels PostgreSQL 18.4 as the latest stable version without explicit confirmation from the tools" (90%), and a PDF-ingest turn refuted at 100% for stats the tool had literally printed.

Root cause (measured, not guessed): VERIFY rides the worker route, which on this box is Gemma 4 E4B — a 4B model — while the main box runs Qwen3.6-35B. Replaying three cases against both judges: the 4B scored 1/3 (it refuted a correct entailed superlative, and called 49152 bytes "not exactly 48 KB" — wrong arithmetic), the 35B scored 3/3, including correctly refuting a fabricated version. The prompt was never the problem; the judge's capability was. Prompt-only iteration was tried first and produced only partial improvement, which is what motivated measuring the model.

Fix: the cheap judge still screens every turn (no added latency, no main-slot contention on the common path), but a REFUTED verdict is now re-adjudicated on the MAIN model before it is allowed to act — _escalate_refute + force_main routing that bypasses both the critic pool and the worker route. On disagreement the strong model wins; on any error the original verdict stands, so escalation can only ever REDUCE false refutes, never make the gate less available. Cost is one main-model call on the rare refute path only. This matters because a false REFUTE is expensive: it scrubs the turn's lessons, files follow-up tasks, shows the user a correction banner, and marks the trajectory failed — poisoning the corpus every downstream learner trains on. Every one of those actions is gated on REFUTED specifically, so an overturn to CONFIRMED or UNCERTAIN is a safe outcome. Kill switch: GHOST_VERIFY_ESCALATE_REFUTE=0.

Live A/B after the fix (cheap judge + escalation): the PostgreSQL turn went REFUTED(0.9) → UNCERTAIN, the unit-conversion case REFUTED → CONFIRMED(1.0), and the fabricated-version control stayed REFUTED(0.95). Confirm escalation: the other direction was ungated (2026-08-04)

Symptom (measured over the live stores, not inferred): escalation was one-directional by construction — _escalate_refute returns immediately on anything that is not REFUTED. Over the recorded window that is 50 REFUTED escalations (84% overturned by the main model) against 0 CONFIRMED escalations. Two further measurements make the asymmetry load-bearing: the ≥0.7 consumption gate is a no-op on the cheap judge — 130 of 130 recorded cheap verdicts came back at 0.9 or 1.0, so nothing was ever filtered by it — and since the 2026-07-31 honest-failure decision a CONFIRMED outranks a structural execution failure (resolve_turn_outcome rule 3 before rule 4). Result: 61 of 1488 live trajectories (4.1%) are outcome=passed with a failed tool call in the turn, each certified by a cheap 4B judge that nothing checked.

Still load-bearing after the 2026-08-04 shape rule. That rule (rule 2b) withholds a PASS only from the narrow subset where every tool call failed and the reply never said so — 8 of 1488 live trajectories. The far larger "some calls failed, the reply reads clean" population is exactly what this escalation exists for, and no shape rule can reach it: it needs a model to read the answer against the evidence.

Fix: a CONFIRMED is re-adjudicated on the main model when the caller marks the turn high-stakes — agent._turn_had_tool_failure(tools_run_this_turn), i.e. some tool actually failed, which is exactly when the verdict is what keeps the turn out of a FAILED label. The trigger is computed inside _compute_verifier_verdict, the one place every verdict is produced, so it cannot be live on the finalize path and dark on the in-loop/streamed ones. Firing rate on the live corpus: ~4% of turns, about two extra main-model calls a day — less often than the refute escalation it mirrors.

Deliberately NOT symmetric: a refute is punitive (auditor note to the user, lesson retraction, FAILED corpus label, auto-repair round), and "the strong judge would not confirm this" is weaker evidence than "the strong judge says this is wrong". So when the main model declines, the verdict KEEPS its CONFIRMED label and its confidence is capped at 0.6 — below every ≥0.7 consumption gate, the same idiom as _WEB_EXEC_SKIP_CONF_CAP. The turn is then recorded as unverified: no fabricated PASSED, no manufactured failure. On any error, an unparseable strong verdict, or a missing cheap route the original verdict stands (3 of 10 live replays came back unparseable — those are no-ops). A verdict already overturned by _escalate_refute is never re-escalated. The withheld case sets confirm_withheld, the mirror of escalated_overturn — both now recorded in the escalation ledger below (the to_dict() keys they were originally written to never reach production; see the next section).

Replay evidence: 10 of those live cheap CONFIRMEDs re-run on the 35B — 6 agreed, 1 was overturned (an explicit output-format constraint the cheap judge missed), 3 unparseable. Kill switch: GHOST_VERIFY_ESCALATE_CONFIRM=0 restores the exact one-directional behaviour. Default ON, because the failure it prevents (a fabricated success taught to every downstream learner) is durable while its own worst case is a turn recorded as unverified. Tests: tests/test_verifier_confirm_escalation.py (22).

The escalation ledger: where the watch metrics actually live (2026-08-04)

Symptom. escalated_overturn (the §4F false-positive watch metric) and its twin confirm_withheld were "persisted" into VerifyResult.to_dict() — a serializer with zero production callers (AST sweep of src/: the only to_dict reads belong to other classes; nothing in the turn loop ever calls the verifier's). Live proof: 160 "OVERTURNED a cheap-judge refute" lines in ghost-agent.log against 0 occurrences of escalated_overturn anywhere under $GHOST_HOME/system/. The fix was recorded as done; it was inoperative.

Why not the trajectory record, the obvious candidate. On the STREAMED delivery path _record_turn_trajectory runs in the SSE drain before the stream verifier gate spawns the verdict at all — so a turn_facts stamp (the right tool for a fact known mid-turn) cannot carry a late verdict's flags there, and the web UI always streams. Stamping it anyway would have produced the usual defect: live on one path, dark on the other, with the darkness invisible because "no flag" and "no escalation" look identical.

Fix. One append-only JSONL at $GHOST_HOME/system/verifier/escalations.jsonl, written at the point the escalation RESOLVES — inside _escalate_refute / _escalate_confirm. That is path-independent by construction: finalize, in-loop auto-repair, and the streamed late verdict all funnel through those two methods. One line per escalation: {ts, kind: refute|confirm, route: claim|code, outcome: overturned|upheld|withheld|unavailable, cheap_verdict, cheap_confidence, strong_verdict, final_confidence, req_id, trajectory_id}. req_id/trajectory_id are threaded down as call ARGUMENTS from _compute_verifier_verdict (never read off the context — on the streamed path this code runs after the turn semaphore is released, the lesson core/turn_facts.py exists for), so every row joins back to the trajectory corpus.

Both outcomes are recorded, not just the interesting one. The watch metric is a RATE; a ledger of numerators cannot produce one — which is why "84% of refutes are overturned" previously needed hand-run log archaeology. unavailable (the strong model errored or came back unparseable, so the original verdict stood) is recorded too: a call was spent and changed nothing, and an escalation that silently no-ops is indistinguishable from one that never ran.

Read it with: jq -r '.route+"/"+.kind+"/"+.outcome' $GHOST_HOME/system/verifier/escalations.jsonl | sort | uniq -c — the cheap judge's false-positive rate is overturned / (overturned + upheld) within kind=refute. Kill switch: GHOST_VERIFY_ESCALATION_LOG=0; default ON, because the write is one short line on the rare escalation path (not per verdict), it never raises, and the whole finding is that the metric had nowhere durable to live. The file rotates to .jsonl.1 past 4 MB — rotation, never truncation.

Bench and self-play are excluded, deliberately. A row is written only when the caller supplies a live-turn req_id. scripts/verify_bench.py and optimize_verifier.py drive verify_claim through a two-legged client precisely so _escalate_refute fires — dozens of times per run, in a shell where GHOST_HOME is exported — and self-play/dream turns run the whole turn loop on a shallow-copied context. Either would corrupt the exact rate the ledger measures; the simulation gate is the same skill_memory.is_read_only marker the calibration corpus uses, for the same live reason (§4J). Tests: tests/test_verifier_escalation_ledger.py (36).

Why. The verifier is a trajectory-local judge: the last reply against the last few tool outputs. The lever for a weak judge is a state tracker beside it, not more model.

What. core/turn_state_check.py — pure functions over ONE turn's record (the current request, the tool calls with their results, the delivered reply), producing negative verdicts only:

  • Mechanical constraints of the current request: strict / only / plain-text JSON, "reply with exactly: …" (a SET of allowed phrases — "yes or no" is two — read without its trailing instruction, "PONG. Nothing else." is PONG), "just the number", word / line / sentence caps. When a request says "STRICT JSON on a single line", only the JSON rule runs.
  • Every web retrieval empty, the reply asserts anyway. Per-row accounting over the search tools (the runtime evidence gate's own "empty" definition) and browser page reads — a page is empty only on a browser error or an HTTP 4xx/5xx, never on length, and a later successful load outweighs an earlier 404; a memory miss (recall, knowledge_base) is not an absent source and a successful execute (a three-character curl status) IS evidence — plus a reply of ≥30 words that never says nothing was found. 0 fires on the corpus after these narrowings: it is kept as the judge half of the runtime gate and is unmeasured; retire it if the readout shows nothing by November.

Rule 4: non-assertive objections — built, hardened twice, shipped OFF (2026-08-12, §4BD-b)

What it does. A stated NEXT STEP ("I'll open the parser next") or a QUESTION back to the user ("Want me to look at the service log?") asserts nothing about the world, so no evidence can contradict it — yet after the artifact retirement, 4 of the 6 residual false-refutes on the FP-trap set were exactly future-plan complaints. objection.py rule 4 dismisses such an objection with no main-model call. Proof-based: the fragment must appear verbatim in the claim; a paraphrase is never accepted, because a paraphrase cannot be checked. Guards: a single clause opening with the marker, ≤160 chars, no numeral (ASCII, unicode or spelled out), no inflected result verb (bare infinitives after a modal are future actions and stay legal), no clause break, no subordinator or relativizer, no copula — and every word left once the fragment is removed must be in an explicit framing allowlist.

⚠ It ships DEFAULT-OFF (GHOST_VERIFY_OBJECTION_NONASSERTIVE=1 opts in), and the reasoning matters more than the rule. The guard is a lexical proxy for a semantic property. Two adversarial rounds each found it leaking in a shape that had not been modelled: v1 dismissed a whole objection on finding any non-assertive span (so an objection citing a real contradiction and quoting the next step laundered), and v2 fell to ; and : as clause joins, to inflection (passed vetoed, passes not), to relative clauses ("I'll fix the bug that broke prod"), and to framing words that spell an alignment complaint. v3 closes all 32 reported inputs — but the honest read is that the next escape is one word cleverer, not that none exists.

The asymmetry is the argument: a false negative costs one main-model call on a turn that was making one anyway; a false positive erases a real catch with no model call and no visible trace — CONFIRMED@0.9 with objection_dismissed=True is indistinguishable in the ledger from a correct rescue. Two measured rescues do not buy that.

⚠ The original justification was retracted. An LLM probe scored "0 damage over 31 corrupted trials"; review showed that numerator was structurally incapable of being nonzero — the bench's fault_fabrication strings carry digits and result verbs (vetoed before rule 4 can act) and fault_silent_failure keeps the claim, so its objections are absence-shaped and settle at rule 2. The damage surface now lives in tests/test_objection_nonassertive_damage.py: 12 adversarial fixtures asserted at the per-objection and whole-verdict levels, plus mutations (punctuation, tense, subordinator) so the suite pins the mechanism rather than the strings that motivated it. Its stated limit: it proves no laundering on shapes we thought of. Do not run a bench sweep to decide the default: a sweep is itself an opt-in, and the bench's fault injectors provably cannot produce the shapes that break this rule — which is exactly why the earlier probe was retracted. A sweep would come back clean for the same structural reason and that number would be used to argue default-ON.

Why there is no v4. Findings per adversarial round ran 3 → 32 → 34 — not falling. The decisive class is presupposition smuggling: "Let me restart the crashed service now" asserts that a service crashed, with no copula, subordinator, clause break, inflected verb or numeral, so it is unreachable by the only kind of veto this design has. Making it safe means inverting the test — requiring the fragment's content words to appear in the user's request — which is a different rule, not another guard. The known-unsafe classes are enumerated in code (_NONASSERTIVE_KNOWN_HOLES), and setting the env var logs a warning naming them: a flag that silently arms a rule with known laundering paths is a trap, a loud one is a choice.
