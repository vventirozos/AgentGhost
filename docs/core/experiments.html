core / experiments.py — live randomized arms

Every eligible request is assigned, blind and deterministically, to one arm of each running experiment. Production traffic becomes the controlled experiment that stopped-prod ablations and synthetic batteries could no longer provide.

Why this exists

Every "is this actually better?" question in this project had been blocked on the same missing instrument. Paired ablation (scripts/ablation_paired.py) is the gold standard but needs prod stopped and a synthetic battery to drive; those batteries ceilinged twice in one day (B4 single-step 33/33, compositional 10/10), so they can no longer discriminate. The §4F fallback — a two-week observational watch — has no control arm, which is why its own caveat (e) admits the T+14d verdict can report "the stack improved" but cannot attribute it.

The earn-keep post-mortem pre-approved exactly one revival route: change the instrument. This is that change.

Assignment

arm = f(sha256(salt | "arm" | experiment | req_id))
enrolled = f(sha256(salt | "enroll" | experiment | req_id)) < traffic

A pure function of the request id — so a retry, a replay, or a late verdict lands on the same arm as the original, and no assignment state is persisted or synchronized. The enrollment draw uses a different hash prefix from the arm draw, so a partial-traffic experiment does not correlate the two. The 53-bit mantissa mapping avoids modulo bias; measured split over 4000 units sits inside 47–53%.

Configuration

Built-in defaults live in DEFAULT_SPECS. An optional file overrides them wholesale:

$GHOST_HOME/system/experiments.json

{"salt": "2026-08",
 "experiments": [
   {"name": "risk_steer", "arms": ["control", "treatment"],
    "traffic": 1.0, "enabled": true}
 ]}

Reloaded on mtime change. A malformed file falls back to the defaults with a warning — assignment sits on the request hot path and may never raise. Kill everything with GHOST_EXPERIMENTS=0; consumers then see "" and take the control path, which is the same code path as a genuine control assignment (one branch to reason about, by design). ⚠ The file replaces DEFAULT_SPECS wholesale — when adding a spec (e.g. the first bench-scoped one), re-list every live default you want to keep enrolling. enabled: false stops NEW enrollment only: the spec's accumulated results keep rendering and announcing (R6 — the report/announce filters are a DENY-list of the other scope's names via deny_names, so retiring or disabling a spec never erases its history; only a spec re-scoped live↔bench has its stale other-population stamps excluded).

An experiment name that collides with the trajectory redactor's sensitive-key list (auth_token, …_key, …) is rejected at load: its arm would be stored as <REDACTED> in every trajectory and the whole run would be unanalysable after the fact.

Populations: scope="live" | "bench" (§4BF Track 1c)

A spec may declare "scope": "bench" to run on the idle bench-bank population instead of real turns (default "live"; an unknown scope SKIPS the spec — a typo must never run a bench-intended experiment on live traffic). The populations split at BOTH ends: enroll_request(origin=…) assigns only scope-matching specs (bench solves cannot reach live toggles, real turns cannot reach bench ones, plain self-play reaches neither), and summarize_streaming(admit_task_kinds=…) folds only the matching task_kind into arm stats — a stamped record of any other population lands in coverage["skipped_kind"], never in a verdict. The bench randomization UNIT is the bench item (bench|<bank>|<item>), not the per-attempt req_id — all attempts of one item share an arm, so the retry prompt (a function of the previous attempt's output) can never cross arms; the ≤3 same-arm rows per item are dependent and the CS reads them as extra n (documented, accepted). Bench verdicts announce with an explicit caveat: a bench win gates a live watch-window, it is not an auto-apply (operator decision, 2026-08-13 — see core/admissibility). introspect action='experiments' renders the bench population as its own labeled section; the CLI equivalent is scripts/experiment_report.py --bench. All four live-view surfaces and both announce passes DENY the names DECLARED in the other scope (names_in_scope, enabled or not — R6/R7: an allow-list of this scope's enabled names erased a disabled spec's history, and an enabled-only deny let re-scope-then-disable resurrect stale stamps; a disabled spec always keeps its own-population history), the bench report divides by its OWN population (coverage["admitted_turns"]) under a bench-labeled title with an items-vs-attempts caveat (all attempts of one item share an arm, so experiment n exceeds the flywheel's item count by design), and bench verdict computation honors --no-bench through the admissibility chokepoint. This is what unblocks the Track-2 flip queue at bench speed (~6-11 graded solves/night vs scarce real turns).

tts_bon — the first bench-scoped arm (§4BF Track 2 flip ii)

Registered in $GHOST_HOME/system/experiments.json (which replaces DEFAULT_SPECS wholesale — the four live defaults are re-listed there, and the file deliberately carries no salt so live assignments are unchanged). The arm measures adaptive best-of-N on the verifier's wobble band (core/tts.py) on text-graded bench attempts (gsm8k_text): trigger = the in-loop verifier verdict lands UNCERTAIN, or REFUTED below the 0.7 action threshold, on a non-repairing final. The trigger is stamped on BOTH arms as tts_bon_fired (presence = the wobble condition; value = treatment ran); treatment substitutes the BoN winner as the final, control withholds. The consumer sits at the single BoN call site in handle_chat: an enrolled turn's arm decides (env ignored — control with GHOST_TTS_ADAPTIVE_BON=1 still withholds), an unenrolled turn falls back to the env default (OFF), so live behavior is untouched. tts_bon_fired is also in CONTEXT_MUTATING_KEYS: BoN never mutates what the model saw generating the turn, but the substituted final enters the conversation history and the recorded trajectory, so replay consumers must be able to exclude treatment turns. Outcomes come from the bank oracle via the 1c write-back; decision rule pre-registered at system/eval/flip_ii_tts_bon/DECISION_RULE.md (ship = open a live watch-window discussion; abort on trigger starvation <5%, TREATMENT WORSE, or >2× wall-clock). R1 amendments to the rule: the starvation share is computed over gsm8k_text attempts only (every bench attempt of every bank enrolls, so the report's all-enrolled trigger line is diluted by construction); starvation must be TRIAGED (no verdict at all / verdict missed the await window / genuinely no wobble) before concluding on the population; and a live watch-window must be a LIVE-scoped spec, never the bare env — the env path stamps no compliance key, so substituted finals would enter the corpus unmarked. Starvation-triage observables (R2/R3): enrolled finals that reach the BoN decision point stamp verify_in_window (was a verdict in the in-loop cache — either arm, wobble or not), and an async await-window miss stamps verify_late_pending — the two keys that make the abort rule's triage falsifiable (neither is a TRIGGER_KEYS or CONTEXT_MUTATING_KEYS member; finals that never reach the gate — repair-exhaustion, force-stop, execution failures — carry no verify_in_window stamp and form the trigger-ineligible bucket). Tests: tests/test_track2_flip_ii.py.

verify_depth — the router's first live consumer (§4BR, 2026-08-16)

The §4BQ complexity router has been accurate-but-unconsumed since its embedding flip. This arm consumes it: on a turn the router calls confidently hard (label="hard" and NOT escalated — an untrained or unsure router escalates with label=hard, so counting those would fire on nearly everything), the treatment runs the verifier's cheap-leg adjudication with self-consistency n=3 instead of one sample. Control keeps n=1, byte-identical to today. See verifier for the vote itself.

The premise is untested and that is the point. "Harder turns are likelier to get a wrong verdict" has never been shown here — §4AN's standing lesson is that this router was accurate overall and worthless exactly where it acted. So it ships as a randomised arm rather than a default, and the deploy is the measurement. Pre-registered at system/eval/verify_depth/DECISION_RULE.md, which opens with a mechanism gate — if the judge does not vary on this traffic the arm retires regardless of outcomes, because the outcome metric (human feedback, the only signal independent of the verdict) is sparse enough that it may never reach its floor.

⚠ That gate had to be rescaled, and the error was a live hazard. The predicted ~17% disagreement was measured over three full repeat runs, while the recorded statistic comes from an early-stopped vote that stops at two samples whenever the first two agree. The two differ by exactly 2/3 (full: 1 − p³ − (1−p)³; early-stopped: 2p(1−p)), so a mechanism behaving exactly as measured records 11.1%, not 17%. The first version of the gate compared the recorded number against the full-draw prediction and would have retired a perfectly healthy arm with probability 0.164 at n=40 — it was likelier to kill the feature than the feature was to be inert. The live rule is calibrated on what is actually recorded; treat system/eval/verify_depth/DECISION_RULE.md as the only authority for the thresholds, and do not restate them here. The convenient metric, resolve_turn_outcome's SUCCESS/FAILED label, is circular: the verdict is an input to it, so a treatment that changes verdicts moves it mechanically.

Where the decision is taken matters more than what it decides. Both the trigger and the arm are resolved in handle_chat, in the router block, and the verdict path only reads the result. Taking it at the point of use looked right — _compute_verifier_verdict is the one place every verdict is produced — but on the streamed path the trajectory is written before that coroutine is spawned, so the enrolment and the trigger would land after the drain: measured 2/169 rows, against 145/169 for facts stamped in handle_chat. The block must also sit after enroll_request, because mark_trigger refuses to create a ring slot and returns silently when none exists.

verify_depth_fired is a TRIGGER_KEYS member, stamped only on turns that actually triggered (trigger_fired reads presence, not value, so an unconditional stamp would make "triggered only" mean all traffic); its value carries whether the treatment ran. A deep turn additionally stamps verify_depth_context, a CONTEXT_MUTATING_KEYS member — a changed verdict can append the correction note to the final text and add a repair round, both of which enter the conversation history and the recorded trajectory, so the GEPA fixture corpus must exclude them. Kill switch GHOST_VERIFY_DEPTH_ROUTING=0; note GHOST_VERIFY_TWO_STAGE=0 also removes the voted leg, and both switches are folded into the single verifier.depth_for_turn predicate so a turn can never be recorded as treatment while behaving as control. Rollback of enrolment = delete the entry from system/experiments.json (hot-reloads on mtime). Tests: tests/test_verify_depth_routing.py.

⚠ The registry lesson, learned twice. This arm shipped 100% inert: it was added to DEFAULT_SPECS only, and the on-disk system/experiments.json replaces those wholesale, so arm_for returned "" and every turn took the control path while the tests stayed green. The file's own comment already recorded this lesson from Track 1c. tests/test_verify_depth_routing.py now carries a general drift check that fails for any enabled default missing from the live file.

Circularity is per-(experiment, metric) — NO VERDICT (2026-08-17)

failure_rate derives from resolve_turn_outcome, whose inputs include the verifier verdict. For an arm whose treatment changes that verdict the metric moves mechanically in whichever direction the treatment pushes it, with no bearing on answer quality — so a difference there is the instrument moving. verify_depth's pre-registered rule says exactly this and disowns the metric; tts_bon substitutes the final text chosen by the verifier's own score and is in the same position. Both are listed in _CIRCULAR_FOR, and compare_arms(..., experiment=…) attaches a CIRCULAR caveat that makes MetricComparison.verdict render NO VERDICT and suppresses the operator announcement.

It is deliberately per-experiment: failure_rate stays a legitimate metric for risk_steer, fs_batch and use_planning, which change the ANSWER rather than the instrument. Every caller threads the name — including scripts/experiment_report.py's --json, which for one round did not and therefore reported TREATMENT WORSE on a bench arm the human report already showed as NO VERDICT.

⚠ Suppression creates an obligation: _CIRCULAR_REMEDY must name a REACHABLE replacement per experiment. "Read the human-graded metric" is reachable on the live population only — human feedback arrives against a user request_id, so human_failure_rate is structurally n=0 on bench turns.

⚠ A retraction worth keeping. tts_bon was listed as circular for one round on the reasoning that bench outcomes are verifier-derived. They are not: dream's §4BF-1c write-back stamps the bench trajectory outcome from the bank oracle (source="bench_validator", measured 79/79 rows), and the oracle-yield leg in update_outcome stops a late verifier verdict from superseding it — so failure_rate there IS the ground truth. The suppression removed that arm's only decidable metric and made its pre-registered SHIP condition ("no confound annotation on the winning metric") unsatisfiable. The general lesson: suppressing a metric is not the conservative default — it can leave an arm undecidable, which is a silent-inoperative defect wearing a caution label.

Recording

The arm is stamped on the turn's trajectory as extra["experiments"] = {"<experiment>": "<arm>"} by _record_turn_trajectory, which both the streamed and non-streamed finalize paths reach. Treatments that actually fire also stamp a compliance key (risk_steer_fired) — without it, an arm whose trigger never fired reads as a null result rather than as a non-event, which is the easiest way to misread an A/B.

Both the arm and the compliance flag are held in a small req_id-keyed ring, not in a single context slot. A streamed turn hands back a generator and writes its trajectory after the semaphore is released, so a single slot belongs to whichever request is running then: that both leaked a treatment bit onto a control turn (poisoning the triggered-only block and dropping a clean GEPA fixture) and lost it from a steered one (defeating the GEPA isolation on the common path). Ineligible turns — internal requests, simulated/self-play turns, and anything running without a trajectory collector — are never enrolled at all: a turn whose arm cannot be recorded must not be perturbed by one.

Reading the results

introspect action='experiments'
PYTHONPATH=src python scripts/experiment_report.py [--day YYYY-MM-DD] [--alpha 0.05] [--json]

Metrics: failure_rate (UNKNOWN turns excluded — an unverifiable turn is not evidence either way), human_failure_rate (the same rate restricted to turns a HUMAN graded — see the guards table), n_steps, duration_s — all lower-is-better and all four consuming the Bonferroni budget — plus human_label_rate, which is higher-is-more-data, DESCRIPTIVE, exempt from the alpha split, and never renders a direction verdict.

Why confidence SEQUENCES, not a t-test — and what they do not promise

The operator will peek. A fixed-n p-value checked daily is not a valid test; a confidence sequence is built for continuous monitoring, so "the interval excludes 0" is a legitimate stopping rule. The implementation is the asymptotic CS of Waudby-Smith & Ramdas (2023): 

radius = σ̂ · sqrt( 2(nρ² + 1) / (n²ρ²) · log( sqrt(nρ² + 1) / α ) )

Asymptotic is load-bearing. There is no finite-sample guarantee, and the first version of this page claimed one. Measured miscoverage at a nominal 5%, 3000 simulated streams:

Dataplain SD, from n=2regularised SD, from n=30
Bernoulli p=0.552%2.5%
Bernoulli p=0.358%3.3%
Bernoulli p=0.182%9.2%
Normal(0,1)21%1.8%

Three guards follow, and all three are load-bearing:

  • Regularised variance (_regularised_sigma). The plain sample SD is 0 on constant input, which collapsed the interval to a POINT — six Bernoulli observations that happen to be constant per arm then "prove" a difference. At p=0.5 that shape occurs 12.2% of the time at 2 turns/arm.
  • No verdict below n=30/arm. The numbers and the interval are still shown; only the conclusion waits.
  • α split across metrics (Bonferroni ÷ the number of TESTED metrics — 4 today; descriptive rates like human_label_rate are excluded, since a denominator must not widen every real interval to pay for a diagnostic) as well as arms (÷2). Without it, "stop when ANY interval crosses" runs at ~15% against a nominal 5%.
  • human_failure_rate / human_label_rate (2026-08-17): the failure rate over turns a HUMAN graded, and its denominator. §4BR's decision rule accepts only human feedback as a correctness signal and disowns the plain outcome label as CIRCULAR — but the corrections overlay dropped the sidecar's source, so a human 👎 and a verifier_late machine verdict were byte-identical to the analysis and the pre-registered metric was uncomputable. The overlay now stamps extra["outcome_source"] (plus human_labeled, so a later machine correction cannot silently drop the turn from the denominator). human_failure_rate inherits the differential-attrition caveat a fortiori (it conditions on resolved AND labelled); human_label_rate carries a DESCRIPTIVE caveat and never announces a verdict — with lower-is-better false, "more thumbs in treatment" would otherwise have announced as a quality win, and it is the first human metric to clear the n≥30/arm floor on live data.

The p=0.1 row is the honest weak spot, and a low failure rate is exactly this agent's regime — treat a just-crossed interval on a rare event as a reason to keep collecting.

The difference interval is the conservative union of the two per-arm sequences: [lo_t − hi_c, hi_t − lo_c] — the exact Minkowski difference of the two boxes, ~40% wider than a purpose-built two-sample CS, but an argument that cannot go subtly wrong.

The dilution trap: read the TRIGGERED block

The risk-steer trigger fires on ~7.6% of turns. Averaging the effect over all enrolled traffic dilutes it roughly 13×, so the headline comparison would read "no difference detected yet" indefinitely while the treatment was really changing behaviour. The report therefore renders two blocks per experiment, and points at the second: 

■ risk_steer  (n=1200)
    [all enrolled turns]        ← safety net: would catch harm to turns the trigger never touched
    ── trigger fired on 91/1200 turns (7.6%) — READ THIS BLOCK
    [triggered turns only]      ← the comparison with power

Conditioning on the trigger is legitimate because the trigger is evaluated from state that does not depend on the arm: both arms compute the same reading and stamp the same key, and only the action differs. The key's presence means the gate tripped; its value means the treatment actually ran.

Variance reduction (§4I Phase 3)

Time-to-verdict is the binding constraint: at ~16 resolved turns/day against an n≥30/arm gate, anything that narrows the interval shortens every future answer. So a pre-treatment covariate (today: the complexity router's turn-0 confidence, stamped by core/turn_facts.py) is regressed out of the residual series that feeds the confidence sequence — CUPED. The reported MEANS are untouched; only the interval narrows.

Safe by construction: pre-treatment, so unbiased; θ ≈ 0 for a useless covariate makes it a no-op; a covariate that would widen the interval on the current sample is discarded rather than adopted; and it needs the covariate on ≥80% of rows before it engages.

Measured, not assumed — and smaller than the textbook figure. CUPED's usual 20–50% comes from a pre-period version of the same metric (correlation 0.6–0.9); a turn-0 difficulty score against a BINARY outcome cannot reach that. At n=200/arm:

Covariate strengthCS half-width reduction
none / weak0.0–0.3%
moderate1.3%
strong4.1%
very strong8.6%

A real but small win that costs nothing, and every report line prints what it actually bought ([CS −8% via covariate]) rather than claiming a benefit it did not deliver.

Honest caveats

  • Carryover / SUTVA violation. Cross-session memory means a lesson learned on a treatment turn can help a later control turn. That contaminates the control arm and biases the measured effect toward zero — a positive reading is conservative, a null one is genuinely ambiguous.
  • The outcome label is a proxy (verifier + structural signal): process health, not correctness. Same caveat grade_turn_outcome carries.
  • Differential attrition is the sharpest trap. failure_rate and human_failure_rate (_ATTRITION_SENSITIVE — the human-graded one also conditions on being LABELLED, so it inherits the bias a fortiori) condition on the turn resolving to PASSED/FAILED — a POST-treatment variable. A treatment that makes turns end unverifiable (the risk steer literally says "STOP. Report what is known") changes WHICH turns are scored; simulated with zero true effect that manufactured a 14-point "improvement". The report tests the UNKNOWN rate itself and flags both attrition-sensitive metrics CONFOUNDED when the arms differ on it — unless circularity takes precedence, since a metric the treatment moves mechanically cannot be rescued by an attrition caveat.
  • n_steps and duration_s are mechanism, not outcome, for any treatment that ends turns earlier. "TREATMENT BETTER" on those two is tautological, so they carry that annotation permanently.
  • Traffic is not iid. Requests arrive in correlated bursts; randomization balances that in expectation, but the variance estimate is optimistic when one session contributes many turns.
  • The measured population is narrower than "all traffic". Trivial greetings take _handle_trivial_chat, which bypasses the turn loop and the finalize chain — those turns write no trajectory, so they are assigned an arm that is never recorded. Correct (nothing under test can affect a one-shot "thanks"), but arm counts will always run below the raw request count.
  • Between-request only: it cannot measure anything that differs only WITHIN a request, nor a change that alters the corpus both arms read from.

Interaction with the GEPA optimizer

A treatment that mutates the prompt context contaminates the §4F Phase 2b fixture corpus, because that optimizer replays recorded payloads verbatim. Turns carrying a CONTEXT_MUTATING_KEYS flag are therefore excluded from mined fixtures by default (counted as experiment_context_excluded, never silent; --include-experiment-context overrides). Any future experiment whose treatment alters what the model sees must register its compliance key there, or the exclusion silently rots.

An honest limit on that trigger. The contract above says a trigger must be computed from state that does not depend on the arm. fs_batch_fired meets that to first order only: a changed schema can in principle change whether the tool is chosen at all. It is still much closer to pre-treatment than the obvious alternative ("the turn made ≥2 file_system calls"), which is precisely the quantity the treatment reduces and would condition the comparison on a POST-treatment variable — the same trap as reading failure_rate without unknown_rate. If the trigger RATE diverges between the arms, read the triggered-only block as confounded.

2026-08-11 — read the MECHANICAL half first: --fs-batch-arms

§4F's stated verification for this arm was never the outcome comparison: “re-run the ontology report; those n-grams must collapse. If they do not, the macro did not land, whatever the latency says.” That question needs no statistical power, so it is readable long before the effect is — which matters, because at this traffic the effect never becomes readable at all. 

PYTHONPATH=src python scripts/tool_ontology_report.py --fs-batch-arms

The eligible denominator is printed first, and the read declines itself when it is thin. “The model refused the capability” and “the model was never once offered a chance to use it” both render as zero paths calls, and only the eligible count separates them. Eligibility is derived from collapse_fs_batch — the shipped macro's own rule — never from a hand-written “≥2 reads” test, which would count read_chunked pagination that the macro deliberately does not touch and so measure a macro nobody deployed.

Standing cost, so the operator can price it. Registering fs_batch_context excludes the whole treatment arm from newly mined Phase 2b fixtures — roughly half of new supply while the arm runs at traffic: 1.0. That is the correct trade (a contaminated corpus is worse than a slower one), and it is dialable without a deploy: lower traffic or set enabled: false for fs_batch in $GHOST_HOME/system/experiments.json.
