core / task_wait.py

§4SU Phase 3 (2026-11-02): why a task is waiting is stored in three fields, not in its summary text. The model and the briefing see five states.

Why it exists

Before this phase, the reason a task waited lived in its result_summary: "… — not closed unattended" (a hold), "human gate: …", "not closed: <gate>: …" (a roll-up refusal), "flagged for human review". Thirteen string checks read those marks. Most review MAJORs in Phases 0–2 were in them: a mark quoted as evidence, a mark restated, a mark that lost its prefix.

The fields

A waiting task (stored status NEEDS_USER or BLOCKED) carries:

columnvaluesmeaning
wait_onownerthe owner must decide, approve or do it; nothing runs it until they do
owner_turna hold: never run unattended; the owner's own run takes it back and runs it
dependencyanother task (a failed child, an open depends_on)
wait_codehuman_gate, review, rollup_<gate>, a hold kind (unverified_build, model_experiment, gate_form, refused_<gate>, held…), child_failed (the failure cascade's block, the only one lifted automatically), blocked (any other block), asked, pausedwhat kind of wait
wait_whytext, ≤ 300 charsthe short reason the owner reads

Rules

  • Leaving a waiting status clears all three, for every writer: the store (update_task) and the tree (TaskTree.update_status, settle_waits).
  • A status write sets a wait only from its own wait=. With none it gets the safe default from default_wait: owner/asked, or dependency/blocked for BLOCKED. Review r5 found that the earlier default, child_failed, made a parent the model blocked ("waiting on the API key") reopen when any child closed. It never keeps the row's earlier wait. A missed writer fails safe (the owner decides); it cannot turn a task into a hold that runs. Review r1 MAJOR: a kept wait turned the model's park "the owner must approve the wording" into a hold the owner's run then ran.
  • The summary keeps its human text, and nothing reads it as state. The old marks are parsed in one place, wait_from_marks, used only by the one-off migration of old rows. The advancer's batch split reads the summary only when the task row is gone.
  • Folded statuses. READY is stored as PENDING. A task-level PAUSED (a phase the owner paused; the system never sets it) is stored as NEEDS_USER with owner/paused, so a paused phase still holds its subtree back. The stored names IN_PROGRESS / NEEDS_USER / BLOCKED stay, so the web console, Slack and the database keep their vocabulary (operator 11-02).

A claimed hold comes back (review r2)

The owner's run takes a hold back by claiming it: IN_PROGRESS, which clears its fields. The claim logs hold_claimed {wait_on, wait_code, wait_why, summary}. If the run is stopped, runs out of time, crashes, is deferred for the owner's request or has no tool runner, the release goes through ProjectStore.release_claim. That method puts a claimed hold back as the same hold (same summary) and anything else to PENDING. The boot reaper (reset_orphaned_in_progress) does the same. The claim is logged before the task is claimed: a kill between the two writes must not leave an unclaimed IN_PROGRESS row (r3). It ends with hold_claim_ended, which update_task logs on any status write other than IN_PROGRESS while a claim is open, whoever writes it, so an old claim never comes back later with its old summary. That includes a claim whose own IN_PROGRESS write had failed (r3, r4). At boot, the reaper restores claimed holds first, through update_task. A restore that fails leaves the row IN_PROGRESS, never PENDING, and the next boot tries again. claimed_hold(project_id, task_id) is the open claim. Before this, a release wrote PENDING and the next unattended tick rebuilt the held build.

Parents that wait for the owner (review r2)

A failed child no longer turns a parent that waits for the owner for its own reason (_owner_own_wait: NEEDS_USER, not a gate or roll-up park, no HUMAN_GATE postcondition) into BLOCKED. A gate or roll-up park over a failed child is blocked, so it cannot be approved with a FAILED child under it (r4). The cascade's block was later lifted to PENDING, and a paused or asked phase then ran with no release. The unblock lifts only the cascade's own block (code child_failed, the proof; r6 dropped an older test on failure_reason that kept a cascade block with a stale reason forever). The cascade never re-codes a parent the model blocked for its own reason (r6). A parent closed by its roll-up also lifts the cascade block on the parent above it (r7, a Phase 0 gap: the grandparent stayed BLOCKED, so its other children were never handed out). The migration codes an old BLOCKED row child_failed only when a child failed and no reason of its own was written, and blocked otherwise. A NEEDS_USER parent is not closed by its children finishing unless it is a roll-up refusal, a human-gate park, or carries a HUMAN_GATE (its roll-up parks it as the gate). The migration gives a held row that carries a HUMAN_GATE the gate's wait, not the hold's. When the owner releases such a parent (a write to PENDING from NEEDS_USER or PAUSED), it is judged at once (r3). A DONE parent that is reopened stays open: r4 found that it closed again at once and its dependants ran. A FAILED child closed DONE directly also lifts the block it caused (r4; older gap): it closes if its children are all DONE, and is BLOCKED if one failed. Before this it sat PENDING forever, because it is not a leaf.

The five-state view

view_state(task) returns {state, on?, why?}, and view_label(task) returns one label: PENDING, RUNNING, DONE, FAILED, or WAITING(on: why). The briefing's OPEN TASKS, task_list (field state, filter WAITING/RUNNING) and the tool's status enum use them. task_update status="WAITING" is stored as NEEDS_USER waiting on the owner, and "RUNNING" as IN_PROGRESS.

Functions

  • fold_status(status): the stored name (READY → PENDING, PAUSED → NEEDS_USER). It accepts a TaskStatus enum.
  • default_wait(status): (wait_on, wait_code) for a waiting status written with none.
  • wait_from_marks(status, summary): the migration's reader.
  • is_hold(task): wait_on == "owner_turn" and the status is NEEDS_USER.
  • is_waiting_on_owner(task, code=, prefix=).
  • view_state, view_label.

Migration

ProjectStore._migrate adds the three columns. _migrate_task_states folds READY rows into PENDING, and gives each NEEDS_USER / BLOCKED / PAUSED row with an empty wait_on the result of wait_from_marks plus its folded status. It is idempotent. If the column add fails (for example, a locked database), _has_wait_cols() is false and task writes drop the wait_* fields instead of failing (review r1).

Lab holds are not a wait 2026-11-04 §4SX D4

A build that could not get a lab is not a waiting status. It stays PENDING, and the hold lives in the project's metadata (core/lab_waits.py, see project_advancer). The design's "auto-lifting wait_code" was not used, because a BLOCKED leaf sets off the failure cascade and a NEEDS_USER leaf stops the project's autopilot.

Where it is read and written

  • memory.projects: the columns, the migration, and the clear and default rules in add_task / update_task.
  • planning: TaskNode.wait_*, set_wait, update_status(wait=), settle_waits, the human-gate park, the roll-up refusal (rollup_<gate>) and the failure cascade (dependency/child_failed).
  • project_advancer: every park or hold names its wait. The owner's take-back and the held pick read wait_on == "owner_turn".
  • tools.projects: not_closed[].waiting, task_list state and filter, and the autoadvance gates/holds split.
  • api.projects_routes: the owner's click over a constraint hold reads wait_code == "rollup_constraints" and the reason from wait_why.
  • prompts: the briefing's labels.
