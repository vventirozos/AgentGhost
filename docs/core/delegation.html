The job registry (jobs)

core.jobs.JobRegistry is the status surface every fire-and-forget mechanism was missing. A promoted sandbox command (below) registers into it (so did delegate and delegate_to_swarm until §4SI), and the jobs tool reports every job together: status (running + recently finished), collect (a finished job's full result — or every unread result), cancel. In-memory by design: jobs are per-process (their asyncio tasks die with the process), so persisting them would only resurrect zombies. Completed jobs are retained (bounded at 50, FIFO-evicted, running jobs never evicted) so a later turn can still collect a result the model never read. Tasks are spawned via spawn_bg — the codebase's one fire-and-forget primitive (strong ref + contextvar propagation + exception logging), never a bare create_task.

Sandbox jobs join the surface 2026-08-11. An execute command still working after 90 s is detached rather than left blocking the turn (sandbox.jobs) and appears here as kind sandbox. When it lands, the reaper WAKES the model with its result through the same internal-turn path scheduled tasks use, so the work continues without the operator; this surface is for asking about it in between. It breaks one assumption of the registry above: the process lives in the CONTAINER, not this Python process, so its row carries no asyncio task and nothing in-process can land it. _sync_sandbox_jobs therefore reconciles against the supervisor before every jobs answer — landing a finished job's exit code and output tail, enforcing the lifetime cap via reap(), and ADOPTING a job promoted before this process started (a promoted job survives an agent restart; without adoption it would run and be reaped with nothing able to report it). cancel on such a row kills the real process group FIRST and only marks the row when the supervisor reports a VERIFIED kill — a boolean, not a message prefix: "already done — nothing to cancel" carries no Error: and was being read as a successful kill, overwriting a completed job's result with CANCELLED. Cancelling the row alone would leave precisely the invisible orphan the subsystem exists to prevent. A row whose supervisor record has vanished is failed loudly rather than left hanging RUNNING for ever, and a FAILED job still hands back its output — a build that broke at minute 12 collecting as a bare "exited 1" leaves the model nothing to act on but the command it was just told not to re-run. The supervisor's log is deliberately NOT deleted at landing: this sync runs on every jobs call, so forgetting there destroyed the full output before anyone could read it. Test: tests/test_jobs_tool_sandbox.py.

Collect read-marking 2026-07-22. jobs(action='collect') with no job_id (the "collect all" case) previously re-dumped every retained finished job — up to 50 × 8000 chars ≈ 400 KB — back into context on every call, and the status text steered the model to keep doing exactly that (a real context-pressure hazard). Job gained a collected flag: a no-id collect now returns only un-collected finished jobs and marks them collected via JobRegistry.mark_collected; a repeat says "no NEW results" with a by-id re-fetch hint. An explicit collect(job_id=…) still returns that job's result unconditionally (explicit re-fetch is never hidden). Test: test_jobs_collect_readmark.py.

History: Job.result_resolver was added (2026-07-14 bug hunt) so a swarm job, whose worker returned a bool while its output landed in the scratchpad, collected its real content. The swarm is gone (§4SI); the optional hook stays on Job.

§4NS — background jobs 2026-10-12

  • Results over 8,000 characters say they were cut; every alias of collect (get, fetch) marks the output untrusted; a restart-lost result is named as such.
  • Ownership: a turn that is not the owner's (probe, scheduled run, job wake) sees, collects and cancels only the jobs IT started (started_by on every job).
  • The sub-agent fixes made in §4NS (FAILED on unfinished turns, own execute folder, no command promotion, polling hint) went with delegate in §4SI.
