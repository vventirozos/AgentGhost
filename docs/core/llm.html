Routing tasks

RoutingTask is a plain class of string constants — not an enum, and not a closed set. route() accepts any string, so these are a convenience for the call sites that share a label, not a contract. Members with a live caller:

The pool budget is a deadline, not a per-node duration 2026-08-18

A caller's queue budget covers the whole pool attempt and the request, as one wall-clock deadline. Before §4BV R5 it was spent in full by every node in the retry loop, and then again by the POST, so the two budgets added:

pool sizestated budgetmeasured, beforeafter
1 node (the shipping topology)12 s23.91 s9.01 s
2 nodes12 s24 s≤ 12 s
3 nodes12 s36 s≤ 12 s

route() states a 12 s fail-fast because it is awaited on the user's critical path and its fallback is free (a string concat), so every second past the budget is dead air. Two properties are load-bearing and easy to get wrong:

  • The remainder is shared across untried nodes. A flat per-attempt deadline removes the blow-up but lets node 0 consume the entire budget while node 2 — free right now — is never asked.
  • The floor is on the total, and the HTTP reserve comes out of it. _MIN_HTTP_FLOOR is held back so a caller cannot spend everything queueing and then POST with nothing left; flooring at _MIN_SLOT_WAIT alone would leave only 2 s of real queue time and quietly disable the gate.

Callers that state a budget do so by name via slot_wait=: route(), the web-summary distillation in search / darkweb_search (whose 55 s outer per-URL deadline would otherwise be exceeded — a saturated node then loses the URL instead of degrading to raw page text), build_gates, and the Verifier's critic leg. Everything else inherits GHOST_NODE_SLOT_WAIT_S (90 s), which remains a ceiling, never a value. keepalive bypasses the gate entirely, so a busy node can never read as a dead one.

Per-node concurrency gate — one budget per node URL 2026-08-11

The defect it removes (req 0fb69c5f). Deep research capped itself with an asyncio.Semaphore(3) built inside the function — so the cap was per call. The model issued three deep_research calls in one tool batch: 3 semaphores × 3 permits = 9 concurrent requests at a node advertising 4 slots (20 worker calls in 74 s, bursts of 3/second). The excess queued on llama-server past the route timeout; every one of those ReadTimeouts counted as a node fault; three consecutive tripped the breaker and ejected a perfectly healthy Nova for 60 s. It "recovered" 20 s later because nothing had ever been wrong with it — and the user's research came back degraded (the model's own next thought: "the deep research results are mostly timeout errors from the scraper backends").

No tool could fix this from where it stood. On this deployment Nova serves the worker and critic roles at once, and (until §4NQ) query expansion, web summaries, fact distillation and the verifier all reach it by different paths. A limit scoped to a call — or to a role — is individually polite and still collectively floods one box. The budget is therefore keyed on the node URL, held in LLMClient._node_slot(), and every node POST in _do_chat_completion passes through it (pinned by a seam test that counts POST sites against gated sites, because an un-gated path is a hole in a budget that only works if it is total).

Capacity comes from the node, not from configuration. The number that matters is llama-server's -np, so it is read once from the node's own /props (total_slots) and cached; a hand-set copy would drift the moment a node restarts with different flags. A node that will not answer the probe falls back to 3 — the old per-call value — so an unprobeable node behaves exactly as before rather than becoming unbounded. A gate whose failure mode is "no gate" is the defect it exists to remove.

And saturation is ours, not the node's. Waiting now happens in our gate rather than in llama-server's queue, which turns "is it sick or did we flood it?" from a heuristic into a fact: NodeSaturated means the request was never sent, so _is_node_fault() returns False and the breaker never sees it. A genuine ReadTimeout is still a node fault — the narrowing must not swallow the case the breaker exists for. Knobs: GHOST_NODE_SLOT_WAIT_S (default 90 s before giving up on a permit) and GHOST_NODE_SLOTS_DEFAULT (fallback capacity).

⚠ The health probe bypasses the gate entirely. keepalive_workers() is what prints "node X stopped answering"; if its ping queued behind the traffic it watches, a busy node would report as a dead one — the identical false alarm, reintroduced one layer down. One extra in-flight request against a 4-slot node is a rounding error, and an unstarvable probe is the entire point of a probe.

Tests: tests/test_node_concurrency_gate.py — 8 pins, 5 mutation-checked red.

Caller-fault exclusion 2026-07-22. A node failure only counts toward the breaker when it is actually the node's fault. _is_node_fault(exc) returns False for an HTTP 4xx (a bad or oversized payload, an unknown model) — a deterministic caller bug that would repeat identically on any node, so counting it would trip the breaker on a perfectly healthy node (e.g. a verify payload exceeding Nova's n_ctx) and force every routed call onto the single main slot for 60 s. Timeouts, connection errors and 5xx stay node faults. Applied at all five pool branches (worker/critic/coding/swarm/vision).

Upstream token accounting (2026-08-05)

The gap. Trajectory.tokens_in / tokens_out and eval.TaskResult.tokens_used were declared fields that read 0 on every record — 0 of 1515 trajectories, and the only producer of tokens_used was a hardcoded 0 in scripts/eval_baseline.py, so every SuiteResult ever written reported total_tokens: 0, summed and serialised beside real numbers. Nothing anywhere read the upstream usage block (grep '"usage"' over core/: no hits). The paired ablation could only report "~1.8× latency" because the token half was never measurable.

The shape. A turn makes MANY calls — each tool round, the verifier, and anything routed to a worker — so the per-turn number is a sum keyed on request id, not one completion's usage. LLMClient keeps a bounded (32-request) LRU ring; usage_for(req_id) reads it. An absent entry returns {} rather than zeros, so "no data" and "a genuinely cheap turn" stay distinguishable — the whole defect being fixed is a zero that meant "never measured".

Concurrency model

  • Fully async; asyncio.Semaphore(3) caps concurrent background routing tasks.
  • Per-node httpx AsyncClient means a single failing node cannot starve the others.
  • The breaker is process-local — restart resets state.

Streaming idle timeouts

_do_stream_chat_completion guards each SSE read with asyncio.wait_for so a genuinely hung upstream can't hold the event-loop slot forever (which keeps foreground_tasks > 0 and parks the idle scheduler, biological_watchdog). The budget is split because the first token of a turn is legitimately slow — the upstream must prefill (prompt-eval) the whole context before emitting any bytes, and on a large context (e.g. 120k tokens) or a loaded/CPU node that prefill routinely takes longer than the inter-token gap, with zero bytes during it:

ConstantEnv varDefaultApplies to
_STREAM_FIRST_BYTE_TIMEOUTGHOST_STREAM_FIRST_BYTE_TIMEOUT180sTime to the FIRST byte (prompt prefill / time-to-first-token).
_STREAM_IDLE_TIMEOUTGHOST_STREAM_IDLE_TIMEOUT60sGap between subsequent bytes (catches a real mid-stream hang).
_STREAM_ERROR_BODY_TIMEOUTGHOST_STREAM_ERROR_BODY_TIMEOUT15sReading the BODY of a >=400 response, purely to improve the error message.

Any received line — including SSE keepalive/blank lines — ends the first-byte wait and resets the gap timer. A timeout yields an error SSE event + [DONE]; the agent then sees a turn with thinking but no actionable output and forces a retry. The earlier flat 30s tripped that false "stall → forced retry" whenever a turn's prefill exceeded 30s, wastefully re-prefilling the whole (growing) context. The httpx client timeout (1200s) bounds the overall request above these. Tune the env vars for very slow or very fast nodes. Covered by tests/test_stream_idle_timeout.py.

The streaming coding pool joins the node discipline (2026-08-18, §4BV R7)

Until R7 _do_stream_chat_completion picked a coding node once, above its retry loop, with no concurrency gate, no circuit-breaker bookkeeping and no main-model fallback — while its non-streaming sibling _do_chat_completion has had all three since 2026-08-11. The breaker never learning is what made get_coding_node's is_available() filtering provably dead code on this path — verbatim the defect this file already records as fixed at generate_image. The node is now selected per attempt (so a retry moves to the next box instead of re-hitting the dead one), the permit is held for the whole generation, NodeSaturated advances without ever touching the breaker, a 4xx is not charged to the node, and an exhausted pool falls back to main with the caller's model restored in the payload.

Fan-out, 6 concurrent coding streams at a node advertising total_slots=2: peak simultaneous requests on the wire went from 6 to 2, with all 6 streams still completing.

Budget. The streaming path adopts _do_chat_completion's _queue_deadline (one wall-clock budget for the whole pool loop, divided by the attempts still to come including the current one, floored at _MIN_ACQUIRE, handed to the gate as a callable so the /props probe is inside it). It deliberately does not adopt _total_deadline/_http_budget: a stream has no meaningful total budget — nothing can pass one, and a long answer is not a fault — so its bound stays the per-chunk watchdog above.

Live impact: none. --coding-nodes is empty on this deployment, so the loop reduces to the same two main-model attempts as before. That equivalence is pinned by test_an_empty_coding_pool_is_still_exactly_two_main_attempts.

Stall attribution: our own queue is not the upstream's fault (§4BV R7)

Measured: 3 concurrent streams plus 1 non-streaming POST against the 1-slot main node put 2 of the 3 streams over the first-byte budget waiting in llama-server's queue behind our own traffic — and all of them printed Upstream Stream Stall. That is the same diagnosis corruption NodeSaturated exists to remove one layer down.

A self-queued verdict is now issued only on proof: a /props probe must have succeeded (only successful probes land in _node_slot_caps, so the capacity is never a default or a guess) and our own in-flight count must exceed it. Otherwise the line states the concurrency as a fact and leaves the diagnosis open — an unknown capacity is not evidence of innocence either, and a probed capacity we are within is reported as such rather than as "unknown".

SituationLog line
cap known, exceededStream Stall (Self-Queued): … 4 of OUR OWN requests were in flight against a 1-slot node …
cap known, within itUpstream Stream Stall: … (3 concurrent requests …; a 4-slot node, within capacity)
cap unknownUpstream Stream Stall: … (3 concurrent requests …; capacity unknown)
sole callerUpstream Stream Stall: … (sole in-flight request)

The counter is keyed on the configured URL (node["url"] / self.upstream_url), never str(client.base_url): httpx normalises the latter (http://h:8088/v1 → …/v1/, http://h:80 → http://h), and _node_slot_caps is keyed on the configured string, so a normalised key would silently never match and the whole verdict would be dead code. On the shipping topology --visual-nodes is byte-identical to the upstream URL, so main's capacity (1) is populated for free by the first vision call. A held _main_node_lock counts as one more in-flight request; pool POSTs are not counted at all, which can only lose an accusation, never manufacture one.

Three "a chunk may be bytes" fixes in one function (§4BV R7)

The chunk loop already documented that a chunk "is str on the real aiter_lines path but bytes on others". Two of its three consumers honoured that; the other two did not:

  • _note_usage_from_sse — decoded first. Correct.
  • The emit — interpolated the object into an f-string, shipping its Python repr (b'data: {…}'), a frame no SSE parser accepts. Invisible to the existing test, whose assertion is a substring a repr still contains.
  • _stream_rec_accumulate — its type guard sat outside its own try, so bytes.startswith("data:") raised TypeError, which the stream loop's except Exception turns into a re-raise with no [DONE]. With GHOST_LLM_RECORD=1 a bytes chunk killed the turn outright, despite a docstring promising "tolerant by contract".

All latent in production (httpx yields str), all fixed. Covered by tests/test_stream_coding_gate_4bv_r7.py (27 tests, 26/26 mutations killed).

Foreground-request yield (2026-06-11)

Background LLM callers (is_background=True) used to wait only on foreground_tasks — LLM calls in flight — capped at 30s. But a user turn spends much of its wall-clock between LLM calls (tools, file I/O, browser); in those gaps the counter reads 0, a background turn grabs the single llama slot, and the user's next turn queues behind a full background generation. Post-req-70 this starved the prompt for ~12 minutes while consolidation/self-play churned (both since removed, §4NM).

Two-signal policy in _wait_for_foreground_clear (shared by chat_completion and stream_chat_completion):

foreground_requests > 0a USER REQUEST is anywhere in its handle_chat lifecycleas long as it takes (600s hard ceiling against a leaked counter)
main_slot_idle_windows > 0 and foreground_tasks == 0 (§4KJ, 2026-09-24)the request is active but blocked on a NON-LLM node — generate_image opens the window (with self.main_slot_idle():, a counter) around the wait for the image node's slot AND its POSTONE caller admitted per render window, and only while exactly one user request is active (R4/R6 reviews: every parked caller used to pass in the same tick, and a second request's gaps between tool calls are not idle): the main slot is provably idle for the ~200 s render, during which every background call used to sit parked. The moment the turn resumes an LLM call, foreground_tasks parks callers again; the residual is one background generation the next foreground call may queue behind. foreground_requests is bracketed at the API layer by routes._mark_foreground(agent, ±1) around both chat handlers (the streaming one spans the whole SSE generator, agent loop + final-answer streaming). The helper only touches a counter that is actually an int, so mocked test apps and partial contexts no-op instead of raising. Failure replay's isolated handle_chat runs never pass the API layer, so background cycles cannot deadlock themselves. Covered by tests/test_foreground_yield.py.

Priority routing fixes — inline self-stall & off-main skip (2026-07-07)

The wait above protects exactly one resource: the main inference slot. Two classes of caller were misclassified against that rule (IMPROVEMENTS.md #2/#19):

  • Inline self-stall (fixed): three calls awaited inline by the user's own turn carried is_background=True and parked in _wait_for_foreground_clear against their own still-active request — a deterministic stall up to the 600s ceiling that read as “agent went silent” on long-output turns. Fixed to foreground: the Context Shield summarizer (fires on any oversized non-exempt tool result), the _prune_context history condenser, and the --perfect-it inline optimization (its shared helper takes foreground=; the deferred internal-learning path keeps background priority).
  • Foreground learning work (fixed; reflection and post-mortems were later removed, 2026-10-11 §4NM): the reflection closures (_critique_fn, _verify_plan_fn) and post-mortem closures (_analyze_fn, _patch_fn) in main.py ran at foreground priority — contending with the user's next turn for the 35B slot and inflating foreground_tasks so the “is a user live?” checks misread an idle reflection as an active user. Now is_background=True; if a user turn is running, the Reflector's per-call timeout simply defers the trajectory to the idle backstop.
  • Off-main skip (new): a background call that will be served by an existing off-main pool (use_worker/use_critic/use_vision/use_swarm/use_coding with a non-empty pool) skips the wait entirely — it never touches the main slot, so parking it was pure latency. The use_coding pool was added to this predicate 2026-07-22 (it had been the one off-main pool still misclassified as main-targeted). If every pool node fails, _do_chat_completion may still fall back to main: a rare, already-bounded edge, same as proceeding after the 600s ceiling.

Observability: a background caller parked 120s behind an active request now logs one BG Queue Wait line, so the operator's stream shows the park instead of a silent multi-minute gap. Covered by the priority-routing section of tests/test_foreground_yield.py.

Consumer degradation — off_main_only reaches the callers 2026-07-22

The off-main skip above still let a failed off-main call fall back to the main 35B (a worker hiccup mid-idle-loop dogpiled the single slot the user was waiting on). off_main_only=True makes that fallback raise OffMainNodeUnavailable instead, so the caller degrades — skips the cycle, uses a cheap local fallback — rather than stealing the foreground slot. Historically only route() and keepalive passed it; the 2026-07-22 LLM-stack review threaded it through the remaining background consumers: dream's worker calls (then 8, for self-play; mirroring their is_background), the verifier's last-resort fallback (bounded + is_background when no user request is live), project research's idle summariser, and the selfhood/workspace critique closures in main.py. Several untimed background calls (smart-memory extract, and — until their removal on 2026-10-11, §4NM — post-mortem and dream challenge-gen) also gained bounded timeouts so a wedged-but-connected node can't pin the journal drain for the 1200s httpx default.

Retry classification 2026-07-22. The main-path retry-except now also catches httpx.ConnectTimeout and httpx.PoolTimeout — these mean the request was never put on the wire (connection / pool-slot acquisition failed before send), so a retry is idempotent and worth it right after a llama-server restart. ReadTimeout is deliberately still not retried: the request may already be executing upstream, so a retry could double-run a non-idempotent generation. Covered by tests/test_llm_contention_fixes.py.

Empty / non-JSON upstream body — crash-proof decode (2026-06-23)

On the non-streaming path _do_chat_completion returned resp.json() directly. A 200 with an empty body therefore crashed as json.JSONDecodeError: Expecting value: line 1 column 1 (char 0), which the generic handler logged as “Upstream Fatal” and re-raised. Observed live right after a context overflow: while the agent's emergency-prune retry was in flight the upstream returned 0 bytes, turning a recoverable state into a hard failure with an opaque message.

The decode is now wrapped: an empty/non-JSON body is retried once (a transient empty body followed by a good body self-heals), and on a second failure it raises a clean, explanatory RuntimeError (“Upstream returned an empty/non-JSON response …”) instead of a bare decoder traceback. The handler catches ValueError (which json.JSONDecodeError subclasses) rather than naming json — conditional import json in the swarm branches above makes that name function-local and thus unbound on the no-swarm main path.

The caller side is gentler too: when the context-overflow emergency-prune retry fails, the agent now surfaces a calm, actionable message (“I hit my context limit … the task and its files are preserved … ask me to retry”) instead of a raw CRITICAL: dump. Covered by tests/test_upstream_empty_body.py.

Off-main node warmup + keepalive (2026-07-12)

Two background routines keep worker/critic nodes hot so the short route() timeout never eats a cold path: warm_up_workers() fires 3 tiny thinking-off generations per node at boot (covers model-load / first-request latency) — concurrently and off_main_only=True 2026-07-22: the old serial loop awaited each warmup in turn so they all re-grabbed the one slot that freed first (the other -np slots stayed cold, defeating the intent), and it omitted off_main_only (the sibling keepalive had it), so a node that was down at boot made each of the 3 pings fall back to the main 35B — burning the single main slot and able to evict the freshly-warmed main prefix cache. Now the 3 fire via asyncio.gather to occupy distinct slots, a dead node degrades instead of touching main, and the "pre-warmed" line only logs when a slot actually warmed. And keepalive_workers(interval_s) (spawn_bg'd from main.py, default 45 s via GHOST_WORKER_KEEPALIVE_S, ≤0 disables) pings each node forever — covering Tailscale/WireGuard idle cool-down mid-session, which boot warmup can't.

Heartbeats log transitions, not ticks. Healthy pings are fully silent in the live stream (the per-45s keepalive → Worker Node line was pure spam); a node that stops answering logs one WARNING, and its recovery logs one line. Per-ping traffic stays at logger.debug. Keepalive also passes off_main_only=True: a failed ping must never "fall back" to the main upstream (that was a max_tokens=1 hit on the single 35B slot every 45 s for as long as a node stayed down). Covered by tests/test_worker_warmup.py.

Main-node prefix warmup (2026-07-14)

The worker warmup above covers the off-main nodes; the main node's cost is different — the FIRST request of a session prefills the ~30k-token rendered head (system slot ≈ 14 KB + native tool schemas ≈ 63 KB, rendered by the chat template immediately after the system text) at the measured ~450 tok/s ≈ 70 s on the user's critical path. Both blocks are byte-stable across conversations (all volatile continuity was moved to the tail injection precisely for cache stability), so GhostAgent.warm_up_main_prefix() (spawn_bg'd from main.py at lifespan start; opt-out GHOST_MAIN_PREFIX_WARMUP=0) sends one background max_tokens=1 request carrying that exact head. The server's prefix cache (cache_prompt + --cache-ram) then serves it, and the first real request pays only its unique tail (hydrated memory + dynamic state + query ≈ 20-25 s). §4FM (2026-09-08): the warmed head did not stay warm. llama-server saves a ~200 MiB prompt-cache entry (the hybrid model's recurrent state) on every slot release; --cache-ram 6144 holds about 30; the idle loop makes 2–4 requests a minute — so the boot warmup's entry was evicted ~10 minutes in and every later user turn re-prefilled the head (measured through the agent 90 min after boot: 28,767 prompt tokens, 0 cached, 34 s). cache_prompt: false on the churn does not prevent the save (probed), and a mid-prompt divergence can only restore a checkpoint some request actually ended at — the head-only warmup request is exactly that checkpoint. GhostAgent.rewarm_main_prefix_loop (spawned at boot by main._spawn_main_prefix_rewarm, inside the warmup opt-out guard) ticks every GHOST_MAIN_PREFIX_REWARM_S (180; positive values floored at 30, 0 or negative = off) seconds and reads the main node's /metrics first: a tick is skipped while requests_processing > 0 (a coding leaf or bench in flight — re-warming inside a burst is the expensive, useless case) or when prompt_tokens_total has not moved since the last re-warm (nothing ran, the head is still the newest entry); metrics unreachable → re-warm. A mentioned </think> is not the close 2026-09-29 §4KP

llama-server's reasoning parser ends the reasoning at the FIRST </think> it sees — including one the model merely writes ("reasoning blocks end with `</think>`"). Everything after that mention reached the agent as content: the rest of the reasoning, the real close, the answer. Live probe probe-ff2dd1d7 shipped "` tag signals…" — the answer's head had gone to reasoning_content. Measured on the live server, streamed and not: a real close leaves the reasoning ending in a newline; a mention split leaves it ending mid-line, and the content resumes that same line.

core/think_split.py repairs it at this client, the one choke point: chat_completion (both branches) runs repair_message, stream_chat_completion wraps the upstream in repair_stream. When the reasoning channel stops mid-line at the first content delta, content is HELD until a real close (the tag starting its own line, then a newline) — what is before it goes back to reasoning_content, what is after it is the answer — or until the end of the generation, where an answer written INSIDE the reasoning is rebuilt from the last reasoning paragraph + the tag + the content, but only when the tag sat in an open inline code span on that line. Anything else is left as the server sent it. Frames that arrive during a hold (usage, a keepalive) are released after the resolved content, in order; an end frame that also carried content keeps its finish_reason. Every stream without a mid-line split is yielded chunk for chunk. While a hold lasts, each held upstream frame yields an SSE comment (: held), so the consumer's per-chunk work — cancel checks, the loop detector, the activity heartbeat — keeps running; the close search restarts at the last held newline. A hold ends at the close, at the end of the generation, at the first native tool_calls frame (the flood guards must see the calls), or past 8,000 characters (released unchanged). Only a generation that ended with finish_reason: stop may have its answer rebuilt from the reasoning; one cut by its token cap, a stall/abort error frame or a stream that simply ends, and an EMPTY non-streamed content, are never rebuilt into an answer: that is the cap cutting the reasoning, which callers such as the vision tool detect by the empty content. Known limits: held frames' own logprobs are not forwarded; a model whose real close does not end the reasoning in a newline (Gemma 4 on Nova, measured) would have every thinking-on reply held — no caller enables thinking there today.

A killed stream is still a call 2026-10-01 §4KV

The usage block rides a stream's final chunk. A stream the consumer walks away from — every thinking-loop or tool-flood kill — never delivers it, so the call was not counted at all: request slack-124c85b8 made four model calls and generated about 5,200 tokens, and its record said llm_calls: 2, tokens_out: 220 (the two killed calls were 3,765 and 1,284 tokens).

_do_stream_chat_completion now remembers, per attempt, whether a usage frame was counted and how many delta chunks went by. In the finally that closes the response, a stream that delivered chunks but no usage frame is counted by _note_unmetered_stream: one call, its output estimated as the chunk count (the upstream streams a token per chunk). The estimate is added to tokens_out and kept apart in tokens_out_estimated; unmetered_calls says how many calls' prompts tokens_in lacks (the prompt size of a killed call is not known). The request id is read when the stream is opened, because the finally may run at generator finalisation, outside the request's context. The trajectory carries extra.unmetered_llm_calls and extra.tokens_out_estimated only when there were such calls.

Limits, stated. The estimate counts frames that carry a delta, so it includes the role and finish frames (one or two too many per call). A stream that delivered no delta at all (a prefill stall) is not a call. The count is written when the stream's generator is finalised, a few event-loop turns after the consumer's break; every record measured carried it, but the client-streamed final path was not measured. _note_usage now reads every number of a usage block before adding any: a block with one unreadable number used to add its prompt tokens and stop.

Our impatience is not the node's illness 2026-10-02 §4KW

The worker and the critic are the same Nova server, so they share one circuit breaker. Three paths charged our own behaviour to it (independent review, with live timestamps):

  • route()'s 12 s was the client's own timeout, so a healthy Nova answering at 12.1 s — busy with our own critic verdict — raised a ReadTimeout that counted as a node fault (11 live at exactly +12.0 s, 6 within 1–2 s of our own critic dispatch; one opened the breaker). The deadline is now enforced by cancellation (the call runs as a task; route() waits on it and cancels it); the client gets _ROUTE_CLIENT_TIMEOUT_S (60 s). A caller that sets its own timeout without a total keeps its explicit request budget. Second review: a pure cancellation also stopped a hung node from ever tripping its breaker (reproduced: five hung calls, breaker still closed). A deadline miss is charged again — only when our request had held the node's permit for _ROUTE_HUNG_SILENCE_S (6 s; a routing call is ~0.5 s) with no other job of ours on that node (_charge_route_deadline_miss). Time spent queueing for the permit, a node busy with our critic, and a caller's own outer cancellation (e.g. the since-removed announced-work check's 3 s) are never charged. Alone means for the whole hold, read from the concurrency-seconds accumulator (fresh review: a critic that slowed the node and finished before the deadline had got it charged). After cancelling at the deadline, route() waits at most _ROUTE_CANCEL_GRACE_S (1 s) — py3.10 can swallow a cancel that lands as the permit frees, and the call then ran on its 60 s client timeout — uses an answer that lands in that grace, and lets the caller's own cancellation through. Not covered: VERIFY and DISTILL_PATTERN still pass their own timeout as the client timeout, so a ReadTimeout there is still charged.
  • Keepalive pings bypass the permit gate, so when our own gated jobs held every slot a one-token ping waited in llama-server's queue and timed out (two live trips were three such pings and nothing else). _charge_node_fault does not charge a keepalive then; with a free slot — or an unprobed capacity (second review) — it still does.
  • The memory optimizer's 4,096-token call could not finish in its 180 s at the worker's rate: a 600 s deadline by cancellation. Swarm charges only node faults (not a 4xx), and a client closed at shutdown is not a node fault.
