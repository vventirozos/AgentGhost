optim / tool_ontology.py — is the toolbox carved right, or just badly labelled?

§4F Phase 2b optimizes tool DESCRIPTIONS: same tools, better prose. This asks the two structural questions prose cannot answer.

The evidence that prompted it

The 2026-08-03 early ceiling check measured incumbent tool-choice fidelity at 0.772 (44/57) on never-seen fixtures — and the misses are not scattered. They cluster into a handful of specific pairs: browser↔file_system, execute→file_system, manage_projects over-selected (introspect/web_search misrouted into it), three no-tool stalls, workspace/notify_operator→system_utility.

When a model keeps confusing the same two affordances, "the description is unclear" competes with "the boundary is drawn in the wrong place" — and only the second is fixed by moving the boundary. The verifier rounds already taught the general lesson the expensive way: two candidates rejected by the private gate, and the diagnosis revised to capacity-bound rule-following. More prompt text cannot fix a problem that is not about text.

Two fidelity numbers, both reported. fidelity(replayable) excludes unreplayable rows (they measure the replay plumbing, not the toolbox); fidelity(all rows) is what the Phase 2b runner prints, since a GEPA metric must not reward a candidate for skipping hard fixtures. On a 57-row dump with 5 unreplayable they differ by ~7 points — the first version claimed they were the same number.

Why there is no merge verdict

The obvious feature — "tell me when two tools should be merged" — was attempted five times. Each attempt was killed by measurement, not by argument:

#GateMeasured failure
1count threshold alone92.8% spurious directives at n=400
2observed > expected98.5% — a comparison is not a test
3Poisson excess, naive marginal null42.8% at n=1000 — the null ignored that a miss can never land on the TRUE tool
4leave-one-out marginals90% false positives — over-corrected
5marginal null + symmetry + dominanceboth error rates moved the wrong way with corpus size: FP 0.0% → 11.7% → 50.1% (n=400 → 3000 → 6000) while power fell 74.7% → 3.9% → 0.0%

Attempt 5 failed for three independent reasons, each worth remembering:

  • the marginal null was biased, not noisy — obs/exp converged to a constant 1.20 under skewed tool usage instead of decaying to 1.0, so the Poisson p decayed exponentially in n and eventually fired on noise with certainty;
  • one condition ACCEPTED a null (p_sym ≥ α) — an acceptance region that shrinks to nothing as n grows, so any genuinely two-way pair is rejected once there is enough data to see it;
  • the Poisson tail underflowed to a constant 1.0 above λ≈745, switching the route off in silence at ~17k rows.

The instrument's job is to SURFACE candidates for a human decision, not to authorise "merge two tools" on its own. So a two-way pair is now reported with its raw shape — both directions, share of all confusion — and no tier that could be mistaken for a mandate. That is a deliberate scope reduction, and it keeps the part that was actually useful.

2. Sequences — what should have been ONE call?

PYTHONPATH=src python scripts/tool_ontology_report.py --min-support 5

Consecutive tool-call n-grams (n = 2..4) over the trajectory corpus, ranked by steps_collapsed × cohesion. This matters beyond ergonomics: depth is the agent's strongest measured failure predictor (17.8% at step 1 → 60.6% at step 12), so shortening the common path attacks the failure RATE, not just latency.

FieldMeaning
supportDISTINCT trajectories containing the sequence. Counted per-turn, never per-occurrence — otherwise one pathological grind session mints a macro proposal on its own.
cohesionFraction of occurrences whose calls share a TARGET. Enum fields (operation=read, action=ledger) and the redaction sentinel are excluded — counting them read 0.89 on every same-tool run, which is "doing the same KIND of thing", not "working on one thing".
steps_collapsedLoop steps a macro would ACTUALLY remove, computed from non-overlapping matches. Counting windows overstated the saving by 1.75–3.4×: five identical consecutive calls contain four overlapping 2-grams but collapse into only two macro calls. Candidates are also not additive — the same calls are mined at 2-, 3- and 4-gram sizes.
priorityRanking uses a per-turn cap on collapsible occurrences. Without it a single 50-call grind session (support 3) outranked a genuine 9-turn macro by 5.7× — the exact "one pathological turn redesigns the toolbox" failure min_support exists to prevent, leaking back in through the ranking.

Target matching runs two passes: exact, then CONTAINMENT for path/identifier-shaped tokens — because the same target is spelled differently by different tools (file_system(path="app.py") vs execute(command="python3 app.py")). Restricted to token-shaped strings so an English word cannot match inside a sentence.

The dominant finding is a batch affordance gap: the agent reads and writes files one at a time, across 108 distinct turns, at 0.72 cohesion — i.e. usually on the same file. A batch/multi-path file_system call is the single highest-value macro on the board.

This table has been wrong twice, in opposite directions, and both are worth knowing. v1 read steps=1431 for the ×4 row — the overlapping-window count, 3.6× the achievable saving. v2 fixed that with a greedy non-overlapping cursor but shared ONE cursor across all n-gram sizes, so a match of one sequence consumed windows belonging to another: that understated the corpus total by 49.6% and did so DIRECTIONALLY — same-tool runs claim the cursor first, starving exactly the cross-tool sequences a macro proposal is for (file_system → execute read 45 against a true 110). The cursor is now per-sequence — independently re-verified against the live corpus, which reproduced both numbers exactly. With it fixed, the raw window count overstates the corpus total by 1.34× (median per-candidate ratio 1.00), not the 1.75–3.4× an earlier note claimed against the broken version. The three file_system rows still describe the same underlying calls, so they must not be summed.

The fs_batch acceptance instrument (2026-08-04)

"The n-grams must collapse" is the acceptance test for the file_system batch macro, and it has a timing problem: mine_sequences reads a corpus of turns that have ALREADY happened, so on the day the macro ships the report cannot move no matter how good the macro is. simulate_fs_batch closes that gap — it rewrites the existing corpus as if the macro had been available and always used, so the same miner runs over both and the two reports are diffable: 

PYTHONPATH=src python scripts/tool_ontology_report.py                     # observed
PYTHONPATH=src python scripts/tool_ontology_report.py --simulate-fs-batch  # upper bound

It applies exactly the two rewrites the macro implements — merge a run of consecutive read calls into one (in chunks of 12), and drop a read that immediately follows a replace on the SAME target — and nothing else. Notably it does NOT collapse read_chunked runs (pagination is a different fix) or cross-file edit runs (not implemented); claiming those would overstate the macro.

It is an UPPER BOUND, and that is the point. It assumes full model uptake, which is the one thing a simulation cannot establish — that is what the live randomized arm measures. Read it as "here is the ceiling, and here is the instrument that will tell you how much of it was realised".

Measured on the live corpus (1336 user turns, 2026-08-04): file_system calls 1138 → 934 (−17.9%), all tool calls 3568 → 3364 (−5.7%), touching 51 turns (5.8%). Those 51 turns are not a random sample — their mean depth is 24.4 steps against 5.8 for the rest, and their failure rate is 58.3% against 23.7%. The macro is small in aggregate and concentrated exactly on the failing tail, which is what a depth intervention is supposed to look like.

Scope: this proposes, it never applies

Everything here is read-only analysis over data already on disk — no LLM, no replay, no prod involvement for the sequence half. Promotion of any proposal stays an operator decision behind the same private-tier gate Phase 2b uses. A self-modifying tool registry with no gate is precisely the failure mode this project's own history warns about.
