tool ontology experiments risk metacognition

optim / tool_ontology.py — is the toolbox carved right, or just badly labelled?

§4F Phase 2b optimizes tool DESCRIPTIONS: same tools, better prose. This asks the two structural questions prose cannot answer.

The evidence that prompted it

The 2026-08-03 early ceiling check measured incumbent tool-choice fidelity at 0.772 (44/57) on never-seen fixtures — and the misses are not scattered. They cluster into a handful of specific pairs: browser↔file_system, execute→file_system, manage_projects over-selected (introspect/web_search misrouted into it), three no-tool stalls, workspace/notify_operator→system_utility.

When a model keeps confusing the same two affordances, "the description is unclear" competes with "the boundary is drawn in the wrong place" — and only the second is fixed by moving the boundary. The verifier rounds already taught the general lesson the expensive way: two candidates rejected by the private gate, and the diagnosis revised to capacity-bound rule-following. More prompt text cannot fix a problem that is not about text.

1. Confusion — where are the boundaries wrong?

PYTHONPATH=src python scripts/optimize_tool_descriptions.py --confusion-out /tmp/confusion.jsonl …
PYTHONPATH=src python scripts/tool_ontology_report.py --replays /tmp/confusion.jsonl
VerdictPatternWhat it means
merge_or_redrawA→B and B→A both frequentThe two tools answer the same question for the model. Rewording either one MOVES the error rather than removing it — redraw the boundary or merge.
Every verdict is tiered by evidence — significant / suggestive / insufficient. A merge directive needs FOUR conditions: enough misses for power, the quieter direction attested, symmetry not rejected (exact binomial), AND the pair hotter than its tools' usage share already predicts (Poisson excess vs a marginal null, Bonferroni'd across pairs) — or, covering that null's blind spot, the pair being ≥40% of ALL confusion. Measured against a pure-noise corpus: 0% spurious merges up to n=1000, 2% at n=3000, versus 92.8% with a count threshold alone and 98.5% with a bare observed > expected comparison. Power on an injected real pattern: 64–97%.
describeA→B onlyA genuine one-way over/under-selection. This is what Phase 2b's description work actually targets: say what B is NOT for, or what A uniquely owns.
missing_affordanceno tool called at allThe request had no affordance the model recognised — a missing tool, not a confused one.

Two fidelity numbers, both reported. fidelity(replayable) excludes unreplayable rows (they measure the replay plumbing, not the toolbox); fidelity(all rows) is what the Phase 2b runner prints, since a GEPA metric must not reward a candidate for skipping hard fixtures. On a 57-row dump with 5 unreplayable they differ by ~7 points — the first version claimed they were the same number.

2. Sequences — what should have been ONE call?

PYTHONPATH=src python scripts/tool_ontology_report.py --min-support 5

Consecutive tool-call n-grams (n = 2..4) over the trajectory corpus, ranked by steps_collapsed × cohesion. This matters beyond ergonomics: depth is the agent's strongest measured failure predictor (17.8% at step 1 → 60.6% at step 12), so shortening the common path attacks the failure RATE, not just latency.

FieldMeaning
supportDISTINCT trajectories containing the sequence. Counted per-turn, never per-occurrence — otherwise one pathological grind session mints a macro proposal on its own.
cohesionFraction of occurrences whose calls share a TARGET. Enum fields (operation=read, action=ledger) and the redaction sentinel are excluded — counting them read 0.89 on every same-tool run, which is "doing the same KIND of thing", not "working on one thing".
steps_collapsedLoop steps a macro would ACTUALLY remove, computed from non-overlapping matches. Counting windows overstated the saving by 1.75–3.4×: five identical consecutive calls contain four overlapping 2-grams but collapse into only two macro calls. Candidates are also not additive — the same calls are mined at 2-, 3- and 4-gram sizes.
priorityRanking uses a per-turn cap on collapsible occurrences. Without it a single 50-call grind session (support 3) outranked a genuine 9-turn macro by 5.7× — the exact "one pathological turn redesigns the toolbox" failure min_support exists to prevent, leaking back in through the ranking.

Target matching runs two passes: exact, then CONTAINMENT for path/identifier-shaped tokens — because the same target is spelled differently by different tools (file_system(path="app.py") vs execute(command="python3 app.py")). Restricted to token-shaped strings so an English word cannot match inside a sentence.

The dominant finding is a batch affordance gap: the agent reads and writes files one at a time, across 108 distinct turns, at 0.72 cohesion — i.e. usually on the same file. A batch/multi-path file_system call is the single highest-value macro on the board.

This table has been wrong twice, in opposite directions, and both are worth knowing. v1 read steps=1431 for the ×4 row — the overlapping-window count, 3.6× the achievable saving. v2 fixed that with a greedy non-overlapping cursor but shared ONE cursor across all n-gram sizes, so a match of one sequence consumed windows belonging to another: that understated the corpus total by 49.6% and did so DIRECTIONALLY — same-tool runs claim the cursor first, starving exactly the cross-tool sequences a macro proposal is for (file_system → execute read 45 against a true 110). The cursor is now per-sequence. The three file_system rows still describe the same underlying calls, so they must not be summed.

Scope: this proposes, it never applies

Everything here is read-only analysis over data already on disk — no LLM, no replay, no prod involvement for the sequence half. Promotion of any proposal stays an operator decision behind the same private-tier gate Phase 2b uses. A self-modifying tool registry with no gate is precisely the failure mode this project's own history warns about.
