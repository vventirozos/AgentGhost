Metacognition — validator logging

What --enable-metacog does today: each time the shell or SQL validator blocks a command, it logs one metacog valid line and counts it; at shutdown it prints the total. Off by default. The validators themselves run whether or not the flag is set.

Removed in §4PT (2026-10-17). Host telemetry (the CPU/RAM/disk poller), the trigger bus, the runtime-budget and repetition alarms, and the replan bridge that could ask a project task to re-plan were all removed at the operator's request. See §4PT below for what went and why.

Removed in §4PJ (2026-10-16). The uplift originally also had a per-turn composite confidence score (core/confidence.py), its inputs — a per-domain competence profile (memory/competence.py) and a per-token logprob entropy tracker (core/entropy.py) — the calibration corpus with its hourly idle refit (core/calibration.py, the metacog calib / 📐 lines), the dual-solver arbiter (core/arbiter.py, already hard-disabled since 2026-06-28 after an ablation showed no gain at ~1.8× latency), the low-confidence deep-verification trigger (the lowest 15% of recent turns got a 3-sample verdict) and the daily "shakier answer" 👍/👎 label ask. All of it was cut at the operator's request. Why: measured on the current epoch the score ranked outcomes at AUC 0.48 (interval 0.30–0.67, i.e. chance) and lost to a constant as a probability, and its only live consumer sat behind the verifier's LLM judge, which the operator turned off on 2026-10-14. The main turn loop no longer asks the model server for logprobs. The flags --metacog-confidence-threshold, --metacog-disable-logprobs, --metacog-disable-arbiter and --metacog-arbiter-timeout-s are gone; --calib-refit-cooldown is still accepted and ignored. The data files under $GHOST_HOME/system/calibration/ and competence_profile.json were left on disk untouched.

Status

With --enable-metacog set, the server builds a small core/metacog.py:MetacogBundle at startup and hangs it on GhostContext.metacog. The bundle holds one thing: a counter of validator blocks. Without the flag, context.metacog is None and nothing is logged or counted — but the shell and SQL validators still check every command, so safety does not depend on the flag. The production launcher passes --enable-metacog.

The pre-flight repeat-failure guard below lives in the same area for historical reasons, but it has its own flag and does not need --enable-metacog.

Pre-flight repeat-failure guard feature 1A

Blocks a known-failing action before dispatch instead of mining the loop after the turns are spent. (It began as the live counterpart of the post-mortem engine's repeated-error fingerprint; that engine was removed on 2026-10-11, §4NM.)

The idle post-mortem (reflection/postmortem.py, removed 2026-10-11, §4NM) computed a TranscriptSignature whose dominant pathology was usually the SAME error from the same tool recurred N×. That insight only lands after a failed run has already burned its turns. The pre-flight guard promotes the same notion into the live tool loop: RecentFailureGuard (core/triggers.py) keeps a bounded rolling memory of recently-FAILED calls keyed by (tool, primary target) — the same primary_target_from_args key the offline read-loop detector and the in-run no-progress loop-breaker use — with the error text normalised to an 80-char lowercased prefix so two failures that differ only in a trailing variable count as one recurring failure.

Before each tool is dispatched (core/agent.py, just before dispatch), the loop asks would_repeat(tool, target). If the same action has already failed the same way at least repeat_threshold times in the window, the call is skipped and replaced with a synthetic SYSTEM BLOCK tool message carrying the prior error, telling the model to change approach (or re-issue with an explicit modification if it believes the failure was transient). Every FAILED result is fed back into the guard in the per-call outcome loop.

Default repeat_threshold = 2 is deliberate: keying on (tool, target) alone would block a legitimate retry — e.g. re-running execute on a script after editing it to fix the bug (the exact case the idempotency guard already exempts execute/file_system.write for). Requiring the identical error to recur means a post-fix re-run that now succeeds, or fails a new way, never trips the guard — only a genuinely stuck loop does. Idempotent setters (update_profile, learn_skill, knowledge_base insert/forget) are exempt entirely, since the idempotency guard above already covers them.

Lifecycle & keying hardening (2026-07-30). The threshold rationale above has a blind spot: it only protects a fix made between the two failures. Fix the cause after the second identical failure and the retry is blocked pre-dispatch — it can never run, so it can never refute the stale entries, and the guard deadlocks (observed live: the model killed the process holding a port and confirmed it free, then three consecutive requests were boxed in re-attempting a manage_services start that would have succeeded). Three changes close this: (1) world-changed reset — a successful state-mutating call (file_system mutation, mutating manage_services action, or an execute command matching looks_mutating_command: kills, file-mutation verbs, service-manager subcommands, bare redirects — not probes) clears the guard via note_world_changed(); fresh identical failures re-arm it at the threshold. "Successful" is execute-aware: shell results carry an EXIT CODE: banner rather than an Error: prefix, so the world-changed branch parses it — a failed kill (exit 1) must not clear the guard. Execute failures still are not recorded into the guard, deliberately: repeated identical shell failures are the strike ledger's / System-3 pivot's crisis signal, and pre-dispatch blocking would starve the pivot. (2) signature keying — when primary_target_from_args recognises no key (manage_services' identity is name/port/ command), guard_key_target keys on an args# SHA-1 of the full canonical call, so only a byte-identical re-issue counts as a repeat and changed-arg retries stay legal. (3) request scoping — the guard resets at request start; entries no longer leak from a previous request's world. Cross-request pathology is no longer mined by anything since the post-mortem engine was removed (§4NM); the activity ledger and the learning loop are where repeated failures surface.

The guard is independent of --enable-metacog: it ships on by default and is governed by its own --enable-preflight-guard / --no-enable-preflight-guard flag. When disabled, the guard object still records failures (cheap) but is never consulted as a hard block. Covered by tests/test_preflight_guard.py.

Module map

ModuleRole
tools/validators.py validate_shell and validate_sql reject unparseable, deny-listed, or unguarded destructive forms (for example a SQL DROP without confirm=true) before the executor sees them. Validators never raise; they return (ok, reason). They run on every call, flag or no flag.

core/metacog.py / core/metacog_log.py The bundle (an enabled flag, the validator-block counter, count(validator_block=True) and shutdown()) and the single log-line shape.

Pipeline

  1. Before a shell or SQL call runs, the validator checks it. A block returns the reason to the model instead of running the command.
  2. If --enable-metacog is on, the block is also logged as metacog valid and counted.
  3. At shutdown, the bundle prints metacog summary validator_blocks=N.

Operational notes

  • Cost. Validators are local parsing. Nothing adds a model round-trip or a background poller.
  • Failure modes. A validator that itself crashes returns safe-reject. If the bundle fails to build, the boot line says state=init_failed and the agent runs without it.

Logging contract

Every metacog event reaches the operator in one shape: a single grep prefix and structured fields. See core/metacog_log.py. 

metacog <subsystem>    key=value key=value ...

Subsystems

IconSubsystemFired byLevel
🌱metacog bootLifespan enable / disable / init_failedINFO / ERROR
📊metacog summaryShutdown — one lifetime rollup lineINFO
🚧metacog validEach pre-execution validator blockWARNING

The metacog host, metacog replan and metacog gate subsystems were removed in §4PT (2026-10-17); metacog conf, metacog arbiter and metacog calib in §4PJ (2026-10-16).

Field conventions

  • Floats render at %.2f.
  • Booleans render as yes / no.
  • None renders as -.
  • Strings with spaces are auto double-quoted so a parser can split on whitespace without losing words.

Example lines

metacog boot      state=enabled validators="shell, sql"
metacog valid     verdict=block tool=shell reason="rm -rf / deny-listed" command_head="rm -rf /"
metacog summary   validator_blocks=1

Host telemetry and replanning removed 2026-10-17 §4PT

At the operator's request, everything in the metacog add-on except validator logging was removed:

  • Host telemetry — utils/telemetry.py (HostTelemetry, HostSnapshot, HostSignal), the 1 Hz CPU/RAM/disk poller and its metacog host lines.
  • The trigger bus and its alarms — from core/triggers.py: TriggerBus, TriggerEvent, LoopDetected, ResourceExhausted, ExecutionAnomaly, the loop_event/resource_event/anomaly_event factories, ToolRuntimeBudget and RepetitionCounter. The turn loop's per-tool metacog hook in core/agent.py (loop/anomaly publishing and runtime-budget recording) went with them.
  • The replan bridge — ReplanBridge and the metacog replan lines, plus its only callees ProjectPlan.request_revision and TaskTree.request_revision (core/planning.py) and the project advancer's _metacog_set_task calls. TaskNode.revision_count and its reporting were removed afterwards (§4PV); only the unused DB column remains.
  • The bundle shrank to the validator-block counter: set_active_task, record_outcome and the telemetry/bus/bridge/runtime-budget/repetition attributes are gone. The metacog_log subsystems HOST, REPLAN and GATE (which never had an emitter) were removed. The boot line is now metacog boot state=enabled validators="shell, sql".
  • Flags — the six host flags (--metacog-cpu-high, --metacog-mem-high, --metacog-mem-floor-mb, --metacog-mem-warn-free-mb, --metacog-disk-high, --metacog-host-heartbeat-s) are still accepted and ignored.
  • Script — scripts/metacognition_functional_test.py was deleted.

Why (evidence from the whole log history): about 3,000 host signals, nearly all "CPU above 85%" from before the launcher set the CPU/RAM trip points to 101% (off), and every one was log-only — nothing acted on them. The replan bridge made 2 re-plan attempts, both rejected, and caused 0 revisions ever. The only part that did anything was the validators: 14 blocks (10 shell, 4 SQL DROP without confirm). Those validators run regardless of the flag, so they were kept, and so was the line that logs and counts their blocks.
