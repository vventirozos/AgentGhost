optim / env_mining.py — turning the agent's own failures into verifiable-reward tasks

§4CV. GEPA scores a candidate prompt by token overlap against a recorded reply. An executable oracle replaces that proxy — and unlocks the 191 FAILED turns that contribute nothing today.

Why

optim/trainset.py builds GEPA's examples from PASSED trajectories and scores a candidate by token overlap against the recorded final_response. Two consequences follow. The 191 failed turns in the corpus contribute nothing — a failure has no gold answer to overlap against. And the metric rewards looking like the recorded reply rather than being right. An executable checker fixes the second and unlocks the first: a mined failure becomes an example whose target is "the checker exits 0", which is a verifiable reward rather than a string-similarity proxy.

The shape is Envs-FORGE and SENTINEL reduced to what this corpus can actually support.

Both corrections are recorded here rather than somewhere quieter, because the funnel is the argument for the scope. The first draft said 67 containment-clean seeds — that used a hand-written list of "live-world" tools, where the real REPLAY_FORBIDDEN_TOOLS also denies manage_services, system_utility, postgres_admin and knowledge_base. The second said "~12 items" by applying Envs-FORGE's ~34% acceptance rate to those 35; measured over live runs once both gates worked, it is 12 synthesised, 1 accepted.

So the honest expectation is one to two usable items, not twelve — below GEPA's documented 20–100 range, which means this does not yet supply the consumer it was scoped for. That is a measured result, not a setback to work around: the remedy is a better synthesiser or a different seed population, and loosening the gates would restore the count while destroying the reason to want it.

One design assumption also died on contact: 112 of 176 failing turns carry no failure_reason at all, and only ~10 have a specific diagnosable one. SENTINEL's Controller mines recurring failure modes; this corpus does not have them, so mining is per-trajectory and no recurrence threshold is applied — one would look principled and reduce 35 seeds to almost none.

Two gates, and the second exists because the first was not enough

Gate 1 — oracle_is_sound: can this checker FAIL? The reference answer must be accepted and two mechanical negative controls — a sentinel string and the empty string — must be rejected. Mechanical, not model-authored: a model asked for a "wrong answer" can produce an accidentally correct one, and the resulting rejection would be a real oracle failing a real answer, exactly backwards. Every run is repeated (currently 4×) on both legs, because a validator that sometimes accepts a wrong answer manufactures false PASSes — label noise pointed straight at the learning corpus.

Gate 2 — solvability_probe: is there ONE right answer? These are different questions, and the first live run proved it. A mined chess item validated if data['move'] != 'e7e6': sys.exit(1). That oracle passes every check in gate 1 — it accepts its reference and rejects both controls, so it demonstrably discriminates — but e7e6 is one of many reasonable moves. The task is indeterminate and the validator encodes a preference as a fact.

⚠ The pass-rate band alone was not enough either. It cannot distinguish hard-but-determinate from indeterminate-whose-preferred-answer-is-sometimes-produced: a "favourite colour" item was accepted at 1/4 while a determinate 6×7 item was rejected as trivial at 4/4. The distinguishing signal is not the pass rate — it is whether the independent samples agree with each other. A determinate task pulls samples toward one answer; an indeterminate one scatters them, and the checker's preferred value is merely one of the scatter. So the modal answer must recur. It costs nothing extra (the samples were already drawn) and errs toward rejection, which is the safe direction for a trainset.

Two counters are kept apart on purpose: a sample the checker could not score, and a call that produced no output at all. Folding them together subtracted an empty generation from the denominator twice and flipped a mixed item to TRIVIAL.

Model-authored code runs under the kernel sandbox

The first version ran validators with subprocess.run(..., cwd=tmpdir) and called a tuple of 11 module names its containment. cwd is not confinement. Reviewers walked 13 of 15 bypasses straight through the deny-list — os.system("curl …"), subprocess with an absolute path, import http.client (the top-level name is http), ctypes, webbrowser, shutil.rmtree of the live bank directory — and executed one that wrote outside the temp dir and spawned a socket-holding grandchild while the gate reported "accepts its reference, rejects both negative controls".

A deny-list of module names is a lexical proxy for "cannot touch the box"; the AST rewrite moved that proxy rather than removing it. §4CI's lesson is that every exemption in a deny-list becomes the next bypass, and §4CR's is that closing this class needs the child under the sandbox rather than beside it. evolve/confine.py already existed for exactly this. The static checks remain as a cheap pre-filter; they are no longer the containment.

Verified by execution, both directions: every attempted escape is a PermissionError under confinement — direct writes, os.replace, symlinks, hardlinks, ../ traversal, rewriting the child's own policy file, detached grandchildren after the parent exited, os.fork, TCP/UDP/AF_UNIX — and the identical validator succeeds with GHOST_EVOLVE_CONFINE=0, which is the half that makes the other half mean anything.

What it does not close, stated because the bypass list enumerates it. The policy is an integrity boundary, not a confidentiality one: reads stay open (a read-tight policy would refuse the interpreter its own stdlib), so a validator can read a secret. What it cannot do is make that value land anywhere — writes, network and every destination outside the workdir are denied, and stdout is discarded. The residual is (allow default) permitting mach IPC. The honest statement is "a validator may read what this box can read; it may not change or transmit anything", and that is the property the gate relies on.

Staging is not arming

eval.banks.pick_next_item walks every bank in system/bench/banks/, and the biological watchdog calls it in production. Writing there is not "saving a file", it is arming a live loop with unvetted synthetic items. Mining writes to system/optim/mined_envs/; --promote is a separate operator act. The separation was a path convention until a reviewer wrote straight through it with --name ../../bench/banks/live_bank — it is now a checked boundary on both sides.

Staging accumulates: the first version truncated, so each run deleted the previous run's items and the corpus could never grow toward GEPA's range. It also read through the epoch filter before rewriting the whole file, which meant the first run after an MINING_EPOCH bump silently erased the superseded corpus. Superseded rows now stay on disk unserved, and the write is atomic.

The consumer — and the loop that shipped unwired twice

scripts/run_gepa.py --mined-bank NAME loads staged items, stamps the reference into the signature's own output fields, and scores those rollouts by running the checker instead of by token overlap. Items carry origin="bench", so trainset.real_only_gate keeps them out of the private ship tier: bench may teach, it may never grade (§4BH).

⚠ This is the third time this loop has been built without a working consumer, and the second was inside the fix for the first. Version 1 shipped with oracle_score called by nothing at all. Version 2 added the flag — and stamped {"final_response": ref, "plan": ""}, which run_gepa's keyed filter twelve lines later drops, because it keeps only examples with a truthy field named in sig.outputs. Measured on the live corpus: 0 of 1 mined examples survived, the oracle never fired, and nothing said so. Now: 12 of 12 survive, none reaches the private tier, signatures without a user_request input are refused (their golds would arrive empty and score 0.0 in both arms), and if the filter ever zeroes them anyway the run aborts rather than silently losing the flag's whole effect.

The loop also has a mining.failure_envs row on the LOOP YIELD view from day one, where invoked counts items a GEPA metric can train on rather than items staged — counting production as consumption is the defect that view exists to expose.

Running it

# the seed funnel only — no LLM calls, nothing written
PYTHONPATH=src python3 scripts/mine_failure_envs.py --dry-run

# mine into STAGING (never the live bank)
PYTHONPATH=src python3 scripts/mine_failure_envs.py --limit 20

# arm the live bench flywheel with the staged items (SEPARATE act)
PYTHONPATH=src python3 scripts/mine_failure_envs.py --promote

# train a prompt against the executable oracles
PYTHONPATH=src python3 scripts/run_gepa.py --signature planning.decompose \
    --mined-bank ghost_failures …

Environment: GHOST_MINE_REQUIRE_CONFINE=1 refuses to execute model-authored code without the kernel sandbox (default off, so the miner still works off macOS — the item records verified_confined either way). --no-probe skips the determinacy gate and the report says so, because "accepted" means something weaker without it.
