Memory hydration with Reciprocal Rank Fusion

How a query becomes a sectioned markdown injection of vector + graph + skill + episodic results.

RRF formula

combined_score(doc) = Σ_ranker  weight_ranker / (k + rank_in_ranker + 1)
k = 10  (MemoryBus._RRF_K on the hydration path; 60 is only the classmethod default)

The hydration path uses k = 10 (_RRF_K): over the bus's 5–15-item lists the web-scale 60 flattened intra-tier spread to ~19% while the tier weights spread up to 20×, so a list's own order was discarded (2026-07-22). A smaller k favours each ranker's top result more.

Intent weights

The bus first classifies the query as factual, procedural, or contextual with a keyword classifier (MemoryBus._classify_query_intent, no LLM call), on the user's own words (raw_user_text), not an expanded follow-up. Since §4MJ it tokenises on letters, reads "how" as procedural only in "how to/do/can/should/would", as factual in "how old/many/much/long/far", and not at all in a greeting ("how are you"), and ignores "should".

Global budget & fused-score ordering

Final markdown is capped at max_chars: production passes context_budget=4000, scaled to 8000 / 12000 for 16+ / 31+ words of the USER's message (§4MJ: not the expanded query). The fused RRF ranking now drives inclusion and order. Items are emitted in descending fused score (interleaved across sources) under a single global budget — source headers are emitted lazily on first sight so a tier's items still cluster under its header. The earlier fixed per-section budget map (_SECTION_BUDGETS, graph 25 % / vector 40 % / skill 20 % / episodic 15 %) was removed: it re-grouped items by source and silently discarded the fused score / intent weights / learned weights, making them cosmetic.

  • Per-source cap _PER_SOURCE_CAP = 6 — a count cap (not a char budget) stops one tier monopolising the budget while still honouring fused-score order.
  • Cross-tier relevance floor _RELEVANCE_FLOOR (default 0.0) — fused scores are normalised to [0,1] against the top item, and anything below the floor is dropped before injection. Kept 0.0 deliberately: measured 2026-07-15 that this floor CANNOT reject an off-topic query — RRF scores derive from (rank, tier weight, intent) and discard embedding distance, so the best match normalises to 1.0 either way. It survives only as a relative-pruning knob.
  • Vector best-match gate _VECTOR_MATCH_FLOOR (0.42, env GHOST_VECTOR_MATCH_FLOOR) — the actual off-topic gate. If the closest vector candidate's raw embedding distance exceeds it, the query has no strong semantic match and the vector tier injects nothing. Measured separation on BGE-small: worst on-topic best-match ≈ 0.40, best off-topic best-match ≈ 0.44 → 0.42 sits between with margin, and on-topic hydration is untouched so recall can't regress. Applied on the hydration path only (via search_items(min_relevance_dist=…)); the recall tool leaves it unset and stays best-effort.

Companion gates upstream: VectorMemory.search now admits name-memory / summary rows on a relaxed distance threshold (threshold × 1.5) instead of unconditionally, and EpisodicMemory._vector_search derives relevance_score = clamp(1.0 − distance, 0, 1) and drops hits below MIN_VECTOR_RELEVANCE = 0.70 (was a flat 1.0 for every hit). Graph seed-term extraction (_extract_query_terms) no longer auto-seeds the literal "user", which previously returned the user ego-graph every turn regardless of topic. Covered by tests/test_memory_relevance_gating.py.

Step-by-step

  1. Decompose the user query into 2-3 sub-queries (LLM call or "and also" / "as well as" heuristic). Internal requests (sub- gets an empty bus; sched-/job-/sim-) still get every tier, but no decomposition; decomposition needs 8+ user words and an un-rewritten query.
  2. Fan-out: asyncio.gather hits each available memory tier with each sub-query.
  3. Per-source ranking: each tier returns its own ordered list (token-overlap + BM25 re-rank for vector (no cross-encoder); spreading-activation BFS for graph; BM25-augmented vector for skills; trigger-similarity for episodes).
  4. Fuse: RRF scores each candidate across rankers; intent weights bias the sum.
  5. Format: sections grouped by source, in first-acceptance order: ### TOPOLOGICAL KNOWLEDGE GRAPH:, ### MEMORY CONTEXT:, ### SKILL PLAYBOOK (…), ### PAST EPISODES (…), ### PAST CONVERSATIONS (…).
  6. Inject: NOT into the system prompt — the block rides the per-turn injection wrapped in <session_context>; with GHOST_PIN_TOOL_SCHEMAS=1 (live) it is pinned to the conversation's first user message so the cached prefix stays byte-stable.

Dedup gate (write side)

publish_fact uses an LRU of 256 most-recent (event_type, fact_data) MD5 signatures to short-circuit replays. The signature includes the REQUEST id (§4KZ) and excludes metadata.timestamp, so dedup is per request: the same fact published in a later turn is written again (a value changed back must not be dropped as a repeat).

Episodic semantic recall feature 1C

The episodic tier stores action sequences with outcomes in episodic_memory.db and is recalled by trigger similarity. Its semantic path (EpisodicMemory._vector_search) maps vector hits tagged type=="episode" back to episode rows — but for a long time nothing wrote episodes into the vector store with that metadata, so the path found nothing and recall silently fell back to substring matching (missing any past episode that shared no keywords with the query).

record_episode now accepts a vector_memory and indexes each episode's trigger (+lesson) via VectorMemory.add with {"type":"episode","episode_id":…} metadata; the significant-turn writer (GhostAgent._record_episode_safe) passes context.memory_system. The store stays bounded: episodes evicted by the 500-row capacity cap have their vector entries removed via VectorMemory.forget_episode(episode_id) (collection.delete(where={"episode_id":…})), and the vector store already treats type=="episode" as a non-prunable population owned by the episodic store. Indexing dedups on the document text (md5), matching add's own contract. Covered by tests/test_episode_vector_recall.py.

Belief-revision surfacing REMOVED §4KZ

This section is historical. The prompt block was removed in §4KZ; explain_belief_change has no caller (the contradiction log is write-only — see §4MI G-8).

The contradiction engine logs every supersede to ContradictionLog (I previously thought X, updated to Y because you said Z), but explain_belief_change(query) had no live caller, so the agent could never actually voice it. Immediately after the MemoryBus.hydrate_context fan-out, GhostAgent now calls explain_belief_change(last_user_content) and, when a recorded revision matches the turn's query, appends a ## BELIEF REVISION HISTORY block to the hydrated context. Best-effort and query-scoped; absent a match it injects nothing.

Learned intent→source weights

The 3×5 _INTENT_WEIGHTS matrix (graph/vector/skill/episodic/session per factual/procedural/contextual) is hand-tuned magic. core/rrf_weights.py makes it learnable: fit_intent_weights derives a matrix from (intent, source, success) observations (a source that correlates with successful turns under an intent is up-weighted, clamped to [0.1, 3.0]), and the bus loads a fitted weights.json if one exists under $GHOST_HOME/system/rrf/. Absent → the hand-tuned defaults stand, byte-for-byte — the fusion weights sit on the hot path that feeds every turn, so an ungrounded fit must never silently degrade recall (same load-if-present posture as the PRM / router checkpoints). The _reciprocal_rank_fusion classmethod stays back-compatible (the learned matrix is an optional weight_overrides=). Covered by tests/test_rrf_weights.py.

Graph links and episodes are no longer auto-loaded 2026-10-10 §4NC

Operator decision ("Off in prompts, keep recall"), measured on 86 real owner requests.

  • The graph tier was 20% relevant and 16% harmful when loaded (about 53 tokens a turn). One image request's subject surfaced on 7 unrelated turns, and riddle details were stored as world facts.
  • The episodic tier was 15% relevant and 19% harmful (about 59 tokens a turn). A two-month-old "all systems green" greeting episode surfaced on 12 requests.
  • The switch: MemoryBus._fetch_graph and _fetch_episodic return nothing unless GHOST_BUS_GRAPH_TIER=1 / GHOST_BUS_EPISODIC_TIER=1. The switches are read per call, like GHOST_BUS_VECTOR_TIER, and the tier instrumentation shows them as "-".
  • Nothing is deleted: the stores are still written and stay searchable by recall, which does not go through these fetchers. The skill, session and profile tiers are unchanged.
  • The owner's facts are kept (r1 review). A first-person question about the owner ("where do I live?", §4KZ) still gets owner_facts_matching through MemoryBus._owner_facts; only the topical edges are off.

§4MJ (2026-10-08) — what each tier may inject

Measured by replaying 80 real owner requests through the real bus on a copy of the live stores: 12.8% of injected tokens were relevant and 8.6% misleading. Changes:

  • Episodes: a FAILED episode with no lesson is not hydrated (it rendered as the failed reply's own text — 2 of 87 relevant); recall still returns it. A mostly non-Latin query needs two shared content words with the episode's trigger, because the English embedder places any two Greek sentences ~0.1 apart. Stored tool-call/think markup is stripped from a rendered episode.
  • Graph: hydration seeds no fuzzy matches (get_neighborhood(..., fuzzy=False); 91 items, 0 relevant) and no generic hub words (project, sandbox, task, file …) — the project node holds every project's title, which put one project's chains into 16% of unrelated turns. The recall tool keeps the fuzzy tier.
  • Sessions: a message matches only where the query terms sit together — the hit is the 240-character window holding the most distinct terms, and the ≥2-term floor is counted inside it (two 5.9 KB replies used to match 23 of 80 unrelated requests and inject their opening).
  • Budget scales on the user's own words, not the expanded follow-up string.
  • Ranking-weight refit reads only usefulness rows written after the probe/member gates (RRF_OBSERVATIONS_CLEAN_SINCE, 2026-09-24 18:31): the earlier rows were 17% probe/member.
  • Public channel: an owner turn in a public channel is not written to the autobiography (episodes already refused it).
