UI layout

One full-width column over a full-window face since 2026-08-02 — not the left/right split it used to be. The face (the web UI's matrix_graph.js in a QWebEngineView; the three QPainter faces are gone) is the background of the whole window at explicit geometry, and every panel is glass floating on a translucent overlay above it.

  • Top row: workspace (◇/◆), face-form cycle (◈), fullscreen-face toggle (◐/○).
  • Middle: left_widget → the transcript, as real QLabel bubbles (operator right, agent left). This is the only item in the column with a stretch factor.
  • Bottom row: text input (with up/down history) sharing one row with camera snap, push-to-talk, TTS toggle and the stats readout.

Fullscreen face (◐ / F11)

Hides self.overlay — the entire glass sheet, leaving nothing but the face. Verified on-device against the real MainWindow: 9 of 9 controls visible normally, 0 of 9 while hidden, face still rendering.

Getting back. This is a frameless, always-on-top kiosk, so with the overlay hidden there is no visible control to restore it — losing the way back would be worse than the bug. Two independent paths, deliberately redundant:

  • F11 — an ApplicationShortcut, not the default WindowShortcut: with the overlay gone the QWebEngineView is all that is left to hold focus, and a window-scoped shortcut could be swallowed by it. The face is also NoFocus for the same reason.
  • Any other key — keyPressEvent restores the UI before its normal type-to-focus handling.

Escape / Alt+Escape / Ctrl+Escape never reach keyPressEvent (they are QShortcuts and fire first), so push-to-talk, TTS and SNAP keep working while the UI is hidden — face-only voice mode rather than a dead end.

Live turn status — what replaced "cogitating" (2026-08-03)

The waiting bubble used to read cogitating ··· for the whole 30–90 s a turn takes. It now carries the same caption the web UI shows under its waiting bubble — elapsed clock, a plain-English description of the current step, and that step's icon: 

0:34   reading a file · notes.md   📖
1:02   delegating to the worker node · verify → Worker Node (Nova)   🔧
1:19   thinking…   💭

The chat stream cannot supply this. /api/chat carries content tokens only — nothing about tools, memory or thinking — so the description comes from a SECOND channel, exactly as it does in the browser: the interface server tails the agent's pretty log and rebroadcasts every line over wss://eva:8080/ws?key=…, and the client turns those lines into captions. Same host, port and self-signed cert as the voice endpoints, so GHOST_VOICE_VERIFY_TLS applies here too; GHOST_LOG_WS overrides the whole URL. The key rides in the query string because the endpoint is gated the way the web UI is and WebSockets take no custom headers.

  • turnstatus.py (new file — remember it in deploy.sh) holds the caption logic and the socket reader. It is deliberately Qt-free, so unlike the rest of the client it is unit-tested for real: tests/test_clockwork_turnstatus.py.
  • Corridor filtering. Dreams, self-play and other clients stream over the same socket. The ticker adopts the id of the first request started corridor to open after the operator sends and ignores every line that does not carry it — otherwise the handheld narrates the agent's dreams while the operator waits on their own question. A corridor already open at send time can never be adopted.
  • Degradation is the design. The reader reconnects forever with exponential backoff and never raises; if the interface is down (or websockets is missing from ~/gui_env) the caption falls back to the old cogitating and chat — which talks to the agent directly on :8000 — is unaffected.
  • One line, always. The description is elided at 46 characters (caption_html). The web UI one-lines with white-space: nowrap + text-overflow: ellipsis; a QLabel has no equivalent, and a caption that wraps also changes the bubble's height every few seconds, which reads as the transcript twitching. The description is raw log text and is escaped — the bubble is in RichText mode, so an unescaped < from a tool's output swallows the rest of the line.
  • Repaints are gated on change. Every mutator returns whether the caption actually moved; each repaint re-measures and re-fits a QLabel, and the socket carries every line the agent logs. The clock ticks at 1 s (second granularity — 500 ms bought nothing but fits).
  • Hand-synced tables. ICON_CLASS / TICKER_VERBS / TICKER_NOISE are ports of the tables in interface/static/app.js. The device never sees app.js, so nothing at runtime can catch drift — the test parses both files and fails when they diverge. Change the JS and the Python together.

The face — the web UI's own, hosted in QWebEngineView (2026-08-02)

The three QPainter faces below were removed. The handheld now runs the same matrix_graph.js the browser does (webface.py + webface/), so it gets the thermal two-pole palette, all eight forms (abyssal · horizon · cortex · vortex · lattice · stack · embedding · descent), the immersion dive, pulses and error flinches — and future work on the web face lands here for free instead of the two drifting into forks. The ◈ chip now cycles forms rather than swapping renderers.

The face opens on the last form you chose (2026-08-03)

A ◈ press is remembered and applied at the next start. Precedence: GHOST_FACE_FORM (explicit, this run only) > the remembered form > facestate.FALLBACK_FORM = descent on a device that has never been cycled.

Why localStorage could not do this. matrix_graph.js already persists the choice and restores it at load, and on the handheld that mechanism can never work — for two independent reasons, either one fatal:
  • The client's QWebEngineView uses the default, off-the-record profile (there is no ~/.local/share/**/QtWebEngine directory on the device), so web storage dies with the process.
  • localStorage is keyed by origin, and the face is served from http://127.0.0.1:<free port> — a different port, so a different origin, every boot. Even a persistent profile would look the value up under a key it never wrote.
So the memory is one line of text in ~/.ghost_face_form, written by cycle_form and read by startup_form — facestate.py (new file; add it to deploy.sh), Qt-free and unit-tested in tests/test_clockwork_facestate.py. A corrupt, over-long or no-longer-existing form name is ignored rather than handed to setForm, which no-ops silently on an unknown name.

The startup choice is printed ([face] opening on 'lattice' (remembered='lattice') in /tmp/ghost_ui.log), because otherwise which form the face opened on is observable only by looking at the panel — no help over ssh, and none at all when the screen is asleep.

  • Why a browser and not a port: reimplementing ~2,700 lines of particle engine and GLSL in QPainter would have been a fork with a maintenance tail. QtWebEngine and WebGL 1.0 are both already available on the device, so hosting the original costs nothing to build and nothing to keep in sync.
  • Performance is purely fill-rate bound (measured on the CM4): 16 fps at 1280×720, 35.7 at 854×480, 50.9 at 640×360. Busy state + dive cost nothing extra. GHOST_FACE_ZOOM (default 2.0) shrinks the CSS viewport so the drawing buffer shrinks with it and the browser upscales — and at 640×329 the face also trips its own IS_MOBILE query (max-height: 600px), halving node count 250→120 and bloom scale. That mobile profile exists for exactly this class of GPU.
  • ES modules need HTTP — file:// silently refuses to execute the module (no console error at all), so webface.py serves the bundle from a loopback-bound thread. This is not optional.
  • QtWebEngineWidgets must be imported before QApplication exists, otherwise Qt refuses to construct the view ("must be imported … before a QCoreApplication instance is created") and the face degrades to a blank panel. Hence the module-level import in webface.py plus AA_ShareOpenGLContexts in client.py.
  • three.js r160 is vendored under webface/vendor/ (module + EffectComposer/RenderPass/UnrealBloomPass and their deps) so the device needs no CDN at runtime and the face works offline.
  • Measured CPU after the swap: the client process fell from 61% of a core to below the 3% reporting threshold; QtWebEngine holds ~41% for the rendering. Memory: client ~284 MB, webengine ~233 MB. This contradicts the claim in the legacy notes below that hidden QPainter faces cost zero CPU — on the deployed build they did not, and pausing their timers explicitly changed nothing (60.8% vs 61.0%). Only removing them recovered the core.

Glass UI restyle (2026-08-02)

The face moved from the right half to the background of the whole window, and every panel became tinted glass over it. Placement is unchanged — transcript and input left, chips top-right, status strip bottom-right — but nothing is opaque, so the thermal palette reads through the entire interface.

  • Widget-over-webview compositing works on this device, which is what makes the design possible at all — but only with the face as an explicitly-positioned child plus raise_() on a transparent overlay sheet (WA_TranslucentBackground). The window is a fixed-size frameless kiosk, so no resize handling is needed.
  • The cyan accent was dropped. The face's ring runs blue → violet → crimson with essentially no green channel, so #7be0ff sat outside that range and made chrome and face look like two different applications. The accent is now violet (#c9a6ff) lifted from the face's own mid-palette, with warm sand (#ffc08a) for user text against its crimson core.
  • Qt cannot do backdrop-blur, so readability comes from tint alone: the transcript carries a heavier fill (0.46) than chips and inputs (0.30), rather than the uniform low alpha the web UI can afford with real blur behind it.
  • The left/right split is gone (second pass, same day). Once the panels were transparent the split had no purpose — a nearly-invisible container was still reserving half the screen and still reading as two columns. The transcript container is now fully invisible (no fill, no border) and spans the full width; each message is its own glass bubble that places itself, operator right, agent left, exactly as the web UI does, capped at 54% width so the face stays visible down the middle (the web UI caps at 35% for the same reason — to clear the sphere). Input keeps its bottom-left position and the action chips keep bottom-right; they simply share one row now instead of living in separate columns.
  • Rounded bubbles + typography (third pass, same day). The QTextBrowser was replaced by chatlog.py — a QScrollArea of per-message QLabels — which gets true per-corner radii (notched on the speaker's corner, 16/4/16/16 like the web UI) and content hugging, so a one-word reply is a small pill instead of a half-width slab.
    The non-obvious part: a word-wrapped QLabel reports a SMALL sizeHint().width() regardless of maximumWidth, so any size policy that defers to the hint (Maximum, Preferred) leaves every bubble a narrow ribbon — and raising the cap changes nothing, because the cap was never the binding constraint. _Bubble.fit() measures the text unwrapped, then pins minimum == maximum width to min(natural, cap) so the layout has no choice.
    Typography: markdown arrives as bare <h2>/<p>/<ol> and Qt applies its own defaults — <h1> at ~2x base, <h2> at ~1.5x — so a briefing's headings came out enormous. QLabel offers no document-stylesheet hook, so style_markup() injects sizing inline per tag, with headings only slightly above body size (in a bubble a heading is a label, not a page title). Prose is now SANS (DejaVu/Liberation) at 20px; monospace is reserved for the operator's own messages, inline code and code blocks — mirroring the web UI, where only .message.user overrides to mono. Reading a briefing in 21px monospace was the bulk of "text doesn't look great".
  • Superseded: bubbles as TABLES (square). Qt's rich-text engine lays tables out reliably with per-cell width and background where aligned/floated divs stack unpredictably — but QTextDocument does not support border-radius at all. That is a hard engine limitation, not a styling oversight, so the bubbles use a 2px accent rail on the speaker's side instead of the web UI's notched corners. Rounded bubbles would require replacing the QTextBrowser with a QScrollArea of per-message QLabels.
  • Cost of the glass: translucent widgets must be re-blended as the webview repaints underneath, so the client process went from below the 3% reporting threshold to ~49%, with QtWebEngine at ~32% (load ~2.5 of 4 cores). That is the price of the look; turn GHOST_FACE_ZOOM up to claw it back if it ever feels sluggish.

Legacy: face/ — avatar package (REMOVED 2026-08-02, kept for context)

Three interchangeable faces share one public API (set_mood · pulse · feed_audio · startle · wake · set_state) and one mood system (moods.py: idle/listen/think/speak/error/sleep, palettes lerped over 0.45 s transitions). The default is NetworkFaceWidget; the ◈ toolbar chip cycles to FluidFaceWidget (smoke oracle) and NeuralFaceWidget (iris eye).

  • NetworkFaceWidget (2026-07-12 "tamed" rework) — sparse MoE diagram: 42 nodes / 72 edges (was 111/276), 4 experts, one expert per pulse. A wavefront takes ~1.8 s to cross; activations decay fast enough that a thought visibly passes instead of lighting the whole net. Expert hues are the dark-jewel family: deep violet, crimson, dark blue, dark green. No bloom pass, no offscreen buffer, no wavefront bands, no status readout.
  • Mood palettes follow the same family as the web UI dark theme: idle/listen indigo-blue, think deep purple, speak dark green, error crimson.

Performance model (CM4, software raster — the lessons)

  • All three faces exist in a QStackedWidget, but animation timers are gated by showEvent/hideEvent — a hidden face costs zero CPU. (Previously all three simulated at 30 fps forever: the client pinned a core at ~113%.)
  • Full-screen software ops are the budget: nebula composite, wireframe skeleton, and vignette+scanlines are all cached pixmaps, re-rendered only when their inputs actually change (nebula scroll ~3 s, wireframe 200 ms, vignette per-resize). Grain is the only per-frame overlay blit.
  • Per-node QRadialGradient halos were replaced by flat translucent discs; active edges get one Bézier stroke, not glow+core, and are skipped below the skeleton's own brightness.
  • Adaptive frame rate: 20 fps active moods, 15 fps idle, 10 fps sleep.
  • Measured on-device: client steady-state ~20% of one core idle (was 113%), think ~60% during generation.

External dependencies

  • PyQt6 + qasync + PyOpenGL.
  • httpx, OpenCV (cv2), markdown, subprocess (arecord/aplay).

Voice — repointed 2026-08-02

STT/TTS used to target http://192.168.0.24:8000, a Raspberry-Pi voice server (faster-whisper + Kokoro) that no longer exists — so voice on this device had been failing silently against a dead LAN host, which is why it looked "unused". Both now use the interface's local endpoints (see Voice loop): STT = ffmpeg + the Gemma 4 audio node, TTS = the macOS synthesiser in Ava (Premium) since 2026-08-03. The device inherits the voice change for free — it only ever posts text to /api/tts and plays the WAV it gets back, so nothing on the uConsole needed touching.

Two differences from the old Pi server, both load-bearing:

  • The endpoints live on the interface (port 8080, TLS), not the agent (port 8000, plain HTTP) that chat uses — hence https and a different port. GHOST_VOICE_BASE / GHOST_HOST override the default https://eva:8080.
  • They require X-Ghost-Key, like /api/chat already did. The interface serves a self-signed cert, so TLS verification is off by default (GHOST_VOICE_VERIFY_TLS=1 to enable) — the hop is inside the tailnet, which is already WireGuard-authenticated, and carries the same key the chat calls send in clear to :8000.

Verified on-device 2026-08-02 (host clockworkpi, aarch64): eva resolves via MagicDNS to the tailnet IP; a real-speech clip posted from the device transcribed correctly; TTS returned audio/wav and aplay -q - played it (exit 0); the default arecord capture device (a USB Logitech BRIO on card 3) records real audio, so no -D flag is needed. STT errors now surface the server's own message instead of a bare status code — "HTTP 503" alone sent one diagnosis down entirely the wrong path.

Two traps found while deploying on 2026-08-03, both of which looked like broken builds:
  • A hand-started client survives every deploy. deploy.sh used to pkill -f 'bin/client.py', which does not match python3 client.py (launched from ~/bin by hand). One such instance ran alongside five successive deploys. Two clients is not cosmetic: they compete for the CM4's single GPU, the newer face never gets a WebGL context, and grim screencopy starts failing. The pattern is now 'client\.py' and the deploy reports the client COUNT.
  • A powered-off panel stalls the face. swayidle -w timeout 600 wlopm --off '*' blanks the screen after 10 minutes idle; while the output is off, grim fails with "failed to copy output DSI-1" and the webview never finishes WebGL init, so no [face] line appears and the remembered form is never applied. wlopm reports the truth (DSI-1 off) where wlr-randr still says Enabled: yes; wlopm --on '*' wakes it and the face comes up immediately.
Deploy note: the LIVE client on the device is ~/bin/client.py (launched by ~/bin/launch_ghost.sh, which sources the ~/gui_env venv and sets QT_QPA_PLATFORM=xcb) — not ~/clockwork_ghost/. Deploy with scp to ~/bin/client.py, keeping a timestamped backup, and restart with setsid env DISPLAY=:0 XAUTHORITY=~/.Xauthority ~/bin/launch_ghost.sh. Always diff the device copy against the repo copy first — device-deployed externals can drift. The API key lives at ~/.ghost_api_key (mode 600).
