Streaming model

  • Per-task state dict keyed by UUID in global active_chat_tasks.
  • Background worker spawned on POST /api/chat with stream=true, sharing a pooled httpx.AsyncClient.
  • The worker reads upstream chunks and appends bytes to task["buffer"]; an asyncio.Event signals new data.
  • The stream generator yields by chunk index (not byte index) and clears the event before draining to avoid races.
  • Truncation is detected via task["truncated"] and surfaces as an SSE error marker.
  • Resume endpoint accepts an offset for reconnection.
  • A janitor task evicts done tasks past 10-min TTL or hard cap of 200.

Request timeouts

Chat proxying to the agent backend uses a split httpx.Timeout built by _chat_timeout(), applied to the shared pooled client, the streaming client.stream() call, and the non-streaming client.post() call.

  • Read / write / pool: CHAT_TIMEOUT_S (env GHOST_CHAT_TIMEOUT, default 1800s / 30 min). This is the ceiling that matters for long turns. httpx's read timeout is the max gap between received bytes, not total wall-clock — a long agent turn (deep browser automation, many sequential tool calls) can run for minutes without flushing any SSE bytes. The old flat timeout=600.0 fired the read timeout at 600s, aborted the stream, and the UI rendered a bare "No response" because no assistant tokens had arrived yet. Raising this prevents that premature cut.
  • Connect: CHAT_CONNECT_TIMEOUT_S (env GHOST_CHAT_CONNECT_TIMEOUT, default 10s). Kept short and separate so a genuinely down backend still fails fast instead of hanging for the full read window.
  • The browser front-end (app.js) imposes no timeout of its own — it streams via fetch until the reader reports done, and only aborts on explicit user action (stop button). The server-side ceiling above is therefore the effective limit.

Buffer & payload limits

  • Per-task stream buffer cap 50 MB (GHOST_INTERFACE_STREAM_CAP).
  • Global stream buffer ceiling 200 MB across all chat tasks (GHOST_INTERFACE_TOTAL_STREAM_CAP) — the per-task cap alone still allowed hard-cap × 50 MB ≈ 10 GB worst-case. On overflow the worker first reclaims the oldest done tasks' resume buffers (_reclaim_buffered_bytes) — otherwise a few large completed turns would brown-out every new stream for up to the 10-min TTL — and only truncates (same BufferCapExceeded marker, message says which cap fired) if live streams alone exceed the ceiling. A resume of a reclaimed stream 404s.
  • Request body: max 500 chat messages.
  • Body sizes are enforced at the ASGI layer by BodySizeLimitMiddleware BEFORE parsing: upload routes (upload, workspace/load, stt) get MAX_UPLOAD_BYTES (100 MB, plus 1 MB multipart-envelope slack), every other POST body is JSON and gets MAX_JSON_BYTES (env GHOST_INTERFACE_MAX_JSON_BYTES, default 10 MB). Oversized declared Content-Length → immediate 413; chunked bodies with no declared length are counted as they arrive and aborted on overflow. This matters because FastAPI parses the entire multipart body (spooling to disk) before a handler runs, and request.json() slurps the whole body into RAM — a handler-level check alone fires only after the bytes were already received.
  • Upload body backstop: 100 MB per-file cap via _read_capped_upload(); 64 KB chunks; rejects non-bytes.

Document caching

The root GET / reads index.html from disk on every request (so front-end edits need no server restart) and serves it with Cache-Control: no-cache, must-revalidate, private. Static assets are cache-busted via a ?v= query (e.g. style.css?v=2.7); without no-cache on the document, a browser holding a cached copy of the HTML would keep referencing the old ?v= and never fetch updated CSS/JS until a manual hard refresh. private stops shared proxies caching the document, which carries the injected GHOST_API_KEY. Guarded by tests/test_interface_index_no_cache.py. Note: bumping the ?v= on changed assets in index.html is still required for those assets themselves.

Log streaming

A log_streamer() task spawns tail -f on the agent log and broadcasts to connected websockets. Detects ERROR/Exception and tags is_error for client reactivity. Lines decode with errors="replace" (binary garbage in the log must never kill the loop), and the tail subprocess is reaped with timeout-then-kill in a finally — i.e. on every exit path, not just cancellation. Broadcast is concurrent with a per-send timeout (GHOST_WS_SEND_TIMEOUT, default 2 s): a stalled client is evicted and closed instead of back-pressuring the whole broadcast (and, transitively, the tail pipe) for everyone else.

Auth

  • GHOST_API_KEY mandatory; the module fails to import without it.
  • All state-mutating endpoints depend on verify_interface_key() which compares X-Ghost-Key.
  • The page itself is gated by a query parameter check (browsers send keys in URL on first load only).
  • CORS: allow_origins=*, allow_credentials=False.
  • Key provenance (2026-07-13 rotation): the prod key comes from the canonical mode-600 secret file ~/Data/AI/.ghost_api_key, exported by bin/start-ghost-client.sh — this deliberately OVERRIDES the stale GHOST_API_KEY=ghost-secret-123 still present in /Library/LaunchDaemons/com.local.ghost-client.plist (plist edit needs sudo; the old public key no longer works anywhere). The same value is the AGENT's key (agent auth enabled the same day), which is why the baked upstream X-Ghost-Key keeps working. Bookmarks using ?key=ghost-secret-123 must be re-saved with the new key.

Concurrency

  • asyncio throughout; one shared httpx.AsyncClient pool.
  • FastAPI Depends(verify_interface_key) for auth.
  • StreamingResponse with custom generator for back-pressure.
  • Background tasks for upstream polling + log streaming.

Chat area layout

The #ui-layer is a full-height flex column: header (flex-shrink:0), main#chat-container (flex-grow:1), then the input footer. The dominant cause of "the top third isn't showing chats" was the header height, not the chat area: #header-controls stacked its 5 icon buttons in a flex-direction:column, making the non-shrinking header ~300px tall and reserving the top third (its transparent gradient background made that band look like empty sphere backdrop with floating buttons). Visualizer iframes & sandboxing

The floating "VISUALIZER" window uses two iframes. #render-iframe (sandbox="allow-scripts allow-same-origin") is used only to display our own blob previews — images and PDFs — which need the parent to write into contentDocument. Untrusted agent-authored HTML/CSS/JS from "Visualize" buttons goes into a separate #render-iframe-sandboxed (sandbox="allow-scripts", no allow-same-origin) via srcdoc, so it runs in an opaque origin and cannot reach window.parent or read the injected GHOST_API_KEY. Mixing allow-scripts + allow-same-origin on a single iframe rendering agent code would let it escape the sandbox and exfiltrate the key.

Agent reasoning (<think>…</think>) and <tool_call> blocks are stripped from the displayed transcript (via _stripInternalTags) so the visible chat matches what the TTS engine speaks.

Inline media handling for /api/download/…

A MutationObserver in app.js watches #chat-log for tool-emitted artefact links. Two cases:

  • Images (<img src="/api/download/gen_*.png">): the unauthed <img> load 401s because browsers don't attach custom headers to plain image loads. _handleChatImage fetches through the authed wrapper, caches a blob URL in an LRU (cap 100), and swaps img.src to the blob. Failed fetches surface a "broken image" badge.
  • PDF reports (<a href="/api/download/report_*.pdf">): _handleChatPdfLink decorates the anchor with the .pdf-link card style, intercepts the click, fetches the bytes through the same authed wrapper / blob cache, opens the blob in the right-rail visualizer iframe (browsers render application/pdf blobs natively), and simultaneously triggers a real download via a hidden <a download>.

Both code paths share _toAuthedBlobUrl and the same blob cache, so an artefact opened once doesn't refetch. Because a MutationObserver only reports future mutations, the same processing (_processChatLogArtifacts) is also run once on startup against the chat history restored from localStorage, so restored images/PDF links get the authed-blob treatment instead of 401-ing. Auto-opening the visualizer is suppressed while history is being restored (live replies still auto-open).

2026-07-27 audit fixes

  • Upstream chat failures were recorded but never emitted (MED, closed). background_stream_worker stored the exception in task["error"] and set done, but stream_generator surfaced only truncated — so when the agent on :8000 was down or returned 4xx/5xx the browser received HTTP 200 with a zero-event SSE stream and rendered a bare "No response" with no diagnostic. Both the live stream and /api/chat/resume/{id} now emit an event: error frame shaped like the existing buffer-cap marker, and resume replays the terminal truncation/error status too.
  • An empty GHOST_API_KEY booted into a silent all-401 outage (MED, closed). The import guard only checked that the variable exists, so a whitespace-only key file (rotation mishap) produced "" — which passes the presence check but can never match under compare_digest, making every route including / return 401 while launchd's KeepAlive kept the dead service "up". The agent, meanwhile, treats an empty key as auth-OFF, so the two diverged. An empty key now raises at import.
  • stream_generator null-checks its task: the janitor's hard-cap path can cancel and pop a live task before the generator's first iteration, which previously raised TypeError and aborted the stream instead of yielding the intended error marker.

2026-07-28 review fixes

Regression-guarded by tests/test_interface_review_fixes.py.

  • Non-UTF-8 log line leaked a tail process every 5 s (HIGH, closed). line.decode('utf-8') raised UnicodeDecodeError out of the read loop, but subprocess cleanup lived only in the CancelledError handler — the restart wrapper then spawned a fresh tail while the old one lived on, and because tail -n 10 -F re-reads the last 10 lines on every respawn, a poison line re-triggered the leak every cycle. Now errors="replace" + cleanup in a finally.
  • Body caps didn't protect what their comments claimed (HIGH, closed). See Buffer & payload limits: enforcement moved to BodySizeLimitMiddleware at the ASGI layer; JSON routes got their own MAX_JSON_BYTES cap (previously request.json() was unbounded — message count was capped but one giant string sailed through).
  • Download proxy rebuilt the upstream URL without quoting (MED, closed). The :path param arrives decoded; a filename containing ?, # or % changed the upstream request's meaning. Now urllib.parse.quote(filename) (with safe="/" so subdirectories still work).
  • Malformed JSON surfaced as 502, not 400 (MED, closed). A garbage body raised out of request.json() into the generic handler and came back as a 502 "upstream error", sending client retry loops chasing an unfixable request. _parse_json_body() maps it to 400 on chat/tts/workspace-save, rendered via a dedicated _JSONBodyError handler in the interface's standard {"error": ...} shape (FastAPI's default {"detail": ...} is invisible to app.js, which only reads .error).
  • One stalled websocket froze log broadcast for everyone (MED, closed). Serial await ws.send_text() never raises on TCP backpressure, it just never returns — freezing the loop and, once the 64 KB tail pipe filled, the whole stream. Sends are now concurrent with a bounded per-send timeout; offenders are evicted + closed.
  • Startup tasks were created without strong references (MED, closed). The event loop keeps only weak refs to tasks, so the unreferenced create_task() results for the log streamer and janitor could be GC'd mid-run. Startup/shutdown also migrated from the deprecated @app.on_event to a lifespan context that holds refs in _BACKGROUND_TASKS and cancels them (plus closes the shared httpx client) on shutdown.
  • Janitor TTL never expired an unstamped done task (LOW, closed). t.get("finished_at") or now recomputed the fallback every sweep without storing it, resetting the TTL clock each minute; now setdefault. The cancel endpoint also stamps finished_at and sets new_data_event itself, so parked readers wake immediately instead of waiting for the cancelled worker's finally (which never runs at all if the worker was cancelled before its first step). Sweep logic extracted to _sweep_active_chat_tasks(now) for testability.
  • Improvements in the same pass: all proxies (workspace save/load, upload, download, stt, tts) now ride the shared pooled client with per-request timeouts instead of building a fresh AsyncClient each call; the three inline SSE error frames were unified into _sse_error_frame(); upstream chat 4xx/5xx now includes a body snippet in the error frame (was just the bare status line), bounded in both size (~512 B) and wall-clock (UPSTREAM_ERROR_SNIPPET_TIMEOUT_S, 5 s — httpx's read timeout is per-gap, so a drip-feeding failed upstream could otherwise park the worker); tts passes through the Pi's actual content-type instead of hardcoding audio/wav; /ws evicts its socket in a finally (any exit path, not just clean disconnect).
