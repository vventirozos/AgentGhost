Running it

When something breaks

Sorted by what you'd notice, not by which component is at fault.

Check these two things first

Most confusing behaviour resolves into one of two states, and both are visible from one request:

curl -s -H "X-Ghost-Key: $GHOST_API_KEY" \
     http://127.0.0.1:8000/api/health | python -m json.tool
memory_system_loaded
false means Ghost booted degraded: HTTP answers normally, but there's no memory and every background pass is silently disabled. It will chat with you and remember nothing.
biological_watchdog_alive
false means the background loop — the idle scheduler — died (the key keeps its old name). Ghost still answers, but it has stopped its idle work: the memory journal, maintenance, store hygiene and the workspace tidy. The web status chip shows idle scheduler DEAD; at boot a healthy one logs Idle Scheduler — started; jobs: …. Nothing will tell you this — it just goes quiet.

Beyond the two fields: the live verification harnesses

Health says something is serving. Three scripts under scripts/ ask whether the parts work, against the running agent (all read the key from ~/Data/AI/.ghost_api_key, all send their LLM turns as diagnostics that never teach, except the selfhood one, which tests the recording path itself):

  • functional_live_test.py — API, auth, malformed input, sessions, workspace save, then three live turns (--core skips the turns).
  • tool_probes_live.py — one bounded "reply with only X" prompt per tool family, checked mechanically, with the tool that actually ran read back from the log.
  • selfhood_functional_test.py — capture, tool-using turn, narrative, stress, unity (the section that drove the removed self_state tool is gone). Section G corrupts the live state.json and needs --corrupt-live-state.

For the idle loops, scripts/learning_health.py (or introspect action='learning') is the liveness screen: every registered phase, what its zero means, and a ✗ DEAD only for a periodic loop whose heartbeat has not declined recently.

The judgment systems — the verifier, the claim binder, escalation — used to be scored against known truth by the night oracle benches (night_bench_round.py, verify_bench*.py, if_bench.py); those scripts and the bench banks were deleted on 2026-10-11 (§4NM). The owner's regression suite, which replaced them as the standing check from 2026-10-10, was removed on 2026-11-05 (§4SZ): it held no kept test. No standing automatic check of the judgment systems runs now; the failure census (scripts/failure_census.py) and its hand-graded sample are the measurement.

It won't start

"REFUSING TO START … no API key configured"

You bound to something other than localhost without deciding about authentication. Either set GHOST_API_KEY, or pass --api-key '' to knowingly turn auth off on a trusted network, or bind to 127.0.0.1.

It aborts complaining about Tor

Mandatory Tor is on by default and Ghost probes it at boot. Check the daemon is running and listening:

curl --socks5-hostname 127.0.0.1:9050 -s https://check.torproject.org | grep -o "Congratulations"

If Tor is fine but Ghost still refuses, check TOR_PROXY points at the right port.

The boot probe is only a TCP connect to the SOCKS port — it does not wait for a bootstrapped circuit. So "the port answers" is the whole gate, and Tor being slow to bootstrap is never the cause of this abort. Tor being absent is.

Nothing came back after a reboot

Almost always dependency ordering rather than Ghost itself. Ghost boots fail-closed on Tor, so if Tor is not up yet Ghost aborts — and under KeepAlive that abort becomes a respawn loop that re-pays the full model-loading startup on every iteration. The giveaway is a service that reports as running while never holding a port:

sudo launchctl print system/com.local.ghost-agent | grep -E "state|last exit"
#   state = spawn scheduled      <-- looping, not stopped
#   last exit code = 3

Two things make this survivable, and both are worth checking if you are setting up a new host:

  • Run every dependency as a system daemon, not a login agent. A LaunchAgent starts at login. If Ghost is a system daemon and Tor is a login agent, a headless reboot leaves Ghost looping until somebody physically logs in.
  • Wait for dependencies in the launcher, don't race them. launchd starts jobs concurrently, so "Tor also autostarts" is not by itself enough. start-ghost-agent.sh waits for port 9050 (bounded — after the timeout it proceeds and lets the fail-closed abort speak, rather than hanging silently forever).

A second Tor keeps appearing, or Tor rotation reports success but nothing changes

If Tor is supervised by your own service definition rather than by Homebrew's, be careful with anything that "restarts Tor" by calling brew services restart tor. Homebrew owns its own label, so that call installs and starts a second Tor job — which cannot bind port 9050 because the real one already has it, and sits in error state forever. The Tor that is actually serving is never restarted.

Ghost's request_new_tor_identity() hit exactly this. It now restarts the supervising launchd job instead, and returns a truthful failure when it cannot (restarting a system daemon needs root, and Ghost runs unprivileged) rather than reporting a renewal that did not happen. Nothing is lost: exit-node rotation runs on per-circuit SOCKS isolation, which needs neither Tor's control port nor a daemon restart.

Check for a stray rival job with:

ls ~/Library/LaunchAgents/ /Library/LaunchDaemons/ | grep -i tor
lsof -nP -iTCP:9050 -sTCP:LISTEN

PostgreSQL won't start after an unclean shutdown

If the log repeats FATAL: lock file "postmaster.pid" already exists naming a PID that is alive, check what that PID actually is:

ps -p <pid> -o comm=

Across a reboot the kernel reuses PID numbers, so the PID in a leftover lock file frequently belongs to some unrelated process. PostgreSQL can see the PID is alive but not that it belongs to something else, so it refuses forever — this does not heal on its own, and under KeepAlive it retries every few seconds indefinitely. Remove the lock file only once you have confirmed the PID is not a postmaster; if it is one, you have a real second instance and deleting the lock would be actively harmful.

Docker/OrbStack: the app is running but the sandbox still fails

On macOS the OrbStack app and the OrbStack engine are separate. The app can be up and idle in the background while the VM has not been spawned, and the app only starts it on demand — so seeing OrbStack in Activity Monitor tells you nothing about whether Docker works. Ask the engine directly:

orb status          # "Running" is the answer that matters
docker info --format '{{.ServerVersion}}'

This is also the one dependency that cannot be made to start before login, because it is a GUI VM manager. On a headless reboot the sandbox tools stay unavailable until somebody logs in; everything else is a system daemon and comes back on its own.

"Sandbox manager not initialized" from execute/browser (2026-08-26): this means boot-time sandbox construction failed — classically the agent daemon won the race against OrbStack's docker socket by a few seconds after a reboot (the log shows one sandbox failed — Error while fetching server API version line at boot). Since 2026-08-26 the agent recovers on its own: the next execute/browser call after docker comes back rebuilds the manager (backoff-gated, ~60 s) and logs Sandbox Recovered — see sandbox → Lazy re-init. If the error persists for minutes while docker info answers, that self-heal is what broke; before that date the only fix was restarting the agent.

First-ever boot hangs or fails loading the embedder

This one catches everybody. On a fresh install the embedding model hasn't been downloaded yet, and the Tor egress guard blocks that download because it's a direct connection to a public host. Boot once with --no-mandatory-tor to let it cache, then run normally from then on.

It refuses to start and mentions re-embedding

The embedding model doesn't match the one that built your vector store. Both models produce vectors of the same size, so nothing would crash — the stored vectors would simply stop meaning anything and retrieval would return plausible-looking garbage. Ghost refuses instead.

Either put GHOST_EMBED_MODEL back to what it was, or migrate deliberately:

PYTHONPATH=src python scripts/reembed_memory.py

Port already in use

Usually a previous instance that didn't shut down. If you run it under launchd with KeepAlive, remember that a plain kill restarts it — you need launchctl bootout to actually stop it.

It started but acts like it has amnesia

It knows nothing about you at all

Almost always GHOST_HOME. If it isn't set, Ghost uses ~/ghost_llamacpp — so an agent started from a shell where you'd exported it and one started by a service manager where you hadn't are two different agents with two different memories.

Under launchd or systemd this is the default outcome, because a service doesn't inherit your shell profile. Set it inside the service definition. Confirm which path is live:

ps -o command= -p $(pgrep -f ghost_agent.main | head -1)

It forgot one specific thing

Two very different causes with opposite fixes. Ask it to search for the fact directly. If it can find it on request, the fact is stored fine and the retrieval ranking didn't surface it — that's a ranking problem, not a lost memory. If it can't find it at all, it was never stored.

Things mentioned in the last couple of minutes may genuinely not be searchable yet; the queue that files them drains after about two minutes of quiet. More on memory →

It keeps repeating something wrong about you

That entry is in your profile, which is injected into every conversation rather than searched. Correct it directly ("my wife is Maria, not Anna") or use the memory-correction control in the web UI.

Tools don't work

Anything involving code or files fails

Check Docker is running. Ghost needs the daemon up; without it, execute, browser and the file tools all fail. The very first container start also pulls a base image, so it's slow once and fast afterwards.

"It can't reach my app on localhost:3000"

Correct — and not a bug. The sandbox has its own network namespace, so its 127.0.0.1 is not yours. Ghost cannot see services you run on your machine, and cannot stop or restart your processes. If you need it to test a local app, have Ghost start that app itself inside the sandbox.

It says the app is running, but the link won't open

The app is probably listening only on the sandbox's own loopback address. Ghost publishes a small range of sandbox ports to your machine, but a published port only reaches an app that listens on all interfaces. Many development servers — Flask's app.run() is the usual one — listen on 127.0.0.1 unless told otherwise, and inside the sandbox that address is the sandbox's, not yours. Everything Ghost checks from inside the sandbox still works, so from there the app looks healthy.

Ghost looks at the address the app actually bound and says so in the service report: the fix is for the app to bind 0.0.0.0 (the HOST and PORT variables are set for it) and to be restarted. If the report instead says the port is not published, ask for the service to be stopped and started again on one of the published ports — a restart keeps the port it had.

Web search returns nothing, repeatedly

Often search operators. The scraper backends Ghost reaches over Tor don't support site:, quoted phrases, or AND/OR, so Ghost removes them before searching and keeps the words. When a site: filter is dropped this way the agent is told so in the search result, along with the query that actually ran — a site: search is not a restriction to that site. To aim at a site, name it as an ordinary keyword. Plain keywords work best.

For dark-web search specifically, zero results is normal. Onion search engines are unreliable and reachability varies by exit node; an empty result is not a reason to retry the same query.

It won't do something, and explains why instead

If the model declines rather than the tool failing, that's model alignment, not a bug. Ghost is developed against uncensored models; a standard aligned one will refuse operations that are routine for an agent on your own machine — wiping its sandbox, deleting files on request, searching Tor hidden services, handling security material.

Tell them apart in the log: a broken tool logs a failure with its own icon, while a refusal shows the model reasoning (💭) and then a normal ✅ turn outcome with no tool line at all. The second one means nothing ran. The same applied to the verifier's LLM judge while it was on — an aligned judge can refuse a sound answer on subject matter alone, which surfaced as retries you couldn't otherwise explain.

A tool that used to work now refuses to run

The pre-flight guard is doing its job. When the same tool fails the same way on the same target repeatedly, Ghost stops re-running it and hands the model the previous error instead. Fix the underlying cause and it'll clear.

It's slow

Every answer is slow

Your model has one inference slot, and Ghost competes with itself for it: conversation compaction, background fact extraction and classification are all model calls. Moving them to a second machine with --worker-nodes is the highest-value change available — see Settings that matter. (The self-check used to be the biggest of these calls; its LLM judge is off since §4OW, 2026-10-14, and the checks that remain are mechanical.)

Finding out what a turn actually cost

Every turn now records its real token cost, summed across each model call it made — the tool rounds and any work sent to a worker node. It lands in the turn's trajectory record and on the reply itself:

curl -s -X POST http://127.0.0.1:8000/api/chat \
  -H "X-Ghost-Key: $GHOST_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"'"$GHOST_MODEL"'","messages":[{"role":"user","content":"hello"}],"stream":false}' \
  | python -c "import sys,json; print(json.load(sys.stdin).get('usage'))"

The interesting field is cached_tokens. Ghost sends a large system prompt on every call and relies on the server's prefill cache to avoid re-processing it. If cached_tokens is near prompt_tokens, the cache is working and most of that prompt costs nothing. If it's near zero, you're re-prefilling the whole prompt every round — which is the difference between a fast turn and a slow one, and it's usually caused by something changing early in the prompt between calls.

ghost_llm_calls tells you how many model calls the turn took. A simple question that made eight calls is doing more work than you asked for.

One turn takes forever

Watch the log panel in the web UI. A turn can use up to 40 passes through the tool loop, and something like deep research legitimately takes minutes because every page is fetched over Tor. If it's stuck on the same tool repeatedly with the same result, that's a loop and Ghost's own guards should break it after three identical attempts.

A configured node stopped being used

Look at node_health on the health endpoint. A node that keeps failing gets its circuit breaker opened and is taken out of rotation. The most common cause is an address that moved — point node flags at tailnet addresses or stable hostnames, not DHCP-assigned LAN IPs.

The answers are wrong

It claims it did something it didn't

The self-check catches only part of this, mechanically: a file the reply says it wrote that is not on disk, a page it built that throws on load, a reply that narrates instead of answering, a picture that does not show what the reply says. When the file, page or reply check fails within about 15 seconds, the reply gets one repair round before it is sent; otherwise the failure is recorded with the turn, and you are generally not shown a correction. Other false claims are not checked: the LLM judge that read answers against the evidence is off since §4OW (2026-10-14). Correct it, or give it a 👎.

If the mechanical checks seem not to run at all, confirm they are on: --no-verifier disables them.

It answers a different question than the one asked

Tell it. A correction marks the previous turn as failed, and that label is kept with the turn. A correction needs a recognisable correction phrase and real overlap with your previous message, so "no, I asked for the file paths, not the counts" registers where a fresh unrelated question doesn't. The label does not change later answers by itself (the loop that replayed failed turns and proposed a rule was removed on 2026-11-05). If the same mistake keeps coming back, state a rule: "learn this rule: …" puts your sentence into every prompt of yours (Owner rules).

It got worse after learning something

Only rules you stated change its behaviour now. Say "show my rules", then "forget rule N" and "confirm forget rule N" for the one that hurts. Owner rules →

"Your rules file … so I left it exactly as it is"

The rules file, $GHOST_HOME/system/owner_rules.json, is damaged or cannot be read. Ghost does not rename, replace or rewrite it. Until it reads again, no rule is in your prompts and every rule command answers with this line, which names what is wrong (for example "is not readable JSON", "holds two rules numbered 3", or "holds more than 10 rules" after an edit by hand). A directory in the file's place counts as damage too ("cannot be read (IsADirectoryError)"). So does a key written twice in the file ("is not readable JSON"), and a row with a blank rule text or a rule number above 999,999 ("holds a row that is not a rule"). The health check's Learning line says owner rules file DAMAGED (…). Repair the file, or remove it to start with no rules. A damaged rules file →

"I could not write your rules file … so nothing was changed"

The rules file reads fine, but Ghost could not save a change to it. The line names the error, for example PermissionError (the system folder is read-only) or OSError (the disk is full). The rules you had are intact and nothing was added or removed. Fix the folder or free space, then send the command again. When the file cannot be written →

"delete rule 3" or "add rule: …" did nothing

Those are not commands. Only the exact messages change a rule: "learn this rule: …", "forget rule N" then "confirm forget rule N", and "forget all my rules" then "confirm forget all my rules". A short message about your rules that is none of these ("delete rule 3", "add rule: …", "new rule: …", "erase rule 2", "reset my rules") goes to the model, which is told that nothing was changed and which message to send. To change a rule, say "show my rules" to see its number, send the new one with "learn this rule: …" on one line, then "forget rule N" and "confirm forget rule N" for the old one (with ten rules, forget first). A message in Greek, or one longer than 20 words, reaches the model without that note, unless it starts with "learn this rule". The rules block itself always ends with a line saying the model cannot change a rule and must name the messages to send, which makes a reply with the commands likely for a long "edit this rule, …", though a prompt line cannot guarantee it. The old commands of the replay loop ("learn rule N", "dismiss rule N", "show me all proposed rules") are in the same group: they do nothing. The commands →

"show all rules" did not list my rules

The list command needs "my": "show my rules" (also "list my rules", "show all my rules"). "show all rules" and "list all rules" stopped being commands on 2026-11-05 (review r3), because that is also what one says about a firewall or a linter. They go to the model, which is told to answer with the message to send.

"learn this rule …" was not stored

A dictated rule needs a colon after "this rule" (not a comma, a full stop or a dash), has to be one line, the message may not open with a quote mark, and the rule may not hold a question mark anywhere (or end with ";"). A rule that quotes a question, such as "when I ask 'what's new?' give five headlines", is not taken: write it without the question mark. Otherwise the message goes to the model, which is told that nothing was stored. Send the rule alone: "learn this rule: answer in English". The four conditions →

A rule holds more than I meant

One line that states a rule and also asks for something else ("learn this rule: answer in English, and now tell me the weather") is stored whole, and the second request is not answered. The reply quotes what was stored. Say "forget rule N", then "confirm forget rule N", and dictate the rule alone.

I said "yes" and the rule is still there

A forget is confirmed only by the exact message Ghost asks for: "confirm forget rule N" (or "confirm forget all my rules"), within 15 minutes. A bare "yes" or "ok" removes nothing, because it may be answering something else; while the preview is still waiting, the model is told that nothing was removed and to answer with the message to send. A bare "yes" confirms nothing →

Reading the log

The log is the primary debugging tool here, and it's built to be read by a person rather than parsed by one. Almost every question on this page is answered faster by looking at it than by guessing.

There are two of them, and they're for different jobs

The live stream
What the agent prints as it works — boxed per request, colour-coded, one icon per subsystem. This is for watching. The web UI shows it in a panel beside the conversation, which is the easiest way to see it. If you run Ghost under a service manager, that manager captures it (with launchd, whatever you set as StandardOutPath).
The durable file
$GHOST_HOME/system/ghost-agent.log. Same events, one line each, timestamped and with a log level. This is for grepping — after the fact, when you know roughly what you're looking for.

What one request looks like

A request is framed top and bottom, so you can always see where one ends and the next begins. This is a real turn from 2026-08-04 — asking for the weather, which makes the agent call a tool. In that turn the useful reading is the timing: 7.8 seconds of thinking before the tool call, the tool itself returning in 10 milliseconds, and then 14 seconds waiting on the verifier's judge (off today). If this felt slow, the model was the cost — not the weather lookup.

A warning, and why they're worth reading

Warnings are deliberately rare, so when one appears it usually says something real. This one is from the same session, from the LLM judge that is off today (§4OW) — you will not see this exact line in production:

│  48  🔶  +37.1s  agent               Verifier escalation OVERTURNED a cheap-judge refute:
                                       main model says CONFIRMED. Original issues:
                                       Memory usage is 90.7%, not 91%.
│  48  🧪  +37.1s  verifier            CONFIRMED (95%) — All suspects are false alarms; claim…

Read that as: the cheap judge rejected the answer for rounding 90.7% to 91%, the main model was asked to re-examine, and it overruled the rejection. Nothing was broken — but lines like this showed the cheap judge was too strict. Measured on real turns, 9 of 17 of its refutes were false, which is why it was switched off.

Grepping the durable file

The file has one line per event, so ordinary tools work:

# everything from one request
grep 1165839c "$GHOST_HOME/system/ghost-agent.log"

# just the warnings and errors
grep -E "WARNING|ERROR" "$GHOST_HOME/system/ghost-agent.log" | tail -40

# how did recent turns end?
grep "turn outcome" "$GHOST_HOME/system/ghost-agent.log" | tail -20

# did the background loop do anything last night?
grep "\[SYSTEM\]" "$GHOST_HOME/system/ghost-agent.log" | tail -40

Lines in that file look like this — same events, flattened for grep:

2026-08-04 19:35:16 - GhostStream - INFO  - [1165839c +0.08s] llm request — Turn 1 | Temp 0.20
2026-08-04 19:35:24 - GhostStream - DEBUG - [1165839c +7.78s] thinking — The user is asking for the…
2026-08-04 19:35:24 - GhostStream - INFO  - [1165839c +7.79s] system weather — Location: Reykjavik
2026-08-04 20:10:41 - GhostStream - INFO  - [SYSTEM] memory journal — read 1 memory

[SYSTEM] in place of a request id means the agent did that on its own — background work, not something you asked for. Filtering on it is the quickest way to see what the idle scheduler has been doing; each idle pass that did work leaves one idle cycle — ran … line.

The log is redacted by default. Secrets, API keys, .onion addresses, home directory paths and personal details are masked in both sinks, because the log is the thing you leave on screen. If you're chasing a bug and need to see the raw content, --no-redact-logs turns it off — and should be turned back on afterwards.

Working out where to look

  1. Is it up and healthy?

    /api/health — the two fields at the top of this page.

  2. What is it doing right now?

    The live log, in the web UI panel or $GHOST_HOME/system/ghost-agent.log.

  3. What has it been doing?

    Ask it: "what did you do while I was away?" That reads the real background activity ledger.

  4. Is the idle work alive?

    Ask it: "is your learning working?" (or run scripts/learning_health.py). That reports whether the idle passes are actually running and succeeding, which absence of errors will not tell you. Only maintenance is expected to leave a regular heartbeat; the other jobs record a row when they had something to do.

  5. What does it think is broken about itself?

    Ask "what did you do while I was away?" — the activity ledger lists every idle outcome, including failures. (The post-mortem queue that used to answer this was removed on 2026-10-11, §4NM.)

A useful habit: when a subsystem seems to have stopped, check that it's running before you debug what it's doing. The characteristic bug in a system like this isn't a wrong answer — it's a component that silently stopped being called, which looks exactly like a component with nothing to do.
