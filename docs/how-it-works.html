How it works

One message, end to end

The same five steps from the home page, with the parts named — so when something goes wrong you know which one to look at.

Where the pieces live

Ghost is one process. Everything in the middle happens inside it; the bottom row is what it reaches out to.

Memory is files on your disk. The sandbox is a container. The LLM server is a separate process, usually on the same machine.

The five steps in detail

  1. Your message arrives

    Whatever you used to send it, the message lands on the same HTTP endpoint. Ghost checks your key, attaches the message to a session so the conversation has history, and starts a turn.

    POST /api/chat  ·  src/ghost_agent/api/routes.py

  2. Ghost recalls what it knows — before the model sees anything

    This is the step people miss. Ghost doesn't hand your message straight to the model. Your profile is already in the instructions. On top of that it searches two sources in parallel — facts about you, and rules and lessons — and merges the results into a single ranked list. (The general fact store, the graph's topical links, past episodes and past conversations are no longer searched on every message since October 2026; they answer when you ask it to recall something.)

    Merging matters because the stores disagree. A fact that ranks 1st in one store and 4th in another should probably beat something that ranked 2nd in only one place. Ghost scores each result by its position in each list rather than by raw similarity, which lets it combine stores that don't share a scoring scale. Each source's weight comes from a fixed table (§4NN removed the learned weights). The best few thousand characters get pasted in above your message.

    MemoryBus.hydrate_context()  ·  src/ghost_agent/core/bus.py

    If Ghost answers as though it forgot something it clearly knows, this is the step that failed — not the model. What it remembers covers how to inspect and correct it.

  3. The model decides: answer, or reach for a tool

    The model gets your message, the recalled context, and a description of every tool available. It either writes an answer or emits a tool call — a small structured request like "run this Python" or "read this file".

    Ghost accepts tool calls in two formats, because local models are inconsistent about which they emit: the standard OpenAI tool_calls field, and an XML-ish <tool_call> block in the text. A malformed call gets one repair attempt before it's treated as a failure.

    src/ghost_agent/core/agent.py  ·  src/ghost_agent/tools/registry.py

  4. The tool runs, and the result goes back to the model

    Anything that executes code or touches files runs inside the Docker container, not on your machine directly. Anything that reaches the internet goes through Tor. The result is appended to the conversation, and the model gets another go.

    This loop repeats up to 40 times in one turn. Most messages use one or two passes; a real task might use a dozen. If it hits the ceiling, Ghost stops and tells you it ran out of budget rather than looping forever.

    Tool implementations live in src/ghost_agent/tools/

  5. The result is checked

    Since 2026-10-14 (§4OW) only the mechanical checks run. They are mostly programs, not a second model reading the answer (only the image check asks the helper model to look at the picture): they look at whether the page loads without errors, whether the written files exist, whether the reply is an answer rather than narration, whether turn constraints were kept, what the reply claims about memory, and whether an image shows what the reply describes. They do not check whether a fact in the answer is true.

    The reply waits up to 15 seconds for them (GHOST_MECHANICAL_REPAIR_BUDGET, §4OX). A page that throws or a missing file gets one repair round before the reply is sent. A failure found later is recorded and can start a replay in the learning loop; it is not shown to you (§4NF).

    The LLM judge is off by default: measured on a week of real traffic, 9 of its 17 refusals were wrong. GHOST_VERIFIER_JUDGE=1 turns it back on. With it on, a second model reads the answer against the evidence the tools produced and asks, in order, does this answer what was asked? and is it supported by the evidence? — and on this machine (GHOST_CRITIC_ASYNC=1) its verdict lands after the reply and is recorded, not shown.

    src/ghost_agent/core/verifier.py

Two things that behave differently than you'd expect

Streaming answers are checked after they reach you

(Since §4OW the check is the mechanical one; the LLM judge is off by default.) When the reply streams word by word (the web UI does this), the text has already left before the check finishes. Blocking it would buy nothing — the words are on your screen. So the check runs in the background instead. A failure it finds is recorded and can start a replay in the learning loop; since 2026-10-10 (§4NF) no correction notice is shown to you.

Nothing happens instantly after you stop typing

Ghost's background work is gated on you being idle. Two minutes of quiet before it files facts from your recent turns (the journal); ten minutes before memory upkeep; an hour before it replays your recent failures and runs your regression tests (the learning loop). If you're chatting constantly, none of it runs — and it will never interrupt a turn in progress. Checking and learning has the full schedule.

Reading the log when a turn goes wrong

The live console is designed to be watched. Each subsystem logs with its own icon, so you can follow a turn without reading every line. What to look for, by symptom:

SymptomWhich step failedWhere to look
"It forgot something I told it last week" Step 2 — recall The hydration line for that turn. If the fact isn't in the merged list, the retrieval missed it; if it is, the model ignored it.
It described running a tool but nothing happened Step 3 — the tool call didn't parse Look for a repair warning. A malformed call that fails repair becomes text, not an action.
A tool errored and it kept going anyway Step 4 Tool failures are logged loudly. Repeated identical failures trip a guard that blocks the retry and hands the model the previous error instead.
"Done!" but the file isn't there Step 5 should have caught it Look for the verdict line. A refused answer that still shipped means the check landed after the reply (streaming, or past the 15-second window) — it is recorded, not shown to you.
It stopped mid-task Step 4 hit the ceiling A turn-budget message. The task needed more than 40 passes; break it into smaller asks.
