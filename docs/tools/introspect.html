tools / introspect.py

Read-only handle the agent reaches for when asked to describe itself, recall what it has been working on, or surface specific past turns.

Why this tool exists

The selfhood wake-up prefix is off on the request path (_SELFHOOD_PREFIX_ENABLED = False in core/agent.py, journal §3 — it added tokens and steered nothing). So nothing about mood, diary, principles or open questions reaches the model except through this tool, and routing is load-bearing: the system prompt's SELF SURFACE rule sends every "how are you / how's things / what did you do while I was away / tell me about yourself" question here, and overview is the one-call answer. (This page claimed the prefix was live until 2026-09-05; measured over two months of trajectories, 48 such questions were asked, 9 reached the tool, 28 were answered with no tool at all and 9 went to system_utility — the machine's CPU and RAM, not the self.)

introspect is also the deterministic handle for specific recall ("what do you remember about X" — matched against the request and the answer since 2026-09-05), for a structured self-report, and for evaluation scripts that need a known shape.

Counterpart to self_state: introspect reads, self_state writes. The two are deliberately split so a single tool description does not conflate "introspect myself" with "author my forward-looking continuity slot".

Failure semantics

  • Selfhood disabled (--no-self-model / --no-memory): the tool returns a single human-readable "unavailable" sentence. It does not raise.
  • Unknown action: returns "SYSTEM ERROR: 'action' must be one of …".
  • Missing query on recall: returns "SYSTEM ERROR: 'query' is required for recall.".
  • Internal exception in the SelfModel read path: caught at the tool boundary, logged at WARNING, returned as a short failure string. Introspection must never break a user turn.
  • activity exceptions: the branch returns before the SelfModel try-block, so it carries its own guard (added 2026-07-27 — it previously escaped the never-raises contract). A failed ledger read returns an explicit read-error message, never the calm "No background activity recorded" a genuinely quiet window produces.
  • learning exceptions: caught in-branch; degrades to "Learning health unavailable: …".
  • overview: every surface degrades on its own and names its absence ("ledger is not attached", "Learning: unavailable (RuntimeError: …)", "queue not attached") — a missing block is a report of a missing subsystem, never silence. The branch carries its own guard like activity.

Wiring

Declared in tools/registry.py:

  • TOOL_DEFINITIONS entry adjacent to self_state, with the read-only intent emphasised in the description so the model picks the right tool when asked introspective questions.

2026-08-10 — calibration audit: honest numbers, and a consumer that was dead

The headline Brier was in-sample. brier in the params file is a 2-parameter Platt map scored on the rows it was fitted to, and it was printed as the headline beside brier_base_rate — a comparison only one side of which paid for its parameters. The fit now also records brier_cv (5-fold, deterministic seed), the renderer scores the beats/loses verdict on the cross-validated number, and the in-sample figure is shown explicitly labelled as "not performance, the fit scored on its own rows".

The [DEAD] feature verdicts came from an under-powered test. _separation_sigmas is a difference-of-means gate between outcome classes, and the live store carries 18 negatives in 694 rows — at that balance it can only resolve a gap of about 0.60 SD of the feature. It called competence_component dead at 0.05σ, yet ablating that feature costs 0.021 AUC. The fit now records a per-feature held-out Brier delta (feature_contrib), the report renders it, and where the two disagree the ablation wins — it answers the question actually being asked ("does the composite get worse without it?"). The negative count is now printed with an ⚠ UNDER-POWERED flag, because every verdict on that screen is estimated from those 18 rows.

⚠ The threshold has no consumer. The only thing that reads below_threshold is metacog arbitration, and that call site is hard-gated by _METACOG_ARBITER_ENABLED in core/agent.py — a module constant, False, independent of every flag. Measured across 209 metacog summaries in the live log: confidence computed 865 times, below_threshold fired 118 times, arbitrations 0. The report now says so beside the number, because a reader who sees "threshold 0.837" reasonably assumes something happens at 0.837. Nothing does. (The same log shows ask_user, replans_ok and host_critical also at zero lifetime.)

Competence cells reached the prompt without precision. sql: 74% (n=17) rendered identically to fetch: 99% (n=847); sql's 95% CI is [0.50, 0.89]. Cells now carry a Wilson interval and a ⚠ provisional marker below n=30 or CI width 0.20. Wilson rather than Wald because these rates sit against the boundary — and the first version of this fix rendered "98% ±6%", i.e. an upper bound of 104%, so it now prints the bounds rather than a symmetric half-width.

Tests: tests/test_calibration_audit.py, every pin revert-tested, with over-firing guards on both the UNDER-POWERED flag and the CONSUMER-DEAD notice (a warning that is always on is furniture). One pin was initially a false negative — it asserted a symbol existed in the source rather than reaching the output, and stayed green under mutation until it was rewritten to assert on the rendered string.

2026-08-24 (§4CT) — the last unmeasured loop gets its counter

§4CS's yield surface named exactly one remaining instrumentation gap: skills.graduated read unmeasured because the graduated skills are injected into the prompt on every matching turn and nothing anywhere counted it. That is not a zero, and the two lead opposite places — the remedy for "no counter" is to wire a counter, and the remedy for "measured zero" is to kill or fix the loop.

GraduatedSkillStore.surfaced_for_prompt() now returns the prompt block and the signature hashes it listed (format_for_prompt is a thin wrapper over it, so there is one formatter and the hashes cannot drift from the block), and record_surfaced() books a retrieval per skill in one load+save. The row moves from unmeasured to a real number, and activated becomes retrieved at least once — it used to be len(rows), "all of them are eligible", which is true of every store and evidence of nothing.

Three properties, and the third is the one that is easy to get wrong:

  • Idempotent per turn. A counter that can over-report is not an honest number. Dedup is keyed per turn in a bounded map, not held in a single slot — the lesson store's equivalent keeps one _retrieval_turn_key that any interleaved retrieval resets, which a review found to be one of three routes by which it double-books.
  • REAL traffic only. The gate is turn_origin(context) == "user" — the canonical predicate, the same one the liveness denominator and the foresight gate use, so this counter cannot drift from the population those views interpret. Self-play, dream, subagent and bench turns inject the same block, and counting them is the §4K defect verbatim: 28 "user turns" reported on a box whose true count was zero. A missing context does not book either — turn_origin(None) answers "user" by its own correct default, so without that guard the absence of a context would read as real traffic, which is a check that cannot run reporting the favourable outcome.
  • It is NOT helpfulness, and the row says so. invoked counts prompt injections. Unlike lessons, this store has no outcome arm (succeeded_retrievals / failed_retrievals fed from the turn's verified verdict), so nothing here says a surfaced skill was read, used, or useful. Wiring that arm means threading a second population through _record_lesson_outcomes, its trajectory stash, its flushed-retain ring and its opposite-sign re-book — a reviewed hot path — and is deliberately not done here.

verifications is still not read as usage: it is the PRODUCER-side re-verification count from the graduation gate, and reading it as consumption would turn a silent loop into a healthy-looking one. Tests: tests/test_4ct_graduated_skill_retrievals.py (31 tests, 20 mutants, 20 killed).

2026-08-24 (§4CU) — retrieval SPREAD, and a seventh state: retired

The gap. invoked is a sum over per-item counters, and a sum cannot tell a store whose 50 items are all being drawn from a store where one item takes every retrieval and 49 never surface. Those are opposite findings with opposite remedies — the first is healthy, the second means the retriever is broken and minting more cannot help. The failure has a measured signature: arXiv:2604.27003 reports 88.5% of queries retrieving the identical top item despite high key-level diversity, and concludes that "pool size alone predicts nothing about retrieval effectiveness" — which is a direct statement that the two numbers this view already had cannot see the pathology.

Nothing new is recorded. Every store already carries the per-item counter that invoked sums (retrievals on lessons and graduated skills, usage_count on macros and acquired skills). The spread is a second statistic over the same vector, which is why total must equal the row's own invoked — pinned as an executed test, because a concentration computed over a different population than the row it sits on is exactly the kind of plausible lie §4CE found three instruments telling.

VerdictMeans
distributedNo item takes a majority and most of the store is reached.
concentratedOne item takes more than 50% of retrievals — strictly greater, because the sentence the branch prints is "more than every other item combined" and ≥ does not mean that (at n=2 a uniform [5,5] store tripped the bar with a claim that is arithmetically false) — or at most half the eligible store has ever surfaced. The remedy is the retriever, not the producer.
underpoweredFewer than 5 retrievals per eligible item (the standard expected-cell-count convention, not a tuned constant). The numbers are still printed; the verdict is withheld. Only the judgement needs a denominator — and reporting one a denominator cannot support IS the §4CE instrument failure, not a conservative reading of it.
undefinedFewer than two eligible items (a 100% share over one item is true by construction), or nothing retrieved at all (the row's own status is the finding; repeating it here would double-count it).

The eligible population, not the minted one. 26 of 29 live auto-mined macros are proposed, and a proposed macro is not advertised and cannot be run — scoring over all 29 would report 100% top-1 about a store with exactly one runnable item, which is the derived_zero error transplanted onto a new axis. Eligible is therefore currently eligible ∪ anything with a non-zero count: the union half is the invariant that keeps total == invoked when an item is used and later demoted, and a non-zero count is itself proof the item was eligible when it was drawn.

Measured on the live stores the day it shipped, and the first finding was an exoneration: lessons.playbook reads distributed — top-1 21% of 676 retrievals, 40 of 45 served lessons reached, evenness 0.82. Nowhere near the published collapse signature. The other three loops read underpowered and their numbers are printed unjudged (skills.acquired: 24 retrievals over 5 items, all 24 on one). Assuming collapse and "fixing" the retriever would have been work against a store that is working.

retired — the seventh state. foresight.gate read barren: "produces artifacts nobody invokes", sorted first in a worst-news-first view, remedy "find it a consumer". The real answer was that §4CS item G had settled it — the index is anti-predictive (rows it claims will fail fail 7.1%; rows it claims will succeed fail 10.6%), and _evaluate_bucket checks precision before the interval test, so a bucket under the bar cannot enable at any n. More traffic does not fix it. barren reads as owed work every time an operator opens the view; retired says measured dead, decision recorded, nothing owed, and sorts with the settled states.

It is derived, never asserted — read off the gate's own numbers, not off its verdict string, because a lexical proxy for a semantic property means rewording the prose would silently un-retire a dead loop with the suite green. The moment the measurement changes, the row un-retires itself with no code change and no operator action; the gate builder keeps running throughout, because a closed gate is a measurement and measurements do not stop when a feature is off.

⚠ THE RULE WAS WRONG TWICE BEFORE IT WAS RIGHT, IN OPPOSITE DIRECTIONS, and both versions passed review until someone executed them.

  • v1 — the sign, with no power. spread <= 0 with both denominators merely truthy. On the live gate that retired a loop on 14 predicted-fail rows of which one failed: Fisher exact p = 1.00, and the interval for the spread contains both zero and the +0.10 bar the verdict cites as the thing it fails. A terminal "nothing owed" verdict on an arithmetically undetectable difference — §4CE verbatim, committed inside the instrument added to prevent it.
  • v2 — power, with no sign. Replacing it with "is the pooled precision provably below the bar" fixed the power and lost the semantics: it retired an index where predicted-fail rows fail 40% and predicted-ok rows fail 2% (spread +0.38, hugely predictive), and the row printed the builder's own verdict — "discriminates in the right direction… but pooled precision is under the bar" — directly above "SETTLED, nothing is owed". Two sentences in one string saying opposite things.

v3 needs both, because they are different findings with different remedies. spread ≤ 0 means the index is backwards — nothing to do but build a better one, so RETIRED. spread > 0 means the index works and the bar is wrong for it — that is owed work, so not retired. Retirement therefore requires the index to fail to discriminate and its precision interval to be provably unable to reach the gate's own min_fail_precision, with the gate's own min_fail_n applied to both legs (v2 retired on 3 rows while a bucket needed 10 before it could object — every tie broke toward "settled"). On the live row: 1/14, Wilson upper 0.31 against a 0.60 bar, and the note carries the interval so a number on the row can contradict the verdict.

A bucket with enough data to still reach the bar vetoes retirement — an aggregate can be dead while a stratum is alive. But "alive" needs its own power: 4 of the live gate's 64 buckets have an interval reaching the bar and every one sits at 1–3 rows, where the Wilson upper bound is wide by construction. Counting those is absence of evidence read as evidence, and would make RETIRED unreachable forever. And when no bucket is eligible to be assessed, the note says so rather than claiming a check that could not have run.

Pinned in tests/test_4cu_retrieval_spread_and_retired.py — 111 tests, 42 mutants killed, each running whole test files. Several pins exist only because a mutation showed the first version green: the entropy clamp looked like dead defence until the sweep reached n=5 (the smallest uniform store that actually overflows 1.0 — the test now carries the unclamped value as its own negative control); top1 = max(counts) survived as counts[0] because every fixture in the file put the busiest item first, and under that mutant the published 88.5% collapse signature is silently reclassified as healthy; the "cannot fall below" sentence was a token pin that stayed green when rewritten to a wrong number; and the fixed-width name column ate its separator the moment a 22-character probe name was registered, so the width is now sized from the data.

⚠ And a patch of ours silently deleted an entire test class — TestForesightGateRetires sat between two anchors a scripted edit replaced. Nothing failed, because deleting tests is invisible to a test run. The mutation harness caught it: "retired": [...] → [] suddenly survived, because the only test reading that bucket had ceased to exist. pin-the-deletion, one level up.

2026-08-24 (§4CU) — verifier.rubric_shadow: grading the turns the verifier declines

The population. Measured over user_request turns with the corrections overlay applied: tool-using turns are 80.7% decided over the last 14 days, chat turns 30.4%. The undecided remainder is dominated by turns that ran no tool — nothing was executed, so there is nothing for an evidence-packing verifier to check. §4CS item D established there are zero lost verdicts there: the verifier is not failing on chat, it is declining, correctly.

Declining is right for a binary evidence check and wrong as the last word, because "was this a good answer to this request" is a multi-criteria judgement rather than a claim to be refuted. Rubrics as Rewards (ICLR 2026) measures the gap: structured checklist rewards beat direct Likert LLM-judge scoring by up to 31% on HealthBench, and — the part that matters for a local 35B judge — they yield better alignment for smaller judges and reduce variance across judge scales.

⚠ Why it ships in shadow, and why that is not timidity. A rubric IS a checklist injected into a judging prompt, and §4BE is what that shape did here last time: the checklist nudge asserted the user had given learning instructions, 59 of 59 arming turns had none, it fired 39 times, and a model that reasoned "there's no explicit learning instruction… But the system is requiring it" complied and minted a lesson that dedup reinforced to freq=11. A checklist the model feels obliged to satisfy manufactures the evidence it asks for.

The contract is therefore structural, not aspirational:

  • It cannot write an outcome label. One file, system/verifier/rubric_shadow.jsonl, which no learning path reads. traj.outcome is never touched. A source-level pin refuses the symbols that would make it a labelling path.
  • The rubric is synthesised from the REQUEST ALONE. build_rubric() does not take the response as a parameter — a caller cannot leak it even by mistake, because there is nowhere to put it. A criterion written while looking at the answer is a criterion written to fit it, which is the "predict the label from the label" failure that made "any tool errored" the strongest and most useless confidence feature (AUC 0.229). Pinned twice: on the signature, and by running the real two-call flow and asserting a canary from the answer is absent from the first prompt and present in the second.
  • ABSTAIN is a real outcome, never a fabricated neutral. Small talk scores nothing; so does an ungraded criterion (which is not a pass — a truncated grading reply would otherwise shrink the denominator in the flattering direction), and so does an all-na rubric (1.0 over an empty denominator is a fabricated pass). Recording 0.5 for any of these would put a zero-variance column into a corpus, which is how w_entropy stayed pinned at 0 across 1200 samples.
  • It carries an epoch. Change the prompt or the scale and old rows stop being comparable; the agreement reporter drops them rather than pooling eras — the Simpson's-paradox trap that once forced a negative Platt slope on the calibration corpus.
  • Default OFF (GHOST_RUBRIC_SHADOW=1). Nothing here becomes autonomous by having been built.

The only route out of shadow is agreement(), and it is built to refuse. It scores against human labels only (scoring a judge against another judge measures their shared blind spot), returns NO VERDICT under 30 paired rows while still reporting the rate, and compares the Wilson interval's lower bound against the majority-class baseline rather than the point estimate against 50% — with ~76% passed chat labels, "always say pass" scores 0.76, which is the §4BR wrong-statistic trap waiting to be walked into.

The loop got its yield row on day one rather than once it mattered: verifier.rubric_shadow reads gated while the flag is off, and once on reports minted (judgements written) → activated (those that GRADED rather than abstained) → invoked (graded rows a human label has since landed on). invoked is deliberately the paired count and not the row count: a shadow verdict nobody can check against ground truth is production posing as consumption, which is the exact defect round 1 of §4CS item B built into evolve.candidates.

⚠ THE PROMOTION GATE WAS CALIBRATED ON THE WRONG POPULATION, AND THREE INDEPENDENT REVIEWERS FOUND IT. rate was measured over the joined rows while base_rate was computed over every human label on the box — two different populations, compared. Because ABSTAIN concentrates on ungradable turns, the scored subset is more class-skewed than the label pool, so a judge emitting 1.0 for every row — zero information content — read "agrees 95%, whose LOWER bound beats the 78% majority-class baseline: USABLE". It failed the other way too, refusing a genuinely discriminating judge when the unpaired labels skewed the opposite way. This is the §4BR wrong-statistic trap inside the function whose own comment cites §4BR. The baseline is now computed over the rows that actually paired, a single-class paired set returns usable=None (no contrast to beat is a property of the labels, not of the judge), and base_rate is present on every return path.

Pinned in tests/test_4cu_rubric_shadow.py — 100 tests, 36 mutants killed. Everything above verified the module and nothing verified the CALLER until a reviewer showed three mutants surviving all 83 tests: swapping the first two arguments at the call site — so the rubric is synthesised from the agent's own answer, inverting the headline contract — plus switching the feature off entirely and ignoring the population gate. The class written to prevent exactly that checked hasattr, a source substring, and iscoroutinefunction; §4CS item B verbatim. The call site is now driven for real, with a canary asserting the request reaches prompt 0 and the answer reaches prompt 1. Two further pins came from mutants rather than design: GHOST_RUBRIC_SHADOW=TRUE was silently off (case-sensitive compare), and every agreement test but one had rate == base_rate exactly — where the point estimate and the interval agree by accident — so promoting on the point estimate survived until an 80%-judge / 75%-baseline / n=40 case was added.

2026-08-24 (§4CS) — LOOP YIELD: a SECOND axis, and the one the macro loop had to be found by hand

The section below answers "did this mechanism RUN?". That is not the same question as "did it produce anything anyone CONSUMED?", and the gap between them is where this project keeps losing work. The macro loop ran on schedule for six weeks, mined sequences and minted 25 composed skills; every liveness probe read fired throughout, and invocations across every auto-mined macro, all time, were 0. Nothing anywhere reported that. §4CH found the same shape wearing a number — dream ledgering a constant, 919 identical rows, for its busiest subsystem.

core/liveness.py now carries a second probe table reporting, per producing loop: minted → activated → invoked plus when it was last invoked. It renders under introspect action='learning' beside the liveness section (extended rather than given its own action: a parallel surface is one more thing an operator must remember to look at), and collect_learning_health() carries the same data under loop_yield so it can be alarmed on programmatically, not only read.

2026-08-10 — SUBSYSTEM LIVENESS: a probe per mechanism, and a third state

MECHANISM LIVENESS (below) made absence a row rather than a silence — but only for the 18 phases that write to autonomous_activity.jsonl. The most important dead loop found that day, metacog arbitration (0 firings against 118 below-threshold opportunities), does not write there and was found by grepping the log by hand. A dead-loop detector blind to the class of thing that justified building it is the defect it exists to remove, one level up.

core/liveness.py therefore has each mechanism declare where its own durable evidence lives, and reads it read-only — no production write-path changes, no new ledger volume. Nine probes cover metacog arbitration, verifier outcomes, router decisions, the router checkpoint, calibration fits, foresight predictions, RRF observations, experiment stamps and GEPA applies.

The third state is the point. Statuses are FIRED / ZERO / NO_SOURCE / GATED. The older view conflates the middle two — a phase absent from the ledger reads as zero whether it is quiet or unobservable, which is the same missing-vs-empty conflation removed from the response cache, and precisely how arbitration stayed invisible. NO_SOURCE is an instrumentation gap, reported separately from dead and never alarmed on; GATED reports where the switch is rather than a meaningless count.

A turn denominator (user turns in 24h) accompanies the table, because turn-driven mechanisms are correctly silent when nothing asked them to run — without it, three quiet stores read as a simultaneous triple failure. Alarms are withheld at zero turns, as one fact.

2026-08-11 — the denominator was counting self-play, so the guard argued for the false alarm it was built to prevent

Read on the live agent: 28 “user turns” in 24 h, of which 28 were self-play and 0 were real. Self-play and dream turns enter through the same handle_chat as a human request and emitted an identical request started line, so _count_user_turns counted every one of them. Meanwhile foresight.predictions, rrf.observations and the trajectory writers sat at zero — correctly, because their own simulation gates exclude exactly those turns. The denominator and the ledgers were counting opposite populations, and the denominator is the number a reader trusts.

Two coupled defects, and the first hid the second:

  • The count included self-play, so it could reach 0 — the branch that withholds alarms — only on a box where the hourly self-play loop was also dead. A guard whose triggering condition is unreachable in production is furniture.
  • The withholding cleared every row. The only two probes that alarm are driven by the idle clock or by any request, not by user traffic; had the first defect ever let this fire, it would have silenced precisely the alarms a quiet day does not explain. Fixing the count is what arms this one, so both had to move together.

The fix stamps the population at the source. agent.turn_origin() derives origin=user / origin=sim from the read-only skill store — the same derivation as the foresight simulation gate and finalize's is_simulation, deliberately not a second notion that can drift from them — and the request-started mirror line carries it. The console frame is unchanged, because the uConsole turnstatus parser and the Slack owner-lock both key on it and neither needs this.

A log window written before the stamp is reported as UNCLASSIFIED, not as a number. The stamped subset would be a lower bound on user turns while the label says count; quoting the total is the original bug. Missing is UNKNOWN, never zero and never an inflated count — and an unknown denominator withholds simulation-gated alarms too, since a zero that cannot be interpreted does not license a DEAD verdict.

Each probe now declares which absence excuses its silence (DEN_USER_TURNS / DEN_REQUESTS / DEN_NONE), a separate axis from the cadence vocabulary shown to the reader. router.decisions renders as periodic but routes on every request including self-play, so an idle box explains it while a user-quiet one does not; calibration.fit runs off the idle clock and gets no excuse at all. The default is DEN_NONE — a mechanism must earn its excuse — so the decision cannot be skipped by omission.

Tests: tests/test_subsystem_liveness.py + tests/test_log_beautify.py, six pins, every one mutation-checked red — including the live defect reproduced in miniature (three self-play turns must count as 0; reverting the origin filter yields assert 3 == 0) and a seam test that turn_origin agrees with the gate it borrows from, pinning the load-bearing is True so a MagicMock context cannot read as a simulation.

Eight defects were found in these probes during review, none in the systems they watch, and each is pinned in tests/test_subsystem_liveness.py: a regex that matched verify but not verifier (false DEAD against 43 real verdict lines); float(ts) against stores that write ISO strings (two healthy stores read as ZERO); probing experiments.json, an optional override whose absence is normal (healthy system reported as a gap); no turn denominator; mtime-based freshness that a touch can fake into a false GREEN (now read from fitted_at inside the file); a core.agent import costing 1.8 s of a 1.97 s runtime (now a literal AST read, verified to agree with the imported module, declining rather than guessing if the flag ever becomes computed); three full 14 MB log scans (now one shared parse keyed on size+mtime); and a caller passing $GHOST_HOME/system instead of $GHOST_HOME, which blinded all eight probes at once. Cost after: 1974 ms → 232 ms.

2026-08-10 — MECHANISM LIVENESS: absence became a row instead of a silence

The BACKGROUND ACTIVITY line enumerated phases observationally — it counted whatever slugs happened to already be in the ledger. A loop that stopped writing, or never wrote, produced no key and so was invisible, which is indistinguishable from a mechanism that does not exist. Measured against the live ledger: 15 phases are instrumented in src/, 7 had written anything in seven days, and the report showed seven green rows with no hint of the other eight. Two silent caps rode along — the renderer sliced [:8], so a phase at zero (the only kind worth acting on) sorted last and was structurally the first row dropped, and the reader took limit=2000 against a ledger already past 2,600 records.

PHASE_EXPECTATION in core/autonomous_activity.py is now the registry, and activity_liveness() iterates it rather than the ledger. Rendering the zeros is not sufficient on its own: reflection legitimately sits at 0 because it records only outcome-producing runs, while dream at 0 would be a dead loop — a benign zero and a fatal zero must not look alike, which is the same defect one level up. So every phase declares what its own zero means: periodic (scheduled, fires on its own — zero is an ALARM), on_output (runs on schedule but records only when it produced something, e.g. if stale: / if _tidy_deleted:), on_demand (externally triggered), gated (needs a flag or consumer that may be off, e.g. PRM retrain). Only periodic can alarm; alarming on a benign zero is how an operator learns to scroll past the section, rebuilding by hand the blindness it exists to remove.

An agent-down guard withholds per-loop alarms when nothing fired in the window — a stopped agent is one fact, not five dead loops — and it keys on total silence only, so a single surviving record still lets a genuinely dead loop alarm. Zeros sort first; unregistered slugs render marked rather than dropped; a truncated tail-read is reported rather than silent. Two windows are shown (24h alarm, 7d context) because "ran three days ago" and "dark for a week" are different diagnoses that one boolean cannot carry.

Tests: tests/test_activity_liveness.py — including a mutation test per periodic loop (silence exactly one mechanism, require the monitor to name it), a coverage test that fails when a phase literal exists in src/ but not in the registry, and an over-suppression guard on the agent-down logic. A monitor never observed to alarm proves nothing — that is the defect class this section exists to catch, and shipping one untested would be the purest form of the mistake.

TOOL-CALL FRAMING LEAK — recurrence watch (added 2026-08-04)

Scans the trajectory corpus for tool-call framing that leaked into an argument value — e.g. 'operation': 'read_chunked>\n<parameter=path>\nindex.html', where the recorded operation and path are fiction. Reported via utils/leaked_framing.py.

The verdict is keyed on the NEWEST occurrence, not the count. The corpus is append-only, so the 16 historical cases never go away; what matters is whether the latest one postdates the 2026-07-31 QWEN_TOOL_PROMPT_NATIVE fix. Pre-fix reads "all historical — no action"; a post-fix timestamp renders "⚠ REGRESSION", because the dual-dialect corruption wasted whole turns when it was live.

Why it exists: the journal recorded "repair fires ≈0 now, each one is news" — and nothing watched, so 17 historical cases were re-discovered by hand four days later and briefly mistaken for a live defect. Dating a defect against the fix that closed it is the check that was missing. The same scan also excludes those calls from optim/tool_ontology.py's macro mining (they inflated the n-grams ~1.5%), and the report prints the exclusion in a corpus purity header rather than applying it silently.

The detector is deliberately wider than agent._value_has_leaked_framing, which decides whether to TRUNCATE a live value and must stay strict. Counting is not truncating. Position is the discriminator — framing at the start of a value or after a newline, or appearing twice — so prose that merely mentions the dialect is not flagged. Tests: tests/test_leaked_framing.py.

VERIFIER ESCALATION — the §4F false-positive watch metric (added 2026-08-04)

Reads $GHOST_HOME/system/verifier/escalations.jsonl and reports the overturn rate per (route, kind) — claim/refute, claim/confirm, code/refute. Averaging the routes together would hide both populations: measured 2026-08-04, claim-path refutes are overturned by the main model 84% of the time, while all 7 live code-path refutes were upheld on replay.

Why it exists: the metric was previously written only into VerifyResult.to_dict(), which has no production caller, so the rate could only be recovered by hand-run log archaeology — and a naive grep over-counts it by 9 points, because the OVERTURNED line is a WARNING mirrored to a second logger while "verdict stands" is INFO. The ledger records at the point escalation resolves, and records both outcomes, which is what makes a rate computable rather than a numerator.

unavailable rows (the strong model errored or returned unparseable output, so the original verdict stood) stay in n — a call was spent — but are excluded from the rate and reported separately. An absent ledger is reported as "no ledger file" rather than silently rendering nothing: the file is created on the first escalation after a boot, so absence right after a deploy is expected, and the report says which silence it is.
