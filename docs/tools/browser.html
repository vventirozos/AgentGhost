tools / browser.py

Native headless-browser automation via Playwright — Tor-aware, DNS-leak-safe, session-persistent.

Why a native tool

Before this tool, headless-browser usage was LLM-authored raw Playwright in execute(stateful=True). Four recurring footguns came with that path:

  1. API shape drift: await async_playwright().start() vs async with, top-level await rules, cleanup order. Any slip crashed the Jupyter kernel.
  2. DNS leaks: Chromium's SOCKS5 proxy tunnels traffic but can still resolve names via the container's /etc/resolv unless --host-resolver-rules is also set. Easy to miss.
  3. WebRTC IP leaks: STUN/TURN can expose the host IP even over Tor.
  4. Concurrency races: "store browser/page globally" broke when two plan branches both used the kernel.

The browser tool bakes correct-by-construction defaults for all four. Raw Playwright remains available in execute for advanced flows (response interception, custom wait conditions, file uploads).

Tool: browser

Six operations. The first five are atomic: each launches a fresh Chromium context and re-navigates via the .last_url sidecar. The sixth, interact, runs a sequence of sub-actions in a single context so transient DOM state survives between steps — required for multi-step SPA flows.

navigateurlHTTP status, final URL, page title, and a capped ~8 KB text preview of the body innerText (+ length, truncated) — 2026-07-07
extract_text—Rendered innerText of body (or a CSS selector), truncated at max_chars (64 KB default)
clickselectorPost-click URL + title + the post-click text preview

close—Deletes the persistent profile so the next session starts fresh
interactactionsPer-action results (ok/error), final URL, final title. One Chromium context across the whole list.

navigate/click return page text (2026-07-07; formatter fixed 2026-07-14)

Every atomic op opens a fresh Chromium context and reloads the page, so a bare navigate that returned only status/title forced a second extract_text op that re-launched Playwright and re-fetched the same page over Tor (5–20 s) — the dominant cost of the common scrape flow. navigate and click now include a capped ~8 KB text preview (_body_excerpt), so navigate → read is one op instead of two; call extract_text only when the preview was truncated or you need a precise selector. Pass nav_text_chars=0 to opt out. The tool description tells the model it usually does not need a follow-up extract_text. The warm-runner tier (a long-lived in-sandbox process holding the persistent context open, eliminating the per-op launch entirely — the L tier of this improvement) remains future work. Covered by tests/test_browser_navigate_text.py.

Formatter regression fixed (2026-07-14). The runner computed and shipped the preview, but the host-side result formatter silently DROPPED it for both navigate and click — so the model never saw the text and the "one op instead of two" saving never happened. The runner side was tested; the formatter wasn't. click also dropped the captured JS diagnostics, so a click that crashed page JS looked identical to one that worked. Both now render a --- PAGE TEXT (capped preview) --- block (+ js_errors for click); nav_text_chars is plumbed end-to-end (previously the runner default was unreachable), and settle_ms/post_click_ms are coerced with _safe_int (a settle_ms="2s" used to raise a raw ValueError out of the tool). Covered by tests/test_browser_formatter_and_render_fixes.py.

MAIN_IMAGE: the page's own picture, as a URL 2026-09-22 §4JY

navigate and extract_text also return the page's main image:

MAIN_IMAGE: https://upload.wikimedia.org/wikipedia/commons/thumb/f/fe/K.jpg/960px-K.jpg
MAIN_IMAGE_SOURCE: og:image — download it with file_system(operation="download", url=…) if you need the picture itself

Why it exists. Asked to fetch a photo of a person, the agent could not get one. It hand-built Wikimedia thumbnail URLs — sites pre-render only some widths, so 800px-… and 640px-… returned HTTP 400 while 500px-… returned 200 — then fell back to screenshotting the file page and passed a 1280×2290 picture of a web page to the image model as the "photo". Nothing was blocked: the URL the page declares in og:image fetched 200 over Tor. The model was guessing because nothing handed it the answer.

MAIN_IMAGE_SOURCE is not decoration. og:image (or twitter:image) is the site's own declaration and can be trusted; largest-rendered is a heuristic and should be checked with vision_analysis before use. The fallback ranks by rendered geometry (getBoundingClientRect), never by the HTML width/height attributes — those are intrinsic, and ranking by them picked a 7651×5103 photo of an entirely different politician on the very page under test. Images under 128 px, data: URIs and SVGs are skipped, and every URL is resolved absolute so it can be downloaded as-is. Pinned in tests/test_browser_main_image.py (26 tests, 9 of them executing the JS under node against fake DOMs; 12/12 mutants).

Atomic ops vs. interact

The atomic ops are perfect for single-page scrapes. They are not suitable for interactive multi-step flows, because every op's fresh context discards the JS-driven DOM mutations made by the previous op. A click that opens a modal is invisible to the next click, which sees a page just-loaded from its initial HTML. The 2026-04-23 WebOS eval hit this wall: the agent couldn't drive the Calculator because the Calculator window vanished between every click.

interact solves this by taking a whole sequence in one call:

browser(operation="interact",
        url="file:///workspace/webos/index.html",
        actions=[
          {"action": "click", "selector": "[data-app='calc']"},
          {"action": "wait_for_selector", "selector": "#calc-display"},
          {"action": "click", "selector": "#calc-btn-7"},
          {"action": "click", "selector": "#calc-btn-plus"},
          {"action": "click", "selector": "#calc-btn-3"},
          {"action": "click", "selector": "#calc-btn-eq"},
          {"action": "extract_text", "selector": "#calc-display"},
          {"action": "screenshot", "out_path": "calc_result.png"},
        ])

Sub-action types:

  • {"action":"goto","url":"...","wait_until":"load"} — navigate mid-sequence (e.g. follow a link into a subpage).
  • {"action":"click","selector":"...","wait_for_hidden":"#overlay","force":false} — see "Stability guard" below for the optional fields.
  • {"action":"dblclick","selector":"..."} — required for ondblclick-bound UIs (desktop-icon launchers etc.). A plain click never fires dblclick listeners; the 2026-04-24 webOS session produced 8 identical screenshots because the agent fired single clicks on .desktop-icon elements whose openApp() handler was wired to dblclick only. Accepts the same wait_for_hidden / force options as click.
  • {"action":"extract_text","selector":"...","max_chars":65536} — each extraction is preserved in the results so you can read multiple points in the flow.
  • {"action":"fill","selector":"input[name='email']","text":"a@b","wait_for_hidden":"#busy"} — real text input (atomic ops don't support typing). Same overlay-wait option as click.
  • {"action":"wait_for_selector","selector":"...","state":"visible|hidden|attached|detached","timeout_ms":5000} — state defaults to visible; use hidden to wait for an overlay to GO AWAY (the LLM-facing missing primitive that drove the 2026-04-26 incident).
  • {"action":"screenshot","out_path":"..."} — sandbox-safety + host→container path rewriting is applied per sub-action.
  • {"action":"sleep","ms":500} — when you need an explicit pause and there's no selector to wait on.
  • {"action":"evaluate","js":"({x: ball.x, y: ball.y})","max_chars":16384,"timeout_ms":5000} — run a JS expression (or () => ... arrow function) in the page and get its JSON-serialised value back in the per-action results. Aliases expression/script are healed. Output is capped like extract_text (true length + truncated flag reported); non-JSON-serialisable values degrade to strings via default=str (circular structures via the ValueError fallback). Per-action bounded: page.evaluate is not governed by Playwright's default-timeout machinery, so the runner wraps it in asyncio.wait_for (step timeout_ms, else the op default; floored at 1s) — an unsettled Promise fails that action with a "poll with sleep+evaluate instead" steer rather than hanging until the subprocess kill, which would have discarded every earlier action's result along with the [BROWSER_OK] payload.

evaluate: exact-state probes for agent-built apps (2026-07-31)

The incident. Debugging its own pinball game (req 66d64313), the agent needed one fact — did the ball exit the launcher channel? — and had no way to ask the page. page.evaluate existed inside the runner (powering extract_text) but was never exposed as a sub-action, so the agent fell back to screenshot + describe_picture: five ~30 s vision round-trips returning caption-shaped answers, one misjudged frame, and five failed wall-geometry fixes steered by feedback too coarse to discriminate between hypotheses. A single evaluate of ball.x would have answered exactly, instantly.

The rule of thumb (mirrored in the tool description and the system prompt): screenshots + vision are for how things look (rendering, colours, layout); evaluate is for what the state is (positions, scores, velocities, getBoundingClientRect() geometry). For motion, sample twice: click → sleep → evaluate → sleep → evaluate — two samples show the trajectory.

Trust & safety. The JS runs in the page context — the same trust domain as click/fill on a page the agent can already navigate and rewrite. JS-initiated fetch/navigation still passes the context's SSRF route guard (_install_ssrf_guard), so evaluate adds capability, not network exposure.

Coverage: tests/test_browser_interact_evaluate.py.

Project-scoped file:// heal (2026-06-20)

_resolve_file_url(sandbox_dir, url) rewrites a file:// URL to where the file actually lives when a project scopes the sandbox to <root>/projects/<id>/. It resolves the path the same way _get_safe_path does and translates back with _to_container_path, so every route the model invents — file:///workspace/..., file:///sandbox/projects/<id>/..., a bare name — lands on the single correct container path file:///workspace/projects/<id>/<name>. This is what fixed the live net::ERR_FILE_NOT_FOUND loop where a model-built file:///workspace/sandbox/projects/<id>/browser-os.html double-nested and 404'd three times. Applied to navigate and to each goto sub-action of interact. Covered by tests/test_browser_path_scoping.py.

Stability guard: wait_for_hidden + force + wait_for_selector(state) (2026-04-26)

Bare page.click() auto-waits for its TARGET to be actionable, but knows nothing about an unrelated overlay still intercepting clicks. The 2026-04-26 webOS session lost ~70 minutes to this exact shape:

actions=[
  {"action": "click", "selector": "#unlock-btn"},   # JS sets #lock-screen.style.display='none'
  {"action": "click", "selector": "#start-btn"}     # ←  fails: lock screen still intercepts
]

Three new options give the LLM a clean way to express "wait for the overlay to leave, then click":

  • wait_for_hidden on click / dblclick / fill: a CSS selector for the overlay that must disappear before the action fires. Internally calls page.wait_for_selector(overlay, state="hidden") first; if the overlay does NOT go away in time, the action fails with wait_for_hidden(...) timed out before click(...) — a much clearer signal than Playwright's generic "element intercepts pointer events". An optional wait_for_hidden_ms (default min(5000, op.timeout_ms)) tunes the wait.
  • force on click / dblclick: skips Playwright's actionability check (visibility, stability, hit-test). Use sparingly — meant for cases where the LLM is certain the target is correct but Playwright is being conservative (mid-CSS-transition, or a target whose stability oracle is overzealous).
  • state on wait_for_selector: defaults to visible (Playwright's own default, the prior behaviour). New values hidden / attached / detached mirror Playwright's API. Bare wait_for_selector(sel) waited for the selector to APPEAR — useless for an element that's already in the DOM and just needs to fade out, which was the missing primitive that drove the incident.

Recommended pattern for a flow with a fading overlay:

actions=[
  {"action": "click", "selector": "#unlock-btn"},
  {"action": "wait_for_selector", "selector": "#lock-screen", "state": "hidden"},
  {"action": "dblclick", "selector": ".desktop-icon[data-app='calc']"},
  {"action": "screenshot", "out_path": "calc.png"},
]

Coverage: tests/test_browser_interact_stability_guard.py.

By default (stop_on_error=false) a failing sub-action is recorded and the sequence keeps going — so you get full visibility into which step is flaky. Pass stop_on_error=true to abort on first failure.

The subprocess wall-clock budget for interact scales with action count (timeout_ms × len(actions)), so a 20-step flow doesn't hit the single-op default cap.

Session persistence

Cookies, localStorage, and auth tokens survive across tool calls via Chromium's launch_persistent_context(user_data_dir=/workspace/.browser_profile). Each op opens → runs → closes cleanly; there is no long-lived subprocess to manage. Call operation="close" to wipe the profile (e.g. after logging out, or when switching user contexts).

Chained-op continuity (.last_url sidecar)

launch_persistent_context restores cookies/localStorage but NOT open pages — each op's browser process is a fresh launch. Without extra plumbing, a "step 2 continues where step 1 left off" call pattern would land on about:blank and every selector query would fail (surfaced by the 2026-04-23 eval, which then caused the LLM to burn a turn misattributing the error to a DOMContentLoaded race).

To let the LLM chain ops ergonomically, the runner writes the final URL of every successful navigation to a sidecar in <profile_dir>: .last_url.<req> for the current request since §4LN (the shared .last_url only outside a request). Any subsequent extract_text/click/screenshot without an explicit url reads the sidecar and re-navigates first. Typical usage:

browser(operation="navigate", url="https://example.com/login")
browser(operation="click", selector="#login-btn")      # no url — uses sidecar
browser(operation="extract_text", selector=".welcome") # no url — uses sidecar
browser(operation="screenshot", out_path="landed.png") # no url — uses sidecar
browser(operation="close")                             # wipes profile + sidecar

When neither an explicit url nor a sidecar URL is available, the runner errors out with extract_text needs a URL: pass `url=...` or call `operation="navigate"` first — no silent query against about:blank.

The sidecar lives inside the profile dir, so operation="close" (which rmtree's the whole directory) wipes it for free. Since §4LN the sidecar records the page ASKED for before loading it (a navigate that times out must not leave the previous page for the next url-less read); since §4PC the files are .last_url.<request> and .last_url.c<conversation> — the global .last_url is neither written nor read.

Tor & DNS-leak hardening

When the sandbox was started with a tor_proxy, every op forwards it as Chromium's --proxy-server. The in-sandbox runner (_chromium_args) always adds, alongside the Docker-safe flags:

  • --host-resolver-rules="MAP * ~NOTFOUND , EXCLUDE localhost , EXCLUDE <proxy-host>" — forces DNS through the SOCKS proxy; EXCLUDE localhost keeps the self-play fixture server + in-container services reachable, and the proxy's own host is excluded too (see the warning below).
  • --webrtc-ip-handling-policy=disable_non_proxied_udp (and the --force- variant) — suppresses host UDP/STUN candidate gathering that could expose the real IP even when HTTP is proxied.

Host-side SSRF guard skips DNS in Tor mode (2026-07-03). The pre-navigation SSRF check (_browser_blocked_url → url_ssrf_reason) used to resolve the target hostname via getaddrinfo on the host even in anonymous mode — a DNS leak of the site about to be visited that defeated the DNS-over-SOCKS hardening above. It now passes resolve=False when a tor_proxy is set (Tor can't route to an internal address anyway, so literal-IP internal targets are still blocked without resolving). The guard also refuses non-http/https/file/about/data schemes (chrome://, view-source:, ftp://, …) and fails closed on an unparseable URL. The prior --disable-features=WebRtcHideLocalIpsWithMdns flag was REMOVED — it turned OFF the local-IP-hiding feature (backwards); keeping the feature on hides 192.168.x.x from page JS.

In-sandbox request interceptor: redirects, subresources, file:// & DNS-rebind

The host-side guard only vets the initial URL, but inside the sandbox's own network namespace a navigated page can still 302-redirect to an internal address, pull an internal subresource (blind SSRF via <img>/<iframe>/fetch), or re-navigate via the .last_url sidecar — none of which Chromium re-vets. The runner therefore installs a Playwright request interceptor (_install_ssrf_guard → ctx.route("**/*", …)) before any navigation, so it covers the very first goto and its whole redirect chain. Its decision (_ssrf_should_block) enforces three rules; a failed route call degrades to continue so a guard bug can't brick every navigation.

  • Internal host string (2026-07-04). Any http(s) request whose host is an internal target — loopback, RFC1918, link-local 169.254/16 (incl. cloud metadata 169.254.169.254), reserved/multicast, or a known local name (localhost, metadata.google.internal) — is aborted with blockedbyclient (classifies the host STRING only, so no DNS query, no Tor leak).
  • file:// container-read (residual, 2026-07-07). file:// renders self-play fixtures, but under host mounts a file:///etc/passwd — or any path above the mount, including ../ escapes and symlink hops — is a container read outside the sandbox subtree. The interceptor now allows file:// only when its resolved real path (os.path.realpath) stays within sandbox_root — the mount that holds the profile dir, i.e. /workspace, derived as os.path.dirname(profile_dir). Containment is checked component-wise with os.path.commonpath (so a sibling like /workspace-evil is not confused for the root), and an unresolvable path fails closed. A file:// inside the subtree (every project-scoped fixture, after _resolve_file_url healing) still passes — the check does not over-block.
  • DNS-rebind re-resolution (residual, 2026-07-07). The host-string check can't see a name that was vetted while pointing at a public IP but later re-resolves to an internal one (a rebinding subresource/redirect host). In non-Tor mode only, the interceptor re-resolves each request's host (_resolves_internal → getaddrinfo) and aborts if any resulting IP is internal — the same policy as url_ssrf_reason. Over Tor (anonymous, a proxy is set) the lookup is skipped: DNS happens at the exit node, so a local resolution would both leak the query and mean nothing, and Tor can't route to an internal address anyway. A resolution failure fails open (a transient resolver hiccup must not brick a legitimate fetch), and a literal internal IP is still caught by the string check without any DNS. Both residual fixes are covered by tests/test_browser_ssrf_residual.py; the original interceptor by tests/test_bughunt_browser_ssrf.py.
  • Supervised-service allowlist (2026-07-11). An explicit-loopback URL (127.0.0.1 / localhost / ::1 literal — no DNS involved) whose port belongs to a service the agent itself started via manage_services is admitted by BOTH guards (host-side _browser_blocked_url and the runner's _ssrf_should_block via the op payload's allowed_local_ports, sourced from the service registry — see sandbox.services). Without this, the agent could host an app but never drive it. Every other loopback/internal target keeps the pre-existing block, and the allowlist never opens non-loopback private hosts. Covered by tests/test_sandbox_services.py.
  • WebSocket blind spot (KNOWN RESIDUAL, documented 2026-07-14). Playwright's ctx.route() does not intercept WebSocket connections, so the request interceptor above cannot vet ws:///wss:// targets. Exposure analysis: over Tor with no supervised service, loopback ws:// goes through the SOCKS proxy, which can't route loopback → dead. But when a supervised service is running, the <loopback> proxy bypass opens direct loopback for ALL ports and the interceptor's port-level gate doesn't apply to WebSockets — a malicious page could then open ws://127.0.0.1:<any> (e.g. a local dev socket). Same in non-Tor mode. Mitigations considered: Chromium has no "disable WebSockets" flag, and per-port bypass lists are ignored (see _proxy_bypass_for_ports). Accepted as residual risk: the window requires the agent to browse a hostile page while hosting a service, and loopback WS targets on this box (Tor control is cookie-authed) don't accept unauthenticated writes. Revisit if Playwright gains WS routing.

The proxy host MUST be excluded from the MAP * ~NOTFOUND rule. The rule maps every hostname to a non-existent address to defeat DNS leaks — but it also catches the proxy server's own host (e.g. 127.0.0.1), so Chromium can't resolve/reach the SOCKS proxy and every navigation dies with net::ERR_PROXY_CONNECTION_FAILED. EXCLUDE localhost does not cover the 127.0.0.1 literal. _chromium_args therefore parses the proxy URL and appends EXCLUDE <host> for whatever host it uses (an IP like 127.0.0.1 or a name like host.docker.internal). This was a silent, total break of browser-over-Tor — every navigate returned a bare runner exit 1 until the failure-cause was surfaced to the stream (see below) and the missing exclude was found. Regression-guarded in tests/test_browser_tool.py.

Chromium only accepts the socks5:// URL scheme. If the caller supplies socks5h:// (some repo helpers do, for httpx compatibility), the tool auto-rewrites — DNS-over-proxy is enforced via --host-resolver-rules regardless of URL scheme.

Navigation milestone over Tor: domcontentloaded by default

The full load event waits for every subresource — images, fonts, analytics beacons, long-poll sockets. Over a slow Tor exit those frequently never settle within the timeout, so a page that had already delivered the content the agent wanted would raise a Playwright TimeoutError and the runner would exit 1 (the classic navigate: runner exit 1). So _build_op_payload now applies a proxy-aware default: when a proxy is set and the caller hasn't pinned wait_until, it defaults to domcontentloaded (the HTML-parsed milestone) instead of load. An explicit wait_until always wins, and without a proxy (e.g. a local file:// fixture) the runner keeps its own load default. For SPAs that paint after DOMContentLoaded, pass an explicit wait_until="networkidle" or use interact with a wait_for_selector. Covered by tests/test_browser_tor_diagnostics.py.

The proxy decision uses the URL actually dialed first 2026-08-19

resolve_egress_proxy is fed the URL the runner will actually dial first, not the top-level url. For interact the runner navigates to actions[0]'s goto target before the top-level URL, so a loopback top-level URL with a public first goto previously yielded proxy=None and would have launched Chromium cleartext against the public host. The decision now runs through the same _runner_first_url resolver the SSRF pre-flight uses, so both guards agree on which URL is judged. Latent before the fix (the sole caller always threads a live Tor proxy and --mandatory-tor aborts boot on a dead one), but a live deanonymization leak for any in-process caller running with tor_proxy=None. Pinned by an executed test in test_browser_service_proxy_bypass.py.

Runner protocol

A tiny script .browser_runner.py is written into /workspace on every call and invoked as python3 .browser_runner.py <op_json>. It emits exactly one sentinel line:

[BROWSER_OK] {...json payload...}
[BROWSER_ERR] <message>

The tool scans stdout for the sentinel so Chromium's unrelated warnings (GTK, ALSA, libpci) don't corrupt the result.

Return shape

Human-readable, deterministic per op, so downstream prompts can pattern-match:

--- BROWSER RESULT ---
STATUS: OK
OP: navigate
URL: https://example.com/
HTTP_STATUS: 200
TITLE: Example Domain

JS diagnostics: console + uncaught exceptions (2026-06-07)

Every op routes through _with_context, which now attaches two Playwright listeners to the page before running the op: page.on("pageerror", …) (uncaught exceptions) and page.on("console", …) (console messages). The captured js_errors and console lists are merged into the op's result dict (only when non-empty) and rendered for the agent by _format_js_diagnostics.

Why this exists. Before this, the tool exposed only navigate / extract_text / screenshot / click — none of which reveal a JavaScript error. A single uncaught exception in an inline script (e.g. TypeError: Cannot read properties of undefined (reading 'y') from a player.spawnPos that was never defined) halts init() and leaves a loading screen frozen forever. The agent's only channels — a screenshot of the frozen screen and extract_text of the loader text — cannot distinguish "crashed" from "slow", so it would misdiagnose the crash as a performance problem and burn tens of minutes optimising world-gen that was never the bottleneck (observed: a 43-minute request that rewrote the file six times without ever fixing the actual one-line bug).

An uncaught exception now appears verbatim at the top of the result, ahead of any page text, so the very next turn can fix the throwing line:

--- BROWSER RESULT ---
STATUS: OK
OP: navigate
URL: file:///workspace/projects/…/index.html
HTTP_STATUS: 200
TITLE: Minecraft Clone
⚠ UNCAUGHT JS EXCEPTIONS (1) — these crash the page silently and are
almost always the real bug; fix these BEFORE assuming a performance/
timeout problem:
  • TypeError: Cannot read properties of undefined (reading 'y')
      at init (file:///…/index.html:132:14)

Caps keep a console.log-in-a-loop page from flooding the context window: uncaught exceptions get the larger budget (_MAX_JS_ERRORS), ordinary console chatter the smaller one (_MAX_CONSOLE_MSGS), and only error/warning console types are surfaced to the agent. _with_context also yields one extra event-loop tick (wait_for_timeout(50)) after the op so a setTimeout-deferred crash still lands. Covered by tests/test_browser_js_diagnostics.py.

Render check + interaction-gated capture (2026-06-09)

The problem. A goto → screenshot with no interaction is blind to content that only renders after the user acts. A WebGL game that loads its world on a pointer-lock click shows nothing but sky in a bare capture — yet the agent, primed to expect a working game, described "✅ terrain, ✅ trees" over an empty frame and the verifier CONFIRMED it (the HUD chrome — crosshair, hotbar — renders without interaction, so the frame looks game-like). A screenshot plus an LLM/vision self-assessment can't catch this; the model grades its own expectation.

Objective render check. After a screenshot, analyze_screenshot_render reads the PNG the runner wrote and reports an un-gameable signal: the most-common colour's coverage and the distinct-colour count (quantised to 5-bit/channel so gradients/anti-aliasing don't inflate it). A near-UNIFORM frame (≥80% one colour and ≤24 distinct colours, or ≤6 distinct colours) is the signature of a blank / loading / sky-only capture. 2026-07-14 tuning: the original dominant-colour-only rule (≥80% or ≤6) false-flagged every white-background TEXT page as BLANK — docs pages are >80% white but their anti-aliased glyphs span dozens of colour buckets, and poisoned evidence cuts both ways (a false BLANK invites the verifier to refute a TRUE "the page renders" claim). Interact screenshots are checked too (2026-07-14): previously only the atomic screenshot op got the render check, so routing a capture through interact silently bypassed the whole apparatus. The verdict is appended to the screenshot result as a RENDER_CHECK line, which the agent — and the verifier, which reads the tool output as EVIDENCE — must reckon with before claiming success:

SAVED: projects/…/screen.png
RENDER_CHECK: UNIFORM (dominant_colour=99%, distinct_colours=8) — this
capture looks BLANK / sky-only / a loading screen, NOT a populated scene.
Any claim that content renders is UNSUPPORTED by this screenshot…

Interaction recipe. screenshot now accepts settle_ms (wait for the first frames to paint) and click_center=true (click the viewport centre to focus/pointer-lock a canvas game before capturing) so the shot reflects what a user actually sees. Both thread through _build_op_payload to the runner's op_screenshot; omitted → absent (back-compat).

Pre-interaction (start-screen) detection. The render check catches a blank frame, but a follow-up run exposed a sharper hole: a game that renders behind a "Click to Play" modal looks colourful (≈66% dominant, ~1400 colours → not uniform), so the agent graded the menu and declared the game "fully functional" — verifier CONFIRMED. The fix is a DOM probe (_probe_pre_interaction, run on both navigate and screenshot): it looks for a visible control whose text matches click to play/start, press to start, loading, etc., and surfaces a PRE_INTERACTION line naming the control. The app hasn't started — the capture is the menu, not the running app — so the agent is told to interact first (click_center=true, or click the control) and re-capture. The visual verifier prompt now REFUTES any "works / renders correctly / fully functional" claim made over a start/menu/loading screen. Covered by tests/test_run_failure_fixes.py.

The render check stopped certifying renders 2026-09-15

The non-uniform branch used to report has_content — the frame contains visual content. That sentence was an assertion this instrument cannot support, and the agent believed it. Live: three screenshots of one Telegram post captured the site's share overlay — a gradient with a three-button pill and nothing else — each scored 13% dominant / 182 colours → HAS_CONTENT, and the turn spent three screenshot+vision rounds re-confirming an empty frame before filing the answer it was looking for as "not obtained".

No pixel statistic separates the two populations. Failure modes surfaced

Interact abort semantics (navigation failures are terminal)

Under the default stop_on_error=False, a per-action failure (e.g. a click on a missing selector) is recorded and the loop continues — useful for "try all these selectors, tell me which matched" exploratory flows.

Navigation failures are the one exception: they always abort the sequence, regardless of stop_on_error. A page.goto(...) that raises (ERR_FILE_NOT_FOUND, ERR_CONNECTION_REFUSED, DNS failure, …) leaves Chromium on an error page; every subsequent click / fill / extract_text would just wait the full per-action timeout for elements that don't exist. Before the fix, a 54-action sequence whose first goto 404'd hung for ~108 minutes (54 × 120 s per-action timeout) before the outer subprocess watchdog killed it.

The fix: op_interact catches the goto exception, records aborted_sequence: True on the result entry, and breaks out of the loop immediately. The agent-facing output gains a banner:

⚠ SEQUENCE ABORTED: goto_failed. Remaining actions were NOT executed
  because the initial navigation failed — page.click/fill/extract on an
  error page would have just timed out one-by-one. Fix the URL and
  retry the whole interact call.

…so the next-turn planner reads the failure as "bad URL, retry the whole interact" rather than misinterpreting it as 53 mysterious per-action selector bugs. The return dict grows two fields: aborted: bool and abort_reason: "goto_failed" | "initial_goto_failed" | None. Non-navigation failures still honour the stop_on_error contract. Covered by tests/test_browser_interact_abort.py (9 cases including initial-goto failure, explicit-goto failure, implicit-nav failure, mid-sequence goto, stop_on_error preservation, and happy path).

One wall-clock ceiling for every call 2026-09-13 §4GI

timeout_ms is model-supplied and was unclamped, and interact multiplied it by the action count; the sandbox exec waited max(60, ms/1000 + 30). A timeout_ms=3600000, or 60 actions at the default 30 s, held _BROWSER_PROFILE_LOCK for up to an hour and queued every other conversation's browser call behind it (execute caps at 600 s). Now one ceiling, _wallclock_ceiling_s() (GHOST_BROWSER_WALLCLOCK_S, default 600, floor 60), bounds three things at their single computation points: the per-op runner budget (_clamp_runner_timeout_ms, kept under the ceiling minus the 30 s slack so the runner always times out before the sandbox kills it), the interact total (same clamp), and the exec timeout (_bounded_subprocess_timeout). An AST enumeration pins that every sandbox_manager.execute in tool_browser passes the one bounded name. Tests: tests/test_browser_wallclock_ceiling.py (a one-hour timeout → ≤ 600 s exec; 60 actions → ≤ 600 s; a normal call unchanged at 60 s; the env override and floor; the runner-before-kill invariant; the enumeration shown to fire).

Round 3: one deadline, shared across retries 2026-09-13 §4GJ

§4GI's "one wall-clock ceiling" was neither single nor a deadline. It clamped the per-action budget and, separately, the exec timeout — so thirty actions at thirty seconds gave a 600 s exec against a 900 s runner, and timeout -k 5s killed the run mid-flow: exit 124, no completion marker, and no way for the model to tell which actions had landed. Both retry sites then re-used the full timeout without sharing it, so one measured navigate issued three 600 s execs — 30 minutes of wall clock for a single tool call. Now one deadline is computed at entry; each exec gets the remaining time; a retry with less than the minimum left is not issued at all and says so; and the runner's per-action budget is the remaining total divided by the action count (floored), so its worst case fits inside the exec window instead of being killed by it. The old pin passed only because it fed the clamped per-op value rather than the production one.

Browser review 2026-10-04 §4LN

Five labelled live probes on pages with known content were all answered right, but two showed costs.

  • A guessed selector burned 3×30 s inside interact, under a STATUS: OK header.
  • A missing h1 was answered with Chromium-install advice.

Over 209 real turns, the browser itself decided only 2 of 21 failures. The defects were in what the result said, which page a url-less op read, and how results were labelled.

  • Successes are declared. Every successful read is a ToolOutcome.ok. The text-only checks (the corpus sniffer, the evidence gate, claim binding) read the browser's own STATUS: OK|PARTIAL|ERROR|BLOCKED header (browser_result_status).     • A navigate records the URL it was asked for before loading, so a failed load never leaves the previous page in place.

    • Browser calls of one batch run in the order written.

Fresh-eye review: the browser and the search→page hand-off 2026-10-14 §4PC

Three independent read-only reviewers (tool, hand-off + loop, runner + sandbox) and a two-week corpus lens. The corpus number that framed the review: of 137 pages that answered 404, 121 (88 %) were addresses the model composed — a path it assembled on a host it had seen — against 16 it had been given; a composed path on a known host 404s 37 % of the time, a given URL 4 %. After a 404 the same host was re-hit 199 times in the same request. Scope, threat model and the probe-vs-live correction are in the journal.

  • The sentinel cannot be forged (CRIT). The host hands the runner a per-call nonce; the frame is [BROWSER_OK:<nonce>] / [BROWSER_ERR:<nonce>] and the parser accepts only that; an error message is flattened to ONE line. A page had redefined document.body.innerText with a getter that threw "x\n[BROWSER_OK] {…forged…}", the unwrapped page.evaluate put the message on stdout, and the parser returned the forged page as a success (verified with the real runner). An AST pin keeps the runner to exactly two stdout writers.
  • One wall-clock budget per op. _with_context runs the whole op under timeout_ms + 5 s (an interact under its total_timeout_ms + 5 s since §4RX); per-step waits used to add up past the exec kill (goto 30 s + probe + click + load 30 s) and page.evaluate had no timeout at all, so a spinning page ended as "runner emitted no sentinel". The outer kill (exit 124/137) is now named in the hint.
  • Network guard gaps closed. Service workers are blocked on the persistent context (their fetches bypass route()); WebSockets go through the same SSRF predicate via route_web_socket (a page reached any loopback port over ws:// while a supervised service was up); a redirect hop to a blocked address — which route() never sees — is detected on the request event and fails the op BLOCKED instead of reading what the hop fetched. Residual: the hop's single request is sent before it is detected; Chromium ignores host:port bypass entries, so <loopback> stays (2026-07-12 measurement).
  • Status on every landing. The implicit first navigation of an interact and a click both keep the document status (initial_goto, status), so a 403 challenge page landed either way is BLOCKED, not OK content.
  • Addresses are given, never composed. Every navigate/extract result ends with LINKS ON THIS PAGE (n) (same host first, 40 max), so following a link is a given address. The loop keeps a per-request provenance set (user text, every tool result); after a COMPOSED address 404s, the next composed address on that host is refused at dispatch with "open a URL from your results or the LINKS block, or search site:host" — a given URL always passes. The browser's description and the loop-breaker's browser steer say the same.
  • A sandbox outage is one designed stop. The [SANDBOX INFRA ERROR] banner returns a rejected outcome (no strike, nothing changed), latched for the request so later browser calls are refused up front — live 769baad7 burned six calls on four weather sites while the daemon was down and the owner got no reply.
  • Smaller fixes. extract_text pages with offset (the result's NEXT line gives the next one) and says when max_chars was capped; a url-less op falls back to THIS conversation's sidecar (.last_url.c<key>), never the global one another conversation or the verifier wrote; a clean load by any op clears the host memo; a bot challenge is one strike (0 of 24 re-hits after a challenge ever loaded); probe requests never write the host memo; the fetch memo files only page-level failures (a missed selector no longer bans the page); hints for ERR_ABORTED (a download), ERR_BLOCKED_BY_CLIENT (policy), ERR_NAME_NOT_RESOLVED, ERR_CONNECTION_REFUSED, the budget overrun and the outage; the system prompt no longer tells the model to test 127.0.0.1:8000 with the browser (the sandbox cannot reach it either); the recovery planner's prompt has its identity and instruction back and the message lists the agent's tools (it had proposed google_search).
  • Accepted as-is: strike accounting that let seven structural failures run under the six-cap (§4HN design, now moot for the browser with the latch and the brake); the shared cookie profile across owner conversations; profile-dir growth (an explicit close clears it); page-controlled stderr volume past the 256 KB cap (needs ~300 blocked subresources).
