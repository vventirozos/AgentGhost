Templates & data-flow (save_as, 2026-07-11)

param_template uses $variable syntax, resolved when the macro is dispatched against a live binding scope: the macro's runtime params PLUS any earlier step's result bound via that step's save_as. Two forms — whole-value ("$page", substituted as-is) and interpolated ("Summarise: $page" / "${page}"). An unresolved name becomes "", never the literal "$var".

Why it exists. Before this, $var resolved only against the initial params, so a step could never consume the previous step's output — "fetch → transform → act on the fetched value" was inexpressible, and every real pipeline had to be driven turn-by-turn by the main model (the biggest structural gap of the 2026-07 feature survey). It also meant the skill-graduation loop minted macros that structurally could not be pipelines.

Rules (enforced at define time by _validate_dataflow — rejected with an explanatory error, never silently degraded to ""):

  • Bindings flow forward only — referencing a name a LATER step produces is an error; so is a step referencing its own save_as.
  • save_as requires mode="sequential" — parallel steps start simultaneously, so no sibling can observe another's result.
  • Two steps may not bind the same name.
  • A name no step produces is a runtime param the caller supplies (the pre-existing contract) — the advertised schema subtracts step-produced names, so the LLM is never asked for a value the pipeline computes itself.

A bound value is capped at MAX_BOUND_VALUE_CHARS (16 KB — larger than the 4 KB per-step display cap, since a downstream step may legitimately need a big fetched body). The binding cap is explicit too (2026-07-14): a truncated binding carries an …[binding truncated…] marker, so a downstream step consuming a cut-off body can SEE it was cut instead of acting on partial data believing it is complete (previously only the display cap was marked; the binding was sliced silently). An optional step that FAILED still binds, so a later step can deliberately inspect the error text. The caller's params dict is copied, never mutated. See Delegation, jobs & pipelines.

Shell steps that need shell variables: base64 smuggling (2026-08-12)

The $var resolver above is a trap for an execute step whose command is a real shell program: every $name is resolved, and an UNKNOWN one becomes "". A retry loop full of $i / $RANDOM / $tag would have each of those shell variables silently blanked. The fix used by the youtube_transcribe macro's download step: keep the script as an authoritative repo file (tools/yt_tor_download.sh) and embed it into the macro command base64-encoded. base64's alphabet ([A-Za-z0-9+/=]) contains no $, so the resolver passes the blob through untouched and substitutes only the genuine $url runtime param; the sandbox decodes and runs it (echo '<b64>' | base64 -d | bash -s -- "$url"). tools/yt_download.build_download_command() builds this, and a test decodes the stored command to assert it never drifts from the script. Tests: tests/test_yt_tor_download.py.

The downloader itself (yt_tor_download.sh) rotates the Tor exit node on every attempt: it folds the attempt number into the SOCKS username so Tor's IsolateSOCKSAuth hands each try a fresh circuit (the same control-port-free trick tools/search.py uses for search reachability) and retries when an exit is rate-limited/blocked (HTTP 429 and friends), backing off between tries and stopping early — with the real yt-dlp exit status — on a genuinely non-retryable error. It also pre-cleans yt_audio.* before downloading, so a leftover file from a prior video can't make yt-dlp skip the download and the transcribe step's stem-resolver can't pick stale audio. This is why a YouTube-over-Tor download now survives the aggressive 429s that a same-circuit retry would just re-hit.

JavaScript runtime (deno). Recent yt-dlp needs a JS runtime to extract YouTube; without one it falls back to a limited client that YouTube answers "Video unavailable" — the wall behind Tor once the 429s are dodged. Of yt-dlp's providers only deno is actually supported here (node — even v20 — bun and quickjs all report "unavailable"/"unsupported", verified 2026-08-12). The script therefore installs deno to /usr/local via the official installer when it's absent — best-effort, gated on apt-get so it never fires on a non-Debian host, and once per container — then passes --js-runtimes deno:<path>. YT_TOR_NO_JS=1 disables it. Note: clearing the JS wall does not guarantee a successful download — YouTube may still gate extraction behind PO-tokens on top of the exit rate-limiting.

The URL is treated as DATA, never code. The resolver substitutes $url by raw string replacement, so interpolating it into a shell command (… "$url") would let a hostile URL like https://x/$(rm -rf ~) command-substitute when the sandbox runs it. Instead the command writes the URL to .yt_url through a quoted heredoc (<<'DELIM'), which bash copies out verbatim with no expansion; the script reads the file and only ever uses the value as a quoted "$URL", rejecting anything that isn't an http(s) URL.

Deploying an update: re-sync the stored macro to the code-owned definition with scripts/sync_youtube_transcribe_macro.py — but run it while the agent is stopped, then start it. The live agent caches the composed-skill registry in memory and rewrites the whole store on any macro save, so a sync applied while it is running is clobbered by the next in-memory save; boot reloads the fresh definition from disk.

Registry

  • Up to 50 skills in memory; persisted to composed_skills.json.
  • On overflow the least-used skill is evicted — but proposed drafts are evicted before any active macro, so a flood of auto-proposals can never push out a macro the user approved or uses.
  • compile_from_pattern(pattern_name, tool_sequence, description, *, status="proposed", execution_mode="sequential") creates a macro from a mined sequence. It defaults to proposed status (see auto-proposals).
  • execute(skill_name, executor_fn, params) dispatches on execution_mode (see below) and returns a result dict with success · results · steps_completed · total_steps · mode.
  • record_usage(skill_name, success) updates counters.

Status: active vs. proposed

The status field gates visibility:

  • active (default for user-defined macros) — advertised to the LLM via to_tool_definitions() and dispatchable via register_composed_skill_runners().
  • proposed — an auto-discovered draft. Stored and listable, but deliberately hidden from the tool catalogue and not dispatchable until the user approves it with manage_composed_skills(action="approve"). This keeps possibly-stale mined macros out of the live tool list until a human signs off.

Execution modes

execution_mode selects how execute() runs the steps:

  • sequential (default) — steps run in order; branch_condition is evaluated against each result to optionally jump into a named branch; an optional=true step that fails does not abort the macro. Best for pipelines where a later step consumes an earlier step's output.
  • parallel — every step is fanned out concurrently via asyncio.gather and all results are collected. Branching is ignored (there is no ordered result to test). A non-optional step failing marks the macro partial/failed but never aborts the fan-out. Best for an independent, read-only bundle like a morning briefing. Bounded fan-out (2026-07-14): a semaphore caps concurrency at _PARALLEL_STEP_CONCURRENCY (4) — most steps land on the single-slot local llama box, and an unbounded 20-step macro would stampede it; excess steps queue and all still run.

Result gating (2026-07-14): _step_result_ok also treats the SYSTEM INSTRUCTION: / REJECTED: prefixes (file_system's hard-failure family — missing params, replace block not found, syntax-regression rollback) as failures. They previously counted as successes, inflating macro success_rate. Prefix-only: a SUCCESS message that merely mentions the phrase mid-text still counts as ok.

Branching (authoring wired 2026-07-14)

A sequential step may declare branch_condition (a substring to match in its result) and branch_target (the name of an alternative step sequence in the macro's branches dict). When the condition matches a successful step's result, execution jumps to that branch, REPLACING the remaining main steps. Total step executions are capped at 64, so a self-referential branch chain can't loop forever.

Previously built-but-unwired: the executor honoured branches, but nothing could author them — define never parsed the branch fields, so the only route was hand-editing composed_skills.json. manage_composed_skills(action='define') now accepts per-step branch_condition/branch_target (both or neither) plus a top-level branches param mapping branch names to step lists (same step shape). Validation enforces: sequential mode only, every branch_target resolves to a defined branch, and branch sequences pass the same _validate_dataflow checks (a branch step may reference main-step bindings — at runtime the branch runs after the branching step). Branch-only $params are mined into the advertised schema. Tests: tests/test_composed_skills_fixes.py.

Per-step result cap

Each step's result body is bounded to MAX_STEP_RESULT_CHARS (4000 chars) by _cap_step_result() before the per-step blocks are assembled, so one chatty step can't blow the context budget when the combined macro output is handed back to the LLM.

Truncation is explicit, never silent. When a step exceeds the cap, the body is sliced and an …[truncated N chars — re-run this step's tool standalone…] marker is appended. The model (and the verifier gate) can then see that content was dropped and re-fetch the step on its own, instead of believing it received the whole result and delivering a short answer.

Regression fixed: the cap was previously a fixed [:1000] slice applied silently. A list-bearing step — the morning_briefing macro's "latest 10 headlines" fetch (well over 1000 chars for 10 items) — was truncated down to ~2 headlines, and the model, with no signal that anything was missing, delivered a 2-headline briefing. Raising the cap to carry a realistic 10-item list and marking any truncation explicitly closes both halves of that bug. Tests: tests/test_composed_skill_step_truncation.py.

Defining a macro: manage_composed_skills

The manage_composed_skills tool lets the agent (or user) declare a named bundle on demand — action ∈ define · run · list · approve · delete. A defined (or approved) macro becomes a top-level tool the agent invokes by name; its steps run and the combined results return for the model to synthesise. run executes an existing active macro by name (see Invoking a macro); list shows active macros and, separately, any auto-discovered proposed ones; approve activates a proposed macro; delete removes (or rejects) one. Macro names must be bare identifiers (they become tool names), and a step may only call a built-in tool or an acquired skill — not another composed skill (no nesting / recursion). No silent overwrite (2026-07-14): define refuses a name that already exists — register() replaces the object, which also resets usage/success stats, so a name typo could clobber a tuned macro; replacement must be explicit (delete, then define). The refusal message leads with the execution path (2026-08-12): for an active duplicate it says "use action='run' or call the tool directly — do NOT re-define" (run first, because run re-verifies dispatchability itself and so stays truthful even for an active-but-shadowed macro), for a proposed one it points at action='approve', and delete is framed only as the replace-my-definition recovery — the earlier delete-first wording steered a run-intent model into deleting an active macro it merely wanted to invoke. Check order matters: the duplicate check runs before the built-in shadow check — the call-time known-tools set already contains every active macro's own registered runner name, so with the shadow check first a duplicate define of an active macro was misdiagnosed as "already a built-in tool… choose a different name" and the guidance above never rendered. Volatile counters (steps/usage) sit at the message tail, outside the pre-flight guard's 80-char normalized-error prefix, so repeated duplicate-defines still key as the identical failure (tests: ::TestDuplicateDefineMessage). The dream cycle's compile_from_pattern path is unaffected (it may refresh its own proposals).

Example — a parallel morning_briefing:

manage_composed_skills(
  action="define",
  name="morning_briefing",
  description="daily briefing: weather, headlines, diagnostics, lessons",
  mode="parallel",
  steps=[
    {"tool": "system_utility", "description": "Weather",     "params": {"action": "check_weather"}},
    {"tool": "web_search",     "description": "Headlines",   "params": {"query": "latest news headlines"}},
    {"tool": "system_utility", "description": "Diagnostics", "params": {"action": "check_health"}},
    {"tool": "list_lessons",   "description": "Lessons",     "params": {"scope": "today"}},
  ],
)
# → 'morning_briefing' is now a tool. Calling it fans the four steps out
#   concurrently and returns all four panels for synthesis.

A step's params value of "$varname" is substituted from the macro's own runtime arguments at call time, so a macro can take parameters too.

Invoking a macro (2026-08-12 postmortem)

An active macro can be run two ways, and both land on the same runner:

  • Direct call (preferred) — call the macro by its name like any built-in, e.g. youtube_transcribe(url="…").
  • Management verb — manage_composed_skills(action="run", name="youtube_transcribe", params={"url": "…"}). Runtime inputs may also be passed as bare kwargs; an explicit params object wins on a key clash.
Why the run verb exists. Asked to invoke an active macro, the worker model reached for the management tool with action="define" instead of calling the macro by name — hit "already exists", struck out, then deleted the macro to break the loop and deadlocked (see the guard fix below). The run verb makes the model's instinct correct rather than fatal; it dispatches through the same runner register_composed_skill_runners wires, so there is exactly one execution path. Two supporting changes: the advertised macro schema now marks its mined runtime params required (the weak model was firing the macro with an empty arg set because url read as optional), and the macro's advertised description tells the model to call this tool directly and not to re-define it. Planning-prompt rule 10 (MACRO INVOCATION) states the same contract. Tests: tests/test_composed_skill_run_action.py.
Guard deadlock fixed (Fix B). The pre-flight repeat-failure guard's world-changed reset (core/agent.py, _call_mutated_world) previously recognised only file_system, manage_services, and execute as state-mutating. A successful manage_composed_skills delete therefore did not clear the stale "already exists" block on define, so a model that deleted a macro to escape a loop could never re-create it. The registry-mutating actions define · approve · delete now count as world-mutating, so a successful delete unblocks the subsequently-legal define. run is deliberately excluded (as is the read-only list): a macro can be entirely read-only, so treating every successful run as a mutation would reintroduce the same read-only-probe hole the execute branch's looks_mutating_command discipline exists to avoid — a model could interleave a read-only macro between failing calls and defeat the guard permanently. The predicate was extracted into the pure _call_mutated_world helper so it is unit-testable in isolation.

Auto-discovered macro proposals

The dream cycle mines the agent's own trajectory log (distill/ — ordered tool calls with arguments, across sessions) for recurring tool-call sequences and registers the strongest as proposed macros. The user reviews them with manage_composed_skills(action="list") and activates the good ones with action="approve".

  • mine_recurring_tool_sequences(trajectories, …) (in core/dream.py) finds contiguous tool-name windows (length 2–4) that appear in ≥ min_support distinct trajectories. Failed trajectories are skipped, single-tool repeats and all-meta windows are dropped, and a sub-window subsumed by a same-support longer window is discarded.
  • Each step's params is the most common argument set observed at that position — so an approved macro replays realistic arguments, not an empty skeleton.
  • Dreamer._propose_macros_sync() walks the collector, mines, and calls compile_from_pattern(..., status="proposed") for the top few — skipping any signature already on file so the same sequence isn't re-proposed every REM cycle. Each proposal is surfaced via a pretty_log line and counted in the dream summary ("N macros proposed").

Collector source. The live recording collector is wired onto the context by main.py during lifespan (context.trajectory_collector = TrajectoryCollector(...), under $GHOST_HOME/trajectories, disabled by --no-trajectories). When the dream cycle runs on a context that lacks the live collector (headless / cron, or a context built outside lifespan), _propose_macros_sync falls back to a read-only collector at the same canonical on-disk root, so mining still runs over the recorded corpus — unless --no-trajectories is set, which it honours.

LLM exposure & dispatch wiring

  • to_tool_definitions() renders each active composed skill as an OpenAI-style tool definition (proposed drafts are skipped). Every mined runtime param (a $var the pipeline references but no step produces) is marked required — the macro cannot run without it — and the description tells the model to call the macro directly (2026-08-12; see Invoking a macro).
  • register_composed_skills(tool_defs, context) appends those definitions into the active tool list (called from registry.get_active_tool_definitions) — this is what makes the LLM see the macro.
  • register_composed_skill_runners(tools, context) wires a callable runner per active macro into the dispatch dict (called from registry.get_available_tools) — this is what makes the macro executable. Each runner dispatches steps through build_step_executor, which blocks nested composed-skill calls.
  • After a define / approve / delete, the agent loop calls invalidate_tool_defs() so the macro appears (or disappears) in the very next turn-iteration rather than waiting for the next user message.

Macros persist to composed_skills.json under memory_dir, so they survive sandbox wipes (same rationale as acquired skills).

Audit fixes (2026-07-26)

Mint safety: compile_from_pattern now sanitizes names into legal identifiers (graduation-minted names arrived DOTTED — live: auto.generic.…c73e69 reached the registry in violation of this module's own contract) and NO-OPs when the name already exists — re-graduation of the same candidate used to re-register unconditionally, demoting an operator-APPROVED macro back to "proposed" (vanishing from the tool list) and wiping its stats. register() itself merges-not-demotes as belt-and-braces. Shadowing both directions: composed defs now shadow against the FULL acquired-skill registry, not just the defs routed this turn (routing could filter the acquired def out, advertising the composed schema while dispatch ran the acquired runner). Approve message tells the truth about params: graduation-minted macros carry EMPTY templates (tool order only) — the blanket "params were mined from past calls" claim now only appears when templates exist. Tests: ::TestComposedMintSafety.

2026-07-27 audit fixes

  • Failed steps reported "FAILED — unknown error" (MED, closed). Tools in this codebase signal failure by returning an error string, which _execute_sequential records under result with success=False and no error key — so the formatter's r.get('error', 'unknown error') discarded the actual diagnostic and the model could neither recover nor re-route. The failure branch now falls back to the result body.
  • Invalid macro names could reach the LLM function catalogue (MED, closed). _load and the approve action skipped _validate_composed_name, and the live registry still held a dotted legacy entry (auto.generic.…, status proposed). Approving it would have emitted a dotted function name, violating the module's naming contract and risking native-tools parse corruption for the whole catalogue. Names are now validated on load (invalid entries quarantined with a warning) and re-validated on approve.
  • save()'s mkdir moved inside its try: on a read-only or full volume it raised through record_usage → execute(), discarding a successful macro run's results, contradicting the method's own swallow-and-warn design.
