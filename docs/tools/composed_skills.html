composed_skills (removed)

2026-11-05 §4TA The macro engine is gone: tools/composed_skills.py, the manage_composed_skills tool (define / run / list / approve / delete) and the macros it advertised as top-level tools. The page keeps its file name so old links still work.

What it was

A composed skill, or macro, was a named sequence of tool calls: steps with $variable templates, an optional save_as data flow and branches, run in order or in parallel. A registry file under the memory directory (composed_skills/composed_skills.json) held them. An active macro was shown to the model as a tool of its own, and a runner dispatched its steps.

Why it was removed

Measured on the live store on 2026-11-05:

  • Nothing had proposed a macro since the miner was removed on 2026-10-11 (§4NM). The last proposal was dated 2026-09-16, and the function that minted one (compile_from_pattern) had no caller.
  • 12 proposed macros were never approved and never used.
  • 4 auto-mined macros were active and shown to the model on every turn. Three were never used. One was used 3 times, on the day it was created, with 1 success.
  • No macro was ever defined by hand.
  • The only macro in real use was the code-owned youtube_transcribe (8 uses, 5 successes, last on 2026-10-16), and it was a one-step alias.
  • The tool definitions cost about 1,650 tokens of the roughly 26,700-token cached head on every request: 980 for manage_composed_skills and 668 for the four auto macros (counted with the live tokenizer).

What replaced it

  • youtube_transcribe is a built-in tool. Same name, one required parameter url. Its handler calls knowledge_base(action='transcribe', filename=<url>) and returns that tool's own result (no macro envelope, no 4,000-character step cap). See registry and youtube_ingest.
  • Custom tools are created with create_skill and listed or deleted with manage_skills, as before. See acquired_skills. The news_headlines skill is one of these.
  • A recurring bundle such as a daily report is an owner rule, and the model calls the tools itself. Say: learn this rule: when I ask for my daily report, give me the weather, the news headlines and a health check. See Owner rules.

What went with it

  • the tool definition, its dispatch entry, and the two registration steps in tools/registry.py (register_composed_skills, register_composed_skill_runners);
  • tools/yt_download.py (the code-owned macro definition) and scripts/sync_youtube_transcribe_macro.py;
  • the turn loop's special cases for the tool: the registry-mutating actions in _call_mutated_world and is_mutating, and the tool-definition refresh after define / approve / delete (the refresh after create_skill and manage_skills delete is unchanged);
  • its entries in REPLAY_FORBIDDEN_TOOLS and READWRITE_LOOP_TOOLS, and the rule that dropped every macro from a contained replay;
  • the macro-step deny list (MACRO_FORBIDDEN_STEP_TOOLS);
  • the macros.auto_mined row of the loop-yield report (core/liveness.py);
  • the "Composed skills (named macros)" part of the manage_skills list, and create_skill's refusal of a name that a macro had.

What still holds

  • An old registry file is ignored. composed_skills/composed_skills.json and auto_skills.json, if they are still on disk, are never loaded, shown or rewritten, and nothing creates the composed_skills folder again.
  • The tables that named youtube_transcribe still do: a replay cannot call it (REPLAY_FORBIDDEN_TOOLS), its result counts as outside content (UNTRUSTED_SOURCE_TOOLS), and the failure census counts it as a lookup. Members and coding leaves do not get it (their lists are allow-lists).
  • Containment. The handler of youtube_transcribe calls the knowledge-base tool directly, through the egress-guarded callable. So a restricted tool surface that forbids knowledge_base also forbids youtube_transcribe (restrict_tool_surface in isolation).
  • A model that still calls an old macro name gets the ordinary unknown-tool reply with the list of tools. No code names manage_composed_skills any more; the general rule for a mistyped tool name resolves it to the closest real tool, which is manage_skills. There the macro actions (define, run, approve) are unknown actions and list lists the custom tools.
  • The request kinds that may book a skill run (_usage_is_bookable) moved to tools/acquired_skills.py, the module that still uses the rule.
