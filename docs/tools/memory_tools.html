unified_forget — four-store sweep

forget(target) sweeps four stores in order: disk (sandbox files), vector memory (fuzzy filename match + semantic sweep), the profile, and the knowledge graph. The profile pass is the one users notice, because the profile is injected into the system prompt every turn — so anything it misses keeps being "remembered".

The profile pass now runs in two stages:

  1. Key sweep — exact key match, then word-boundary substring match on keys only (so forget('age') can't wipe a language key). Matched keys are deleted whole.
  2. Value sweep — for every key not already handled, match the values with _value_mentions_target (token/word-boundary aware). A matching scalar deletes the key; matching list items are pruned via ProfileMemory.prune_value, dropping the key/category when emptied.

Stage 2 fixes the long-standing case where a forgotten entity lived as a value (e.g. assets.pets = ["Hanzo the dog", "Mortimer the iguana"]): the key-only sweep never matched forget('mortimer'), so the model kept reporting the pet as owned — often annotated "(removed)" from an earlier soft-delete tombstone the merge semantics left behind. The token-boundary matcher avoids the destructive greedy-substring behaviour the key-only rule originally guarded against. Covered by tests/test_forget_profile_value_sweep.py.

Vector sweep — literal-mention override

The semantic sweep originally deleted a candidate only when its L2 distance fell under a type-dependent threshold (0.8 auto / 0.6 identity). That silently missed facts that name the entity outright — e.g. forgetting iguana left "user previously had an iguana that was removed" in place because the sentence-vs-word distance exceeded the bar. The sweep now also deletes any candidate whose text mentions the target as a word-boundary token, regardless of distance. n_results was raised 10 → 20 so more candidates are examined.

Entity-aware expansion (alias tombstones)

A deleted entity often survives under a synonym: forget('mortimer') can't reach a fact stored under iguana. Before severing graph edges, unified_forget calls GraphMemory.get_connected_entities(target) to pull the target's direct (1-hop) neighbours — mortimer → iguana via a mortimer IS_A iguana edge — filtering generic hubs (user, pronouns). It then runs a literal-mention-only secondary sweep (vector + graph + profile values) for each neighbour, so the alias tombstone goes too without semantic over-reach.

Stopping tombstone regeneration

The deepest cause was a feedback loop: each time the user asked "what pets do I own?", the model answered "you previously had an iguana that was removed", and the smart-memory consolidator (run_smart_memory_task) extracted that sentence back into a positive fact + graph triplet — so the tombstone regenerated itself faster than forget could remove it. Consolidation now drops removal/negation statements: is_removal_or_negation_text() bails before a removal fact is embedded, and is_removal_triplet() filters past-ownership predicates (PREVIOUSLY_OWNED, NO_LONGER_HAS, …) and (removed)-tagged entities before they reach the graph. A removal must delete knowledge, never insert a memory about the deletion. The post_mortem learning pass is also skipped on a forget turn (forget_was_called). Covered by tests/test_forget_hardening.py.

Intent guard on self_play / self_play_loop

Both tools refuse to run unless the current turn's user text explicitly asks for self-play, a practice round, or a training cycle. handle_chat stashes the turn's message on context.last_user_content right after parsing the request body; _user_asked_for_self_play(context) matches a conservative allow-list of phrases ("run self-play", "train until stopped", "practice cycle", "synthetic self-play", etc. — see _SELF_PLAY_INTENT_PHRASES). If the guard trips, the tool returns _SELF_PLAY_INTENT_REFUSAL without invoking the Dreamer. Rationale: the 2026-04-24 webOS incident showed the 30B-A3 model hallucinating "The user wants me to run self-play" 33 minutes into a webOS-building session where the user had never mentioned self-play. The tool description says "Use this EVERY TIME the user asks to practice, train, or do self-play" but that's LLM-side prose — the guard makes it enforceable.

The biological watchdog bypasses this check: phase 3 of _biological_tick calls Dreamer.synthetic_self_play directly, not through tool_self_play, so legitimate background self-play fires unaffected. Covered by tests/test_self_play_intent_guard.py.

Deterministic dispatch on an explicit terminal command (self_play / dream_mode)

Symptom. A bare self play ran the cycle the first time, but every repeat (self play again) printed an identical "Self-play complete…" summary without actually re-running — the trace showed tool=- in the metacog line and a ~126-char text reply, i.e. the model answered in prose and never emitted the tool call. dream_mode (go to sleep, consolidate memories) shares the identical failure mode.

Cause. Two reinforcing priming sources. (1) The direct-from-tool summary bypass (in agent.py, the block that stops terminal tools re-firing 2–3× per ask) persists the cycle result as a plain-text assistant turn with no tool_call. (2) The memory bus then re-hydrates that text as Context: Self-play complete…. So the model's only in-context example says the correct response to "self play" is to reprint that summary — which it dutifully imitates.

Fix. When the user's message is unambiguously a single-cycle terminal command, handle_chat dispatches the tool deterministically at the top of turn 0, before the LLM turn, so the model's indecision can no longer swallow the request. _explicit_terminal_command() is the single routing gate, returning "self_play", "dream_mode", or None:

  • _is_single_self_play_command() requires a command phrase (_SELF_PLAY_COMMAND_PHRASES — a tighter set than the intent guard's, single-cycle only), rejects continuous-loop markers (_SELF_PLAY_LOOP_MARKERS — "loop", "keep ", "until stopped", … which route to self_play_loop, the model's call), and caps length so a long task message that merely mentions self-play is left to the model.
  • _is_dream_command() matches _DREAM_COMMAND_PHRASES ("dream mode", "go to sleep", "consolidate memories", …) under the same length cap. Bare "sleep"/"rest"/"dream" are deliberately excluded — they substring-match prose ("interesting" contains "rest", "daydream" contains "dream"). dream_mode has no continuous-loop variant, so there are no loop markers to exclude.

The dispatch records a genuine tool_call + tool result in history (so any future model-driven turn imitates the tool, not the summary), distills the user-facing summary via _distill_terminal_tool_summary (with the right prefix — "Self-play complete." / "Dream cycle complete."), and breaks the turn loop straight into the post-loop metacog/calibration finalisation (the reading still records domain=memory tool=<name>). A thinking_budget_override == "selfplay" guard prevents any recursion from a self-play solver sub-agent. As part of the dream extension, _distill_terminal_tool_summary also gained an explicit strip for dream's two-clause SYSTEM: SESSION FINISHED. STAND BY. footer (the single-keyword pattern couldn't span the period — the model-driven dream bypass leaked it too). Covered by tests/test_self_play_deterministic_dispatch.py.

Self-play loop internals

  • Cool-off between cycles is adaptive (5–180 s clamped) via FrontierTracker.adaptive_cooldown. Falls back to a 30 s baseline if no tracker is available.
  • The loop task + stop event are stashed on context.selfplay_loop_task and context.selfplay_loop_stop. handle_chat checks these on every user message and sets the stop event — the loop checks it at each cycle boundary and during the cool-off asyncio.wait_for.
  • Between cycles the loop explicitly drains the short-term journal via context.agent.process_journal_queue() so hippocampus doesn't fall behind during long runs. Cheap no-op when the journal is empty.
  • Inside the isolated sub-agent's context, selfplay_loop_* attributes are stripped to prevent the inner solver's handle_chat from tripping the user-message interrupt on the outer loop.

Memory bus pattern

When a MemoryBus is attached, insert_fact calls publish_fact("insert_fact", ...) rather than writing the vector store directly. The bus fans the write out to vector + graph (and other tiers) in parallel, and the dedup-LRU gate prevents re-publishes within a 256-unique-event window.

Audit fixes (2026-07-26)

Findability: transcribe is an alias, and that is the point 2026-08-12

The tool is named for what it STORES, but a model that needs this capability is holding a VERB. It thinks "I need to transcribe", scans the tool list for a transcriber, finds none, and plans a Whisper pipeline — observed live twice: once installing openai-whisper, once producing a four-task project plan whose middle two tasks ("Whisper Transcription", "Knowledge Base Integration") were a single existing tool call.

Presence was never the problem. §4AW measured it: knowledge_base was advertised on all 16 tool-carrying payloads, sat 3rd of 44, and its description already contained "Do NOT write or install transcription code" — at 82% through a 537-character run-on. A guard built on that measurement was reviewed and reverted (it saw only execute(command=…), scanned post-base64, and blocked grep of the repo's own docs). Adding a second prohibition would have repeated a failed experiment.

So the fix is discoverability, on three surfaces the model actually reads:

  • action='transcribe' is a first-class alias of ingest_document (with transcribe_document, transcription, ingest, ingest_file). The action enum is short and always read — it is where a model with a verb in mind looks — so transcribe leads it. An unknown action is still rejected; the aliasing is a fixed map, not a catch-all.
  • The description leads with the capability and carries a worked call. "transcrib" moved from 20% of the text to 1%, and the prohibition is now attached to the positive claim ("this tool IS both of those steps") rather than trailing at 82%. It names what not to build — Whisper, ffmpeg, speech-to-text, transcribe.py — because those are the words that appear in the wrong plan.
  • A planning rule (PLANNING_SYSTEM_PROMPT §8), because the observed failure was a PLAN, not a tool call: a plan may never contain a transcription task or a separate "save it to the knowledge base" task. It deliberately does NOT forbid the download — fetching the media is real work, and yt-dlp genuinely is not in the image.

Tests: tests/test_transcribe_discoverability.py (16 pins, including one that fails if the capability drifts back down the description).

forget is type-scoped: both sweeps (semantic + entity-expansion) queried the nearest-20 with NO type filter, and the literal-mention override deletes regardless of distance — with 96.6% of live rows being ingested document chunks, forgetting a word appearing in a manual silently gutted the document (library index still listed it; content-hash dedup then refused re-ingest), and episode/skill twins were fair game too. Both sweeps now scope {"type": {"$nin": _FORGET_PROTECTED_TYPES}} (document / episode / skill / acquired_skill) with a per-row belt check. Ingest dedup re-check after auto-resolution: the library pre-check ran on the RAW argument, so ingest_document('postgresql-manual') sailed past it, resolved to …pdf, and re-extracted + re-embedded the whole 3k-page manual (hours of CPU, zero effect). Bus reports honored: remember / update_profile / learn_skill no longer discard the publish report — subsystem failures return PARTIAL:. Bare excepts on the recall path no longer swallow asyncio.CancelledError. Tests: tests/test_memory_audit_fixes_2026_07_26.py::TestForgetSweepScoping, ::TestBusPartialReporting.

Splitter corruption (utils/helpers.py, the audit's #1 finding): recursive_split_text dropped whitespace separators on rejoin (found_sep.strip() falsy for \\n/\\n\\n/space), fusing the last word of each line to the first word of the next in EVERY chunk it produced — live: all 7,131 postgresql-manual chunks ("DocumentationThe PostgreSQL…"), degrading embeddings, BM25 token matching, and the passage text the model reads. Separators are now re-attached to every fragment, and chunk_overlap finally applies on the separator path (it only ever worked on the no-separator hard split) — capped at chunk_size//4, because callers can arrive with the overlap clamped to chunk_size-1 (semantic_split_text shrinks the effective chunk size below the overlap for long headers) and an uncapped carry advances one fragment per chunk: quadratic output blowup that spun the test suite for 36 CPU-minutes before the cap. Already-ingested documents remain corrupt until re-ingested — delete + re-ingest to repair. Tests: ::TestSplitterSeparatorPreservation.

An error may only name a parameter the tool accepts 2026-08-28

The user asked the agent to forget a topic. It never happened. The model called knowledge_base(action='forget') with no subject, got back "SYSTEM ERROR: The 'target' parameter is MANDATORY", obediently retried with target='…' — and got the identical error. Every retry after that was byte-identical, until the strike budget ran out.

Obeying the error could not work. target was the name of a local variable inside the dispatcher and a parameter of the inner tool_unified_forget. It was not in the schema, and it was not in the dispatcher's alias chain (filename|fact|content|source|path|topic), so a target= kwarg fell into **kwargs and was discarded before the guard that demanded it ever ran.

Two defects, opposite sides of the same seam:

  • The error named a rejected parameter. _KB_TARGET_ALIASES is now the single statement of what the dispatcher accepts, and _kb_target_or_error performs the lookup and builds the message from the same list it just tried — including the worked call, which is generated from the required parameter's name rather than typed at the call site.
  • The first call was unwinnable too. The schema advertised no parameter that reads as "the thing to forget" — the only legal slot was filename, whose description is about .mp4/.pdf ingestion. The live log shows the model hunting for exactly this and giving up: "The parameters are: action, fact, question, ref, filename. None is obviously 'topic'." forget now advertises target, described in the vocabulary of the job, and filename's description opens by handing off to it.

insert_fact carried the same trap through a different name (its guard demanded 'text') and is fixed by the same helper. 'text' was deliberately not added to the alias tuple: widening the accepted set to match whatever an error happens to say is how a guard becomes a list of exemptions.

What four review lenses changed, and what they falsified

The first version of this fix claimed the loop "cannot be reintroduced by an edit to either half, because there are no longer two halves." That was false, and a reviewer demonstrated it. There was a third half: each call site passed a free-text hint that carried the worked example — the part a model copies. Changing one hint's target= to subject= reproduced the entire live loop with all 19 regression tests green, because the pins scraped quoted lowercase tokens and a hint's parameter appears as bare name='value'. The example is generated from the required parameter now, and the pins no longer scrape: they recompute the message from _kb_tried_names(primary) and assert the rendered string contains it, plus a negative scan that fails on any identifier-shaped token that is not a name the lookup tried.

Four more things the review changed:

  • The message was steering models into a silent wrong write. It enumerated the whole alias tuple, so insert_fact's error offered 'filename' — and a model that obeyed got tool_remember('meeting_notes.md'), storing the literal filename as a permanent fact and returning SUCCESS. Trading a loud loop for a silent wrong write is not a fix. The first attempt excluded the other actions' schema names — which fixed the example and not the property, because source and path are exactly as filename-shaped as the filename that was excluded for being filename-shaped, and were still advertised. The alternatives are gone entirely. They were never what ended the loop — the required name and the worked call are — and a caller already passing a legacy alias never sees this message. The aliases stay accepted; they are simply not advice.
  • The turn loop was telling the model not to obey the error. MANDATORY classifies FATAL, and FATAL appends "PERMANENT ERROR — do NOT retry this tool call". That advice was accidentally right while these errors named unusable parameters; it is exactly wrong now that the recovery is a corrected re-issue. FATAL still holds (a missing argument must not spend the transient retry budget), but an argument error now reads "do NOT repeat it unchanged; re-issue the SAME tool with the argument the error names".
  • The action slot had the same defect. "Unknown action 'delete'" named nothing to switch to, and delete/erase/remove are not in the alias map — so the next guess was another guess. Both action errors now enumerate the valid set, generated from _KB_ACTIONS, which the schema enum is pinned against.
  • action='update_profile' was dispatched but never advertised. Absent from the enum, reading key/value/category which the schema does not carry, classified UNKNOWN rather than FATAL, and — since is_idempotent_setter covers only insert_fact/forget — the one route bypassing the repeat-write guard written for exactly that call. It is a fully advertised tool in its own right, so the branch now redirects instead of dispatching.

The forget flag that failed open

Reviewing the neighbours turned up the twin of a check that had already been healed 160 lines below it. forget_was_called matched args.get("action") == "forget" on the RAW string, over a strict=True parse, while the dispatcher normalises with str(action).strip().lower() and the dispatch site parses with strict=False. So " forget " (the XML argument parser strips only CR/LF), or any raw control character in the arguments, left the flag False while the wipe ran — and that flag is what suppresses smart_memory, post_mortem and the episode write for the turn. The content the user had just asked to delete was re-learned inside the same request. It is now call_runs_a_memory_wipe(), extracted so it can be executed rather than asserted about, biased toward True (a false positive costs one turn of bookkeeping; a false negative undoes a deletion), with a regex backstop for arguments that do not parse at all.

Its two mechanisms — the healed parse and the regex — were at first redundant for every input the tests used, so deleting either one left the suite green. Two cases now separate them: a \u0067-escaped action that only the parse recovers, and truncated JSON that only the regex catches.

Round two: the fixes were the new code

A second pair of lenses reviewed round one's fixes rather than the original defect, on the standing assumption that each round's criticals live inside the previous round's work. They did:

  • The wipe predicate healed the ACTION and left the TOOL NAME raw. It runs ~314 lines before _canonicalise_tool_name, whose alias table maps kb / knowledgebase / knowledge-base onto knowledge_base — its own comment cites knowledgebase as an observed Qwen 3.5 hallucination. Measured through handle_chat with byte-identical arguments and only the spelling varying: the wipe ran in all five, the flag was False in four, and each of those turns queued a smart_memory item carrying the request text and the wipe report straight back into the store just cleared. Three quarters of a fail-open guard.
  • It also did not cover reset_all — a strictly larger wipe (every id in the collection, the library index, the graph) that returns a SUCCESS string, so nothing else stopped the turn's bookkeeping repopulating what it had just emptied. A predicate named for wipes answering False there is a wrong answer in the direction its own docstring calls unrecoverable.
  • The worked call renamed the caller's verb. action was interpolated after alias normalisation, so a model calling action='transcribe' — the verb §4AW added precisely because the tool was un-findable without it — was handed knowledge_base(action='ingest_document', filename='notes.pdf'): its verb renamed back to the un-findable one, with a PDF example for an audio ask. The caller's action is preserved now, and the transcribe path gets a media example.
  • The examples were live writes if copied. fact='The user lives in Athens' stores a plausible fabricated profile fact and returns SUCCESS; target='project atlas' runs a real four-store destructive sweep. Both are visibly placeholders now, and a test asserts it.
  • Two thirds of the argument-error pattern were unreachable (only MANDATORY classifies FATAL, and the split was consulted only there) while its comment claimed otherwise — so the one live message it was written for, update_profile's "'key' is a required argument", never got it. The split now covers every non-retryable class. And the redirect no longer says "call update_profile instead": that tool is disabled for subagents, self-play and dream, where the advice bounces the model between two differently-signed errors so the same-failure breaker never fires and the strike budget drains.

Round three: the second implementation of one decision

Round two's tool-name fix was itself only three quarters done. The predicate re-implemented the dispatcher's name healing — alias table plus a difflib pass at cutoff 0.85 — while _canonicalise_tool_name matches at 0.70 against the whole tool list. Everything in the band [0.70, 0.85) therefore healed at dispatch and not in the predicate: measured through the real batch dispatcher, knowledge, knowledge_db, knowledgedb, knowledge_bank, knowledge_store, knowledge_base_query and know_base all routed to knowledge_base and ran the wipe with the flag False. The comment justifying the tighter cutoff ("keeps this from swallowing other tools") was measurably false. Two implementations of one decision drift by construction, so the predicate now asks the dispatcher's own question — and a pin runs both over every advertised name and every mangling and asserts they agree. is_mutating and is_idempotent_setter, two lines away, had the same split: they healed the ACTION and read the RAW name, so two identical knowledgebase ingests were classified read-safe and dedup-collapsed, dropping a real ingest — the exact defect their own comment says was fixed, reached through the other half of the identity.

And the newest edit had made its own bug. The blank-subject check computed val.strip() to decide the subject was present, then passed the padded original on — and tool_unified_forget strips in only three of its six uses. So target=' atlas ' (the normal XML shape: that parser strips CR/LF, not spaces) skipped the disk and document sweeps, left atlas.md and atlas.pdf in place, and reported every stage with a ✅. The subject is normalised once, at the boundary, now. A non-string subject — target=['project atlas','mortimer'], a plausible shape for "forget X and Y" — was likewise waved through: the vector and profile sweeps raised and were swallowed, the graph sweep "succeeded" against the repr, nothing was deleted, and the turn was booked as a clean success. It is refused with an obeyable error now.

Tests: tests/test_kb_missing_param_names_accepted_param.py and tests/test_forget_flag_and_argument_error_context.py — 56 test functions, 128 cases. A 50-mutant whole-file run kills 49, covering every escape the reviewers demonstrated: a parameter name smuggled into a hint, a camelCase alias the old scan could not see, a retry-flavoured word in a hint flipping the message out of FATAL, a live example value, the caller's verb overwritten, either half of the wipe predicate deleted, the tool-name healing removed, reset_all dropped from the wipe set, a whitespace subject stored. The one survivor is the stated limit below.

The stated limit. A hint that names a field in bare prose — no =, no quote, no separator character, e.g. "…or use the subject field" — is caught by nothing, because that is indistinguishable from English. The message still carries the generated worked call, which dominates bare prose as a copy target. Everything that renders as a callable fragment is stripped at runtime and pinned.

Left open, deliberately (pre-existing, out of this change's scope, reported to the operator): reset_all materialises the whole vector store and runs its deletes on the event loop, and drops episode/skill/document rows that _FORGET_PROTECTED_TYPES exists to protect; and tool_unified_forget's disk sweep deletes every sandbox file whose name contains the target as a substring, so forget('atlas') unlinks atlas_migration_plan.py.

The follow-on list, taken 2026-08-28

forget deleted files the caller never named. The disk sweep ranked candidates exact → stem → substring and deleted every member of the first non-empty tier. Measured: forget('atlas') unlinked atlas_migration_plan.py, notes_about_atlas.md and sub/deep_atlas_notes.txt — irreversible, model-reachable in one call, no dry-run. The section above made the pressure worse by describing target in the vocabulary that feeds this branch hardest ("a topic, an entity, a person's name"), because a bare word matches far more filenames than a filename does. Forgetting a TOPIC is not a licence to delete every file whose name shares a token with it; the vector, profile and graph sweeps remove the knowledge either way. Substring hits are reported as candidates and left alone — naming one makes it an exact match, and it is deleted.

reset_all stalled the loop and hid what it orphaned. collection.get() with no include pulled every document body back (live: ~8k rows, 7k of them manual chunks) to use nothing but the ids, and it and every delete batch ran synchronously on the event loop — while the cheap graph wipe was already offloaded. Both are in threads now, asking for ids only. It also deletes the document / episode / skill rows _FORGET_PROTECTED_TYPES exists to protect, because each has a record in another store it does not touch: it says so now instead of returning a clean "Wiped clean".

Three of eight name-keyed decisions had been healed; five had not. Still reading the raw tool name in the same block: is_sandbox_mutation (an fs write left the workspace cache stale), the empty-content write block (bypassed by fs), the dedup hash (kb and knowledge_base with identical arguments never matched each other), disabled_tools, and the skill-store guards. The name is resolved once at the top of the block now and the dispatch reuses that value, so the name every guard is keyed on is provably the one that executes. The general pin is an AST scan: no comparison of the raw name against a real tool may appear before the rebind.

"Did you forget a required argument?" told models to ADD when they had to REMOVE. Model arguments are splatted unfiltered into a lambda that already supplies the tool's context, so knowledge_base(action='forget', model_name='x') returned "got multiple values for keyword argument" under that banner — the same class as the loop above, at every tool. describe_invocation_error names the offending argument and says to drop it.

Two of these pins were vacuous when written. The mixed-turn preview test recomputed the budget — 300 if is_argument_error(err) else 140 — and asserted against its own arithmetic, so a mutant that cut the budget to a flat 140 and one that widened every preview to 300 both passed it. Worse, the headline disk-sweep test passed on the pre-fix code: its fixture created atlas.md, a STEM hit, so the or chain short-circuited and the substring tier it was written to exercise was never reached — the old code kept those same three files for the same reason. One of four disk tests discriminated.

And the _cname hoist opened a defect going the other way: the alias table was consulted before the exact-name match, so an acquired skill legitimately named fs resolved to file_system and one of the newly-keyed guards blocked it — which in turn surfaced that profile_update had been a dead alias key since the day it was written, because lookups are normalised and that key is not.

22 mutants, 22 killed, no anchor misses.

The review of the follow-on list 2026-08-28

The report told the caller to do the thing that deletes their files. The disk sweep matched on BASENAME while the kept-report printed candidates as sandbox-relative PATHS and said "forget it by the exact name shown here". Following that instruction deleted every file in the tree with that basename — including candidates the report had listed separately. One target, five sweeps, one rule 2026-08-29

forget runs five sweeps — disk, ingested documents, semantic vector, profile (keys and values) and graph. Diffed mechanically against each other rather than read in turn, they were five tools wearing one name.

clean_target normalisation (stripping ./, a leading / and a sandbox/ prefix) reached the disk and document halves only. So forget('./notes.md') and forget('sandbox/notes.md') deleted the file and the document and silently skipped the semantic, profile and graph sweeps entirely — and the report never said the knowledge half had not run. sandbox/ is documented elsewhere in this codebase as an observed live model shape.

The ambiguity gate was disk-only too, so a single report printed "kept 3 file(s) … Nothing on disk is deleted for a partial name match" directly above three "✅ Vector: Wiped document" lines naming the same three files — the irreversible half ignoring the policy the other half had just printed. And the gate covered only the exact tier: forget('index.html') refused three files while forget('index') — five characters shorter — unlinked five, through the stem tier the gate never inspected.

All five sweeps read one normalised target and one gate now. The gate keys on how many directories the matches span, not how many files: notes.md and notes.txt in one directory are the stem tier doing its job; five index.html files in five projects are five different things wearing one name, and the caller cannot have meant all of them.

A refusal is not a world change 2026-08-29

file_system answers a malformed mutating call with "SYSTEM INSTRUCTION: you used operation='replace' but forgot 'replace_with'" or "REPLACE REJECTED (byte-identical)". Neither matched any failure predicate, so a call that changed nothing was credited with changing the world: every recorded pre-flight failure cleared, the loop-breaker's memory wiped, the strike count decremented — a run of rejected replaces erases the strikes earlier failures earned, so the cap can never fire — the file marked modified in the work log, and the foresight model taught that the call succeeds. 63 live occurrences across 36 requests.

Separately, op_outcomes.ok did not know about EXIT CODE:, so the MULTI-STEP OUTCOME line — the one message in the loop that tells the model "this live outcome is AUTHORITATIVE over any prior context" — reported a command that exited 127 as SUCCEEDED, in 15 live turns.

Both are fixed behind result_is_rejection, deliberately kept separate from result_is_failure because the skill success-rate readers exempt steering instructions on purpose.
