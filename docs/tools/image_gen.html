tools / image_gen.py

Image generation routed to the external GPU node (ghost: Qwen-Image-2.1 via stable-diffusion.cpp since 2026-09-22).

Tool: image_generation

Auto-registered when context.llm_client.image_gen_clients exists.

  • Heals missing prompt by checking related kwargs (image, description, subject, text).
  • Omits steps unless the model set it (the node's tuned default, 30, wins); an explicit value is clamped to [15, 50].
  • Passes the requested size THROUGH untouched — the node owns geometry. It searches 246 legal sizes (multiples of 32, as sd.cpp requires for this model, within a 768×512 pixel budget) for the closest match inside a log-space aspect band, so 1920x1080 renders 736x416 (0.5% aspect error) and 2560x1080 renders 768x320 (1.3%). If no size is given the tool sends none and the node uses its default, 768x512. Until 2026-09-22 the tool first snapped to a five-entry ladder (512x768, 576x672, 608x608, 672x576, 768x512) — an SD1.5-era habit from when the node could only scale and clamp. It threw away precision before the node's search ever saw the request: 1920x1080 became 768x512, 15.6% off, and 2560x1080 was 36.7% off. _snap_to_bucket, _NODE_BUCKETS and _DEFAULT_BUCKET are deleted; tests/test_image_gen_model_swap.py and tests/test_image_gen_node_retune.py assert they cannot come back.
  • Passes seed and negative_prompt through when given (the negative only matters if the node runs with CFG on, which it does not by default).
  • Editing (reference_images, one filename on this node): resolves the sandbox file the model names in any of the spellings it uses (gen_x.png, /gen_x.png, /sandbox/gen_x.png, the /api/download/… link it was shown), refuses anything outside the sandbox or missing before calling the node, sends it base64, omits the size so the edit keeps the reference's shape, and reads the actual size back from the returned PNG for the SUCCESS note. Synonyms the model hallucinates (reference_image, input_image, source_image, …) are healed. An edit takes ~11 minutes (the node runs guidance for edits, without which the instruction is ignored) and costs some fine detail to the VAE round trip, so the tool result tells the model to re-attempt at most once and never to chain edits.
  • Calls llm_client.generate_image({"prompt", "width", "height", …}); the transport allows 20 minutes — one image takes ~3.3 minutes on the node, and no tool-level timeout wraps the call.
  • Decodes base64 PNG, writes to sandbox as gen_UUID.png.
  • Returns a markdown embed with a short alt text (![generated image](/api/download/gen_UUID.png)) — the giant raw prompt is deliberately kept out of the alt text.
  • Instructs the model to follow the embed with one or two short sentences describing what it generated, in its own words, so the user always gets a human-readable caption instead of a bare link.

A real person's likeness comes from pixels (§4JX)

Asked to put the Greek prime minister in space, the agent searched, downloaded a photo into the sandbox, ran vision_analysis describe_picture on it — and then called image_generation with a text prompt and no reference. The node logged refs=0 and returned a generic dark-haired man in an astronaut suit. The model cannot draw a likeness from a name or from a caption, however detailed, unless that person is saturated in its training data.

The cause was the advice, not the model: reference_images was described only as EDIT MODE … change an EXISTING image, so "put this person in space" never read as an edit. The description and the system prompt now state that a specific real person (or product, building, pet) must come from a photo, that a name or description yields a stranger, and that looking at a photo with vision_analysis is not passing it. With the same request afterwards the agent reached for the reference in 13 s (refs=1) and the result is recognisably him. Pinned in tests/test_image_gen_model_swap.py — asserting the claim ("must pass a photo", "never from a name", "generic stranger"), not the topic word, because a first draft of those pins passed against a mutant that replaced the steer with its opposite.

Acquisition was the weak link, and the cause was guessing. In that run the agent never obtained a usable portrait: it hand-built Wikimedia thumbnail URLs, and only some widths are pre-rendered — 800px-… and 640px-… return HTTP 400 while 500px-… returns 200 — so it fell back to screenshotting the Commons page, a 1280×2290 picture of a web page. It was never a Tor or host problem: the URL the page itself declares in og:image fetched 200 over Tor from both thumb. and upload. hosts. Fixed in the browser tool (§4JY): navigate and extract_text now return MAIN_IMAGE, a ready-to-download URL, with MAIN_IMAGE_SOURCE saying whether it came from the site's own og:image or from a rendered-size guess. See browser.

What the model is told (2026-09-22 swap)

The tool description and the system prompt teach the new backend's contract: write the prompt as natural-language prose in any language (Greek works); put text that should appear in the image in double quotes (it renders legibly); do not use A1111 attention-weight syntax — the model's text encoder is an LLM and would read (x:1.2) as literal characters (the old SD1.5 node parsed it; the new node flattens it defensively); and one image takes 3–4 minutes, so call the tool once and wait. The self-correction loop now ends in an edit: look at the wrong image with vision_analysis, then call image_generation with reference_images and a prompt that describes only the change. Transparency is deliberately not offered — the backend cannot deliver it yet (see the server page). The old advice — attention weights, 624×624 squares, "SD1.5 DreamShaper" — is gone from tools/registry.py and core/prompts.py; a pin fails if it comes back.

Backend, memory phasing and the Tegra allocator trap: image-gen server.

2026-07-14 audit fixes

  • The SUCCESS message states the actual output size. The node can render a size other than the one asked for, but that was only logged for the operator — so the model told the user it had generated the requested size, or re-called the tool trying to "fix" a size the node had chosen deliberately. The message now reads Rendered at WxH (you asked for …). Superseded 2026-09-22: the reported size is read from the node's authoritative width/height response fields, falling back to the PNG header and only then to the request — echoing the request could state a size the node had overridden, as fact, to the user.
  • The sandbox dir is created before the write. A fresh project scope may not have created the dir yet; without the mkdir a FileNotFoundError discarded an image the GPU node had already spent minutes producing. Covered by tests/test_tools_batch_audit_fixes.py.

No second image blind 2026-09-24 §4KJ

Four Slack requests (slack-e6…, slack-3e…, slack-15…) generated a SECOND image — ~200 s of the image node each — without ever looking at the first: the model reinterpreted the ask between turns and re-rolled. The result's "Respond DIRECTLY to the user" lost every time; prose loses to a re-read of the ask. The rule is mechanical now, at dispatch next to the §4KD clarify-first block (core/agent._blind_regeneration_block): a second image_generation in one request is REJECTED (reason blind_regeneration) until the earlier output — read off this tool's own SUCCESS line — was inspected with a vision_analysis call the node ANSWERED (the call read off the assistant rows' tool_calls, its result matched by tool_call_id; an empty or cap-hit answer is not a look). The user's words never decide (a multi-image ask regex was built and removed — it misclassified a third of realistic asks in two languages); a verifier repair may regenerate, and a second image in the same batch is always blocked. The block names the file and the ways out. With the vision caption fixed on the same day (no-think for every action), "inspect first" is once again a ~4 s call rather than a 44 s empty one. Pins: tests/test_blind_regeneration_guard.py.

The seed line is information, not a next action 2026-09-24 §4KD

The SUCCESS result used to end with "Seed: N. Reuse seed=N with a tweaked prompt for ANOTHER TAKE …". A tool result is read at the moment the model decides what to do NEXT, and on 2026-09-23 a Slack member's unintelligible follow-up (emp1) after an image turn resolved into exactly that action — a second image nobody asked for (the instrument-teaches-the-agent pattern). The result now records (Seed N — a record for reproducibility; the result is saved and this request is complete.) and suggests nothing. The measured facts — same seed + tweaked prompt = a different composition; only an edit keeps THIS picture — moved to the seed and reference_images parameter descriptions, which the model reads when it CHOOSES an action, ending with "Never re-run the tool because a result mentioned a seed." Paired with the clarify-first guard in the turn loop. Pins: tests/test_4kd_clarify_first_and_slack_lessons.py, tests/test_image_gen_model_swap.py.

The pipeline review — tool and client 2026-09-24 §4KD

Two fresh-eye reviewers (agent side; node side) over generation AND edit. Agent side, fixed and pinned in tests/test_4kd_image_pipeline_review.py: the client threw the node's detail away on every HTTP error (a 400 "reference image 0 is not a PNG/JPEG/WEBP" reached the model as "400 Bad Request" and an MDN link — _node_error_detail is used now); every 4xx was retried three times (a 413 re-sent a 16 MB body thrice) and a read timeout was re-posted while the node was still rendering that very job — only node faults (503, connect errors, other 5xx) retry now; the schema said "LONG prompts are fully used" while the node 400s above 8,000 characters — the tool truncates at the node's cap and SAYS so; a list prompt went to the node verbatim, an int crashed the log slice, whitespace burned a render — text in, text out; a 0-byte or non-image reference crossed the LAN to be refused — magic-checked here; reference_images=[] plus a synonym silently ran a plain generation; negative sizes passed through; a boolean seed became 1; the rendered steps are reported ("Rendered at 768x512 in 30 steps"); and the clarify-first guard's link fallback missed project-scoped links. One pin in test_image_gen_model_swap.py had gone vacuous with the §4KD seed wording.
