Vector-store deletion uses $and (2026-07-26)

Chroma rejects flat multi-key where filters with "Expected where to have exactly one operator" — multiple conditions must be wrapped in {"$and": [...]}. Both delete_skill and retire_degraded_skills passed where={"name": ..., "type": "acquired_skill"}, so the vector-store cleanup never worked: manual deletes logged the warning the operator saw, and the retirement path swallowed the error silently (except: pass — now logs a warning instead), leaving stale skill embeddings behind on every delete/retire since inception. Fixed to where={"$and": [{"name": name}, {"type": "acquired_skill"}]}, matching the pattern already used in memory/skills.py. Regression tests capture the filter passed to the (mock) collection and run it through chromadb.api.types.validate_where, so a mock can never again accept a shape real Chroma rejects — tests/test_acquired_skills.py::test_acquired_skill_manager_delete + tests/test_acquired_skill_retirement.py::test_retirement_with_vector_store.

Orphan back-fill: embeddings stranded by the broken deletes have no registry entry left, so no per-skill path can ever clean them. purge_orphaned_skill_embeddings() reconciles the vector store against the registry (vector snapshot taken FIRST so a concurrent save_skill — registry write, then embed — is never misread as an orphan) and deletes orphans by id. Wired into tool_manage_skills next to the retirement sweep. Orphans never advertised phantom skills (semantic routing filters candidates against the live registry) but they crowded the routing query's n_results=15 slots. Tests: tests/test_acquired_skills.py::test_purge_orphaned_skill_embeddings* + ::test_tool_manage_skills_sweeps_orphaned_embeddings.

Duplicate embeddings per skill (2026-07-26, same-day follow-up)

Live symptom: the routing log said "injected 3: news_headlines, news_headlines, …" while manage_skills correctly listed 2 skills. The registry is one-entry-per-name and authoritative; the routing line counts vector-store hits. save_skill embedded the description on every content change but never removed the previous embedding for that name (the content-hash dedup only stops re-embedding of identical content), so each edit of a skill permanently added one more embedding — confirmed in the live store: two news_headlines rows minted 3 minutes apart with slightly different descriptions. Harmless beyond logs and slot waste: the advertising loop iterates the registry with a membership check, so a duplicated skill was never offered to the model twice.

Three-part fix: (1) save_skill now deletes the name's existing embeddings (working $and filter) before adding the fresh one — an edited skill holds exactly one routing slot; (2) the manage-time sweep also collapses same-name duplicates, keeping the embedding whose document matches the registry's current description (fallback: newest insert) — back-fills stores polluted before the fix; (3) the semantic-routing candidate list in registry.py is deduped order-preserving, so "injected N" counts distinct skills even if stale rows exist. Tests: tests/test_acquired_skills.py::test_save_skill_replaces_previous_embedding, ::test_save_skill_unchanged_content_skips_embedding_churn, ::test_purge_collapses_duplicate*; tests/test_registry_skills.py::test_get_active_tool_definitions_query_dedupes_duplicate_embeddings.

Skill-name validation (path-traversal guard)

Skill names are used as bare filenames (<skills_dir>/<name>.py) AND as registry keys visible in the tool catalogue shown to the LLM. They must therefore be pure identifiers: no separators, no traversal, no punctuation.

Prior behaviour wrote to the resolved path with no validation. A name like "../../pwn" escaped skills_dir — confirmed exploitable: save_skill(name="../../pwn", python_code="...") wrote the payload to the sandbox's PARENT directory on disk.

Fix: _validate_skill_name(name) enforces ^[A-Za-z_][A-Za-z0-9_]{0,63}$ before any filesystem write. Belt-and-braces: the resolved skill_path is ALSO checked against skills_dir.resolve() so any future regex widening can't silently re-open the hole. Invalid names are rejected via pretty_log("Skill Rejected", ...) so reflection can learn to use identifier-shaped names. Covered by tests/test_acquired_skills_name_traversal.py (20+ bad shapes rejected, 8 good shapes accepted, full FS escape probe, boundary + belt-and-braces doc assertion).

TDD validation

The skill is written to test_skill.py, executed with test_payload as sys.argv[1] (parsed as JSON inside the script). The payload must produce EXIT CODE: 0 with non-empty stdout. A common failure (forgetting if __name__ == "__main__":) is detected and reported with a specific hint.

python_code is normalized at the entry point (2026-04-24). Before writing test_skill.py, tool_create_skill now runs sanitize_code(python_code, "test_skill.py"). This strips CDATA envelopes (<![CDATA[...]]>) that sometimes leak through the XML tool-call parser when the LLM forgets a closing </parameter> tag, decodes HTML entities when they're clearly corrupt (&quot; inside Python source), and extracts code from markdown fences when the whole thing is wrapped. Strips are AST-gated — clean Python is never perturbed. If the body still doesn't parse after normalization, the LLM gets a specific actionable error naming the common causes (CDATA wrapper, HTML entities, truncated stream, escaped-newline JSON confusion) instead of a generic test failure. Without this, the 2026-04-24 in_gr_news session burned 18+ turns re-submitting CDATA-wrapped payloads because the test-phase error was the generic "failed its TDD test" line. Covered by tests/test_sanitizer_cdata_and_entity_leak.py (20 cases) + tests/test_acquired_skills_storage_relocation.py::test_tool_create_skill_normalises_cdata_wrapped_python + …_rejects_unparseable_python_with_actionable_error.

TDD failure cause surfaces in the trace (_summarise_tdd_failure). When the TDD test fails, the pretty_log line no longer reads just "Skill 'X' failed its TDD test." — it appends the one-line cause extracted from tool_execute's output, e.g.:

❌  test failed  Skill 'greece_top_news' failed its TDD test — ValueError: invalid literal for int() with base 10: '{"length": 16}'

Priority order when extracting: (1) Python traceback's last <Err>: <msg> line — most actionable; (2) Syntax Error Detected: / SYSTEM ERROR: surfaces from the sanitizer; (3) the no-stdout sentinel ("script exited 0 but printed nothing to stdout"); (4) first non-empty body line fallback. Truncated to 200 chars. Never raises — pure log-surface polish. Covered by tests/test_acquired_skills_tdd_failure_summary.py (14 cases).

Tool description hardening (LLM invocation)

Acquired skills are registered as top-level callable tools via the registry's make_skill_runner closure. But without explicit guidance, the LLM saw the generic [ACQUIRED SKILL] <desc> label and gravitated to calling execute or python -c to wrap the skill — especially after the storage relocation, which removed the skill's .py from the sandbox listing the LLM could ls. The 2026-04-24 greece_top_news session burned 8 turns flipping between python -c "from X import X", ls /workspace/acquired_skills/, python3 acquired_skills/X.py, and writing an import-wrapper run_news.py before finally calling the skill by name.

Fix: the description now reads (example for a skill named greece_top_news):

[ACQUIRED SKILL — CALL BY NAME] <user description>

USAGE: This IS a top-level tool. Invoke it directly: `greece_top_news(...)`.
Do NOT wrap it in `execute`, `python -c`, or `file_system` — the implementation
lives OUTSIDE the sandbox (in $GHOST_HOME/system/memory/acquired_skills/) so
`import greece_top_news` and `python3 acquired_skills/greece_top_news.py` will
both fail with ModuleNotFoundError / ENOENT. Just call `greece_top_news` the
way you'd call any built-in tool.

Plus an inline--c block heuristic: if the LLM's rejected body looks like a skill-invocation wrap (from X import X where the module and symbol match, or acquired_skills/X.py in a subprocess call), the SYSTEM BLOCK error appends a targeted hint pointing at the canonical X(...) invocation. So even if the LLM's first instinct is wrong, the rejection steers it at the right answer on the retry. Covered by tests/test_acquired_skill_invocation_nudge.py (6 cases including negative tests pinning that unrelated inline-c bodies never get a phantom skill hint).

Storage layout

Canonical storage lives under $GHOST_HOME/system/memory/acquired_skills/ — outside the Docker bind-mount. A sandbox wipe (docker volume rm, rm -rf $GHOST_SANDBOX_DIR, container recreation) no longer destroys learned skills. Execution is still sandboxed: the registry's skill-runner closure reads the canonical file and passes content= to tool_execute, which writes it into the sandbox just-in-time and runs it.

$GHOST_HOME/system/memory/acquired_skills/
├── <name>.py
├── retired/
│   └── <name>.py
└── skills_registry.json   { name: {description, parameters_schema, usage_count, failure_count, status, content_hash}, ... }

Migration: if an earlier install left skills at the legacy path $GHOST_SANDBOX_DIR/acquired_skills/, they're copied over on first AcquiredSkillManager construction when the canonical dir is empty. Idempotent: a second construction with a populated canonical store does nothing. Legacy files are left in place (to be cleaned up manually once the operator confirms the move). Unsafe-named legacy entries (anything the identifier-shape regex rejects) are skipped and logged.

Audit fixes (2026-07-26, second wave)

"Degraded" is recoverable: a success now clears the flag (it only reset the counter before, leaving a permanent zombie — invisible to defs/runners yet unretirable because retirement keyed on the reset counter); a re-create with CHANGED content that passed TDD starts clean (status/streak were carried forward, making the error message's "re-create it" advice a lie); retirement also catches legacy zombie entries by status, and the dead second rule (failures ≥ 5 and usage < 10 — unreachable behind ≥ 3) was dropped. TDD gate parses the exit banner (first match) instead of substring-matching "EXIT CODE: 0" — a failing test whose stdout echoed an inner banner used to pass. Cross-namespace shadow check: create_skill refuses built-in tool names (persisted-but-never-dispatchable, while claiming "LIVE") and composed-macro names (advertise one tool, execute another). Listing is honest: manage_skills(list) marks degraded acquired skills and proposed macros as not-callable. Tests: ::TestDegradedRecovery, ::TestAcquiredResultClassification.

Shared manager instance (2026-07-26, §4B residual)

Every call site constructed a FRESH AcquiredSkillManager, each with its own RLock — so the lock serialized nothing across callers and two concurrent telemetry writes could interleave load→mutate→save, losing a failure_count increment (which undermines degrade/retire). AcquiredSkillManager.get_shared(base_dir, …) returns one process-wide instance per resolved base path (upgrading a cached None memory_system when a later caller supplies one); all four call sites (manage_skills, registry advertise + dispatch, composed-shadow) use it. Test drives 8 threads × 60 increments with zero loss: tests/test_memory_audit_fixes_2026_07_26.py::TestSharedAcquiredManager.

2026-07-27 (later 8) — a skill went invisible, and the prefix cache was primed twice

Two operator-reported symptoms, one root cause: the advertised acquired-skill set.

The tell

One log line, identical on every request regardless of query — including the request whose hydration was literally "news_headlines tool usage":

semantic routing    injected 1: format_results_to_csv

A line that never varies with its input is a constant where a variable belongs. Measuring the two stores explained it: the registry held 3 active skills, the vector store held 1 embedding.

Why the skill was invisible

Routing queries the vector store (where type=acquired_skill) and filters the advertised tool schema by the result, so news_headlines was never in the catalogue the model saw. Everything after that is downstream: the model called manage_skills twice hunting for it, tried to shell out (blocked — inline body 219 chars), tripped the loop-breaker, and had its final answer eaten by the stream scrub.

It could never self-heal. save_skill embeds only when the content hash CHANGES, so once an embedding was lost — the pre-2026-07-26 broken deletes, or an orphan sweep — nothing rebuilt it. The index could only ever lose entries, while the skill stayed active and dispatchable. That is the "invisible-but-callable drift" the routing degrade-paths guard against, reached from the opposite direction.

  • backfill_missing_skill_embeddings() re-embeds any ACTIVE registry skill with no vector entry, wired into the same sweep as the orphan purge.
  • The purge is now fail-safe: an empty registry alongside existing embeddings is treated as a failed read, not as "all skills deleted". Without that, one transient mid-write read wipes the whole routing index unrecoverably.

Why the prefix cache loaded twice

The boot warmup primes the request head via get_active_tool_defs(""). The empty string is FALSY, so routing is skipped and it advertises ALL skills — while every live request passes a real query and gets a SUBSET. The ~22,186-token warmup prefix therefore never matched a single real request, and each request re-prefilled the entire head. (The warmup's own comment claimed it mirrored "the same neutral-query routing a live request's first turn resolves to" — false the moment routing became query-dependent.)

Fixed at the design level rather than by patching the warmup: below _SKILL_ROUTING_MIN_SKILLS (25) every active skill is advertised and per-query routing is skipped. Filtering three skills saves a few hundred tokens once; it costs a full re-prefill of a 22k head on every request. Above the threshold routing still applies. This also makes the tool block byte-identical ACROSS requests — the per-turn stability was already correct.

Verified live: the routing line is now absent (advertise-all = what the warmup primed), and the skill dispatches — turn outcome verified · tools: news_headlines · 804 chars, returning real RSS headlines, no scrub fallback.
