tools / runs.py

The run tool: everything that keeps running after a tool call returns, wherever it runs. 2026-11-04 §4SX Phase C

Status: advertised since the D5 switch 2026-11-04 §4SX D5

Since D5 run is in the model's tool list and manage_services / jobs are not. See the switch below. The Phase C history follows.

Phase C builds run next to manage_services and jobs, which are unchanged. It is not in the model's tool list and not in the dispatcher (design review r1 M2: a different tool list re-prefills the prompt head). The Phase D switch advertises it, adds aliases, moves execute's promotion to job runs and removes the old tools. Until then the only entry is the operator route POST /api/operator/run-probe (probe origin only, refused while a user request is live), used for live acceptance. Design: docs/labs/PHASE_C.md.

Actions

  • start name command where lifetime [port] — where is required (workspace or lab_<8 hex>/<member>; no default). lifetime is job (runs once) or server (keeps serving). app is refused: an app run is made by lab keep (§4SX D3), and run then starts, stops and restarts it by name. A start is never a result: the reply says "Still running: this is not a result".
  • status [name] — every live run, or the newest of that name, probed now from its backend; the probe is written back to the registry.
  • logs name [lines], collect name (a finished job: output plus EXIT CODE; unresolved while it runs), stop name, restart name (servers only; a job is started again), url name.

Where a run lives decides who runs it

server @ workspaceServiceSupervisor (sandbox/services.py)Same lease, token and loopback rules as manage_services. The services key is <project>:<name>; a conversation owner uses c-<sha1(key)[:12]>, so two conversations never share or replace a service (r1 H3). A live service of that key that run did not start is refused, never replaced.
job @ workspaceSandboxJobSupervisor.start_detached (sandbox/jobs.py, new)Starts at once (no budget wait, no progress test), same script, TTL (45 min), cap and re-run guard as a promoted job. The row carries started_via="run": the jobs tool does not adopt it, and its wake names run collect (r1 H1, H2).
job / server @ lablabs host exec detach → /jobs/{id}The command is wrapped in timeout --foreground -k 30 2700 (45 min, r1 M4). --foreground keeps it in the job's process group, which the host kills on run stop. Plain timeout makes its own group, so the 11-04 live check found a stopped server still running and holding its port. When the command ends, whether by itself or by the TTL, the labs host ends the rest of the job's group before it writes the exit code (TERM, then KILL 2 s later), so a pipeline or a backgrounded child cannot outlive a job that reads exited. Only a process that left the group on purpose (setsid/setpgid, e.g. nginx or redis --daemonize yes) escapes this. Nothing polls labs in the background: only an explicit status/logs/collect reads them. A run on a destroyed lab is lost (its lab was destroyed); a host kill is stopped. A lab server has no tailnet address (disposable labs are not exposed): url points at lab http.

The registry (memory/run_registry.py)

<memory_dir>/runs.db, never on the sandbox bind mount. A row is a pointer: backend (services | jobs | labs_job) and backend_ref (services key, job id, or lab_id/job_id), plus owner (project:<id> or conversation:<key>), origin, and for a service the start's token. A token that no longer matches means another start reused the name: the run reads replaced and run neither stops nor restarts that service (r1 M3). Ended rows are pruned after 30 days.

Who may use it

Members and replays are refused (the lab rule). A probe stops or restarts only runs a probe started. Autopilot may start and stop job and server runs; app runs come with Phase D and are owner-only there.

Code review r1 2026-11-04

  • The probe route sets the probe's request id and origin, not only the scope: a job's started_by is read from them, and an empty one woke the model as an owner turn and wrote the owner's activity ledger when the job landed (CRITICAL).
  • Every service call after a start uses the run's full services key, and a run whose row is lost or replaced is never stopped, restarted or read by name: by name the services lookup falls back to another project's service.
  • A restart counts only when the token changed. A start is recorded under a shield and, if the registry did not record it, undone (service stopped, job cancelled, lab job killed) — never left running untracked. One start at a time per owner and name.
  • stop probes first: a run that already ended is reported as it ended, never "stopped". A lab stop is decided by the DELETE answer (a later GET never says killed). A lab job the host no longer knows is lost, so its name can be started again.
  • A legacy unscoped service of that name is never taken over. On a lab, a probe starts runs only on a probe's lab, and another owner's lab is named in the result. A start that raises (a missing project folder) is a failed start, not a crash. The sweeper's landing line names run collect for a run job.

Code review r2 2026-11-04

  • Every start and restart (workspace server, workspace job, lab start, services restart) runs its backend call → record → rollback as one shielded step that catches its own errors: a cancelled turn still records what it started, and no step ends as an unretrieved exception.
  • A restart whose kill did not take leaves the run running and answers FAILED with nothing changed (it used to write failed over a live server, which then nothing in run could stop). A crashed server (exited) can be restarted whether or not a status probed it first. Restarts take the same per-name lock as starts.
  • An unrecorded lab start reports whether its kill was confirmed. A job that ends between the stop's probe and the cancel keeps its real end. A stop whose check gets no answer is unresolved, not stopped.
  • collect and logs of a run that already ended use its recorded end (a stopped lab job re-probes as lost; a stopped service has no row) — the probe only fetches output.

Code review r3 2026-11-04

  • A job cancel that the supervisor refused ("could not kill … left RUNNING") is a failed stop, not "already running" OK; a check with no answer is unresolved.
  • collect of an ended job whose backend no longer has the exit code uses the recorded end (exit N); a check with no answer is unresolved, never a false FAILED.
  • A start or restart runs, with its per-name lock, as one shielded task (_locked): a cancelled turn used to release the lock while the backend step still ran, and a quick second start raced it into two live rows.
  • A restart the registry did not record is stopped again. A lab server restart whose second start fails says the old one was stopped.

Code review r4 (MINOR only) 2026-11-04

  • A run stop is recorded as stopped (stopped by run), not as a service "stopped outside run".
  • The user's stop is read inside the shielded start: a backend step already sent finishes and is recorded, but nothing starts after the stop (run_stopped_by_user).
  • A restart never rewrites a recorded end; a restart check with no answer is unresolved; a failed server can be restarted. A lab restart of a server that had already ended does not claim it stopped one.
  • Undoing an unrecorded start or restart is verified; if the service survives, the reply says it may still run.

Reconcile and the boot line 2026-11-04

reconcile(context) checks the run registry against the workspace supervisors (design C3):

  • Every live workspace run, of every owner, is probed now and the result written back. If its service or job row has vanished, the run becomes lost. A probe that gets no answer leaves the run as it was.
  • Lab runs are only counted, never read. Reading a lab touches it and keeps a disposable lab alive (design r1 M4).
  • Rows of the old tools are reported, never adopted: services that no run points at (for example a manage_services start), and jobs started by run that no live run points at.

At startup, after the labs line, one Runs line is logged in the background. Example: 3 live run(s) · workspace 2 re-probed (1 ended: run_… lost (…)) · lab 1 not probed · 4 service(s) outside run. The line is a WARNING when a run has ended, a run job has no row, or a supervisor could not be read (partial: …). A service whose run ended in an EARLIER pass counts as outside run; one whose run is live, or started during the pass, does not. Nothing is restarted or adopted at boot.

App runs 2026-11-04 §4SX D3

A kept lab's app shows up as a run with lifetime app (backend labs_app, ref <lineage>/<app>). run cannot make one; you get one from lab keep ("run_app_via_keep"). The lab that serves it is looked up at probe time (_app_serving): the owner's kept labs of that lineage are listed, and the one with the app mounted serves. Staged versions are named in the note.

  • Host app states map to: up/restarting/starting → running, stopped → app_stopped, crashloop → crashloop. If only a staged version exists, the state is staged. If no kept lab of the lineage exists, the state is lost (the row ends). Silence from the host gives unknown and nothing is written. app_stopped, crashloop and staged are not ended states: the app comes back with run start.
  • start/stop/restart are POST /app/{op} on the serving lab. If the app is not up after a start or restart, the result is RUN ERROR (app_not_up). url and logs (the app's member) read it, and status shows the URL. A probe cannot drive an owner's app run.
  • Down notice (watch_kept_apps, every 300 s, background task "kept-app-watch"): app_down_sweep needs two down polls in a row, and an owner stop is not "down". It sends one notice per sweep that names every app newly down (autonomous activity at NOTIFY, plus the notify rate limit). The notice is marked in the run's meta only when it was recorded, and the mark is cleared when the app is up again, so the next down period notifies again. An unknown answer changes nothing.
  • The registry gained a meta JSON column (migration for old databases, set_meta where None removes a key, meta_of).

The switch 2026-11-04 §4SX D5

  • Schema. RUN_TOOL_DEFINITION takes the place of manage_services + jobs in TOOL_DEFINITIONS. The tool list changes once, so one re-prefill per deploy.
  • Aliases. The old names stay callable but are not advertised, for one release cycle. Each prefixes a one-line hint and keeps the result's status.
    • manage_services_alias: start runs run start where=workspace lifetime=server. A workdir becomes cd <dir> &&, and a name that is not a run name is folded to one, with the fold named in the hint. stop/restart/logs/status map to the same action on run. stop-all/adopt and anything else are refused, naming the run way.
    • jobs_alias: status runs run status. collect/cancel <job_id> become collect/stop on the run row of that job. A job with no row (promoted before the switch) is still read by the old jobs tool.
  • Read calls. READ_ACTIONS (status/logs/url/collect) and is_read_call keep a read open on a status question. A read never resets the failure guard and is never a dropped change.
  • Wired by meaning (core/agent.py and the sets elsewhere):
    • mutating world, edit-churn verify, last clean tool, external evidence, work tools, batch wall, drop note, the idempotency guard's mutating set;
    • replay-forbidden, macro-forbidden, egress url_literals + code tools, claim-source excluded, evidence tools (task state and gate), the read-write loop set;
    • provenance (logs/collect count as outside content);
    • program output: only a collect result (head [run NAME STATE exit=N] + an EXIT CODE: line). A log's "ERROR" is content (outcome_heuristics._run_result_failed).
  • Batch order (_run_call_depends):
    • a run waits for an earlier execute; an execute waits for an earlier changing run;
    • a run waits for an earlier run of the same name, and a nameless status for any changing run;
    • a run on lab_x/… waits for lab calls on lab_x, and for kept-app lab actions;
    • a lab call on the run's lab, or a kept-app lab action, waits for a changing run.
  • Promotion. execute gets run_context. record_promoted_job records a promoted command as a job run named after its job id (backend jobs), so the banner and the landed-job hint (main._collect_hint) name run collect name=job-…. With no row (registry down, a member), the banner falls back to the jobs wording, which still answers.
  • Briefing. project_running_summary lists the project's live runs (the state each had when last probed, with an absolute UTC time) and its live labs from the inventory. It uses local records only: no probe, no docker exec, no host call per turn. build_project_briefing(running=) renders the RUNNING block, and a run-backed service is not listed again under SERVICES.
  • Leaf. run joins the autopilot leaf's tools. A start inside a leaf carries meta.leaf, and stop_leaf_runs stops those runs when the leaf ends, before its labs are destroyed. Unattended work never starts, stops or restarts a kept app; it may read one.
  • Removed: the operator route POST /api/operator/run-probe. Live checks drive run through probe-header chat turns.

Review r1 of the switch 2026-11-04 §4SX-r

  • A leaf's promoted job outlives the leaf. record_promoted_job writes no leaf tag. A pip install or pytest that an execute inside a leaf detached after 90 s finishes, and its wake carries on. Before this fix, the leaf's end cancelled it.
  • The leaf tag is written in the insert. RunRegistry.add(meta=) writes it in the same INSERT, and the start sites pass _leaf_meta(), which reads LEAF_ID inside the shielded start. A leaf cancelled mid-start used to leave its server untagged, and a workspace server has no TTL. A restart carries the old row's leaf onto the new row.
  • run collect reads a workspace job like the wake does. It strips the stage-status marker with _take_pipestatus and applies _normalise_exit, so a | head exiting 141 is not a failure. It also calls mark_woken, so a collected job is not reported a second time by its wake.
  • Owner-less turns (a job's wake, a scheduled task: no project, no conversation): run status, and run collect/stop name=job-…, go to the jobs tool and its own §4NS rule (the owner's turn, the job's starter, or its wake). Anything else is refused, and the refusal says to switch to the project. run_name_for_job(owner=) reads only the caller's rows, so jobs collect falls back to the jobs tool for a job this caller has no row for.
  • The RUNNING block stays current. end_landed_job_runs ends the run row of a landed job. The reaper calls it on take_unreported, and the summary calls it on a local registry read. The summary shows the twelve newest rows. A run-backed server keeps the container-generation STALE mark (§4LR M1).
  • Smaller fixes.
    • A leaf may stop or restart only the runs it started (same meta.leaf). Other unattended work (a scheduled task) still may.
    • A workspace run start runs execute's guards first: one naming the labs host is refused with lab_host_from_workspace, one probing the agent's own port with run_agent_port.
    • manage_services log/tail is read as logs, and jobs list job_id=X as status.
    • A promoted job is listed once in the project inventory (under runs).
    • _run_result_failed reads a declared status first, then the anchored exec_exit_code.
    • The execute schema and the release note name run.
  • Kept as is:
    • a replay still has no run status, which is safe;
    • the alias name fold can join web_1 and web-1;
    • a name-only run stop on a lab run does not wait for a lab exec on that lab in the same batch.

Review r2 2026-11-04 §4SX-r

  • A leaf's end waits for its in-flight starts. _locked registers each start or restart task under the leaf (_LEAF_INFLIGHT). stop_leaf_runs waits up to LEAF_INFLIGHT_WAIT_S (90 s, inside coding_loop's 120 s cleanup bound), then reads the rows. Before this fix, a leaf cancelled mid-start ended before its shielded start recorded the row, so that run stayed up.
  • Only the owner, or the job's starter, marks a collected job delivered (_delivers: the owner's turn or internal code, or the launch record's started_by). A leaf or a scheduled task that reads the owner's job leaves the wake alone, so the owner's waiting work still carries on.
  • A promoted job carries meta.started_leaf. The leaf that detached it may stop it. The leaf's end reads leaf only, so it leaves the job running.
  • A restart keeps the old row's leaf, on the workspace path and the lab path alike.
  • Landed jobs never overwrite an ended row. end_landed_job_runs writes with set_state(only_live=True), so a concurrent run stop stays "stopped".
  • run_name_for_job finds ended rows too. The reaper ends a row before it writes the hint.
  • The alias hint follows the result, so the result's own head stays first for every head reader.
  • The stored verdict matches the live one. _RUN_COLLECT_RE reads our own two head lines: an expired, stopped or lost job is a failure, and a later EXIT CODE: 3 the program printed is ignored.
  • An owner-less run stop name=job-… cancels through the jobs tool, then ends the run row.

Reviews r3 and r4 2026-11-05 §4SX-r

  • A reused run name. run_name_for_job gives a job's name only while that name still resolves to the job's own row. When a newer run has taken the name, jobs collect/status/cancel job_id=<old> acts on the old job's row directly (_old_job_row_op): collect reads the old job, and cancel of an ended job is refused, naming the newer run. In that case the landed-job hint names jobs(… job_id=…).
  • An exited job with no recorded exit code is UNRESOLVED (run_exit_unknown) and its head says "judge it by the output". The stored verdict agrees with the live one, and the turn loop does not call it "still running".
  • Leaf cleanup. The end's wait is now 40 s. A start that lands after the end stops its own row (_LEAF_ENDED, a held task). A leaf's stops run one at a time (_LEAF_STOP_LOCKS), so each row is stopped once.
  • Wake arm. A wake turn that collects its own job marks it delivered (the same arm as §4NS _mine).
  • Old-name rows. A jobs/manage_services row that holds a run result (head [run , RUN , No runs here) is graded by the run rule. A stored collect under the failure banner is still read.

Review r5 2026-11-05 §4SX-r

  • Exit code not recorded. In a batch summary, a collect with no recorded exit code goes on its own line: "FINISHED, EXIT CODE NOT RECORDED (not a verdict — judge each by its output)". It is no longer listed under SUCCEEDED, which had told the model not to report it as failed. The turn loop marks the op exit_unknown.
  • Banner before the head. The stored verdict strips the failure-banner lines before it reads the head. As a result, a stored [FAILURE BANNER] RUN ERROR: … row counts as a failure, including under the jobs alias.
  • Leaf stop lock. The lock is keyed by (event loop, leaf), so the same leaf id on a second loop never hits a lock bound to another loop.
  • A live job under a reused name. jobs cancel job_id=<old> stops the old row directly, under the probe and leaf rules run stop applies.
  • SQL hint. SQL sent to lab (or the old postgres/postgresql/psql names) points to lab exec … cmd="psql -U postgres -v ON_ERROR_STOP=1" stdin="<the SQL>". It does so only when a labs host is configured. Otherwise the answer says SQL cannot run here.

Review r7: one head rule 2026-11-05 §4SX-r

Stored rows are re-graded later from their text alone, and each review round found another result shape that read wrong: a refusal passed through under an old tool name, a failed restart, an UNRESOLVED no-answer. Every run result now goes through one exit point, runs._headed. It runs in tool_run and in the aliases' _with_hint.

  • A FAILED or REJECTED result always starts with RUN ERROR. If it did not already, RUN ERROR — is put in front of its first line, so that line keeps its reason (review r8: on a line of its own, the head became every failure's error line).
  • A result that is not failed never starts with it. An UNRESOLVED RUN ERROR (no_answer): … may have started becomes RUN UNRESOLVED (no_answer): ….
  • A collect keeps its own head ([run x exited] + EXIT CODE:). Its pattern is pinned equal to the stored grader's.

The stored grader (outcome_heuristics._run_result_failed) reads just that head and the collect head.

Review r8 2026-11-05 §4SX-r

  • The evidence gate counts an unanswered run as "no answer", never as evidence. This covers RUN UNRESOLVED … and results under the banner.
  • A [run x logs] or [run x app …] result whose first log line reads EXIT CODE: 1 is content, not a collect. All three collect patterns agree: the grader, the head rule and strikes.
  • The alias hint keeps every field of the result (declared, call_args, duration_s).
  • Known, kept: jobs rows answered by the old jobs tool (a job with no run row) are graded by the old rule, as before D5.

Review r9 2026-11-05 §4SX-r

Review r9 found no MAJOR issues. Its minor findings were fixed:

  • The head rule now covers the third state. Every UNRESOLVED run result starts with RUN UNRESOLVED; examples are "stop sent, but the backend did not answer the check" and "no result yet". A collect keeps its own head, and an exited collect with EXIT CODE: none counts as unresolved.

End-to-end review r11 2026-11-05 §4SX-u

  • Workspace jobs run through bash -c with pipefail (execute._bash_c), like a promoted execute job. The runner script is #!/bin/sh + timeout … <cmd>, so cd app && pytest, FOO=1 x, source … and loops exited 127, and only the first command of a && b was under the ceiling.
  • The shell guards execute runs apply to a workspace run (runs._shell_guard_refusal): the destructive deny-list (fails closed), writes into a RELEASED project, YouTube downloads and detached … & servers are refused before anything starts.
  • Autopilot runs only on its own project's disposable labs. _start_lab refuses another owner's lab and any kept lab for the autopilot origin (the lab tool's rule).
