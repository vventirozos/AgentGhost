Single source of truth for every LLM-facing tool. Builds the active definition list per turn, dispatches calls, injects context.

Active list construction

get_active_tool_definitions(context, query) assembles the per-turn tool list:

  1. Start with the static TOOL_DEFINITIONS array.
  2. Append vision_analysis when the LLM client supports vision.
  3. Append image_generation when context.llm_client.image_gen_clients exists.
  4. If a query is provided, RAG-retrieve relevant acquired skills via memory_system.collection.query(query_texts=[query], where={"type": "acquired_skill"}) and inject only the matches. A failure of that vector query now degrades to advertise all active skills (2026-07-03) instead of aborting the whole block — a transient store hiccup used to hide every acquired skill from the schema while leaving them dispatchable (invisible-but-callable).
  5. Otherwise inject every active-status acquired skill that doesn't shadow a built-in.
  6. _intent_filter drops tools whose required configuration is missing (e.g. lab without a labs host).

Dispatch & handler binding

get_available_tools(context) returns a dict of tool_name → async lambda. Each lambda binds the live sandbox_dir, memory_system, llm_client, scheduler, and other context state to the underlying tool function so the tool implementations stay stateless. Both both-values project-scope consumers (execute, browser) unpack host_dir, workdir = _proj_ws() from a single call so a concurrent mid-request current_project_id clear can't desync the host dir from the container workdir (browser previously called _proj_ws() twice). Tool functions that could receive a hallucinated extra arg all end in **kwargs so an unexpected key surfaces as the tool's own validation message rather than a dispatch-layer TypeError.

Acquired skills run via tool_execute(filename=f"acquired_skills/{name}.py", args=[json_kwargs]). Success / failure telemetry is recorded by manager.log_telemetry(name, success).

youtube_transcribe (§4TA, 2026-11-05). The handler is _youtube_transcribe inside get_available_tools. It looks the knowledge-base callable up in the same tools dict when it is called (YOUTUBE_TRANSCRIBE_INNER_TOOL), so it gets the egress-guarded callable that the loop over CONTENT_GUARDED_TOOLS installs, and calls it with action='transcribe', filename=url. The result is returned as it is. A missing, blank or non-text url is refused (youtube_transcribe_no_url) and nothing is fetched; other arguments are ignored. Because the handler holds the full dispatch dict, restrict_tool_surface (isolation) forbids youtube_transcribe wherever it forbids knowledge_base.

Composed skills (macros) were wired in here by register_composed_skill_runners, and into the definitions by register_composed_skills. Both were removed with the macro engine. An old registry file on disk is not read, so an old macro name is an unknown tool.

Fallback & failure routing

A failure raised by any tool is classified by tool_failure.classify(). RETRYABLE failures retry with exponential backoff (max 3 attempts). FATAL tell the model "PERMANENT ERROR — do NOT retry this tool call" (nothing re-plans; this line said "trigger replan" until 2026-11-05). DIAGNOSTIC inject the full error so the LLM can self-correct. UNKNOWN inject a brief notice. Per-tool fallback chains in fallback_chains.py suggest alternatives.

Continuity & metacognition tools

Three agent-callable selfhood / continuity tools (four until 2026-11-05, when self_state was folded into introspect, §4TB).

  • self_state (removed 2026-11-05, §4TB) — it authored open questions, unfinished threads, principles and a mood. Only the mood is kept, as introspect(action="set_mood"). See the tombstone.
  • introspect — snapshots the agent's own selfhood for introspective queries like "tell me about yourself" or "what do you remember about X?". Read actions: summary (default), overview, stats, narrative, recent, recall, activity, learning, mood (the mood now, why, since when, today's timeline — §4TC). One write, since 2026-11-05 (§4TB), in the owner's own request only: set_mood (mood = a label from a closed list or neutral, intensity 1–3, manner, optional evidence — §4TC). Selfhood actions route through the SelfModel facade — stats, the running diary, recent experiences, and IDF-weighted past-recall; activity/learning/overview read the background-activity ledger and learning stores directly (the experiments action was removed with the experiments registry, §4NN) (they work with selfhood disabled).
  • workspace / workspace_track — world-model counterparts to the selfhood pair. Read tool surfaces file diffs, scheduled-task outcomes, research artifacts, command outcomes, and the running workspace narrative; write tool authors the file watchlist, free-form notes, and manual research dedup markers. Both route through the WorkspaceModel facade (see workspace continuity).

All three are registered in TOOL_DEFINITIONS and get_available_tools.

replan (removed) 2026-11-05 §4TB

What it was. A tool with one parameter, reason, described to the model as "call this if your current strategy is failing … it forces a fresh planning step". Its whole implementation returned one sentence: "Strategy Reset Triggered … The planner will see this and should update the TaskTree accordingly."

Why it was removed. The per-turn planner that sentence was addressed to was deleted in October (§4NM), and nothing in the turn loop reacted to the call. In four months of recorded turns (6,061 turns, 17,062 tool calls) it was called 0 times. Its name also collided with the live manage_projects(action="replan"), which project messages call "replan".

What went with it. The definition, the handler and its dispatch entry; its entries in the member allow-list (_MEMBER_ALLOWED_TOOLS) and the bookkeeping-tool table (_BOOKKEEPING_TOOL_NAMES); the pointer to it in abort_attempt's description ("use replan for those", found by the review); the TaskTree object the turn loop built for every request and never read; and the exemption that kept a replan call in a reply out of the unparsed-call scrub.

What still holds.

  • manage_projects(action="replan") is untouched. See projects.
  • A model that still calls replan(...) gets the ordinary unknown-tool reply with the list of tools. The rule for a mistyped tool name does not resolve it to any built-in (its closest match, recall, scores 0.5 against the 0.7 needed).
  • The cognitive watchdog still cuts a final stream that loops inside a think block. What it appends to the recorded reply is now a plain note, not a synthetic replan call: see agent §4TB.

Tests: tests/test_4tb_replan_removed.py.

2026-07-27 (later 8) — a skill went invisible, and the prefix cache was primed twice

Two operator-reported symptoms, one root cause: the advertised acquired-skill set.

The tell

One log line, identical on every request regardless of query — including the request whose hydration was literally "news_headlines tool usage":

semantic routing    injected 1: format_results_to_csv

A line that never varies with its input is a constant where a variable belongs. Measuring the two stores explained it: the registry held 3 active skills, the vector store held 1 embedding.

Why the skill was invisible

Routing queries the vector store (where type=acquired_skill) and filters the advertised tool schema by the result, so news_headlines was never in the catalogue the model saw. Everything after that is downstream: the model called manage_skills twice hunting for it, tried to shell out (blocked — inline body 219 chars), tripped the loop-breaker, and had its final answer eaten by the stream scrub.

It could never self-heal. save_skill embeds only when the content hash CHANGES, so once an embedding was lost — the pre-2026-07-26 broken deletes, or an orphan sweep — nothing rebuilt it. The index could only ever lose entries, while the skill stayed active and dispatchable. That is the "invisible-but-callable drift" the routing degrade-paths guard against, reached from the opposite direction.

  • backfill_missing_skill_embeddings() re-embeds any ACTIVE registry skill with no vector entry, wired into the same sweep as the orphan purge.
  • The purge is now fail-safe: an empty registry alongside existing embeddings is treated as a failed read, not as "all skills deleted". Without that, one transient mid-write read wipes the whole routing index unrecoverably.

Why the prefix cache loaded twice

The boot warmup primes the request head via get_active_tool_defs(""). The empty string is FALSY, so routing is skipped and it advertises ALL skills — while every live request passes a real query and gets a SUBSET. The ~22,186-token warmup prefix therefore never matched a single real request, and each request re-prefilled the entire head. (The warmup's own comment claimed it mirrored "the same neutral-query routing a live request's first turn resolves to" — false the moment routing became query-dependent.)

Fixed at the design level rather than by patching the warmup: below _SKILL_ROUTING_MIN_SKILLS (25) every active skill is advertised and per-query routing is skipped. Filtering three skills saves a few hundred tokens once; it costs a full re-prefill of a 22k head on every request. Above the threshold routing still applies. This also makes the tool block byte-identical ACROSS requests — the per-turn stability was already correct.

Verified live: the routing line is now absent (advertise-all = what the warmup primed), and the skill dispatches — turn outcome verified · tools: news_headlines · 804 chars, returning real RSS headlines, no scrub fallback.

Per-arm schema: _apply_fs_batch_schema (2026-08-04)

Removed 2026-10-11 (§4NN). The experiments registry is gone and with it the fs_batch treatment schema: every request gets the control file_system schema, the batch macro code itself was deleted in the post-§4NN tidy-up (the dispatch lambda passes no batch flag), and the boot warm-up no longer primes a second tool-schema head. This section and the next are the record of what the arm did.

The first experiment arm to change the ADVERTISED schema rather than an injected message. In the fs_batch TREATMENT arm the file_system definition gains a paths property, loses path from required (a pure paths read has no single path), and gains a short "fewer calls, same work" clause; the CONTROL arm sees today's definition byte-for-byte. Same copy-on-write discipline as _apply_tuned_descriptions — the shared TOOL_DEFINITIONS dicts are never mutated, or a treatment request would leak its schema into the next control request.

Two ordering decisions are load-bearing. It runs after _apply_tuned_descriptions, because a tuned description REPLACES the baseline wholesale and is validated against it (the loader stays; no tuned artifact exists since the optimizer was removed on 2026-10-11, §4NM) — appending first would let the tuned text drop the batch prose AND hand the validator a different baseline per arm, i.e. a second unintended difference between the arms. And the arm is resolved through the request-id ContextVar, not the bare stash slot, for the reason arm_for documents: a turn reading its arm after the slot moved on would take the control path while still being RECORDED as treatment.

Known cost: the boot prefix warmup primes the CONTROL tool block, so a treatment request re-prefills that block. It is bounded (~1.2 KB of the head) and it is the price of measuring a schema change at all.

The fs_batch arm differs by exactly the treatment 2026-08-11

The treatment schema drops path from required so a pure paths batch read is valid — but that also told the treatment arm that write, replace and delete need no path, which has nothing to do with the batch affordance under test. Only read fans out; no mutating op accepts paths. An unmeasured confound in a live A/B whose entire purpose is the batch macro.

JSON Schema cannot express “required unless operation == read” portably (and an invented key is silently ignored — one was tried and removed), so the constraint is stated in the tool DESCRIPTION, which is the channel the model actually reads. The schema stays permissive; the instruction restores parity for every operation except the batch read.

Tool head diet: RETIRED 2026-09-10 §4FX

Shipped flag-gated OFF on 2026-09-07 (§4FE) on the hypothesis — arXiv 2605.24660, ALE-Claw — that a short static tool list cuts prefill without costing selection accuracy. GHOST_TOOL_HEAD_DIET=1 advertised a 16-tool core plus a tool_catalog lookup, 18,625 → 11,465 tokens of static schemas, with every hidden built-in still dispatchable by name. It never flipped, and on 2026-09-10 it was removed from production: the flag, TOOL_HEAD_CORE, apply_tool_head_diet, hidden_tool_definitions, the tool_catalog handler and the apply_diet seam are all gone.

Why, in numbers. Three quantities, each measured on real data rather than argued:

  • Accuracy: null. 0.489 vs 0.481 per DISTINCT REQUEST, p=0.88, n=264 (§4FK — the 587-row p=0.0003 was the wrong unit; one request had been recorded 40×). Proving non-inferiority to a 3pp margin would need n≈1,500–2,000 distinct real prompts, which §4FL established this traffic cannot produce.
  • The token cut buys ~0.13 s per request. 7,160 tokens is 9.6 s at the measured 744 tok/s — but only on a prefill that carries the whole head, and the main node's counters say that is 1.4% of 16,018 prefills (16.9M prompt tokens served from cache vs 3.06M prefilled = 84.7% cached; median prefill 2,299 tokens). §4FM's re-warm loop keeps the byte-stable head resident, which is exactly what removes the diet's value.
  • The catalog tax costs ~0.7 s per tool-using turn. The diet hides 25 of 41 static tools, and 11.5% of 503 real tool-using turns (Aug–Sep, 2,077 calls) touched one — each paying a discovery round at a median 6.3 s per short LLM call. About five times the gain, plus the risk that the model substitutes a visible tool instead of discovering the right one (the §4FJ workspace confusion, 98 wrong picks, is that failure mode).

What would reopen it. The gain scales linearly with the full-head prefill rate; break-even is ≈7.5% (≈15% if discovery needs both a list and a describe), against 1.4% today. If the re-warm loop is removed, the model or context size changes, or that rate climbs past ~7.5%, re-read those two numbers — they are two queries, not a new bench. The decision rule to re-apply: keep iff measured expected gain > measured expected cost AND the accuracy CI excludes harm beyond δ.

Retired, not erased. scripts/tool_head_diet_bench.py stays, and now carries its OWN copy of the construction (CORE, CATALOG_DEFINITION, apply_diet) since production no longer has one; it still reads the live TOOL_DEFINITIONS for the full head, so a re-run measures today's real tools against the frozen core. Absence pins: tests/test_4fx_tool_head_diet_retired.py — the symbols are gone, the advertised head is byte-identical with the flag on and off, every static built-in is advertised again, the catalog is not in the handler map, no module reads the flag, and the bench still loads. Bench-harness pins stay in tests/test_4fi_bench_scripts.py and tests/test_4fj_think_probe_and_workspace.py.
