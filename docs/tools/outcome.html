tools / outcome.py

What a tool call actually did — as data, not as a string to sniff.

Why it exists

Tools in this codebase return error strings rather than raising, so every consumer that wanted to know "did this fail?" grew its own text rule. An audit AST-parsed every return/raise in ghost_agent/tools/ — 1,026 result heads — ran all of those rules over each, then over 4,391 recorded live tool calls. It found ten vocabularies where the code claimed one, and measured what the disagreement cost:

  • 66 refusals credited with changing the world. A malformed mutating call that touched nothing cleared recorded pre-flight failures, wiped the loop-breaker's memory and decremented the strike count — so a run of rejected replaces erased earlier strikes and the cap could never fire.
  • 15 turns reporting a non-zero exit as SUCCEEDED under the MULTI-STEP OUTCOME banner, the one message that tells the model "this live outcome is AUTHORITATIVE".
  • 219 calls where the turn loop and the trajectory corpus disagreed about whether the same call failed — and the corpus is what the learning loop trains on.

Five review rounds had answered by adding prefixes to predicates, and each addition created the next round's split. A string cannot say "this REFUSED and touched nothing" or "this half-landed", and those are exactly the two distinctions whose absence caused the harm.

It IS a string

ToolOutcome is a str subclass. The first version was a dataclass with a hand-written proxy, and reviewers found the holes one at a time: isinstance(x, str) was False, json.dumps raised, "".join([...]) raised, re.search raised, + raised, os.path.join raised. Roughly a thousand call sites treat a tool result as a string; being one is the only version of "behaviour-identical on day 1" that actually holds.

The status rides inside the content value, so the LLM API payload is byte-identical — an extra dict key on a message would be sent upstream. The cost is that equality and hashing are the string's, so ok("x") == rejected("x"); nothing in the tree containerises results by value.

DECLARED vs DERIVED — the rule that took three rounds

A status and a text sniffer will disagree, and the whole question is who wins. Preferring the status once traded +61 refusals for −198 execute failures, because every result is wrapped, so the sniffer became dead code and took the exit-code rule with it. Simply ORing them keeps the sniffer's false positives: a manage_projects read whose JSON ledger quotes a stored autoadvance_failed event — traceback and EXIT CODE: 1 verbatim — was booked as a failed shell command.

Position cannot separate those two: a JSON payload is one line, so "the banner heads the result" is true for a real envelope and for a quote. The producer can. So an outcome records where its status came from:

Built byAgainst the sniffer
DERIVEDToolOutcome.coerce(text) — a guess from the same prose the sniffer readsORs with it. Never overrules.
DECLAREDa producer calling .ok() / .rejected() / …Settles it.

This is safe for one structural reason, and it is pinned: execute never declares a SUCCESS. (It does declare REJECTED and UNRESOLVED — the load-bearing half is that it never declares ok, because that is the only status that could talk the sniffer out of its own exit-code evidence.) Its results are bare strings, so coerce marks them derived and the shell keeps full authority over its own exit code. shell_failed additionally has no declared short-circuit at all, so a producer that declared OK while its envelope says 127 is still caught.

There is no unanchored traceback rule in the verdict. One lived in an earlier wide re-derivation, where it fed only the work log; collapsing the loop's three verdicts into one promoted it to the strike ledger, and a successful file_system read of a log quoting a crash drew a strike, failed the competence profile and got a "the path doesn't exist" hint about the file it had just read — 4.2% of readable files in the live sandbox contain the word.

The marker fallback is unanchored by necessity — a crashing script's traceback can be anywhere in its stdout — and is therefore wrong for any tool that merely quotes code. Applied to every tool it booked 226 live successes as incompetence: a file_system read of a script containing except ValueError:, a recall hit whose memory text mentions PermissionError, a job log quoting HTTP Error 429.

UNRESOLVED is tested before the general non-OK rule in both: an unfinished job has no verdict, and answering True was how exit_code_val = 1 if shell_failed gave an in-flight run a strike.

⚠ Ask the question once. Inside the loop that is _res_is_error; for a row read back afterwards it is agent._action_failed(content, tool_name). Every private re-derivation of it has been wrong — a five-prefix head bank booked 145 of 291 declared non-OK results as successes, and the if/else that replaced it shadowed the bank so 118 non-zero execute exits were still stored successful. Neither could see an EXIT CODE: banner under an --- EXECUTION RESULT --- head.

⚠ There is ONE verdict per call. The loop used to hold three in a single iteration — a status-only one for op_outcomes.ok and the pre-flight guard, a wider one 660 lines down for the competence profile and the work log, and the strike branch, narrower than both. Seven consumers disagreed about the same call on 56 of 4,391 calls, including 8 where ok was False and no strike was drawn at all. Compute it once; never recompute it.

⚠ The loop must not declare on a producer's behalf. Any construction that forwards a status must also forward declared — __new__ defaults it to True, so omitting it re-labels a derived status as a producer's own answer and makes the sniffer unreachable. That mistake cost 151 of 4,391 calls their ToolCall.error flag, 116 of them execute: the −198 regression rebuilt from the other end. It is pinned across agent.py, execute.py and file_system.py.

That list is not maintained by memory. Four readers were migrated in one pass and a fifth was missed — so test_every_result_classifier_reads_the_status enumerates them from the AST and fails on the sixth.

Decorating a result

Never touch the text directly. ToolOutcome is a str subclass, so res + note, f"{res}…", str(res).strip(), a slice and .replace all go through str and return a plain str, silently discarding the status. That defect has been found at nine sites in six modules across four review rounds — three of them after the same thing had been fixed one boundary away, because each sweep was scoped to the module being migrated.

UseFor
outcome.with_text(res, new_text)any rewrite of the text — truncation, compression, summarisation
outcome.append_note(res, note)appending a hint or a verification note

Both are no-ops on a plain str, so they are safe to apply anywhere a result might or might not be an outcome. test_outcome_consumers_r7 walks the whole package for the raw forms.

Where the defects actually are

After seven rounds, the pattern is consistent enough to state as a rule: the defects live where two modules meet. Every one found in the declaration audit sat at the edge of an earlier migration — the last return of a dispatcher whose eight siblings were migrated; the wrapper one boundary out from the producer that declares; the flag armed one line after the await it guards; the += one function later; the refusal wrapped in an envelope that hides its own head from an anchored predicate. When you migrate a module, the next thing to check is not the rest of that module — it is whoever calls it and whoever it calls.

How it is pinned

  • At the producer, with no allowlist. An AST walk over every module defining a tool_* entry point fails when a refusal- or partial-shaped return appears as a bare string. Earlier rounds all pinned a reader, and each round's defect arrived through a writer.
  • With a positive control. The scanner was green because its result set was empty — which is also what a broken scanner produces; all three of its arms could be disabled with the suite green. It now has to find a planted refusal in four shapes (literal, f-string, concatenation, module constant) before it is allowed to report none.
  • By mutation, whole-file, one mutant per run, never naming the expected killer. Two pins were found asserting the fix rather than reading it: the System-3 pivot simulation hardcoded the guard it was supposed to lift from source, and the browser pin asked "is ToolOutcome mentioned in _err" — true either way, since _err imports it on its first line. 30 mutants, 30 killed.
