Infrastructure

Ghost Agent lives on four small computers at home, joined by a private network. Nothing runs in a cloud, and the agent reaches the internet only through Tor.

Runs on: eva, nova, ghost, disorder Tor-only

Four machines, what runs where

eva

Mac Studio, M4 Max, 36 GB
  • The agent itself (launchd daemon, restarted if it dies)
  • Main model: Qwen3.8-27B with MTP on llama-server
  • Web console, API and Slack bot
  • Docker sandbox for code and browsing
  • Tor egress and all memory stores

nova

Mac mini, M4, 16 GB
  • Helper model: Gemma E4B (side calls, vision, audio input)
  • Whisper speech-to-text
  • Phonon text-to-speech
  • Sentiment service
  • Portfolio service

ghost

Jetson Orin
  • Image generation: Qwen-Image-2.1-Turbo via stable-diffusion.cpp

disorder

Raspberry Pi 5
  • ghost-labs: small long-running experiments

A fifth device, a ClockworkPi uConsole handheld, is only a client: it talks to the agent the same way the web console does. All machines reach each other over a private tailnet.

One request, across the machines

Say Elena asks by voice from the handheld: “Draw me a lighthouse at dusk and tell me tomorrow's weather.”

  1. Client → eva

    The handheld sends the audio to the agent's API on eva, with the owner's key.

  2. eva → nova

    The audio goes to Whisper on nova and comes back as text.

  3. eva: main model

    The agent builds the prompt (head, memories, conversation) and the main model on eva decides which tools to call.

  4. eva → Tor → internet

    The weather lookup leaves through Tor. Nothing goes out directly.

  5. eva → ghost

    The picture request goes to the Jetson; the finished image comes back and is looked at before the reply mentions it.

  6. eva → nova → client

    The reply text is spoken by Phonon on nova and streamed back to the handheld.

handheld ─► eva (agent + main model) ─► nova (Whisper)
                 │  ├─► Tor ─► internet (weather)
                 │  ├─► ghost (image)
                 │  └─► nova (helper model, TTS)
                 └─────────────────────────► reply to handheld

How it works

Supervision. The agent runs as a system launchd daemon with KeepAlive, so a crash brings it straight back. A deploy is a SIGTERM to the launchd job; the operator first waits until no foreground request is running, so nobody's reply is cut off.

Tor only. The agent uses no keyed cloud APIs and goes to the internet only through Tor. Inside the Docker sandbox a private Tor runs alongside firewall rules that send every connection through it and reject the rest (other UDP, ICMP, all IPv6). The rules are loaded before Tor starts, so the sandbox fails closed. Separate services the operator chooses, on other machines, may use the normal internet.

Isolation. Each request carries who is asking. The owner's memories, files and rules are walled off from team members and the public; a member's request cannot read the owner's stores.

One model slot. The main model has one slot, so the agent works hard to keep it for the conversation that matters; see Performance.

Where it runs

Everything that holds data or decides anything runs on eva. nova, ghost and disorder are helpers: if one is off, the agent carries on without that ability (or, for side calls, falls back to the main model).

Limits and switches

  • eva has 36 GB of memory shared between the main model, the sandbox and the stores; that is why the model has a single slot.
  • If Tor is down, the agent cannot reach the web at all. This is on purpose.
  • Sandbox Tor is controlled by GHOST_TOR; provisioning (apt, pip, browser download) happens before the rules go in.
  • The handheld depends on eva; it does no model work itself.
