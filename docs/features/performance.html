Performance

The agent runs a 27-billion-parameter model on one desk computer, with no cloud behind it. A handful of tricks keep it from re-reading the same text again and again, so a follow-up question starts in about a second instead of nearly three minutes.

Runs on: eva (main model) and nova (helper model) Local only

What it does

Every request the agent sends to its main model starts with a long fixed part: the instructions and the description of every tool. This "head" is about 28,000 tokens. Reading it from nothing takes the main model close to three minutes on the Mac Studio. After that, the model keeps what it read in memory (its slot), and the next request that starts with the same text only pays for the new part.

The trouble is that the server has a single slot. Anything else that uses the model — a background job, a message from a team member on Slack, another conversation, a restart — replaces what the slot holds. Most of the performance work is about protecting that slot, or getting its contents back quickly when it is lost.

  • Head and conversation saves. The slot's state is written to disk (about 0.7 s and 1.7 GB for the head) and read back in under a second, instead of re-reading 28k tokens.
  • A conversation keeps its slot. A long owner conversation stays in the slot until some other call really needs it. It is saved to disk first, and only then given up. A follow-up gets it back.
  • Cache protection. Small side calls (judging, summarising, labelling) go to the helper machine, so they do not push the conversation out.
  • MTP speculative decoding. The main model guesses several tokens ahead and checks them in one step: about 25–33 tokens per second, against about 19 without it.
  • Reasoning effort. In the web console you can pick how hard the model thinks: low, medium or xhigh.
  • Deadline extension. A request has a 60-minute budget. Coding work that keeps making real progress earns 15-minute extensions, up to 180 minutes.

Correctness never depends on any of this. The model server compares the exact tokens of each new prompt with what the slot holds and reuses only the part that matches. A stale or wrong save file costs time, never a wrong answer.

How it works

  1. Warm the head

    When the agent starts, or the head changes, it reads the head once and saves it to a file.

  2. Track who owns the slot

    Every request carries a conversation key (the web client's session, or the Slack thread). The agent remembers which conversation the slot holds.

  3. Save before giving it up

    When another call needs the slot, the current conversation is saved to disk first (2–4 GB with the model's checkpoints). There is no timer: it stays until something needs the space.

  4. Restore on the follow-up

    When that conversation speaks again, its file is loaded back (0.4–0.8 s) and only the new text is processed. A file is loaded only if the call that built it sent the same tool list and the same instructions as the new request. Otherwise it is deleted and the head's own file is loaded.

  5. Check that it helped

    The model server reports how many tokens of each prompt it took from memory. If the call a restore was made for took nothing past the head from memory, one warning line is logged. Nothing is deleted on this signal.

  6. Keep small jobs away

    Side calls run on the helper model on nova, which has four slots of its own. If nova is down, a circuit breaker sends them back to the main model.

For effort, the level is written near the end of the system text by a modified chat template, so changing it re-reads only the conversation, not the whole head. When a request gets stuck, the agent adds one short “think harder” note at the end of the history for the rest of that request; a level you picked yourself always wins.

Where it runs

The main model (Qwen3.8-27B with MTP) runs in llama-server on the Mac Studio eva, with one slot. Save files sit on eva's disk. The helper model (Gemma E4B) runs on the Mac mini nova and takes side calls, vision and audio input. The two talk over the private tailnet. See Infrastructure for the full machine map.

Limits and switches

  • Saves are switched by GHOST_HEAD_SAVES and conversation keeping by GHOST_CONV_KEEP. Off, everything still works, just slower.
  • The effort menu exists only when GHOST_REASONING_EFFORT=1 (set by the launcher while the 27B model is the main model). There is no automatic level choice; it was removed because a level change before tools forced a large re-read.
  • Save files are large (gigabytes each). A changed head (new tools, new instructions) makes old files useless; they cost time, not correctness. Such a conversation file is deleted the first time its conversation returns. Conversation files saved before this rule existed (at most 6) are deleted the same way, once.
  • A file is kept only when the disk had room for it, the server wrote all of it, and the server confirmed after the save that it is still the one the save was planned for (model path, build, chat template).
  • The model is known by its path. A model file replaced in place under the same path is not detected.
  • The save directory holds at most 3 owner heads, 3 members' heads and 6 conversations (24 GB). Files unused for 14 days (conversations, members' heads) or 30 days (owner heads) are deleted. Files made by another model are kept for 3 days after their last use, so trying another model once does not delete the usual model's files. Files are readable by the owner's account only.
  • If the model server was still loading when the agent started, the agent has no save plan. It tries again when a request needs one and every 10 to 120 seconds, and logs each distinct reason once. A re-warm tick that could not reach the model server to make a plan sends nothing, so it cannot replace a conversation that was not saved.
  • Requests with no conversation key (health probes, scheduled jobs) skip the owner slot paths entirely.
  • The deadline extension applies to web requests, and only coding progress earns it.
