Labs

When a task needs a real PostgreSQL server, a three-node cluster or a running web app, the agent does not fake it. It asks a separate small machine for disposable containers, works on them, and throws them away.

Runs on: Raspberry Pi 5 (disorder) Tor-only

What it does

The agent's own sandbox is one container with no root, no extra ports and no network faults. That suits writing and running code. It does not suit "start PostgreSQL 18 with two replicas, cut the leader off the network and watch who takes over".

For that there are labs. A lab is a set of Docker containers (its members) on a private network of their own, built from a template. The labs host has no AI in it: the agent asks for something, and the service either does exactly that or answers with an error and a hint.

The rule is simple: build in the workspace, run the system under test in a lab. Code, SQL files and reports stay in the sandbox workspace, because labs disappear. Files move between the two, and a lab's recipe can be saved so the same setup can be rebuilt later.

The templates ship with the labs service's code and are read from its own templates/ folder, so deploying the code deploys them. /etc/ghost-labs/templates/ on the host holds only templates the operator adds; a file there with a shipped template's name, or one that does not parse, is not loaded, and the service logs a warning when it starts. (Until 11-11 the service read a copy in /etc that only the installer refreshed, and a template fix synced with the code was not used.)

"Tor" means the lab reaches the internet only through the labs host's Tor gateway, as the agent itself does. pip and npm work through it with no proxy settings. "None" means no route out at all. A lab never reaches the agent's Mac or the home network.

In your own chat you can also change a template: more memory, other or extra published ports, the NET_ADMIN/NET_RAW capabilities, CPUs, or internet on/off, for every member or one member at a time. You can also compose a lab from the images directly ("a lab with two node-app members"). Autopilot builds and test probes use the templates as they are.

Try it

You never have to name the tool. Just describe what you want run.

You sayWhat happens
“Check what SELECT 41+1; returns on PostgreSQL 18.”A pg-single lab is created, the query runs with psql, the answer (42) comes back, and the lab is destroyed.
“Write a schema for Kosmas's library app, load it into a fresh database and save a dump.”The schema is written in the workspace, copied into a lab, loaded, dumped, and the dump is copied back to the workspace.
“Start a three-node Patroni cluster, isolate the leader, and tell me who takes over and how long it took.”A patroni-3 lab; the leader is taken off the lab network without stopping it; the agent reads the new leader and the time, rejoins the node, and can save the recipe for a rerun.
“Run a 10-minute pgbench on the lab and tell me the TPS.”A long job starts on a lab member. The agent collects it when it ends, and grades it by how it really ended, not by what it printed.
“In my chess project, put the app online and keep it running.”A python-app lab is made a kept app: stable address, daily backups, a supervisor that restarts it, and a notice to you if it goes down twice in a row.
“Publish the webOS site.”A static-site lab is kept with just a name, and the site folder is deployed. Notes, screenshots and dotfiles in the folder stay behind.
“Deploy the new version of the shop.”The new code is unpacked next to the running one and its dependencies are installed there. Only then does it replace the old version. If it does not come up, the old version is put back and you are told why.

How it works

  1. Create

    The agent asks for a template and waits until the lab's readiness check passes (at most five minutes, never past the turn's own deadline). The database templates also check each member's own service (PostgreSQL: its socket; MySQL: a ping) inside the same wait. A member that is not ready when the wait ends does not fail the create: the result names it and the command that checks it, and says "not checked" instead when the wait ended before its check could run. The lab is recorded in the agent's lab inventory: who made it, for which conversation or project.

  2. Use

    Run commands on a member, copy files in and out, read logs, call a member's HTTP port, start a long job or a server, or inject faults: stop, start, restart, kill, pause, unpause, isolate, rejoin. A fault, or a destroy, does not wait for a command that is still running on the lab. A command that is still running can be cancelled: you can end any command on your lab, and an autopilot build can end only a command it started itself, never one on a kept lab. The answer says "killed" only when the labs host saw the command gone; when the kill could not be delivered it says so, and that the command may still be running. A folder copied out of a lab is checked entry by entry before anything is written: nothing lands in a released project or a .git directory, and nothing in the workspace is replaced to make room.

  3. End

    The agent destroys the lab when done. If it forgets, the host's reaper removes an idle lab: after 4 hours for an ad-hoc lab, 12 hours inside a project, 2 hours for an autopilot build's lab, 30 minutes for a test probe, or once it reaches its maximum age (1 day ad hoc, 3 days in a project). A lab with a command running on it is in use, not idle.

Things that keep running on a lab

The run tool starts a job (runs to its end, 45 minutes at most, then its result is collected) or a server on a lab member. A server gets its port in $PORT and must listen on 0.0.0.0; it has no time limit of its own and runs until it is stopped or its lab goes. Right after the start the agent asks the port once and reports what it got: an answer, nothing yet, or a process that listens on 127.0.0.1 only. run url gives the tailnet address when the lab's template publishes that port (python-app publishes 8080, web 80).

Nothing automatic ends a workspace server you started. In your own chat, run status all=true lists the live runs of every conversation and project from the agent's records, and run stop name=<run id> stops any of them. A conversation's workspace server that has run for more than a day is listed there with its age and the stop command; it is not stopped.

Kept apps

A lab made inside a project can be kept. It then runs one app under a stable address with no expiry. A web app gets an https address; a database (a kept pg-single, or any app with no web health check) is published as a plain TCP host:port for psql and the like. The app gets its port in $PORT and DATA_DIR=/data. Only /data survives a deploy and is backed up; the app folder is replaced by every deploy.

A backup copies /data of every member of the kept lab (the database of a python-pg app lives in its db member), with PostgreSQL stopped for the few seconds of the copy so the copy is consistent (also when the app has its own backup command, which runs first). Restoring one backup of such a set restores the whole set, the app's member last; a restored database is started and checked before the app starts. Because the stopped file copy is newer than any dump the app's own backup command made, a restore of an app that has a database never replays that dump (not even when undoing a restore or rolling back); the result says so and the dump stays in /data. A backup command that fails no longer blocks anything: the file copy is taken and the failure is reported. A restore that fails before it changed anything leaves the app running as it was. One that fails after it changed /data leaves the app stopped and held, and the result lists the snapshots taken just before, to go back. If a member's data was cleared and not refilled, its database does not start at all, not even after a restart: restore a good backup, or start the app with reinit: true, which starts the database on whatever /data holds now (an empty database only if the restore never got the files in; the good backups stay protected for a week). Why the app is held is shown with it. While held, a deploy installs without starting (and there is no automatic revert when you start it later), rehearse and switch are refused, a rollback needs restore_snapshot: true, and no backup is rotated away. MySQL and Patroni members are copied while running, so their backups are not crash-consistent.

A deploy sends a workspace folder (or one of its subfolders, such as a built dist/). Dotfiles, credential files (.env, .npmrc, .netrc, .pgpass, .ssh/, .aws/, private keys such as id_rsa, *.pem and *.key, and the like, which never go whatever the folder says), the agent's working files (project map, work logs, check screenshots), OS litter and anything listed in the folder's .deployignore are left out, and the result names them. Every file arrives readable, so a web server can serve it. On the labs host the new version is unpacked next to the running one. Its build runs there: requirements.txt is installed into the app folder, and a Node app gets npm ci and npm run build. A failed build changes nothing and shows the end of the build log. The new version then replaces the old one in place. If it crashes or its health check returns an error while the previous version was up, the previous version's folder is put back as it ran (no new build) and the result says "rolled back" and why. Your data is not rolled back with it: the result says so and names the backup taken just before the deploy, which you can restore. A slow start is reported as still starting, and the host keeps checking it.

Keeping a lab that is already kept, with a different start command, health check, port, folder or build, updates the app and restarts it. The older route still works: a second kept lab of the same app, rehearsed on a throw-away twin with empty data and fake secrets, then switched in. Each deploy saves the built folder on the labs host, so a switch, rollback or rehearsal puts that folder back instead of downloading the dependencies again over Tor. A version deployed before this change is built once more there. A Python app should run with plain python3: python3 -I ignores the packages the build installed, and the deploy result says so. App secrets are never tool arguments; the host masks them in every output.

Where it runs

The labs service runs on a Raspberry Pi 5 called disorder. It holds the templates, the reaper that removes idle labs, the kept-app supervisor, a Tor gateway for labs that may go online, and a read-only Apps page listing kept apps. The agent on the Mac Studio (eva) talks to it over the private network with a key. A host firewall stops labs from reaching the agent or the home network.

Limits and switches

  • Text sent to a command's stdin (a password piped to psql, say) goes to a private file on the member that the command's shell deletes before the command runs, and the host deletes it after the command too. If the member is paused in the few milliseconds between those steps, the file can stay on the member until the lab is destroyed.
  • Space is limited: a RAM budget, at most four disposable labs at once, and a separate allowance for kept labs. When the pool is full, your create evicts the oldest autopilot lab, never one of your own.
  • Autopilot cannot destroy a lab you used in the last 30 minutes. A build's lab that you used belongs to you: the build's end leaves it, nothing asks again, and it expires by its idle time, which each use moves.
  • When a build's lab could not be destroyed because the host was busy or did not answer, the agent asks again every five minutes. An outage is logged once when it starts and once when it ends.
  • A command the agent runs on a lab never gets more time than the turn has left. Inside an autopilot build that is the build turn's own 10 minutes.
  • While a command runs on a lab, a second command, a screenshot and every kept-app action wait 30 seconds and then answer "busy". Destroy and the fault actions go ahead.
  • lab http waits 15 seconds in total. A stream or a slow page is cut there and marked as cut.
  • Logs and command output are the last part only: 6 KB in a result, and the host keeps at most 256 KB of each log. A cut result says so and names the full log file on the lab.
  • A kept app's data goes only with the app's last version. The labs host decides that when it deletes; the agent only reports what it did.
  • The labs key is sent only directly, and only to a loopback, tailnet or private IP address written in the usual form, or to a bare local name with no dot. A labs host configured by any dotted name (ts.net included), by an integer or hex address, with a user:password@ part, or by an address outside the loopback, private and tailnet ranges (link-local addresses included) is refused: the agent logs that once and every lab call says so.
  • When the host cannot make a lab right now (no room, Tor gateway or firewall not up, no free port, busy), an autopilot task waits and starts again by itself. After three waits it asks you.
  • An idle time above the lab's maximum is cut to the maximum, on create and on extend, and the answer says so.
  • Times on another day are printed with their date.
  • lab put and lab get move a file or a whole folder. A folder is at most 20 MB and 2000 files and folders. Symbolic links, devices and pipes are never moved; in a folder fetched with lab get, a second name for a file already sent (a hard link) arrives as a separate copy of that file and counts toward the 20 MB, .env files, .git, node_modules, virtualenvs and caches are never sent, and a folder archive with an absolute path or .. in it is refused whole, on the host and on the agent.
  • lab screenshot saves a picture of a member's web page as a .png in the workspace. The agent has not seen the picture until it looks at the file with its vision tool; the result says so. Resources the page loads from the internet do not appear, and a page that redirects is refused.
  • The agent's browser cannot open a lab's ports; it uses the lab tool's HTTP call instead.
  • The tool appears only when a labs host and its key are configured. With neither, it is simply not offered.
  • Common refusals say what to do: the host did not answer, the lab limit is reached, not enough memory, an action only you may take, or an unknown (expired) lab.
  • The agent's old local PostgreSQL is gone. A database request runs in a lab.
