Feature

Coding

Ghost writes code and runs it for real, inside a Docker sandbox that cannot touch the host and reaches the internet only through Tor. It can keep long jobs and small web services running, and it is checked against claiming it ran something it did not.

Runs on: eva (Mac Studio) Tor-only

What it does

  • execute runs Python or shell in the sandbox and reads back the output, errors, exit code and any files written. Python can run in a stateful Jupyter session.
  • file_system lists, reads, searches, writes and edits files in the workspace. Large files are written in parts.
  • Jobs: a run that is still working after about 90 seconds is not killed. It becomes a background job, and Ghost is woken when it finishes.
  • Services: a web app or API can be started as a named service that outlives the turn and even an agent restart. Ports 8100 to 8104 are reachable from outside the sandbox.
  • PostgreSQL 18 client: psql is installed in the sandbox.
  • probe_model: for experiments about language models, Ghost can send prompts to a model for real and keep the raw answers as a transcript the system writes.

How it works

  1. A persistent container

    One Docker container holds the workspace, bind-mounted from $GHOST_HOME/sandbox. The host's home folder is not reachable. Network access goes through Tor.

  2. Guarded runs

    Each command has a 600-second budget for going quiet. A run that is still making progress is detached as a supervised job, marked clearly as "still running", so nobody mistakes it for a success.

  3. Services

    A service is launched as its own process group with a log and a registry entry. Start checks that it is alive and that its port binds; if it crashed, you get the log tail with the cause.

  4. Claims are checked

    When Ghost says "the tests pass" or "I ran it", the system compares that with what its own tools actually returned. Claims without matching tool output are flagged.

  5. Experiments need proof

    In a project, an experiment task can be marked done only with a saved probe_model transcript (or an explicit waiver). This stops "simulated" model answers written by hand from passing as results.

Where it runs

Everything runs on eva: the agent, the main model that writes the code, and the Docker sandbox. probe_model uses the main model by default, or the helper model on nova as a second, different subject. Real database servers for bigger tests live on lab machines (see ghost-labs on the Pi), not in the sandbox.

Limits and switches

  • Only five service ports (8100–8104) are reachable from outside.
  • The sandbox has no clearnet access; downloads are slower over Tor and some sites block Tor.
  • probe_model takes at most 8 prompts per call and 600 seconds in total; inside your turn it shares the main model, so the conversation is re-read after it.
  • Files downloaded from .onion sites go to a quarantine that cannot be opened or run, only inspected.
  • When a background job finishes, its follow-up turn runs with nobody watching and stops at 45 minutes, writing its report in the reserved time (GHOST_JOB_WAKE_S; 0 = no clock).
  • Switches: GHOST_SANDBOX_MEM sets the container's memory limit.

Builds that check themselves (§4UU, 2026-11-17)

Ghost fixes a bug well once it can see it. Most lost time came from not seeing it: big web apps written in one piece, testing by hand in the browser, and "done, tested" after only a syntax check. Five changes make the checking part of the work:

  • Every web write is loaded at once. After Ghost writes or edits a page, script or stylesheet, the page is opened headless and the write's result says [PAGE CHECK] ✓ or ✗ with the JavaScript error. A page that throws is fixed before anything else. Off with GHOST_PAGE_CHECK=0.
  • A checklist only a test can tick. For a build with several features Ghost keeps a checklist: one item per feature, each with a check that runs it. An item turns ✓ only when its check passes. While items are open Ghost sees [CHECKLIST 2/5 passed · next: …] after its tool calls, and "it's done" with unpassed items gets one more round. The list belongs to the project (or the conversation for a day) and is kept outside the sandbox.
  • "Tested" means it ran. node --check, py_compile, cat, grep, ls or curl are not runs. A reply that says "tested, it works" after only those gets the "never run" note and a round to run it. Neither are a compile (gcc, cargo build), --help, or a run hidden behind || true. A run-tool server, cargo run, node ., python -m pkg and a written run.sh do count; files are told apart by path (backend/index.js is not frontend/index.js), and a page load counts only for the scripts that page loads. "Verified", "all 12 tests pass", "live-tested" are all read as claims.
  • A starter for web apps. “Build me a tetris app” can start from template='web-app': a folder already split into index.html, css/, one js/ file per feature and tests/check_page.py, a headless test with one check per feature (python3 tests/check_page.py rotate). It never writes into a folder that has files.
  • Fewer dead ends. Lab templates are a fixed list; lab http / screenshot / logs pick the member when there is one obvious one; the browser refuses tailnet addresses at once and points to lab http; and once su / sudo / setpriv fails with "Operation not permitted", it is not retried in that request — Ghost is told to use a lab machine (labs give root).

Fewer brakes on a coding turn (§4UI, 2026-11-12)

The main model is now a dense model and codes much better than the MoE model many coding guards were written for. Guards that second-guessed the model were relaxed; guards that protect your data, honest "it works" claims and destructive commands stay.

  • A failing test run is not a failure strike. When execute runs your program and the program itself fails (a red test, a traceback), and the output changed since the last such failure, it is logged as "Program Fail" and costs no strike. An output that matches one of the last 8 failures still counts, and after 12 free failures in one request every further one counts again, so a stuck or endlessly varying loop still reaches the cap.
  • A refused edit is not a strike. An edit that would break the file's syntax is still refused (the file stays intact), but the refusal now shows the current lines where the edit began and asks for one edit covering the whole change.
  • Edit-churn only advises; the futility steer is gone (§4UY C5). Many edits of one file without a run (from 6) get a note. The futility steer ("rewritten N× and rerun M×") counted every write part and every node --check, and its one live firing since 11-12 was wrong (it told a web-app build to shrink to "one record/sprite/tile"), so it was deleted. The write/run counters remain for the progress and stuck readers.
  • Nothing ordinary is refused, and nothing is lost (§4UY C6/C21). A file overwritten or deleted by file_system or by a shell command keeps its previous version for 14 days, in a store outside the sandbox. The model lists versions with file_system(operation='versions') and puts one back with operation='restore'. A file a program writes itself is not versioned. When the request had not read that file whole, the result says so and names the kept copy. The one refusal left is wiping a whole project folder: rm -rf *, an unfiltered find . -delete, or git clean -fdx at its top.
  • The exit status is the real one (§4UY C9/C10). A failure of a program that runs code (an interpreter, a test runner, a compiler or build tool) earlier in a ; list is the run's status — the shell records it in a status file the host reads, never in the output. Other commands failing (rm of a missing file, curl, lsof) keep the shell's status, a command that reads $? or PIPESTATUS itself sees exactly what it asked for, and printed text such as "0 failed" or "exit code: 3" is never a status.
  • The same error line under exit 0 only advises. A working program that logs the same warning on every run is no longer force-stopped.
  • Long program output is not summarised. execute output keeps its head and tail (a traceback and pytest's summary are at the end), instead of a worker summary of the first 15k characters.
  • The tool-turn cap follows the time left, so a long write near the deadline cannot run past it.
  • Kept: read-before-rewrite, the "actually run it" check on claims, the write-in-parts guards, the shell deny-list, the Tor-only launch flags for raw Playwright (TOR_PROXY + --host-resolver-rules, so DNS cannot leak) in the execute description, and a rule there never to run a destructive statement (DROP, TRUNCATE, an unbounded DELETE/UPDATE, rm -rf of data) on data the agent did not just create unless you asked and confirmed.
