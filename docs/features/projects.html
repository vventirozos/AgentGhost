Projects and autopilot

Work that takes weeks instead of one chat: a project holds a plan of tasks, their order, their files and their research, and survives restarts. If you switch it on, an autopilot moves a project forward one task at a time while you are away.

Runs on: Mac Studio (eva) Tor-only

What it does

Most questions are answered in one turn. Some jobs are bigger: build a small web app with tests, compare five databases and write a report, migrate a schema and check it on a real server. The model cannot keep a plan like that in its head for days, and a stop in the middle must not lose the work. A project is the durable to-do structure for that kind of job.

A project has a goal, a tree of tasks (with "do this before that" links), its own folder in the sandbox, its research notes and its files. Every later turn about the project gets a short briefing: what is done, what is open, what is waiting and why. So "where are we on the chess app?" is answered from the stored record, not from memory or a guess.

The agent does not open a project for everything. It creates one only when you ask, or when the work really spans many files and many turns. A large single-file page or script is built directly, with no task tree.

Alongside projects sit three smaller tools for work that is not a conversation:

  • Scheduled tasks fire on a clock ("every morning at nine, summarise the news").
  • Watches fire on a condition ("tell me when this page stops answering").
  • Background jobs keep long commands running after the reply, and wake the agent with the result when they finish.

Try it

You sayWhat happens
“Start a project: a Flask app for Bruno's bakery orders, with login, SQLite and pytest. Plan it first.”A project is created, the goal is split into ordered tasks, and the plan is shown. The agent then stops and waits for your go-ahead.
“Proceed with the next task.”Exactly one task is done in a full turn: files written, tests run, and the task is closed only if its promised file exists and is not empty.
“Do the next three.” / “Finish the project.”A bounded loop runs one checkpointed task at a time and stops at the first task that is done, fails, needs you, or hits the budget. Then it reports.
“Research payment providers for the bakery project.”Searches run over Tor, and a Markdown brief with sources is saved in the project's research/ folder. Later turns see it in the briefing.
“Turn on autopilot for the bakery project.”While you are idle, the agent advances that project one task per idle window. Waiting tasks stay waiting.
“Where are we on the bakery project?”A status read from the store: done, running, waiting (and on what), failed.
“Every weekday at 08:00, send me a short weather and news summary.”A scheduled task with a cron time and a stored prompt. Cron times are UTC, so the agent converts your local time.
“Watch Elena's shop site and tell me if it goes down.”A watch that runs a check command in the sandbox every minute or more. It fires once when the condition becomes true, and re-arms only after it clears.
“What did you do while I was away?”The activity log: autopilot ticks, scheduled runs, finished jobs, tasks that need you.

How it works

  1. Plan

    The goal is decomposed into tasks. Each task can depend on others, and a task never starts until everything it depends on is DONE. A task also says what kind it is (coding, research, or one that needs you).

  2. Advance, one task at a time

    By default the agent does one task per go-ahead from you. "Do all" becomes a loop of small, separate ticks, so the context window stays small however long the project is.

  3. Close only on evidence

    A task is DONE only when the file it promised exists and is not hollow, its dependencies are closed, and its result passes the task's check. Otherwise it stays open and the reply says why.

  4. Wait honestly

    A task that cannot go on is shown as WAITING with a reason: waiting on you (a decision, an approval), on another task, or held until you run it yourself. The five states you see are PENDING, RUNNING, DONE, FAILED and WAITING.

  5. Autopilot while idle

    When you have been away for a while, the idle scheduler picks one active project that has autopilot on and runs a single tick, with a cool-down between ticks. If every open task is stuck behind a failed one, autopilot pauses and tells you once which task to retry.

The safety check

  • Budgets. A project can cap its steps, its runtime and its tool calls. A batch stops when a cap is reached.
  • Human gates. A task marked as needing human approval (deleting real data, sending something to a customer) can never be closed by the agent. It goes to WAITING on you.
  • Holds. Some tasks are never run unattended, for example a model experiment. Autopilot leaves them for your own turn.
  • Contradictions. If a new result plainly contradicts an earlier one, the project records it.
  • Opt-in only. Only your own message turns autopilot on. A scheduled task, a background job or a test cannot.

Labs inside a project

A project can use disposable machines on the labs host, for example a real PostgreSQL to test a migration. Autopilot may create labs for its own project; they are destroyed when its step ends. See Labs.

Where it runs

Everything runs on the Mac Studio (eva): the project store, the scheduler, the sandbox where code is written and tested, and the main model that does the work. Research goes out over Tor like all of the agent's web traffic. The web console has a Projects view over the same store. Labs used by a project run on the Raspberry Pi (disorder).

Limits and switches

  • Autopilot is off for every project until you turn it on for that project. It advances only one project per idle tick, and never closes a task that needs you.
  • The idle autopilot loop needs the agent to run with --autoadvance-idle.
  • Watches poll no faster than every 60 seconds. Scheduled-task times are UTC.
  • Background jobs live in memory: they end if the agent restarts. Finished results are kept for a while so a later turn can collect them.
  • "Archive" keeps a project and its files; "delete" removes it.
  • A task's checks are mechanical. A DONE task proves a real file exists and passed its check, not that the work is perfect.
