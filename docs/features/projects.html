Projects and autopilot

Work that takes weeks instead of one chat: a project holds a plan of tasks, their order, their files and their research, and survives restarts. If you switch it on, an autopilot moves a project forward one task at a time while you are away.

Runs on: Mac Studio (eva) Tor-only

What it does

Most questions are answered in one turn. Some jobs are bigger: build a small web app with tests, compare five databases and write a report, migrate a schema and check it on a real server. The model cannot keep a plan like that in its head for days, and a stop in the middle must not lose the work. A project is the durable to-do structure for that kind of job.

A project has a goal, a tree of tasks (with "do this before that" links), its own folder in the sandbox, its research notes and its files. Every later turn about the project gets a short briefing: what is done, what is open, what is waiting and why. So "where are we on the chess app?" is answered from the stored record, not from memory or a guess.

The agent does not open a project for everything. It creates one only when you ask, or when the work really spans many files and many turns. A large single-file page or script is built directly, with no task tree.

Alongside projects sit three smaller tools for work that is not a conversation:

  • Scheduled tasks fire on a clock ("every morning at nine, summarise the news").
  • Watches fire on a condition ("tell me when this page stops answering").
  • Background jobs keep long commands running after the reply, and wake the agent with the result when they finish.

Try it

“Start a project: a Flask app for Bruno's bakery orders, with login, SQLite and pytest. Plan it first.”A project is created, the goal is split into ordered tasks, and the plan is shown. You asked to plan first, so the agent then waits for your go-ahead.
“Create a project for a webOS and build it, with a couple of apps.”The same message asks for the work, so it is the go-ahead: the plan is shown in a line or two and the first task starts in the same turn.
“Proceed with the next task.”The next task is done in a full turn: files written, tests run, and the task is closed only if its promised file exists and is not empty. Then the agent reports and waits.
“Do the next three.” / “Finish the project.”The agent does them in the same turn one after another, or, on a big project, hands them to a bounded loop that runs one checkpointed task at a time. It goes past a task that fails or waits to the work that does not need it, but never builds a task while one before it in the plan waits or runs (unless the plan said that task is independent). Then it reports what ran, what failed and what waits.
“Research payment providers for the bakery project.”Searches run over Tor, and a Markdown brief with sources is saved in the project's research/ folder. Later turns see it in the briefing.
“Turn on autopilot for the bakery project.”While you are idle, the agent advances that project one task per idle window. Waiting tasks stay waiting.
“Where are we on the bakery project?”A status read from the store: done, running, waiting (and on what), failed, the last changes you asked for, and where it is live.
“Add a Tetris game to the webOS.”The plan is finished, so the project is ready: the agent changes its files directly, puts them on the project's lab, and the change log gets one entry (what you asked, files added and changed, what it did, live or not), also written to PROJECT_CHANGES.md in its folder (never deployed).
“What changed in the webOS this week?”The change log, newest first (manage_projects action=changes).
“The webOS is finished, close it.”Only you close a project; the reply says it was closed at your request. A later change reopens it.
“Every weekday at 08:00, send me a short weather and news summary.”A scheduled task with a cron time and a stored prompt. Cron times are UTC, so the agent converts your local time.
“Watch Elena's shop site and tell me if it goes down.”A watch that runs a check command in the sandbox every minute or more. It fires once when the condition becomes true, and re-arms only after it clears.
“What did you do while I was away?”The activity log: autopilot ticks, scheduled runs, finished jobs, tasks that need you.

How it works

  1. Plan

    The goal is decomposed into tasks, in order. Plan order counts: a task does not start while a task before it waits, is still running, or was skipped by the run (§4UL), so a findings page is never written over experiments that did not run. A task that failed does not hold the tasks after it: the next task's turn sees the failure in its briefing, and when you retry the failed one, the finished tasks built on it are flagged for a re-check. A phase (a task with subtasks) whose subtask failed is blocked, though, and does hold the phases after it. A task can instead name exactly what it needs (depends_on: earlier positions or task ids), or say it needs nothing (depends_on: []) and run whenever it can. When a task closes late, the finished tasks built on it are flagged for a re-check. A task also says what kind it is (coding, research, or one that needs you).

  2. Advance at your pace

    One rule decides the pace: a go-ahead covers what you asked for. "Proceed" is the next task; "do the next three" or "finish it" is that many. A message that asks for a project and the work is itself the go-ahead. It is advice the model follows, not a stop the code forces: after a task closes, the agent may go on when you asked for more. On a big project it hands long runs to a loop of small, separate ticks, so the context window stays small.

  3. Close only on evidence

    A task is DONE only when the file it promised exists and is not hollow, its dependencies are closed, and its result passes the task's check. Otherwise it stays open and the reply says why.

  4. Wait honestly

    A task that cannot go on is shown as WAITING with a reason: waiting on you (something only you have, such as a file or a login), on another task, or held until you run it yourself. The five states you see are PENDING, RUNNING, DONE, FAILED and WAITING.

  5. Each task is a full turn (§4UL)

    When autopilot, or your own "do the next tasks", runs a build or research task, the agent runs it as one ordinary agent turn of its own: every tool, the project briefing, and the same close rules as your chat turns. The turn ends by closing its task as DONE (with the files) or FAILED (with the reason), and asks nothing. Run by you, it acts with your authority, so it may deploy to a kept lab. Run unattended, it may not: a task that needs a kept machine waits for your next run, and a DONE with nothing run after its last edit (the program, its tests, a linter, the page, lab http) waits for you to look. Idle autopilot starts a task's turn only while no request of yours is running. Inside the turn the agent cannot steer the project as a whole (no autoadvance, switch, delete and so on). Details.

  6. Autopilot while idle

    When you have been away for a while, the idle scheduler picks one active project that has autopilot on and runs a single tick, with a cool-down between ticks. Unattended work has a daily allowance (30 tasks and a few hours per project, §4UL); when it is used, or three steps in a row moved nothing, the project simply rests until the next day: autopilot stays on and nobody is asked anything. If every open task is stuck behind failed work (it depends on a failed task, or waits in plan order behind one that is blocked by it), autopilot pauses and tells you once which task to retry.

Living projects (§4UM)

A project is an app or site you keep changing, not a one-off. When its planned tasks are all done it stays open and shows as ready; it is never closed by the agent. Only you close it (“close the project”). States: working (planned tasks open), ready (plan done, open for changes), done (closed by you).

  • Every change you ask for is recorded. When your turn wrote into the project (the file tool, or a command run there), its end compares the folder with how it was, so writes, deletes and moves by any command (sed -i, rm, mv, a heredoc) are all seen. A turn that only looked (a question, a search, a screenshot) is never a change, and the agent's own files (screenshots, research notes, clean-up moves) are left out. One entry: your words, the files added, changed or removed, what the reply said, and whether it is live. Autopilot work on a ready project gets its own entry (“task: …”). The log is in the project's store and in PROJECT_CHANGES.md, the agent's own file in its folder; a CHANGELOG.md of your project's own is left alone. The request that built the first plan is not a change (its tasks record it).
  • Going live is recorded. A lab put, lab deploy or lab switch into the project's kept lab is a deploy entry with the URL; a change is marked live once all its files were pushed into the app's folder, or by a later whole deploy or a switch to a version staged after it. The briefing then says “Live at <url>” and which changes are not deployed yet.
  • The briefing shows the last five changes, where it is live, and the project's files as they are on disk now.
  • Old work. A project the agent closed by itself before (when its plan finished) reads ready again. Changes made before the log existed are added with scripts/backfill_project_change.py (running it twice adds nothing). Details.

The safety check

  • Budgets (§4UL). Your own runs are never capped. Unattended runs get a daily allowance per project (30 tasks, a few hours); you can change it with action=budget (unattended_per_day, runtime_cap_hours), and you can ask for a check-in every N tasks (checkpoint_every; off by default).
  • No confirmations (§4UK, 2026-11-12). Nothing waits for your yes: release, unrelease and delete run when you ask, a HUMAN_GATE line on a task is a note (never graded, never a park), words like "approve", "publish" or "send" in a task no longer hold it, and a stated exception to a project constraint goes through in your own turn and is written to the ledger. Who may act still matters: a background, scheduled or test turn cannot delete or release your project, ready or not, and a request that read a web page cannot either.
  • Holds. Some tasks are never run unattended, for example a model experiment. Autopilot leaves them for your own turn. A build whose test command ran and passed is not held just because its task says "test" or "verify" (§4UL).
  • Edits to a project (§4UL, §4UM). When your turn writes a file into a project's folder (with the file tool, or a command — run in the project's own folder, or one that names projects/<id>/ — that writes, deletes or moves files there), that project becomes the conversation's project if none was, and the change goes to its change log at the end of the turn. A project you closed reopens, with no task and no question. The clean-up of a finished plan's scratch files runs at the end of the turn and keeps every file a change touched; a file your turn writes after a project task finished the first plan in the same request is the same work, not a change.
  • Contradictions. If a new result plainly contradicts an earlier one, the project records it.
  • Opt-in only. Only your own message turns autopilot on. A scheduled task, a background job or a test cannot.

Labs inside a project

A project can use disposable machines on the labs host, for example a real PostgreSQL to test a migration. Autopilot may create labs for its own project; they are destroyed when its step ends. See Labs.

Where it runs

Everything runs on the Mac Studio (eva): the project store, the scheduler, the sandbox where code is written and tested, and the main model that does the work. Research goes out over Tor like all of the agent's web traffic. You reach projects through the conversation (any client), the CLI and the agent's HTTP API (/api/projects); the web console has no separate projects page. Labs used by a project run on the Raspberry Pi (disorder).

Limits and switches

  • Autopilot is off for every project until you turn it on for that project. It advances only one project per idle tick, and never closes a task that needs you.
  • The idle autopilot loop needs the agent to run with --autoadvance-idle.
  • Watches poll no faster than every 60 seconds. Scheduled-task times are UTC.
  • Background jobs live in memory: they end if the agent restarts. Finished results are kept for a while so a later turn can collect them.
  • "Archive" keeps a project and its files; "delete" removes it.
  • A task's checks are mechanical. A DONE task proves a real file exists and passed its check, not that the work is perfect.
