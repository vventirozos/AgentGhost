Running it

When something breaks

Sorted by what you'd notice, not by which component is at fault.

Check these two things first

Most confusing behaviour resolves into one of two states, and both are visible from one request:

curl -s -H "X-Ghost-Key: $GHOST_API_KEY" \
     http://127.0.0.1:8000/api/health | python -m json.tool
memory_system_loaded
false means Ghost booted degraded: HTTP answers normally, but there's no memory and every background pass is silently disabled. It will chat with you and remember nothing.
biological_watchdog_alive
false means the background loop died. Ghost still answers, but it has stopped consolidating memory and learning. Nothing will tell you this — it just goes quiet.

It won't start

"REFUSING TO START … no API key configured"

You bound to something other than localhost without deciding about authentication. Either set GHOST_API_KEY, or pass --api-key '' to knowingly turn auth off on a trusted network, or bind to 127.0.0.1.

It aborts complaining about Tor

Mandatory Tor is on by default and Ghost probes it at boot. Check the daemon is running and listening:

curl --socks5-hostname 127.0.0.1:9050 -s https://check.torproject.org | grep -o "Congratulations"

If Tor is fine but Ghost still refuses, check TOR_PROXY points at the right port.

First-ever boot hangs or fails loading the embedder

This one catches everybody. On a fresh install the embedding model hasn't been downloaded yet, and the Tor egress guard blocks that download because it's a direct connection to a public host. Boot once with --no-mandatory-tor to let it cache, then run normally from then on.

It refuses to start and mentions re-embedding

The embedding model doesn't match the one that built your vector store. Both models produce vectors of the same size, so nothing would crash — the stored vectors would simply stop meaning anything and retrieval would return plausible-looking garbage. Ghost refuses instead.

Either put GHOST_EMBED_MODEL back to what it was, or migrate deliberately:

PYTHONPATH=src python scripts/reembed_memory.py

Port already in use

Usually a previous instance that didn't shut down. If you run it under launchd with KeepAlive, remember that a plain kill restarts it — you need launchctl bootout to actually stop it.

It started but acts like it has amnesia

It knows nothing about you at all

Almost always GHOST_HOME. If it isn't set, Ghost uses ~/ghost_llamacpp — so an agent started from a shell where you'd exported it and one started by a service manager where you hadn't are two different agents with two different memories.

Under launchd or systemd this is the default outcome, because a service doesn't inherit your shell profile. Set it inside the service definition. Confirm which path is live:

ps -o command= -p $(pgrep -f ghost_agent.main | head -1)

It forgot one specific thing

Two very different causes with opposite fixes. Ask it to search for the fact directly. If it can find it on request, the fact is stored fine and the retrieval ranking didn't surface it — that's a ranking problem, not a lost memory. If it can't find it at all, it was never stored.

Things mentioned in the last couple of minutes may genuinely not be searchable yet; the queue that files them drains after about two minutes of quiet. More on memory →

It keeps repeating something wrong about you

That entry is in your profile, which is injected into every conversation rather than searched. Correct it directly ("my wife is Maria, not Anna") or use the memory-correction control in the web UI.

Tools don't work

Anything involving code or files fails

Check Docker is running. Ghost needs the daemon up; without it, execute, browser and the file tools all fail. The very first container start also pulls a base image, so it's slow once and fast afterwards.

"It can't reach my app on localhost:3000"

Correct — and not a bug. The sandbox has its own network namespace, so its 127.0.0.1 is not yours. Ghost cannot see services you run on your machine, and cannot stop or restart your processes. If you need it to test a local app, have Ghost start that app itself inside the sandbox.

Web search returns nothing, repeatedly

Usually search operators. The scraper backends Ghost reaches over Tor don't support site:, quoted phrases, or AND/OR — including any of them returns zero results rather than an error. Plain keywords only.

For dark-web search specifically, zero results is normal. Onion search engines are unreliable and reachability varies by exit node; an empty result is not a reason to retry the same query.

It won't do something, and explains why instead

If the model declines rather than the tool failing, that's model alignment, not a bug. Ghost is developed against uncensored models; a standard aligned one will refuse operations that are routine for an agent on your own machine — wiping its sandbox, deleting files on request, searching Tor hidden services, handling security material.

Tell them apart in the log: a broken tool logs a failure with its own icon, while a refusal shows the model reasoning (💭) and then a normal ✅ turn outcome with no tool line at all. The second one means nothing ran. The same applies to the verifier — an aligned judge can refuse a sound answer on subject matter alone, which surfaces as retries you can't otherwise explain.

A tool that used to work now refuses to run

The pre-flight guard is doing its job. When the same tool fails the same way on the same target repeatedly, Ghost stops re-running it and hands the model the previous error instead. Fix the underlying cause and it'll clear.

It's slow

Every answer is slow

Your model has one inference slot, and Ghost competes with itself for it: the self-check, conversation compaction and background classification are all model calls. Moving the self-check to a second machine with --critic-nodes is the highest-value change available — see Settings that matter.

Finding out what a turn actually cost

Every turn now records its real token cost, summed across each model call it made — the tool rounds, the self-check, and any work sent to a worker node. It lands in the turn's trajectory record and on the reply itself:

curl -s -X POST http://127.0.0.1:8000/api/chat \
  -H "X-Ghost-Key: $GHOST_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"'"$GHOST_MODEL"'","messages":[{"role":"user","content":"hello"}],"stream":false}' \
  | python -c "import sys,json; print(json.load(sys.stdin).get('usage'))"

The interesting field is cached_tokens. Ghost sends a large system prompt on every call and relies on the server's prefill cache to avoid re-processing it. If cached_tokens is near prompt_tokens, the cache is working and most of that prompt costs nothing. If it's near zero, you're re-prefilling the whole prompt every round — which is the difference between a fast turn and a slow one, and it's usually caused by something changing early in the prompt between calls.

ghost_llm_calls tells you how many model calls the turn took. A simple question that made eight calls is doing more work than you asked for.

One turn takes forever

Watch the log panel in the web UI. A turn can use up to 40 passes through the tool loop, and something like deep research legitimately takes minutes because every page is fetched over Tor. If it's stuck on the same tool repeatedly with the same result, that's a loop and Ghost's own guards should break it after three identical attempts.

A configured node stopped being used

Look at node_health on the health endpoint. A node that keeps failing gets its circuit breaker opened and is taken out of rotation. The most common cause is an address that moved — point node flags at tailnet addresses or stable hostnames, not DHCP-assigned LAN IPs.

The answers are wrong

It claims it did something it didn't

This is the failure the self-check exists for. If it got through, check whether the answer was streamed — streamed replies are checked after they reach you, and the correction arrives at the top of the next reply rather than as an edit of the last one.

If it's happening often, confirm the check is actually running: --no-verifier disables it, and a critic node that's down means the check falls back to the main model, which is slower but should still run.

It answers a different question than the one asked

Tell it. Corrections are a strong signal — they mark the turn as failed and feed the background review. A correction needs a recognisable correction phrase and real overlap with your previous message, so "no, I asked for the file paths, not the counts" registers where a fresh unrelated question doesn't.

It got worse after learning something

A bad lesson can get recorded. Ask to see the lessons ("show me what you've learned this week") and have it drop the offending one. Ghost also removes lessons on its own when the answer that produced them is later refused by the self-check.

Reading the log

The log is the primary debugging tool here, and it's built to be read by a person rather than parsed by one. Almost every question on this page is answered faster by looking at it than by guessing.

There are two of them, and they're for different jobs

The live stream
What the agent prints as it works — boxed per request, colour-coded, one icon per subsystem. This is for watching. The web UI shows it in a panel beside the conversation, which is the easiest way to see it. If you run Ghost under a service manager, that manager captures it (with launchd, whatever you set as StandardOutPath).
The durable file
$GHOST_HOME/system/ghost-agent.log. Same events, one line each, timestamped and with a log level. This is for grepping — after the fact, when you know roughly what you're looking for.

What one request looks like

A request is framed top and bottom, so you can always see where one ends and the next begins. This is a real turn — asking for the weather, which makes the agent call a tool and then check its own answer:

Reading a line left to right:

PartMeans
11A short tag for this request, repeated on every line and given its own colour. When two requests overlap, this is how you tell their lines apart.
1165839cThe full request id, on the opening frame only. Grep the durable file for this to pull one turn out of everything.
🧩Which subsystem produced the line. One glyph per subsystem, deliberately all distinct.
+7.78sElapsed since this request started — not wall-clock. This is what you read to find where the time went.
thinkingA short fixed label, aligned into a column so you can scan down it.
the restThe detail, wrapped and indented to stay inside the column.

In that turn the useful reading is the timing: 7.8 seconds of thinking before the tool call, the tool itself returning in 10 milliseconds, and then 14 seconds waiting on the verifier. If this felt slow, the model and the self-check are the cost — not the weather lookup.

A warning, and why they're worth reading

Warnings are deliberately rare, so when one appears it usually says something real. This one is from the same session:

│  48  🔶  +37.1s  agent               Verifier escalation OVERTURNED a cheap-judge refute:
                                       main model says CONFIRMED. Original issues:
                                       Memory usage is 90.7%, not 91%.
│  48  🧪  +37.1s  verifier            CONFIRMED (95%) — All suspects are false alarms; claim…

Read that as: the cheap judge rejected the answer for rounding 90.7% to 91%, the main model was asked to re-examine, and it overruled the rejection. Nothing is broken — but this is exactly the line that tells you the cheap judge is being too strict, which is worth knowing before you trust its refusals.

Grepping the durable file

The file has one line per event, so ordinary tools work:

# everything from one request
grep 1165839c "$GHOST_HOME/system/ghost-agent.log"

# just the warnings and errors
grep -E "WARNING|ERROR" "$GHOST_HOME/system/ghost-agent.log" | tail -40

# how did recent turns end?
grep "turn outcome" "$GHOST_HOME/system/ghost-agent.log" | tail -20

# did the background loop do anything last night?
grep "\[SYSTEM\]" "$GHOST_HOME/system/ghost-agent.log" | tail -40

Lines in that file look like this — same events, flattened for grep:

2026-08-04 19:35:16 - GhostStream - INFO  - [1165839c +0.08s] llm request — Turn 1 | Temp 0.20
2026-08-04 19:35:24 - GhostStream - DEBUG - [1165839c +7.78s] thinking — The user is asking for the…
2026-08-04 19:35:24 - GhostStream - INFO  - [1165839c +7.79s] system weather — Location: Reykjavik
2026-08-04 20:10:41 - GhostStream - INFO  - [SYSTEM] hippocampus — Waking up to process 1 buffered memories...

[SYSTEM] in place of a request id means the agent did that on its own — background work, not something you asked for. Filtering on it is the quickest way to see what the idle loop has been doing.

The log is redacted by default. Secrets, API keys, .onion addresses, home directory paths and personal details are masked in both sinks, because the log is the thing you leave on screen. If you're chasing a bug and need to see the raw content, --no-redact-logs turns it off — and should be turned back on afterwards.

Working out where to look

  1. Is it up and healthy?

    /api/health — the two fields at the top of this page.

  2. What is it doing right now?

    The live log, in the web UI panel or $GHOST_HOME/system/ghost-agent.log.

  3. What has it been doing?

    Ask it: "what did you do while I was away?" That reads the real background activity ledger.

  4. Is the learning machinery alive?

    Ask it: "is your learning working?" That reports whether the background passes are actually running and succeeding, which absence of errors will not tell you.

  5. What does it think is broken about itself?

    Ask for the post-mortem queue, if you have --postmortem on.

A useful habit: when a subsystem seems to have stopped, check that it's running before you debug what it's doing. The characteristic bug in a system like this isn't a wrong answer — it's a component that silently stopped being called, which looks exactly like a component with nothing to do.
