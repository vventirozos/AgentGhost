Safety and privacy

Three boundaries: what reaches the internet, what reaches your filesystem, and who can reach Ghost. Each one is enforced by a mechanism, not by a promise.

What leaves your machine

Start with the honest version of the answer, because "nothing leaves your machine" would be a lie:

TrafficGoes whereNotes
Your conversations Nowhere Stored as files under $GHOST_HOME. Never uploaded.
Model inference Your LLM server Usually 127.0.0.1. It doesn't cross a network boundary unless you put the model on another machine yourself.
Web search and page fetches Tor Including DNS — hostnames are resolved by the Tor exit, so your own DNS server never sees what you looked at.
Weather and location lookups Tor Same path as any other fetch.
Sandbox network access Tor When the container has network access at all.
Extra LLM machines you configured Your LAN Direct, on purpose. LAN traffic doesn't deanonymise anything.
Push notifications, if you set one up Depends A LAN or tailnet target is reached directly. A public target only ever over Tor, and skipped entirely if Tor is down.

There is no vendor account anywhere in this list. Ghost holds no API keys for third-party services and has no ability to authenticate as you to anything. Search runs against scrapers over Tor rather than a keyed search API — which costs some result quality, and is a deliberate trade.

How "everything goes through Tor" is actually enforced

Asking every tool nicely to use the proxy doesn't work — one helper that forgets, and you have a silent cleartext leak that looks identical to working. So there are two mechanisms.

  1. At boot: a liveness probe

    Ghost checks that Tor is actually reachable before it finishes starting. If it isn't, Ghost refuses to start rather than starting in a state where the network tools would quietly fall back to direct connections.

  2. At runtime: a process-wide socket guard

    The outbound socket calls are patched for the life of the process. Any attempt to connect directly to a public address raises an error instead of connecting.

    Note what this does not block: loopback and LAN addresses are fine. That's not a hole — Tor traffic leaves via the local SOCKS proxy on 127.0.0.1, so from the socket layer's point of view all anonymised traffic is a loopback connection. The only thing the guard can see and block is a connection that bypassed Tor, which is exactly the leak worth blocking.

Both are on by default. Turn them off with --no-mandatory-tor or GHOST_MANDATORY_TOR=0.

The one time you need to turn it off. On a completely fresh install, the embedding model hasn't been downloaded yet — and the guard blocks that download, because it's a direct connection to a public host. Boot once with --no-mandatory-tor to let it cache, then run normally forever after. If your very first boot hangs or fails while loading the embedder, this is why.

Bounds on any single fetch

A hostile exit node or a slow server shouldn't be able to hang the agent or exhaust its memory. Every outbound fetch is capped:

5 MB
Maximum response body. Anything larger is refused or truncated.
20 seconds
Request timeout.
Private ranges refused
A fetch aimed at a loopback, private or link-local address is rejected before the request is made — so a tool call can't be turned into a scanner of your own network.

Changing Tor circuits

When a page fetch comes back 503, Ghost asks Tor for a fresh circuit and retries — a gateway rate-limit usually clears on a different exit node. 401 and 403 do not trigger this: those mean "you're not allowed", and a new exit node won't change that.

Search works differently. Each query rides its own circuit through per-query proxy isolation rather than burning the whole circuit, which is cheaper and doesn't serialise searches behind a rotation.

The sandbox

Every piece of code Ghost runs goes into a Docker container. The boundary is real, and it's worth understanding its shape because it explains several behaviours that otherwise look like bugs.

What the container can reach

  • One directory: $GHOST_HOME/sandbox, mounted as /workspace.
  • The internet, via Tor.
  • Services it started itself.

What it cannot

  • Any other part of your filesystem.
  • Processes you're running — it has its own PID namespace.
  • Your machine's localhost. The container's 127.0.0.1 is its own.

That last one surprises people. If you ask Ghost to check the app you're running on localhost:3000, it genuinely cannot — it will reach its own empty loopback instead. Ghost is told this explicitly and will ask you to restart your own services rather than pretending to.

Resource limits

Memory
4 GB by default. Change with GHOST_SANDBOX_MEM.
Processes
Capped at 1024, so a fork bomb takes down the container rather than the host.
Base image
python:3.11-slim-bookworm, with a cached provisioned image built after first use so later starts are fast.
The sandbox is not a security boundary against a determined attacker. It's a containment boundary against an agent that makes mistakes — which is the realistic threat when a language model is choosing the commands. Don't run Ghost as root, and don't mount anything into the sandbox that you'd mind losing.

Who can reach Ghost

Requests carry an X-Ghost-Key header matching your GHOST_API_KEY.

Bound to localhost, no key
Runs with auth disabled. Fine — only processes on your machine can reach it.
Bound to anything else, no key
Refuses to start. An unset key on a public bind is indistinguishable from a misconfiguration, so Ghost treats it as one. Pass --api-key '' if you genuinely want auth off on a trusted network.
Using the old default key
Ghost warns loudly. ghost-secret-123 was a hardcoded default in an early version and is publicly known — anyone who has read the source can use it.

The logs

Ghost's live log is designed to be watched, which historically made it the largest cleartext sink in the system — everything the agent handled scrolled past in the clear. So redaction is on by default: secrets, API keys, .onion addresses, home directory paths and personal details are masked in both the console stream and the log file.

Pass --no-redact-logs when you're debugging and need to see the raw content. Don't leave it on.

Sensible defaults, in one place

  • Run it as an ordinary user, never root.
  • Bind to 127.0.0.1 unless you actually need remote access — and if you do, use a tailnet rather than exposing the port.
  • Set a real GHOST_API_KEY, long and random.
  • Back up $GHOST_HOME. It's the whole agent, and nothing in it is recoverable from anywhere else.
  • Leave mandatory Tor and log redaction on.
