How it works

Long tasks

A research question that needs twenty pages, or a build that needs thirty edits and five test runs, is a different problem from a one-shot answer: the model cannot hold the whole plan, the clock is finite, and a stop in the middle must not lose the work. This page says what the system does about each (§4OD evaluation, §4OE changes, 2026-10-12).

The clock and the report

Every request has a time budget (GHOST_MAX_REQUEST_S, 30 minutes by default, 60 in production since §4RA; a client that sends its own timeout gets the lower of the two). A coding request gets more time while it is still writing code: within 15 minutes plus its report reserve of its deadline, if it made progress in the last 30 minutes, the deadline moves out 15 minutes at a time until it is clear again (the reserve is in the window because a slow model's reserve is larger than one step), up to GHOST_MAX_REQUEST_EXTENDED_S (180 minutes in production) and never past the client's own timeout; only a client that sent its timeout (the web interface) is extended. "Progress" is a successful write to a code file (including each part the system appends when it continues a cut write), or a run of a file the request wrote that the futility check counts as progress (fewer failures, more passes, or new output), once per rewrite of that file. The extension is earned whenever the deadline is read, so the report reserve, the preflight wait refusal, image waits and the write continuation all see the same deadline. Since §4SD (2026-10-29) there is no ceiling in production (GHOST_MAX_REQUEST_EXTENDED_S=inf): a build runs as long as it keeps writing code — overnight if it needs to — and stops only after a stall or the owner's cancel. The web page (streamed path) and the CLI both send X-Ghost-Client-Timeout: inf; the CLI used to send nothing, so its builds got the flat 60 minutes (req d886d047 was cut mid-build that way). The stall window is the larger of 30 minutes and this request's longest model turn plus one 15-minute step, so a long thinking turn is never mistaken for a stall; rewriting a file with the same content is not progress. While the model thinks the stream sends a keepalive every 30 seconds, so the web interface's timeout between bytes never ends a working build. The 27B at ~20 tokens a second spent 22–30 minutes on one 44–78 KB web build, and the flat 30 minutes cut both larger builds mid-file (§4QZ). The edit-churn, futility and thinking-loop breakers still force the report on their own, and once the report is forced it stays forced (the deadline may still move, the tools stay off); a loop that keeps writing code successfully without tripping a breaker can ride the extensions to the ceiling. (Alternating errors, test counts or ports and pids are not progress; a file rewritten through execute content rather than file_system earns through neither arm.) After progress stops, a request can still run for up to 30 minutes plus a step plus its reserve before the report is forced. Runs earn only for .py, .sh, .js, .mjs and .ts files (the futility tracker's set); writes to the other code files earn by themselves. The last part of it is reserved for the report: when the reserve is reached, tools are switched off and the model is asked to say where the work stands and where the files are. The reserve used to be a fixed 300 seconds — smaller than a measured report turn — and, after §4OE, twice the longest reply so far. Since §4OG (2026-10-13) it is sized from what the report will actually cost: the forced report's 8k-token cap times one and a half (a retry is rarely a whole second report) divided by this request's slowest measured generation rate (the slowest reply of at least 150 tokens — 22 to 48 tokens a second on the owner's hardware), plus the longest tool batch the request has run, plus a minute; before a rate is known the §4OE sizing applies. Never less than 300 s and never more than a quarter of the budget, so on a 1800 s budget it is 300–450 s. Before each dispatch of a long tool (browser, research, execute, image) the loop also asks whether a batch as long as the longest one so far would run into the reserve, and refuses it with the deadline note instead of letting the batch tail eat the report. Under a client deadline page previews are capped at 16k characters (a 240 s request once spent half its time prefilling 65k-character previews). The reserve is written to the durable log ("Report Reserve") whenever it changes. The measure of this: forced reports that land before the client's timeout.

A report written as a file. Some models answer the report turn by writing the report into a file instead of into the reply. Before 2026-10-13 that write was discarded (tools are off on the report turn), the turn counted as "no answer", and the fallback shipped after the client had already closed. Now, when the report turn's reply is nothing but file writes or appends, the write runs through the ordinary dispatcher with every guard intact, once per request and only while a further turn exists; the next turn is told the file exists and answers in text with its download link. A write beside another tool call is still work, not a report, and is dropped as before. On the streamed path (the web interface's forced final) the same write runs through the file tool before the retry, and the retry is told the file exists; a write the file ledger did not see land (refused by the read-before-rewrite gate, or failed) gives the next turn the plain answer-now ask instead, so no link to a missing file is ever requested. The text the model wrote beside the file call ("Let me compile the findings…") is working narration and is not shipped. The fallback reply's file list now carries each file's download path. A reply that streams live can still carry the model's bare link (/api/download/servers.md for a file in a folder) before the record-side repair runs, so the download route itself resolves a bare file name to the one file of that name in the sandbox; an ambiguous or missing name is still "not found", and a member's downloads are unchanged.

The task state the system writes

Once a tool has run, every later turn of the request carries a TASK STATE block written by the system from the tool records — not by the model: the files this request wrote or edited (with the instruction to read or edit them rather than rewrite them from memory), the last failed command and its error, what ran, and (§4OG) how many code edits went to source files and how many to test files. When, after the last failing run, only test files were edited, the block says so and asks the model to state in its reply which test it changed and what it asserted before — 18 of 26 edits in the §4OF coding probe went to tests, and nothing had noticed. It is factual by construction: it is built with the same parsers the verifier uses, so it cannot name a file that was never written.

The link to give. (§4OI) The block ends with the exact download link of each file the request wrote: "To give the user one of these files, link it exactly like this (a website's own download page is not the file): [pg18.md](/api/download/…)". A census turn asked for "the download link" of a written file and got the vendor's download page. The link is built from the file tool's own sandbox-side path, under the project folder when the request is bound to a project, never doubled, and URL-encoded; the model's own spelling (/workspace/…) used to give a 404. Only whole links that fit the block's size are kept.

A page only loaded. (§4OJ) A page with a script or an inline handler, written or changed by this request, that no later browser click or interact exercised is named in the block: "Pages with scripts NOT exercised since their last change". It asks the model to click a control and check what changes before calling the page working, or to say plainly that it is untested. The §4OI calculator probe loaded its page once and then reported "all buttons functional". A failed click does not count as a test, and a change after a click needs a new one.

A file left unfinished. (§4OI) A file written in parts whose last part never arrived is named in the block ("Still being written in parts — …") and at the end of the reply, logged as "Unfinished File". A file deleted or renamed afterwards is followed or dropped, never reported as unfinished. The note is a system line, so it never counts as the delivered answer.

What survives a stop

If a turn ends because the budget ran out or a guard stopped it (or you pressed Stop on a non-streamed turn), the same facts are stored as the conversation's STATE OF WORK and shown to the model at the start of the next turn of that conversation ("the previous turn did not finish; it wrote these files; its last failure was…"). It is kept per conversation (the web interface, the CLI and the ClockworkPi client send a stable session id; the Slack bot sends one per thread or DM), only for the owner, expires after six hours, and (§4OG) is cleared only after a turn that actually showed it — a queued Stop, an early error or an unrelated quick question no longer destroys it unseen. Each persist, show and clear is a "State Of Work" line in the durable log. A finished turn stores nothing. A Stop pressed while the final answer streams persists it too (§4OH).

The fallback reply of a turn that produced no answer used to carry the last tool output only (700 characters of forty-nine fetched pages). It now carries the heads of every successful evidence-tool output, newest first, within a bound — what exists, so a "continue" can start from it.

The record of a delivered task

Two things wrote a false failure over a delivered long task (§4OF). The "same tool error three times" rule that marks a turn failed for the learning loop fired on a build that went green after three failing runs and on a research turn whose report was on disk after four blocked pages; since §4OG it yields when the turn delivered — its last execute exited clean, or the reply hands over a file this turn wrote. And the verifier judged a report written as a file on the reply's one-line summary (it refuted the report for "lacking the Sources section" the file had): the document files a turn wrote (.md, .txt, .html, .csv…) were then read back from disk into the judge's evidence, as code already was for the code lens. (The LLM judge itself has been off since §4OW, 2026-10-14; the mechanical checks that remain read the files on disk.)

What the reply carries

Text the model writes beside a tool call predates that tool's result, so it is working narration ("Two remaining fixes…"), not the answer. It used to be dropped from the non-streamed reply only for lookup batches; the §4OF coding reply therefore opened with five superseded status notes written beside file and execute calls. Since §4OG the text beside any batch except a memory write is recorded and dropped — whole paragraphs only, never the answer itself, and never when what remains would not stand on its own; text beside a work batch (a file write, a command, a task update) goes only when what remains is at least one and a half times as long as it.

On the web interface (§4OH) the streamed reply follows the same idea at the moment the final answer starts: every status note an earlier tool turn wrote, superseded by later turns, is left out of what streams; the note written beside the very last call stays unless it reads as a working beat ("Let me run the tests again"), because an answer is sometimes written there. Nothing is taken back afterwards, and the text you see is exactly the text stored. The notes still scroll by live while the agent works.

Sources a report did not open. When a request that fetched pages writes a report (.md, .txt, .html, .rst), the reply ends with a "Source check" line naming every link the request wrote into the file without opening it, read from the file as it finally stands — the model was told at write time and may have fixed it. A request that only rewrites earlier research fetches nothing and gets no such line (its sources came from an earlier request).

Guards on a long build

  • Read before you rewrite. A whole-file write over a file that exists is refused unless this request has seen it: a whole read, or ranged reads and chunked pages covering at least 80 % of its lines or bytes (§4OG — a three-line ranged read used to unlock a whole-file discard). The receipt carries the file's version: a file this request only read and then edited must be read again before a whole write (a write from the pre-edit view would discard the edit); a file this request wrote whole stays its own through its own edits, appends and replaces; a change by anything else — a script, another process — makes every receipt stale. Receipts are forgotten when the request ends (after the streamed drain for a streamed turn). New files and parts are never gated.
  • Futility means no progress, not churn. The breaker that stops "rewrite the same script, rerun it" counts a run against every code file the request wrote whenever the command runs a test suite (pytest, unittest, npm test, go test…) — §4OG; before, a run counted only when the command named a code file, and python -m pytest tests/ names none, so the §4OE progress term never ran. Progress is a falling failure count or a rising pass count against the previous run; two green suite runs in a row are never a stall (a green run with unchanged count-less output still is — the breaker's founding case); a converging loop is neither steered nor reported. When the 40-turn budget is reached while the last suite run improved on the one before and the deadline leaves room, the budget extends once by ten turns (the §4OE probe went green on turn 38 of 40). Since §4SD (operator 2026-10-29: "remove the tool turn limit") a request with a time budget — web, CLI, Slack, probes — has no turn count: its deadline (extended only while it writes code) and these breakers end it. Requests with no deadline (scheduled tasks, job wake-ups, bench, internal) keep the 40 turns and the one extension, because the count is their only bound; sub-agents and coding leaves keep their own counts.
  • Failing tests are named. The failure line the model sees after a pytest run names the failing tests (FAILED: tests/test_app.py::test_create, …), not just the summary count. A program's own output (a non-zero exit banner, a test-runner summary) is never booked as a transient failure on the word "timeout" inside a traceback or a test name (§4OG): only the sandbox's own unavailability, the execute tool's budget kill, or a network failure inside the program (pip over Tor, a git clone) count as transient there.
  • Buttons that call nothing. (§4OI) The top error class in the 2026-10-13 census was a page built and called "working" whose buttons called functions that did not exist (the webOS calculator's calcEval, calcInput). After a write, the closing part of a multi-part write, or an edit of an .html file, the result carries an advisory note naming every inline handler (onclick="fn(…)") whose function no script on the page defines globally. It is a note, never a failure. Pages that load a script from their own folder or a non-CDN host, or that create globals dynamically (Object.assign(window, …)), are not judged. Module scripts count only for their window.x = assignments. Comments, <pre>, <code>, <textarea> and <template> are skipped outside scripts, in one linear pass; text inside a script is never altered. Screened on 66 real pages: no false note, and it flags the census page.
  • The sandbox is described truthfully. Python 3.11 and the preinstalled packages are stated in the prompt (no pip install of what is already there; anything else can be installed over Tor, slowly), and the working directory is stated once: the project directory when a project is bound, else /workspace, the same for every command of a task — the §4OF continue turn ran pytest from a different directory than its first turn and hard-coded that directory into the tests.

Guards on a long research task

  • A page is read once. A request remembers every page and search it fetched; an identical fetch is answered from the earlier result without a Tor round trip. The memo is keyed by URL and operation (a navigate preview and an extract_text of the same page are different reads; the extract's selector and size are part of the key), a truncated preview is never memoised (the fuller read runs), and a declared failure — a 404, a bot challenge, a dead host — is remembered by URL so the same dead page is not fetched again this request (§4OG; four of four probes had re-fetched one).
  • Searches are budgeted. At twenty searches in one request the model is steered to open pages; at thirty no further search runs (one turn had run thirty-nine).
  • "Cited" means read. In a chat reply a URL that appeared in a search snippet stays citable (§4LH); a URL that appears nowhere is removed. A report written as a file (.md, .txt, .html, .rst) is checked at write time (§4OG): every URL in it that this request did not fetch with an OK result is listed back to the model in the write's result ("LINK CHECK: 2 URL(s) were NOT fetched successfully…") so it opens them or removes them — nothing is edited silently; the §4OF report cited a page the browser had answered 404 twice. When a long report is cut and continued by the system, every continuation round carries the list of sources the request read.
  • Download links are repaired. A link the model composed with its folder dropped (/api/download/report.md for probe/report.md) is rewritten to the one real file instead of answering 404.

What leaves the prompt

A file the request wrote is on disk; its body does not need to ride every later prompt. Once a write's result is in and the conversation passes 60 % of the context window, write bodies over 2,000 characters outside the last few messages are compacted in the history to the path and a short head (a 70 KB write used to stay verbatim until the emergency prune, which then dropped it whole). The compaction is applied to the message the model actually receives, on both the native and the inline tool-call lanes.

What is still true

The language model server's host-side prompt cache was off from §4OH (2026-10-13) to §4QV (2026-10-23): it saved the previous conversation on every switch — 10 to 50 seconds before the first token after a long task — and never once restored one. §4QV found why: the machine had 0.1 GB free (Apple's fseventsd held 25 GB, and 37 orphaned pylint workers held 20 GB of swap), so every save paged. With the memory back the cache is on again at 4 GiB (--cache-ram 4096 in the llama-server launcher): a vision call, another conversation or idle work no longer costs the owner's next turn a 30 s re-read — the state is restored in seconds (journal §4QV).

A task that needs more than the budget is split by the report: the model is told to say where the work stands, and the next turn resumes from the state of work. Nothing runs unattended for hours by itself; the autopilot steps while you are away are bounded (see checking and learning). The guards stop loops; they do not plan — the plan is the model's, restated to it by the task state.
