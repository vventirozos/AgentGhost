# sentiment-service

The sentiment of the owner's English messages, for the agent's mood (§4TW). It uses [twitter-roberta-base-sentiment-latest](https://huggingface.co/cardiffnlp/twitter-roberta-base-sentiment-latest) (negative / neutral / positive, 125M parameters), exported once to ONNX and run with onnxruntime on the worker node's CPU. A short message takes a few milliseconds there, and a 200-token one takes about 160 ms. The process holds about 870 MB.

Since 2026-11-12 (§4UH-warmth) it can also read the message's EMOTIONS with a second model, [roberta-base-go_emotions](https://huggingface.co/SamLowe/roberta-base-go_emotions) (28 labels, multi-label), loaded from `~/Data/AI/sentiment-service/emotions/` when that directory has a `model.onnx` (about 480 MB; the process then holds about 1.25 GB). The character's warmth dial reads them; the mood still reads only the three-way sentiment.

Since 2026-11-20 (§4VE) it can also read the message's INTENT — what it is doing (an instruction, a question, asking for advice, a greeting, a short reply, thanks, a correction, banter, confiding, venting) and whether it is urgent — with a third model, the zero-shot NLI classifier [deberta-v3-large-zeroshot-v2.0](https://huggingface.co/MoritzLaurer/deberta-v3-large-zeroshot-v2.0) (MIT; the `-base-` one is the runner-up when memory is short, and the code takes either). It is loaded from `~/Data/AI/sentiment-service/intent/` when that directory has a `model.onnx` (about 1.7 GB on disk; the process then holds about 2.1 GB more). See [The intent head](#the-intent-head).

The agent calls it from `selfhood/sentiment.py`, in the background, for owner messages only. A confident positive or negative score (0.85 or more) nudges the mood's pleasantness by ±0.08, and every score is journalled in `sentiment.jsonl` beside the mood journal. See `docs/algorithms/selfhood.html#sentiment`.

The model reads English only, and the service checks that before classifying. A message whose letters are less than 70 % Latin (Greek letters) answers `unknown`, and so does one with fewer than two letters. Then fastText's language identifier [lid.176](https://fasttext.cc/docs/en/language-identification.html) must name English first at 0.4 or more: Greek typed in Latin letters fails here (`not English`), and so does a word it does not know, which gets a flat prior of 0.12 (`language unclear`).

## Set up

onnxruntime publishes no wheels for Python 3.15, so the venv uses 3.10.

```
S=~/Data/AI/sentiment-service; mkdir -p "$S/app"
python3.10 -m venv "$S/venv" && "$S/venv/bin/pip" install onnxruntime tokenizers numpy fasttext-wheel
mkdir -p "$S/langid" && curl -sSL -o "$S/langid/lid.176.ftz" https://dl.fbaipublicfiles.com/fasttext/supervised-models/lid.176.ftz
```

fasttext-wheel's `predict` fails under numpy 2, so the service calls the extension's own predict.

The model repository has no ONNX file, so export it once in a throwaway venv, the only step that needs the internet:

```
python3.10 -m venv /tmp/sent-export && /tmp/sent-export/bin/pip install torch transformers onnx onnxscript
/tmp/sent-export/bin/python deploy/export_model.py "$S/model"
rm -rf /tmp/sent-export
```

`deploy/export_model.py` loads the model with `AutoModelForSequenceClassification`, saves the tokenizer and `labels.json` (the `id2label` order), runs `torch.onnx.export` with inputs `input_ids` and `attention_mask`, output `logits`, dynamic batch and sequence axes, opset 17, and writes `parity.json`: three sample texts and the original model's probabilities for them. The service checks the ONNX model against those at start and refuses to run if any probability differs by more than 0.01. An int8 quantized copy was 3 times faster and shifted probabilities by up to 0.06, so the fp32 export is the one in use.

The emotion model is exported the same way, in the same throwaway venv: `/tmp/sent-export/bin/python deploy/export_emotions.py "$S/emotions"`. The service loads it if the directory is there (`--emotions-dir`), and checks its sigmoid parity file at start.

Copy `sentiment_service.py` to `app/` and `deploy/start-sentiment-service.sh` to `$S/`. Fill `__USER__` and `__HOME__` in `deploy/com.local.sentiment-service.plist`, install it to `/Library/LaunchDaemons/` owned by root, then run `sudo launchctl bootstrap system /Library/LaunchDaemons/com.local.sentiment-service.plist`.

On the agent host, put the same key in `~/Data/AI/.sentiment_service_key` and start the agent with `--sentiment-url http://<service tailnet address>:8097` (or export `GHOST_SENTIMENT_URL`; the flag wins).

## Run it

```
sudo launchctl print system/com.local.sentiment-service
sudo launchctl kickstart -k system/com.local.sentiment-service
```

## API

- `GET /health` answers `{"ok": true}`, without a key. The SENTIMENT model (and the emotion model, when present) is loaded and has passed its parity check before the port opens; the intent model loads after it opens, so `/health` says nothing about it (read the startup log line).
- `POST /classify` with header `X-Sentiment-Service-Key` and body `{"text": "..."}` answers `{"ok": true, "label": "positive", "score": 0.95, "probs": {"negative": 0.01, "neutral": 0.04, "positive": 0.95}, "reason": ""}`, plus `"emotions": {"gratitude": 0.99, ...}` (each label at 0.05 or more) when the emotion model is loaded. `label` is `unknown`, with `probs` empty, when the text is not English (`reason: "not English"`), when the identifier is unsure (`"language unclear"`) or when it has no words (`"no words"`). Text is limited to 4000 characters, and the model reads the first 512 tokens.

  With the intent model loaded, the answer also carries `"intent": {"instruction": 0.0213, "question": 0.0412, ..., "venting": 0.0108}` — EVERY label of `intent.json`, each rounded to 4 decimals, with no minimum (the agent journals every score to fit its thresholds) — and `"urgent": 0.1834`. Both are absent when the model is absent, still loading, failed to load, failed, ran past its budget or was still busy with an earlier message, and for every `unknown` answer (the language gate's answer is exactly what it was before).

## The intent head

The message is the premise and each label is a hypothesis, `intent.json`'s `template` ("This example is {}") with the label's phrase in it. Each label's score is its own hypothesis's entailment probability — softmax over that pair's (entailment, not-entailment) logits — so the scores are independent, in [0, 1], and do not sum to 1. Urgency is softmax over the entailment logits of "This example is urgent." against "This example is not urgent.". Which logit is entailment comes from the model's `config.json` (`id2label`, any case), never from the code, and the model's output must have exactly that many classes and one row per hypothesis. This is how the 11-20 measurement scored it.

- **The labels file.** `deploy/intent_labels.json`, installed as `intent/intent.json`: `template`, `labels` ({label: phrase}, in answer order, 32 at most), `urgency` ([urgent phrase, not-urgent phrase]; leave it out and there is no `urgent`), `max_tokens` (256, as measured), `threads` and `spinning`. The wording is re-tuned by editing it and restarting the service. The agent drops the whole `intent` field for a label it does not know (`selfhood/intent.py` `LABELS`).
- **Threads — an explicit choice.** `intent.json` ships `"threads": 4, "spinning": false`: the model runs on 4 cores and its threads sleep between runs, so llama-server on the same machine keeps the rest. The measured 620 ms median / 980 ms p90 was at onnxruntime's DEFAULT (`"threads": 0` = one thread per core, spinning), which is fastest alone but takes every core while it runs; 4 threads is slower by an amount nobody has measured yet. Step 6 below measures 2, 4 and the default; put the chosen count in `intent.json`. Without a `threads` key the service's `--threads` (2) is used; `--intent-threads N` overrides the file.
- **One run, a hard time bound.** The twelve hypotheses go through one onnxruntime run; only the premise is cut to fit `max_tokens`, never the hypothesis. The run comes LAST, after the sentiment and emotion models, in a worker thread; the request waits for it at most until 2 s after the request arrived (`--intent-budget`), then answers without `intent`/`urgent` and asks onnxruntime to terminate the run (it stops using the CPU; measured to stop within 42 ms). The late run writes only into its own result, which nobody reads any more. One run at a time: a request that arrives while a run is still going (a late one included) waits for it within its OWN budget and then runs with what is left; if the wait takes the whole budget, or leaves less than 50 ms, it goes without the intent and logs `intent skipped: …` once at WARNING. The agent's client allows 3 s per stage and 5 s in all, so a slow model costs at most the budget and never the sentiment; the agent's reply waits 1.5 s for the reading, and a later answer still reaches its journal.
- **Loading.** It loads in a background thread AFTER the port opens, so sentiment answers carry no `intent` until it is ready. A missing or broken directory, a load error or a failed parity check logs one line and the service answers as before. A good load logs `intent model: loaded <name> in <s> s (10 labels + urgency, parity n/13, <threads> threads, peak memory <MB> MB, requests stalled up to <ms> ms by the load)` and writes `intent/.loaded-ok`.
- **The load stalls the other requests.** onnxruntime holds Python's interpreter lock for much of a session's creation (a synthetic test: 0.53 s of a 0.61 s load), so a sentiment request that arrives during the load waits. The "stalled up to" number in the startup line, and in `--check-intent`, is that wait. If it comes close to the agent's 3 s read timeout, the choices are: load the intent model BEFORE the port opens (the service then answers nothing for the load's duration, and the agent's client pauses after three failed calls and retries by itself), or load it in a separate process (not built).
- **Kills, crashes and requested stops.** `intent/.inuse` exists while a process loads or holds the model. A requested stop (SIGTERM from `launchctl kickstart -k`, stop or a reboot; SIGINT) removes it before exiting. The marker holds the owner's pid: if that process is still running (a second instance on the same `--intent-dir`, e.g. a manual debug run on another port), the new process logs `another instance (pid N) is using …` at WARNING, records no death, leaves the marker alone and loads WITHOUT the guard. Otherwise a start that finds it left behind counts a death in `intent/.deaths`: the last process was killed (for memory, or `kill -9`) or crashed while loading OR while serving with the model. Two deaths within an hour and the start goes without the intent head, logging `INTENT MODEL NOT LOADED` at ERROR — once, at that start. There is no retry inside a running process: once two deaths switch the head off, only a restart after the hour (or deleting `.deaths` and restarting) brings it back. A death dated after "now" (the clock set back) counts as expired. Limits: a death is seen only at the NEXT start (one crash loop costs two reloads before it stops); any unrequested end counts, a crash that has nothing to do with the intent model included; and if `.inuse` cannot be written the guard is off (logged at WARNING) and a machine short of memory may restart the service forever.
- **The parity check.** `deploy/intent_parity.json`, installed as `intent/parity.json`: 13 made-up sentences (the 11-20 measurement's own probe sentences, not anyone's messages). Each passes when its `high` label's OWN score is 0.5 or more, its `low` label (a clearly unrelated one) scores under 0.5, and, where `urgent` is given, the urgency is on that side of 0.5 — not "top", because the scores are independent and a correct model often scores `reply` above the expected label. 9 of 13 must pass. Measured with the real models (torch): large 13/13 (lowest high 0.84, highest low 0.02), base 12/13; a swapped entailment index makes every score its complement and passes 0/13, and flat scores (a broken tokenizer) pass 0/13. Relabel `intent.json` and the parity file must follow, or the head refuses to load.
- **The log** adds the top intent label to the `classified:` line, never the text.

### Install, check, roll back

On the service machine (nova), with the model already in its Hugging Face cache (`~/Data/AI/intent-models/hf/hub/models--MoritzLaurer--deberta-v3-large-zeroshot-v2.0/snapshots/<revision>/onnx/model.onnx`):

Run every step as the service's own user (the `UserName` in the launchd plist), never with `sudo`, except the `launchctl` commands: root-owned files in `intent/` make the markers unwritable, which switches the kill guard off (one WARNING line, then silence).

1. Copy the new `sentiment_service.py` to `~/Data/AI/sentiment-service/app/` (the install script validates with its rules and refuses an older one). The running service keeps its old code until step 7.
2. Copy `deploy/install_intent.py`, `deploy/intent_labels.json` and `deploy/intent_parity.json` together into one directory, e.g. `~/Data/AI/sentiment-service/deploy/`: the script reads the two JSON files from beside itself.
3. Install, as the service's user and NOT with sudo: `cd ~/Data/AI/sentiment-service/deploy && ~/Data/AI/sentiment-service/venv/bin/python install_intent.py` (add `--repo MoritzLaurer/deberta-v3-base-zeroshot-v2.0` for the base model; `--snapshot <dir>` if the cache holds several revisions). It checks the labels file, the parity file and the model's config with the service's own rules BEFORE moving anything, builds `intent.new/`, moves the current `intent/` (if any) to `intent.prev-<time>/` and the new one into place. `model.onnx` is a HARD LINK to the cache's blob when they are on the same disk (no second 1.7 GB on disk; deleting the cache later does not delete it), a copy otherwise; the script says which. The newest 3 previous installs are kept, and the newest one the service ever loaded (`.loaded-ok`) is never deleted.
4. Check free memory: the check in step 5 loads a SECOND copy of the model (about 2.1 GB; the settings run one after another in one process, and the memory of an earlier one is not always returned) beside the running service and llama-server. Go on only with at least 4 GB available: `vm_stat | awk '/page size of/ {ps=$8} /^Pages (free|inactive|speculative)/ {n+=$NF} END {printf "%.1f GB available\n", n*ps/1e9}'` (and `memory_pressure | tail -1` should not be falling). With less, measure one setting at a time (`--intent-threads 4`).
5. Check the install: `~/Data/AI/sentiment-service/venv/bin/python ~/Data/AI/sentiment-service/app/sentiment_service.py --check-intent --intent-threads 2,4,0`. For each thread count (0 = onnxruntime's default) it prints the load time, how long a request arriving during the load would have waited, every parity sample (pass/FAIL with its two scores), the latency of short messages (median, p90, max) and of one cut to 256 tokens, and the peak memory. It exits 1 if the model does not load or fails parity. It never touches the live service's markers. The numbers are measured while competing with the live service and llama-server for the cores — that is the real condition, but the default (all cores) setting suffers most from it, so a quiet moment gives the fairest comparison. Memory is printed as "resident now" (after that setting's load) and "process peak so far" (which includes the settings measured before it).
6. Choose the thread count: the smallest one whose p90 is well inside the 2 s budget (the answer also holds the sentiment and emotion models' time), and write it into `~/Data/AI/sentiment-service/intent/intent.json`'s `"threads"` (and into `deploy/intent_labels.json` in the tree, so the next install keeps it).
7. Restart, when no request is in flight for THIS service: `tail -3 ~/Data/AI/Logs/sentiment-service.log` shows no `classified:` line in the last few seconds (the agent sends one request per owner message, each answered within the budget). Then `sudo launchctl kickstart -k system/com.local.sentiment-service`. A restart requested WHILE the intent model is loading is delayed: the stop handler runs only when the load's session creation releases the interpreter lock (measured), so the process may take as long as the remaining load to exit. launchd waits `ExitTimeOut` (30 s in the plist) and then sends SIGKILL — which the next start counts as a DEATH. So do not restart within a load's duration (the load time is in the startup line) of the last start.
8. Read `~/Data/AI/Logs/sentiment-service.log`: `listening on …`, then `intent model: loaded deberta-v3-large-zeroshot-v2.0 in … s (… parity n/13, … threads, peak memory … MB, requests stalled up to … ms by the load)`. A `not loaded` or `INTENT MODEL NOT LOADED` line says why.
9. Ask it (a made-up message): `curl -s -H "X-Sentiment-Service-Key: $(cat ~/Data/AI/.sentiment_service_key)" -d '{"text": "thanks, that was really helpful"}' http://<tailnet address>:8097/classify` — the answer carries `intent` with all ten labels and `urgent`. Time it with `time curl …` for a short and a ~3000-character message; memory of the service itself (not of a check run): `ps -o pid=,rss=,command= -p "$(pgrep -d, -f 'sentiment_service.py --host')"` (rss in KB). Over the next days, `grep -c "intent dropped\|intent skipped" ~/Data/AI/Logs/sentiment-service.log` counts the answers that went without it.
10. Roll back, if needed: `cd ~/Data/AI/sentiment-service/deploy && ~/Data/AI/sentiment-service/venv/bin/python install_intent.py --rollback` moves `intent/` to `intent.rejected-<time>/` and the newest `intent.prev-*` to `intent/` (`--list` shows them; `--rollback intent.prev-<time>` picks one, given as a bare name or a path; the source is checked BEFORE anything moves, so a bad name changes nothing), clearing the run-time markers; then kickstart as in step 7. By hand it is two steps — `mv ~/Data/AI/sentiment-service/intent ~/Data/AI/sentiment-service/intent.rejected-$(date +%Y%m%d-%H%M%S)` then `mv ~/Data/AI/sentiment-service/intent.prev-<time> ~/Data/AI/sentiment-service/intent` (a plain `mv intent.prev-<time> intent` while `intent/` exists would put it INSIDE). To switch the head off entirely, do only the first `mv`: without `intent/model.onnx` the service answers as it did before.
